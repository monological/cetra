# The UI

The retained UI: elements, layout, focus and keys, the text field, the code editor and its vim mode, the text it edits, and the text rendering under all of it.

## Modules

### `text.c/h`

SDF text rendering (stb_truetype) with glow. A `Font` states its em (`em_size`) and its field's edge and falloff (`sdf_edge`, `sdf_falloff`) since spec 14.0, the edge half a code under stb's on-edge value because stb truncates each texel to its byte. The atlas is built once at load and holds printable ASCII, Latin-1, Greek and a short list of symbols (spec 14.2: dashes, curly quotes, the ellipsis, arrows, the minus, Ω, ∞, ≈, ≠, ≤, ≥), less any the font lacks; its UVs are divided only once the last glyph is placed. **Since 14.3 every glyph's distance field is rasterised across threads before any is packed**, and the packing stays serial, so the atlas is the same to the byte (157 ms to 33 for Roboto at 64). **And the font keeps its kerning as a TABLE** (`Font.kern_pairs`, by each glyph's `pair_row`), every pair of its atlas's glyphs, a glyph's row built in the same band as its field and only read after, so the canvas's edit threads read it safely: asking stb at each step was three quarters of a text walk. Each entry is stb's own answer, so no pixel moved; a pair the atlas does not hold still asks stb, and a face with no kerning keeps no table. The glyphs under U+0100 are found by codepoint without the hash (`glyph_latin`), which a text walk and the kerning both ask. **A text layout steps a PEN** (`font_pen_step` over a `FontPen`, spec 14.3): the one advance rule, each character's glyph looked up once and the kerning read from the glyph before and this one, so the UI's walk and the canvas's layout cannot space a string differently; a caller passes only characters, and a change of face starts the pen afresh. Its common case -- a character under U+0100 after one of the same face, read from the table -- is a branch of its own that makes no call, and the rare paths are `noinline`: inlined, they made every character save eight registers and a walk took a fifth longer. `font_kern_advance` stays for a single pair. `font_advance` spaces a character it does not hold, and the UI draws one as an outlined box. **UTF-8 has one home here** (spec 14.3), and a codepoint is a `uint32_t` throughout cetra, stb_truetype's `int` met only inside this file: `text_utf8_next` and `text_utf8_prev` (its exact mirror, malformed bytes included), `text_utf8_encode` and `text_utf8_is_continuation`. What is no character is refused both ways -- a surrogate, a value past U+10FFFF -- and decoding, so are overlong forms, the lead bytes C0, C1 and F5 to FF, and a sequence cut short: each such byte is one U+FFFD, so malformed text never swallows the character after it. **A font is made from a file or from its BYTES** (`load_font_memory`, spec 14.6: a font built into the program, by `cetra_embed_files`), through one maker that keeps the buffer it is given, since stb_truetype reads it for as long as the font lives: a path hands it what it read, bytes a copy. The pool keeps either under its name, a path or the name given; the same bytes make the same font to the byte, its atlas and its kerning table included (`canvas-font-memory`)

### `ui.c/h`

The game UI layer (spec 12.2): a RETAINED tree of elements over a two-pass box layout, a geometric focus model, and a theme whose every zero means "inherit". The element list is CLOSED -- panel, label, button, toggle, slider, selector, since spec 14.2 the scrolling pane and the text field, and since 14.4 the code editor -- and three escape hatches sit under it, each keeping strictly more than the last: `ui_set_draw` keeps layout, focus and input while the app paints, and a panel taking the keys its focus border; `ui_set_element_program` keeps all of that and swaps only the fragment stage; the draw-list primitives take neither. An app's fragment stage is built over the UI's own vertex stage by `create_ui_draw_program` (spec 13.43), so no app restates the UI's vertex layout. Everything is in WINDOW POINTS, top-left origin, +Y down -- the space `text.c`'s ortho and GLFW's cursor already agree on, and deliberately not the engine's `InputState` space. `ui_layout` takes no GL, no clock and no input, which is what lets the `ui` group's arms assert a menu with no GPU. **Since 14.2 it runs ONE AXIS AT A TIME** -- widths (measure, arrange), then line breaks, then heights -- which is what lets a label with `wrap` take its height from the width it was given; widths never depended on heights, so every earlier tree lays out to the same floats. **Every element with text keeps its lines** (`UILines`, since 14.3): a label with `wrap` at its width, any other at its '\n's alone, which its height counts; and its widest line and longest word with them, the measure its width takes, until its text or runs change or its face, size or tracking do -- a wrapping label's lines also until its width does. Every element draws its text through them, so a control's height and its text agree: a button's, a toggle's and a selector's rows centred in it, a slider's at its top with its track below them. A FIXED axis measures no content, since its size is its own. **`max_size` (spec 14.3) is the most an element measures along each axis**, 0 none, for FIT and GROW alike: a pane held at its most scrolls, and a GROW child held at its most leaves its room to the siblings still growing, shared again round by round, with what is left after that placed by `align_main` rather than left as a gap; across the axis a stretched child is clamped before the cross alignment places it. **`UI_SHARE` (spec 14.9) is a size as a share of the parent**, `size[axis]` from 0 to 1: of the inner length less the gaps between the children along the parent's main axis, of the inner length across it, rounded down to a whole point so the edge it puts down draws sharp. It is settled before GROW, so a split is a SHARE side and a GROW side and the second takes exactly the rest whatever it measures -- which a weight on GROW, the roadmap's first idea, would miss by the gap a nested split measures. A SHARE axis measures 0, so a FIT parent is the size of its other children and the share is of what it comes to; every layout without one is the same arithmetic in the same order as before it. **`UI_ALIGN_BASELINE` (spec 14.13) lines a row's children up by their text**, as a row's `align_cross`: each child with a baseline moved down until its first line stands on the deepest one's, and the row as tall as its lowest child then reaches. A label's baseline is its top padding and its face's ascent; a row on the baseline's, its line; any other panel's, its first child's where that child stands in it. A control, a field, an editor, a scrolling pane, a column that centres or ends its children and an element with no text have none and stand at the top, as does a child stretched across the row. **Each element keeps its baseline** (`UIElement.baseline`), set as the measure finishes its height, its children's first, so the arrange reads what the measure found and rows on the baseline nest at one walk a layout: asked live, a row asked its first child three times, and nesting cost three to the power of its depth. **A label draws its text inside its padding** (14.13): its height and its breaks counted the padding while its lines were drawn from its rect's corner, so every label's text sat its top padding high, 4 points by default, and anything centred beside it sat 4 points low. A label or a read-only field takes styled runs (`UITextRun`, `ui_set_text_runs`): a byte range with its own colour and face, in the element's size and line, refused by name out of order, overlapping or splitting a codepoint, and cleared by setting the text. Four things about the rest are easy to get backwards. **A pane's rects stay window positions**: `ui_scroll`'s children are arranged at their full height from its top less its scroll, clipped in the emit, hit only where it shows them; a GROWING pane measures as its padding down the axis it scrolls, since its FIT height is its content and asked of a parent it came out 9,890 points tall. **VIRTUAL ROWS are built and freed INSIDE `ui_layout`** (`ui_scroll_set_rows`): the rows in view, one either side and the one holding the focus, from where the last layout left the scroll, so `ui_layout` runs again on what it built, three times at the most, and a screen with no rows lays out once. A built row's height is taken at every layout and kept for when it is not built; a height changing above the first row ANY of which shows moves the scroll with it -- not above the row at the scroll, which counts the gap after a row as that row's. The rows in view where the pane is easing to are built too, so a focus moved on faster than the scroll finds its rows. A built row is reached with `ui_scroll_find_row` (14.3), NULL while it is not built and valid until the next layout, so an app changes one in place -- appending to a streamed message -- rather than rebuilding it with `ui_scroll_rows_changed`. **The pointer passing over no longer takes a text field's focus**, a press does, and a press on nothing in a screen that is not modal lets go; `ui_wants_keyboard` is what an app asks before taking a key. **A pass's keys go ONE AT A TIME to the focus at their turn** (`_route_keys`): the focused element's key hook first, then a focused field or editor (`UIInput.key_events`, which `ui_input_read` fills from the engine with the pointer, its press and release and their modifiers, the wheel and the clock, leaving `nav_*`, `accept` and `back` to the app's own bindings), and what neither uses -- Esc, Tab, a page key on one line -- to the screen, so a character after a Tab reaches where the Tab moved the focus, and the keys stop at a screen one of them closed. While what takes the keys holds the focus the `nav_*` and `accept` values are ignored, so an app mapping the arrows to navigation does not move the focus while typing; Esc closes a modal screen and lets go in one that is not. **An element the app focused takes none of that pass's keys**, which came before it had the focus, so an app opens a palette from its own key callback and the key that asked is not typed into it. The focused pane takes its FOCUS look while the focus is anywhere inside it. An element's `spacing` of 0 is the theme's and a negative one none, and since 14.3 its `padding` the same, side by side. `ui_set_text` on a field is refused by name: a field's text is `ui_field_set_text` and its hint `ui_field_set_placeholder`. **Since 14.6 an element is taken out with `ui_remove(el)` and moved with `ui_move(el, parent, before)`**, which is all a host's panes need: a split is a row put in front of the pane with the pane moved into it, a close a removal. `before` is the child of `parent` to go in front of, NULL the end, as the DOM's `insertBefore`: an index has to say whether it counts the children with the element among them, which its first shape got to be documented rather than right. Whatever the system or a screen held inside what goes -- the pressed element, a held bar, the focus last seen, a screen's focus -- is let go first (`_forget`, which a pane's rows share). **An element removed DURING a pass -- by its own action, or a key an editor took, as `:q` closes a pane -- is taken out at once and freed only as the pass ends**: `ui_layout`, the input pass and the build count themselves in `UISystem.passes`, since the pass goes on reading what removed it (the hovered element's state, the element taking keys); freed at once, closing a pane from its own key crashed the canvas app under scribbled memory. What waits is a list through the elements themselves (`removed_next`), so taking one out cannot fail for memory. A pane's dropped rows leave by the same path (`_leave`), so nothing is freed mid-pass however it goes. **An element knows its screen through its root** (`UIElement.screen`, set on a screen's root alone), and one taken out has none: that is what `ui_remove` refuses a second time, `ui_move` refuses to move and `ui_set_focus` refuses to focus, with an element of another screen. `ui_move` keeps everything the element holds, focus included. Both refuse a screen's root and a pane's virtual row, and `ui_move` a move out of or into a pane with rows or one of its rows, which the pane would free, into the element itself or under it, or to another screen. **A key something used takes its press's character with it** (`_route_keys`, since 14.6's review): a binding on Space types no space, and a split bound to `|` types no `|` into the pane it made, wherever the key moved the focus -- the character event straight after a used key that makes one is dropped there, in one place, whatever holds the focus at its turn. So a widget says it used a key only when it acted on it: the text field types a letter from its character and reports the letter's key as not used, or no field would type. **Since 14.10 a panel, a pane, a label or a field takes the keys through a hook** (`ui_set_on_key`, `UIElement.on_key`): a pane an app draws -- pcb's schematic -- is handed every key and every character while it holds the focus, before it acts on any, and takes the keys as a field does: the focus kept under a passing pointer, `ui_wants_keyboard` true, what the hook declines left to the screen, Tab and Esc among them. Characters, because a pane's keys are characters on any layout: `+` is Shift and `=` on one keyboard and a key of its own on another. A field's hook is the same call, asked about a character before the field types it. A code editor refuses one, its keys being its modes', and so do a button, a toggle, a slider and a selector: navigation and accept reach the UI apart from the keys (`nav_*`, `accept`), so a hook could not hand them back, and a control holding the keys would be neither pressed nor left. Every other toolkit lets a widget decline a key into navigation -- ImGui's key owners, Qt's and GTK's propagation, the responder chain -- and lifting the refusal wants navigation to come through the keys the same way. A hook does not make an element `focusable`, which a press needs. The pointer's press, drag and release ask whether an element has the widget table, not whether it takes the keys: a hooked panel has no field's press to call. An app that also maps Esc to `back` lets go of a pane whatever its hook does with the Esc key. **Since 14.11 a panel taking the keys is drawn FOCUSED**: `theme.panel` is per state, as `scroll` is, and its FOCUS look is the editor's border by default, drawn over a draw hook's painting too, so a pane an app draws -- pcb's schematic -- shows the keys are in it as the code editor does. A focusable panel with no key hook is not (`_state_of`): a list's row, which the focus follows the pointer over, would be outlined wherever the mouse is

### `ui_field.c/h`

The text field (spec 14.2): ImGui's copy of stb_textedit, compiled as C from this one file behind a block of five compatibility names (`ImS8`, `ImGuiDir_Left`/`_Right`, the `LastMoveDirectionLR` and `Stb` members, `IM_ASSERT`), run on a growing UTF-8 buffer. Single-line, multi-line growing to `max_rows` then scrolling inside itself, or read-only with runs; `max_rows` 0 is no most (14.3), and Page Up and Down page by the rows the field shows. The header is private: `ui.c` lays a field out, routes input to it and draws it through `ui_field_ops`, the table of calls it reaches the field and the code editor alike by (`ui_internal.h`, spec 14.4), so `ui.c` names neither kind but where it picks the table; the public calls are `ui_field_text`, `_set_text`, `_set_placeholder`, `_append` and `_set_on_change` in `ui.h`, its key hook being any element's (`ui_set_on_key`, 14.10). The placeholder is the field's own (14.3), drawn dim while it is empty, and never what it is sized by. **`ui_field_append` adds to the end without disturbing anything**: its runs counted from the start of what it adds, checked as `ui_set_text_runs` checks them and refused on an editable field; the caret, the selection, the scroll and undo kept, no `on_change`, and only the last line broken again (`ui_lines_break_from`). That is what lets a streamed reply grow word by word while a selection in it holds. Setting a field's runs breaks its rows again at once (`ui_field_runs_changed`), so an append made before the next layout cannot keep rows broken in the old faces. Four things about it are easy to get backwards. **stb's widths are the UI's own walk** (`ui_text.h`), so the caret stands where the glyph is drawn, to the pixel snap: a glyph's width is walked from the glyph itself, its advance and its pair with the next, and a row from the rows already broken -- from the row's start each was a walk of the row, and stb asks for every width along a row to place a click. **stb's undo records say what UNDO does**: a typed insert is a record that DELETES, its length in `delete_length`, and joining typing a word at a time reads that. **The keys are the platform's**: Cmd on macOS and Ctrl elsewhere for the shortcuts, Option or Ctrl for a word, Cmd+arrow to a line's or the text's end; the word moves, the word a double press takes, the paste cleaner, the double press and the blink are `ui_typing.c`'s since 14.4, shared with the code editor. **The blink is the wall clock's**, not the UI's `dt`, which idle mode keeps waits out of: the overlay sets `UISystem.now` and asks `engine_request_frame_after` for the caret's next change, so under idle the window wakes only for the blink; headless the caret does not blink, so a picture repeats and an idle run ends

### `fuzzy.c/h`

`fuzzy_match` (spec 14.2): whether a query's characters appear in a name in order, a score, and the byte offset of each matched character, in a `FuzzyPositions` that says how many it wrote (14.3) -- after fzf's second algorithm, the best placement by a dynamic program over a 32 by 256 table on the stack, not the first. A word's start, a turn into upper case, a run and the name's start score higher; gaps cost; ASCII letters match either case. It searches nothing: the app loops over its own list, sorts by the score and its own tie-break, and lights the positions with runs. No GL, no UI, no allocation

### `text_doc.c/h`

The code editor's TEXT (spec 14.4), kept apart from the editors showing it, as lite keeps its Doc and vis its Text: two editors of one text each keep their own carets and scroll, and an edit through either -- or the host's -- moves both. No GL and no UI. An ARRAY OF LINES, lite's shape, each pointing into the bytes the text was made from until it is first edited, so a 10 MB file opens with one copy and one scan (2 ms) and typing touches one line. **Positions are byte offsets from the file's start**, a line break its one or two bytes and a byte-order mark three, which is what pcb's splices hold; a line keeps its ending -- LF, CRLF, or none on the last -- apart from its content, so the bytes come back exactly, and a CR before an LF is the ending while any other is content, as pcb reads a file. Line starts are made good lazily from the first line an edit touched. Four things about it are easy to get backwards. **Every change is ONE replacement and `version` counts them**: an offset or a range held at an older version is brought forward through the last 4,096 (`text_doc_map`, `text_doc_set_ranges`) -- before a change it stays, after it moves by the length, inside the bytes replaced it goes to the end of the new ones, and a range keeps the new bytes outside it. That is how a host's colours from a parse a few keystrokes behind still land on the text they meant. **An action at several carets is applied from the highest start down**, so every change in it is in the action's starting coordinates, and `on_action` reports it so -- with the selections before and after, for a host's undo to restore. The editor making it says where its selections LAND rather than having them moved through each change, since a selection ending where the next one's replacement begins would be pushed past that one's new text; and the text is not changed from inside `on_action`, which is refused by name. Every change, an action's, an undo's or the host's, goes through one path. **The text keeps an undo of its own** (`keep_undo`, on by default), typing joined into words as the field's is, a moved caret sealing a step, for an app with no timeline; pcb turns it off and binds the keys to its own. **A step is PARTS since 14.5**, each an action's changes, undone last first and redone first first; `TextDocAction.step` is the serial the actions of one step share, so a host's timeline groups them as the text's own undo does. The private `text_doc_group(doc, open, view)` holds one step open across the actions of the editor `view` -- a vim command, an insert from `i` to Esc -- its `before` the view's selections as the group opened, and `text_doc_empty_step` keeps a step that changes nothing, as vim keeps one for an operator over nothing. **A step is joined only by the action straight after its last**: each keeps the text's version after its last action, so typing after keep_undo was off, or after another editor's edit, starts a step of its own rather than adding bytes to one that no longer ends where they begin. **The host's edits** (`text_doc_replace`, `text_doc_set_text`, which trims the unchanged ends to one replacement) are not reported back to it. **A text may be READ-ONLY since 14.7** (`TextDoc.read_only`, a setting): what a person does in an editor -- `text_doc_apply` with any edits, the editor's undo and redo -- is refused and told to `on_refused` (`text_doc_set_on_refused`, with the editor), once an action, while the host's edits, undo and redo go through, which is how pcb appends its messages. The private `text_doc_refuse` tells a refusal the text never saw, a vim command refused before it asked. The standard mode needed nothing: a refused action leaves the carets, and cut copies before it deletes. Colour comes two ways: a highlighter asked a LINE at a time (`text_doc_set_highlighter`), its spans kept, until the line changes, in a ring of the last 65,536 written -- a line whose spans were written over colours itself again when drawn, so letting colour go never walks the lines -- `stateful` for a language whose lines begin inside something an earlier one opened, and the host's RANGES in four layers. A text freed while an editor shows it leaves the editor showing nothing. **A view leaving a text** (`text_doc_remove_view`: an editor freed or shown another text, spec 14.6) **closes a group held to it** -- an insert a pane closed mid-way, the step kept as far as it got -- and seals the typing it was joining, since a view made later at its address must add to neither. The editor's half -- views, `text_doc_apply`, the line spans -- is the private `text_doc_edit.h`

### `glyph_cache.c/h`

The code editor's face as coverage BITMAPS made at the exact pixel size shown (spec 14.4), not the UI's distance fields, which go soft at the 12 to 14 pixels code is read at, worst on a 1x screen. Rasterised by stb_truetype as first asked for, packed in rows into one growing `GL_R8` atlas swizzled to white with the coverage as alpha, so the UI's textured quad draws a glyph in its tint with no shader of its own. A size is a pixel height as a `Font`'s is; the cell is the advance of `M` rounded to whole pixels, and the line height and ascent are rounded too, so every glyph lands on the grid it was made for. A new size or screen scale empties the atlas, whose texture is cleared at the next glyph asked for, so a size is set by the layout pass, which touches no GL. Its own object rather than a `Font`, since `load_font` keeps one font per path whatever size is asked. The face shipped for it is JetBrains Mono (`assets/fonts/`, with its OFL licence beside it). Made from a file or, since spec 14.6, from bytes built into the program (`create_glyph_cache_memory`), through one maker as a `Font` is

### `ui_editor.c/h`

The code EDITOR (spec 14.4), the ninth UI element (`ui_editor`, in `ui.h`), on a `TextDoc` it borrows, in the theme's `editor_face`. Its lines WRAP at its width -- after the last space that fits, at the edge for a word longer than a row, later rows hung at the line's indent -- and only the rows in view are wrapped and drawn; every other line's rows are a guess from its length, and **the scroll is held to a line and a row of it**, so a guess put right, or an edit above, never moves what is on screen. A line edited within itself is wrapped again at once, so typing moves no other line's rows; a BUDGET in each draw wraps the guessed rows, 192 KB a frame -- the lines an edit rewrote first, then any others round the text -- and walks a stateful highlighter on, its draw returning a wake of now while either has work, a drawn line came back uncoloured or the atlas grew mid-draw, which idle mode turns into the frames that finish them (at 10 MB: a keystroke 0.11 ms, at 100 carets 0.50, Enter at one 0.20 and at 100 6.5, a jump 0.12). Its geometry is settled by the layout pass and its scroll bar is the UI's own, the pane's, driven through the editor's scroll calls. **Several carets from the start**: the selections are a sorted list, merged where they meet, the last made the primary. **Keys are vis's three pieces**: a MOTION (where a caret goes), a TEXT OBJECT (the range round it -- a word, a line, the bracketed list), an OPERATOR (move, extend, select, delete, cut, copy, paste, indent), each at every caret (`ui_editor_motion`, `_object`, `_apply`). A MODE turns keys into them: a table of bindings to COMMANDS -- named and described, `ui_editor_commands` listing the editor's own for a host's command table -- a reader of its own for sequences like `d2w`, whether it types, and its caret's shape; a key it does not take falls to its PARENT. The standard mode (`ui_editor_standard_mode`) is the platform's keys, through `ui_typing.c`, and the vim mode (`ui_editor_vim.c`, 14.5) another; `ui-editor-mode` still builds a toy one from the public calls alone. A host binds its own commands -- pcb's undo, its view keys -- in a mode whose parent is either. **Four things about modes since 14.5 are easy to get backwards.** A mode may be a LAYER (`UIEditorMode.layer`): keys only, its typing, caret, selection shape and pointer hook those of the first mode up its chain that is not a layer, so a host's keys over the vim mode leave vim's state showing; `ui_editor_mode` still returns the mode set. A command that DECLINES hands its key to the parent, and only with no parent left to the screen, so a host's Space can act in normal mode and hand the key on in insert mode. A key a mode used takes its press's CHARACTER with it, dropped by `ui.c`'s key routing (above), so a binding on a printable key -- every letter of vim's normal mode -- types nothing. And a mode's `selection` SHAPE only draws its bands -- the span, INCLUSIVE of the far character (visual mode), whole LINES (visual line mode) -- while the mode decides what a command takes; its `pointer` hook is called after a press and a drag. Find is `ui_editor_find`, its matches lit in view. What `ui.c` calls on it is `ui_editor_ops` (`ui_internal.h`), what the vim mode reaches of it the private `ui_editor_internal.h` -- an edit at every caret as one action, carets with wanted columns, the rows in view and the scroll -- and what a test reads of it the private `ui_editor_hooks.h`. **Since 14.6 an editor is shown another text** with `ui_editor_set_doc`, and **it keeps its place in every text it has shown**, as a vim window keeps a buffer's: a text new to it starts as a new editor would -- one caret at 0, the view at the top, every line's rows a guess -- and one shown again comes back with its carets, their wanted columns, its view and its rows as it left them (`UIEditorPlace`, all of an editor that belongs to the text it shows). A place left is PARKED on its text as a view of it, so every edit made there since moves it as it moves an editor showing the text, the changed lines' rows made guesses; rows wrapped at other columns are guesses again on return. A text freed lets its parked places go. Its mode, find's query and its look are the editor's and are kept; the text it leaves forgets it as a view, an undo group held to it closed. The first shape put the place back on the host, which kept carets and a top with a version and mapped them through `text_doc_map` on return, and every host would have written that. **A place asked for before the editor is laid out on its text is held for that layout** (`ui_editor_scroll_place`, `ui_editor_reveal`), since only then are its rows and its height known: a pane made by a split is placed where the one it split was at its first layout. `ui_editor(parent, NULL)` makes an editor showing nothing, and `ui_editor_doc` says what one shows, so a host finds a pane's file from the pane. **Each text shown gives the editor a new SERIAL** (`ui_editor_serial`, private), never reused, which is how the vim mode knows another editor from the last it saw

### `ui_editor_vim.c/h`

The code editor's VIM MODE (spec 14.5), held to vim 9.2 itself: the `ui-vim-oracle` arm runs a corpus of 7,056 cases and `ui-vim-random` 1,600 seeded sequences of whole commands through the mode and through headless vim fed the same keys as typed, text and cursor compared byte for byte, CRLF, tabs and letters past ASCII among them; both skip without vim on the path. **ONE `UIEditorVim` per host, shared by its editors**, as vim's state is the person's and not the buffer's -- the mode, a half-typed command, the counts, the register, the last search, the last `f`/`t`, the last change for `.` -- while the selections stay each editor's own. Keys reaching another editor than the last let go of whatever was unfinished in that one -- a command, a line, an insert, a visual area -- its undo group forgotten rather than closed, since that editor and its text may be gone; the text keeps a group to the editor that opened it, and closes it when that editor leaves. **"Another editor" is compared by the editor's SERIAL since 14.6, never its address**: an editor freed and another made where it was -- which the allocator does, measured -- or one shown another text inherited a half-typed operator. Its base mode is `ui_editor_vim_mode`, under a host's layer if it has one; `ui_editor_vim_state` is NORMAL, INSERT, VISUAL, V-LINE or V-BLOCK and `_pending` the keys of an unfinished command, for a status line; `ui_editor_vim_keys` lists every key with a line of description, for a help screen. Keys are read from CHARACTERS (so `$` and `%` come as typed on any layout) and from key events (Esc, Enter, the arrows, the Ctrl keys). Normal, insert and the three visual modes: counts before and inside an operator, the motions, the operators over every motion and text object (words, brackets, quotes, paragraphs), the edits, `.`, a block's `I` and `A` at a caret on every line, search (`/ ? n N * #`, plain text, ignoring case unless a capital is typed, matches lit through `ui_editor_find` until `:noh`) and `:` (a line number, `$`, `noh`; anything else returns false and is the host's -- pcb's `:w`). **Undo goes by vim's units**: a command is one step and so is an insert from `i` to Esc, held by `text_doc_group`, and a host keeping its own timeline takes `u` and Ctrl+R through `ui_editor_vim_set_undo`. Four things about it are easy to get backwards. **The register is the system CLIPBOARD**, vim's `unnamedplus`, with vim's memory of whether it put whole lines or a block there, which holds only while the clipboard still holds that text: what another app copied pastes as characters. **The line for `/ ? :` is the host's when it sets a prompt** (`ui_editor_vim_set_prompt`), answered through `ui_editor_vim_search` or `_command`, NULL letting it go, and lit as it is typed through `ui_editor_vim_light`, which takes case as the search will; with none the mode reads the line from the keys itself and shows it through `_pending`, so any host has search with no code. **Esc in normal mode is always taken**: declined, it reached the screen, which let go of the editor, and vim users press it out of habit. **Its rules are vim's as measured, not as remembered**: dozens were found by the oracle -- an operator resetting the wanted column, a block yank filling a line too short to reach it with spaces, a `.` stopping where the change it makes again fails -- and where the tests guessed wrong, as with `i(` on an empty block, vim's own source decided. The differences left are listed in the spec. Not in 14.5: named registers, macros, marks, the jump list, `:s` and ranges, `R`, `gv`, Ctrl+A and Ctrl+X, completion, tag objects. A keystroke at 10 MB is 0.12 to 0.25 ms. **The keys that need the language ask the host since 14.9**, as vim asks its `tagfunc`, `keywordprg`, `indentexpr` and `formatexpr`, rather than a `:map` of the host's own. `ui_editor_vim_set_lookup`: `gd`, `gD`, Ctrl+] and `K` in normal mode with no operator, and Ctrl+] and `K` on a one-line visual area, which vim's `get_visual_text` alone accepts; the host reads the name from the editor and goes where it likes. With no host, or one finding nothing, `gd` and `gD` are vim's `find_decl` -- the identifier's first use in the block or the text, a use on a comment line or in a C comment or quotes passed over, none on the cursor's line -- and Ctrl+] and `K` do nothing. Under an operator `gd` is always characterwise exclusive, where vim's takes the kind of the motion before it, the one difference kept. `ui_editor_vim_set_indent` answers `=` for a whole run of lines at once -- a column each, worked down the run as vim's `indentexpr` is asked a line at a time, so `=` is one edit however many lines it takes -- and, as a run of one, the indent of every line `o`, `O` or Enter makes and every change of whole lines (vim's `fix_indent`); `ui_editor_vim_set_format` answers `gq` with the lines' new text. With no hook `=` and `gq` do nothing. `ui-vim-layout-oracle` holds both to vim sourcing `scripts/vim_layout.vim`, writable and read-only, the same two rules in C in the probe. **On a read-only text it is vim with `'nomodifiable'`** (spec 14.7), held to vim by `ui-vim-read-only-oracle`, the whole corpus run read-only: a command that would change the text is refused once, through `_refused`, before anything of it is done -- the register untouched, an operator's carets at its start, a visual area let go -- and only where it would do something: a `J` on the last line, an `r` past the line's end and a `~` on an empty line are beeped at, as vim beeps. **A refused command is what `.` makes again, as vim keeps it, and its CALLER keeps it**: the functions that refuse report it as made, so the keep is the one the writable path makes, a visual put's delete under it and a `3s`'s count, and a change takes the Esc its insert would have ended with. A refused `r` is kept for nothing, and normal mode's `i a I A o O` stay in normal mode and are not kept; a visual or block `I` or `A` begins its insert, where each character is refused, except a block `A` whose top line is short of the block, which vim must pad first and so refuses there. A block insert that puts nothing in, read-only or not, ends as any insert does, not at the block's corner, keeping the top line's padding; the writable corpus had no such case until 14.7

### `ui_typing.c/h`

The platform's editing conventions (spec 14.2, shared since 14.4), private: word classes and word moves (to a word's end on macOS, the next word's start elsewhere), the word round a point, a character stepped without reading past its run, the paste cleaner, and the state of a run of presses and of a caret's blink. The text field and the code editor both edit by these, so the two cannot drift

### `ui_draw.c`

The UI's own draw list: quads -- a whole picture or, since spec 13.43, a part of one (`ui_draw_textured_quad_uv`, the whole-picture quad being that quad over 0..1) -- 9-slice, rounded rects and SDF glyph runs batched by (texture, program, clip) into one vertex buffer, drawn as an engine overlay AFTER tone mapping -- so a menu is never graded, bloomed, grained or rescaled by `--render-scale`, and IS captured by a headless screenshot, which is what makes a menu golden possible. Reuses `Font` and `font_get_glyph` from `text.c` and nothing else of it: that file is one draw call per mesh, hardcodes its SDF constants and clobbers GL state rather than restoring it. **Since spec 14.2 every measure, break, caret and glyph comes from ONE walk** (`ui_text.h`, private: `UIText`, `ui_text_span_width`, `ui_text_pen`, `ui_text_break`, `ui_text_draw_span`), over UTF-8 and across styled runs, kerning stopping at a change of face: the per-glyph rule had been spelled out three times in this file and one copy had already drifted. `ui_lines_break` is the one line break, kept while the width and the style are unchanged, for a label's lines and a multi-line field's rows alike: the layout runs several times a frame, and a field broke its whole text again at every one and at every draw until the two shared it. `ui_lines_break_from` breaks again from one line on, for a text changed from there -- an edit from line 0, an append from its last -- and drops the measures; `ui_lines_measure` keeps an element's widest line and longest word under the same face, size and tracking; zeroed lines hold nothing; and at no width a line is found by its '\n' without a walk of its glyphs (spec 14.3). The draw list's OFFSET now moves the rounded-corner rect, the clips and `uRect` with the vertices, which a SLIDE transition had been getting wrong and a scrolled pane would have; `ui_draw_list_quad_count` and `ui_draw_list_quad` read the quads back for the probe
