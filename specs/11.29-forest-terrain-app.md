# 11.29 — apps/forest: a walkable terrain that exercises instancing, LOD and culling

## Context

Spec 11.28 (E5) shipped mesh dedup, a flattened draw list, shadow-layer culling, instanced draws and
LOD chains — and then measured them against a corpus that cannot show them off. `abandoned_window`'s
ivy leaves are 18 triangles each and border-locked; raiden is entirely skinned, so it builds **zero**
LOD chains. The two fixtures that do exercise the path are synthetic: 130 grey octahedra and six
spheres.

There is no scene in this repo where instancing, LOD and frustum culling all matter at once, and no
app a person can walk around in to *see* them working. This builds one: a kilometre of procedural
terrain, a few thousand trees and rocks placed on it, and a character to walk through it.

It also pays down a debt `specs/8.3` recorded in so many words — that `apps/tree`'s mesh builder and
tree generator are stuck in an app directory where the engine cannot reach them.

**Scope decisions taken with the user:** promote the generator into the library (not a copy, not an
`apps/common` target); ~1 km² with ~5,000 props; no wind on scattered trees.

## What the exploration established

Six facts that shape every part of the design. All verified in the tree, not assumed.

**1. Apps genuinely cannot share code.** `apps/CMakeLists.txt` globs `src/*.c` per app and gives no
cross-app include path. There is no `apps/common/`, no shared target, and no precedent anywhere in
the repo. Promotion to `cetra/src/` is the only mechanism, not a preference.

**2. `tree_gen` and `mesh_builder` are already clean.** ~1,035 lines depending only on `mesh.h`,
`util.h` and cglm — no GL call, no `Scene`, no `Material`, no `Engine`. They fill a caller-supplied
`Mesh*` and stop. They move unchanged. `grass.c` does **not**: it calls `ground_height_at()`, whose
definition lives in `tree.c`.

**3. Procedural meshes get no LOD chain.** `mesh_build_lod_chain` is called from exactly one place —
`import.c:1618`. `geometry.c` never calls it; `mesh_builder.c` never calls it. Every mesh this app
generates would have `lod_levels == 1` and `select_lod` would return 0 immediately. **This is the gap
the app hits on line one.**

**4. Batching needs pointer identity AND adjacency.** `draw_run_can_join` is
`next->mesh == head->mesh && next->lod == head->lod && draw_item_visible(...)`, over a pre-order DFS
flatten. So props must share one `Mesh*` (via `mesh_ref`) *and* sit as a contiguous sibling block.
Interleaving rock/tree/rock gives run length 1 and batching silently does nothing.

**5. Wind disables culling.** `draw_list.c:93` marks any `wind_response > 0` material
`DRAW_UNBOUNDED`, and `draw_item_visible` then accepts it unconditionally — camera *and* every
cascade. This is why the scattered trees carry no wind.

**6. Jolt has no heightfield here.** `PhysicsShapeType` is `{BOX, SPHERE, CAPSULE, CYLINDER}`.
JoltC binds `JPC_MeshShapeSettings` but **not** `HeightFieldShapeSettings` — only two orphan enum
constants (`Enums.h:36`, `:89`). A heightfield binding would mean editing the vendored submodule; a
mesh shape is a ~30-line wrapper in `physics.c`.

A heightfield is the shape terrain normally wants: a 2D grid of samples, O(1) lookup because the cell
is implied by (x, z), no index buffer and no BVH. Its limit is that it can only describe `y = f(x,z)`
— no overhangs. A mesh shape is a triangle soup in a BVH: general, heavier, and static-only in Jolt.
Since the heightfield is unavailable without touching a submodule, and this terrain *is* a height
function, the mesh shape carries it at a coarser resolution than the visual tiles.

Two smaller facts that would each have cost an afternoon: `upload_buffers_to_gpu_for_nodes` uploads
**per holder**, so pointing it at 5,000 nodes sharing one mesh re-uploads the same VBOs 5,000 times;
and the outermost shadow cascade is centred on a hardcoded `{0,0,0}` (`shadow.c:1187`), so the
terrain must be centred on the origin.

## Design

### Phase 1 — promote the generator into the library

Pure moves, no behaviour change. `apps/tree` must render **0 px different** afterwards, which is the
whole verification.

| from | to |
|---|---|
| `apps/tree/src/mesh_builder.c/h` | `cetra/src/mesh_builder.c/h` |
| `apps/tree/src/tree_gen.c/h` | `cetra/src/tree_gen.c/h` |

`apps/tree` then includes `cetra/mesh_builder.h` and `cetra/tree_gen.h`. A new header needs a CMake
reconfigure (`cetra/CMakeLists.txt:26-34` emits a forwarding header per file at configure time), so
`./build.sh`, not bare `ninja`.

Not moved: `grass.c` (needs the `ground_height_at` decoupling), and everything in `tree.c` that is
scene wiring, GUI, CLI or `main`.

### Phase 2 — the pieces the library is missing

**`cetra/src/terrain.c/h`** — new. The height function and the tile mesher:

```c
typedef struct TerrainParams {
    float extent;        // half-width in world units; terrain spans [-extent, +extent]
    float height;        // peak amplitude
    float base_freq;     // lowest octave frequency
    int   octaves;       // fbm octave count
    unsigned seed;
    int   tiles;         // tiles per side (tiles*tiles patches)
    int   tile_segments; // quads per tile edge
} TerrainParams;

float terrain_height_at(const TerrainParams* p, float x, float z);
void  terrain_normal_at(const TerrainParams* p, float x, float z, vec3 out);
bool  terrain_build_tile(const TerrainParams* p, int tx, int tz, Mesh* mesh);
bool  terrain_build_collider(const TerrainParams* p, int segments, Mesh* mesh);
```

fbm over `noise_perlin3(x, k, z)` on a constant Y plane — the pattern `grass.c:194-216` already uses.
It must use the **thread-safe** `NoisePerm` / `noise_perlin3_tiled` form rather than global
`noise_seed`, and it must compose octaves at frequencies that avoid the 256-unit lattice repeat of
the global-table path.

Tiles are built through `mesh_builder`, which writes vertex colours — used for altitude and slope
tinting (rock grey on steep faces, grass green on flat, snow at altitude) so the terrain reads well
without a splat-map system that does not exist. `pbr_frag` already consumes `GL_ATTR_COLOR`.

`terrain_build_collider` emits one coarse mesh over the whole extent for physics — same height
function, fewer segments, so it agrees with the visual tiles to within a few centimetres.

**`cetra/src/rock.c/h`** — new, small. A noise-displaced sphere:

```c
typedef struct RockParams { float radius; int segments; float roughness; unsigned seed; } RockParams;
bool rock_build_mesh(const RockParams* p, Mesh* mesh);
```

Closed and dense on purpose: it is the geometry class meshoptimizer simplifies best, so rocks are the
app's cleanest LOD demonstration.

**`SHAPE_MESH` in `physics.c/h`** — extends `PhysicsShapeType`, `PhysicsShapeDesc` and
`physics_create_shape_from_desc` with a case wrapping `JPC_MeshShapeSettings`. It takes the collider
mesh's positions and indices, converts to `JPC_Float3` + `JPC_IndexedTriangle`, and calls
`JPC_MeshShapeSettings_Create`. Static bodies only — Jolt does not allow a dynamic mesh shape, and the
wrapper should reject `MOTION_DYNAMIC` with a log rather than let Jolt assert.

**`GameConfig.profiler`** — one bool. `set_engine_profiler` must be called before `init_engine`, which
`create_game` does internally, so today a game-framework app **cannot turn the profiler on at all**.
Without it this app cannot measure the thing it exists to measure.

**LOD for procedural meshes.** The app calls `mesh_build_lod_chain(mesh)` itself, after the final
indices and `calculate_aabb`, before `upload_mesh_buffers_to_gpu`. `lod.h` is public, so this needs no
library change — but it is easy to get wrong (the chain rewrites `mesh->indices`), so the app funnels
every generated mesh through one local helper that does generate → aabb → chain → upload in that order.

### Phase 3 — the app

`apps/forest/src/forest.c`, following `apps/gametest` for the game-framework skeleton and `apps/spores`
for headless.

**Scene construction, in the order that matters:**

1. Terrain tiles — `tiles × tiles` nodes, each its own mesh, each with a LOD chain. Distinct meshes, so
   no batching; they are the **culling** demonstration and the per-tile LOD demonstration.
2. Tree prototypes — 6 mesh-pairs (3 species × 2 seeds) at **reduced** `TreeParams`. The app's hero
   defaults produce ~90k verts / ~107k triangles per tree, which at 2,000 instances would be 200M+
   triangles submitted before culling. Forest prototypes target ~10–15k triangles (`max_depth 3`,
   fewer branches). One or two hero trees near spawn keep the full-detail look.
3. Rock prototypes — 8 meshes.
4. Scatter — ~2,000 trees and ~3,000 rocks, placed by rejection sampling against slope
   (`terrain_normal_at`) so nothing stands on a cliff, and rooted with `terrain_height_at`.

**The scatter must be grouped by prototype**, one contiguous sibling block per mesh, or batching does
nothing. This is finding 4 and it is the single easiest thing to get silently wrong. Each extra holder
takes a `mesh_ref`; each distinct mesh is uploaded **once** by hand, never via
`upload_buffers_to_gpu_for_nodes`.

**Character and camera.** `entity_add_character_controller` on an entity positioned above the terrain.
There is **no follow-camera helper anywhere in cetra** — `app.h` offers only the orbit
`MouseDragController` — so the app writes a third-person camera: yaw/pitch from the mouse, position
behind the character, then `update_engine_camera_lookat` + `update_engine_camera_perspective` every
frame in `on_render`, without which the view matrix never updates. WASD is rotated into camera yaw
(gametest's is world-axis-aligned, which feels wrong the moment the camera turns).

**Scale settings** that must be set or the frame is broken rather than merely ugly:

- `set_camera_perspective(camera, fov, 0.5f, 2000.0f)` — the default 0.1/1000 is a 10,000:1 depth
  ratio and would z-fight across a kilometre.
- `shadow_system->ortho_size = terrain extent`, `far_plane` sized to match, `cascade_count = 3`.
  The library default is `ortho_size 2000`, `cascade_count 1` — a single origin-centred map.
- Terrain centred on the origin, because the outermost cascade's centre is hardcoded there.
- `physics_default_config().max_bodies` stays at 10240 — only the terrain collider and the character
  are bodies. Props are visual-only `SceneNode`s with no entity, which is the supported cheap path.

### Phase 4 — look

This has to look good, not merely count draws. Concretely:

- **Sky** — the Hillaire atmosphere, which gives aerial perspective over a kilometre for free and is
  what makes distance read as distance.
- **Terrain shading** — vertex-colour tinting by slope and altitude, plus a tiling detail normal so
  close ground is not flat.
- **Bark and leaf textures** — `apps/tree` synthesises these procedurally, but the generators are
  file-static in `tree.c` and interleaved with a `Scene`-dependent upload. Extract the **pure**
  `unsigned char*` generators (bark albedo/normal/height/roughness, the 8-cell leaf atlas) into
  `cetra/src/vegetation_tex.c/h`, leaving each app its own upload. Without this, trees are untextured
  blobs and the scene does not look good at all. Note `TG_LEAF_VARIANTS = 8` is a contract between the
  leaf mesh's UVs and the atlas — the geometry header is the authority.
- **PostFX** — the defaults are already strong (bloom, GTAO, SSR, tonemap). Enable fog for depth.
- Hero trees at full detail near spawn, so the first thing seen is the good-looking one.

## Verification

**Phase 1 is a pure move, so it has an exact bar:** `apps/tree` headless, before and after, must
compare at **0 px**. `AGENTS.md` records tree as baseline-grade headless (×2 at 0 px since spec 11.2).
Nothing else in Phase 1 needs proving.

**The app's own arms**, all reading the profiler's SUBMISSION table — integers with no noise floor,
following the discipline the E5 gates established:

| arm | asserts | catches |
|---|---|---|
| `forest-batch` | opaque `instances` ≫ `draws`; ratio > 10 | the scatter interleaved, or `mesh_ref` not shared — batching silently doing nothing |
| `forest-batch-off` | `--no-instancing`: `draws == instances` | a dead flag, and the inverse that makes the arm above mean something |
| `forest-lod` | `triangles` strictly falls as the camera pulls back over three positions | selection not firing on procedural meshes — the Phase 2 gap, which is the likeliest thing to ship broken |
| `forest-lod-off` | `--no-lod`: `triangles` equal near and far | the same, from the other side |
| `forest-cull` | camera facing away: `meshes_culled` > 0 and opaque `draws` collapses | wind or a flag re-introducing `DRAW_UNBOUNDED` across the scatter |
| `forest-chains` | the generation log reports chains > 0 on rocks and terrain, 0 on leaf cards | a chain silently refused — the arm that tells "LOD works" from "nothing had a chain" |

**Determinism.** The app must be headless-capable (`--headless`, `--frames`, `--screenshot`, plus
`--profiler`) and produce identical frames across two runs of one build, which is the precondition for
any of the above being trustworthy. Everything is seeded: terrain by `TerrainParams.seed`, trees by
`TreeParams.seed`, rocks by `RockParams.seed`, scatter by its own seeded RNG — no `rand()`.

**Physics.** Walk the character across a slope and off a ledge; confirm it does not fall through the
mesh collider and that `character_controller_is_grounded` tracks the terrain.

**Memory and honesty about cost.** Report distinct mesh count, total prototype triangles, node count
and resident VRAM at startup. If the per-frame transform walk over 5,000 nodes turns out to dominate
the draw-call saving, that is a finding worth recording rather than hiding — it is the next wall after
submission.

## As built

**Delivered:** `cetra/src/procedural/` (`tree_gen`, `terrain`, `rock`, `vegetation_tex`),
`mesh_builder` promoted to the top level, `SHAPE_MESH`, `GameConfig.profiler`, and `apps/forest` —
84 distinct meshes, 481k prototype triangles, 7,064 nodes, 5,000 scattered props over 64 terrain
tiles, walked with a character controller on a 131k-triangle Jolt mesh collider. All 21 goldens are
0 px and the six `forest-*` arms pass.

**A `procedural/` subdirectory rather than four loose files**, following `cetra/src/game/` — its own
source and header globs, its own include prefix, `../` to reach back up. `mesh_builder` deliberately
stayed at the top level: it is *how* you build a mesh, not *what* to build, and `specs/8.3` wants
`geometry.c` building through it, which a core file reaching into `procedural/` would invert.

### The two findings, and neither is about the renderer

**Scatter ORDER decides whether batching happens at all.** The batcher joins only *consecutive*
surviving items, so with most props frustum-culled a randomly-ordered scatter collapses to runs of
one. Morton-ordering the instances inside each prototype block:

| | draws | instances | triangles |
|---|---|---|---|
| `--no-spatial-sort` | 2,368 | 2,979 | 22,279,562 |
| Morton | **1,287** | 2,979 | 22,279,562 |

Identical instances and identical triangles — the two runs draw exactly the same geometry, and the
only thing that changed is whether the survivors of a frustum test ended up adjacent. That equality
is the guard in `forest-order`. Z-order rather than row-major because row-major holds along one axis
and a camera looking across the rows shreds every run again.

**LOD fights instancing, inherently.** The batch key is `(mesh, lod)`, so one prototype spanning a
range of distances splits into separate runs. At a fixed camera LOD submits 22.3M triangles against
26.3M without, for roughly double the draws; at a far camera it is 44% fewer triangles for 4.6× the
draws, with opaque GPU 276 → 241 ms and opaque CPU 3.2 → 9.4 ms. A CPU-for-GPU trade whose direction
depends on the framing, and worth stating rather than presenting LOD as free.

### Corrections to this plan

**`forest-lod` as specified was wrong.** "Triangles fall as the camera pulls back" does not hold for
scattered content — pulling back reveals more world, so the count *rises* however well selection
works. The delivered arm fixes the camera and compares LOD on against off, guarded on the instance
count being identical, which is what proves the difference is level selection and not visibility.

**`forest-chains` expected leaf cards to be refused a chain**, on the reasoning that alpha cards are
border-locked. They are not refused: all 84 meshes get chains, because meshopt collapses whole cards
rather than declining. Worth watching for canopy popping; the arm asserts only that chains exist,
since nothing in the engine builds one for a procedural mesh and without that check every LOD arm
would pass against a scene where nothing had one.

**A `--no-spatial-sort` flag was added that the plan did not call for**, because the ordering finding
was otherwise undefended — the app's largest result with no arm behind it.

### What the look cost, and the lesson

The rocks read as white. Their albedo was changed three times (0.38 → 0.21 → 0.085), the sun twice
and the exposure once, chasing it. Every one of those was a guess at a symptom.

One measurement settled it: the ground half of the frame had **2,162 pixels above 60% brightness
before and zero after**. The rocks were already dark — what looked white was contrast against a dim
scene in a downscaled screenshot. `--render-mode 1` showed clean normals on every rock, which is the
check that should have run first, and is why that flag is now permanent. The real fault was overall
level: at exposure 1.0 the lit ground averaged 72/255. It is pinned at 1.8 now, near 101, nothing
clipping — and pinned rather than adaptive because `AGENTS.md` names auto-exposure as the top
determinism hazard and every arm here reads a frame or a counter.

Two cross-build comparisons were also made against numbers from an earlier build mid-way through the
look work, which produced an instance-count discrepancy that did not exist. Same trap the E5 spec
records at length, in a different disguise.

## Deliberately deferred

- **Grass.** It is the border-locked case: no LOD chain, no instancing (one merged mega-mesh), and
  wind would disable culling for it. It also needs the `ground_height_at` decoupling first. Adding it
  would make the frame prettier and every measurement muddier.
- **A real terrain system (roadmap D4).** Clipmap / CDLOD / tessellation, effort XL. This app is a
  *consumer* of E5, not D4 — it uses fixed tiles with per-tile LOD chains, which is exactly the
  "mega-mesh with extra steps" D4 warns about at large scale, and is fine at 1 km².
- **A heightfield collision shape.** Would need a new JoltC binding in a vendored submodule.
- **Per-instance wind phase.** `windOffset` is object-space with per-mesh uniforms, so every instance
  of a shared tree sways identically. Fixing it means a per-instance value in the instance block —
  worth doing, and it belongs with the wind-culling fix rather than here.
- **Fixing the wind cull.** Expanding wind meshes' AABB by maximum displacement so they become
  cullable rather than exempt. Benefits `apps/tree` too; wants its own arms.
- **Streaming.** Everything stays resident. That is what caps this at 1 km².
