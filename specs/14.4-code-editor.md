# 14.4: the code editor

## Context

Roadmap item 6 (`docs/eda-roadmap.md`): pcb's code view, built into cetra. pcb's `ARCH.md`
section 8 asks for a code editor of its own in C, borrowing from rxi's lite (MIT) and vis (ISC)
with their notices kept on any copied code. It starts with standard keys, but key handling is
built on modes, so a vim mode can be added later without a rewrite. The widget goes in cetra.
Three things stay in pcb:
- the colouring, from its parser;
- the link that lands edits made in other views;
- undo, on its one project timeline.

**Decided with you (2026-10-30):**
- **Storage is an array of lines** (lite's way). Each line points into the file as loaded until it
  is edited.
- **The text and the editor are two things**, as lite (Doc, DocView) and vis (Text, View) keep
  them.
- **Several carets from the start.**
- **A small undo of its own**, on by default, off when a host takes undo.
- **JetBrains Mono**, drawn from bitmaps made at the exact pixel size.
- **Wrapping from the start**, with no sideways scrolling in this spec.
- **Keys are built from vis's three pieces**: motions, text objects and operators, which a mode
  turns keys into.
- **Colours come in two kinds**: a line at a time from a callback, and ranges from the host's last
  parse.

**What about pcb shapes the seams:**
- **pcb counts positions in bytes from the start of a file.**
  - A view edit says "bytes 1180 to 1185 of `top.ckt` become `odt-2`" (`Splice`,
    pcb `src/core/splice.h`).
  - Its reader takes a whole file as one block of bytes and copies it.
  - A CR before an LF belongs to the line ending, a file keeps its own line ending, and a
    byte-order mark counts in the offsets (`Source`, `src/core/source.h`).
- **Strings and comments never cross a line**, so pcb can colour any line on its own.
- **pcb's undo puts back whole versions of a file.** Typing is grouped into one step by pauses, so
  an undo comes back as new text.
- **One command table** drives pcb's bindings, `h` help, palette, command line and agent
  (`ARCH.md` section 1). So the editor's commands must be listable by name and description, and
  every key bindable by the host. In pcb, for instance, Tab flips views.

pcb's largest sample file is 78 KB (1,393 lines). pcb refuses files over 64 MB.

## The design

### 1. The text: `TextDoc` (`cetra/src/text_doc.c/h`, no GL, no UI)

**Lines.** The file's bytes are copied once into one block, and lines are found by one scan for
LF.
- Each line record points into the block until it is edited, then owns its bytes.
- A line keeps its terminator's kind (LF, CRLF, none for the last line) apart from its content,
  so the bytes round-trip exactly. A lone CR is content, as in pcb.
- Typed and pasted line breaks are written in the doc's own `newline`, found at load as pcb
  finds it. Host edits are written byte for byte.
- A byte-order mark stays as bytes, so pcb's offsets hold, and is drawn as nothing.

**Offsets.** Each line keeps its start offset, made good lazily: an edit on line k marks the starts
after k stale, and a query brings them up to date only as far as it needs. Offset to line is a
binary search over the starts made good.

**Changes.**
- Every change is one replacement: bytes `[start, end)` become new bytes.
- `version` counts changes.
- A ring of the last 4,096 changes maps an offset or a range given at an older version to now.
  - An offset before a change stays put; one after it shifts by the change's length.
  - An offset inside replaced bytes goes to the end of the new ones.
  - A range wholly inside replaced bytes is dropped; one overlapping an edge is clipped.
  - A version older than the ring is refused by name.
- **A user action with several carets is applied from the last caret back to the first**, so every
  change in it is in the action's starting coordinates.

**The host's calls.**
- `text_doc_replace(start, end, text)`: a host edit. It is refused by name out of range or inside
  a UTF-8 sequence.
- `text_doc_set_text`: the whole new text. The unchanged start and end are trimmed, so it lands as
  one replacement.
- `text_doc_map(version, &offset)`: the host rebases its own positions.
- Host edits are not reported back to the host.

**Actions out.** `on_action(doc, action)` is called once per user action from any editor showing
the doc. It carries:
- the changes, each with the removed and inserted bytes;
- the selections before and after;
- the editor that made it;
- the version before.

pcb groups actions into undo steps by pauses, and restores the selection from the first action's
"before".

**Built-in undo.**
- It is kept on the doc, so it is shared by the doc's editors, from the same action records.
- Typing joins into words, as the field's `_merge_typing` does. A caret move or a paste starts a new
  step.
- Undo restores the selections into the editor that undoes.
- Host edits are steps of their own, so an app with no timeline can undo them too.
- `keep_undo` (a setting, default true) set false records nothing; pcb sets it false.

**Colours.**
- **The highlighter** is a per-doc callback: a line's bytes and a state in, giving styled spans and
  a state out (lite's).
  - Its answer is kept on the line until the line changes, or its state in does.
  - A changed state out passes the staleness to the next line.
  - pcb's lines never carry state, so they never wait on the line above. A stateful language is
    coloured from the top within a time budget (see 4), and its lines draw plain until reached.
- **Ranges** come from the host, in up to four layers: errors, the shared selection, and two more.
  - Each layer is set whole at a version and mapped through the changes since.
  - A range's style says its text colour, background and underline.

### 2. The font: `GlyphCache` (`cetra/src/glyph_cache.c/h`)

- **JetBrains Mono Regular** (OFL 1.1) is shipped under `assets/fonts/` with its licence. It is
  downloaded into a directory of its own and checked before it is copied in.
- **Glyphs are rasterised by stb_truetype at the exact framebuffer pixel size** (points times the
  window's framebuffer ratio). They are packed in rows on demand as they are first met, into a
  `GL_R8` atlas swizzled `{ONE, ONE, ONE, RED}`, which grows when full.
- **They draw through the UI's existing textured quad** (`ui_draw_textured_quad_uv`): the tint is
  the colour and the coverage is the alpha, with no shader change.
- **The cell width is the font's advance rounded to whole pixels**, so every glyph sits on a pixel
  column and stays crisp.
- **A new size or a new screen scale empties the atlas and makes it again** on demand.
- It is its own object, not a `Font`, since `load_font` keeps one font per path whatever size is
  asked (`text.c:470`).
- A codepoint the face lacks draws as a box one cell wide, as the UI's do.

### 3. The editor: `UI_EDITOR`, the ninth element kind (`cetra/src/ui_editor.c/h`)

**Shape.**
- `ui_editor(parent, doc)` borrows the doc, and a doc outlives the editors showing it.
- It is wired into `ui.c` at the field's sites (the exploration's table): the theme entry,
  focusable, freeing, `_takes_keys`, `_route_keys`, press, drag, the blink's `caret_wake`, and
  `_emit`.
- It measures nothing; it is sized FIXED or GROW.
- The doc keeps the list of its editors, to map their carets and anchors through every change.

**Wrapping.**
- Each line is cut into rows at the editor's width in cells, after the last space that fits, or
  at the edge for a word longer than a row.
- A continuation row is indented by its line's own indent, unless that indent is over half the
  width.
- A tab runs to the next stop (`tab_width`, a doc setting, default 4).
- **Row counts are the editor's**, since two editors of one doc can be two widths.
  - The lines drawn, and their neighbours, are measured exactly. The rest are estimated from
    their length until a time budget measures them.
  - Row tops are a prefix sum made good lazily, as `UIRows` does (`ui.c:375-389`, `_rows_tops`).
  - A line's row breaks are kept only for lines in view.
- **The scroll is anchored to a line and a row in it**, so an estimate made exact, or an edit
  above, never moves what is on screen.

**What it draws:**
- the rows in view;
- a gutter of line numbers, blank on continuation rows;
- each selection's background and each caret (a bar, or a block when the mode says so),
  blinking as the field's caret does;
- the highlighter's spans and the host's ranges;
- find matches in view;
- a thin scrollbar that drags.

**Pointer:**
- a click places the caret, a drag selects, a double click takes a word, a triple click a line;
- Shift+click extends the selection, and Option+click (Alt elsewhere) adds a caret;
- the wheel scrolls.

**Carets.**
- The selections are a sorted list, merged where they overlap, one of them the primary.
- Each caret keeps its wanted column for moving up and down by row.

### 4. Keys: modes over motions, text objects and operators

- **The pieces:**
  - **Motions** are char, word left/right and word end, row up/down, row start/end, first
    non-blank, line up/down, page up/down, doc start/end, matching bracket, and next or previous
    find match.
  - **Text objects** are word, line, bracket pair (inner and around: pcb's list round the caret),
    string, and all.
  - **Operators** are move, extend, delete, cut, copy, paste, indent, outdent, select, and type.
  - Each runs once per caret.
- **A command** is a name, a description and a function. The editor lists its own
  (`ui_editor_commands`) for a host's table. A host adds its own with user data.
- **A mode** is:
  - a name;
  - a parent;
  - a table of key and modifier to command;
  - whether typed characters insert;
  - the caret shape;
  - optionally a key reader of its own, for sequences like `d2w`.

  A key a mode does not bind falls to its parent. Keys nothing uses fall to the screen, as the
  field's do.
- **The standard mode** hoists the field's platform conventions into a shared private file, which
  the field then uses too. Those conventions are the word classes, word moves, the shortcut and
  word modifiers, the paste cleaner, and the click counting. It also adds:
  - Cmd+D: a caret at the next match of the selection;
  - Cmd+Option+Up/Down (Ctrl+Alt elsewhere): a caret on the row above or below;
  - Esc: back to one caret, else to the screen;
  - Enter keeps the line's indent;
  - Tab and Shift+Tab indent and outdent a selection, and Tab inserts spaces otherwise;
  - copy with several carets joins their text by lines, and paste of as many lines as carets
    gives one line to each;
  - Cmd+Z and Cmd+Shift+Z run the built-in undo; pcb binds them to its own in a mode whose parent
    is the standard mode;
  - find next and previous: Cmd+G and Cmd+Shift+G, F3 elsewhere.
- **Find**: `ui_editor_find(query, flags)` (case, whole word) sets the editor's query. The box it
  is typed into is the app's.

### 5. Speed

- Only the rows in view are laid out and drawn. The monospaced grid places a glyph at its cell,
  with no measuring.
- **A time budget, under 1 ms a frame**, finishes the estimated row counts and the stateful
  highlighting. While it has work it asks idle mode for frames, and headless runs end once it is
  done.
- **The bars, measured by `gametest --ui-bench` on a release build at 80 KB, 10 MB and 64 MB:**
  - a keystroke at one caret, and at 100 carets spread through the file: under 1 ms at 10 MB;
  - jumping to any line and laying out and drawing the screen: under 1 ms;
  - opening: under 50 ms at 10 MB;
  - a resize: the screen exact within the frame.

  A bar missed is fixed in phase 6, or brought to you with the numbers.

### 6. Headless

- Everything runs headless, driven by the input script (`type=`, `key=`, pointer lines) as 14.2's
  field is.
- `gametest --ui-probe` cases print the carets, selections, rows and ranges.
- Most doc arms need no window, since `TextDoc` has no GL.

## As built

### Phase 1: the text

`cetra/src/text_doc.c/h`, with the editor's half in a private `text_doc_edit.h`. Built as planned,
with these differences and additions:

- **Names beyond the approved list**, each needed by one that was approved:
  - `TextDocActionFn`, the type `text_doc_set_on_action` takes;
  - `TextNewline` (`TEXT_NEWLINE_LF`, `TEXT_NEWLINE_CRLF`), the type of `newline`;
  - `TEXT_DOC_HISTORY` (4096) and `TEXT_DOC_LAYERS` (4).
- **The highlighter writes into the doc's array**, up to `max` spans, and returns how many the line
  has; a line with more is asked again with room for them. The doc keeps room for 64 from the
  start, so an ordinary line is asked once. That replaced an "add a span" call, which would have
  been one more name.
- **`text_doc_set_highlighter` takes `stateful`.** With it false every line starts from state 0 and
  is coloured on its own, so pcb's lines never wait on a walk from the top. A host cannot say this
  later without it: a walk over a 64 MB file to find that every state is 0 would wake idle mode for
  hundreds of frames.
- **The private half**: `TextEdit`, `text_doc_apply`, `text_doc_add_view`, `text_doc_remove_view`,
  `text_doc_seal_undo`, `text_doc_undo_in`, `text_doc_redo_in`, `text_doc_map_offset`,
  `text_doc_line_spans`, `text_doc_highlight_step`, `text_doc_ranges`. A view registers four things:
  itself, its element, a `map` through one change, and getting and setting its selections.
- **The two mapping rules**:
  - An offset keeps before an insertion at it, unless it is the acting editor's caret.
  - A range keeps the new bytes outside it at both edges. A range cut into keeps only its old
    bytes; one a change sits strictly inside grows round it.
- **The fast path** edits one line's bytes in place when the change touches no line break. A
  deletion that would leave a CR just before the LF takes the general path, since the two become a
  CRLF ending. The random arm found that rule at step 1,386 when it was broken.
- **Limits**: 10,000 undo steps, the oldest dropped. Spans are kept for at most 8,192 lines at once;
  past that, every line's spans are let go, and the lines in view colour themselves again.
- **An undo is reported to `on_action`** like any action, whoever called it, so a host that saves
  on every change sees it. Its changes keep the action rule: from the highest start down, each in
  the text as the undo found it.
- **The probe's own file**: `apps/gametest/src/ui_editor_probe.c`, `--ui-probe doc-*`, with a
  stand-in view whose carets the doc moves.
- **Falsified**, each committed first and restored:
  - an insertion moving every offset after it: `ui-doc-map` failed at `at_insert`;
  - the CR joining rule removed: `ui-doc-random` failed at step 1,386, a line one byte long.
- **Gates**: `ui` and `gate-docs` pass.

### Phase 2: the font

`cetra/src/glyph_cache.c/h`, and JetBrains Mono 2.304 Regular in `assets/fonts/` beside its OFL
1.1 text (`JetBrainsMono-OFL.txt`). The font came from the project's own tag on GitHub, downloaded
into an empty directory and checked (a TrueType file, the licence's text) before it was copied in.
`.ttf` joined the asset taxonomy as the kind `fonts` (`fixture_paths.KIND`); nothing named a font
through it before, so nothing moved.

- **One name beyond the approved list**: `GlyphBitmap`, what `glyph_cache_get` fills. It holds the
  glyph's place in the atlas as UVs, its offset from the pen in pixels, and whether the face lacks
  it.
- **A size is a pixel height**, ascent to descent, as a `Font`'s is (`stbtt_ScaleForPixelHeight`),
  so the editor's 13 and the UI's 13 are the same size.
- **The cell is the advance of `M`, rounded to whole pixels**; the line height and the ascent are
  rounded too. The editor puts the pen on whole framebuffer pixels, so every glyph's bitmap lands
  on the pixel grid it was made for.
- **The atlas** is 512 pixels wide and starts 256 tall. It doubles in height, its glyphs where they
  were, up to 8192. Glyphs have one clear pixel between them. Each glyph is uploaded alone, from
  the cache's own copy of the atlas, which is also what a growth re-uploads.
- **ASCII is found by index**, and every other codepoint through a hash.
- **`canvas --font-sheet`** draws one line of code at 11, 13 and 16 points, from the cache and
  then as the UI's distance field of the same face. On this Mac's 2x screen the two are close; the
  bitmap row is a little fuller and its spacing exactly even. A 1x screen, where the field goes
  soft, cannot be rendered headless here.
- **Falsified**: an atlas growth that cleared the glyphs already packed. The arm at first did not
  see it, since it checked each glyph straight after asking for it, before a later growth could
  lose it. It now asks for every glyph before checking any, and the growth fault shows as 565 of
  588 glyphs wrong.
- **Gates**: `ui`, `canvas` and `gate-docs` pass.

### Phase 3: the editor on screen

`cetra/src/ui_editor.c`, the public `ui_editor.h`, and a private `ui_editor_hooks.h` for what
`ui.c` calls and what the probe reads, as `ui_field.h` is for the field. `ui_editor` is the ninth
constructor in `ui.h`, and `ui-elements-closed` names it.

- **How it is wired.** `UI_EDITOR` is wired at the field's sites in `ui.c`:
  - its theme entry, focusable, freeing, `_takes_keys`;
  - `_route_keys`, where a field's begin and end bracket fields only;
  - press, drag, release (no activation), its draw with the caret's wake, and the wheel. An editor
    under the pointer takes the wheel before any pane round it.
- **The theme** gains `editor[UI_STATE_COUNT]`, `editor_face` (a borrowed `GlyphCache`), `editor_size`
  (13 by default) and `editor_styles[UI_EDITOR_STYLES]` (32 `UIEditorStyle`s: text, background,
  underline). A span's or a range's style is its index there, and style 0 is plain.
- **Names and shapes beyond the approved list**: `UIEditorStyle` and `UI_EDITOR_STYLES` (named in the
  plan as "the theme's style table"); `ui_editor_selections` returns the primary's index through a
  pointer; and the private hooks `ui_editor_wrap`, `ui_editor_point_of`, `ui_editor_offset_at` and
  `ui_editor_top`.
- **`TextDocView` gained `lines`**: which lines a change rewrote (`removed` from `first` became
  `inserted`), called before `map`. That is what lets an editor keep its row counts per line and
  hold its view to a line.
- **The view and the rows.** The scroll is a line, a row of it and a fraction of a row, and may run
  until the last row is at the top. Rows above are guessed from a line's length (`len / cols + 1`)
  until the line is wrapped. A guess put right changes the row tops after it, never the view's
  line. A new width makes every line a guess again.
- **The gutter** is as wide as the line count's digits, three at least so it does not widen at line
  10 and 100, and two columns more.
- **The pointer:**
  - a second press within 0.4 s and 4 points takes a word (letters, digits, `_` and anything past
    ASCII, then spaces, then the rest), a third the line with its ending;
  - a drag extends by the unit;
  - held past the top or the bottom, it scrolls a row a pass;
  - Shift extends the primary selection, and Alt (Option) adds a caret;
  - a click past a wrapped row's end puts the caret before its last character, so it stays on that
    row.
- **Not yet**: the keys (phase 4), the time budget for guessed rows and stateful colours (phase 6).
  Carets are drawn only while the editor holds the focus, as a field's are.
- **Look**: `canvas --editor cetra/src/text_doc.h`, wide and narrow, and with a scripted drag
  selecting across lines. The input script's pointer carries Shift and no other modifier, so
  Option+click is the probe's.
- **Falsified**: the view's line not moved past lines put in above it. `ui-editor-anchor` failed at
  `edit kept`.
- **Gates**: `ui`, `canvas` and `gate-docs` pass.

### Phase 4: keys through modes

The motions, text objects and operators (`ui_editor_motion`, `_object`, `_apply`), commands
(`ui_editor_commands`, `_run`), modes (`ui_editor_set_mode`, `_mode`, `_standard_mode`) and find
(`ui_editor_find`), in `ui_editor.c` and `ui_editor.h`. The field's conventions are hoisted into a
private `ui_typing.c/h`, and the field now uses them too. Its arms ran unchanged and pass. The
shared conventions are:
- the word class, word left and right (still split by platform), and the word round a point;
- the paste cleaner, the double-press test, and the caret's blink and width.

- **Names beyond the approved list:**
  - the enum values `UI_MOTION_*`, `UI_OBJECT_*` and `UI_OP_*`;
  - `UIEditorCommandFn` and `UIEditorKeyFn`;
  - `UI_EDITOR_FIND_CASE` and `UI_EDITOR_FIND_WORD`;
  - `ui_editor_type`, the plan's "type" operator. It is a call of its own since it takes text.
- **A command returns whether it did anything.** Esc's `single-caret` declines with one caret, so
  the key falls to the screen and lets go of the editor, as Esc does a field. A command a key
  binds that declines lets the key fall the same way.
- **A binding points at its command**; no registry by name stands between them. A host's commands
  are its own `UIEditorCommand`s with its own `user`, bound in a mode of its own whose parent is
  the standard mode. `ui_editor_run` finds the editor's own by name, for a palette.
- **A mode's reader sees each key first, then its table, then its parent's, and so on up.**
  Typing types only where the topmost mode says it does. A vim normal mode takes every character
  and types none; its insert mode types and takes the standard mode's arrows from its parent.
- **The operators' rules:**
  - Delete, cut and copy take a selection over the motion where there is one, as a key does
    everywhere.
  - Moving left or right with a selection lets go of it at that side.
  - Copying several selections joins them with line breaks. Pasting as many lines as there are
    carets gives one line to each.
  - Copy with nothing selected copies nothing.
- **Motions:**
  - `WORD_RIGHT` is the platform's word move; `WORD_END` is vim's `e`.
  - A word move at a line's edge crosses the line break.
  - Row moves keep each caret's wanted column; line moves keep the column in the line's own count.
  - Home goes to the line's first character that is not a blank, then to the row's start, and back.
- **Find** matches within a line, letters folded in ASCII unless `UI_EDITOR_FIND_CASE`. Its
  matches are tinted in view. `find-next` with no query takes the selection's text.
- **Cmd+D** first takes the word at the caret, then adds the next match of the selection, round
  the text's end.
- **The standard mode's table** is built on first asking, from the commands by name, with
  `#ifdef __APPLE__` for the two platforms' keys. It lists 48 commands.
- **The input script knows `f1` to `f25`**, since find's next match is F3 off macOS.
- **`canvas --editor` under `--canvas-probe`** prints the text as hex and the selections at exit,
  which `ui-editor-script` reads.
- **Look**: three carets typing `// ` at three lines' starts, and a word found again further down,
  the view following it.
- **Falsified**: a key not falling from a mode to its parent. `ui-editor-mode` failed at `inherits
  arrow`.
- **Gates**: `ui`, `canvas`, `idle` and `gate-docs` pass.

### Phase 5: the host's seams in the demo

`apps/canvas --editor FILE` stands in for pcb, through the editor's public calls and the text's:

- **The highlighter**: pcb's lexical rules, a line at a time and stateless.
  - A comment runs from `;` to the line's end; a string stays on one line, with its escapes.
  - Brackets are dim, and the atom after `(` is the form's head.
  - `:keywords`, and numbers (an atom starting with a digit, or `-` or `.` and a digit) have
    colours of their own.
  - The styles are 1 to 8 of the theme's table.
- **The parse** runs on a thread of its own (`cetra_thread_create`) over a copy of the text taken
  with its version. It finds brackets left open or closing nothing, and strings their line ends
  inside. Its result is taken with `text_doc_set_ranges` at the version it read, layer 0, and
  underlined in red where the typing since put the errors.
  - One parse runs at a time; another begins once the text has changed since the last result.
  - **`--editor-lag N`** takes each result N frames after its parse began, joining the thread if it
    has not finished. A headless run then repeats, and the result is a known number of versions
    behind. In a window it is 1.
- **F6 lands an edit at the text's start** with `text_doc_replace`, as another view's would, and
  marks it in layer 1. **F7 reads the file again** through `text_doc_set_text`. Both are bound in
  a mode of the host's (`pcb`) whose parent is the standard mode, which is how pcb binds its own
  keys.
- **Under `--canvas-probe`** the run also prints the errors as they stand and where the first is
  drawn, in framebuffer pixels.
- **Look**: pcb's own `tests/designs/sample/parts/xcku040.ckt`, coloured. The landed line is tinted,
  a URL string longer than the row breaks at the edge at its line's indent, and an unclosed
  bracket typed in is underlined.
- **Falsified**: the parse's errors handed in at the text's current version instead of the one it
  read. `ui-editor-ranges-late` saw them at 9 to 10, where the text had since moved them to 12.
- **Gates**: `ui`, `canvas` and `gate-docs` pass.

### Phase 6: speed

**The budget** (`_settle` in `ui_editor.c`) runs in each draw, after the rows in view.
- **What it does a frame:** it wraps guessed lines, up to `SETTLE_BYTES` (192 KB) of them, looking
  at no more than 256 K lines. It also moves a stateful highlighter's walk on, up to 2,000 lines,
  toward the furthest line drawn. While either has work left it asks idle mode for a frame. It is
  counted in bytes rather than timed, so a headless run repeats.
- **The editor counts its guessed lines.** The walk does nothing while the count is 0, and picks up
  from where it stopped, round the end of the text. A first version instead went back to the line
  each edit touched and scanned from there. That cost every keystroke in a large file a scan of
  every line after it, though the line typed on had already been wrapped as it was drawn.
- **ASCII steps a byte at a time**, in the editor and in `ui_typing.c`, without the bounded copy a
  multi-byte character takes.

**A text freed while an editor shows it now leaves the editor showing nothing.** The bench found
the case: a popped screen keeps its elements until the UI is freed, and no element or screen can
be freed sooner. So the rule "a text outlives its editors" was easy to break, and breaking it
crashed.
- `TextDocView` gained `gone`, and `free_text_doc` calls it on each view.
- Every editor entry point goes through `_of` or `_seen`, which give the editor only while its text
  lives.
- `ui-editor-host-edit` frees the text under two editors and checks that both let go of it.

**`gametest --ui-bench`** times the editor on texts of pcb's lines: 80 KB, 10 MB and 64 MB, in a
900 x 700 editor, 13 points on a 2x screen. The numbers are from a release build, with the budget
settled before the keystrokes are timed. Each pair is two whole runs; within a run the spread is
the five runs' max less min. Milliseconds:

| | 80 KB | 10 MB | 64 MB |
|---|---|---|---|
| open | 0.015, 0.018 | 2.05, 2.00 | 12.4, 11.8 |
| first frame | 0.61, 0.65 | 1.02, 1.11 | 2.40, 2.51 |
| the budget to settled (frames, total, longest frame) | 0, settled in the first | 53, 44.1, 0.97; 53, 42.8, 0.89 | 341, 285, 0.96; 341, 280, 0.93 |
| a keystroke, one caret | 0.118, 0.119 | 0.167, 0.151 | 0.357, 0.359 |
| a keystroke, 100 carets through the text | 0.27, 0.30 | 0.82, 0.78 | 3.20, 3.26 |
| a jump far down, laid out and drawn | 0.13, 0.13 | 0.149, 0.142 | 0.142, 0.150 |
| a resize, the view wrapped again | 0.40, 0.41 | 1.09, 1.05 | 2.19, 2.47 |

**Against the bars at 10 MB, all are met:**
- a keystroke: 0.17 ms at one caret and 0.82 ms at 100, against 1 ms;
- a jump: 0.15 ms, against 1 ms;
- opening: 2.0 ms, against 50 ms;
- a resize has the screen exact within its frame.

The resize's frame also carries its share of the budget, since every row is a guess again. At
64 MB the 100-caret keystroke is 3.2 ms. Most of that is the line starts being worked out again
from the first caret's line to the view's, 790,000 lines after a keystroke at the text's start.
That is not built, since no bar asks for 64 MB; a tree of line lengths would make it a
logarithm.

**`idle-editor`**: a run on a line of text draws 47 frames, which are the UI's own eases. A 24 MB
text draws 128 and ends with every row wrapped.
- **Falsified:** the budget asking for no frames. The 24 MB run ended at 47 frames with rows still
  guessed.
- The first version of the arm used 3 MB, which settles inside the eases' 47 frames, and could not
  see that fault.

**Gates**: `ui`, `canvas`, `idle` and `gate-docs` pass.

### Phase 8: reviews

Six reviews ran in background agents, and all were back before anything was changed:
- `/simplify`'s four angles: reuse, simplification, efficiency, altitude;
- a correctness pass;
- the thermo-nuclear code-quality review.

The changes went in two commits, the text's first.

**Six bugs, each found by running something, and each repro run again after its fix:**
1. **A heap overflow** in `_own`. A line still in the loaded block was copied whole into room sized
   for its length after the edit, so a deletion wrote past the copy. The reviewer's ASan repro is
   clean now. Its fuzz harness was adapted to the new calls and run under ASan and UBSan against
   the restructured text: 400 seeds of 200 multi-caret steps, with undo, redo and `set_text`
   mixed in. All passed.
2. **Touching selections typed over put a caret after the wrong text.** The acting editor's
   carets were moved through every change, so a selection ending where the next one's change
   began was pushed past that one's new text.
   - Now the editor works out where each selection lands (`_landed`) and gives that to
     `text_doc_apply`; the doc no longer moves the acting editor's carets.
   - The repro now gives `zz` with carets at 1 and 2, then `zyzy`.
   - The `editor-carets touching typed` arm holds it. Falsified with the old mapping put back:
     the arm went to 0.
3. **After one drag of the scroll thumb, a drag in the text scrolled instead of selecting.** The
   editor had its own copy of the pane's bar and never let go of the thumb.
   - The bar is now the UI's one bar for anything that scrolls (below).
   - At the reviewer's 400 x 300, the old build ends with no selection (`2729 2729`) and the new
     one selects `2620 2682`.
   - The `editor-carets bar_then_drag` arm holds it.
4. **A caret at a selection's start was not merged with it**, so the typing action was refused as
   overlapping. `_merge` now merges selections that touch where either is a caret, and ties sort by
   end. Arm: `editor-carets caret_at_start merged`. Falsified with the old test put back: the arm
   went to 0.
5. **With a stateful highlighter, idle mode could leave the screen uncoloured.** The draw now
   returns a wake of now when a line it drew came back without colour.
6. **The atlas growing mid-frame garbled glyphs already drawn that frame.** The draw returns a wake
   of now when the atlas grew while it drew. The texture is now also uploaded at the next glyph
   asked for rather than at a new size, so the layout pass can size the face without touching GL.

**The lower-severity findings, all applied:**
- the drag's grabbed unit is held to the text;
- the tab width is clamped (`_tab`);
- `'\r'` is no longer a blank in `ui_typing_class`, as the field had it before 14.4;
- a change asked for from inside `on_action` is refused by name, with the `doc-undo inside refused`
  arm;
- the view's top row is held to its line's rows (`_top`);
- host ranges are capped per layer, not across all layers;
- bracket matching and the bracket object read a line at a time.

**Structure:**
- **The text** has one path for every change, `_run`, under the action, the undo and the host's
  edit.
  - One failure policy: changes made before running out of memory stand, and the undo history,
    which no longer matches, is let go.
  - `_replace` is split into the in-line edit and the lines' rewrite.
  - The removed bytes are copied into one block.
  - `_history_reaches` holds the version window.
  - `TextUndoStep.typed` is gone, since an unsealed history already says it.
  - The view's `lines` and `map` callbacks became one, `changed`, carrying a `TextViewChange`, and
    `text_doc_map_selection` holds the actor rule in one place.
  - `text_doc_byte` replaces the editor's one-byte copies.
  - The editor owns the edits' order; the doc refuses them out of order rather than sorting again.
- **Colour** is a ring of 65,536 spans. A line whose spans were written over colours itself again
  when drawn, so letting colour go no longer walks every line. One `_coloured` serves the draw's
  lookup and the stateful walk.
- **`ui.c`** reaches the field and the editor through one table, `UIWidgetOps`, in the private
  `ui_internal.h`. `_emit`, the key routing, the press and the drag are kind-free. The field's
  hooks are static, with the same signatures as the editor's.
- **The bar** is defined once for a pane or an editor (`ui_bar_place`, `ui_bar_at`,
  `_scroll_place`), and the wheel goes to the deepest thing that scrolls. The editor's copy of the
  constants, its grab state and both of its bar branches are gone.
- **The editor's geometry** is settled by the layout pass (`place`); the input hooks and the draw
  read it.
- **Inside the editor:**
  - two column walks, `_col_after` and `_byte_near`, replace seven copies;
  - a line's rows come back as a value, `Rows`, from a one-line wrap cache, rather than through
    hidden scratch;
  - `_top` and `_rows_down` walk the rows;
  - the draw's four band passes share `_band` and `_on_row`, and the ranges are read once, before
    the loop;
  - the word and line objects hold the logic the pointer's double and triple clicks use;
  - caret helpers: `_carets_one`, `_carets_add`, `_follow`;
  - `_find` takes a `Query`, so Cmd+D no longer swaps the editor's own query;
  - the command table has its steps inline and no flags smuggled through `user`;
  - one `_newline`, one `_caret_edits`, one `SPACES`.
  - `_of` and `_seen` stay two. Merged into one taking a const element, cppcheck's
    `constParameterPointer` asked for every entry point that changes the editor to take its
    element const, which would change public signatures.
- **`ui_typing`** holds the run of presses (`UITypingPresses`), the blink (`UITypingCaret`), a
  bounded character step (`ui_typing_next`) and the word end, which the field and the editor both
  use.
- **The probe's vim mode** keeps its state in the modes' `user`.
- **`gates.py`:** `doc_flags` is built on `_probe_wrong`, and `idle-editor` reads `_canvas_run`.
- **The canvas app's parse thread** begins and ends its work with the engine, as the board thread
  does. Its result is taken on the frame that end wakes; `--editor-lag` still pins it for a
  headless run.

**Speed.** A line edited within itself is wrapped again at once, so typing no longer turns the line
into a guess for the budget. The budget wraps the lines an edit rewrote before walking the text for
others. Selections are found by binary search, find scans from just before the row, and the ranges
that colour text are picked out once a frame. The bench, release, ms:

| | 10 MB before | 10 MB after | 64 MB before | 64 MB after |
|---|---|---|---|---|
| a keystroke, one caret | 0.17 | 0.11 | 0.36 | 0.11 |
| a keystroke, 100 carets | 0.82 | 0.50 | 3.20 | 2.25 |
| Enter, one caret | | 0.20 | | 0.74 |
| Enter, 100 carets | | 6.45 | | 41.8 |
| a jump | 0.15 | 0.12 | 0.15 | 0.12 |
| the budget's longest frame | 0.97 | 0.82 | 0.96 | 0.87 |

**Enter at 100 carets misses the 1 ms bar.** The efficiency review predicted it. Each line break
moves every line after it in the text's array and in the editor's rows, once per caret. A fix
rebuilds both once an action, which reaches across the text and every view, so it is a question for
the user rather than done here.

**Not applied:**
- **Questions, needing new public names:**
  - text objects as an operand of `ui_editor_apply`;
  - a smart-home motion;
  - a way to free a UI element or screen early, so `gone` could go;
  - a public bounded UTF-8 step (the private `ui_typing_next` serves both users for now).
- **Deferred:**
  - a tree of line lengths and row counts, for the 64 MB walks;
  - a link from an element to its UI, so the clipboard works before the first layout.
- **Skipped as low value:**
  - the field's undo-join blank set (a space) against the text's (a space or a tab);
  - `_ranges_in` scanning each layer from its start;
  - the undo array's shift past 10,000 steps;
  - find skipping ahead with `memchr`;
  - the canvas app copying the whole text for each parse;
  - the probe's input helpers duplicating `ui_text_probe.c`'s, and its `printf` lines beside
    `say_flag`;
  - `EDITOR_FONT` written in three apps' files;
  - the canvas app's `draw_bitmap_line`;
  - the glyph atlas's texture setup (an R8 with a swizzle, which `create_texture_2d_float` does not
    make);
  - `_map_ranges` walking every range per change.
