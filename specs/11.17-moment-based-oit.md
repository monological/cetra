# B6 — Moment-based OIT (Münstermann 2018)

## Context

Transparency today is weighted-blended OIT (spec 4.17, `--oit`, off by default):
each fragment's occlusion is approximated by a depth-weight curve, summed
order-independently. It is cheap and stable, but the weight is a heuristic, and
4.17's own deferred list names the defect and the successor:

> the McGuire depth weight **saturates for near-camera fragments** (the fixture
> quads all hit the ceiling), so it is *effectively uniform weighting* there
> — `specs/4.17-oit.md:141-143`
> moment-based OIT or dual-depth peeling for exactness — `:152-155`

MBOIT replaces the guess with a measurement: pass 1 accumulates a compact
statistical summary of absorbance along each pixel's depth axis (4 **power**
moments + total optical depth `b0` — power, not trigonometric, because trig
moments need complex arithmetic and the whole shader tree is pinned at
`#version 330 core`, all 78 files). Pass 2 reconstructs transmittance at each
fragment's own depth from those moments and weights its colour by it.

Roadmap row 16, effort L, unparked since Tier 2 landed with 11.13. Stated best
customer: **hair card tips (B8)**, whose plan already has soft tips opting into
MBOIT while the rest rides alpha-to-coverage.

## Two findings that shape this

**1. The existing fixtures cannot judge it.** `oit_fixture.gltf` is three quads at
nearly one depth — precisely where 4.17 measured the weight already saturating to
uniform, so WBOIT and MBOIT will agree there by construction. It is a
no-regression check, not a demonstration. What discriminates is **depth spread**,
not layer count. Hence Phase 0.

**2. `pbr_frag` has no free texture unit, and the escape is already load-bearing.**
All 16 are taken, pinned by a `_Static_assert` chain (`render.c:32-59`). But the
OIT accumulate is routed to `is_blend && !is_transmissive` (`render.c:314-319`),
so a fragment in that pass **cannot** be sampling `TEXUNIT_SCENE_COLOR` (unit 6,
the refraction resolve) — transmission wins over OIT and takes the other path.
Unit 6 is therefore free *by construction* during exactly the pass that needs it,
enforced by existing routing rather than by convention. The moments bind there.

## Design

**Moment generation gets its own FBO, mirroring `_ensure_oit_targets`
(`engine.c:2458-2484`) line for line.** `pbr_frag` already declares outputs at
locations 0-7 — the entire GL 4.1 guaranteed draw-buffer budget — split across the
scene FBO (0-4, 7) and the OIT FBO (5, 6). Locations 5/6 are the only free
fragment outputs, and a 4-moment MBOIT needs exactly their shape:

| location | moment FBO | matches |
|---|---|---|
| 5 | RGBA16F — power moments `b1..b4` | `oit_accum` format exactly |
| 6 | R32F — optical depth `b0` | `oit_revealage`'s slot, widened for conditioning |

So: no change to `GBUFFER_DRAW_BUFFER_SLOTS`, no change to
`engine_set_scene_draw_buffers`, no new output locations in `pbr_frag`.

**Three transparent traversals, not two.** Today OIT already draws transparents
twice (`render.c:847-874`) — once into the OIT FBO, once into the scene FBO for
transmissives. The moment pass slots in as a third bracket *before* the
accumulate, with `current_program = 0; current_material = NULL;` between brackets
— that reset is load-bearing, it is what forces `oitPass` to re-upload
(`render.c:395`).

**Reuse, don't invent:** `oit_mesh_count` (`scene.h:118`) gates it unchanged — the
mesh set is identical. The `oit_enabled`/`oit_this_frame` intent-vs-actual split
(`engine.h:131,179`) is copied exactly; 4.17's R-phase found a real bug from
keying routing on intent, and transparents vanished when the toggle was on but the
pass did not run (`specs/4.17-oit.md:126-130`). The resolve is a postfx pass built
like `create_oit_resolve_program` (`program.c:945-947`), where units are per-program
and ~13 are free. The gate is threaded as a folded FBO handle
(`moment_this_frame ? moment_fbo : 0`), matching `engine.c:2262-2264`.

## Phase 0 — a fixture that can tell the two apart

`assets/gen_oit_cards_fixture.py` → `oit_cards_fixture.gltf` + `.cscn`: ~12 thin
quads, alpha ~0.15, **staggered across a large depth range** (the discriminating
variable, per finding 1), viewed near-grazing. Approximates hair-card tips, which
is what B6 exists for.

Its correct composite is analytic: for N layers of uniform alpha `a` over a
background, transmittance is `(1-a)^N` and the composite is a geometric series —
a number, not an eyeball. Gate asserts measured-vs-analytic, following
`run_skin_offpath_gate` (`gates.py:343-402`), including **its inverse half**: an
opted-in fixture must differ, "else the zeros prove nothing."

Pin `--exposure 0.08` — 4.17 records that lit flat quads blow out otherwise
(`:115-117`).

Gate: WBOIT's error against analytic is *measured and recorded* here, before any
MBOIT exists. That number is what MBOIT has to beat.

## Phase 1 — moment generation

- `_ensure_moment_targets` cloned from `_ensure_oit_targets`; fields beside
  `engine.h:112-115`, zero-init beside `engine.c:183-187`, **teardown beside
  `engine.c:484-488`** — mandatory, the FBO aliases `depth_renderbuffer` and a
  missed teardown leaves a dangling attachment after any resize or MSAA change.
- `engine_begin_moment_pass` / `engine_end_moment_pass`; additive blend on both
  slots, depth test live via the shared depth RB, `glDepthMask(GL_FALSE)` already
  set by the caller.
- `include/mboit.glsl`: absorbance → moment vector. Shared-include idiom so a
  constant cannot drift between generation and reconstruction (precedent:
  `include/preintegrated_skin.glsl`, designed that way in `specs/11.13:266-270`).
- `oitPass` extends to a 3-value mode (0 off / 1 accumulate / 2 moments).

Gate: moments render; off path still 0 px; fixture unchanged.

## Phase 2 — reconstruction and the weighted colour pass

- Hamburger 4-moment solver in `include/mboit.glsl` — biased Cholesky, the
  standard conditioning fix for the moment problem.
- Resolve moments MSAA→single-sample with `resolve_color_attachment`
  (`postfx.c:1908-1915`), then bind on **unit 6** for the accumulate pass.
- Accumulate weights colour by reconstructed transmittance instead of
  `oitWeight()` (`pbr_frag.glsl:718-723`), into the existing accum/revealage
  targets, so the existing composite (`postfx_run_oit`, `postfx.c:2554`) is reused
  unchanged.

Gate: the Phase 0 analytic error must beat the WBOIT number recorded there.

## Phase 3 — toggle, and off is byte-identical

`--oit-moments` following `--oit` exactly: `render_args.h:115` → usage
`render.c:167` → parse `render.c:752-755` → apply `render.c:1803-1805` →
`engine.h:179` → `igCheckbox` in the feature block `engine.c:2069-2078`. Docs:
`CLAUDE.md` toggle list, pass order, postfx chain, shader index; README bullet.

**The hard rule, from 4.17's biggest recorded risk (`:98-99, :65-67`): never touch
`FragColor`'s expression or grouping.** Everything new goes behind a
uniform-guarded `if` so it dead-code-eliminates on the off path. Reassociating
that expression shifts every golden by an LSB.

## Risks, with the measurement that settles each

| Risk | Settled by |
|---|---|
| **MSAA resolve bias.** `glBlitFramebuffer` box-averages samples. Moments *sum* linearly, but reconstruction is nonlinear, so averaged moments ≠ average of reconstructions — biased at every silhouette crossing an MSAA edge, i.e. exactly hair tips. | Ship the blit first (mirrors WBOIT, cheapest), **measure on the Phase 0 fixture**. If it fails, the fallback is already built: single-sample moments over `engine_resolve_scene_depth` (`engine.c:2399-2449`), which the particle pass already uses. Third option, `sampler2DMS` in the resolve, would be the corpus's first — avoid. |
| **Is 4 moments enough for 12 layers?** | The Phase 0 analytic number answers it directly. If not, 6/8 moments need a third target and exceed the free-slot budget — that is a re-plan, not a tweak. |
| **Memory.** Roughly doubles OIT's footprint (~100 → ~200 MB at 1080p/4×). | Logged at allocation like the shadow budget does. |
| **Ordering vs shadow catcher.** OIT composites after the scene FBO resolves, so translucency behind the catcher lands in front (`4.17:144-147`). MBOIT inherits it. | Out of scope; recorded, not fixed. |

## Verification

1. **Off → 0 px** on `oit_fixture`, `oit_sphere_fixture`, `cornell_box`, and the
   raiden recipe, against a build of the base commit — not against committed
   images. `--no-auto-exposure -E 1.0` is load-bearing (`AGENTS.md:548-568`:
   auto-exposure moved 99.77% of pixels on a provable no-op).
2. **`python3 scripts/gates.py`** green, including the new analytic OIT gate.
3. **Determinism ×2** — headless bit-identical.
4. **Orbit strip** on `oit_sphere_fixture` (`--screenshot-every`): layering stable,
   no popping, matching 4.17's own ON-path protocol (`:86-94`).
5. **First OIT golden** — there is none today. Bake one once MBOIT is trusted, and
   verify it differs from `--no-oit` by a large margin, so it cannot pass by
   pinning a frame where the feature does nothing (`specs/11.14:295-303`).

# As built

Shipped. Moment weighting lands **4.94x closer to the arithmetic** than the
weighted-blended weight it replaces: 0.0157 RMS against 0.0773, on a stack of
twelve translucent layers spread over a 25:1 range of view distance. Every scene
that does not ask for it is byte-identical to a build of the base commit,
including the weighted-blended path itself.

Three things in the plan above were wrong, and two of them changed the design.

## The plan's finding 2 was right about the unit and wrong about why

The plan argued that unit 6 is free during the OIT accumulate — that part holds,
and holds structurally: the accumulate is routed to `is_blend &&
!is_transmissive`, and `sceneColorTex` is read only where `transmission > 0`, so
the two tenants are kept apart by the routing rather than by a convention.

What does not hold is the conclusion that a free unit means a free *sampler*.
Adding one produced, immediately:

    Implementation limit of 16 active fragment shader samplers exceeded,
    fragment shader uses 17 samplers

The driver counts **declared** samplers, not distinct units. `pbr_frag` declares
exactly sixteen. There is no seventeenth for any unit, free or not, and no
amount of aliasing changes that — the moments have to arrive through a sampler
that already exists.

Two consequences.

**The moments are read through `sceneColorTex` itself**, with `#define
oitMomentTex sceneColorTex` so the reading site still says what it means. One
declaration, two tenants, disjoint by routing.

**And they have to fit in four floats, when a four-power-moment scheme needs
five** — `b0` and `b1..b4`. Everything stored has to be a real number the
hardware can add, because the accumulation IS a `GL_ONE`/`GL_ONE` blend, so no
packing trick is available. Dropping to three moments does not help either: the
Hamburger machinery wants an even count, and `(b0, b1, b2, b3)` buys exactly the
two-moment bound with a wasted channel.

So the generation pass keeps its two render targets and they are resolved into
**one double-height atlas** — `b1..b4` in the lower half, `b0` in the upper, one
`sampler2D`, two taps half a texture apart. Both targets are RGBA32F-shaped for
this reason alone: a multisample resolve blit demands identical formats, and
`glBlitFramebuffer` allows a destination offset (it forbids scaling, not
translation), so the two halves are two blits and there is no packing pass.

## The composite is not reused unchanged

The plan said the existing composite could be. It cannot, and the reason is the
point of the feature: weighted-blended accumulates a weighted AVERAGE of
candidate colours and has to be divided by its own weight sum, while moment
weighting accumulates each layer already scaled by its true transmittance, so
the sum IS the foreground. `oit_resolve_frag` takes a `momentWeighted` uniform
and the C side switches the blend from `(GL_ONE_MINUS_SRC_ALPHA, GL_SRC_ALPHA)`
to `(GL_ONE, GL_SRC_ALPHA)`.

## What the constants are worth, measured

Everything below is RMS against the arithmetic on `oit_cards_fixture`, where
weighted-blended measures 0.0773.

| variant | RMS | note |
|---|---|---|
| **shipped** — fp32 targets, bias 5e-7, overestimation 0.25 | **0.0157** | 4.94x |
| fp16 targets, bias 6e-4 (the reference's 16-bit pair) | 0.0217 | 3.6x, half the memory |
| depth warp fitted to the transparent geometry | 0.0158 | no change |
| overestimation 0.0 | 0.0674 | worse than the weight it replaces |

**Overestimation is load-bearing and counter-intuitive.** Exact alpha
compositing says a layer is not attenuated by itself, so zero looks like the
principled value — and zero is the worst number in the table. The
reconstruction returns a LOWER bound on the absorbance in front, so it
under-occludes by construction, and the reference's quarter is what pays that
back.

**The depth warp's range is not the limit.** Fitting it to the transparent
content moves the warped span from 39% of `[-1, 1]` to all of it and the error
does not move (0.01577 against 0.01565). What limits the reconstruction is how
many moments there are. So the shipped warp uses the camera's own near/far and
no per-frame bound is computed.

**fp32 costs a third of the accuracy to give up**, which is why the targets are
fp32 despite the memory: 156 MB at 640x400 on a Retina framebuffer, 244 MB at
800x500, logged at allocation. That is the largest single allocation the
renderer makes, and it is opt-in and lazily allocated.

## The MSAA-resolve risk, still open

The plan named it as the risk with no cheap answer, and it is still unsettled:
the blit box-averages samples, moments sum linearly but `exp(-b0 * F)` does not,
so a 50% coverage edge between `A = 0` and `A = 2` reconstructs 0.368 where the
average transmittance is 0.568.

**The Phase 0 fixture cannot arbitrate it.** Its cards are parallel to the image
plane and the bands are sampled at their centres, precisely so every pixel sees
an integer layer count — which is what makes the gate analytic and what makes it
blind to this. Reasoning rather than measurement, then: single-sample moments
were considered and rejected because they quantize coverage to the pixel centre,
turning that same edge into a choice between 0.135 and 1.0 — a worse error, and
noise rather than smooth bias, on exactly the hair-tip silhouettes the feature
exists for.

## Residual, and where the next gain is

The 0.0157 that survives is the method's own conservatism, and it has a
signature: the deep bands come out systematically BRIGHT, because the bound
under-estimates the absorbance in front and therefore over-estimates
transmittance. Bands 1-4 sit under 0.011; bands 9-12 reach 0.049.

Six or eight power moments would fix it and cannot be built here: they need a
third render target, and there is no third free fragment output location in GL
4.1's guaranteed eight. That is a re-plan, not a tweak, and it would want the
same double-height trick generalised or a different storage scheme entirely.

  under `--oit` — the weighted-blended path included, so the new code is inert

- **`python3 scripts/gates.py`**: 30 pass, 0 fail, including three new OIT arms.
- **Determinism x2**: 0 px, on the card fixture and on the golden's scene.
- **First OIT golden**, `assets/oit_sphere_moments_golden.png`:

      ./out/bin/render -m assets/oit_sphere_fixture.gltf -x -f 30 -W 640 -H 400 \

      magick compare -metric AE out.ppm assets/oit_sphere_moments_golden.png null:

  Battery 17 -> 18. It differs from `--no-oit` by 107383 px, 10.5% of the frame,

## On by default

4.17 shipped OIT off and called flipping it "a later 'live with it' call (like
AgX)". That call is made here: **both OIT and moment weighting default ON.**

The blocker was never the accuracy, it was the ordering defect below, and it is
still open — this is a deliberate trade, not a fix. What makes it affordable is
that the path is gated on `scene->oit_mesh_count > 0`, so a scene with no
translucent mesh allocates nothing, runs no extra pass, and is byte-identical to
`--no-oit`. Only scenes that actually have transparency pay, and those are the
scenes the ordering issue can bite.

Flipping a default is mostly plumbing, and the plumbing had a trap:
`args->oit` was a one-way switch (`if (args.oit) engine->oit_enabled = true`),
which silently ignores `--no-oit` the moment the thing it would disable is
already true. Both flags are now tri-state against the `auto_exposure_override`
precedent, and `--no-oit-moments` is new — without it there was no way to ask
for weighted-blended at all, since `--oit` alone now inherits the default
weighting.

**That last point bit the gate immediately.** Its weighted-blended arm ran
`--oit` and would have measured the moment path against itself, reporting a
1.00x gain. Every arm now names its weighting explicitly.

Measured for the flip:

| scene | vs the base commit's default |
|---|---|
| `cornell_box`, `glass_fixture`, `contact_debug`, and the 17 committed goldens | 0 px |
| `raiden` recipe | 10179 px, **0.12%** — the hair silhouette, nothing else |
| `oit_sphere_fixture` | 107383 px, 10.5% |
| `oit_fixture` | 214011 px, 21.0% |

No committed golden moves, and that is structural rather than lucky: no golden's
scene contains an ALPHA_BLEND mesh, so `oit_mesh_count` is 0 in every one. The
nine-scene shadow battery and the sheen and DoF goldens were re-run to confirm.

`--no-oit` reproduces the base commit's frame at **0 px** on both OIT fixtures,
so the escape hatch is exact rather than approximately equivalent.

The raiden number deserves its own line because it is small enough to read as
noise and is not: the rig carries an alpha-blend mesh, and a baseline captured
before this commit will not compare against one captured after. Recorded in
`AGENTS.md` beside the recipe.

## Deferred

- **Six or eight power moments**, above.
- **MSAA moment bias**, above — wants a fixture with a transparent silhouette
  crossing a sample edge, which is a different fixture than this one.
- ~~**Ordering vs the shadow catcher**~~ — **FIXED in spec 11.18.** Inherited
  from 4.17, and the default flip above raised it from a quirk of an opt-in to
  the one known defect the default carried, so it was fixed immediately after.
  Neither guess at the fix here was right: it needed no composite change at all,
  only the catcher drawn before the transparent pass, which repairs the unsorted
  late pass and the particle depth resolve along with OIT.
- **`oit_fixture` is now known to be undiscriminating** — three quads at one
  depth, where weighted-blended is exact by construction. It stays as a
  no-regression check; it is not evidence about any OIT scheme.

# Review round

Four background audits over the branch (render.c, engine/postfx, the GLSL, and
the app/gates/fixture layer), applied as one commit.

## The one that mattered: generation shaded a whole frame it threw away

`oitPass == 2` needs two values, `finalOpacity` and view depth, and both are
resolved by `pbr_frag.glsl:1060`. Everything after it — the clustered light loop
with its shadow taps, LTC area lights, the three-cubemap IBL block, SSS,
clearcoat, sheen — ran in full and was discarded, and the driver could not
eliminate any of it because `FragColor` is written unconditionally at the end.
Turning both toggles on by default is what made that bill real: **every scene
with an alpha-blend mesh shaded that mesh set twice at full PBR cost.**

Fixed with an early return after `NdotV`, which the shader already had the idiom
for two hundred lines above ("discard early before expensive lighting"). Legal
because the generation FBO binds only locations 5 and 6, and coherent because
`oitPass` is a uniform.

Kept as a mode rather than split into its own program, deliberately: a separate
shader would have to reproduce the UV transform, POM, the mask-array opacity
chain and the Fresnel to reach a bit-identical `finalOpacity`, and the moments
have to describe exactly the opacity the accumulate writes. That drift would be
silent; a mode cannot drift. The Fresnel is now `fresnelOpacity()`, shared by
both sites for the same reason.

## Cost: the hair moves, and why

The early-out is not pixel-free on one asset. The raiden recipe moves **10179 px
(0.12%), RMSE 0.0008, and it is the hair silhouette and nothing else** — the
same mesh and the same magnitude as the default flip itself.

Isolated rather than assumed. With `--no-oit-moments` the two builds are **0 px**:
the accumulate, which uses the same new shared helper, is byte-identical, so the
whole difference enters through the generation pass. The inputs there are
mathematically unchanged, and no `discard` was skipped (all three sit above the
early return). What changed is the instruction stream the compiler schedules
that arithmetic in, so `finalOpacity` differs by ULPs.

ULPs are enough because **the reconstruction is ill-conditioned exactly where
hair lives.** `mboitTransmittance` factors a Hankel matrix that is singular when
several layers sit at one depth — which is what `MBOIT_BIAS` exists to
regularise, and hair strands are the case. The card fixture, whose layers are
deliberately well separated, is bit-identical: the analytic gate reports
`worst 0.04898 rms 0.01565, 4.94x` before and after, to every digit. So is the
`oit_sphere_moments` golden, at 0 px.

Accepted: an A/B of the hair crop is visually indistinguishable, the accuracy
instrument does not move, and the pass it buys is a full PBR shade per blend
mesh per frame. Worth knowing for the same reason the flip itself was: a raiden
baseline captured before this commit will not compare against one after.

## Structural

- **`oitPass` carried two facts.** It encoded which sub-pass was drawing AND
  which weight the accumulate used, so `3` meant "accumulate, moment-weighted" —
  while `oit_resolve_frag`, added in the same commit, modelled the same bit as
  its own `momentWeighted` uniform. One concept, two encodings. Split: `oitPass`
  is now 0/1/2 behind an `OitSubpass` enum in `common.h` (the `RENDER_MODE_*`
  precedent for a C enum mirrored in GLSL), and the weighting rides
  `oitMomentWeighted`, matching the composite.
- **A branch that existed to undo a premature write.** `moments_this_frame` was
  published before its consumer was known to run, so an `else` un-published it.
  It is now written once, inside the branch where the accumulate provably runs,
  and the `else` is gone rather than moved. `engine_end_moment_pass` lost a
  `GLuint` return whose documented 0 case could not occur.
- **`glActiveTexture(GL_TEXTURE6)`** was the only hardcoded unit number in
  `render.c`, on the one unit this branch gave a second tenant. The
  `_Static_assert` wall pins relative ORDER, not values, so moving
  `TEXUNIT_SCENE_COLOR` would have broken refraction and MBOIT with every assert
  still green. Now `GL_TEXTURE0 + TEXUNIT_SCENE_COLOR`.
- **Two loose bools on `postfx_run`** moved into `PostFXGBufferWrites`, whose own
  comment already says it exists to carry the engine's frame-start decisions.
  The "meaningless when `oit_fbo` is 0" caveat became structural adjacency.
- **The atlas layout** now lives in `mboit.glsl` as `MBOIT_ATLAS_B0_TAP` beside
  the reconstruction that reads it, instead of being restated in three files.
  `oitMomentWeight` was a wrapper and is gone.
- **`oitNearFar` / `oitMomentInvSize`** uploaded on every program switch of every
  pass, guarded on "has the generation pass ever allocated" rather than "does
  this pass read them". Now scoped to the sub-passes that do. The `if (camera)`
  beside them was dead — `render_current_scene` returns on a null camera and both
  helpers are static.

## Documentation defects the audits caught

Four claims in this branch's own comments were wrong, three of them about things
a reader would act on:

- **The atlas orientation was documented backwards in four places** — this spec,
  `engine.h`, `render.c` and `pbr_frag.glsl` all said b0 sat below b1..b4. The
  blit puts b0 at `y ∈ [rh, 2rh)` and the shader taps it at `+0.5`; code and
  shader agreed with each other and with nothing else. This is the one fact
  someone editing the blit offsets needs.
- **"Both generation targets are RGBA16F"** sat directly above two `GL_RGBA32F`
  calls, stale from the variant this spec's own measurements rejected.
- **The flipped default carried a comment describing the ordering defect 11.18
  fixed two commits later** — on the highest-traffic line in the diff, telling
  the next reader the default shipped a known bug.
- **`mboit.glsl` claimed a guarantee it did not provide** ("both passes include
  this file so a constant cannot drift"): both passes are in `pbr_frag`, so there
  was one includer and nothing to drift. The bias vector's description was also
  wrong — it is a conditioning constant, not the moments of a uniform
  distribution, which would be 1/3 and 1/5.

Also: the catcher comments in `render.c` narrated the change ("that is *now*
load-bearing *rather than* incidental") instead of stating the invariant, which
is changelog voice in code.

## The app and tooling layer

- **`render_args.h`'s diff was 158 lines for two fields.** Five real insertions;
  the other 152 were clang-format re-aligning trailing comments, because a block
  comment inserted mid-struct splits an alignment run. That re-pointed `git blame`
  for 76 fields at this commit, in the header that IS the CLI contract, and it
  would recur on the next field added nearby. Moving the tri-state note into the
  trailing comments — which is why `auto_exposure_override` never caused this —
  makes the diff **3 lines** and format-stable.
- **`_cscn_camera`** reads a fixture's camera out of its own `.cscn` instead of
  transcribing it. Three gates had hand-synced copies; this branch added the
  third. The failure mode it removes is silent: the gate keeps passing while
  measuring a different scene than it predicts.
- **`--oit` and `--oit-moments` were undocumented in `--help`** while `gates.py`
  depends on both, so anyone debugging a gate failure would conclude the gate
  invoked a flag that does not exist.
- **Two "undo the display encode" helpers disagree** in `gates.py`:
  `_oit_untonemap` uses `pow(2.2)`, which matches `tonemap_frag`'s
  `displayEncode`; the older `_linear_rgb` uses the sRGB piecewise curve, which
  does not. Recorded at the new one rather than reconciled — every existing
  threshold is fitted through the old curve.

## Not taken

- **Decomposing `render_current_scene`** into named pass functions. The audit
  makes the case well — 11.18 moving one pass one slot cost an 85-line block
  relocation that git renders as a 130-line delete/insert — and the argument is
  sound. It is a larger change than a review round should carry, and it belongs
  with its own before/after.
