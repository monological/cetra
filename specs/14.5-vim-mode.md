# 14.5: the vim mode

## Context

**Why this comes before pcb 6.1.** pcb's step 6, the window, starts with spec 6.1: the window and
the code view on cetra's code editor (spec 14.4). The user wants that editor to be **vim, and only
vim**:
- `i` enters insert mode and Esc leaves it;
- visual modes;
- `/` searches the text.

The vim mode is built in cetra, beside the standard mode, as a ready-made mode any cetra app can
use, and pcb stacks its own keys on top. So it is cetra spec 14.5, and pcb 6.1 is planned once it
is built. The decisions already made for 6.1 are kept at the end of this plan.

14.4 built the editor on modes so that a vim mode would be an addition and not a rewrite. Its
`ui-editor-mode` arm built a toy vim mode from the public calls alone. The machinery reading that
mode has gaps a real vim exposes, listed under "Found while planning"; 14.5 closes them.

**Numbering and name.** `specs/14.5-vim-mode.md`, on branch `14.5-vim-mode`. It is a new row in
`docs/eda-roadmap.md`, taking "the vim mode itself" out of item 6's "left for later".

### Decided with the user in planning (2026-10-30)

- **Vim only, in pcb's code view.** cetra keeps both modes; pcb shows only vim.
- **Built in cetra**, as spec 14.5, before pcb 6.1.
- **Undo goes by vim's units.**
  - One normal-mode command (`dw`, `p`, `3>>`) is one step.
  - So is an insert session, from `i` (or `c`, `o`, `A`...) to Esc.
  - A host keeping its own timeline groups its steps the same way, from the actions the text
    reports.
- **Space is pcb's help key**, in normal mode and the views that do not type. The user notes it can
  change later: it is one line in pcb's key table. Vim's own Space (move right) is given up there.
- **`/` searches what the focused view shows:** text in the code view, as vim does, and parts and
  nets in the schematic, layout and 3D views.

### Decided in planning, with reasons (the user can overrule any)

- **One vim per host, shared by all its editors.** This is vim's own model: the mode, a half-typed
  command, the count, the registers, the last search, the last `f`/`t` and the last change for `.`
  all belong to the person typing, not the buffer. The selections stay each editor's own. pcb will
  have an editor per open file, and one vim object serves them all.
- **The vim mode stands alone; it does not fall back to the standard mode.**
  - In vim's normal mode Enter moves down and Backspace moves left. Falling back to the standard
    mode, as the 14.4 probe's toy did, gave Enter a newline in normal mode.
  - Vim takes every key it means: arrows, Home and End, Page Up and Down, Tab, and Esc.
  - It declines what it does not use, so a host's layer, then the screen, may take it. Esc in
    normal mode with one caret and nothing pending is declined.
- **The unnamed register is the system clipboard**, as with vim's `clipboard=unnamedplus`.
  - `y`, `d`, `c` and `x` write the clipboard, and `p` reads it.
  - Vim remembers whether its last yank was whole lines. `p` pastes whole lines when the clipboard
    still holds exactly that text.
  - Named registers are left for later.
- **Search ignores case unless the query has a capital** (vim's `ignorecase` + `smartcase`), with
  plain text, as cetra's find matches today. Regular expressions are left for later, as in 14.4.
- **Several carets work in every command.** Ctrl+V's block selection is a selection per line, and
  `I` or `A` then types at every one.
- **Vim itself is the reference.** vim 9.2 is installed (`/opt/homebrew/bin/vim`) and runs
  headless with `-es` and `normal!`. Tried in planning on a pcb fixture, it ran a sequence of
  `dw`, `ciw`, `u`, Ctrl+R and `.` correctly.

  So the tests run each key sequence through both cetra's vim and vim on the same text, and
  compare the text and the cursor. This is done for a fixed corpus and for thousands of seeded
  random sequences. On a machine without vim, those arms skip.

### Found while planning

- **`types` and `block_caret` are read from the top mode only**, and `name` is never read by the
  editor (`ui_editor.c:2139`, `:2263`). So a host layer on top decides whether keys type. A vim
  that changes state underneath it could not show its caret or stop typing.
- **A binding whose command declines ends the walk**: the key goes to the screen, not to the parent
  (`ui_editor.c:2122-2147`). So a host key that should act only in normal mode, such as Space,
  cannot hand the key on in insert mode.
- **A press makes two events**: a key event, then a character event with no modifiers
  (`engine.c:1733-1749`). A host binding on a printable key, such as Space, would run and then
  the character would still be typed or read.
- **A mode's `user` is per mode, and an editor has no slot for a mode's state**; nothing is called
  when the pointer changes the selections.
- **Selections are half-open `[lo, hi)` and drawn the same in every mode.**
  - There is no inclusive or whole-line selection.
  - The block caret covers the character after the head.
- **The primitives' vim gaps:**
  - `CHAR_LEFT` and `CHAR_RIGHT` cross line breaks.
  - `WORD_RIGHT` differs by platform.
  - `ROW_START` and `ROW_END` are screen rows, not lines.
  - There is no `f`/`t`, `W`/`B`/`E`, `ge`, paragraph or go-to-line motion.
  - The objects lack quote kinds, bracket kinds, a word with its space, and paragraphs.
  - `ui_editor_apply` uses its motion only where a caret has no selection.
  - Paste has no whole-line form.
- **Text objects as an operator's operand**, 14.4's open API question, needs no new call: select
  the object at each caret, then apply the operator to the selections.
- **Undo joins only typed inserts, and nothing groups several actions into one step**
  (`text_doc.c:492-561`). An insert session holds Backspaces and Enters, which are their own steps
  today.
- **Find is literal, within one line, and folds ASCII case only** (`ui_editor.c:1112-1160`).
- Sizes: `ui_editor.c` 2,395 lines, `text_doc.c` 1,013, the probe 1,284.

## The design

### 1. The editor's seams

These are general, not vim's own; the standard mode and the canvas app's host mode go through them
too.

- **Layers.** `UIEditorMode` gains `layer`.
  - A layer adds keys over its parent and takes everything else from it: `types`, `block_caret`,
    `name`, the selection shape and the pointer hook.
  - The editor resolves these from the first mode in the chain that is not a layer.
  - The canvas app's host mode and the probe's host-undo mode become layers.
  - A host shows the state through `ui_editor_mode(el)`, which resolves the same way.
- **A declining command passes the key to the parent**, not to the screen. With no parent left,
  the key goes to the screen as now. `single-caret` keeps its behaviour, since the standard mode
  has no parent.
- **A key a mode uses takes its character with it.** `_route_keys` drops the character event that
  directly follows a key event the editor used. So a host's Space binding does not also move right
  or type a space. Characters arriving on their own, from an input method or the script's `type=`,
  are untouched.
- **Selection shapes.** `UIEditorMode.selection` takes one of three values:
  - `UI_SELECTION_SPAN`: `[lo, hi)`, as now.
  - `UI_SELECTION_INCLUSIVE`: the character at the far end counts too, as in vim's visual mode.
  - `UI_SELECTION_LINES`: whole lines, as in visual line mode.

  It changes only how bands are drawn. The mode is what acts on the range. The block caret covers
  the character at the head, which is vim's cursor in every state.
- **A pointer hook.** `UIEditorMode.pointer` is called after a press or a drag changed the
  selections, so vim enters visual mode on a drag and keeps the cursor on a character after a
  click.
- **Undo steps.**
  - `TextDocAction` gains `step`, a serial: the actions sharing one are one undo step, for the
    text's own undo and for a host's timeline alike.
  - A private `text_doc_group(doc, bool open)` holds one step open across any actions until it is
    closed.
  - The standard mode's word joining gives the same serial to what it joins, so its undo is
    unchanged.
- **What vim needs from the editor, as private calls** in `ui_editor_internal.h`. Vim's file
  reaches them; nothing new is public:
  - edits at every caret as one action, with the selections after;
  - the text's line at an offset;
  - scrolling a row to the top, middle or bottom (`zt`, `zz`, `zb`);
  - the rows in view (`H`, `M`, `L`, Ctrl+D and Ctrl+U).

  The motions vim adds live in its own file, since most take arguments the public enum cannot
  carry, such as `f`'s character.

### 2. The vim mode: `cetra/src/ui_editor_vim.c/h`

- **The object.**
  - `create_ui_editor_vim()` returns a `UIEditorVim` holding the state, and its base mode is
    `ui_editor_vim_mode(vim)`.
  - A host sets that mode on its editors, or a layer of its own over it.
  - `ui_editor_vim_state(vim)` returns `UI_VIM_NORMAL`, `_INSERT`, `_VISUAL`, `_VISUAL_LINE` or
    `_VISUAL_BLOCK`.
  - `ui_editor_vim_pending(vim)` returns the keys of an unfinished command (`2d`), for a host's
    status line.
  - The base mode's `name` is `NORMAL`, `INSERT`, `VISUAL`, `V-LINE` or `V-BLOCK`.
- **Keys** are read from characters (so `$`, `%` and `A` come as typed on any keyboard layout) and
  from key events (Esc, Enter, Backspace, arrows, and the Ctrl keys).
- **Normal mode.**
  - **Counts** before a command and between operator and motion, multiplied: `3dw`, `d3w`, `2d3w`.
  - **Motions:**
    - characters and lines: `h j k l`;
    - words: `w b e ge`, and `W B E gE` for words split at blanks only;
    - line positions: `0 ^ $ _`;
    - text positions: `gg G {N}G`;
    - on the line: `f F t T ; ,`;
    - brackets and paragraphs: `% { }`;
    - the rows in view: `H M L`;
    - rows of a wrapped line: `gj gk`;
    - scrolling: Ctrl+D, U, F and B, and `zt zz zb`.

    `h` and `l` stop at the line's ends, and the cursor sits on a character, never past the
    line's last one.
  - **Operators** with any motion or object: `d c y > < g~ gu gU`, each doubled for a line (`dd`,
    `cc`, `yy`, `>>`). A motion is exclusive or inclusive, characterwise or linewise, as vim
    defines it, so `dw`, `de` and `dj` take what vim takes.
  - **Edits:** `x X s S D C Y J r ~ p P o O i a I A`, and counts on inserts (`3ihi` Esc).
  - **`u` and Ctrl+R** undo and redo through the text's undo, or through the host's when it sets
    `ui_editor_vim_set_undo(vim, undo, redo, user)`. A host taking undo leaves `u` meaning undo
    in normal mode and lowercase in visual.
  - **`.`** repeats the last change, with a new count if given. Vim records the events from the
    change's first key to its end and plays them again.
  - **Esc** drops a pending command, and goes to one caret when there are several.
- **Insert mode.**
  - Characters type.
  - Enter keeps the indent.
  - Tab indents by the text's setting.
  - Backspace and Delete delete; Ctrl+W deletes a word back and Ctrl+U to the line's start.
  - The arrows move and close the step, as in vim.
  - Esc or Ctrl+[ returns to normal mode, the cursor stepping back onto the last character.
- **Visual modes.**
  - `v`, `V` and Ctrl+V enter them, `o` swaps the ends, and Esc leaves.
  - The operators and `x J r ~ u U > < p` work on the selection.
  - `I` and `A` in block mode type at every line's caret.
  - `iw aw iW aW`, the bracket objects (`i( a( i[ a[ i{ a{ i< a<`, `ib ab iB aB`), the quote
    objects (`i" a" i' a' i\` a\``) and the paragraph objects (`ip ap`) work in visual mode and
    after an operator.
- **Search.**
  - `/` and `?` ask the host for a prompt through `ui_editor_vim_set_prompt(vim, fn, user)`, since
    the line is the app's as the find box was.
  - On Enter the host calls `ui_editor_vim_search(vim, el, query, backward)`, and it may call
    `ui_editor_find` as the query is typed, to light matches.
  - `n` and `N` repeat in the search's direction.
  - `*` and `#` search for the whole word under the cursor.
- **`:`** asks the same prompt. The host runs the line through `ui_editor_vim_command(vim, el,
  text)`, which knows `:N` (go to line N) and `:noh`, and returns false for anything else, which is
  the host's (pcb's `:w`, `:q`, its commands by name).
- **Clipboard keys on macOS:**
  - Cmd+C copies the visual selection.
  - Cmd+V pastes in insert and normal mode.
  - Elsewhere Ctrl+V is vim's block selection, so the clipboard is reached through `y` and `p`.
- **The list of keys.** `ui_editor_vim_keys(&count)` gives each key or sequence with a line of
  description, for a host's help screen.
- **Not in 14.5:**
  - named registers;
  - macros (`q`, `@`);
  - marks;
  - the jump list (Ctrl+O, Ctrl+I);
  - `:s` and ranges;
  - replace mode `R`;
  - `gv`;
  - `=` and `gq`;
  - Ctrl+A and Ctrl+X;
  - insert completion;
  - tag objects (`it`).

## Carried to pcb 6.1 (planned after 14.5 is built)

**Decided with the user:**
- **cetra master is pushed** for the submodule bump.
- **The chat column is left out until step 9.**
- **Vim only.** Space is help; `/` searches the focused view; `:` is the command line (the palette
  typed); Cmd+K is the palette; Cmd+P jumps to a file, part, net or definition; `gd` goes to a
  name's definition.
- **Typing becomes undo steps by vim's units.** It is saved to disk at each half-second pause in
  insert mode, those saves joined into the session's one history step. `u` and Ctrl+R are pcb's
  timeline, through `ui_editor_vim_set_undo`.

**Found exploring pcb, for 6.1's plan:**
- **The core evaluates from memory** (`design_changed`, `eval_design`) and has no mutable globals,
  so a worker thread can evaluate the editor's text. The sample is 49 files, 176 KB, about 40 ms an
  evaluation in the sanitizer build. A syntax error anywhere gives the reader's errors only, no
  board.
- **No line lexer exists.** The scanners in `syntax.c` are static and `form.c`'s form words are
  private. 6.1 wants one lexer the reader and the colouring share.
- **The history's record and undo paths are the CLI's.** `commands.c` and `cmd_undo.c` print and
  hold the lock from open to close; one held for a session would block every `pcb edit`. 6.1
  moves them into the core, returning results instead of printing, and takes the lock for each
  save only.
- **Typed versions need a new cause, `:typed`**, which an older pcb refuses to read. Step names
  (`continues_step`) already join consecutive versions.
- **Writing files the window saves itself would be logged as `outside`** by the next recording, so
  the window saves through the recording path. `design_write` refuses when the disk changed, which
  is where an outside change during typing is caught. `linediff_revert` is the three-way line
  merge for it.
- **The window today is cetra's old 2D demo** on `CanvasController`, renamed `PlaneDrag` in 14.0.
  It is replaced whole.
- **pcb has no asset path.** The fonts come from the submodule's `assets/fonts/`.
- **The editor has no `set_doc`, and the UI cannot hide or free an element**, so 6.1 gives each
  open file a screen of its own, swapped on the stack.
- **Tests shell out to `PCB_BINARY`, with byte-exact goldens.** Nothing tests the window yet.

# As built

## Phase 1: the editor's seams, as built

- **Layers.** `UIEditorMode.layer`: the editor reads `types`, `block_caret`, `selection` and
  `pointer` from the first mode up the chain that is not a layer (`_look`, `ui_editor.c`). The
  canvas app's host mode and the probe's host-undo mode are layers now. `ui_editor_mode` still
  returns the mode set, the inverse of `ui_editor_set_mode`, rather than resolving as the plan
  said: a host shows a vim mode's state through `ui_editor_vim_state`, and walking the chain for
  a name is one loop.
- **A declining command hands its key to the parent** (`_walk`); with no parent left the key goes
  to the screen, as before.
- **A key a mode uses takes its press's character -- inside the editor, not in `_route_keys`.**
  The plan put the drop in `ui.c`, but the text field uses every key event, letters included, so
  a drop there would have stopped every field typing. The editor keeps a flag instead, set when a
  key it used is one that makes a character (a printable key, without Ctrl or Cmd: `_makes_char`)
  and spent on the character event straight after. The first version set it on any key used, and
  a Backspace then ate the next character the probe typed alone; the steps arm found it.
- **Selection shapes** (`UI_SELECTION_SPAN`, `_INCLUSIVE`, `_LINES`) change only the bands drawn
  (`_drawn`). The block caret already covered the character at the head, which is vim's cursor.
- **The pointer hook** (`UIEditorMode.pointer`) is called after a press and after a drag.
- **Undo steps hold parts.** A `TextUndoStep` is a list of `TextUndoPart`s, each an action's
  changes; undo takes them back last first and redo makes them first first, each told as an
  action of one new step. `TextDocAction.step` is the serial; `_joining` decides it, and the
  rule that joins typing into words reads a record of the last typing (`doc->typing`) instead of
  the last undo step, so it holds with `keep_undo` off. `text_doc_group(doc, open)` holds a step
  open; a host's edit inside a group is a step of its own, and the group's next action starts
  another.
- **Arms** (`ui` group): `ui-editor-layer` (4 flags), `ui-editor-decline` (1),
  `ui-editor-paired-char` (3), `ui-editor-shapes` (4), `ui-editor-steps` (6).
  `ui-editor-mode` and `ui-editor-host-undo` unchanged and passing.
- **Falsified** on the committed work: a declining binding ending the walk again reads
  `editor-decline declined parent 0`; a group holding no step reads `editor-steps ... grouped 0`

## Phase 2: the vim core, as built

- **`cetra/src/ui_editor_vim.c/h`**: normal and insert mode. Counts before and after an
  operator, every motion of section 2 but search's, the operators `d c y > < g~ gu gU` over them
  and doubled, the edits `x X s S D C Y J gJ r ~ p P o O i a I A`, counts on inserts, `u` and
  Ctrl+R, and `.`. The register is the clipboard, with vim's memory of whether it put whole lines
  there. View keys (`H M L gj gk`, Ctrl+D/U/F/B/E/Y, `zz zt zb`) through the editor's private
  calls.
- **`ui_editor_internal.h`**: what the vim file reaches of the editor:
  - `ui_editor_doc` and `ui_editor_engine`;
  - `ui_editor_edit`, the selections left by the caller with their primary;
  - `ui_editor_set_carets`, with wanted columns, and `ui_editor_wants`;
  - `ui_editor_rows_shown`, `_row_at`, `_scroll_place` and `_scroll_rows`.
- **`text_doc_empty_step`**: vim keeps a step of undo for an operator over nothing (`x` on an
  empty line, `d0` at the line's start, `>>` on an empty line), so `u` after it takes back nothing.
  The vim mode makes one there.
- **Esc in normal mode is always taken** -- the plan had it declined with one caret and nothing
  waiting. Declined, it reached the screen, which let go of the editor, and the next key went
  nowhere; vim users press Esc in normal mode out of habit, constantly. A host that wants Esc binds
  it in its layer.
- **The oracle feeds vim the keys as typed** (`feedkeys(keys, 'xt')`), not through `normal!`.
  `normal!` makes every command one step of undo, so `xxu` took back both; and it lets go of
  every key after one that fails, as typed keys are not. Vim writes its buffer with `:w!`, so the
  text is compared byte for byte, CRLF kept. The fixture with no final line break was dropped:
  once its last line is emptied, vim's buffer still holds an empty last line, flagged apart from
  the bytes, where the text alone reads as ending in a line break. This is the one known
  difference: such a text's cursor goes to the line above.
- **Vim's rules the oracle found, each now kept**:
  - a count of lines past the end takes what there is (`3dd`, `2$`, `2_`), failing only from the
    last line itself;
  - `d<BS>` at a line's start takes the line break before it;
  - `cb` back onto an empty line is a linewise change;
  - a change of case leaves the cursor at the operator's start;
  - `3J` or more on the last line joins nothing and goes to the line's start;
  - ß raised is ẞ;
  - Enter in insert mode indents the new line as the text before the cursor is, and drops the
    blanks after it;
  - undo and redo put the cursor where the step began when that is on its first changed line or
    the line above, else on that line's first character not a blank, or the last line's when the
    step's line is gone. An operator's start is the earlier of the cursor and its motion's end --
    for `dd`, the line's first character not a blank -- so the carets are moved there before the
    edit, and the text's undo step keeps it.
- **The corpus** is `_VIM_SEQUENCES` in `gates.py` beside its fixtures, not under `assets/data/`
  as the plan said, since nothing else reads it: 198 sequences, each on 4 texts at 3 starts, 2,376
  cases. All agree with vim.
- **Arms** (`ui` group): `ui-vim-oracle`, `ui-vim-state` (8 flags), `ui-vim-undo` (7),
  `ui-vim-host` (4). **`ui-editor-mode` keeps its toy mode**, where the plan put it on the real
  vim: the toy is built from the public calls alone, which is what that arm shows a host can do,
  and the real vim reaches private ones.
- **`apps/canvas --editor FILE --vim`**: the app's layer over the vim mode, and a line under the
  editor with vim's state and a half-typed command.
- **Falsified** on the committed work: with `cw` no longer changing what `ce` would, the oracle
  finds 26 cases differing (`cw`, `c2w`); with the exclusive motion's rule at a line's start gone,
  30 (`d}`, `cb`, `dw`).
- **Gates:** `ui`, `canvas` and `gate-docs` pass.
