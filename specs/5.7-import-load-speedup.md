# 5.7 Speed up scene loading — dedup materials + stop re-decoding embedded textures

## Context

Loading the `abandoned_window` scene is slow, and `import.c` is a confirmed contributor. Two
redundancies on the main-thread load path:

1. **Embedded textures re-decoded per mesh.** The GLB embeds all 14 images (verified: 14
   `image/png` blobs, zero external `textures/*.png` URIs), so every texture takes the synchronous
   `load_embedded_texture` path (`import.c:356`), which calls `stbi_load_from_memory` (`import.c:381`)
   to fully decode the PNG **before** the texture-pool cache is consulted (the cache-check is
   downstream in `load_texture_from_memory`, `texture.c:395`). The `IvyLeafReal` material is **one**
   glTF material shared by **483 meshes**, so its embedded texture is decoded on the main thread up
   to 483x -- only the GL upload is deduped, not the decode.
2. **No material dedup.** `process_ai_node_async` (`import.c:1528-1541`) builds a **new** cetra
   `Material` per mesh -- 483 duplicate `IvyLeafReal` Materials, each redoing ~30 `aiGetMaterial`
   property queries + a 13-slot texture-resolution loop + an O(n) `add_material_to_scene` scan
   (`scene.c:453`) + a mask-array layer.

Both are pure redundancy: fixing them changes **nothing visually** and also cuts memory + material
bloat. The earlier review fix (moving the wind mask off the shared `Material` onto a per-mesh
uniform) already makes material sharing safe. (The GPU IBL/probe bake is a separate, larger,
quality-affecting lever -- deliberately out of scope: "import cleanups only".)

## Design -- two low-risk fixes in `cetra/src/import.c`

### 1. Cache-check before decoding embedded textures
At the top of `load_embedded_texture` (`import.c:356`), after the `tex_index` validation and
**before** the `stbi_load_from_memory` decode (`import.c:379-382`):
```c
Texture* cached = get_texture_from_pool(tex_pool, tex_path);
if (cached)
    return cached;
```
`get_texture_from_pool` (`texture.c:255`) keys by string, and `tex_path` (e.g. `"*5"`) is the same
key `load_texture_from_memory` already uses (`texture.c:395`) -- so the 2nd..Nth call for a shared
embedded texture returns the cached `Texture*` immediately, skipping the decode + dilate pass. Same
colorspace semantics as the existing (later) cache-check, just earlier. (Shared by both load paths,
since `load_embedded_texture` is common.)

### 2. Dedup materials by glTF material index
Thread a transient `Material** mat_cache` (size `ai_scene->mNumMaterials`, `calloc`'d) through the
node recursion:
- Add a `Material** mat_cache` param to `process_ai_node_async` (`import.c:1512`); pass it in the
  recursive child call (`import.c:1568-1569`).
- Replace the per-mesh build (`import.c:1536-1541`) with a cache lookup:
  ```c
  unsigned int matIndex = ai_mesh->mMaterialIndex;
  if (matIndex < ai_scene->mNumMaterials) {
      Material* mat = mat_cache[matIndex];
      if (!mat) {
          mat = process_ai_material_async(ai_scene->mMaterials[matIndex], tex_pool, ai_scene, loader);
          mat_cache[matIndex] = mat;
          add_material_to_scene(scene, mat);
      }
      mesh->material = mat;
  }
  ```
- In `create_scene_from_model_path_async` (`import.c:1583`) allocate `mat_cache` before the root
  `process_ai_node_async` call, pass it, `free` it after.

Collapses ~500 Material builds -> ~15 (IvyLeafReal 483 -> 1): eliminates the redundant property
extraction, texture-resolution loops, embedded decodes (compounding with fix 1), the O(n^2)
`add_material_to_scene` scans, and duplicate mask layers. Safe: meshes already share `Material*`
(textures refcounted; `add_material_to_scene` dedups by pointer; per-mesh AABB stays on the Mesh;
the wind mask is already a per-mesh uniform).

### 3. Mirror fix 2 in the sync twin
Apply the same `mat_cache` dedup in `process_ai_node` / `create_scene_from_model_path` (the
loader-NULL fallback) to avoid divergence. (Fix 1 is automatically shared.)

## Files
- `cetra/src/import.c` -- the only file changed: cache-check in `load_embedded_texture`; the
  `mat_cache` param + dedup in `process_ai_node_async`/`create_scene_from_model_path_async`, mirrored
  in the sync `process_ai_node`/`create_scene_from_model_path`.

## Reuse
- `get_texture_from_pool` (`texture.c:255`) -- existing pool lookup.
- `add_material_to_scene` (`scene.c:449`) -- already dedups by pointer; the cache just avoids building
  the dup. No new data structures beyond a transient `Material**` scratch array.

## Verification
1. `./build.sh` clean.
2. **Load time before/after**: `time ./out/bin/render assets/abandoned_window/abandoned_window.cscn
   --headless --frames 2` (and read the log timestamps). Expect the import/decode phase to drop
   substantially (the 483x ivy decode -> 1; ~500 material builds -> ~15).
3. **Identical look**: `--headless --frames 300 --screenshot after.ppm`, diff against a pre-change
   capture -- curtains (wind), ivy (SSS), dust, walls render identically.
4. **SSS intact**: the `configure_sss_materials` log now reports IvyLeafReal tagging ~1 material (not
   483), and the ivy still shows subsurface scattering.
5. **No regression**: load a multi-material model headless -- materials/textures still correct, no
   missing textures.

## Risks
- Material dedup relies on safe `Material*` sharing -- verified (per-mesh geometry on the Mesh, wind
  mask already a per-mesh uniform). Any future per-mesh material state would need per-mesh storage.
- Texture cache-check keyed by the embedded-index string, matching the existing downstream key -- same
  behavior, just earlier.

# Shipped outcome

The plan above is the *original* scope ("import cleanups only") and describes code that no
longer exists -- `process_ai_node_async`, the sync/async twins, and the inline embedded decode
were all removed. It is kept for context; what follows is what actually landed.

**Result: 11.21s -> 4.73s (2.37x) loading `abandoned_window.cscn`.** User CPU is unchanged
(10.35s -> 10.50s), so the win is entirely parallelism, not less work.

## What shipped, in order

1. **Material dedup + embedded cache-check** (`c820574`) -- the original plan. One cetra
   `Material` per glTF material index instead of per mesh (IvyLeafReal: 483 -> 1), and the
   texture-pool cache consulted before decoding rather than after. ~36s -> ~11s.
2. **One always-async import path** (`f0368e9`) -- `create_scene_from_model_path` now requires
   an `AsyncLoader` and always streams; the sync twin and its `process_ai_node`/
   `process_ai_material` duplicates are gone. The async material builder was already a superset
   (it handles glTF combined metallic-roughness), so this removed the weaker path, not a choice.
3. **Embedded textures decode on the worker pool** (`5d62405`) -- compressed embedded images
   (`mHeight == 0`) decode on workers like file textures, overlapping the node walk. The
   compressed bytes are copied at submit so the `aiScene` can be released immediately. Raw
   embedded pixels (rare) still decode inline. ~11s -> ~6s.
4. **In-flight decode coalescing** (`30e0998`, hardened in `9dc8c1c`) -- see regression 2.
5. **Worker pool sized from the machine** (`ab6d888`) -- `get_cpu_cores()` in `util`,
   pool = cores-2 clamped to [2,8], replacing a hardcoded 4. Not a speedup; it stops a
   dual-core box being oversubscribed and removes an unexplained constant.

## Two regressions this caused, and why

Both were invisible to the quality reviews (which explicitly do not hunt correctness bugs) and
were found only by running the thing.

### 1. Textures decoded upside-down, nondeterministically (`2416a31`)

`load_hdr_environment` (`ibl.c`) sets stb_image's vertical-flip for the equirect HDR and never
restores it. That flag is **process-global** -- stb consults a thread-local one only if that
thread has explicitly pinned it, and nothing did.

While embedded textures decoded synchronously at import this was harmless: they were all
finished before the IBL ran. Moving them onto workers put those decodes on *both sides* of the
flag change, so whichever lost the race decoded flipped. Flipped albedo showed as surface
detail in the wrong place; flipped normal maps as black hatching at grazing angles.

Fix: workers pin their own thread-local flip to 0, and the IBL flag is scoped to its own load.

**The lesson worth keeping:** moving work to another thread inherits every process-global that
work touches. stb's flip flag was the one here; it will not be the last.

### 2. Every aliased texture decoded twice (`30e0998`)

The submit-time pool lookup can only dedup against textures already *uploaded*, and during
import none are -- the whole node walk queues before `process_pending` runs once. Assimp
reports one glTF image under several texture types (baseColor as both `DIFFUSE` and
`BASE_COLOR`, metallicRoughness as both `METALNESS` and `DIFFUSE_ROUGHNESS`), so this scene
paid 28 decodes for 15 images, the 19MB metallic-roughness map among those done twice.
Synchronous embedded loading never had this problem because its cache check and its decode
were the same step.

Fix: the loader tracks keys currently decoding. A request for one already in flight attaches as
a waiter and gets the same `Texture` when it lands. For embedded images the check precedes the
compressed-byte copy, so a duplicate does not memcpy megabytes either.

Review of that fix (`9dc8c1c`) found it claimed the key *before* work that could still fail,
leaving four failure ladders each needing to un-claim -- and one did not. A stranded key is
silent and permanent: later requests join a decode that never runs, are never invoked, and
never raise `pending_count`, so `is_busy` reads idle while callbacks are owed and the mask
array and probe bake against unpopulated materials. Restructured so everything fallible is
allocated *before* the claim, making the failure unwritable. The registry is also keyed on
`(pool, key)`, not the string alone -- one `AsyncLoader` serves an Engine while a `TexturePool`
belongs to a Scene, and embedded keys (`"*0"`, `"*1"`) repeat in every glTF, so the render
app's `-s` source-skeleton import could otherwise join another scene's decode.

## Verification actually used

- Pixel-diff against a pre-async master build, with a **measured noise floor**: two runs of the
  same build differ by 0.79% RMSE (animated dust), so anything under that is indistinguishable.
  The flip bug showed as 7.9% -- ten times the floor. Post-fix sits at 0.58-0.66%.
- All three load paths, because they exercise different code: embedded-only (`-m ...glb`),
  external files (`parallax_fixture.gltf`, which also confirms aliased slots share one decode
  and POM height resolution still runs after the drain), and the probe/drain path (`.cscn`).
- Attachment count held at 28 while decodes dropped to 15 -- aliased slots now land back to
  back off one load.

**Note for the next person measuring this:** run the same command the user runs. An early A/B
here compared `.cscn` against their `-m ...glb` and concluded, wrongly, that the branch was
innocent. Different load paths, different answer.

## Known-open

- **The submit-time pool check is dead code for file textures.** It looks up the caller's raw
  path, but the pool is keyed by the worker's *resolved* path, so it never hits. File-texture
  dedup therefore only holds within one in-flight window; a request arriving after finalize
  re-reads and re-decodes from disk. Pre-existing. This is also the only reason
  `submit_key`/`pool_key` both exist -- resolving the path at submit time would collapse them,
  at the cost of moving filesystem walks onto the main thread during import.
- **483 separate ivy meshes** remain the next big lever, but *not* via assimp's
  `aiProcess_OptimizeMeshes`: the meshes sit on 483 separate nodes with distinct transforms, so
  that flag cannot merge them without `aiProcess_OptimizeGraph` flattening the hierarchy --
  which would break name-based light/camera binding (`import.c:1268`) and, because the wind
  height mask is per-mesh from `mesh->aabb` (`render.c:452`), visibly change the wind. Batch at
  the render layer instead, keeping per-mesh AABBs and node identity.
