# E6 / spec 11.30 — depth prepass + opaque draw ordering

## Context

**Wall 4 of the Tier 4 preamble: the opaque pass is unshielded.** On `apps/forest` at the default
1600x900 on an M1 (a 3200x1800 Retina framebuffer), `opaque` is **312 ms of a 346 ms timed frame** —
90% of it — against `shadow cascades` at 23 ms. The shadow pass pushes 5x the triangles (130M vs 26M)
in 1/14th the time, because it is depth-only.

Three probes say the cost is neither geometry nor submission:

| probe | condition | result |
|---|---|---|
| 3.2x fewer triangles (`--lod-bias 0.2`) | 800x450 fb, MSAA off | 42.6 → 38.6 ms, **9%** |
| 12x more draws (`--no-instancing` 2,617 vs `--no-lod` 219) | same | 44.2 vs 65.6 ms — more draws is **faster** |
| MSAA 4 → 1 | 3200x1800 fb | 312 → 220 ms, **−92 ms** |

Fragments are the limit. There is no depth prepass anywhere in the engine, no occlusion culling, and
opaque draws are issued in draw-list order — a pre-order DFS flatten, Morton-ordered within a
prototype for batch contiguity, which is deliberately *camera-independent*. A forward renderer with
no prepass depends entirely on hardware early-Z, and early-Z rejects nothing unless nearer geometry
wrote depth first. Every layer of canopy shades in full.

Two content properties make `apps/forest` the worst case, both ordinary authoring choices
(`forest.c:646-649`): the leaf material is `doubleSided` (every card rasterizes twice) and
`ALPHA_MASK` (a shader that can `discard` forfeits early-Z outright).

**Intended outcome:** the opaque pass stops shading hidden fragments, measured, behind an opt-in flag.
This also collects E5's deferred third limb (draw sorting), which 11.28 declined as an unfalsifiable
claim against the corpus it had — `apps/forest` is now that corpus.

## What the exploration established

Nine facts that shape the design. All verified in the tree.

**1. The opaque pass sets no depth state at all.** `render.c:891-905` has no `glDepthFunc`,
`glDepthMask` or `glEnable(GL_DEPTH_TEST)`. It inherits `GL_LESS` + depth-mask-on from `engine.c:2097`,
set once before the frame loop. So the prepass must set and restore depth state explicitly, and
nothing else in the opaque path will fight it.

**2. The draw list is built once per frame and shared.** `engine_build_draw_list` (`render.c:582`) is
stamp-guarded (`total_frames ^ (scene_graph_epoch() << 32)`); the shadow pass builds it at
`shadow.c:1162` and `render.c:781` reuses it. A prepass inside `render_current_scene` gets it free.

**3. `DrawItem` already carries everything a prepass needs to filter on** — `DRAW_LANE_OPAQUE`,
`DRAW_ALPHA_MASKED`, `DRAW_FOLIAGE`, `DRAW_DOUBLE_SIDED`, `DRAW_UNBOUNDED`, plus the resolved `lod`.
Classified once at build (`draw_list.c:71-95`).

**4. `engine_set_scene_draw_buffers(engine, with_gbuffer)` (`engine.c:1702`) is the existing MRT seam.**
Captures already run with attachment 0 alone, so a reduced attachment list has precedent.

**5. `shadow_depth_vert` is NOT reusable as a prepass vertex shader.** It computes
`(lightSpaceMatrix * cetra_instance_model(model)) * localPos` — a mat4xmat4 concat — where `pbr_vert`
computes `projection * (view * (model * vec4(posCurr,1)))`, three chained mat4xvec4 products.
Different rounding, fatal for `GL_EQUAL`. It also hard-sets `glPolygonOffset(2,2)` (`shadow.c:1394`),
alpha-tests at raw `aTexCoords` rather than the KHR-transformed UV, ignores `VertexColor.a`, and keys
its alpha test off `DRAW_FOLIAGE` rather than `DRAW_ALPHA_MASKED`.

**6. There are already THREE hand-written position paths that are supposed to agree** — `pbr_vert`,
`pbr_skinned_vert`, `shadow_depth_vert` — written three different ways. This is a latent divergence
the prepass work should fix rather than add a fourth to.

**7. No `invariant` qualifier exists anywhere in the shader corpus.** Grepped: zero hits in `.glsl`.
`invariant gl_Position` is the GL-spec remedy for exactly the two-programs-must-agree problem, and
GL 4.1 supports it.

**8. A2C coverage is not a cutoff.** `render.c:507-509` enables `GL_SAMPLE_ALPHA_TO_COVERAGE` for
masked materials when `msaa_samples > 1 && !capturing`. The hardware reads the **last alpha-carrying
colour output** (`NormalOut.a`, `pbr_frag.glsl:1945`), which is `finalOpacity` =
`fresnelOpacity(coverage, materialOpacity, iorF0, NdotV)` — so coverage depends on the opacity mask
layer, the normal map and the TBN. `pbr_frag.glsl:1934-1936` records this was measured: forcing that
alpha to 1.0 moved 8,580 px of masked hair. **A prepass that writes no colour attachment has no alpha
for the hardware to read**, so masked geometry must keep attachment 0 bound with `glColorMask` off,
not `glDrawBuffers(GL_NONE)`.

**9. `Mesh.id` does not exist.** Spec 11.28:295 claims `Mesh` gained `unsigned id` as "a sort/batch
key that is [not a pointer]" and 11.28:363 says it "currently has no reader". Only `refs` landed
(`mesh.h:86`). Every `mesh->id` in the tree is vendored assimp. The sort key must add it, and 11.28
needs a correction.

## Why a dedicated prepass shader, not the pbr program in a depth-only mode

The case for reusing `pbr` is that a second shader can silently drift out of agreement with the first,
and depth must agree bit-exactly for `GL_EQUAL`. That failure mode is real — but **this repo already
has the mechanism that removes it and uses it for exactly this situation**. From CLAUDE.md, on OIT:
`include/mboit.glsl` holds the moments and their reconstruction, "shared by the generation and
accumulate sub-passes so a constant cannot drift between them". `wind.glsl` and `skin.glsl` work the
same way, which is why `shadow_depth_vert` displaces identically to the shading passes today.

So "dedicated" does not mean "duplicated". It means a lean program that `#include`s the same chunks.

The cost of reuse is what decides it. Running `pbr_vert` for the prepass computes `windOffset`
**twice** (current and previous frame), `CurrClip`, `PrevClip`, `ViewPos` and the TBN, then
interpolates ~8 varyings the prepass discards — on a pass that runs over all 26M triangles and whose
entire justification is being cheap. A dedicated vertex shader emits `gl_Position` and one `vec2`.

Two guards make it safe rather than merely fast: the position chain moves into a shared include so
there is one copy, and `invariant gl_Position` is declared in every program that draws scene geometry.

## Design

Five phases. **Ordering first**, because it needs no new shader, no new pass and no depth-identity
question, and it quantifies how much overdraw actually costs before the expensive half is built.
Every phase ends at a measurement; a phase that does not pay is reported and not shipped.

### Status, and the one change ordering-first forced

| phase | state |
|---|---|
| 0 — instrument | **done**, and it corrected itself twice (1.85 → 3.87) |
| 1 — sort | **done, shipped on**, and it is not a 0 px flag |
| 2 — position include | next |
| 3 — prepass | after 2 |
| 4 — measure | rewritten, see below |

**Ordering first was right for the reason given and wrong about which half was risky.** The sort was
cheap to build and turned out to perturb a lane that is not order-independent — masked materials
blend, so reordering them changes the picture, costs a golden re-bake, and forced two gate arms to
exclude it as a confounder. The prepass, which this spec called the fragile half, **reorders nothing**
and therefore has none of that.

That inverts what Phase 4 is for. Sorting took depth complexity **3.87 → 2.17** on the shipping
config; it did not reach 1.0, so roughly half the redundant shading is still there and the prepass is
what reaches it. But if the prepass alone gets to ~1.0, **the sort should be turned back off**: the
same win, with no look change, no coplanar-tie golden movement, and `forest-order` and
`overdraw-probe` restored to measuring what they name. The sort would become the thing tried on the
way rather than a thing shipped.

So Phase 4 measures **prepass alone against prepass + sort**, not the two stacked.

### Phase 0 — the instrument

Nothing in the tree measures depth complexity, which is why Wall 4 went unseen. Add it first.

`GL_SAMPLES_PASSED` around the opaque pass counts samples that survived the depth test — i.e. samples
actually shaded. Divided by the framebuffer sample count that is mean depth complexity. It is core
GL 3.3, needs no extension, and is an integer, which is the kind of claim this repo prefers.

- New profiler counter alongside `SubmitStats`, read through the existing `PROFILER_RING` 4-frame
  latency so it never stalls (`profiler.c:133` already owns the query pool pattern).
- Reported as a new SUBMISSION column, or its own line under the timing table. Note: adding a column
  means `SUBMIT_COLS` in `gates.py:2346` and `k_submit_fields` in `profiler.c:78` move together, by
  design — a new line is the smaller change and is preferred.
- This doubles as the latency probe E7 (occlusion culling) will need.

**Arm:** `overdraw-probe` — the counter is > 0, and it *falls* when the camera aims at empty sky.

#### As built — and it moved the goalposts for every phase after it

The driver answers `GL_SAMPLES_PASSED`, which needed showing rather than assuming: this is the driver
that accepts `GL_TIMESTAMP` and returns 0 (spec 11.27), so "the call was accepted" proves nothing. The
arm therefore asserts the number **moves** — exactly 0 aimed at sky, above 1 over the forest.

| scene | opaque GPU | depth complexity | samples/sec |
|---|---|---|---|
| `apps/forest` | 312 ms | **1.85** | 137M |
| `abandoned_window_shadowed` | 35 ms | **2.78** | 602M |

Two findings, and the second is the uncomfortable one.

**The interior has more redundant shading than the forest.** The roadmap's Wall 4 explained its own
blindness by asserting the corpus was "content with no depth complexity". It was not. That sentence
was a second guess offered in the same breath as admitting the first had gone unchecked, and it is now
withdrawn there too.

**Forest's 312 ms is mostly not overdraw.** It shades 4.4x slower per sample than the interior, so the
cost is per-sample shader work — clustered lights, IBL, sheen, clearcoat, SSS, POM — at 3200x1800 with
4x MSAA. A prepass does nothing about that. The roadmap priced E6 at 250 ms; that price is withdrawn.

**The instrument's own blind spot, recorded in `profiler.h` rather than left for the number to
over-claim:** it counts samples that *pass*, and a fragment that `discard`s costs a full shader
invocation while passing nothing. So it understates the work exactly where alpha-masked foliage
dominates — the case a prepass most wants to shield. It is a **floor** on depth complexity, not an
estimate: above 1 proves redundant shading, near 1 does not prove its absence. 1.85 is also a
whole-frame average including sky, where no opaque sample passes at all; within the covered region it
is materially higher.

**What this changes downstream.** Phase 1 and Phase 3 are now understood to be competing for the same
redundant share rather than adding to each other — both drive depth complexity toward 1.0, one by
ordering and one by rejecting, and neither can go below it. That makes Phase 4 the load-bearing phase
of this spec rather than a formality, and makes "ordering first" the right call for a second reason:
if sorting alone reaches most of the way to 1.0, the prepass has little left to win and its extra
geometry pass may not pay for itself at all.

### Phase 1 — the sort key, and front-to-back ordering

#### As built — shipped ON, and it is not a 0 px flag

**−29% of the opaque pass** on `apps/forest` (551 → 394 ms), depth complexity 1.85 → 1.06. Enabled by
default with `--no-sort-opaque` as the escape.

Unlike `--no-instancing`, **this one moves pixels**, and the reason is a defect it did not cause.
Masked materials still blend into attachment 0 (`engine.c:440` enables `GL_BLEND` globally;
`engine_set_scene_draw_buffers` disables it only for slots >= 1), so reordering overlapping leaf
cards changes the result. Spec 11.19 §2.3 measured that double-apply and rejected the fix because TAA
resolves the dither and the render app always has TAA on.

**Which way it moves is the interesting part, and the first reading of it here was wrong.** Sorting
makes the canopy *brighter and flatter*, not darker:

| far band (horizon canopy) | sort off | sort on |
|---|---|---|
| mean | 105.7 | 108.4 |
| stddev | 63.6 | 60.8 |

Unsorted, a pixel accumulates several blends and each pulls the result back toward the near-black
clear colour, with the layer count varying pixel to pixel — which reads as shadowed depth inside
distant trees. Sorted, the nearest leaf wins the depth test and the rest are rejected, so fewer
layers contribute and the count is more uniform.

**So the aerial depth in the unsorted frame is overdraw**: hidden leaves still darkening the pixel. It
resembles Beer-Lambert attenuation through a canopy because N layers of `(1-a)` *is* that equation —
with the layer count set by how many draws happened to survive the depth test rather than by how much
leaf the light crossed. Right maths, wrong inputs. The honest sources for that look are translucent
shadow maps (spec 11.26, which forest does not enable despite the leaf material already setting
`foliage_shadows` and `subsurface`), fog and aerial perspective.

**Two things measured and rejected along the way.** Holding masked geometry out of the sort wins *no*
GPU time (557 vs 551 ms) and still moves 204k px, because drawing masked after opaque changes what it
blends against. And sorting during GI cubemap captures is pure cost — a face is too small for the
saving to matter and a bake pays it six times per face — so captures are excluded.

**Golden movement: `cornell_box`, 1 px.** At (837, 1114) on the box floor, PAE 6/255, on a scene with
no masked geometry at all: an exact depth tie between coplanar quads, which `GL_LESS` breaks by
whichever drew first. `--no-sort-opaque` reaches the pre-change frame at 0 px. Re-baked. Every other
golden is 0 px, which is the useful part — opaque geometry really is order-independent apart from
exact ties.

**Two gate arms needed the sort excluded, and that is not a threshold being relaxed.** `forest-batch`
already passed `--no-lod` because the batcher joins only consecutive `(mesh, lod)` items and LOD
fragments them; the sort is a second fragmentation source and gets the same treatment, so the arm
still tests the batcher and the floor stays at 8. `forest-order` needs it more urgently — the depth
sort *replaces* the Morton ordering that arm exists to defend, and with it on the comparison read 1684
vs 1819 instead of 1287 vs 2368, i.e. the arm had quietly started measuring the bucket count.

**Still weak, and recorded rather than hidden:** `overdraw-probe` now reads 1.05 against a `> 1.0`
floor, because its own baseline sorts. It should take `--no-sort-opaque` too.

#### The AA change that came out of this, and what it corrected

Forest was running 4x MSAA with **no temporal filter at all** — the render app pairs TAA with MSAA off
and forest never did, so masked foliage got raw coverage dither and 11.19's dark fringe with nothing
to resolve either. Fixed: TAA replaces MSAA when windowed, headless keeps MSAA unless `--taa`.

| | MSAA 4, no TAA | MSAA 1, TAA |
|---|---|---|
| opaque GPU | 551 ms | **393 ms** |
| TIMED | 578 ms | **427 ms** |
| depth complexity | 1.85 | **3.87** |

That last row corrects Phase 0. With 4x MSAA a leaf at alpha 0.5 writes two samples of four, so
samples-passed saw **half** the fragments that actually shaded — the "floor, not an estimate" caveat,
quantified at about 2x. **Every Phase 0 figure was taken on the MSAA path and understates.**

#### The look investigation, and why none of it needed a renderer change

The canopy depth that made the unsorted frame preferable is **hidden leaves double-blending**, and two
mechanisms already supply it honestly:

- **Fog and aerial perspective.** With fog on — the frame forest actually ships — the sort's effect on
  the far band collapses to 0.9 mean / 1.2 stddev, against 2.7 / 2.7 with `--no-fog`. **Every
  comparison in this spec taken with `--no-fog` understates how little the sort costs the look.**
- **Foliage self-shadowing.** `foliage_shadows = true` puts leaf cards in the cascades, which is where
  the dappling comes from.

**Translucent shadow maps were tried for this and are the wrong tool**, measured: routing leaves
through the transmittance path requires `foliage_shadows = false`, and the frame got *brighter and
flatter* (far band mean 182.5 → 191.1, stddev 53.6 → 51.9) because it traded real dappled shadows for
a uniform absorber. `shadow.c:530` says why in advance — "Foliage opts back in, because leaf cards are
large enough to resolve at map-texel scale" — TSM is for sub-texel geometry like hair. Reverted; no
change shipped.

Add `unsigned id` to `Mesh` (monotonic at `create_mesh`), which 11.28 said it had.

Sort the opaque lane by a composite key built per frame:

```
key = (depth_bucket << 40) | (material_id << 20) | (mesh_id << 4) | lod
```

**Depth bucketed, not exact**, and that is the whole trick. Exact front-to-back shatters batch runs,
because `draw_run_can_join` (`draw_list.c:207`) joins only *consecutive* identical `(mesh, lod)`.
Quantizing to ~32 buckets gives coarse front-to-back across the frame while leaving identical meshes
adjacent inside a bucket, so batching survives. Material sits above mesh in the key so E5's third limb
falls out of the same sort.

Sorting is an index permutation over the existing list, not a rebuild — the list stays the shared,
stamp-guarded object every other pass reads. The shadow pass keeps its own order (it is a different
frustum; front-to-back for the camera is meaningless there).

- Engine toggle `bool opaque_sort_enabled` (default **false**), flag `--sort-opaque`.

**Arms:**
- `sort-identity` — sorted vs unsorted at **0 px**. Opaque geometry with depth testing is
  order-independent; if this fails, something is order-dependent that should not be, and that is a
  finding either way.
- `sort-batching` — `instances` and `triangles` identical between sorted and unsorted, so only
  ordering moved. The `forest-order` arm is the template.
- `sort-switches` — `material switches` falls. This is the arm 11.28 said could not be written.
- `sort-overdraw` — the Phase 0 counter falls.

### Phase 2 — the shared position include

Pure refactor, own commit, its own 0 px bar. Extract the object-to-clip chain into
`cetra/shaders/include/object_position.glsl`, exporting something like
`cetra_object_position(aPos, uv0, uv1, time)` returning the wind-displaced, optionally skinned,
instanced world position, with the three-step association preserved exactly.

`pbr_vert`, `pbr_skinned_vert` and `shadow_depth_vert` all move onto it. Add `invariant gl_Position`
to each.

**Bar:** all 21 goldens at 0 px, plus the raiden recipe at 0 px. Nothing may move. If the shadow
shader's association change moves a shadow, that is a pre-existing divergence surfacing and gets its
own note.

### Phase 3 — the prepass

New program `depth_prepass` = `depth_prepass_vert.glsl` + `depth_prepass_frag.glsl`, both built from
the shared includes. Vertex emits `gl_Position` (via the Phase 2 include) and `TexCoords`. Fragment
runs only for masked materials and reproduces `pbr_frag`'s coverage decision through a second shared
include, `include/coverage.glsl`, which `pbr_frag` also adopts: `transformUV` -> POM offset -> albedo
alpha -> `VertexColor.a` -> the `alphaToCoverage ? A2C_MIN_ALPHA : alphaCutoff` selection ->
`fresnelOpacity`.

The pass, inserted in `render_current_scene` immediately before `engine_set_scene_draw_buffers(engine,
true)` at `render.c:894`:

1. `profiler_scope_begin_if(profiler, prepass_on, "depth prepass")` — the row is absent when off.
2. Attachment 0 bound, **`glColorMask(GL_FALSE x4)`** — not `glDrawBuffers(GL_NONE)`, per finding 8,
   or A2C has no alpha to read and masked coverage collapses.
3. `glDepthFunc(GL_LESS)`, `glDepthMask(GL_TRUE)`.
4. Iterate `scene->draw_list` filtered to `DRAW_LANE_OPAQUE`, reusing `_visible_run` /
   `instance_chunk_upload(..., shading=false)` — the shadow pass already proves `shading=false` is the
   right arm for a depth-only stage (`shadow.c:619`).
5. Restore colour mask; opaque pass then runs with `glDepthFunc(GL_EQUAL)`, `glDepthMask(GL_FALSE)`.
6. Restore `GL_LESS` + mask on before the skybox, which sets its own (`sky.c:657`).

**The instancing decision must match between the two passes**, or `gl_InstanceID` indexes a different
UBO slot and the model matrix differs. Both iterate the same list with the same lane filter and the
same frustum, so runs are identical — stated as an invariant and asserted by the identity arm.

- Engine toggle `bool depth_prepass_enabled` (default **false**), flag `--depth-prepass`.

**Arms:**
- `prepass-identity` — prepass on vs off at **0 px**, on `apps/forest` and on the new fixture. This is
  the arm the whole feature rests on; `GL_EQUAL` failing shows up as missing surfaces.
- `prepass-row` — a `depth prepass` row appears in SUBMISSION with `draws > 0`, and is **absent**
  without the flag.
- `prepass-overdraw` — the Phase 0 counter falls sharply.
- `prepass-equal-guard` — a deliberately-broken variant (prepass with polygon offset) must FAIL
  `prepass-identity`, proving the arm can detect divergence rather than passing vacuously.

### Phase 4 — measure, and decide

**Phase 0 promoted this from a formality to the phase the spec turns on.** The prepass is not
universally a win: it costs a full extra geometry pass and pays back only above some depth complexity.

**The question this phase answers has changed.** It is no longer "does the prepass pay" but **"does
the prepass make the sort unnecessary"**. The four configurations, measured on the shipping config
(TAA, MSAA off), all four required because the levers overlap rather than add:

| config | expected | what it decides |
|---|---|---|
| neither | 3.87 | the baseline |
| sort only | 2.17 | measured, shipped today |
| **prepass only** | ? | **if this reaches ~1.0, revert the sort** |
| both | ? | if this beats prepass-alone materially, keep both |

Prepass-only is the load-bearing row. Reaching ~1.0 there buys the same shading reduction with **no
look change, no coplanar-tie golden movement, and `forest-order` and `overdraw-probe` restored** —
strictly better than the pair, even at equal GPU time. Only a material gap justifies keeping the sort.

Scenes: `apps/forest` (high complexity, TAA on so the counter is not halved),
`abandoned_window_shadowed` (interior, 2.78 on the MSAA path so higher still — the case *for* it), and
`instancing_fixture` (complexity ~1, where it should **lose**; an arm showing it losing is worth more
than one showing it winning).

**Measurement discipline this spec has already violated three times, so it is written down.** Take the
noise floor first, at the exact resolution, frame count and flag set — `apps/forest` is *not*
pixel-deterministic (34,991 px at 60 frames; the Hillaire sky). Measure with **fog on**: every
`--no-fog` figure above overstates what these changes cost the look. And read depth complexity only on
the TAA path, since 4x MSAA halves it.

The prepass's own default stays **off** until Phase 4 reports. The sort's default is already on and
Phase 4 may reverse it.

## Verification

Per-phase, following 11.28's cross-cutting table:

- **21 goldens at 0 px after every phase**, plus the raiden recipe at 0 px.
- **`--no-sort-opaque` reaches the pre-change frame at 0 px, but the sorted default does NOT.**
  Written as "true by construction … which is the point of shipping opt-in", and then the sort shipped
  on and moved `cornell_box`. The off-path identity holds; the on-path identity was never available,
  because masked materials blend. **The prepass is the one that can be 0 px on both paths**, and that
  is now a property to verify rather than assume.
- **Phase 2 is a pure refactor and must be 0 px with nothing switched on at all.** It is the only
  phase that touches the default path unconditionally. Use the stronger check: unescape
  `cetra/src/shader_strings.h` before and after and diff comment-stripped, proving no shader code
  changed beyond the extraction.
- **Measure the noise floor first, every time, at the exact configuration.** `apps/forest` is **not**
  pixel-deterministic — 34,991 px at 60 frames / 3200x1800, 7,134 at 20 / 1600x900, and the Hillaire
  sky is the source (`--no-sky` drops it to 4 px, `--render-mode 6` to 0). A pixel count without its
  floor is not a measurement, and this spec quoted one before checking.
- **Use `instancing_fixture` for any 0 px claim about ordering**: purely opaque, and measured at
  exactly 0 px across the sort, which is what isolates blending as the cause everywhere else.
- Exposure pinned (`--no-auto-exposure -E 1.0`) on every cross-configuration comparison — `apps/forest`
  pins its own.
- `prepass-equal-guard` proves the identity arm can fail.

End-to-end, by hand. Note `--taa --headless-jitter` on the profiling runs: without them forest keeps
4x MSAA and the depth-complexity reading is halved.

```bash
./build.sh
# noise floor FIRST -- this must be understood before any diff below means anything
./out/bin/forest -x -f 60 -S /tmp/f1.ppm
./out/bin/forest -x -f 60 -S /tmp/f2.ppm
magick compare -metric AE /tmp/f1.ppm /tmp/f2.ppm null:

# the four configurations Phase 4 compares, on the shipping AA path
./out/bin/forest -x -f 60 --taa --headless-jitter --profiler --no-sort-opaque -S /tmp/a.ppm
```

## Deliberately deferred

- **The A2C + blend defect that makes any of this order-dependent.** Masked materials blend into
  attachment 0 while alpha-to-coverage has already spent that alpha, so it lands twice. Spec 11.19
  §2.3 measured it (393,554 px) and **rejected the fix** because TAA resolves the dither and the frame
  a person looks at is jittered. That rejection rested on "the render app enables TAA for every
  non-headless session" — which was true, and **`apps/forest` did not enable TAA at all until this
  spec did**. Forest now satisfies 11.19's premise, so the fix is viable there for the first time. It
  is still not this spec's business: it changes every masked material including raiden's hair, and it
  wants 11.19's own arms rather than a perf spec's.
- **Turning the prepass on by default.** Needs Phase 4 first. The *sort's* default is already on and
  Phase 4 may reverse it.
- **Occlusion culling (E7).** Its own row. Phase 0's counter is the instrument it will need, and
  Phase 4's numbers should re-price it — on current evidence it is not justified.
- **A prepass for the shadow cascades.** They are already depth-only; there is nothing to shield.
- **Transparent/OIT ordering.** OIT is order-independent and on by default; sorting would move
  `--no-oit` pixels including the raiden hair, which has moved four times already, for no measured win.
- **The `doubleSided` + `ALPHA_MASK` foliage cost itself.** Real, and an authoring question rather
  than a renderer one: single-sided leaf cards with correct normals would halve their rasterization.
  Belongs with `apps/forest`, not here.
- **MSAA cost (−92 ms at 4→1).** A separate lever with a separate look tradeoff.
