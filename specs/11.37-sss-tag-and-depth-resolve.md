# Spec 11.37 — the SSS profile tag and view depth are MSAA box-filtered

## Context

Reported from `apps/tree`: with SSS on and everything else off, the flowers throw sparkling
firefly flashes as they move. **MSAA-only, and independent of TAA.**

> **CORRECTION (spec 11.38, after phase 1 shipped): the sparkle was not this.** The cause was an
> extrapolated `VertexColor` varying — under MSAA a partly covered pixel is shaded at the pixel
> centre, which can lie outside the triangle, so a colour authored in 0..1 arrives above 1 — and it
> was fixed at `35338e5` by qualifying that varying `centroid`. The two channels below **amplified**
> it: the scatter pyramid was faithfully spreading a genuinely out-of-range input. Both defects
> below are real and worth fixing, and everything this spec says about the *mechanism* holds. What
> does not hold is the attribution to that symptom, and therefore this spec's acceptance test —
> see the corrected Verification section. Read every "that is the sparkle" below as "that is a
> second, real defect that was found while looking for the sparkle".

That pair of observations is what led here. An MSAA colour resolve is a **box filter** — it is
only valid for quantities linear in radiance — and `resolve_color_attachment`
(`postfx.c:1992`) is a `glBlitFramebuffer` applied to every channel alike. Two of the channels
the SSS chain reads are not radiance:

- **Attachment 4's alpha is a categorical profile tag.** `pbr_frag.glsl:2020-2021` writes
  `float(max(sssProfileIndex + 1, 0))` into `DiffuseOut.a`. The average of tag 2 and tag 0 is
  tag 1 — which does not mean "half of profile 2", it means **profile 1**. Meaning is destroyed,
  not degraded.
- **Attachment 2's `.z` is a view depth**, i.e. a position, and the average of two surfaces is a
  surface that exists nowhere. Attachment 2 clears to zero (`engine.c:102-106`), so a silhouette
  pixel averages its depth toward the sky's 0.

`apps/tree` registers two profiles — leaf → tag 1, grass/flowers → tag 2. At 4× MSAA a petal
pixel with 2 of 4 samples covered resolves to `(2+2+0+0)/4 = 1.0` → `int(1.5)` = **1 = the LEAF
tag**, so it is seeded into the leaf walk with the leaf's wider radius and different channel
weights, its delta taken against the grass's own diffuse. 1-of-4 → 0.5 → also 1. Quarter- and
half-covered pixels are systematically misfiled.

The flashing itself is the second channel. `sss_gather_frag.glsl:114` computes
`basePx = sssProfile.w * projScale / depth` from `depth = -texture(auxTex, TexCoords).z`, so a
depth averaged toward 0 inflates `basePx` — bounded by the sample count (2-of-4 → ×2, 1-of-4 →
×4), which is enough to jump the gather several pyramid levels and replace a petal with a broad
neighbourhood average. Wind changes per-pixel coverage every frame, so the tag crosses integer
boundaries and the depth swings: pixels jump between profiles and LODs frame to frame. **That was
read as the sparkle and was not it** — see the correction above; it is a real defect of its own.

**Why it reaches a windowed session.** `engine->msaa_samples = 4` by default (`engine.c:164`)
and **`apps/tree` never calls `set_engine_msaa_samples`** — the 1-sample-plus-TAA policy is
`apps/render/src/render.c:3029-3040`, an app-level decision that tree does not share. So tree
runs 4× MSAA with TAA on (`tree.c:1305`), which is exactly the configuration where this fires.

**Intended outcome:** the SSS chain stops reading averaged categorical and positional data, and the
rule gets written down where the G-buffer table lives. ~~the sparkle goes with it~~ — struck: the
sparkle was the varying and is already gone (`35338e5`), so no phase here can claim it.

## Non-goals

- **Per-sample SSS on edge pixels** (Lauritzen; The Order: 1886). It is the complete answer —
  even after this, an edge between two surfaces of the *same* profile still gets one blurred
  result — but it roughly doubles those passes on edges and needs `sampler2DMS`, which spec
  11.17 rejected. The industry's answer to this exact incompatibility was to stop multisampling
  the G-buffer at all.
- **Changing the headless default sample count.** That moves every golden and must not ride
  along on this.
- **Auditing the other suspect channels.** Attachment 2's `.w` roughness and attachment 1's `.a`
  SSR marker are under the same rule and are recorded at the end, not fixed here.

## Phases

### Phase 1 — the view depth, which is what flashes

**Most of this already exists.** `postfx.c:2879-2883` already resolves scene depth into
`fx->depth_fbo` / `fx->depth_texture` with `GL_BLIT ... GL_DEPTH_BUFFER_BIT, GL_NEAREST` — and a
depth blit takes a **sample, not a mean**, which is precisely the property the SSS chain needs.
It is merely gated on `ssr_active || dof_active`, and it runs at `:2880` while the SSS chain runs
at `:3118`, so the ordering is already correct.

So: widen that gate to include the SSS condition (`sss_written && fx->sss_ready`, the same
expression `:3116` uses), bind `fx->depth_texture` in `postfx_run_sss`, and have the two shaders
that read `auxTex.z` read it instead:

- `sss_pyr_seed_frag.glsl:24` — `z` for the covered test and for `DepthOut`.
- `sss_gather_frag.glsl:102` — `z` for the off-skin test and for `basePx`.

Both convert with `viewZFromNdcZ` from `include/depth.glsl`, which needs a `projection` uniform
in the including shader — `postfx_run_sss` already receives `projection`, so it is a set away.

**No stencil, no linearize pass, and no GL 4.1 feedback loop**, which an earlier draft of this
design worried about: the SSS passes draw into `sss_pyr_fbo` / `sss_delta_fbo`, and neither has
the depth attached, so sampling it there is legal. The feedback-loop hazard only arises for the
phase 2 stencil test, which attaches the depth-stencil to the draw FBO.

### Phase 2 — the profile tag, which needs stencil

Averaging cannot be fixed by reading more carefully; the value is destroyed at resolve. The tag
has to live somewhere integer and per-sample, and the storage is already paid for:
`engine.c:622/:624` allocate `GL_DEPTH24_STENCIL8` at both sample counts, the frame clear
already clears stencil (`:2400`), and there are **zero first-party `glStencil*` calls** — all 8
bits are free. `MAX_SSS_PROFILES` is 8, so 4 bits hold every profile plus "none".

`postfx.c:1536-1567` walks one profile per iteration with `profileTag = p+1` as a uniform to both
seed and gather, so both compares map one-to-one onto `glStencilFunc(GL_EQUAL, p+1, 0xFF)` with
ops KEEP and `glStencilMask(0)`. Both tag-consuming passes run at full render res, so the
stencil attaches at matching size; the downsample mips never touch the tag.

Three things this drags in, which is why it is its own phase:
- **A write policy for every scene-FBO draw**, because nothing touches stencil today so nothing
  is right by accident: opaque/masked REPLACE with their own ref (non-skin writes 0, so an
  occluder clears the tag), and skybox, catcher, water, transparent/OIT, particles and the
  `--depth-prepass` program each need `glStencilMask(0)` or a deliberate ref.
- **The resolve**: add `GL_STENCIL_BUFFER_BIT` to the existing depth blit. Formats already
  match. The GL spec calls the multisample depth/stencil downsample implementation-dependent
  rather than promising sample-select; every real implementation selects, and a stencil bitmask
  has no meaningful mean.
- **Per-profile clears**: the seed writes zeros for non-covered pixels today, so under
  stencil-discard mip 0 of both pyramid targets needs an explicit clear per profile. The gather
  is already clear-then-additive, where discard ≡ +0.

Note **stencil cannot be sampled on GL 4.1** (`ARB_stencil_texturing` is 4.3), so the
fixed-function test is the only consumer path available — test-based by necessity, not by taste.

### Phase 3 — the fixture that can see this

`assets/sss_scale_fixture.cscn` already authors two profiles (`sss_skin_a`/`sss_skin_b`;
`gates.py:58` renders it). What does not exist is two-profile **thin or small** geometry, which
is what makes nearly every pixel a silhouette pixel. Build that, then assert the **MSAA frame
matches the 1-sample frame** within tolerance — the 1-sample render is ground truth because
nothing is averaged in it. `--msaa <n>` exists and composes with `--taa`
(`render.c:3041-3043`).

# Corrections to phase 2, from verifying it against the code before executing it

Every claim in phase 2 about storage and structure **verified TRUE**: `GL_DEPTH24_STENCIL8` at both
sample counts (`engine.c:621-624`), attached as `GL_DEPTH_STENCIL_ATTACHMENT` (`:625`), the frame
clear already clears stencil (`:2400`), and **exactly one** `GL_STENCIL*` mention exists in the whole
first-party tree — that clear. No `glStencilFunc`, `glStencilOp`, `glStencilMask` or
`glEnable(GL_STENCIL_TEST)` anywhere. All 8 bits free, `MAX_SSS_PROFILES` 8 so 4 bits suffice. The
per-profile loop is at `postfx.c:1546-1580`; both tag-consuming passes run at `fx->width/height`,
which is what `create_depth_fbo` allocates at, so a stencil attachment matches by construction; the
downsample mips never read the tag. Stale line refs: the gather's compare is at `:113`, not `:105`.

Six things the phase-2 text gets wrong or omits:

1. **The resolve is in `postfx.c`, not `engine.c`** — see the corrected Files row. The spec's own
   phase-1 prose names postfx correctly, so this was an internal inconsistency, but the Files table
   is the row an implementer follows.
2. **The pass list is incomplete, and one entry is wrong.** It misses the **gizmo lane**
   (`render.c:1210`), the **light overlay** (`:1489`), and an **app-issued skeleton overlay**
   (`apps/render/src/render.c:1607`, drawn while the scene FBO is still bound — the list did not
   consider app-level draws at all). And the depth prepass is *not* covered by its existing mask:
   it uses `glColorMask` (`render.c:727`), and **`glColorMask` does not mask stencil**.
3. **So do not enumerate — bracket.** Enable `GL_STENCIL_TEST` and the write mask only for the
   duration of the opaque+masked lane, between `engine_set_scene_draw_buffers(engine, true)`
   (`render.c:1120`) and its `false` counterpart (`:1212`), and leave the global state at mask 0 /
   test off. One bracket makes all twelve other sites right by construction instead of by twelve
   separate promises, and it matches the existing "G-buffer scope" idiom already used for the
   indexed blend disables. It also survives the next pass someone adds.
4. **The frame clear must be reached with the mask at `0xFF`.** `glClearStencil` is never called, so
   the clear value is the GL default 0 — which happens to be exactly the "not skin" tag, free
   correctness that holds by default rather than by decision. But the moment phase 2 starts setting
   `glStencilMask(0)`, the clear at `engine.c:2400` stops clearing stencil unless the mask is
   restored first, and a tag that persists between frames is worse than one that averages.
5. **The seed and the downsample chain share one FBO** (`sss_pyr_fbo`, re-attached per mip at
   `postfx.c:1363-1367` with a shrinking viewport). A full-res stencil attached for the seed would be
   read at the wrong texels by the smaller mip draws, so the test has to be disabled — or the
   attachment dropped — before `sss_pyr_down_program` runs.
6. **A second depth-stencil blit is cheaper than the linearize pass.** The feedback loop is real and
   confirmed — both passes sample `fx->depth_texture`, which *is* the resolve destination
   (`create_depth_fbo`, `postfx.c:172-198`), and the SSS FBOs currently attach colour only, so
   attaching it for the stencil test creates exactly the prohibited sample-and-attach configuration
   that `postfx.c:1369-1372` already documents for the mips. But the remedy need not be a new R32F
   view-Z pass: blitting stencil into a **second `GL_DEPTH24_STENCIL8` texture** and attaching that
   leaves `fx->depth_texture` free to sample, costs one extra blit and no shader, and leaves phase
   1's depth handling alone. Do **not** blit into a `GL_STENCIL_INDEX8` renderbuffer instead — the
   "formats already match" argument holds only packed-to-packed.

## And the thing phase 2 should also do, which nobody had noticed

**Once the tag leaves alpha, that channel should carry real COVERAGE.** Two comment blocks added by
`0b7dcef` already describe this as done, and it is not: the seed's `:51-70` says *"COVERAGE comes out
of the resolve, and declaring it 1.0 is what put light in the frame that nothing emitted"* in the
past tense, while `:92-93` still rounds the alpha to an integer and writes a flat `1.0`; and the
gather's `:203-211` says the delta is *"Scaled BACK by coverage"* while `:212` applies no coverage
factor at all (that block also duplicates its own first two lines).

This is the substitution that makes the resolve *valid* for the channel rather than merely moving the
problem: coverage is linear in radiance, which a categorical tag never was. So phase 2 is two
changes, not one — the tag moves to stencil, and alpha's meaning changes from label to coverage, with
the seed's `1.0` becoming `d.a` and the gather's delta gaining its scale. Shipping only the first
leaves a channel that means nothing and two comments that still lie.

# As built — phase 3 (built before phase 2, per the corrected order)

`assets/sss_msaa_fixture.cscn` and two arms in a new `sss-tag` gate group. **No new geometry**:
`sss_fixture.gltf` already carries two meshes with two materials, so this is a `.cscn` and a
camera. The spec's "build two-profile thin or small geometry" reads as new geometry and did not
need to be — *small* is a camera distance.

## The number — CORRECTED

**An earlier revision of this section reported +3.58% on a band outside the silhouette. That
was bloom, and it is withdrawn.** The gather early-outs off-surface, so SSS provably never
paints outside a subject; with `--no-bloom` that band reads R/G 0.9999 in both variants, which
is neutral background. What filled it was the one-profile twin removing SSS from the OTHER
sphere -- a large shading change that bloom spreads across the whole frame. The arm now passes
`--no-bloom`, and reads a band ON the sphere, which is the only place the delta is ever added.

**The fixture also had to be re-lit.** Scatter is `blur - centre`, so a uniformly lit sphere
contributes nothing however wrong its profile is. Under the original back key the entire
gather moved 129 px of the frame and the misfile moved 23 -- the terminator is what makes the
defect exist to be measured at all.

With both corrected, sample count held fixed at 4x and only the profile count varying:

| build / config | tag-2 rim R/G shift |
|---|---|
| **before phase 2**, 4x MSAA | **+2.174%** |
| **before phase 2**, 1 sample | **0.000%** |
| after phase 2, 4x MSAA | **0.000%** |

The 1-sample row is the control that makes the top row attributable: with no partial coverage
there is nothing to average, so it held at zero while the 4x arm was failing. The difference is
about coverage, not about a second profile existing.

## Three things the design got wrong first, all of which produced a plausible number

1. **Comparing 4x against 1 sample does not work, and fails in the flattering direction.**
   Antialiasing dominates — the rim blends with the backdrop at 4x and is binary at 1 — and it
   moves the same read from 0.4648 to 0.4396, i.e. the *opposite* way from a misfile. An arm built
   on it would have reported the defect as absent. This is why the isolation varies the profile
   *count* instead.
2. **Locating the sphere by its own hue includes its scatter halo**, so the radius reported moves
   with the very thing being measured and the two frames get different rings. That read **19%**
   where pinned rings read 3.6%. The geometry is now projected from the camera, which is
   shading-independent.
3. **Weights beat radius, measured.** Opposite channel weights at equal radius give 3.6%; equal
   weights at radii 1.2 against 0.35 give only 2.0%. The scatter delta is what the blur differs
   from the sharp value by, so a weight substitution acts on it directly where extra reach does
   not. Equal radii also keep profile a's halo from crossing the 26 px gap into the read band —
   and since the twin has no profile a at all, a halo that reached it would plant a difference
   that is nothing to do with the tag.

## What the arms assert, and when they invert

`sss-tag` characterizes the defect at its size; `sss-tag-core` asserts the interior does not move.
Neither is the correct invariant — that is "the two frames agree" — because no fix lands in this
branch. **Phase 2 inverts `sss-tag`**, and it is written to say so, so reaching zero requires an
edit here rather than a silent pass.

Verified inert: **23/23 goldens 0 px**. Phase A adds an asset and a gate arm and touches no
shader and no C, so it could not move one — confirmed rather than assumed.

# As built — phase 2: BUILT, MEASURED, AND REVERTED

Phase 2 works and does not ship. It fixed the misfile — the tag-2 sphere's rim went
**+2.174% → 0.000%** — and broke `sss-scale`, the gate that holds delivered scatter width
independent of resolution, which spec 11.14 exists to establish. Reverted at `3426836`; the fixture, the arms and this record stay.

## Why it cannot work, which is the finding

**The SSS passes are per-PIXEL fullscreen quads, so they can read exactly one stencil value per
pixel.** Resolving a per-sample stencil down to one value per pixel selects a single sample —
and that discards coverage entirely. A rim pixel 90% covered by skin is rejected if the selected
sample happened to miss; one 10% covered is admitted if it happened to hit.

That selection is **uncorrelated with coverage**, where the alpha rule it replaced (`admit iff
coverage >= 0.5`) was monotonic in it. Monotonic error degrades smoothly and cancels across
resolutions; arbitrary error does not, and its weight scales with the rim's share of the object
— which shrinks as the object grows in pixels. Hence a gate failure visible at 500p and absent
at 2000p.

So the tag move trades a **categorical** error (wrong profile) for an **arbitrary** one (right
profile, or dropped, by dice). Semantically better and numerically worse, on the axis this
project already decided it cares about.

**Per-sample storage cannot help a per-pixel consumer.** The complete answer is per-sample
shading of edge pixels, which this spec's own Non-goals already exclude — it needs `sampler2DMS`
and 11.17 rejected that. This phase discovered the reason that exclusion is load-bearing rather
than merely expensive.

## The bisect, because the conclusion rests on it

| config | 500p | 2000p | drift | |
|---|---|---|---|---|
| baseline | 7.04° | 7.16° | 1.7% | PASS |
| coverage arithmetic alone | 7.57° | 7.37° | 2.6% | PASS |
| + stencil | 7.57° | **7.16°** | 5.4% | **FAIL** |

The coverage arithmetic moves both resolutions *together*, so invariance survives it. The
stencil moves only one. That row is the whole argument.

## And the two halves are not separable

"Keep the coverage half" is not available: alpha holds one thing, and coverage-in-alpha works
only by *displacing* the tag. Keeping it leaves multi-profile scenes with no tag at all. That is
the same one-channel squeeze the phase started from, and it is why the revert is total.

A related note worth keeping, because it explains why the coverage change measured as a no-op in
single-profile scenes: with one profile the tag IS 1, so `alpha = tag x coverage` already equalled
coverage. The two readings only diverge once a second profile exists.

## What still stands

`4446a07` stays: `apps/tree`'s grass keeps sharing the leaf's profile, and the 0.15 / 0.25 radius
distinction stays lost. That commit's remedy was right even though its stated cause was not — the
misfile is real, and one tag in a frame makes it unexpressible.

The defect is now measured (+2.185%), guarded by `sss-tag`, reproducible from a committed fixture,
and has a written reason why the obvious fix is not the fix.

# What phase 2 did, for the record

Shipped. The tag lives in stencil, alpha carries coverage, and `apps/tree` has two live SSS
profiles again.

**Result:** the tag-2 sphere's rim moves **+2.174% → 0.000%** when a second profile exists in
the frame, with the 1-sample control at 0.000% throughout. `sss-tag` inverted from asserting
the frames differ to asserting they agree.

## The two halves are one change

Moving the tag out means every partly covered pixel now reaches the pyramid, where before those
under half coverage were dropped by the rounding — and the seed was declaring their coverage
`1.0` while the resolve had already dimmed their radiance. That is the seed's own *"light in
the frame that nothing emitted"*, and phase 2 would have made it **worse** rather than better.
So alpha stopped carrying a label and started carrying coverage in the same commit: the scene
pass writes 1 on skin, the resolve returns the covered fraction, and **coverage is linear in
what a box filter computes** — the property that channel needed for its resolve to be valid at
all rather than merely relocated. The gather now un-premultiplies before differencing and
scales the delta back by coverage, which at full coverage is exactly the old arithmetic, so
only silhouettes can move.

## Corrections to the design, all confirmed by building it

- **One bracket, not twelve opt-outs.** A stencil write requires `GL_STENCIL_TEST`, so enabling
  it across the opaque lane alone makes the skybox, catcher, water, OIT, particles, gizmos,
  overlays and the prepass unable to touch the tag — rather than each being told not to. The
  next pass added to this FBO is safe without knowing any of this exists.
- **A renderbuffer, not the depth texture.** Both SSS passes sample `depth_texture`, and
  attaching a texture while sampling it is undefined on GL 4.1. A renderbuffer cannot be sampled
  at all, so the conflict is unconstructible. One extra blit, one D24S8 at render res — cheaper
  than the R32F linearize pass the design assumed, and it leaves phase 1's depth handling alone.
- **`glStencilOp(KEEP)` for read-only, never `glStencilMask(0)`.** This one cost a debugging
  round and is the most transferable thing here. The write mask *also gates `glClear`*, so a
  mask left at 0 stops the frame clear **and** the scene's `REPLACE`; the buffer freezes at
  frame 1 and every later frame blurs where the geometry used to be. It shows as pale stationary
  discs that stay put while the subject moves — **invisible in a still frame**, which is why the
  fixture never caught it and a moving camera did immediately.
