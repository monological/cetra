# Spec 11.74 — what the decal review left

## Context

Spec 11.73 (clustered decals) merged after a seven-agent review that found five real defects and
took its gate group from 8 arms to 12. The review also produced a list of things declined or not
reached; 11.73's REVIEW ROUND records it. This spec closes the four worth closing while the
reasoning is still in someone's head, and leaves the rest declined with those reasons standing.

**One item changed shape during exploration and the plan says so up front**, because the
correction is the interesting part: the missing `texture_retain` on decals is NOT the
use-after-free it looked like. `create_texture` starts the count at 1 and *that is the pool's
own reference*; `free_texture_pool` releases it rather than force-freeing. A decal storing a raw
pointer is therefore balanced today — and **adding a bare retain with no matching release would
turn a clean teardown into a leak.** The fix is the symmetric pair or nothing.

## The four changes

### 1. Decals retain their textures, and release them

`apply_cscene_decals` (`apps/render/src/cscene_apply.c:530-531`) stores raw pointers. All sixteen
material setters (`cetra/src/material.c:368-509`) retain, and `free_material`
(`material.c:306-353`) releases every slot including the layer array — so the convention is
symmetric and real, not a one-way marker.

Do both halves:
- retain in `apply_cscene_decals`, the `x = texture_retain(t)` form the setters use;
- add the matching release to `free_scene` (`cetra/src/scene.c:95-239`), which today contains no
  decal teardown at all. It must run **before** `free_texture_pool` at `scene.c:101-104`, matching
  how materials are ordered against it.

**This is a convention fix, not a bug fix, and the plan should not oversell it** — settled with
the user on exactly that framing. Nothing evicts a texture mid-session
(`remove_texture_from_pool` and `clear_texture_pool` have no callers outside `free_texture_pool`),
so the refcount is only exercised at process teardown and today's code is balanced. The value is
that a decal stops being the single consumer that would break on the first eviction, and that a
silent deviation from a unanimous convention stops being indistinguishable from an oversight.
`--no-decals` is safe either way: it now guards the apply, so no decal image is ever loaded on
that path — which also means the `decal_count = 0` at `render.c:3690` cannot orphan a retain.

### 2. A failed array build stops leaving live decals pointing at nothing

`material_texture_array_build` (`cetra/src/material_texture_array.c`) writes decal layer indices
at lines 131-135, then has two `-1` returns after them, and `arr->layer_count = count` only at
line 262 — after both. `ensure_built` (`:284-296`) clears the dirty flag only on success, so a
failing build retries every frame.

The worse of the two is the `mask_copy`-missing path (`:211-217`): lines 197-206 have already
deleted the old array and allocated a new one with **undefined contents and no mip chain**, so
every `textureGrad` returns `(0,0,0,1)` — which for a decal is `alpha = 1.0`, i.e. a fully opaque
**black** mark over every fragment inside every decal box, re-allocated once per frame. The
max-layers path (`:144-150`) leaves the old array bound while indices point past it; GL clamps the
layer to the last existing one, so a decal reads the wrong image rather than crashing.

Set `albedo_layer` / `surface_layer` back to −1 on both paths. `_decal_is_live`
(`cetra/src/decal.c:17-19`) then refuses, which is the state that already means "not yet built".

### 3. One spelling for the three z-clamps

`light_cluster.c` computes a sphere's slice range three times — lights `:269-271`, probes
`:430-431`, decals `:521-523` — in three different expressions, including `fmaxf` where the others
use `fminf`.

**They are equivalent, and this is a readability change with no pixel behind it.**
`_slice_for_z` (`:61-65`) clamps its input to ≥ 1e-4 and saturates its output to
`[0, LC_CLUSTER_Z-1]`, and `slice_bias` is built so `slice(near) == 0` — so every divergent case
lands on the same slice. The plan states that rather than implying a fix, and the comment that
lands with it should record **what the equivalence rests on**: both internal clamps. Remove the
input `fmaxf` later and the probe spelling becomes the only safe one while the light/decal
spelling becomes the only correct one at the far plane.

**Scope: the CLAMPS only.** The probe path also lacks the depth-range early-reject lights and
decals carry (`:269-270`, `:517-518`). Adding it would be a real behaviour change — mask bits
could only fall, but that needs a probe-gate reading to assert rather than argue — so it is out of
scope and noted for a later spec.

### 4. An arm for decal-over-decal compositing

The fixture's two decals are disjoint in two axes, so `acc = tex*a + acc*(1-a)`
(`decals_ubo.glsl:186`) has never run with a non-zero accumulator. The documented "authored order
is paint order" contract and the whole multi-decal path are untested.

**The committed fixture does not change** — 11.68's rule (*"the committed fixture stays road-free;
road arms render runtime variants"*), and here it is load-bearing rather than stylistic: two arms
assert an exact decal count (`decals-mask`'s `live == 2` at `gates.py:14900`,
`decals-schema`'s `len(clean) == 2` at `:14931`), and four gate mutations index `decals[0]`
expecting the poster. A runtime `cscn_copy` variant leaves all twelve arms untouched. There is no
committed golden for this fixture — `goldens.py` never names it — and no other gate group loads
it, so the blast radius is `run_decal_gate` alone.

**The overlap reuses `decal_scorch.png`**, so no new asset and no image change: the generator
gains constants and asserts and emits the same three files byte for byte, which is exactly what
11.68's generator did for roads. The scorch's flat `(40,40,44)` separates well from the poster's
lower-left quadrant `(96,112,200)` in every channel.

`decals-overlap`: a variant **appends** a decal over the poster's lower-left quadrant — appending
is what gives it the later paint order, since `decalAccumulate` iterates ascending and a later
index paints on top. Read inside the overlap and assert the **later** decal's code; read the
poster outside the overlap as the in-frame control.

- **Anti-vacuity:** the control must return the poster's own quadrant code, or the variant has
  covered everything and the arm is asserting one decal.
- **Falsified by:** reversing the accumulation to `acc = acc*a + tex*(1-a)`, which makes the
  overlap read the poster instead.
- **Read points from the generator, asserted** clear of `POSTER_READ`, the four `QUAD_READS`,
  `FEATHER_READ` and `OBLIQUE_READ`, inside the poster's opaque and unfeathered region
  (`|local| < 0.65`), and on the wall plane. The free rectangle is poster-local
  x ∈ (−0.32, +0.50), y ∈ (−0.30, +0.50), bounded left by the oblique plate and elsewhere by the
  existing reads — **about 3.4 px of margin at this framing**, so the box wants to be the smaller
  end of that and the read points verified by rendering, not by arithmetic alone.
- The generator gains the assert nothing currently makes: that the overlap's index in
  `CSCN["decals"]` is greater than the poster's. Paint order is the arm's whole premise and today
  it is only a position in a JSON list.

**Deliberately NOT changed: the inter-decal blend stays in sRGB code space.** Decal-over-decal
composites in stored codes while decal-over-substrate composites in linear. That is a real
inconsistency and it is also the trade `layers.glsl` already makes on purpose; fixing it means
decoding per decal inside the loop, buying back exactly the `pow()`s 11.73 removed from the hot
path for every fragment of every decal-armed scene. The arm asserts current behaviour and the
choice gets stated in `decals_ubo.glsl`'s header, where it is currently only implied.

| `cetra/src/scene.c` | release them in `free_scene`, before the pool |

## Verification

```bash
./build.sh
python3 scripts/gates.py --only decals        # 13 arms
python3 scripts/gates.py --only fixture-gen   # the generator must still emit byte-identical files
python3 scripts/gates.py --only gate-docs
python3 scripts/gates.py --only layers        # shares the material texture array
python3 scripts/gates.py --only probe-set     # the z-clamp edit touches the probe path's source
python3 scripts/goldens.py                    # 27 goldens, 0 px
```

Items 1-3 must move **no pixel anywhere** — if a golden moves, that is the finding, not a rebake.
Then every named mutation run and recorded, and the full suite once at the end.

## Not in scope

Unchanged from 11.73's REVIEW ROUND: extracting the froxel-mark walk, the full `TextureKind` enum,
FNV-1a's five word-wise copies, `_decal_run`/`_probe_run` unification, the `gen_*.py` helper
triplication, `render_frame_update`'s fourth `get_current_scene`. Newly noted here for a later
spec: the probe path's missing depth-range reject (item 3), the bake-time `GL_REPEAT` wrap in
`mask_copy`, the `decalSurf` live-range measurement 11.73's AS BUILT 11 left undone, and coverage
for the late/transparent pass, an authored `up`, and the `DECAL_MAX` overflow.
