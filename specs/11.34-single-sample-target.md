# Spec 11.34 / E9 — one sample means one sample

## Context

The engine's scene framebuffer is always allocated as `GL_TEXTURE_2D_MULTISAMPLE`, even when 1
sample is requested — and this driver refuses a 1-sample multisample target, returning a **2-sample**
one (the build now logs it: "asked for 1x MSAA, driver gave 2x", found by 11.31's instrument work).
The shipping AA path is TAA, which requests 1 sample *precisely to avoid MSAA*. So every windowed
session and every `--taa` run rasterizes two samples per pixel, stores 2x the depth and colour, and
resolves — on the configuration whose −29% (TAA replacing 4x MSAA, spec 11.30) was measured believing
it had none of that.

Booked as roadmap E9, "found by 11.31, not yet costed". This spec costs it first and builds it only
if it pays.

**Two corrections to the roadmap row, established by exploration before any code:** the row says the
fix needs "postfx's resolve reaching it through `sampler2D` instead of `sampler2DMS`". That is stale
twice over — there is **no `sampler2DMS` anywhere in the codebase** (spec 11.17 explicitly rejected
it: "would be the corpus's first — avoid"), and postfx reaches the scene target **only through
`glBlitFramebuffer`**, never a sampler. A single→single blit is a legal exact copy, so postfx needs
zero functional changes. The GLSL surface of this change is **zero files**.

## What the exploration established

1. **One allocation site.** `_add_msaa_color_attachment` (`engine.c:559-565`) is the only
   `glTexImage2DMultisample` in the tree, and `engine.c:596` the only
   `glRenderbufferStorageMultisample`. The helper has 4 callers covering 10 textures: the scene
   MRT loop (6 targets via the `_gbuffer_attachments` table), OIT accum/revealage
   (`engine.c:1930-1932`), moment b1..b4/b0 (`engine.c:2013-2015`).
2. **No multisample texture is ever sampled.** Every one of the 11 multisample allocations is only a
   render target and/or a blit source. Consumers reach them through FBO names, never texture names.
3. **All 5 affected blits stay legal single-sample** (`engine.c:1847`, `:1906`, `:2096-2101`,
   `postfx.c:2002-2009`, `:2707`, `:2877`): identical rects, identical formats, `GL_NEAREST`. None
   combines a multisample read with scaling or `GL_LINEAR`.
4. **The atomicity constraint.** The scene FBO, OIT FBO and moment FBO all share
   `engine->depth_renderbuffer`, and GL requires all attachments of one FBO to have the same sample
   count. All four allocation sites pass the same `engine->msaa_samples`, so ONE branch inside the
   helper plus one at the renderbuffer flips everything in lockstep by construction. Branching at the
   callers would be the fragile version. (One explorer recommended caller-side branching; it is wrong
   for exactly this reason.)
5. **The `GL_SAMPLES` readback already handles it.** A single-sample FBO reports `GL_SAMPLES == 0`
   and the existing `got < 1 ? 1 : got` clamp maps it to 1. `msaa_samples_actual` starts telling the
   truth with no change.
6. **`a2c_capable` (`render.c:325`) already reads the request** — deliberately, after 11.31 measured
   routing it to the actual count at 18% on raiden and rejected it. Under this change request and
   actual agree at 1 and its comment's premise ("those diverge") goes stale, not its behaviour.
7. **A correctness win rides along.** Spec 11.17 records MSAA moment resolution as mathematically
   biased (moments sum linearly, reconstruction is nonlinear — biased exactly at hair tips). A
   genuine 1-sample target makes that bias vanish on the TAA path.
8. **The capture path is not a precedent.** It renders into a colour-only single-sample scratch FBO
   with every G-buffer-dependent pass skipped via `!engine->capturing`. It proves the raster passes
   don't care about sample count; it adapts nothing.
9. **The verification surface is small.** Zero of the 22 goldens carry `--taa`, so **no stored image
   can move** — goldens run headless at 4x MSAA, which this change does not touch. The gate arms on
   the 1-sample-request path are: `_taa_churn` (frame-to-frame within one run), `gpu-scale` (timing
   ratios), `mask-opaque`/`mask-cutoff` (two quads within one frame, both losing the same second
   sample), the six overdraw renders (integers; `GL_SAMPLES_PASSED` and the budget both halve so
   complexity ratios are preserved — `overdraw-exact` still reads exactly 8.00), and
   `prepass-shading` (ratios + draw counts). All should survive; run the suite to confirm rather
   than assert.
10. **What actually changes on screen**: the 1-sample-request path loses the *accidental* 2-sample
    geometric edge AA it never knew it had. That is every windowed session and every `--taa` run.
    Nothing stored asserts on those pixels, so this is a look call — decided by crops, per the
    A2C precedent.
11. **The sharp edge is the runtime toggle, not startup.** There is a THIRD caller of
    `set_engine_msaa_samples`: the GUI "MSAA 4x" checkbox (`gui.c:598-605`), which flips 4↔1 live
    through `_engine_rebuild_msaa_target` — tearing down and rebuilding the shared
    `depth_renderbuffer` plus the OIT and moment FBOs. **No gate or golden covers the runtime
    toggle**; every one sets the mode once at startup. The single-sample path must survive a live
    4→1→4 round trip, verified by hand in the windowed app.
12. **One measured literal to watch, not pre-tune:** `CLOUD_CHURN_FACTOR = 9.7` (`gates.py:1500`) is
    a hard-coded churn ratio measured on the 2-sample path; it is the constant most likely to need
    re-derivation if the churn arms move. `cloud-churn` is currently report-only, so watch it rather
    than trust it. The other churn constants are coarser and should hold.
13. **Two different −29% figures exist for forest and must not be conflated in the spec:** TAA
    replacing 4x MSAA (11.30: opaque 551→393 ms) and the front-to-back sort (11.30: 551→394 ms,
    later revised to −45% by 11.31). Same scene, same magnitude, different levers.
14. **MSAA shades per pixel, not per sample**, and the resolve rows already read 0.000 ms in the GPU
    table. So the win is per-sample depth/coverage/blending work and bandwidth inside the `opaque`
    row — which is why Phase 0 measures before Phase 1 builds.

## Phase 0 — price it before building it (decision gate)

Nothing today can vary sample count independently of TAA: MSAA is only reachable as "TAA off → 4"
or "TAA on → 1". Add the lever, then measure.

- **`--msaa <n>`** on the render app (`render_args.h` + `render.c`, Pattern A) and forest
  (`forest.c`), applied AFTER the TAA branch so `--taa --msaa 4` is expressible. Clamped by the
  existing `_clamp_msaa_samples`. ~30 lines, useful beyond this spec.
- **Measure forest's opaque GPU row** at request-4 (actual 4) vs request-1 (actual 2), TAA held on,
  1600x900 / 60 frames — the config with the measured 0.23% floor. INTERLEAVE the configs (A/B/A/B)
  per the protocol 11.31 established; never A-then-B.
- The 4→2 delta prices a sample. Extrapolate 2→1 as roughly half that saving (it is a step, not a
  slope — 2→1 also ends multisample rasterization outright — so treat the extrapolation as a floor).

**Gate: if 4→2 moves the opaque row by less than ~3x the floor, stop.** Close E9 as measured-and-not-
worth-it, keep the flag, record the number in the spec and the roadmap row. That outcome is a
success, not a failure — 11.30/11.31 withdrew seven claims that were written before measuring.

## Phase 1 — the single-sample scene target (only if Phase 0 pays)

One branch, inside the helper, so all four callers and all three shared-depth FBOs flip atomically:

- `_add_msaa_color_attachment` (`engine.c:559`): at `samples <= 1`, allocate `GL_TEXTURE_2D` via
  `glTexImage2D` + `glFramebufferTexture2D(..., GL_TEXTURE_2D, ...)`, with NEAREST/CLAMP sampler
  params (multisample textures carry no sampler state; a plain texture must set it — follow
  postfx's `create_color_fbo` (`postfx.c:29-64`), which is the house pattern for exactly this and
  already knows every format in the MRT table except RGBA32F/RGBA8, both trivial). Rename the helper
  (`_add_scene_color_attachment`) since its name would lie.
- The depth renderbuffer (`engine.c:596`): `glRenderbufferStorage` at `samples <= 1`,
  `glRenderbufferStorageMultisample` otherwise. It stays a renderbuffer — it was never sampleable
  either way, which is why `engine_resolve_scene_depth` exists.
- Rewrite the helper's header comment: the current one is E9's job ticket, and its `sampler2DMS`
  premise is wrong.

Explicitly NOT in this phase, recorded in the spec as banked follow-ons so they are not silently
bundled: eliminating the now-pure-copy hdr resolve blit (`postfx.c:2707`), dropping
`moment_b0` from RGBA32F to R32F (the "blit demands identical formats" constraint relaxes), replacing
the depth renderbuffer with a depth texture and deleting `engine_resolve_scene_depth` on the 1-sample
path. Each is its own measurable change.

## Phase 2 — verify, and decide by crops

- **Full gate suite + all 22 goldens.** Goldens must be 0 px by construction (none runs at a
  1-sample request); a moving golden is a finding, not a re-bake. Run ONCE, tee to a file, grep the
  file (memory: never re-run to re-read).
- **The arms that CAN move** are the `--taa` family from finding 9. Expected: complexity ratios
  identical, `sample budget` printed at half, pixel-churn arms still within their floors. If
  `mask-opaque`'s 2% band or the churn floors break, that is the second sample's edge AA showing up
  — measure, don't tune the threshold to fit.
- **A/B crops for the look call**, per the user's decision: forest foliage and the raiden groom,
  current (2-sample) vs genuine 1-sample, both under TAA, point-filtered magnification — the same
  discipline as the A2C comparison. TAA is designed to carry edges; whether it does well enough
  here is decided by looking, before merge, not after.
- **Confirm the log line flips**: "asked for 1x, driver gave 2x" must disappear; `GL_SAMPLES == 0`
  clamps to 1 in `msaa_samples_actual`.
- **The runtime toggle, by hand** (nothing automated covers it): windowed render app, flip the GUI
  "MSAA 4x" checkbox 4→1→4 with an OIT scene loaded (raiden), and confirm no
  "OIT framebuffer incomplete" / "moment framebuffer incomplete" in the log — those are the quiet
  failure modes of the shared-depth rebuild, and they degrade rather than crash.
- **Measure the actual win** on forest, interleaved, same protocol as Phase 0, and record it against
  the Phase 0 prediction. Also re-measure the interior (`abandoned_window_shadowed`) — its numbers
  are small but its floor is 0.04%. Optional, cheap, and makes the win defensible: a gate arm on the
  `msaa resolve` row via the existing `_timing_delta(row=...)` — the row is not in
  `GPU_REQUIRED_ROWS`, so today nothing would notice the resolve disappearing OR regressing.

# As built

## Phase 0 — the price, and the confound the first A/B hid

The naive comparison (`--msaa 4` vs the default) read 539.8 vs 150.9 ms and was **confounded**:
`a2c_capable` flips with the sample count, so that delta moved two variables. Adding `--msaa 2`
split it, interleaved with repeats at 1600x900/60f, TAA held on:

| config | samples | A2C | opaque mean |
|---|---|---|---|
| `--msaa 4` | 4 | on | 539.8 ms |
| `--msaa 2` | 2 | on | 353.2 ms |
| default | 2 (accidental) | off | 150.9 ms |

**A2C alone costs 202 ms** of forest's opaque row — the fragment set explodes when foliage stops
discarding. Headless-only relevance, but it is the corpus's first direct measurement of what the
A2C path costs on real content. **A sample costs ~93 ms** on that inflated set. The E9 estimate —
2→1 on the smaller A2C-off set — came out at ~40 ms optimistic, and the decision bar (3x the 0.23%
floor = 0.35 ms) was cleared by two orders of magnitude under any discounting.

## Phase 1 — as planned, one branch, and the measured win

Landed exactly as designed: the branch inside the renamed `_add_scene_color_attachment` plus one at
the depth renderbuffer, flipping the shared-depth family atomically. Zero shader changes, zero
postfx changes, as the exploration predicted.

**Measured: forest opaque 150.9 → 121.6 ms (−19.4%)** against the 0.23% floor, with byte-identical
submission integers — 1127 draws, 2979 instances, the same triangles. The same work, cheaper. Just
under the optimistic ~25% estimate, well above any discounted one. The "asked for 1x, driver gave
2x" log line is gone; the sample budget reads `rw*rh*1`; the OIT moment allocation drops by a third,
not half — the formula is `2*samples + 2`, so 2→1 takes the factor from 6 to 4: the two multisample
targets halve, the sample-independent atlas does not (227 MB at the raiden size).

## Phase 2 — everything held

- **All 23 goldens 0 px** — the 4x path untouched by construction, and now by evidence.
- **The crops**: raiden strands at 400% and forest canopy against the sky at 300%, point-filtered,
  before (accidental 2-sample) vs after (genuine 1-sample), both under TAA. Indistinguishable. TAA
  carries the edges; the accidental second sample was buying nothing visible.
- **The live rebuild** (the GUI toggle's path): 4→1 and 1→4 with raiden's OIT loaded, both
  directions complete, moments allocating at the right count. No incompleteness.
- **One gate arm failed and the failure was the arm's**, third strike for the same shape:
  `prepass-crossover`'s floor sampled 5% against a rigid <3% ceiling while its effect read +18% — a
  sound measurement at 3.6x separation, rejected by a rule asserting on the weather. Probed the
  floor x3: it genuinely wanders 0.2–5% at ~2.9 ms absolute. The assertion is now **relative** —
  the effect must clear the measured floor by 3x — which keeps the floor-swallows-signal property
  the ceiling was for without failing a wide floor under a wider effect.

## What rides along

- **MBOIT's moment-resolve bias (11.17) is gone on the TAA path.** Moments sum linearly and
  reconstruction is nonlinear, so multisample moment averaging was biased exactly at hair tips; at
  a genuine single sample there is nothing to average.
- `--msaa <n>` outlives the spec as the only lever that varies sample count independently of TAA.

## Banked follow-ons — two resolved as an addendum, one declined, one open

- **DONE (addendum):** `moment_b0` RGBA32F → R32F at one sample — the "resolve blit demands
  identical formats" constraint only ever bound multisample, so the padding goes on the shipping
  path: a quarter of the b0 target. The VRAM log's formula moved with it.
- **DECLINED, and the note it came from was wrong:** replacing the depth renderbuffer with a depth
  texture and deleting `engine_resolve_scene_depth`. Both of that resolve's consumers — soft
  particles and water — sample the copy WHILE the scene FBO is bound and being drawn into, so the
  copy is the **feedback-loop break**, exactly as `engine_resolve_opaque_color`'s comment records
  for colour, and not a workaround for the renderbuffer being unsampleable. Aliasing the depth
  attachment into a sampler during those passes is undefined on GL 4.1. The copy is load-bearing;
  the deletion this item promised does not exist.
- **Open, deliberately:** eliding the now-pure-copy HDR resolve blit (`postfx.c`) and binding the
  scene colour directly. Looks like deleting a blit; is actually aliasing `hdr_texture` onto the
  scene target, which later passes write into, with differing sampler state, while the 4x path
  still needs the copy. Its measured motive is also weak — the resolve rows read ~0 ms. Priced as
  not-worth-it until a measurement says otherwise.
- **Open:** re-measure forest's `--taa` pixel floor (the recorded 140,910 px was taken against the
  accidental 2-sample target; AGENTS.md is era-stamped).
