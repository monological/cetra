# Spec 11.90 — the shadow pass

## Context

Tier 5, phase 1 of six. The evidence base is `specs/11.89-frame-budget-and-an-honest-instrument.md`
and this spec cites it rather than re-deriving it. In short: `apps/forest` renders at **127.7 ms**
against a 16.6 ms budget, GPU-bound, and the shadow pass is **33.7 ms of GPU and ~33 ms of genuine
CPU submission** — the only CPU row in the frame that carries a claim, proven by `--no-lod` taking it
to 11.9 ms while its GPU only moves 33.1 → 29.8.

Four of 11.89's nine root causes live in this one subsystem. They are taken together because they
share a fixture, a measurement, and in two cases a fix.

## What is wrong

### 1. Cascade 1 and cascade 2 cover almost the same ground

`shadow.c:1399-1421` uses a practical (Zhang) split with **`lambda = 0.75` as a literal** at `:1412`,
and `shadow_dist = fminf(ss->far_plane, camera->far_clip)` at `:1414`. **There is no shadow distance
separate from the camera far clip.** Forest's is 2000, so the splits land at 172.7 / 427.9 / 2000.

At fov 58° / 16:9, `k2 = 1.278 > 1`, so the `zc > slice_far` clamp at `shadow.c:342` always fires,
`dz = 0`, and `radius = 1.1306 · slice_far`. The outermost cascade is not a slice fit at all — it is
the whole-scene fit (`shadow.c:1461-1467`) at `2 × ortho_size`:

| cascade | ortho box width | texel @2048 |
|---|---|---|
| 0 | 390.5 | 0.191 |
| 1 | **967.8** | **0.473** |
| 2 | **1000.0** | **0.488** |

**Within 3% of each other.** Cascade 1 costs a full whole-scene traversal for almost nothing, and
`pbr_frag.glsl:825` unions the fragment's own cascade with every wider one, so a near fragment
samples both near-identical maps.

### 2. The pass re-uploads `model` for instanced runs

`shadow.c:703` calls `uniform_set_mat4(u, "model", ...)` unconditionally. The camera path guards
exactly this at `render.c:899`, with the reason at `:894-898`: *"a batched draw reads the transform
from the instance block, and writing `model` anyway dirties the program's whole uniform block and
costs a copy of it at submission. This pass exists to be cheap; it should not re-buy that."* The pass
that issues more draws than any other in the engine does not have the guard.

### 3. Runs must be contiguous, so camera-derived LOD shatters shadow batching

`draw_run_can_join` (`draw_list.c:327-329`) needs same mesh, same LOD, and visible;
`_visible_caster_run` (`shadow.c:633-645`) then walks contiguous items only, because
`instance_chunk_upload` indexes with raw list indices and cannot skip. Mean batch size in the shadow
pass is **2.79 of a possible 64**.

LOD is selected from the camera (`render.c:722`), so instances form concentric LOD rings around the
camera and every ring boundary crossed in graph order ends a shadow run — even where the cascade sees
those instances identically.

**Spec 11.28's reason for camera-eye selection is sound and stays** (`draw_list.h:62-65`): a caster
whose depth-map silhouette DISAGREES with the surface it is shaded with reads as acne. Note the rule
is symmetric and an earlier draft of this spec narrowed it to "coarser" — a caster drawn *finer*
than the surface it shades puts that surface behind its own depth map, so pinning the shadow pass to
level 0 is refused for the same reason as coarsening it. **What the rule does not license is the
shadow pass inheriting the camera's batch fragmentation** along with its levels, which is what
happens today.

### 4. Nothing is cached, staggered, or skipped

No dirty flag, no sun-moved test, no frame parity, no static/dynamic split. Every cascade of every
caster is cleared and fully re-rendered every frame, and each punctual face costs a whole scene
traversal (`shadow.c:1556-1557`).

**The outermost cascade is the natural first cache target and carries the largest caster set.** Its
matrix comes from `compute_directional_light_space_matrix(light->direction, scene_center, ortho_size,
near_plane, far_plane)` (`shadow.c:1462`), which in forest depends on nothing that changes. Skipping
`begin_shadow_pass` also skips its `glClear`, so content persists correctly.

Two things block naive caching and both are tractable. **Wind** displaces every tree every frame
(`wind.glsl:79-128`), and `object_position.glsl:1-24` establishes the shadow pass must displace
identically to the shading pass — but `wind_max_offset` (`wind.c:89-125`) is already a closed-form
conservative envelope. And **movement detection needs no new storage**: `prev_global_transform` /
`prev_valid` already exist for motion vectors (`scene.h:51-57`).

Also relevant and already known: `render_shadow_depth_pass` (`engine.c:2607`) runs **before**
`apply_transform_to_nodes` (`forest.c:2434`), so shadows read last frame's transforms and LOD is
selected from stale positions. That is phase 5's item, but it bounds what a cache may assume here.

## Plan

In this order, so the two that cannot move a pixel land and are verified first.

1. **Guard the redundant `model` upload** (`shadow.c:703`), mirroring `render.c:899`. Provably 0 px:
   an instanced draw already reads its transform from the block.
2. **Compact-then-group submission for the shadow pass.** Gather visible casters into a scratch index
   array, group by `(mesh, lod)`, form runs over that. A depth-only map is order-independent, so
   there is no ordering constraint to protect — which is not true of the camera lane, and is why this
   starts here. `--no-lod` bounds the win: 7,630 → 1,621 draws, 33.1 → 11.9 ms CPU.
3. **A shadow distance separate from the camera far clip**, and `lambda` as a field rather than a
   literal. **Moves pixels** — the splits move, so the cascade a fragment samples changes.
4. **Per-cascade caster rejection by shadow-map footprint** — reject a caster whose projected extent
   in that cascade's texels is below a conservative threshold. Does not coarsen a drawn silhouette,
   so it does not violate 11.28's rule. **Moves pixels.**
5. **Cache the outermost cascade**, keyed on light direction, a per-caster moved bit off
   `prev_global_transform`, and the `wind_max_offset` envelope. **Moves pixels** if anything is
   wrong, and 0 px if nothing is — which is the arm.

## As built, steps 1 and 2

| | draws | CPU | GPU |
|---|---|---|---|
| baseline (11.89) | 7,630 | 32.9 ms | 33.1 ms |
| step 1 — the `model` guard | 7,630 | 31.1 ms | 32.0 ms |
| step 2 — reordered submission | **1,293** | **7.8 ms** | 28.9 ms |

Triangles, meshes seen and meshes culled are all unchanged: the same work, submitted six times less
often. Below what `--no-lod` reached (1,621) with LOD still on.

**The win splits 94/6 between the two halves, and the intuition is backwards.** With LOD off the
regroup is a no-op, which isolates compaction at 1,621 → 1,226 = 395 draws, against 6,337 total. The
reason is that forest's scatter is Morton-ordered, so culled items arrive in long contiguous blocks
and cost few splits — where LOD rings cut ACROSS that curve and cost thousands. A compaction-only
change would have been a tenth of the work for a sixteenth of the win.

**Three corrections from review, all in step 2.**

The stable partition first shipped as a rotate, which is not linear: its move count is exactly the
INVERSION COUNT of the level sequence, so a span of m costs up to 3m²/8 and clustering the input
lowers only the constant. It survived because forest parents instances under global per-prototype
groups, giving twenty spans of ~435 — merging those into one prototype would have cost **20x for
identical content**, a perverse price on the thing you do to batch better. Replaced by a counting
pass into the upper half of the same allocation: linear, one buffer, and a byte-identical
permutation, so it moved no golden.

`_ordered_caster_run` spelled the run key out, making a fifth hand-written copy of a comparison
`draw_list.h:143-151` records having already drifted four times. Split out as `draw_run_key_equal`
and shared with `draw_run_can_join`.

**And "a depth-only map is order-independent" does not cover all three callers.** The TSM absorbance
walk runs with the depth test off and additive blending into fp32, so what holds there is
commutativity, not exact reassociation — reordering moves the last bits of a sum in any texel more
than one translucent caster reaches. Accepted, and now stated, because the sentence as written would
license the next reordering on a premise that covers two callers of three.

**What the grouping does NOT do**, since the comment first claimed the general fix: it only reorders
within spans the scene graph already made adjacent. A scene interleaving two prototypes has spans of
length one and gets nothing. Grouping the whole list by `(mesh id, level)` once at build time would
remove that precondition and the per-layer repetition with it — and moves **zero draws** on the one
app that satisfies the precondition, so it is booked rather than built.

**For the phases after this one, measured after step 2 and before step 3**: the terrain quadtree was
**735 of the 1,293 draws then standing**. `terrain_quadtree.c:152` creates a `Mesh` per patch, so all
385 patches are distinct `Mesh*` carrying one instance each — runs of length one by construction,
under any ordering, which is why no amount of reordering reaches them. Netting them out, props
carried ~36-56 instances per draw against a ceiling of 64, so prop batching in this pass is at its
optimum.

Step 3 then took the total to 730, which is *below* that 735 — the tightened slices cull terrain
patches too, so the split has to be re-measured before it is quoted again. Per-draw CPU at the end
of step 2 was 7.8 ms / 1,293 = **6.0 µs**, already well above 11.89's 3.53 µs marginal because the
cheap draws are the ones that went; what remains is dominated by the 12,288-byte `InstanceChunk`
orphan-and-refill that phase 2 exists to delete. *(An earlier draft said 10.4 µs, which divided step
2's CPU by step 3's draw count.)*

## As built, step 3 — and the default did NOT change

| | draws | tris | CPU | GPU | frame |
|---|---|---|---|---|---|
| after step 2 | 1,293 | 163.6M | 7.8 ms | 28.9 ms | 118.3 ms |
| after step 3 | **730** | **82.9M** | **5.5 ms** | **17.1 ms** | **102.0 ms** |

`shadow_distance` and `cascade_lambda` are fields now, which is the fix — a hardcoded λ and no shadow
distance at all is the defect. **But the plan said this step would change the default and rebake, and
it does not, because a gate falsified the derived default.**

Deriving `shadow_distance` from `ortho_size` gives forest exactly what this spec wanted — cascade 1
drops from a 967.8-unit box to 255.9 against the outermost's 1000 — and regresses `pillar-msm` from
**0.0000 to 0.1757**: light leaking into a thin caster's shadow band under moment shadows.

**The cause is not the slicing, and it is worth writing down because it bounds every later
tightening.** `compute_cascade_light_space_matrix` spends `[0.1, 2·radius + scene_pad]` of depth on
a box `2·radius` wide, and `scene_pad` is `far_plane * 0.5` — fixed. So the quantity that matters is
the RATIO, `1 + scene_pad / (2·radius)`, and it grows without bound as the slice tightens. On
`dir_shadow` (`far_plane = 8·scene_radius = 68.96`, so `scene_pad = 34.48`) it goes from **1.96 to
12.7**, and four moments cannot absorb the second.

*An earlier draft of this paragraph said the depth range "does not shrink with the slice". That is
false against the code — `ortho_far = 2·radius + scene_pad`, so it shrinks by exactly `2·radius`;
only the pad is invariant. The conclusion was right and the sentence was not, and its four quoted
numbers could not be reconciled with any single configuration.*

PCF holds throughout (`pillar-pcf` stays 0.0000); only the moment reconstruction breaks.

So the default stays at the camera far clip, all 29 goldens stay 0 px, and forest sets
`shadow_distance` against its own content. **Sizing `scene_pad` to what can actually cast into a
slice is the prerequisite for any tightening default**, and it is booked rather than built here — it
is a change to the fit itself, which wants its own before/after and its own arm.

**What is NOT verified: forest's shadows visually.** Two attempts at a fixed-camera A/B were defeated
by the app's own non-determinism (`docs/verification.md` records 35k px run-to-run, and the camera
does not settle identically from `--cam-eye` across two builds). The change is carried by the full
gate suite and a 0 px corpus; it is not carried by anyone having looked at forest, which has no
golden and cannot have one. What would close the gap is in the Verification section below, and it is
not the arm this spec originally promised.

## Steps 4 and 5 — both closed with a measurement, neither shipped

**Step 4, small-caster rejection: built, measured, reverted.** Rejecting a caster whose extent is
below two of the layer's own texels culls **exactly nothing** on forest — 16,205 culled and 730 draws
with it and without it, to the integer. The implementation is not at fault: raised to 60 texels the
same code culls 20,892 and drops to 638 draws, so the mechanism works and the content simply has no
sub-texel casters. Even the whole-scene cascade's texel is 0.488 world units at 2048, and forest's
smallest prop is an order of magnitude larger; the threshold that would bite is one that starts
deleting trees people can see.

So it was reverted rather than kept as a no-op. The precedent is this document's own treatment of E7:
*"booked so the gap is visible, not because a measurement demands it"* — and E7 is not built either.
It would matter on content this engine does not have yet (grass, debris, crowds), and the four lines
are recoverable from this spec's history when something wants them.

**Step 5, caching the outermost cascade: refused on the content, not attempted.** The cascade is the
right target — with the slices at 27 and 74 units across a 1000-unit island, the whole-scene fit
carries almost all 10,951 caster instances — and its matrix depends on nothing that changes in
forest. But `g_mat_bark` and `g_mat_leaf` carry `wind_response` 0.45 and 0.7, so **every tree in that
cascade displaces every frame**. A cached map would freeze a swaying canopy against its own moving
geometry, which is a worse artefact than the cost it removes, and `wind_max_offset` does not rescue
it — that bound says how far a caster can move, and these casters really do move.

The version that could work is a different design: a static caster map and a dynamic one per cascade,
min-combined at lookup, so the static half is cached and the swaying half is not. That is two maps per
cascade and a composite, it changes what `begin_shadow_pass` means, and it wants its own spec and its
own arm. Booked, not smuggled in at the end of this one.

## Verification

- **Noise floor first**, per `docs/verification.md`: render one configuration twice and diff those
  before quoting any number. 11.89 established ~0.3% on the frame total and ~3.5% on the opaque row.
- `scripts/gates.py --only` scoped to the blast radius per step — `dir-shadow`, `submission`,
  `forest`, `overdraw`, `catcher`, `penumbra`, `grazing` — and the whole suite once at the end.
- `scripts/goldens.py`. Steps 1 and 2 must be **0 px**; any movement there is a bug, not a rebake.
  Steps 3, 4 and 5 are expected to move, and each names its fixtures and its reason **before**
  rebaking. A fixture that moves unexpectedly is investigated rather than accepted.
### As built — what shipped, and what is still owed

**`shadow-batch`** (submission group) is the only arm that can see the COMPACTION half: a culled item
no longer ending a run. Its bound is derived the way `inst-count` derives its own —
`ceil(instances / UBO_INSTANCE_MAX) + groups − 1`, exact at full visibility — rather than compared
against the opaque pass, which was the first form and was wrong twice: the "handicap" it claimed
cancels in a ratio, and it tied a shadow assertion to a lane whose fragmentation is a tuning knob.

**`forest-shadow-lod`** (forest group) is the only arm that can see the LEVEL half, which is 94% of
the win. It rides `forest-lod`'s existing pair at no extra render. `shadow-batch` is blind to it —
`instancing_fixture`'s meshes are under `LOD_MIN_TRIANGLES`, so every item there is level 0 and the
regroup is an identity permutation.

**Owed, and it is not the arm this spec first promised.** A cascade-separation arm asserting the
fitted box widths are distinct would measure the INPUT, not the frame — trivially satisfied the
moment `shadow_distance` is set, and blind to a seam, a shadow ending where a map runs out, or a
density discontinuity. The arm actually wanted follows from `calculateShadow` taking
`min(...)` across the fragment's cascade **and every wider one** (`pbr_frag.glsl:822-844`): with
forest's boxes now ≈61 / 167 / 1000, cascade 0 is 16x finer than the map it is min'd against, so it
is an open question whether step 3 bought a picture or only a draw count. The test is to set a tight
`shadow_distance` on `dir_shadow_fixture` and assert the measured penumbra NARROWS — which the
`edge` arms in the dir-shadow group already know how to measure. **That question is unanswered and
this spec should not be read as having answered it.**
