# Spec 11.105 — An app outside the tree: cetra as a submodule

## Context

Every app that uses the engine lives inside its repository, and the one that does not
(`apps/pcb`) is smuggled in through `apps/.gitignore` and a manifest glob. Nothing documents how
a project of its own consumes the engine, and the three ways a reader might guess are in three
states: `add_subdirectory` works but nobody has said so; `install()` exists in
`cetra/CMakeLists.txt:131-141` but has no export set, installs none of the seven dependencies
the static library links, and does not install the generated shader header, so an installed tree
cannot even compile against; `find_package` does not exist. Three pre-existing sketches in
`../apps` (pcb, globe, network — 2023-2024, one file each, every CMakeLists fetching GLFW by hand)
are the first real consumers and will each become their own repository with cetra at
`extern/cetra`.

Exploration found three engine-side defects a consumer meets before writing a line:

1. **`cetra/src/shader.h:6` includes the generated `shader_strings.h`**, and `shader.h` is
   reached from `engine.h`, `scene.h`, `render.h` and `program.h`. Every TU that includes
   `cetra/engine.h` therefore compiles 2.1 MB of `static const char*` literals, a `.glsl` edit
   recompiles every such TU, and a consumer's object depends on a file nothing orders before it
   (in-tree, `apps/CMakeLists.txt:13`'s `add_dependencies(... cetra_shaders)` papers over exactly
   this). The only reader of those symbols is `cetra/src/program.c`.
2. **Output directories are written to `CMAKE_BINARY_DIR`** (`CMakeLists.txt:97-99`,
   `cetra/CMakeLists.txt:17`), which under a parent project is the CONSUMER's build root: the
   engine's `libcetra.a`, every vendored `.a`, the forwarding-header tree and the generated
   header all land in the consumer's `build/lib`, `build/bin`, `build/include`.
3. **`CETRA_BUILD_APPS` defaults ON** (`CMakeLists.txt:93`), so a consumer that forgets it builds
   all seven example apps into its own tree.

The user decided: **submodule / FetchContent only** (no install, no `find_package`; the half-built
install rule is deleted with the reason in the file), and **port all three `../apps`** onto the
new path as the proof, after the engine change lands.

## The design

**Consumer contract, eight lines**, and it is the whole README section:

```cmake
cmake_minimum_required(VERSION 3.25)
project(myapp LANGUAGES C CXX)     # CXX too: Jolt, ImGui and draco are C++, and so is the link
set(CMAKE_C_STANDARD 11)
add_subdirectory(extern/cetra)
add_executable(myapp src/main.c)
target_link_libraries(myapp PRIVATE cetra)
```

`LANGUAGES C` alone fails at LINK, not configure: CMake picks the link driver among the languages
enabled in the consumer's directory, so a C-only project links Jolt/cimgui/draco objects with the
C driver and the C++ runtime is undefined. Say so in the template and the README.

**What NOT to fix, recorded rather than churned**: `BUILD_SHARED_LIBS` forced OFF in the cache
(`CMakeLists.txt:150`) and cglm building a shared library nobody links — seven vendored builds on
three platforms are not worth touching for a consumer who can write `SHARED`. Two consumers in one
superproject collide on target names (`if(NOT TARGET cetra)` is their guard). **`CETRA_BUILD_JOLTC=OFF`
is not a working configuration today** — `cetra/src/game/physics.c:3` includes `JoltC/JoltC.h`
unconditionally and the include path is only added inside the `if` — so the template leaves it ON
and the README does not advertise it; recorded as a finding, out of scope.

### Engine changes (four files)

- `cetra/src/shader.h`: delete line 6. `cetra/src/program.c`: `#include "shader_strings.h"` after
  `program.h` with a two-line comment (the one TU that reads the generated strings; a public
  header that included it put 2 MB of literals into every consumer TU and rebuilt the world on a
  `.glsl` edit). `apps/render/src/render.c:44`: delete (vestigial, uses no symbol).
  `apps/CMakeLists.txt:10-13`: delete the `add_dependencies` and its comment — `add_dependencies(cetra
  cetra_shaders)` at `cetra/CMakeLists.txt:78` orders generation before `program.c`, and an app now
  reaches the header only through `libcetra`. `cetra/CMakeLists.txt:87-89`: the
  `${CETRA_PUBLIC_INCLUDE_DIR}/cetra` entry moves to `target_include_directories(cetra PRIVATE ...)`.
- `CMakeLists.txt:93`: `option(CETRA_BUILD_APPS "Build example applications (default: only when cetra
  is the top-level project)" ${PROJECT_IS_TOP_LEVEL})`. In-tree unchanged (TRUE); under a parent OFF.
- `CMakeLists.txt:97-99` and `cetra/CMakeLists.txt:17`: `${PROJECT_BINARY_DIR}`. In-tree
  `PROJECT_BINARY_DIR == CMAKE_BINARY_DIR == out` at the root and in `cetra/` (no `project()` there),
  so `out/bin`, `out/lib`, `out/include` are byte-identical; under a parent they become
  `build/cetra/{bin,lib,include}`. **Line 212 `include_directories(${CMAKE_BINARY_DIR})` stays** —
  draco writes `draco_features.h` to `CMAKE_BINARY_DIR` (`contrib/draco/CMakeLists.txt:27`) and the
  two must agree; add the sentence. Nothing else references `out/lib` or `out/include`
  (`.clangd`, `gates.py:61-72`, `goldens.py:60` use `out` / `out/bin`; grep-verified).
- `cetra/CMakeLists.txt:90` (`$<INSTALL_INTERFACE>`) and `131-141` (both `install()` calls): deleted,
  replaced by a comment: no export set so nothing could `find_package` it; none of the seven
  dependencies installed while five of their own install rules (glfw, glew, cglm, cimgui, JoltC)
  were still live and would fire under a consumer's `cmake --install`; the generated header not
  installed. The supported path is `add_subdirectory`; a real install is its own spec.

### `template/` — the reference consumer (root of the repo, NOT under `apps/`, whose manifest
glob would add it in-tree and recurse)

`template/CMakeLists.txt` — the eight lines above plus: `CETRA_DIR` as a `CACHE PATH` defaulting to
`${CMAKE_CURRENT_SOURCE_DIR}/extern/cetra` with a `FATAL_ERROR` naming `git submodule update --init
--recursive` when `${CETRA_DIR}/CMakeLists.txt` is absent; `add_subdirectory("${CETRA_DIR}" cetra)`
(the second argument is required when the source is outside the tree, and names the engine's build
dir `build/cetra`); `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)`; `target_link_libraries(myapp PRIVATE

optional. A header comment says what the directory is (copy it to start your own; put cetra at
`extern/cetra` as a submodule; `scripts/consumer.py` builds this same directory against a checkout
with `-DCETRA_DIR`).

`template/src/main.c` (~70 lines) mirrors `apps/shapes/src/shapes.c:163-486` minus everything
optional, with the render app's three capture flags parsed by hand (`-x`, `-f N`, `-S path`), all
applied BEFORE `init_engine` as `render.c:2760-2809` does:

```
create_engine("myapp", 320, 240) -> set_engine_headless -> set_engine_exit_after_frames ->
set_engine_screenshot_path -> init_engine -> camera at (0,0,300) looking at origin, up +Y,

                                                // update_engine_camera_perspective; render: render_current_scene
```

The rectangle spans 40% of the frame height around the centre; `(w/8, h/8)` is background.
`template/.gitignore`: `build/`, `cooked/`, `*.ppm`, `imgui.ini`, `cetra_config.json`, `.DS_Store`.
No README in the directory; the CMakeLists carries the explanation and `README.md` points at it.

### `scripts/consumer.py` — the instrument (standalone, not a gates group)

Standalone because `gates.py` hard-requires `out/bin/render` (`:21683`) and probes the framebuffer
scale before any group, neither of which a check that builds its own binary wants; because gates
`rmtree`s its workdir and this check must LEAVE its scratch dir (a failed 40 s build is what you
inspect and rebuild incrementally); and because ~45 s cold on a suite 11.65 fought to make
affordable is wrong for a check that matters only when CMake files change. Recorded in the spec:
a thin `consumer` gates group that shells out to it is one function if anyone wants `--only consumer`.

CLI: `python3 scripts/consumer.py [--cetra-dir DIR] [--dir DIR] [--config Debug|Release]`. Default
scratch is `tempfile.mkdtemp(prefix="cetra_consumer_")`, printed first and **never removed**
(`--dir` reuses one for an incremental re-run). Module docstring in the gates style: what it proves,
what it cannot see (anything past frame 2; the engine's behaviour, which gates/goldens own), when to
run it (any change to a `CMakeLists.txt`, `template/`, `gen_shader_header.py`, or a public header's
include graph; before tagging), the measured cost, and that it needs a display like every headless
run. Arms, in run order, each printing `  name PASS|FAIL detail`:

| arm | what | how |
|---|---|---|
| `consumer-configure` | a consumer's configure succeeds and derives the version | `cmake -S <copy of template> -B build -G Ninja -DCETRA_DIR=<abs> -DCMAKE_BUILD_TYPE=<config>` (+ clang on Linux, clang-cl on Windows, as the presets pin); detail = the `Cetra version ...` line from `configure.log` |
| `consumer-build` | it builds | `cmake --build build`, `build.log`, detail = last `[N/M]` + seconds |
| `consumer-header` | no consumer TU depends on the generated header | `ninja -C build -t deps`; the block whose output contains `myapp.dir` must list no path ending `shader_strings.h` |
| `consumer-scoped` | cetra keeps its outputs out of the consumer's tree | `build/bin` and `build/lib` absent; `build/cetra/lib/*cetra.*` present |
| `consumer-no-apps` | the example apps stay off under a parent | `build/cetra/bin/render[.exe]` absent |
| `consumer-run` | the binary runs headless and writes a frame | `myapp -x -f 2 -S frame.ppm`, timeout 120 s, exit 0, file non-empty; on failure the last three stderr lines |
| `consumer-pixels` | the frame is right | P6 reader (the 17 lines of `gates.py:451-467`, copied rather than importing 21k lines); centre `(w//2, h//2)` == `(255,0,0)` exactly; `(w//8, h//8)` neutral (`max-min <= 1`) and `< 128` |

Pixel bars derived, not guessed: attachment 0 clears to 0.1 grey (`engine.c:98-100, 2741`), the 2D
preset's linear curve display-encodes it to ~89.5, so "neutral and dark" not an exact value; the
rectangle's shading under the preset is `ambientRadiance * albedo * ao` exactly (`pbr_frag.glsl:2458`),
no sky without an IBL (`render.c:1610`), overlays off, so pure red. The PPM is `fb_width x fb_height`
(2x on this Mac): read `w,h` from the header, sample by fraction. Missing `cmake`/`ninja` is
`sys.exit(2)` with the tool named — the prerequisite is the thing under test. `Failed to create GLFW
window` stays a FAIL (the script cannot tell no-display from a break); the docstring says so.

## After the merge: the three ports (each its own repository, outside this repo's commits)

**Repository setup, per app**, in `../apps/<name>` (none is a git repo today; `../apps` is not either):

```
git init -b master
git -c protocol.file.allow=always submodule add <abs path of this checkout> extern/cetra
# edit .gitmodules -> url = https://github.com/monological/cetra   (the portable URL)
# .git/config keeps the local path: that is the override, so unpushed engine commits are
# reachable; never `git submodule sync` (it copies .gitmodules back over it); re-apply with
# git config submodule.extern/cetra.url <abs path>
git -c protocol.file.allow=always submodule update --init --recursive   # nested deps from GitHub, ~0.5 GB once per app
# CMakeLists.txt = template's with project(<name>); .gitignore = template's; src/main.c
git add .gitmodules extern/cetra CMakeLists.txt .gitignore src ; commit
```

Build: `cmake -S . -B build -G Ninja`, `cmake --build build`, `./build/<name>`. Push cetra's master
before pushing any app repo (the pinned sha must be reachable on GitHub for anyone else). Bumping
the engine: checkout inside `extern/cetra`, `git add extern/cetra`, commit; a new engine commit needs a
manual reconfigure (a submodule's `.git` is a file, so `CMakeLists.txt:68-73`'s `CONFIGURE_DEPENDS`
on `.git/HEAD` is inert there).

## Risks

- **FetchContent with `URL`** fails at the first vendored `add_subdirectory` — no submodules in a
  tarball — before the version check matters. README says `GIT_REPOSITORY`.
- **Cache pollution**: `BUILD_SHARED_LIBS`, `ONLY_LIBS`, `IMGUI_STATIC`, the Jolt `USE_*` ISA switches,
  `DEBUG_RENDERER_IN_DISTRIBUTION`, and on MSVC `CMAKE_MSVC_RUNTIME_LIBRARY` land FORCE'd in the
  consumer's cache. Only the first changes a consumer's own targets; documented.
- **Ninja is what is tested**; Xcode/VS generators are unverified and said so.
- **`build/draco/draco_features.h` and `build/compile_commands.json`** appear in the consumer's build
  root (draco's `CMAKE_BINARY_DIR`; the template turns compile commands on itself). Documented.
- **Linux gcc rejects JoltC**; the script and README pass clang, as the presets do.
- **HiDPI**: sample points are fractions of the header's `w,h`, so 1x and 2x both work.
- **`ninja -t deps` block format** is a tool contract, not an API; if it changes the arm reports
  unverifiable rather than passing.
- **Cold-build cost on the VMs**: the consumer check compiles the whole engine; on the Windows VM
  (software-rendered, slow) run it alone, not with the suites.
