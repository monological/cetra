# Spec 11.109 — Gamepad input

## Context

The rendering roadmap's table is closed and `docs/game-engine-status.md` lists what the engine
lacks as a game platform, smallest first. The first item is gamepad input: the game layer's
input is keyboard and mouse only (`cetra/src/game/input.h`, seventeen functions, no device
concept and no action concept), and nothing outside the vendored code reads a joystick.

The engine already carries everything a controller needs. The vendored GLFW is 3.4, whose
gamepad API maps any known controller onto one Xbox-style layout (fifteen buttons, six axes)
through a bundled copy of the SDL controller database (929 mappings: 395 Linux, 365 Windows,
169 macOS), with evdev on Linux, IOKit on macOS and XInput on Windows, all compiled
unconditionally today, and the database parsed at `glfwInit` by every app already; device
enumeration is lazy, so an app that never asks pays nothing. So a controller costs no new dependency and no build change, and Steam
Deck is a Linux box with a pad the database already knows. Steam itself presents a virtual
Xbox pad to a game that uses GLFW alone, which is how most independent games ship; Steam Input's
own API is a later backend behind the seam this spec draws, when the Steamworks item lands.

Four things found while reading the layer get fixed on the way because they live in the
lines being rewritten: `input_init` installs its own GLFW scroll callback (`input.c:25`),
which overwrites the engine's (`engine.c:857`), so for every game-framework app ImGui gets
no scroll and the app's own scroll hook never fires; `input_reset_scroll` is called by
nothing, so `input_scroll` reports a running total since launch rather than a per-frame
delta; the key array is sized `GLFW_KEY_LAST` and polled below it, so the last key is never
read; and gametest's pause toggle sits in `on_update`, which the fixed-step loop skips while
paused, so once paused it can never be unpaused.

**The constraint that shapes the design: there is no pad on the development machine, only
macOS is available, and macOS has no supported way to fake a pad** (a virtual controller there
needs a DriverKit extension; Linux's uinput would do it, and no Linux box is at hand). So the
layer reads the pad through a seam, everything above the seam is verified headless by a
scripted pad, and the real GLFW device path is stated as unverified in the ledger until a pad
or a Linux machine exists -- with the recipe for each written down, so the check is a minute
when one does.

## Scope

The game layer's input: pad state with edge detection and dead zones; a reader seam with a
scripted reader; an action layer binding named actions to keys, mouse buttons, pad buttons
and axes; hot-plug; an optional controller database file; the scroll fixes; gametest and
forest on actions with pad support; a `gamepad` gate group; docs. **Non-goals:** any
verification of the real device path in this spec (no pad, no Linux; the recipes for both are
written, not run); the engine's own `InputState` (the mouse-drag model the 2D and
viewer apps use, untouched); `apps/tree`'s player, which polls GLFW directly and is not on
the game framework (recorded, not ported); rumble; Steam Input (a second reader behind the
same seam, booked with Steamworks); a remapping UI (the binding table is data, which is what a
UI would edit); glyphs (the pad's name and GUID are exposed for the game UI item to use).

## Design

### 1. Pad state on `GameInputState` (`cetra/src/game/input.h`, `input.c`)

```c
#define GAME_MAX_PADS 4

typedef struct GamePadState {
    bool connected;
    bool buttons[GLFW_GAMEPAD_BUTTON_LAST + 1];
    bool buttons_prev[GLFW_GAMEPAD_BUTTON_LAST + 1];
    float axes[GLFW_GAMEPAD_AXIS_LAST + 1]; // sticks -1..1 after the radial dead zone,
                                            // triggers 0..1 after theirs
} GamePadState;
```

`GameInputState` gains `GamePadState pads[GAME_MAX_PADS]` and is laid out under 11.108's
three banners (it has none today): ENGINE-OWNED for everything the poll writes, BY FUNCTION
for the reader and the binding table, SETTINGS for `float stick_dead_zone` (default 0.2,
radial per stick, RESCALED so the edge of the zone reads 0 and full deflection 1) and
`float trigger_dead_zone` (default 0.1, per axis, after GLFW's -1..1 trigger is remapped to
0..1; GLFW's trigger RESTS at -1, which is the one thing a reader filling the struct by hand
gets wrong). `input_update` polls the pads after the keys, through the reader (§2):
`buttons_prev` copied, then each slot read. A slot whose read fails is disconnected with
everything zero, so a pad pulled mid-game releases every button it held (one edge, as a real
release would); a slot that CONNECTS copies its buttons into `buttons_prev` on that frame,
so a button already held when a pad appears is not a press. The key arrays grow to
`GLFW_KEY_LAST + 1` with the loop bound to match.

Queries mirror the keyboard's: `input_pad_down/pressed/released(input, pad, button)`,
`input_pad_axis(input, pad, axis)`, `input_pad_connected(input, pad)`, and
`input_pad_name(input, pad)`, which asks GLFW each call rather than caching a pointer the
mapping table can reallocate under it. `pad` is a slot 0..3; slot 0 is GLFW's joystick 1.
The action layer (§3) is what a game reads; these are for a game that wants a specific pad.

**Hot-plug.** `input_init` installs `glfwSetJoystickCallback` (global to GLFW; the game layer
is its only installer and the header says so; fired from the engine's `glfwPollEvents`,
which headless runs still call), logging `gamepad <slot> connected: <joystick name>` with
`(no mapping)` appended when GLFW has none for it, and `disconnected`. The joystick name,
not the gamepad name: the latter is NULL for an unmapped pad, which is exactly the pad a
player needs to see named. The per-frame poll is what tracks presence; the callback is the
log and nothing else, so a pad present before the callback existed (GLFW does not fire it
for those) is still found.

**The controller database.** `game_load_gamepad_mappings(game, path)` reads a file and hands
it to `glfwUpdateGamepadMappings`, which re-resolves every connected pad, logging the outcome
by name; callable any time after the game exists, so it is a call and not a config field
(the config's own test, "must precede `on_init`", does not hold for it). A file beside the
executable is how a shipped game picks up controllers released after it was built. gametest
takes `--gamepad-db <file>`.

### 2. The reader seam, and the scripted reader

```c
// Fills `out` for slot `pad` and returns whether a pad is there. The default reads GLFW.
typedef bool (*GamepadReadFn)(void* ctx, int pad, GLFWgamepadstate* out);
void input_set_pad_reader(GameInputState* input, GamepadReadFn read, void* ctx);
```

The default is a static that maps slot to `GLFW_JOYSTICK_1 + pad` and calls
`glfwGetGamepadState`, which polls the device itself and returns false for an absent or
unmapped one. The seam is the particle sim backend's shape (`particle_sim.h:65-81`): one
output struct both readers fill, the consumer byte-identical. It exists so that everything
above it can be verified with no hardware.

**The scripted reader** (`bool input_set_pad_script(input, path)`, in `input.c`; the parse
is ~80 lines): a text file, one line per frame range, applied to slot 0:

```
# frame ranges are inclusive; a frame no line covers is connected and idle
0-59    idle
60-149  a
150-209 lx=-1.0
210-269 lx=0.1
270-329 lx=0.6 dleft
330-359 off
```

Tokens are the fifteen button names (`a b x y lb rb back start guide lstick rstick dup dright
ddown dleft`) and the six axes as `lx= ly= rx= ry=` in -1..1 and `lt= rt=` in 0..1, which
the reader converts to GLFW's -1..1 rest-at-minus-one form; `off` is a disconnected frame.
The reader counts frames itself, one per `input_update`. It returns false, with the reason
logged, for a file that is missing or will not parse: a refusal the caller can act on, and
gametest exits non-zero on it, so a gate never mistakes an idle pad for a passing layer. Its
ctx is freed when the input is (`input_free`, new, called from `free_game`; the pairing
`lut_free` and `cscene_free` use for owned contents).

### 3. The action layer

Every action is ONE float in -1..1, from whichever of its sources is largest in magnitude: a
key or button contributes its `scale` (±1), an axis its value times its `scale` (which is
how the left stick's Y, down-positive in GLFW, becomes up-positive). Digital and analog are
then one thing, and a 2D move is two actions read together. This is the shape Unity's classic input
manager and every gamepad-first engine converge on, and it makes a stick and a key pair the
same action rather than two code paths.

```c
typedef enum { INPUT_SRC_KEY, INPUT_SRC_MOUSE_BUTTON, INPUT_SRC_PAD_BUTTON, INPUT_SRC_PAD_AXIS }
    InputSourceKind;
typedef struct InputSource { InputSourceKind kind; int code; float scale; } InputSource;
#define INPUT_ACTION_SOURCES 6
typedef struct InputAction {
    const char* name;
    InputSource sources[INPUT_ACTION_SOURCES]; // unused entries zero (kind KEY, code 0)
} InputAction;
#define INPUT_MAX_ACTIONS 32

void input_bind(GameInputState* input, const InputAction* actions, size_t count); // borrowed table
float input_action_value(const GameInputState* input, const char* name);
bool input_action_down(const GameInputState* input, const char* name);     // |value| > 0.5
bool input_action_pressed(const GameInputState* input, const char* name);  // crossed it this frame
bool input_action_released(const GameInputState* input, const char* name);
// Two actions as a move direction on the ground plane, (x, 0, -y), clamped to length 1 so a
// diagonal on keys is not faster than a stick pushed straight; magnitude below 1 is kept.
void input_action_move(const GameInputState* input, const char* x, const char* y, vec3 out);
```

A pad source reads slot 0 today (`pad` in `InputSource` is a later field; a one-player game
has one pad). `input_update` evaluates every bound action after the poll and keeps the
previous frame's values, which is where the edges come from -- so an action's edge is per
FRAME, exactly as a key's is now (a frame with two fixed steps sees one press on both, a
frame with none drops it; the existing behaviour, stated in the header). An unknown name logs
and reads 0: a typo is a dev-time error and the log says so at once.

`input_wasd_direction` and `input_arrow_direction` become two lines over `input_action_move`
and are deleted once gametest and forest are on actions (below); their normalise-to-1
destroyed a stick's magnitude, which is why the move helper clamps instead.

### 4. The scroll fixes

`input_init` takes the `Engine*` rather than the window and registers through
`engine_set_scroll_callback`, so the engine's own callback keeps feeding ImGui and forwards
the app's turn to the input layer (with the engine's one rule, stated in the header: scroll
over a GUI panel reaches ImGui and not the game). The header says the game layer owns that
slot: a game reads scroll through `input_scroll`; no game-framework app installs one today.
The engine's callback carries only the `Engine*`, whose user data becomes the Game in
`game_run`, after `input_init`, so the accumulator stays the file static it is. `input_update`
moves it into `scroll_x/y` and zeroes it, so `input_scroll` is the frame's delta;
`input_reset_scroll` goes. `game.c:31` changes to pass the engine.

gametest's pause moves from `on_update` to `on_pre_render`, which runs every frame whether or
not the sim is paused; the P key and Start then both unpause.

### 5. The apps

**gametest** (`apps/gametest/src/gametest.c`) binds a table and reads it:

| action | keys | pad |
|---|---|---|
| `move_x` | D +1, A -1 | left stick X, dpad right +1 / left -1 |
| `move_y` | W +1, S -1 | left stick Y (negated: up is +1), dpad up / down |
| `jump` | Space | A |
| `spawn` | F | X |
| `pause` | P | Start |
| `raycast` | R | Y |
| `ground` | G | B |

`input_wasd_direction` at `:452` becomes `input_action_move(&game->input, "move_x", "move_y",
dir)`, the four `input_key_pressed` sites become `input_action_pressed`, and the stale
"Space - Push all boxes up" line in the printed controls goes. Four flags: `--pad-script
<file>` installs the scripted reader (exit 1 when refused); `--gamepad-db <file>`;
`--trace-player` prints forest's line (`player t= pos vel grounded`) plus `move x y jump` for
the step, which is what the gate reads; `--trace-every <steps>` (default 30, as forest's) so a
short run has enough samples; `--print-bindings` lists the table and exits. The AGENTS.md
app-table row gets its controls and its headless column corrected (it has taken `-x` since
11.103), and the Headless Mode section names it.

**forest** (`apps/forest/src/forest.c`) binds `move_x`, `move_y`, `jump`, `sprint` (Shift /
left bumper) and `look_x`, `look_y` (right stick), reads the move at `:2711` and the jump at
`:2763` through actions, and in `on_pre_render` beside the mouse look (`:2809-2815`) adds the
stick look at a rate per second scaled by `game->sim_clock.delta` (the deterministic frame
delta; the engine's is wall clock even headless, and `on_pre_render` receives an interpolant,
not a dt). Its `--walk` scripted override (`:2713-2725`) is untouched: it writes the direction
after the read, as before, and every `forest-*` gate arm goes through it.

**tree** is not ported: its player polls GLFW itself outside the game framework
(`apps/tree/src/player.c:30-37`), and the port is a separate small change once the framework
is the target.

#### 5b. forest in first person (a correction, phase 5)

*Added after phase 4. The forest port above kept the app's third-person orbit and its Q and E
turn keys, which had been there since 11.29 (spec 11.109's own ledger records folding them into
`look_x`). Played, that scheme is no game's: Q and E rotate the camera in strategy games, where
the mouse is busy, and nowhere a character walks. The user asked for first-person controls.*

The scheme is the one every first-person game on PC uses, and tree's `--player` mode already
half has: **WASD moves** (A and D strafe, never turn), **the mouse looks** with the cursor
captured so no button is held, **the arrow keys look** as the keyboard-only fallback tree has
(left and right yaw, up and down pitch), **Space jumps, Shift sprints**, and the right stick does
what the mouse does on a pad. Q and E go.

- **The table.** `look_x` is the right stick's X, Left at -1 and Right at +1; `look_y` is the
  right stick's Y at -1 (GLFW reads a stick down-positive and up is a look up), Up at +1 and Down
  at -1. The move, jump and sprint rows are unchanged.
- **Pitch is the look's elevation, positive up**, clamped to 1.4 rad in first person. It was the
  orbit camera's height above the character, which is the opposite sign and a different bound.
- **The eye** is the capsule's origin plus 1.0 (the capsule spans 1.3 either side of its
  origin, so that is a head), looking along the yaw and pitch. The character has no mesh of
  its own to hide.
- **The cursor** is captured (`GLFW_CURSOR_DISABLED`, raw motion where the platform supports
  it) on a left click inside the window while the GUI does not want the pointer, and released
  on Tab -- Escape is the framework's quit. The delta of the capture frame is discarded, since
  the virtual position starts wherever the platform puts it. Mouse look is per pixel, 0.0025
  rad, and never scaled by a frame delta; the stick and the arrows are per second over the sim's
  frame delta as before, 1.8 rad/s yaw and 1.2 rad/s pitch. Nothing captures headless.
- **The orbit survives behind V**, for looking at what the character is doing: the same yaw and
  pitch, the eye `CAM_DISTANCE` behind the head along the look, pitch clamped to the old range
  in the new sign, and the eye kept above the ground as before. First person is the default.
- `--cam-eye` / `--cam-target` and `--walk` are untouched, and every `forest-*` arm still goes
  through them.

### 6. The `gamepad` gate group (`scripts/gates.py`)

Five arms over gametest, each a headless run with a script under `out/gates/` and
`--trace-player`, parsed with a regex of its own in the `forest-rest` shape
(`gates.py:14522-14556`; a `GAMETEST` binary constant beside `FOREST`, and the group
registered in `GATE_GROUPS` with the arm list in its docstring, which `gate-arm-docs` holds it
to). gametest's determinism is measured first (phase 1): headless, the engine hands the game
`ENGINE_FIXED_FRAME_DT` (`engine.c:2506`) and that feeds the accumulator, the wall clock
reaches only the camera, the seed is fixed and Jolt steps a fixed dt, so two runs of one
script should trace identically. `docs/verification.md:195`'s "48 px between two identical
runs" and its wall-clock explanation are NEWER than the fixed step, not older, and cannot be
right for the sim; the likely source is the FPS overlay, which gametest draws headless from
the wall clock. Phase 1 compares traces, and the docs get the measured answer.

The player spawns two units up and takes about fifteen steps to land, and a jump is
`pressed && grounded`, so every script waits for the trace's `grounded 1` before pressing.
Each arm is written so a plausible wrong implementation fails it:

- `pad-edge`: A held frames 60-149 → exactly one `Jump!`. A level-triggered bug prints a
  second at re-landing about a second later; a per-step edge would print none or two.
- `pad-deadzone`: left stick at -0.1 for 60 frames (toward -x, away from the door at +5,
  which the character passes through) → x displacement under 0.05; at -0.6 → displacement
  0.5 ± 0.05 of the -1.0 leg's (the rescaled zone: (0.6 - 0.2) / (1 - 0.2)). A ratio, not
  "less than", so a wrong scaling fails. At 10 m/s the full leg travels 10 m in 60 steps.
- `pad-dpad`: dpad left for 60 frames displaces x within 1% of the stick at -1.0.
- `pad-off`: a stick held, then `off` → the move stops within one step; then a button held
  through the `off` and still down on reconnect → no press edge, per §1's connect rule.
- `pad-keys-alias`: `--print-bindings` lists every action with a key AND a pad source, so a
  binding that lost one half is caught at the table, since keys cannot be scripted headless.

The keyboard path is the same evaluation with a different source and is checked by hand.

### 7. The device path, unverified, and the two recipes for later

Nothing in this spec exercises GLFW's real joystick backends. What it rests on: the seam
above them is verified end to end, and `glfwGetGamepadState` is the code every GLFW game
ships. The ledger states the gap plainly, and `docs/verification.md`'s gametest row carries
the two ways to close it:

- **A pad on this Mac.** Any Xbox, PlayStation or Switch controller pairs over Bluetooth;
  `gametest --trace-player` windowed, move the stick, read the trace. One minute.
- **A Linux machine with no pad.** The kernel's `uinput` lets a process create an input
  device it serves like any other, and GLFW's Linux backend reads `/dev/input/event*` with an
  inotify hot-plug watch, so a virtual pad is indistinguishable from a real one -- provided it
  matches a database entry, which GLFW does by the full GUID: bus 0x03, vendor 0x045e,
  product 0x028e AND version 0x0104 (a zero version falls back to a name-keyed GUID that
  matches nothing), i.e. the "Microsoft X-Box 360 pad" row; exactly eleven key bits in
  ascending code (A, B, X, Y, TL, TR, SELECT, START, MODE, THUMBL, THUMBR, since an extra bit
  shifts every button index), six absolute axes X, Y, Z, RX, RY, RZ each with range info, the
  two hat axes, and a SYN_REPORT per frame. Two permission grants, not one: writing
  `/dev/uinput` and reading `/dev/input/event*`. The recipe is `python3-evdev` (an Ubuntu
  universe package), `modprobe uinput`, a script that creates that device and replays the
  same text format at a wall-clock frame rate, and gametest headless with `--trace-player`.
  Written down as a recipe, not built: a tool that cannot be run here is the kind of code
  this repo does not commit.

## Verification, and what you can check on this Mac with no pad

- **The gate group** is the proof for everything above the seam: edges, dead zones, the
  magnitude path, dpad, disconnect, the binding table. It runs on every suite run, here.
- **Keyboard by hand**: gametest and forest play exactly as before through the action layer
  (WASD, jump, F, P, R, G in gametest; WASD, Shift, Space and mouse look in forest). This is
  the check that the port lost nothing, and the one that needs your hand.
- **The scroll fix by hand**: the GUI panel in gametest scrolls, where before this spec it
  did not.
- **Goldens and captures** are unaffected by design; they run to prove it.
- **Not verifiable here**: GLFW's real device path. The two recipes in §7 close it later,
  and the ledger says which was run (neither, at the time of writing).

## Risks

- **gametest's determinism.** The reading of the code says two headless runs trace
  identically, with Jolt's thread pool the one residual (documented thread-count-independent
  on one build). If phase 1 finds otherwise, the arms assert with tolerances on displacement
  rather than equality, and the docs say why.
- **GLFW's joystick init on macOS** enumerates IOKit devices on first touch; a machine with no
  HID game devices returns false for every slot and that is the whole cost.
- **The device path ships unverified.** The scripted reader proves the layer, not the driver;
  a mapping or hot-plug defect in GLFW's backends would surface only with a pad. The recipes
  are the mitigation, and the ledger says the check is owed.
- **The joystick callback is global** to GLFW; the game layer is the only installer, stated in
  the header.
- **The scroll ownership** changes which callback a game app's scroll reaches: through the
  engine now, with ImGui fed first. No in-tree game app sets a scroll callback of its own.
- **Steam Input** remapping a pad to keyboard presses is a player's choice and reaches the
  key path; nothing here is broken by it.

**Effort:** 2-3 days.

## As built

Four commits on `11.109-gamepad-input`: the spec, the layer (§1, §2, §4, gametest's flags),
the actions with the apps and the gate group (§3, §5, §6), then the docs, this ledger and the
review fixes together. Phase 1's measurement was taken as soon as `--trace-player` existed and
its answer is in the docs; every later phase's gate ran as written.

**What matches the plan.** `GamePadState` and the four slots, the radial and trigger dead zones
rescaled, the disconnect release and the connect rule, the hot-plug log by joystick name with
`(no mapping)`, `game_load_gamepad_mappings`; the reader seam and the scripted reader with the
plan's text format, `input_free` from `free_game`; the action layer with the max-magnitude
rule, `input_bind` and the five queries, `input_action_move` clamped rather than normalised,
the two direction helpers deleted; the scroll fixes (through `engine_set_scroll_callback`, a
per-frame delta, `input_reset_scroll` gone), the key arrays at `LAST + 1`, gametest's pause in
`on_pre_render`; gametest's seven-action table and five flags, forest's six with the stick look
scaled by `game->sim_clock.delta` and `--walk` untouched; tree not ported; the five arms; the
two recipes; the docs.

**What deviated, and why.**

- **An action's previous value is evaluated from the devices' PREVIOUS STATE**, not stored
  from last frame's answer. The plan's stored copy went 0 to 1 on the frame a pad reconnected
  with A already down, so the `pad-off` arm's second half read a press: the pad's connect rule
  was written into the pad's previous buttons and the action layer never looked there.
  Evaluating both values from device state puts the rule in one place. (Its first shape,
  committed in phase 3, was four parallel `_prev` arrays and a `bool prev` threaded through the
  evaluation; the reviews reshaped it into one `InputDevices` struct held twice, below.)
- **The gate arms read the trace's commanded `move`, not the position.** gametest's five boxes
  fall at `rand()` positions, which differ per platform's libc, and the first draft's dpad leg
  walked into one here (4.055 of the stick's 5.000 units). A displacement arm would be green on
  this Mac and red on Linux for a reason that has nothing to do with input. The move column is
  the action value the app commanded from -- the input's product exactly, and the same on every
  platform.
- **The key poll starts at `GLFW_KEY_SPACE`**, not 0: `glfwGetKey` reports every code below it
  as `GLFW_INVALID_ENUM` to the error callback, thirty-two times a frame since the layer was
  written. No game-framework app installs an error callback, which is why it was silent.
- **forest's Q and E are `look_x` sources** at the same rate the stick turns, 1.8 rad/s, which
  is what 0.03 rad a frame was at 60 Hz. Phase 3 had left them as the per-frame turn they were,
  beside the stick's rate-per-second path; the audit called that a half-port, and it was.
- **The forest capture against phase 2 was not taken.** forest's pixel floor is 35k px (the sky)
  and its frame reads no input, so a capture could only say "at floor"; `forest-rest` reads the
  same question with a floor of zero (0.000 units of idle drift through the action layer) and the

**The reviews** (four simplify angles and the thermo-nuclear audit, in background agents, all
finished before a line moved) reshaped the layer more than they trimmed it. Each item is a
departure from the phase-3 code and, where it says so, from the plan's own text:

- **One `InputDevices` struct held twice.** Phase 3 kept `keys_prev`, `mouse_buttons_prev`,
  `buttons_prev` and a new `axes_prev` as four shadows of one idea, three `memcpy`s maintained
  them, and a `bool prev` threaded through the action evaluation chose between them at four
  ternaries. Now `GameInputState` holds `now` and `prev`, `input_update` is `prev = now` then a
  poll into `now`, the connect rule is one struct assignment, and every edge in the file -- a
  key's, a button's, an action's -- is the two compared. `GamePadState` lost its `_prev` halves,
  and `shift_held` / `ctrl_held` / `alt_held`, which nothing read, went with them.
- **Actions are evaluated on read.** The plan's per-frame cache (`action_values[]` and its
  previous, `INPUT_MAX_ACTIONS`, the refusal for a larger table, two memsets, the "after every
  device" ordering in the poll and the header's "bound mid-frame reads on the next") existed for
  a cost a query never had -- the name scan already dominates, and six array reads on top of it
  are nothing.
- **No implicit rules.** `kind KEY with code 0` meant unused and `scale 0` meant +1; both were
  magic, and gametest's table printer had copied both, which was the tell. `INPUT_SRC_NONE = 0`
  makes a zeroed entry say what it is, every source states its scale, and `input_bind` checks
  each code against its kind's range once and refuses the table by action and source rather
  than range-checking on every read.
- **The table vocabulary is the header's**: `INPUT_KEY` / `INPUT_MOUSE` / `INPUT_PAD` /
  `INPUT_AXIS`, which the two apps had each defined and `#undef`'d; and the table printer is the
  layer's `input_print_actions`, so the format the `pad-keys-alias` arm parses is owned where the
  enum is.
- **The wheel is the engine's.** Phase 2 accumulated it in file statics in the game layer
  through the engine's one app scroll slot, and the header had to legislate that the layer was
  the slot's only installer (an app taking it after `create_game` would have read 0 forever).
  The engine's own `InputState` already has the charter "the engine's reading of the pointer,
  written by its GLFW callbacks before the app's are called"; it now carries `scroll_dx/dy`,
  accumulated after the GUI gate and zeroed before each end-of-frame poll, and the game layer
  reads them at its poll. The statics, the callback and the rule are gone, and every app gets a
  per-frame wheel delta.
- `input_set_pad_reader` takes the context's free function as a fourth parameter, so ownership
  is in the signature and `input_free` is the call with NULLs; `input_load_gamepad_mappings`
  (above); `PadScriptRange` embeds a `GLFWgamepadstate` and the reader copies one struct; the
  range list grows through `grow_array`; `_stick` and `_trigger` clamp with `glm_min` and the move
  helper normalises with `glm_vec3_normalize`; a dead `pad_read &&` guard went; the threshold is
  one `_over` helper; the tokeniser's comment says why it exists (`strtok_r` versus `strtok_s`,
  and `lut.c`'s hand lexer as the house pattern) rather than a false premise about `strtok`.
- **An unknown action name logs once**, not every step: the flood buried every other diagnostic
  and the repository's rule since 11.107 is that a refusal says why once.
- **gametest's trace prints its step** and the two action values as they are, so the gate keys
  on the step rather than reconstructing it from a two-decimal time and the fixed timestep, and
  no longer negates a value the app had already negated; the trace regex captures what is read.
- forest's Q and E (above).
