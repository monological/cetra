# Spec 11.77 — retire the bent spec-occ mode

## Context

11.76 replaced the default specular-occlusion term: the reflection lobe is now tested
against the sector bitmask inside the AO sweep, and the Klehm-style cone survives only as
`--spec-occ bent`. The user asked why that mode should survive at all, and the defence did
not hold: the mode misapplies the paper it is named after (Klehm §3.2 explicitly declines
to use cone overlap as a visibility gate — the usage that produces the ring), it still
carries the ring 11.76 removed from the default, and the falsifiability argument for
keeping it was false — the `ao-ring` arm never touches it; the old term was falsified
against the pre-change renderer through git, not through the mode.

The ladder becomes **off / legacy / split**. No saved-session migration: the user said so
explicitly ("I don't care about saved session. remove bent from the code.").

**This partially reverses a recorded decision.** `specs/11.9-review-cleanup.md:10-15` kept
LEGACY and BENT as "the only way to A/B the split composite against what it replaced."
Legacy still serves that purpose for the composite's *placement*; bent no longer serves it
for the *term*, because 11.76's term is not the cone. The spec and commit must say this;
11.9 itself is a closed spec and is not edited.

## Every claim below was verified against the code first-hand this session

The reference sweep was agent-run and then the decisive facts were re-checked directly:

- **`POSTFX_SPEC_OCC_BENT` has exactly 2 uses**: `postfx.h:104` (the enum value) and
  `render.c:796` (the parse). Nothing else names it.
- **`specOcclusionCone` has exactly one call site** — `tonemap_frag.glsl:376`, inside the
  `specOccMode == 2` branch (`:374-381`). `coneOverlap`'s only two calls are inside
  `specOcclusionCone` (`spec_occ.glsl:50, :57`). `VIS_EDGE_SOFTNESS` (`:10`, used `:35`)
  and `TRUST_OPEN` (`:76`, used `:78`) live only in that code. All transitively dead once
  the branch goes.
- **`specOccSplitAt` does not touch any of it** — its body is the zero-normal/catcher
  guard plus `specPair.x / specPair.y`. The split path is structurally unaffected.
- **`spec_lobe.glsl`'s reason for existing was false from birth** (my error in 11.76):
  its header claims the lobe is "measured in two places", but the cone never calls
  `specLobeCos` — `spec_occ.glsl:48` open-codes the identical
  `exp2(-3.321928 * r * r)`. Sole includer is `gtao_frag.glsl:69`, sole call `:232`.
  Fold the function into `gtao_frag.glsl` and delete the file (the build GLOBs shaders;
  no registry to update).
- **Renumbering `SPLIT` 3→2 breaks exactly one line**: `tonemap_frag.glsl:495`'s
  `specOccMode == 3` in debug view 7. The only other literals are `== 0` (`:344`) and the
  `== 2` branch being deleted (`:374`); legacy is the fall-through, no `== 1` exists. The
  C side uploads the enum raw (`postfx.c:3731`) and compares only symbolically
  (`postfx.c:653, :2306, :3210`; `render.c:2526-2527` with the `-1` sentinel intact).
- **`config_snapshot.c` is compile-guarded and string-keyed.** `CFG_SPEC_OCC` (`:173`) is
  indexed by enum value (`_enum_label` / `_enum_value` return the index as the value); the
  `_Static_assert` (`:199-200`) is written against `POSTFX_SPEC_OCC_SPLIT + 1`, so
  removing the label without renumbering the enum fails the build — the safe direction.
  Snapshots store strings, so an old file saying `"bent"` hits the existing
  "not a known value; ignored" warning path. No committed asset carries the key at all
  (verified: no `spec_occlusion` under `assets/`).
- **`gui.c:830-834` has NO static assert** tying `spec_occ_names` to the enum — the combo
  casts its index straight into the enum. Deleting the label without the enum would
  compile clean and mis-select silently. An assert gets added.
- **`CFG_DEBUG_VIEWS`' `"bent"` (`:172`) is debug view 9, the bent NORMAL — different
  thing, one line above `CFG_SPEC_OCC`'s. It stays.** View 9 (`tonemap_frag.glsl:506-514`)
  reads `aoSampleAt().gba` and never mentions `specOccMode`; its C gate is on
  `ssao_enabled` (`postfx.c:3753`). `--bent-debug` stays with it.
- **The legacy fallback stays as-is** (`postfx.c:3203-3211`). Verified reachable only via
  hard failures that already `log_error` (target allocation failed / composite program
  NULL); passthrough tonemap is CLI-unreachable by design and debug render modes skip the
  chain. Repointing it at the bitmask term was considered and dropped: it would be an
  untestable change to an error path — there is no way to exercise it.
- **`scripts/` reference the mode nowhere.** `gates.py:2444` uses `--spec-occ-debug` (the
  debug view, at the default mode) and `gates.py:11220` maps the GUI local `so` to the
  surviving field name. `goldens.py` has zero hits; no recipe passes `--spec-occ`.
- **One dangling comment**: `gtao_frag.glsl:125-131` justifies the sector clamp by
  contrast with `TRUST_OPEN`, which will no longer exist; reword to describe the cone
  form's second overlap without naming the deleted constant.

## The bent NORMAL stays — explicitly out of scope

After this change its only shader consumer is debug view 9, and its production costs a
real 64-iteration loop per pixel plus 3 of 4 channels through the blur, accumulation and
upsample. Whether to delete it is a separate question to be answered with a measurement,
not bundled here: this diff's strongest property is that goldens should not move, and
touching the AO write path would destroy that attribution. Also to check first before any
future removal: 11.75's RGBA8→16F move stands on a second recorded reason in `postfx.c`,
not only on bent-normal precision.
