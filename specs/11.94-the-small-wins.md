# 11.94 — The small wins, and the three different things they turn out to be

Phase 5, the last of the Tier 5 performance programme (11.89 carries the shared evidence base).

## Every claim in the roadmap row is TRUE, which is new

The four phases before this each opened by finding their booked premise stale or wrong: 11.91's
105 MB/frame had already been deleted by 11.90, its arena had an upper bound of zero, and 11.92's
prescribed fix would have silently moved every canopy onto a different mesh builder. So the first
thing this spec did was check row 60 against the tree rather than trust it.

| claim | verified |
|---|---|
| `glGetError` 23x/frame, unconditional in release | **23** `check_gl_error` calls in `postfx.c`, and `check_gl_error` (`util.c`) has no build guard at all |
| No zero-light early-out in the cluster build | no early return anywhere in `light_cluster.c` |
| `_item_bounds` recomputed ~7x per item per frame | one call site, inside `draw_item_visible`, which has **7** call sites outside `draw_list.c` |
| ~100 MB of dead shadow VRAM | `layers = MAX_SHADOW_LIGHTS * cascade_count` = 3x3 = **9 layers at 2048² DEPTH24 = 150 MB**; forest uses 3 |
| Shadows read last frame's transforms | the depth pass runs at `engine.c:2625`, before the app's render callback |

All five hold. That is worth stating because it is the first time in this programme.

## But they are not one kind of thing, and the row treats them as one

Grouping them as "small independent wins" is what makes this phase easy to get wrong. They are
four different categories, and only one of them is plausibly a frame-time win:

**A STALL.** `glGetError` is a synchronous round trip to the driver — it must flush pending
commands to answer. 23 of them per frame in the post chain alone is not bookkeeping. This is the
only item here that could move the clock, and the only one with a mechanism for doing so.

**WASTE THAT IS PROBABLY INVISIBLE.** The cluster build's missing early-out (~25 KB memset, 6,144
iterations, a 12 KB all-zero upload) and `_item_bounds`'s recomputation are real work that does
nothing. But this programme has now measured **three times** — 11.90, 11.91, 11.92 — that removing
CPU-side work does not move a frame whose opaque pass is 74% of it. Expect zero, and say so.

**A CORRECTNESS BUG.** The shadow pass runs before the app's transforms are applied, so shadows lag
the geometry by a frame *and* LOD is selected from stale positions. That is worth fixing whatever
it costs, and it is misfiled under a performance row. It is also the item most likely to move
pixels, so it is the one with a goldens obligation.

**MEMORY, NOT TIME.** 100 MB of shadow VRAM is 100 MB. It will not show up on any clock in this
suite, and an arm asserting a frame-time change for it would be measuring the wrong axis.

**The deliverable this spec expects** is therefore: one possible speedup, two hygiene fixes that
measure zero, one bug fix, and one allocation change. Written down now so the closing measurement
is read against it rather than against hope.

## Steps

1. **Measure the baseline**, two runs, floor first. Post-11.93 forest sits at ~123.5 ms opaque and
   ~177 ms frame.
2. **`glGetError` behind a build guard**, and measure it ALONE — it is the only candidate, so
   folding it in with the others would make its contribution unreadable. Keep it in debug: it is
   how GL errors are found at all, and `check_gl_error` is called from ~40 files.
3. **The cluster zero-light early-out.** Measure; expect nothing.
4. **`_item_bounds` caching.** Measure; expect nothing. Note the bound is a pure function of
   (mesh, node transform, wind, pose), so the cache key is the draw list's own stamp.
5. **The transform ordering.** Establish first whether the shadow pass can move after the app's
   callback at all, or whether the callback is where the app expects to draw. This is a frame-loop
   change, not a one-liner, and it is the item most likely to be refused on structure.
6. **Size the shadow array to the live caster count.**

Each measured on its own. A phase whose five items are folded together and reported as one number
cannot say which of them did anything, and four of the five are predicted to do nothing.

## Verification

- **0 px on all 29 goldens for items 2, 3, 4 and 6.** None of them changes what is drawn; a
  movement there is a bug, not a rebake.
- **Item 5 will move pixels** — a shadow that stops lagging by a frame is a different shadow. It
  names its fixtures before rebaking, and `dir_shadow` is the one that should show it.
- Whole gate suite at the end, **and not `--only`**: 11.93 shipped a red `gate-arm-docs` because
  `gate-docs` is the last group and `--only` matches by substring, so no targeted run reaches it.
- **Do not edit `gates.py` while the suite runs.** It reads its own source for the docs arm, and
  doing so corrupted 11.92's first full run.
- `prepass-crossover` is red on unmodified master on this host (11.91 measured it three times a
  side); check it the same way rather than re-running until green.
