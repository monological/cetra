# Spec 11.97 — One denominator

## Context

Roadmap **row 55b (T0.1)**, booked by spec 11.89, **measured there and deliberately not fixed** —
because the fix changes every number the profiler prints and wanted its own verification pass.

Every published number divides by **its own count**:

| column | denominator | site |
|---|---|---|
| GPU row | `scope->samples` — GPU results the driver returned | `profiler.c:195` |
| CPU row | `scope->cpu_samples` — frames the scope was entered | `profiler.c:460, 497` |
| `FRAME (wall)` | `profiler->frame_samples` — frames in the window | `profiler.c:361` |

So a scope gated on something occasional publishes a **per-occurrence** cost in a column of
**per-frame** means, and `TIMED` sums it in as though it ran throughout. Measured on
`dir_shadow_fixture --gi-volume`: a one-frame 699 ms GI sweep in a 38-frame window prints
**`TIMED` 17.9x its `FRAME`** — with nothing wrong in the timing code.

**Two gate arms already assert the property that is false.** `gpu-sum` (`gates.py:5168`) asserts
`TIMED >= 0.30 * FRAME`; `cpu-bound` (`gates.py:13964`) asserts `TIMED <= FRAME + 0.05` and every row
`<= FRAME + 0.05`, reasoning that "scopes are flat and non-overlapping, so no pass can spend more wall
time than the frame that contains it". Both are green only because their fixtures have no conditional
scope. **`profiler.h:175-182` states the defect in its own doc comment.**

There are 40-odd conditional scopes. The worst are `"gi capture"` (`engine.c:2645`, gated on
`dirty_count > 0`, and its first sweep runs every probe in ONE frame), `"sky cycle"`
(`engine.c:2593`, gated on a time-sliced re-bake being mid-flight), and every lazily-allocated post
pass.

## Design

### 1. One denominator: `frame_samples`

Every row becomes *how much of an average frame did this cost*. CPU: `cpu_accum_ms / frame_samples`.
GPU: `accum_ms / frame_samples`.

That is only correct if GPU results and frames-entered are the same set, which today they are not —
results lag `PROFILER_RING` (4) frames and unready slots are dropped, so `samples` is a *sampling*
artifact while frames-entered is the *physical* rate. **So drain the ring at each latch**: spin on
`GL_QUERY_RESULT_AVAILABLE` with a bounded give-up, once per ~0.5 s window, at a site outside every
scope and outside the frame bracket. This buys three things:

- `samples == frames_entered` by construction, so **no correction factor** and `int samples` deletes.
- It removes the **ring warm-up bias**. `_gpu_cmd` runs `-f 45` and `profiler_report` publishes the
  last *latched* window — which at 45 frames is the **first** one (`gates.py:4936-4951` says so in
  prose). Retires only begin at frame 4, so every profiled gate run and every spec table is currently
  understated ~8-11%.
- It is the option that **deletes** state rather than adding it.

The alternative — publish `(accum/samples) x (frames_entered/frame_samples)` — was rejected on
review: the numerator and the rate come from frame sets 4 apart, so a one-frame sweep straddling a
latch boundary reads **zero in both windows**. Turning "17.9x too big" into "silently absent" is worse
than the bug. Give-up on the drain is logged, never silent.

`frames_entered` (renamed from `cpu_samples`, guarded by `entered_this_frame`, renamed from
`cpu_counted`) survives as the **row-presence predicate** only. `latch_rows:306` must key presence on
it alone — leaving `samples > 0` in the predicate emits a phantom 0.000 row, which is exactly what
`profiler.h:135-136` says the design avoids.

### 2. Self-bracket the frame clock, and publish the period beside it

`profiler_begin_frame` stamps `glfwGetTime()`; `profiler_end_frame(profiler)` measures the bracket.
The `dt` parameter deletes. `FRAME (wall)` becomes the bracket — a **tight** ceiling, making
`TIMED <= FRAME` an identity for the CPU column (not the GPU column: GPU work runs asynchronously and
can outlive the CPU-side end).

The bracket excludes `glfwSwapBuffers` (vsync wait), `glfwPollEvents`, `_engine_advance_frame` and the
screenshot blocks — all outside it in `engine.c`. That would cost the HUD its headroom reading, so a
**`PERIOD` row** publishes the true inter-begin wall period alongside. One measurement feeds both it
and the latch timer (clamped).

**The latch moves from `end_frame` to `begin_frame`.** At begin N, frame N-1's bracket *and* its
period are both complete, so one `frame_samples` counts frames that contributed both and
`FRAME <= PERIOD` holds exactly — which is what makes it assertable. Frame 0 contributes neither (it
has no predecessor period), which is the principled version of today's frame-0 special case.

**Delete the frame-0 exclusion at `profiler.c:359-362`.** Not cleanup — load-bearing in the wrong
direction: left in place, `frames_entered = 38` against `frame_samples = 37` inflates every
steady-state row 2.7% and lets `TIMED` exceed `FRAME` on a table where nothing is wrong.

**Keep `PROFILER_LATCH_STEP_MAX`.** Driving the latch off raw wall time was considered and rejected:
the clamp is what amortizes a rare expensive frame across a representative window — the premise of the
per-frame denominator being introduced — and without it a 699 ms sweep latches a 2-4 frame window that
is nothing but the sweep. It also keeps the profiler's window aligned with the FPS counter's bucket
(`engine.c:2467`), and `profiler_suspend` does **not** protect the latch.

**Do not rename `FRAME (wall)`.** The literal is parsed at `gates.py:5142, 5168, 5256, 13964, 13966,
13981` and `gui.c:1176`, plus six spec tables; the regex would still match but every `.get()` returns
`None` and three arms go red for a word. The label contrasted wall-clock against GPU time, and still
does.

### 3. Two latent defects in the same file

- **`profiler_end_frame:331-335` logs an unclosed timing scope but never calls `glEndQuery`** — the
  exact bug the samples query five lines below was already fixed for (`:340-344`). Once tripped, the
  next `glBeginQuery` fails while `issued[slot]` is set anyway and the following `glEndQuery` closes
  the *previous* scope's query: the GPU column desyncs silently for the rest of the run.
- **`profiler_cpu_scope_begin` may open inside a GPU scope** (`profiler.h:114-115` makes the two
  deliberately independent). That would double-count wall time and break the identity. Refuse on
  `active >= 0`, incrementing `cpu_suppressed` so the matching end is still swallowed. This converts
  "scopes are flat" from a call-site convention into an enforced invariant — a precondition for
  claiming the identity at all. It also protects `cpu_t0`, one field shared by both paths.

## Phases

### Phase 0 — the instrument, before any behaviour change

The suite cannot see this bug. Three arms, each **proven RED on the current build before phase 1**:

- **`profiler-conditional`** — `dir_shadow_fixture --gi-volume`, assert `TIMED <= FRAME` on the CPU
  table. Reads 17.9x today.
- **`profiler-period`** — `FRAME <= PERIOD` in both tables.
- **`profiler-wall`** — the arm 11.89 booked and never built: **check FRAME against a clock the
  profiler does not own.** Difference the harness's own wall time across a 45- and a 90-frame run and
  compare against `PERIOD x frames`. No fixture in the suite is slow enough to trip the original clamp
  bug, which is why it survived.

`--bin-dir out/bin` explicitly when falsifying — the suite auto-selects `out/release/bin` and a
debug-only rebuild falsifies against a stale binary (11.96's trap).

### Phase 1 — the arithmetic

One denominator; drain-at-latch; `samples` deleted; self-bracket; `dt` deleted; PERIOD row; latch
moved to `begin_frame`; frame-0 exclusion deleted. Update `engine.c:2464, 2489, 2766` and `gui.c`.
Add `"PERIOD"` to the excluded-row sets in `gates.py` (5142, 13964-13966, 13981) or `cpu-bound` fails
on it by construction.

### Phase 2 — the two latent defects

Both above. Neither is reachable from a live call site today, so both need a deliberate reproduction
rather than a gate.

### Phase 3 — every number re-checked

The roadmap's own condition on this row. Publish a before/after table for `dir_shadow_fixture` and
`forest`. **Forest's numbers should barely move** — every scope there runs every frame, so the three
counts already agree — *except* for the ~10% warm-up correction the drain introduces, which is a real
change and must be reported as one. Numbers quoted in specs 11.89-11.94 are left as measured and
annotated as pre-11.97 rather than rewritten.

### Phase 3 result: the prediction held, and it was not the interesting half

`dir_shadow_fixture --gi-volume`, the motivating case: **`gi capture` 724.689 → 7.949 ms**, and CPU
**`TIMED` 736.855 ms against a 35.049 ms `FRAME` → 20.211 against 20.250**, i.e. from 21x the ceiling
to 99.8% of it. The GPU column was over by 3.4x and is now at 59%.

`forest -x -f 60 -W 800 -H 450 --no-fog`, two runs each side so every number below carries its floor:

| row | before | after | delta | floor |
|---|---|---|---|---|
| GPU `opaque` | 51.153 | 50.962 | **−0.4%** | 0% |
| GPU `shadow cascades` | 17.536 | 17.346 | **−1.1%** | 0% |
| GPU `TIMED` | 71.011 | 71.457 | +0.6% | 0–1% |
| CPU `ssr` | 56.213 | 54.417 | −3.2% | 1–3% |
| CPU `TIMED` | 84.220 | 84.361 | +0.2% | 0–2% |
| `FRAME (wall)` | 88.521 | 86.847 | −1.9% | 0–2% |

**Every row whose floor is under 5% moved less than 4%**, which is the prediction: forest's scopes all
run every frame, so its three counts already agreed. Rows with a floor of 30% to 160% — `atmosphere`,
`sss`, `bloom pyramid`, `tonemap + finishing` — support no claim in either direction and are not read
as ones.

**The finding is what the drain uncovered.** Five GPU rows read **exactly 0.000 in both before runs**
and read real time now:

| row | before | after |
|---|---|---|
| `gtao sweep` | 0.000 | 0.252 |
| `ao denoise` | 0.000 | 0.216 |
| `spec occ denoise` | 0.000 | 0.202 |
| `spec occ composite` | 0.000 | 0.106 |
| `bloom pyramid` | 0.000 | 0.031 |

All five ran every frame — each has a row and CPU time on both sides — so their GPU results were
never being collected at all. **A dropped result and a free pass print the same 0.000**, and the
suite's own `gpu-nonzero` arm exists because that ambiguity was already known at the whole-table
level; nobody had looked for it per row. It is worst exactly where it matters, since a frame deep
enough for the driver to run several behind is a frame somebody is profiling.

This does NOT invalidate the numbers in 11.89-11.94: their headline rows are the ones that moved
under 4% here. It does mean any 0.000 GPU row quoted from before this spec should be read as
unmeasured rather than as free.

`--profiler` still moves no pixel: `gpu-off` reads 0 px.

### Phase 4 — documentation

`profiler.h`'s `profiler_frame_ms` doc (delete the "ONLY VALID FOR A SCOPE THAT RAN EVERY FRAME"
paragraph, state the new identity and what still bounds the GPU column), the `dt` doc at `:85-86`,
`profiler.c`'s latch/end_frame comment blocks, `latch_rows`' header, `print_timing_table`'s "loose
bound" framing (now an identity for CPU, still loose for GPU), roadmap row 55b, `docs/verification.md`
ledger. Note `specs/11.89:292-294` is already stale — it describes a `PROFILER_FRAME_MS_MAX` that was
reverted and does not exist.

Branch `11.97-one-denominator` off `master`. Spec committed first, alone. Merging to master needs
explicit per-instance permission.

## What this will NOT do

- **Publish a later window instead of the first.** It would independently remove the pipeline
  transient, but it changes what every timing gate measures. Named, not done.
- **Rename `FRAME (wall)`.** Three arms go red for a word.
- **Drive the latch off raw wall time.** The clamp is what makes a window representative.
- **Rewrite the numbers in specs 11.89-11.94.** They were honestly measured under the denominators of
  their day; annotated, not restated.
