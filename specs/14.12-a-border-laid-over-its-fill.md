# cetra 14.12: a border laid over its fill

## Context

Trying 14.11 in pcb, the user saw the schematic pane's focus border far fainter than the code
pane's, though both have one style: the editor's blue at alpha 0.6, one point wide. Measured on
pcb's headless frames, the code pane's border peaks at RGB (67, 100, 140), the schematic's at
(50, 68, 91).

The cause is a bug in `cetra/shaders/ui_frag.glsl`, the one place a UI border is composited
(no app's fragment stage reads `vBorder`):

```glsl
vec3 rgb = mix(fill.rgb, vBorder.rgb, band * vBorder.a);
float alpha = mix(fill.a, max(fill.a, vBorder.a), band) * inside;
```

It mixes the border toward the fill's colour as though the fill were opaque. A clear fill's colour
is meaningless, and is black here, so a border over it is pulled 40% to black and then laid on at
alpha 0.6 again: the border's alpha is applied twice. `max(fill.a, border.a)` is not how two layers'
coverage combines. And `band` already carries `inside`, the box's outer-edge coverage, which `alpha`
applies again, so even over an opaque fill the outermost anti-aliased pixel of a border is pulled
toward the fill. Over an opaque fill everywhere else, the bug cancels out, which is why nobody saw
it: nearly every bordered element has a fill of 0.88 alpha or more. pcb's schematic, a self-drawn
panel whose border (14.11) has nothing under it, is the first that shows it.

**The fix is the definition, not a tuning**: lay the border over the fill with Porter-Duff over,
in straight colour since the UI blends with `GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA`
(`ui_draw.c:1027`), and apply the outer edge once.

Branch and spec: `14.12-a-border-laid-over-its-fill`, off cetra's master (`8302db71`).

## The design

`ui_frag.glsl`, the box path only (glyphs untouched):

```glsl
// The inner edge of the border's band, anti-aliased; the outer edge is `inside`, applied once to
// the whole box below.
float ring = border_w > 0.0 ? smoothstep(-aa, aa, d + border_w) : 0.0;
// The border laid over the fill, Porter-Duff over: each weighted by its own alpha, so a clear
// fill's colour adds nothing. In straight colour, for the blend.
float ba = ring * vBorder.a;
float a = ba + fill.a * (1.0 - ba);
vec3 rgb = mix(fill.rgb, vBorder.rgb, a > 0.0 ? ba / a : 0.0);
float alpha = a * inside;
```

`mix(f, B, ba / a)` is exactly over's colour, `(B*ba + f*fa*(1-ba)) / a`. Two properties fall out
and are stated in the shader's comment:
- **No border** (`ba = 0`): `rgb = fill.rgb` and `alpha = fill.a * inside`, bit for bit as now
  (`mix` with weight 0 returns its first argument), so every unbordered element is unchanged.
- **An opaque fill**: `a = 1`, `rgb = mix(fill, border, ba)`, as now everywhere but the outermost
  anti-aliased pixel, which now takes the border's colour at its coverage rather than one pulled
  toward the fill: a slightly crisper edge.

What changes on screen, said in the spec as built:
- A border over a clear fill (pcb's schematic, any self-drawn panel) shows at its stated opacity.
- A **scrolling pane's focus border** (no fill, alpha 0.45, the "subtle border" of
  `_default_style`) shows at 0.45 where it showed at about 0.2: brighter. Its value is kept, since
  0.45 is what it states; the look is checked in the canvas app's palette and history.
- Panels at 0.88 and fields and controls at 0.95 move by a code or two at a border.

## Tests

**`canvas-ui-borders`**, a new arm in the `canvas` group, beside `canvas-under-ui`
(`scripts/gates.py:31233`, the same `_canvas_run` and `_ppm_array` pattern). Under a new
`--ui-borders` flag (`apps/canvas/src/canvas_app.c`, beside `--ui` at 3259), the app lays an
opaque backdrop panel of colour C holding four boxes of one size, radius and border
(B = the focus blue at 0.6, width 2), and prints each one's framebuffer rect as `canvas border NAME
x0 y0 x1 y1` with `say_box`:
- `opaque`: fill C, alpha 1;
- `clear`: fill magenta at alpha 0 -- a colour that must count for nothing (an all-zero colour means
  "inherit" in a style);
- `half`: fill F at alpha 0.5;
- `mixed`: fill `0.5F + 0.5C`, alpha 1, which is F laid over C.

The arm holds over's two properties pixel by pixel over each box: `clear` matches `opaque` and
`half` matches `mixed`, within 2 codes a channel (8-bit rounding in the blend); and the border is
there at all, its ring at least 20 codes from C, so a box drawing nothing cannot pass. The current
shader fails both comparisons by tens of codes, the clear box tinted magenta.

## As built

### Phase 1: the instrument

`--ui-borders` in `apps/canvas` (`build_borders`): an opaque backdrop panel, colour (0.16, 0.20,
0.26), holding four boxes of 70 by 40 points, radius 8, border the focus blue at 0.6 and 2 wide;
the half box's fill is (0.80, 0.30, 0.20) at 0.5 and the mixed box's that laid on the backdrop.
Each prints `canvas border NAME x0 y0 x1 y1` in framebuffer pixels. `canvas-ui-borders` compares
the boxes pixel for pixel.

On the shader as it was, the arm fails: over the clear fill 45 codes from over the backdrop's
colour, over the half fill 46 from over the mixed one, the border 114 codes off the backdrop. Seen
in the picture, the border over the clear fill is purple, the zero-alpha magenta mixed into it, and
the one over the half fill a greyed pink, where the opaque box's is blue. Every other arm of the
`canvas` group passes.

**Found on the way**: the build broke under Homebrew's CMake 4.4.5, which re-detected the compiler
with the Command Line Tools' SDK (`xcrun --show-sdk-path` now names it) where 4.4.4 had Xcode's. The
cache still held zlib in Xcode's SDK, an implicit include no longer, so every C++ object took it as
an explicit `-I` ahead of libc++'s headers and failed. `cmake --preset macos-debug -U "ZLIB_*"`
found zlib again in the compiler's SDK and the build came back; the cache, not the tree, was wrong.
