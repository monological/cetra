# Coverage vs translucency, and B8 hair

## Context

A close-up of the raiden rig shows flat olive quads through the hair — whole hair
cards, visible as rectangles, in a colour that appears nowhere in the groom.

**Diagnosed, not guessed.** `pbr_frag.glsl` lifts opacity toward 1 at glancing
angles:

```glsl
f = iorF0 + (1 - iorF0) * pow(1 - NdotV, 5)
finalOpacity = mix(opacity, 1.0, f)
```

At grazing `f → 1`, so `finalOpacity → 1.0` **regardless of the authored alpha,
including alpha = 0**. A hair card seen edge-on is exactly that case, so its
transparent texels turn opaque and the whole quad appears, showing the atlas's
inter-strand region — colour the artist never intended to be seen (I pulled
`Image_20_14.png`: strands are pale grey, transparent texels store near-black; the
frame samples `srgb(26,32,24)`, green-dominant against a blue-dominant
background). Confirmed positively by stubbing `fresnelOpacity` to return `opacity`
unchanged: the sheets vanish entirely. `--no-oit` does not change them, so this is
not the OIT path.

**The root cause is that alpha means two different things and the code multiplies
them into one number** at `pbr_frag.glsl:954`:

- **Coverage** — how much of the pixel contains geometry. Comes from the texture.
  A hair card's alpha is a stencil: "there is no hair here."
- **Translucency** — how much light a solid surface transmits. Comes from the
  scalar `materialOpacity`. A visor is 20% opaque everywhere.

Fresnel is physically right for the second and meaningless for the first: where
there is no geometry there is no interface, so there is no Fresnel event to have.
Boosting coverage invents surface the artist deleted.

Two consequences beyond the sheets: the same boost feeds `NormalOut.a`, which is
the A2C coverage channel, so alpha-*masked* card silhouettes thicken at grazing
too; and the moments MBOIT builds are built from the same inflated number.

**Scope.** This is the coverage fix plus **all of roadmap B8** (row 19,
"Physically based hair (Karis/Marschner)", Effort XL, `:403-410`) — both its
transparency half and its shading half — and, per B8's stated gate, **B3.1 and
B3.2** first.

Read it as a programme, not a session, and note the shape: **the value is
front-loaded into a handful of shader lines.** The olive sheets are gone at the end
of Phase 1. Phase 3 shrank to near-nothing once the evidence came in (raiden is
already banded in the asset). Phases 5 and 6 are the two Effort-M prerequisites
and the Effort-XL shading model, and they are where the real time goes.

**Every phase is independently landable and independently revertible**, and they
are ordered so nothing later invalidates the evidence for anything earlier — with
one exception, called out in Phase 6.

## Phase 1 — separate coverage from translucency

The fix, in `cetra/shaders/pbr_frag.glsl`:

```glsl
// Coverage: geometric presence, authored in the texture.
float coverage = 1.0;
if (opacityLayer >= 0)     coverage = texture(maskArray, vec3(uv, float(opacityLayer))).r;
else if (texAlpha < 1.0)   coverage = texAlpha;
float opacity = coverage * materialOpacity;    // unchanged for every existing reader

// Fresnel lifts only what is genuinely translucent; coverage rides through.
float fresnelOpacity(float coverage, float materialOpacity, float iorF0, float NdotV) {
    if (materialOpacity >= 1.0)
        return coverage;
    float f = iorF0 + (1.0 - iorF0) * pow(clamp(1.0 - NdotV, 0.0, 1.0), 5.0);
    return coverage * mix(materialOpacity, 1.0, f);
}
```

The invariant this establishes is the whole point: **`finalOpacity <= coverage`,
always.** Today's code violates it — a texel at alpha 0 reaching 1.0.

| surface | today | after |
|---|---|---|
| glass, scalar opacity 0.2, no alpha texture | `mix(0.2, 1, f)` | **identical** |
| hair card, texAlpha 0 | → 1.0 at grazing | 0.0, always |
| hair card, texAlpha 0.5, opacity 1 | → 1.0 at grazing | 0.5, no boost |
| textured translucent, 0.5 × 0.4 | `mix(0.2, 1, f)` → 1.0 | `0.5 × mix(0.4, 1, f)` ≤ 0.5 |

Everything whose alpha is scalar-only is bit-identical, which is what makes the
golden battery a real check rather than a re-bake exercise.

**Be precise about which class moves, because "scalar-only stays identical" reads
wider than it is.** The materials that change are exactly those with
texture-driven alpha and `materialOpacity == 1.0` — today they reach
`fresnelOpacity` with a fractional argument and get lifted; after the split the
`materialOpacity >= 1.0` early-out returns `coverage` untouched. That is the
intended fix, and it is the class raiden's hair is in (none of its four
alpha-carrying materials authors a `baseColorFactor`, so `materialOpacity` stays
at its 1.0 default). Note also that `material_finalize_alpha_mode`
(`material.c:88-91`) promotes *any* material with an `opacity_tex` to
`ALPHA_BLEND` regardless of opacity, so opacity-mapped materials land in this
class too.

**This matters most for the measuring instrument.** `gen_oit_cards_fixture.py:165`
and `gen_catcher_transparency_fixture.py:144` both author alpha as
`baseColorFactor[3]` with **no base-colour texture** — so `coverage == 1.0` and the
new expression reduces to today's exactly. The three analytic OIT gate arms
(`oit-sorted` / `oit-weighted` / `oit-moments`, which compare absolute radiance
against closed-form arithmetic) and the catcher-transparency gate must therefore
report identical numbers to the digit. If they move, Phase 1 is wrong. That keeps
the OIT accuracy instrument valid as a before/after reference across this change.

For the record on the test asset: the raiden GLB declares **three BLEND materials
and one MASK**, so both bands exist in it and the close-up exercises both.

`fresnelOpacity` is called from two sites (`:1090` moment generation, `:1804`
shading) and both must keep using the shared helper — the moments have to describe
the same opacity the accumulate writes.

**Also in this phase, because they are the same conflation:**

- **`opacityLayer` silently drops the albedo stencil.** At `:955-960` a mask-array
  opacity layer *replaces* `texAlpha` rather than combining. A material with both an
  opacity map and an alpha-cut albedo loses the cutout. Make coverage the product of
  both, and state the change in the spec — this is a behaviour change, not a
  refactor, so it needs its own before/after.
- **Two debug paths duplicate the opacity chain** (`:830` renderMode 6, `:1040`
  renderMode 7). Both already compute `materialOpacity * texAlpha` with no Fresnel —
  i.e. they already do the right thing. Route them through the same `coverage` so
  there is one definition.
- **`material_finalize_alpha_mode`** (`cetra/src/material.c:83-92`) promotes
  OPAQUE→BLEND when `opacity < 1 || opacity_tex`. "An opacity map implies
  translucency" is the same category error at import: a hair stencil implies MASK,
  not BLEND. Do **not** change the promotion in this phase — it moves geometry
  between passes for every asset in the corpus. Record it and address it in Phase 3
  where the routing work already lives.

Files: `cetra/shaders/pbr_frag.glsl` only.

## Phase 2 — three defects the audit surfaced, sized before committing

Each is independent of Phase 1 and each needs measuring before it is called a bug.
Land whichever survive as separate commits.

1. **`SpecOut.a` is a dead store.** Attachment 7 is `GL_R11F_G11F_B10F`
   (`engine.c:114-118`) — no alpha channel — yet `:1856` writes `finalOpacity` into
   it, and a comment claims the value matters for A2C. Either the format or the
   comment is wrong. Verify, then delete the write or fix the note.
2. **The "last active output" A2C rule does not match the attachment table.**
   Comments at `:38` and `:1817` say the driver derives coverage from the last
   active colour output's alpha. But attachments 2, 3 and 4 carry `roughnessMap`,
   `metallicMap` and `sssProfileIndex+1` in their alpha. If the rule holds, an
   `--sss` frame derives coverage from a profile index. Test it directly on an
   A2C fixture with SSS on and off before changing anything.
3. **Attachment 0 keeps `SRC_ALPHA` blending during the opaque pass.**
   `glEnable(GL_BLEND)` is global (`engine.c:416`) and
   `engine_set_scene_draw_buffers` disables it only for slots ≥ 1 (`:2339-2346`,
   loop starts at `i = 1`). So a masked fragment's alpha is applied twice — once as
   MSAA coverage, once as the blend factor — which would darken card interiors by
   roughly alpha². Opaque materials are unaffected (alpha 1 makes the blend a
   no-op), so this is specific to hair and foliage. **Measure it** before deciding —
   on `apps/tree`, whose leaves are the only A2C content in the repo
   (`tree.c:1545-1546`, ALPHA_MASK cutoff 0.4 on a baked RGBA albedo) and which is
   baseline-grade deterministic. If real, the fix is `glDisablei(GL_BLEND, 0)` for
   the opaque pass, re-enabled for the late pass.

## Phase 3 — hair cards: the renderer-side band split is probably not needed

**A design review killed the dual-pass design I originally wrote here, and one
piece of evidence reframes the whole phase.**

**raiden's groom is already banded, in the asset.** `Hair_1` (`MASK`, cutoff 0.5,
doubleSided) and `Hair` (`BLEND`, doubleSided) are separate meshes whose
`baseColorTexture` indices 23 and 24 both resolve to **image source 14** — one
atlas, two materials, two alpha bands. That is not merely convenient test content:
it *is* the core/tips architecture, authored where the alpha band actually lives
(the DCC), with zero renderer changes. The thing Phase 3 was going to build into
`render.c` is already solved one layer up.

So the standing assumption inverts. The default is: **Phase 1 fixes hair, because
the asset pipeline already does the banding.** Build nothing here until that is
falsified on the acceptance shot.

### Why the dual pass was wrong anyway

Recorded so it is not re-proposed. As specified it was **inert** — a `hair_cards`
flag on an `ALPHA_MASK` material leaves `is_late = false`, so the mesh takes
`draw_here = true` in the opaque pass and never reaches the `!draw_here` branch
where all three counters live (`render.c:321-337`). `oit_mesh_count` stays 0, the
whole Pass 2 block at `:968` is skipped, the tips traversal never runs. It renders
a hard-cutoff groom and fails silently.

Four further problems, three of them intrinsic to the shape rather than the
implementation:

- **Ambient-specular seam.** `splitAmbientSpec` keys on `!alpha_pass`
  (`render.c:402-403`), so the core routes to attachment 7 and the tips must keep
  specular inline. One card, two ambient-specular paths, meeting at an arbitrary
  alpha contour. A single pass cannot have this defect.
- **Tips lose the G-buffer.** Attachments 2/3 (velocity, aux linear-Z, roughness,
  albedo) bind in the opaque pass only. `taa_resolve_frag.glsl:72` does an
  undilated velocity fetch, so tip pixels reproject with the *background's*
  velocity — a trailing smear on exactly the silhouette the feature exists to
  soften, on a walking rig.
- **Captures bake bald hair.** `render.c:981` gates OIT on `!capturing`, so every
  probe and DDGI face would see the core with a hard cutoff while the main camera
  sees soft tips.
- **`alphaToCoverage` is doing double duty** (`render.c:165` crosses a material
  property with an engine property, no pass term). Leave it 1 for the tips and
  `glEnable(GL_SAMPLE_ALPHA_TO_COVERAGE)` fires inside the OIT accumulate, applying
  coverage twice; set it 0 and `alphaBelowCutoff` silently deletes the entire tips
  band. Both obvious implementations are broken, in opposite directions.

Plus a cost I had not budgeted: routing hair into `oit_mesh_count` triggers
`_ensure_moment_targets`, logged at `engine.c:2618-2620` as the largest single
allocation the renderer makes (156 MB at 640x400, 244 MB at 800x500). That would
undo 11.17's stated justification for OIT-on-by-default — that a scene without
translucency allocates nothing.

### If Phase 1 turns out not to be enough

The escalation is three lines, not a pass. Route the whole material to OIT while
keeping the `ALPHA_MASK` contract intact:

```c
// render.c:305
bool is_blend = mat->alpha_mode == ALPHA_BLEND ||
                (mat->alpha_mode == ALPHA_MASK && mat->hair_cards);
// render.c:543 — A2C is an opaque-pass mechanism; hair no longer uses it
bool use_a2c = mat->alpha_mode == ALPHA_MASK && !mat->hair_cards && a2c_capable;
// render.c:165 — and the discard threshold follows
uniform_set_int(u, "alphaToCoverage", masked && !mat->hair_cards && a2c_capable ? 1 : 0);
```

`alphaMasked` stays 1, so the shadow-map exclusion (`shadow.c:436-440`) and the
GTAO zero-normal skip keep working off the material exactly as `material.h:23-35`
says they must. Every counter works **unmodified**, because the mesh now genuinely
takes the `!draw_here` branch. Captures, the refraction resolve and the shadow
catcher all get one documented behaviour instead of a split one.

**I was wrong about the authoring path** and it should not count against this. A
`.cscn` dropped beside the model auto-loads (`cscene_apply.c:42-51`, cwalk swaps
the extension and probes), so `my_models/raiden/source/raiden_textured_rigged.cscn`
is a file, not a feature. Adding `hairCards` to the material vocabulary is **one
row** in `MATERIAL_PARAMS` (`cscene_apply.c:319-347`) — the table's own comment
says as much. The "SHADING ONLY" rule above it (`:310-314`) is a real convention
with a real rationale (a typo moves geometry between queues rather than merely
misshading it), but it is a convention, and `windMode` already sits in that table
while redefining what UV1 *means*. Extending it deliberately, with the comment
updated to say why, is legitimate.

### Worth doing regardless: a raiden `.cscn`

Independent of any hair work, and cheap. It pins the camera, exposure and tonemap
for the hair close-up so the acceptance shot is reproducible instead of a pasted
command line, and it gives raiden the same footing every fixture already has. This
is the fix for the class of problem 11.18 kept hitting — recipes that live in prose
rather than as files.

### Fixture and gate — only if the escalation is needed

`assets/gen_hair_cards_fixture.py`: overlapping cards with a *generated* alpha ramp
texture, so coverage is analytically known. New for the corpus — every existing
fixture is flat colour with no texture dependency, so the generator must emit the
PNG too, base64-embedded like `gen_contact_fixture.py`. Note this is the **only**
instrument that would measure any of this: `11.17:254-261` records that the card
fixture is blind to it by construction, and `oit_fixture` cannot discriminate two
OIT schemes at all.

`run_hair_cards_gate`, self-verifying: a texel authored at alpha 0 must read the
background exactly at every viewing angle including grazing — that is the
regression bar for Phase 1 and it fails today — plus the inverse half, per house
practice.

## Phase 4 — goldens: the prediction is that NOTHING moves

The blast radius turned out far smaller than the change sounds, and this is the
single most important fact for executing it:

**No fixture in `assets/` uses texture-driven alpha.** Every authored alpha in the
whole corpus is a scalar `baseColorFactor[3]`, on exactly four fixtures
(`oit_cards`, `oit_fixture`, `oit_sphere`, `catcher_transparency`). The only two
fixtures with a base-colour texture at all (`dof_fixture`, `parallax_fixture`) ship
PNG colortype 2 — no alpha channel. No fixture has a `COLOR_0` attribute either, so
the `texAlpha *= VertexColor.a` branch is dead across the entire fixture set.

Therefore, if Phase 1 is correct, **all 18 goldens measure 0 px and every gate
reports identical numbers.** Any movement is a bug in the split, not a re-bake
candidate. That converts Phase 4 from a re-bake round into a falsification test.

**The OIT gate deserves specific attention** because it bakes the Fresnel boost
into its own ground truth (`gates.py:1150-1157`):
```python
f0 = ((OIT_IOR - 1.0) / (OIT_IOR + 1.0)) ** 2      # 0.04
a = alpha + (1.0 - alpha) * f0
```
The cards face the camera and are sampled on the horizon line, so only normal-
incidence F0 survives. Under the split, `coverage == 1` and the expression reduces
to today's exactly — so this stays valid. If it moves, the scalar path was touched
and Phase 1 is wrong.

**Where movement IS expected — real assets, none of them goldens:**

| asset | materials with texture alpha | note |
|---|---|---|
| raiden | `Hair_1` (MASK, cutoff 0.5), `Hair` (BLEND), `Cool_Touch`, `rai_decal` | none authors `baseColorFactor`, so `materialOpacity == 1.0` and `fresnelOpacity` returns pure coverage after the fix |
| `abandoned_window` | `LaceCurtain`, `SheerCurtain`, `IvyLeafReal`, `Glass_Grime` | `Glass_Grime` peaks at alpha 76/255 = 0.30, so the boost currently dominates it everywhere — expect the largest visible change here |
| `apps/tree` | procedurally baked RGBA leaf albedo, ALPHA_MASK cutoff 0.4 | baseline-grade deterministic (headless ×2 0 px); add it to the verification set |

Capture before/after crops for all three and record them; they are the evidence
the fix does what it claims, since no golden can show it.

**Recipe corrections to make while here** — the first is an error I committed in
11.17's review round and should be struck:
- `roughness_sweep`, `guard_thin_panel` and `backface_dark` **do** have recipes —
  `assets/area_light_goldens.md:31-72`, committed before 11.17. They need
  `--no-scene-file` and `--area-light`, which is why they were missed. The spec
  says "no recipe recorded anywhere"; that is wrong and should be struck.
- `ao_fixture`'s recipe is genuinely partial: `specs/11.5:188` writes
  `--spec-occ <mode>` as a literal placeholder and never records the mode.
- `cornell_box` remains genuinely unreproducible (86% of pixels, identically at
  HEAD; spec 10.3 baked it against a known-inverted area-light response). Already
  filed; not this change's problem.

## Phase 5 — B3.1 and B3.2, the stated prerequisites

The roadmap gates B8 on these, and it is specific about why: *"hair shares the
shadow-scattering and area-light problems and is far more expensive to iterate
on"* (`:516`). Both are Effort M, both depend only on shipped work, neither owns
foundations.

- **B3.1 Shadow-penumbra scattering** (`:316-323`) — Penner's second LUT,
  pre-integrating the diffusion profile against the shadow's penumbra gradient so
  light bleeds across a cast-shadow edge instead of being multiplied to zero. The
  penumbra width is already estimated for PCSS, so the input is in hand.
- **B3.2 Skin under an area light** (`:325-332`) — the SSS accumulation path
  `continue`s past LTC panels, so `sssDiffuse` never sees them. Wants a
  representative direction and a solid-angle-aware width.

**Both are about *diffuse transport into a surface*, which hair's R/TT/TRT lobes
do not use.** TT (transmission through the strand) is the closest analogue and is
a strand-local absorption term, not a diffusion profile. So my read is that the
dependency is about *iteration cost and shared tooling*, not a hard blocker — you
do not want to be tuning hair while the shadow terminator and area-light response
underneath it are still moving.

That gives a real choice, and it should be made explicitly rather than drifted
into: **do B3.1 and B3.2 first** (adds two M items before any hair shading, and
means hair is tuned against a settled terminator), **or** proceed and accept that
hair under a cast-shadow edge and under an LTC panel will be re-tuned once they
land. I would do them first — the roadmap's reasoning is about not paying the
tuning cost twice, and hair is the most expensive thing in the tier to iterate on.

## Phase 6 — B8 shading: Karis/Marschner

Per `docs/aaa-rendering-roadmap.md:403-410`. This is the XL half.

- **`cetra/shaders/hair_frag.glsl` + `create_hair_program`** — a dedicated program,
  selected per material by a hair flag, following the existing program-cache idiom.
- **Three-lobe specular (R / TT / TRT)** from shifted anisotropic lobes along the
  strand tangent, which for cards is the UV V-direction. Karis azimuthal scale
  factors; absorption colour; wrapped-diffuse standing in for multiple scattering.
  CSM as-is.
- **Material params**: `hair_roughness`, `hair_shift`, `hair_tint`, `hair_backlit`,
  plus the program flag — the same `foliage_shadows`-style contract as Phase 3's
  `hair_cards`, and the same reason for keeping them out of the `.cscn` table if
  they select a program rather than merely shade.
- **Import**: hair flag from glTF extras, card tangents derived at import, flow map
  as a `mask_array` layer (the existing packing path, `mask_array.c`).
- **Fixture + gate**: the lobes need an acceptance instrument of their own. The
  honest one is a shift/roughness sweep asserting lobe ORDERING and separation
  (R nearest the highlight, TRT offset by the shift, TT on the backlit side)
  rather than a stored image — same shape as the skin curvature-ordering gate,
  which asserts orderings that cannot drift rather than pixels that can.

**Sequencing note.** Phase 6 changes what the hair *looks* like, so it invalidates
every hair before/after captured in Phases 1–3. Land 1–3 with their evidence
first, then treat Phase 6's baseline as new.
