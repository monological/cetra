# Name the directional shadow caster that silently stops casting

## Context

This came out of a survey of "what is global in this engine that shouldn't be,"
run after 11.22 landed and verified by five explore agents. Nearly all of it came
back negative, and that negative result is the more useful half:

- **The nine material feature toggles on `Engine` are already per-material.** Seven
  of them gate a per-material value with a straight `&&` — `clearcoatEnabled > 0 &&
  clearcoat > 0.0`, `sssEnabled > 0 && subsurface > 0.0`, and so on — so a material
  at 0 is unaffected either way and the global is a forced-off debug override, not
  a missing granularity. Six of the declaration comments already say this. The
  other two gate nothing per-material: `energy_comp_enabled` keys off `Ess` and
  `iblEnabled` (scene-level), and `oit_enabled` reroutes every `ALPHA_BLEND` mesh
  between two transparency algorithms, which is a pass-routing choice rather than a
  material property.
- **Per-light or per-cascade shadow *technique* is unreachable**, not merely
  expensive. `csm.glsl` declares one `sampler2DArray` on unit 10 and it binds either
  the depth array or the moment array for the whole draw. All 16 units are occupied
  and the `_Static_assert` chain at `render.c:37-59` pins the ledger, including unit
  14 being double-booked between the skybox cube and the GI atlas by mutual
  exclusion. So PCSS-near + MSM-far is a hardware ceiling, not a refactor.
- **Per-light `cascade_count` would touch 18 sites across 6 files**, three of which
  assume a uniform stride: `cascade_splits` is one schedule shared by every
  directional light, `fragCascade` is hoisted outside the per-light loop in
  `pbr_frag.glsl:1254`, and `froxel_inject_frag.glsl:186` computes
  `fogVisibility(j * cascadeCount, P)` — which would silently address another
  light's layers under non-uniform counts. No scene in the repo generates the
  demand.

Recorded so the next survey does not re-derive them. **One real finding survived.**

## The finding: two directional capacities disagree, silently

- `LC_MAX_DIR_LIGHTS` / `MAX_DIR_LIGHTS` = **4** — directional lights the lights UBO
  carries (`light_cluster.h:28`, `include/lights_ubo.glsl:17`)
- `MAX_SHADOW_LIGHTS` = **3** — directional lights that can own cascade slots
  (`shadow.h:11`, `include/csm.glsl:21`)

A 4th shadow-casting directional light has `shadow_map_index` reset to `-1` in the
classification pass and never reassigned, because the assignment loop's own guard
`slot < MAX_SHADOW_LIGHTS` stops iterating before that light's body runs. Nothing is
logged. In the shader, `shadow` stays at its initialised `1.0` when
`dirShadowSlot < 0`, so the light illuminates the scene at full strength and darkens
nothing — indistinguishable from one that never asked for a shadow. A shading
correctness bug that reads as "everything worked."

Which light loses depends purely on `scene->lights[]` order; nothing prioritises by
intensity or name.

**Reachable through ordinary authoring.** `.cscn` caps total lights at 16 with no
per-type cap (`cscene.c:126`), and `add_light_to_scene` (`scene.c:293`) has no cap at
all — it reallocs by one per call. No fixture or gate in the repo has more than one
directional light, which is why this has never been observed.

## Why it is worth eight lines

**The engine already made this exact decision the other way, one code path over.**
The punctual pool latches the first overflowing light and names it, and the comment
states the reasoning:

> Named, because the alternative is a light that silently stops casting and reads as
> a shading bug.

`shadow.h`'s own comment on `MAX_PUNCTUAL_SHADOW_LAYERS` makes the same argument from
the other side — erring small is deliberate, because "exhausting the pool is a
failure a log line can name, where an over-large pool costs frame time with no signal
at all."

Both of those are arguments about shadow casters in general. Neither is specific to
punctual lights. The directional path simply never got the treatment.

## Change

Mirror the punctual overflow warning. Reuse the idiom rather than invent a second.

**`shadow.h`** — one latch field beside `punctual_pool_warned`, with a one-line
contract comment.

**`shadow.c`, `render_shadow_depth_pass`:**

1. In the classification loop, the overflow is already detectable as the untaken
   branch of the directional count. Capture the first overflowing `Light*` into a
   local, exactly as the punctual path captures `pool_overflow`. Only lights with
   `cast_shadows` reach that point, so no extra predicate is needed.
2. Beside the punctual warning, emit the directional one under the same
   latch-and-rearm shape, naming the light and the cap, with the same
   `"unnamed light"` fallback.

**No behaviour change.** The 4th light still does not cast, exactly as today. This
only makes the existing behaviour audible.

## Not in scope

- **Raising `MAX_SHADOW_LIGHTS` to 4 or lowering `MAX_DIR_LIGHTS` to 3.** A capacity
  decision with real consequences — `cascade_matrices[MAX_SHADOW_LIGHTS *
  SHADOW_CASCADES]`, the matching GLSL arrays, and `POSTFX_FOG_MAX_LIGHTS`, which is
  `_Static_assert`-ed equal to `MAX_SHADOW_LIGHTS`. The mismatch may well be
  correct; it should just not be silent.
- **The moment-shadow blur curve** (near sharp, far soft), proposed and dropped. The
  premise was that it would keep the pillar gate passing while allowing a higher
  blur. The fixture's pillar band computes to view depth ~12.6-13.6 against splits of
  ~6.9 / 19.0 / 68.9, putting it in cascade **1**, not 0 — so protecting only the
  near cascade would not protect it. The proposal does not deliver what it was for.
- **The stale fixture comment.** `assets/gen_dir_shadow_fixture.py:36-40` claims the
  pillar's band "crosses the cascade-0/1 split," which the computed splits
  contradict. One of the two is wrong; worth knowing the comment is unreliable as
  documentation, not worth chasing here.
- Everything else from the survey above.

## Verification

1. `./build.sh` clean.
2. **The warning fires and names the light** — a temporary `.cscn` with 4 named
   directional lights, all `cast_shadows`, rendered headless. Exactly one warning,
   naming the 4th.
3. **It does not fire at 3.**
4. **It fires once, not per frame** — the latch, over enough frames that a repeat
   would show.
5. **Nothing else moved.** Every fixture has a single directional light, so the full
   gate suite must pass and `dir_shadow_fixture.cscn` must render 0 px against a
   pre-change build, pinned with `--no-auto-exposure -E 1.0`.
