# 11.65 — making the gate suite cheap enough to run often

## Context

`scripts/gates.py` cost **14:51** for 265 arms across 51 groups — more than double the ~7 minutes
this file used to claim from memory. It now costs **10:17**, a 31% cut, from one change: running
the apps from a release build. The standing advice ("`--only <group>`
between phases, whole suite once at the end") is a symptom: a suite you avoid running catches
things later than it could.

**This spec does not parallelise.** Everything here is about doing less; parallelism stays
available afterwards, on a smaller base. **And nothing here may weaken an arm** — two arms shipped
inert this cycle (`quadtree-render`, `region-shift`), so "still green" is not evidence a cut was
safe. Every changed frame count gets a comment naming its floor; every touched arm gets its
falsifying mutation re-run.

**And the outcome is mostly a set of things NOT done.** Four of the six planned steps were aimed at
costs that measurement showed do not exist, and the spec keeps them, with their prices, rather than
deleting them — a future reader who re-derives "cut the frame counts" from first principles should
find the number attached to it.

## What the investigation established (source-read, line-cited by the two survey reports)

- **~339 renderer processes per run** (~284 `render`, ~55 `forest`) + 44 Python fixture
  generators + ~114 ImageMagick launches (`compare()` spawns two per call). At the suite's wall
  clock that is roughly **1.2 s per process while the median process renders 30 frames of 0.36
  requested Mpx** — per-process fixed cost dominates, not pixels.
- **Every requested pixel is 16 shaded samples**: HiDPI doubles each dimension
  (`engine.c:479-481`) and headless defaults to **4x MSAA** (`render.c:3400-3403`) unless `--taa`
  or `--msaa 1`.
- **The suite runs the DEBUG binaries** — `out/bin` hardcoded at `gates.py:39`, `:4252`,
  `goldens.py:46`; `CMakePresets.json` pins that dir to `-O0`. Forest startup measured 6.57 s
  debug / 1.40 s release. The erosion bake is 5x slower in debug (2.3 s vs 452 ms), and 9-12
  launches erode.
- **~37 shader programs compile+link per process, no cache** (`engine.c:1307-1492`, plus ~39 at
  PostFX init) — ~12,500 GLSL compiles per suite run. NOTE: the obvious fix, `glProgramBinary`,
  is almost certainly DEAD on this platform — Apple's GL driver reports zero binary formats.
  Verify with a three-line probe before anyone builds a cache; the viable alternative is LAZY
  program creation for off-by-default passes, for which `postfx_ensure_taau_program`
  (`postfx.c:357`) is the in-house precedent.
- **`-f 30` is the file's most-repeated number (~130 of ~339 processes) and is never justified
  once in 12,480 lines.** The engine audit found no mechanism that produces 30:
  - With no `--taa`, every shared temporal accumulator (TAA, GTAO, SSGI, SSR, SSS, fog layer,
    contact) is off AND force-invalidated per frame (`postfx.c:3333` et al.).
  - Pinned exposure skips metering entirely (`postfx.c:3493`) — zero frame requirement.
  - Animation/wind/particles/water are pure functions of the frame index headless
    (`engine.c:2461-2468`).
  - The one unconditional floor is the async loader at **5 texture uploads/frame**
    (`engine.c:2612`) — and the corpus barely triggers it (25 of 40 PNGs are goldens; most
    fixtures load 0-1 textures).
  - The genuinely load-bearing counts are **60** (froxel fog + clouds: alpha=0.1 EWMA, sub-1/255
    first at N~54; 30 retains 4.2%), **150** (exposure converges at 91 on its fixture; water foam
    ramps ~150), **240/400** (`--trace-player` prints every 30 steps; the region walk needs cells
    crossed). None is 30.
- **Frame-0 froxel bug found in passing**: `froxel_prev_frame` initialises to `-1` and frame 0's
  continuity test `-1 == frame_index - 1` MATCHES, so frame 0 blends against zero-cleared history
  and fog starts at 10% strength (`postfx.c:721`, `:2575`). `sky_clouds.c:329` carries the
  `>= 0` guard the fog path lacks. One-line fix.
- **Two resolutions the code itself retracted** (`gates.py:434-448`, `:1078-1084`): the skin arms'
  1200x750 existed for a pixel-cap lever spec 11.14 removed — the comments say resolution
  "creates no slack at any size". Six renders, 162 Mpx-frames, to sample eight pixels.
- **`_raiden_render` x3 inherits the app's default 1920x1080** (no `-W/-H` passed) x 120 frames,
  loading an 8K HDR and two FBX clips each time — ~12 G shaded samples serving ONE arm
  (`prepass-masked`), whose `-f 120` is inherited from the AGENTS.md recipe, not required.
- **Exact duplicates and dead output**: 4 byte-identical command pairs across groups (dir-shadow ~
  origin, flare pt0 ~ base, translucent on ~ offpath on, a third `--no-oit` render), 3 near-dups
  foldable with `--screenshot-every` or an added probe flag, and ~55 launches that write `-S`
  screenshots nothing ever opens (`_terrain_run` already dropped its `-S` with the reason
  written; the pattern was never propagated).
- **`--screenshot-every` works in every app since 11.62** and the suite uses it twice.

## Step 0 — MEASURED, and it reorders everything below

Done first, and the numbers invalidate the ranking this spec was written with. All figures are
`user` time, three samples each, medians quoted.

**The suite's own baseline, measured: 14:51 wall clock** (641 s user, 80% CPU) for 265 arms across
51 groups — not the ~7 minutes this spec opened by quoting from memory.

| launch | debug | release |
|---|---:|---:|
| `render`, `-f 1`, 100x100, trivial fixture | **0.41 s** | **0.36 s** |
| `render`, `-f 30`, 400x300, trivial fixture | **0.45 s** | — |
| `render`, `-f 1`, 800x600, `dir_shadow_fixture` | **0.42 s** | — |
| `render`, `-f 30`, 800x600, `dir_shadow_fixture` | **0.46 s** | — |
| `forest`, `-f 1`, 320x200 | **6.58 s** | **1.36 s** |

**A methodology note bought the hard way**: the baseline run reported one failure,
`gate-arm-docs`, and it was self-inflicted — that arm re-reads `scripts/gates.py` from disk to
check documented arm names against printed ones, and the file was being edited while the suite
ran. The other 264 arms were unaffected, since they run from the module already loaded. Do not
edit a file a running suite parses.

**Three conclusions, and two of them kill planned work.**

**1. Frames are free. The frame-count audit is worth about five seconds.** Thirty frames at
800x600 cost **0.04 s** more than one frame — 29 frames at 16x the pixels of the trivial case,
for four hundredths of a second. Across the ~130 `-f 30` launches, cutting every one to 5 saves
~5 s of a suite over 600 s. This was the spec's headline question and the answer is that it does
not matter. The audit is still worth doing for HONESTY — the file's most-repeated constant should
not be its least-justified one — but it is a documentation fix, not a speed fix, and it must be
described that way.

**2. Release does nothing for `render` and almost everything for `forest`.** The render app is
0.41 vs 0.36 (12%), because its startup is GL context plus ~37 driver-side shader compiles, which
`-O2` cannot touch. Forest is 6.58 vs 1.36 (**4.8x**), because its startup is CPU work the
optimiser does reach: procedural 1K texture bakes, 20 cluster-DAG builds, the scatter, erosion.

**3. Process count is the whole game, and it is dominated by forest.**

| | processes | debug | release | saving |
|---|---:|---:|---:|---:|
| `render` | ~284 | ~119 s | ~102 s | ~17 s |
| `forest` | ~55 | **~362 s** | **~75 s** | **~287 s** |

So the ordering is: **release build for forest (~287 s) >> removing processes (~0.4 s per render,
~6.6 s per forest) >> everything else >> frame counts (~5 s)**. Steps below are re-ordered
accordingly, and Step 3 is re-scoped from a speed change to a correctness-of-comment change.

## The re-scoping Step 0 forces

Four of the six planned steps were aimed at costs that turn out not to exist. Recorded here in
full rather than quietly dropped, because the reasoning is the useful part and a future reader
will otherwise re-file them.

| planned step | measured worth | verdict |
|---|---|---|
| Step 5 — release build for `forest` | **~287 s** | **the spec.** Everything else is rounding |
| Step 1 — drop dead `-S` screenshots | ~3 s | keep: free, and removes a readback nothing reads |
| Step 3 — the `-f 30` audit | **~5 s** | **re-scoped to documentation.** Still worth doing, but as honesty, not speed |
| Step 1 — the two retracted 1200x750 skin resolutions | ~0.3 s | **dropped.** Six renders at 0.05 s each |
| Step 2 — opt-in render memo | ~1.7 s | **dropped.** Four renders, against surgery on a 95-call-site function |
| Step 4 — `--msaa 1` on text-only runs | **~0** | **dropped.** MSAA is per-frame cost, and frames are free |

**And two structural facts that would have bitten during Step 1/2.** A cross-group duplicate
cannot be DELETED, only memoized — `--only origin` never runs the dir-shadow group, so
`org_home` must still render. And a command-keyed memo applied blindly collapses the deliberate
a/b determinism pairs (the same command run twice to MEASURE the run-to-run floor) into
`compare(x, x) == 0`, which is the inert-arm failure this cycle already shipped twice. Both are
reasons the memo is not worth 1.7 s.

**What is left, in order:** the build-type lever, one honest documentation pass over the frame
counts, the dead screenshots, and the froxel bug found on the way.

## Step 1 — dead screenshots (as built)

Five helpers wrote a `-S` capture that nothing ever opened: `_forest_run`, `_probe_render`,
`_region_run`, `_grid_tiles`, and through the first of those every profiler-reading arm. Each is a
`glReadPixels` and a file write per launch, ~55 launches. `_terrain_run` had already reached this
conclusion with the reason written down; the pattern was never propagated.

Removing them made `workdir`, `tag` and `out_name` dead in six wrappers, so those went too — the
signatures now say what the functions actually need. The four gate entry points that no longer use
`workdir` keep it, because the dispatcher calls every group as `fn(workdir)` and a uniform
interface parameter is not dead code.

**Dropped from this step**: the two retracted 1200x750 skin resolutions (~0.3 s) and capping
`_raiden_render` (measured separately — see below). Both were priced after Step 0 and neither
survives its own cost/benefit at 0.05 s per render.

## Step 2 — render memo: dropped, with the reasons recorded

Worth ~1.7 s against surgery on a 95-call-site function, and two structural facts make it worse
than the arithmetic suggests:

- **A cross-group duplicate cannot be deleted, only memoized.** `--only origin` never runs the
  dir-shadow group, so `org_home` must still render. Deletion is only available within a group.
- **A command-keyed memo applied blindly collapses the a/b determinism pairs.** Those are the same
  command run twice ON PURPOSE, to measure the run-to-run floor; served from a cache they become
  `compare(x, x) == 0` and every floor reads zero. That is the inert-arm failure this cycle
  shipped twice, bought for 1.7 s.

`_FOREST_RUN_CACHE` stays as it is — memoized on `(extra, cam)`, at one helper, where the pairs it
could collapse do not exist.

## Step 3 — frame counts: documented, not changed

Re-scoped by Step 0 from a speed change to a correctness-of-comment change, and the classification
work argued against changing the numbers at all.

`render()`'s docstring now records what the engine actually forces — that no mechanism produces
30, that without `--taa` every shared accumulator is off AND force-invalidated per frame, that a
pinned exposure imposes no requirement, that animation is a pure function of the frame index, and
that the one unconditional floor is the async loader at five uploads a frame (about two frames for
this corpus). It also records why the number is NOT lowered.

**Why not lowered.** Cutting every call site to the floor saves ~5 s of a ten-minute suite,
because a frame at 400x300 costs ~0.0013 s. Against that, `frames` is load-bearing for any arm
reading a POSE — wind travel, surf advance, an animation clip — and those arms take the shared
default. Lowering it would move them silently: the arm still passes, reading a different moment.
That is the inert-arm failure class this cycle shipped twice, and five seconds does not buy it.

The counts that ARE derived keep stating their reason where they are set: 60 (froxel and cloud
accumulators), 150 (auto-exposure, foam history), 240 and 400 (trace cadence, walk geometry).

## Step 4 — samples per pixel: dropped

`--msaa 1` on text-only launches would cut shading 4x on ~100 processes, and Step 0 says that is
worth approximately nothing: MSAA is a per-FRAME cost, frames are 0.0013 s, and the suite's time is
process startup. The documented hazard (overdraw's budget once read double under a sample-count
change) would have to be re-verified across four groups to buy that nothing. Recorded so the 16
shaded samples per requested pixel — HiDPI doubling times 4x MSAA — is not re-discovered as a
finding without also being priced.

## Step 5 — the build-type lever, as built

`--bin-dir` and `CETRA_BIN_DIR` on both scripts, and gates prints the resolved directory on every
run because which binaries a number describes is part of the result.

**gates auto-selects release by FRESHNESS**, which is the one rule that cannot test a stale
binary: release is used only when `out/release/bin/forest` is at least as new as
`out/bin/forest`. Rebuild debug and the ordering flips back on its own. `forest` is the app whose
mtime decides, because it is the app the choice is for — 4.8x against render's 1.1x.

**goldens does NOT auto-select**, and the asymmetry is the point: goldens are committed PNGs, `-O2`
changes CPU float results, and checking release frames against debug-baked goldens is a comparison
across two builds, which this repo's own rule says does not hold. Moving them requires `--rebake`
and a deliberate decision.

## Step 6 — the froxel frame-0 sentinel

`froxel_prev_frame` starts at `-1` to mean "no previous volume", and its own comment says `0` was
avoided *because it would match frame 0*. But the continuity test is
`froxel_prev_frame == frame_index - 1`, so at frame 0 it evaluates `-1 == -1` and the sentinel
matched exactly the frame it was chosen to exclude. The volume then blended against its
zero-cleared history, and the first frame's fog came out at a tenth of its converged value,
ramping up over the following dozens. `sky_clouds.c:329` has carried the `>= 0` guard all along;
`postfx.c` now does too.

Affects the cold start only, and the blast radius was measured rather than argued. Every 60-frame
fog and cloud ARM read identically (`fogvol-tint`, `fogvol-off`, `fogvol-fold`, all six
`cloudshadow-*`). Of the goldens, only `froxel_fog` moved: the two cloud goldens share the
accumulator but never had the bug, and `water_submerged` — which arms the same volume by putting
the camera under water — was unmoved too. One golden, and it was the one pinning a transient.

**The lazy-program half is NOT done, and the reason is worth recording**: it was contingent on
Step 0 showing shader compilation dominates, and Step 0 showed a `render` launch is 0.41 s of
which release recovers only 0.05 s. Compilation is a real fixed cost but it is bounded by that
0.41 s total, and no restructuring of when programs are created removes the GL context, the ImGui
context or the BRDF LUT bake alongside it. Anyone returning to this should first check
`GL_NUM_PROGRAM_BINARY_FORMATS` — on this platform it is expected to be 0, which makes a program
binary cache impossible rather than merely unhelpful.

## Verification — as run

Three full-suite runs, so each change is attributed rather than lumped:

**Baseline (debug, unmodified): 14:51.33.** **Run A (debug, modified gates.py): 14:49.13.**
Arm-by-arm against the baseline: **244 identical, 9 same-verdict-different-text, 1 verdict flip.**
Every mover is a known-noisy reading rather than a behaviour change — `gpu-dof`, `gpu-scale`,
`gpu-sum` and `prepass-crossover` are GPU timing arms the suite itself documents as drifting
between samples; `quadtree-depth` is a forest pixel count on a scene AGENTS.md records as not
pixel-deterministic; `exposure-mask` moved in its seventh decimal (-1.446326 to -1.446333). The
flip is `gate-arm-docs` FAIL to PASS, which is the baseline's self-inflicted failure clearing.

So the gates.py changes are non-behavioural, and the ~2 s delta is the dead screenshots — the
estimate was ~3 s.

**Run B (release): 10:16.85. Against run A that is 4:32 off, a 31% cut**, and against the original
baseline 14:51 to 10:17. Predicted ~287 s from the per-launch figures; measured 272 s.

**All 265 arms pass on release, with 0 verdict flips** — 241 identical, 13 moved. Ten of the
thirteen are timing or non-determinism: `gpu-dof`, `gpu-scale`, `gpu-sum`, `cpu-attrib`,
`cpu-bound`, `prepass-crossover`, `overdraw-empty` read milliseconds; `quadtree-depth`,
`quadtree-render` and `catcher` are forest/pixel counts on scenes that are not pixel-deterministic
(`quadtree-render` moved 6493 to 6494 px).

**The other three are the real `-O2` effect and are worth knowing about**: `forest-lod` reads
36,124,657 triangles against 36,122,167, `cluster-bands` 288x against 277x, `cluster-parity` 2.8%
against 2.7% drift. meshoptimizer makes marginally different collapse decisions under `-O2`, so
**a LOD chain and a cluster DAG are build-type-dependent**. The control is exact: `--no-lod`'s
65,098,553 triangles is *identical* in both, so what moved is the simplifier's arithmetic and not
the geometry it was given. Every one stays well inside its bar — 2.7% against a 6% limit, 277x
against an 8x floor.

**Consequence to carry: forest triangle counts are not comparable across build types.** Every run
prints the binaries it used, which is what makes that checkable rather than a trap.



```bash
python3 scripts/gates.py                              # baseline: debug, unmodified
python3 scripts/gates.py --bin-dir out/bin            # isolates the gates.py edits
./build.sh --release
python3 scripts/gates.py --bin-dir out/release/bin    # isolates the build type
python3 scripts/goldens.py                            # 25/25 at 0 px, DEBUG (goldens do not move)
```

The bar is that **arm output text is unchanged where the arm did not change** — the same numbers,
not merely the same verdicts. A gate whose reported measurement moved because it now renders
fewer frames is a gate that was measuring the frame count.

**Release is expected to move SOME numbers and that is not automatically a failure.** `-O2`
changes CPU float results, so any arm reading a computed float may shift in its last digits. Each
one that moves gets checked against its stated tolerance and recorded; an arm that moves outside
its bar is a real finding about that bar, since every digest comparison in the suite is
within-run and should be unaffected by construction.

`--bin-dir out/bin` remains the way to reproduce a debug-referenced result, and goldens stay on
debug until someone deliberately re-bakes them.
