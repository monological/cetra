# Post-11.60 cleanup: three refactors the review asked for and 11.60 deferred

## Context

Spec 11.60's review raised three structural findings that were real but separable from the feature,
so they were recorded and left. Each is mechanical, each is independently verifiable, and each has a
concrete reason beyond tidiness:

1. **`MaterialMaskArray` now holds albedo.** The type is a `GL_TEXTURE_2D_ARRAY` of a scene's unique
   per-texel material textures. It was named for the six masks it was built for; 11.60 put layer
   albedo/surface maps and a splat in it. An albedo is not a mask under any reading — the name went
   from narrow to **false**, and it took a 16-line header comment to explain that. That comment is a
   rename in prose form.
2. **`create_material` hand-assigns ~50 fields after a `malloc`.** Nothing enforces completeness, and
   that is not hypothetical: it is the bug that shipped in 11.60. A field added without a matching
   line gave the shader a garbage `layer_count` and `free_material` junk pointers to release — after
   the screenshot was written, so **21 goldens reported a render failure with a correct image on
   disk**.
3. **Two apps carry the same six-line texture-bake helper**, and 11.60 added five call sites to one
   of them. What it encodes is a fact about `texture.c` — the pool does not keep your pixels — which
   the header does not state anywhere.

**Three commits, in this order.** The rename is large enough that mixing it with anything else makes
the diff unreadable.

---

## 1. `MaterialMaskArray` → `MaterialTextureArray`

Pure rename. No behaviour change, no signature change beyond names.

| from | to |
|---|---|
| `MaterialMaskArray` | `MaterialTextureArray` |
| `mask_array.c` / `.h` | `material_texture_array.c` / `.h` |
| `create_material_mask_array` / `free_material_mask_array` | `create_material_texture_array` / `free_material_texture_array` |
| `mask_array_build` / `_bind` / `_ensure_built` | `material_texture_array_build` / `_bind` / `_ensure_built` |
| `mask_array_alloc_dummy`, `mask_layer_for` | `material_texture_array_alloc_dummy`, `material_texture_layer_for` |
| `MASK_ARRAY_CAP` | `MATERIAL_TEXTURE_ARRAY_CAP` |
| `Scene.mask_array` / `.mask_array_dirty` | `Scene.material_textures` / `.material_textures_dirty` |
| `TEXUNIT_MASKS` | `TEXUNIT_MATERIAL_ARRAY` |
| GLSL `uniform sampler2DArray maskArray` | `materialArray` |
| guard `_MASK_ARRAY_H_` | `_MATERIAL_TEXTURE_ARRAY_H_` |

`TEXTURES_PER_MATERIAL` already reads correctly — leave it.

**Files:** `cetra/src/mask_array.[ch]` (renamed), `scene.[ch]`, `render.c`, `engine.c`, `common.h`,
`cetra/shaders/pbr_frag.glsl`, `apps/render/src/cscene_apply.c`.

### The four things that are not a blind find-and-replace

- **`render.c:500` is the dangerous site.** `uniform_set_int(u, "maskArray", TEXUNIT_MASKS)` couples a
  C string literal to a GLSL identifier with **no compiler check**. Renaming one side alone leaves
  the sampler defaulted to unit 0 — where a `sampler2D` lives, which `render.c:474-483` already
  measures as a whole-program undefined-behaviour hazard worth 62,009 px. Both sides move together.
- **Delete two includes rather than renaming them.** `gi_volume.c:8` and `probe.c:7` include
  `mask_array.h` and use **no symbol from it** — the only occurrence of "mask" in either file. Drop
  the include; do not carry a dead dependency into the new name.
- **`scene.h:192` uses `struct MaterialMaskArray*` as an incomplete type** and never includes the
  header. It stays incomplete; only the tag changes.
- **Two paragraphs argue AGAINST this rename and must be inverted, not edited**:
  `cetra/src/mask_array.h:18-24` and `AGENTS.md:570-576`. Both cite the `anisotropy_tex` precedent
  (11.20). The correction to record: that precedent does not transfer, because `anisotropy_tex`'s
  declared contract — per-texel grain direction — is *still true* of a hair strand map. The name
  narrowed. This one became untrue.

### Deliberately out of scope

- **`mask_copy` / `mask_copy_frag` / `create_mask_copy_program` stay.** It is a general
  fullscreen-quad blit (`texture(src, TexCoords)`) that happens to be used to fill array layers — a
  mild misnomer with no contract attached. It also has two silent-failure couplings a rename would
  have to get exactly right: the shader symbol `mask_copy_frag_shader_str` is generated *from the
  filename*, and `"mask_copy"` is a runtime string matched between `program.c:737` and the array
  build. Not worth it in the same commit.
- **`specs/*.md` are not touched.** Fourteen spec files mention these identifiers; they are dated
  records of what was true when written, and rewriting them would falsify the history. **`AGENTS.md`
  (7 lines) and `docs/aaa-rendering-roadmap.md` (13 lines) ARE updated** — those are living.
- **`TEXUNIT_MASKS` has no `_Static_assert`** (units 0/1/2 are unasserted; the chain at
  `render.c:40-62` starts at `TEXUNIT_CLEARCOAT_NORMAL`). Nothing to keep in step.

### Build note

`cetra/CMakeLists.txt:64` globs `src/*.c`, so the `.c` rename needs no edit — but `:26-35` generates a
forwarding public header per `src/*.h`, and per its own comment a **new header name requires a
reconfigure**. `./build.sh` does that anyway. No app includes `<cetra/mask_array.h>` today.

## 2. `create_material`: a designated-initialiser template

Follow the house form, which already exists: `cetra/src/water.c:74-98` declares
`WATER_DEFAULT_WIND_SEA` / `WATER_DEFAULT_SWELL` as `static const T NAME = { .field = ... }` with a
`//` comment per field, and applies them by plain struct assignment at `:454-455`. The reasoning at
`water.c:67-72` argues explicitly for `static const` over a compound-literal macro. Same shape here.

```c
static const Material MATERIAL_DEFAULTS = { .albedo = {1,1,1}, .roughness = 1.0f, ... };

Material* create_material(void) {
    Material* m = malloc(sizeof *m);
    if (!m) { log_error(...); return NULL; }
    *m = MATERIAL_DEFAULTS;
    m->id = g_next_material_id++;
    for (int i = 0; i < STOCHASTIC_LUT_SIZE; i++) { ... }   // the one derived table
    return m;
}
```

**~25 non-zero defaults survive as designated initialisers** — `albedo` (1,1,1), `ior` 1.5,
`specular_factor` −1, `subsurface_color` (1, 0.3, 0.2), `subsurface_profile` −1, the six mask
`*_layer` −1 sentinels, `splat_layer` −1, `splat_size` (1,1), the four `layers[]` entries
(`uv_scale` 1, both indices −1), `layer_blend_sharpness` 0.5, `layer_triplanar_sharpness` 4.0, and
the rest. **~44 zero/NULL/false assignments are deleted** and left to C's zero-init rules, which is
the whole point: a field added later is initialised **by the language rather than by memory**.

Two things cannot be initialisers and stay as post-assignments:

- **`id = g_next_material_id++`** is per-instance, not a default.
- **`stochastic_lut`** is 192 computed floats — entry `i` is `(i + 0.5)/64` replicated across three
  components. C has no initialiser-list arithmetic; the alternative is 192 literals. It stays a loop,
  which is honest: it is a derived table, not a default.

**The hazard to respect:** the allocation stays `malloc`, so this is only safe because `*m =
MATERIAL_DEFAULTS` writes the *whole* object. Dropping the zero assignments while keeping
field-by-field writes would leave ~44 fields indeterminate. The struct assignment is load-bearing and
should say so.

**Verified before planning:** there is no hole today (all 71 `Material` fields and all 5 fields of
each of the 4 `MaterialLayer` slots are assigned), `free_material` releases all 16 texture pointers
across *all* layer slots rather than `layer_count` of them, and `create_material` is the **only**
construction path — 16 call sites, no `malloc(sizeof(Material))` anywhere else.

## 3. One texture-bake helper, in the library

`apps/forest/src/forest.c:420-427` (`bake`, 9 calls) and `apps/tree/src/tree.c:75-83`
(`bake_texture`, 11 calls) are **byte-identical modulo names**. Move one copy into `cetra/src/texture.[ch]`
beside `load_texture_from_memory` (declaration slot: `texture.h:140`, before `remove_texture_from_pool`):

```c
// Upload a CPU buffer through the pool and FREE it. The pool keeps no pixels --
// glTexImage2D takes GL's own copy and Texture stores no pointer -- so the
// buffer is dead the moment this returns, which is what every procedural bake
// wants and what the header did not say anywhere.
// NULL `pixels` returns NULL, so a generator that failed needs no guard at the
// call site.
Texture* load_texture_from_memory_owned(TexturePool* pool, const char* key, unsigned char* pixels,
                                        int width, int height, int channels, bool is_srgb);
```

**Signature note:** `texture.h` does not know `Scene` (it includes only glew, stdbool, uthash,
thread.h). Both existing helpers take `Scene*` and immediately dereference `scene->tex_pool`, so the
shared one takes `TexturePool*` and all 20 call sites pass `scene->tex_pool`.

Delete both app-local helpers.

### Three call sites that need care

- **`forest.c:494` splits ownership**: `splat` is caller-`malloc`'d, freed by the helper on success
  and by the caller at `:496` on failure. It is the only call whose buffer is not produced inline by
  a generator. Preserve both legs exactly.
- **`tree.c:149-152`** relies on the NULL guard: `sand_alb` may be NULL, is mutated in place by
  `stochastic_gaussianize`, and `sand_stochastic_ready` is derived from it before the bake consumes
  it.
- **`tree.c:71-74`'s doc comment is now wrong** and must not be carried over verbatim. It cites the
  transparent-texel dilate as a reason to use the helper; 11.60 gated that dilate on `is_srgb`, and
  **2 of forest's 9 calls pass `channels=4, srgb=false` precisely to bypass it** — layer alpha is a
  HEIGHT, not an opacity.

**`import.c:509` is deliberately left alone.** It is a third malloc-upload-free dance but cannot
share this helper: it uses `stbi_image_free` rather than `free`, its buffer is sometimes *borrowed*
from Assimp and must not be freed at all, and it does its own pool pre-check.

# AS BUILT

All three shipped as planned, in three commits, each **25 goldens at 0 px**. The plan's inventory
held: no site was missed, and nothing turned out to be load-bearing that the survey had called
mechanical.

## The rename's verification was better than pixels, and that is the transferable part

The generated GLSL is reproducible, so `out/include/cetra/shader_strings.h` before and after is a
direct statement about what the shader source became. It diffs **20 lines, and every one of them is
`maskArray` → `materialArray`**. That is a stronger claim than 0 px: pixels say the frame did not
move, where this says the shader *text* did not move except where intended. For a pure rename it is
the right instrument, and it costs one `cp` before the edit.

## What the plan got right by looking first

- **`gi_volume.c` and `probe.c` included the header and used no symbol from it.** Renaming those
  includes would have carried a dead dependency into the new name; they were deleted instead.
- **`render.c`'s `uniform_set_int(u, "maskArray", ...)` has no compiler check.** Moving the C string
  without the GLSL identifier leaves the sampler defaulted to unit 0, where a `sampler2D` lives —
  undefined for the whole program, and already measured at 62,009 px elsewhere in that file. Both
  moved in one edit.
- **`mask_copy` stayed.** Its shader symbol is generated *from the filename* and its program name is
  a runtime string matched across two files, so a rename there has two silent-failure modes and buys
  a mild misnomer with no contract attached.

## The one thing the plan did not anticipate

**The bake helper's argument order.** Both app-local helpers put `key` LAST; the library function it
wraps puts it SECOND. A `replace_all` on the call name produced nine call sites with `key` and
`pixels` transposed — caught immediately by the compiler as an int-to-pointer conversion, not
silently, because the two parameters have incompatible types.

That is worth recording as luck rather than design. Had the transposed pair been two `int`s — say
`width` and `channels` — it would have compiled clean and rendered a plausible texture. The lesson is
narrow and useful: **a mechanical rename is only mechanical when the signature is unchanged.** Here
the signature changed, so it was nine hand edits wearing a rename's clothes.

The order still follows `load_texture_from_memory` rather than the apps' old convention, which is the
right call for a wrapper: a reader who knows the wrapped function knows this one.

## Measurements

- Rename: 17 files, **+181 / −165**, and the generated GLSL identical modulo the one identifier.
- `create_material`: **−91 lines**. Twenty-seven non-zero defaults survive as designated
  initialisers, checked field by field against the old list before building; ~44 zero assignments are
  now the language's job.
- Bake helper: 20 call sites collapsed onto one library function, and forest's array logs **11 layers
  at 2048x1024, 117.3 MB** — unchanged, which is what says the 20 moves were faithful.

## The generalisable part

Two of the three exist because **a comment was doing a job the code should have done**. The array's
header spent sixteen lines explaining that its name meant something other than what it said;
`create_material` carried a comment telling the next person to remember a rule nothing enforced —
and that rule had already been broken once, in the spec immediately before this one.

The test that separates the two cases is whether the prose is recording something the code *cannot*
express. A rejected alternative, a measured tradeoff, a failure mode being avoided: those earn their
length. **"This name does not mean what it says" and "remember to add a line here" are both the code
asking to be changed instead.**
