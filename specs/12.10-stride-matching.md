# Spec 12.10 — Stride matching

## Context

Spec 12.9 shipped foot locking and exposed something worth more than the feature. `gametest`'s
player travels at `PLAYER_SPEED` 10 m/s on a rig whose walk clip implies 0.95, so no contact is
ever labelled, no lock ever forms, and the frame is **0 px** against `--no-lock`. The roadmap
(`docs/game-engine-roadmap.md`, Part 3 item 6) now calls matching travel speed to clips "the
nearest thing to a blocker in this list", and `docs/foot-locking.md`'s last section says the same
under "What the demo cannot show".

Locking only works where the clip's feet are already moving at roughly the speed the ground is.
Stride matching is what makes that true at every speed: measure the ground speed a clip's own feet
imply, then play it at `wanted / implied`. Without it, locking is a feature with one working
operating point.

**One premise of the request is already satisfied and the spec is smaller for it.**
`Animator.speed` exists (`cetra/src/animator.h:118`, default `1.0f`, set at `animator.c:32`). It
multiplies the base space clock, the live outgoing clock and the override layer clock
(`animator.c:474-489`) and deliberately does **not** scale the fade envelopes — `animator.h:29`
states that contract. `apps/render` already has a GUI slider on it and `save.c` already serialises
it. Nothing needs adding. What is missing is the **denominator**: nothing anywhere in the engine
knows how far a clip's feet travel. Grep confirms it — `Animation` carries `name`, `duration`,
`ticks_per_second`, `channels`, `events`, `skeleton` and nothing spatial; the only stride
measurement in the tree is app-local, inside the gametest probe.

Outcome: a stance foot stays planted at any travel speed the clips can honestly carry, not only
near 1 m/s.

## Design

### The measurement lives in `animation.c`, and it is allowed to refuse

`--ik-probe lock` already does this fit (`apps/gametest/src/gametest.c:3972-4005`): least squares
on the stance toe's XZ against tick index over a contact window, scaled to m/s. It is correct and
its comment records why the endpoint form was wrong (a foot that rocks at heel-strike moves the
endpoints without moving the average, and read a stride 2x short). It is also entangled — it
writes six variables the probe's other three passes read, and interleaves nine `printf`s. Lift the
arithmetic, not the code around it.

```c
// animation.h
// The ground speed this clip's own feet imply, in MODEL units per second at playback rate 1,
// and the direction the body travels to make it so (may be NULL). False when the clip does not
// walk -- which is a real answer and not a failure.
bool animation_stride_speed(const Animation* clip, const Skeleton* skeleton,
                            const int ankle[2], const int toe[2],
                            float* out_speed, vec3 out_dir);
```

**Model units, and the caller owns the scale.** This is 12.9's live bug restated: the solver's
world/model confusion cost a silently halved `unlock_distance` that no arm could see, because the
probe runs at scale 1 and `gametest` carries `PLAYER_SCALE 2`. The same seam is here. The header
says MODEL in the contract line; `gametest` multiplies by `PLAYER_SCALE` at the one call site.

**The refusal is the interesting half.** The generated puppet's walk is a straight-leg pendulum —
`gait()` (`assets/generators/gen_puppet_fixture.py:185`) swings the thigh as `A·cos(p)` with no
knee bend, so each ankle is LOWEST at mid-swing where it is moving FASTEST, and both ankles reach
their minimum at the same instant. Run naively, the probe's window rule picks a mid-swing window
and the fit returns a plausible magnitude in the **wrong direction** — a silently wrong number,
which is worse than none. Four cheap tests over data already collected refuse it:

- each foot lifts at all (`lift > eps`);
- **exactly one** stance window per foot per loop;
- the two windows are antiphase (`|Δφ − 0.5| < 0.15`) — this is the test `gait()` fails, since
  both its feet bottom out together;
- the two fitted slopes agree in direction and in magnitude.

**Sample two loops, not one.** A stance straddling the loop point reads as two runs in a linear
scan, and `ik_probe_longest_run` (`gametest.c:3420`) is linear. Two loops, require two runs, take
the middle one — which also pairs the feet cleanly for the antiphase test.

There is no public pose-to-globals helper (`skeleton_compute_bind_globals` is bind-only), so this
needs its own parent-first accumulation over `animation_sample_pose`'s output — the loop
`animation_state_apply_pose` already runs internally. Hoist or copy, ~12 lines either way.

### The blended query lives in `animator.c`, because only it can be right

`AnimatorEntry` gains one field:

```c
typedef struct AnimatorEntry {
    const Animation* clip;
    float position;
    float stride; // ground speed this entry implies at rate 1, in the param axis's own units;
                  // 0 = unknown
} AnimatorEntry;
```

All six construction sites in the tree are brace initialisers with two fields
(`render.c:2004`, `gametest.c:2418-2420`, `:4327`, `:4403`, `:4425`), so every one stays valid C
and gets `stride = 0` — "unknown", which is the behaviour they have today. Nothing else changes.

```c
// The ground speed the playing pose implies at speed 1, blended the way the pose is.
// 0 when any weighted entry has no stride.
float animator_stride_speed(const Animator* animator);
```

**This cannot be done from outside the engine, which is why it is in here.** The space keeps ONE
clock in the ticks of the reference entry (`animator.h:52`) and advances it by
`dt * tps_ref * speed * rate` where `rate = Σ wᵢ·(ref_seconds/secᵢ)` (`animator.c:113-122`). Write
φ for the phase fraction; then `dφ/dt = speed · Σ wᵢ/secᵢ`, and the blended pose covers
`Σ wᵢ·strideᵢ·secᵢ` of ground per unit φ. So the quantity a caller actually needs is

```
(Σ wᵢ·strideᵢ·secᵢ) · (Σ wⱼ/secⱼ)
```

which collapses to `Σ wᵢ·strideᵢ` only when every clip is the same length. A game dividing by the
weighted mean of the strides is wrong the moment its walk and run clips differ in duration, and it
is wrong by an amount that looks like a tuning problem. **Phase 2's arm tests this empirically —
commanded speed in, measured foot travel out — rather than asserting the algebra.**

### `gametest` gets a blend axis in metres per second

Today the knob is `ground_speed / PLAYER_SPEED` with entries at 0 / 0.5 / 1
(`gametest.c:2674`, `:2418-2420`). Once the strides are known, the entries sit at their own
measured speeds and the knob is `param = ground_speed` — an absolute axis. Two things fall out:

- `speed = clamp(ground_speed / animator_stride_speed(a), RATE_MIN, RATE_MAX)` stays near 1 inside
  the covered range and does the stretching outside it.
- **The `--speed` normalisation bug disappears rather than being fixed.** `gametest.c:2669-2673`
  carries a five-line comment explaining that the knob must divide by the compile-time
  `PLAYER_SPEED` and not by the `--speed` cap, or the gear re-normalises and `--speed` becomes
  useless for the one thing it is for. On an absolute axis there is no gear to re-normalise. The
  comment and the coupling both go.

**Full stick becomes what the clips can honestly carry**: `player_speed = top_entry_stride *
RATE_MAX`, derived at init unless `--speed` overrode it. On `t_pose.fbx` + `strut_walk` that is
about 3.0 m/s against today's 10.

**Two constants are secretly ratios and must become ratios**, or the demo breaks the moment
`player_speed` moves: `CHASER_SPEED 6.0f` (`:170`) and `GROTTO_SWIM_SPEED 4.0f` (`:459`, whose own
comment reads "against PLAYER_SPEED 10: a swimmer is not a runner"). At a derived 3.0 m/s the
chaser outruns the player and swimming is faster than running. Both become fractions of the live
`player_speed`.

**When a clip refuses, say so and keep today's behaviour.** The generated puppet's clips will
refuse, so the bare `./out/bin/gametest` keeps its 0 / 0.5 / 1 axis, `PLAYER_SPEED` 10 and
`speed = 1`. One `if`, and one printed line naming the clip — spec 11.107's rule. That line is the
runtime documentation of the limitation, seen by whoever runs it.

### Decisions already taken (do not relitigate)

- **`gait()` is not being given a stance phase.** The look happens on
  `--puppet assets/models/t_pose.fbx`, which already falls back to `strut_walk.fbx`
  (`gametest.c:2399-2410`) — a real humanoid with a real stance, both committed. That also settles
  the "real character judged by eye" `docs/verification.md` has owed since 12.1. A compass gait for
  the generated puppet is its own piece of work and would cost a regenerate, a `puppet_golden`
  re-bake and `ik-swing`'s band re-argued.
- **Full stick matches the fastest clip**, not the other way round.
- **No new assets.** Mixamo Idle/Running would slot into the same axis with no code change; the
  spec does not wait for them.

## Phases

Branch `12.10-stride-matching` off master; spec committed first, on its own, before any code.
Each phase ends with its arms green and the app run where the phase changed what it draws.

**Phase 0 — look at it, then build the arm that is red.** Before any engine change:
`./out/bin/gametest --puppet assets/models/t_pose.fbx`, walked at a stick deflection near the
clip's stride, at a third of it, and at full. Record what each looks like. Then give
`--ik-probe lock` a travel-speed multiplier and print the stance slide at **0.5x, 1x and 2x** the
clip's own stride; add `ik-slide-speeds` asserting the bar at all three. **It must be red at 0.5x
and 2x today.** That arm is the entire claim of this spec; an arm that cannot fail now proves
nothing later.

**Phase 1 — the measurement.** `animation_stride_speed` in `animation.c`, with the four refusal
tests and the two-loop sampling. Arm `anim-stride`: on `strut_walk.fbx` it agrees with the probe's
own independent fit to within a stated tolerance (two code paths, one quantity — agreement is the
check), and on the generated `walk` it **refuses**.

**Phase 2 — the blended query.** `AnimatorEntry.stride`, `animator_stride_speed`. Arm `anim-rate`:
set `speed` from the helper at a mid-blend `param` across two clips of **different duration**, tick
a cycle, and measure the actual stance-foot travel per second — it must equal the commanded speed.
The weighted-mean shortcut fails this arm; that is why it exists.

**Phase 3 — `gametest` drives it, and the look.** Measure the three clips at init; on success place
entries at their world strides, set `param = ground_speed`, set `speed` from the clamp, derive
`player_speed`, and make `CHASER_SPEED`/`GROTTO_SWIM_SPEED` fractions of it. On refusal print once
and keep today's axis. Delete the `--speed` normalisation comment and its coupling. **Then run it**
— `--puppet assets/models/t_pose.fbx` at a walk, at a stop, at a turn, and against `--no-lock`.
Phase 0's arm turns green.

**Phase 4 — the scale blind spot.** 12.9 shipped a world-space distance compared against a
model-space threshold, live at `PLAYER_SCALE 2`, and no arm could see it because the probe runs at
scale 1. The model-to-world stride conversion is the same seam. Add a lock-probe pass at rig scale
2 and assert the slide bar holds there too.

**Phase 5 — the docs.** `docs/foot-locking.md`'s "What the demo cannot show" section is now
answered and says so. `docs/verification.md` (the IK section's owed items, and the 12.1 "real
character" debt Phase 0 discharges), `AGENTS.md`'s `animator.c/h` and `ik.c/h` rows and the
`gametest` table row, `docs/cli-reference.md` for `--speed`'s changed meaning, and
`docs/game-engine-roadmap.md` — item 6's tail and the intro paragraph that calls this a blocker.

## Verification

Scoped per phase, not the full suite:

```bash
python3 scripts/gates.py --only anim     # phases 1, 2
python3 scripts/gates.py --only ik       # phases 0, 3, 4
```

End of job: `./build.sh`, the full `gates.py`, `goldens.py`. **No golden should move** — no asset
changes, no render-path changes, and the player is idle at startup in both menu goldens, so `param`
is 0 on either axis. Assert 0 px rather than re-baking; a non-zero here means something reached the
frame that should not have.

**The numbers that decide it**, not a green suite:

- `ik-slide-speeds`: the stance slide at 0.5x / 1x / 2x the clip's stride. 12.9's headline was
  0.0034 m at 1x; this spec is the claim that the other two land near it.
- `animation_stride_speed` on `strut_walk.fbx` against the probe's 0.95 m/s.
- `animator_stride_speed` against measured foot travel at mid-blend.

**The watch**, which no arm replaces:

```bash
./out/bin/gametest --puppet assets/models/t_pose.fbx            # walk, stop, turn
./out/bin/gametest --puppet assets/models/t_pose.fbx --no-lock  # the two told apart
./out/bin/gametest                                              # the refusal path, and its printed line
```

## Out of scope

- **Root motion.** The other answer to the same problem, and a larger one — it inverts the
  ownership, making the clip drive the controller rather than the controller drive the clip.
- **A stance phase for `gait()`.** Decided above; its own piece of work.
- **2D blend spaces / strafe sets.** The axis here is forward speed. A turn stops sliding because
  the lock pins the foot, not because anything is matched laterally, and the spec should say that
  precisely rather than claiming more.
- **Authored stride as clip metadata.** The runtime measurement needs no asset format change.
