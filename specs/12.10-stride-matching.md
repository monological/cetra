# Spec 12.10 — Stride matching

## Context

Spec 12.9 shipped foot locking and exposed something worth more than the feature. `gametest`'s
player travels at `PLAYER_SPEED` 10 m/s on a rig whose walk clip implies 0.95, so no contact is
ever labelled, no lock ever forms, and the frame is **0 px** against `--no-lock`. The roadmap
(`docs/game-engine-roadmap.md`, Part 3 item 6) now calls matching travel speed to clips "the
nearest thing to a blocker in this list", and `docs/foot-locking.md`'s last section says the same
under "What the demo cannot show".

Locking only works where the clip's feet are already moving at roughly the speed the ground is.
Stride matching is what makes that true at every speed: measure the ground speed a clip's own feet
imply, then play it at `wanted / implied`. Without it, locking is a feature with one working
operating point.

**One premise of the request is already satisfied and the spec is smaller for it.**
`Animator.speed` exists (`cetra/src/animator.h:118`, default `1.0f`, set at `animator.c:32`). It
multiplies the base space clock, the live outgoing clock and the override layer clock
(`animator.c:474-489`) and deliberately does **not** scale the fade envelopes — `animator.h:29`
states that contract. `apps/render` already has a GUI slider on it and `save.c` already serialises
it. Nothing needs adding. What is missing is the **denominator**: nothing anywhere in the engine
knows how far a clip's feet travel. Grep confirms it — `Animation` carries `name`, `duration`,
`ticks_per_second`, `channels`, `events`, `skeleton` and nothing spatial; the only stride
measurement in the tree is app-local, inside the gametest probe.

Outcome: a stance foot stays planted at any travel speed the clips can honestly carry, not only
near 1 m/s.

## Design

### The measurement lives in `animation.c`, and it is allowed to refuse

`--ik-probe lock` already does this fit (`apps/gametest/src/gametest.c:3972-4005`): least squares
on the stance toe's XZ against tick index over a contact window, scaled to m/s. It is correct and
its comment records why the endpoint form was wrong (a foot that rocks at heel-strike moves the
endpoints without moving the average, and read a stride 2x short). It is also entangled — it
writes six variables the probe's other three passes read, and interleaves nine `printf`s. Lift the
arithmetic, not the code around it.

```c
// animation.h
// The ground speed this clip's own feet imply, in MODEL units per second at playback rate 1,
// and the direction the body travels to make it so (may be NULL). False when the clip does not
// walk -- which is a real answer and not a failure.
bool animation_stride_speed(const Animation* clip, const Skeleton* skeleton,
                            const int ankle[2], const int toe[2],
                            float* out_speed, vec3 out_dir);
```

**Model units, and the caller owns the scale.** This is 12.9's live bug restated: the solver's
world/model confusion cost a silently halved `unlock_distance` that no arm could see, because the
probe runs at scale 1 and `gametest` carries `PLAYER_SCALE 2`. The same seam is here. The header
says MODEL in the contract line; `gametest` multiplies by `PLAYER_SCALE` at the one call site.

**The refusal is the interesting half.** The generated puppet's walk is a straight-leg pendulum —
`gait()` (`assets/generators/gen_puppet_fixture.py:185`) swings the thigh as `A·cos(p)` with no
knee bend, so each ankle is LOWEST at mid-swing where it is moving FASTEST, and both ankles reach
their minimum at the same instant. Run naively, the probe's window rule picks a mid-swing window
and the fit returns a plausible magnitude in the **wrong direction** — a silently wrong number,
which is worse than none. Four cheap tests over data already collected refuse it:

- each foot lifts at all (`lift > eps`);
- **exactly one** stance window per foot per loop;
- the two windows are antiphase (`|Δφ − 0.5| < 0.15`) — this is the test `gait()` fails, since
  both its feet bottom out together;
- the two fitted slopes agree in direction and in magnitude.

**Sample two loops, not one.** A stance straddling the loop point reads as two runs in a linear
scan, and `ik_probe_longest_run` (`gametest.c:3420`) is linear. Two loops, require two runs, take
the middle one — which also pairs the feet cleanly for the antiphase test.

There is no public pose-to-globals helper (`skeleton_compute_bind_globals` is bind-only), so this
needs its own parent-first accumulation over `animation_sample_pose`'s output — the loop
`animation_state_apply_pose` already runs internally. Hoist or copy, ~12 lines either way.

### The blended query lives in `animator.c`, because only it can be right

`AnimatorEntry` gains one field:

```c
typedef struct AnimatorEntry {
    const Animation* clip;
    float position;
    float stride; // ground speed this entry implies at rate 1, in the param axis's own units;
                  // 0 = unknown
} AnimatorEntry;
```

All six construction sites in the tree are brace initialisers with two fields
(`render.c:2004`, `gametest.c:2418-2420`, `:4327`, `:4403`, `:4425`), so every one stays valid C
and gets `stride = 0` — "unknown", which is the behaviour they have today. Nothing else changes.

```c
// The ground speed the playing pose implies at speed 1, blended the way the pose is.
// 0 when any weighted entry has no stride.
float animator_stride_speed(const Animator* animator);
```

**This cannot be done from outside the engine, which is why it is in here.** The space keeps ONE
clock in the ticks of the reference entry (`animator.h:52`) and advances it by
`dt * tps_ref * speed * rate` where `rate = Σ wᵢ·(ref_seconds/secᵢ)` (`animator.c:113-122`). Write
φ for the phase fraction; then `dφ/dt = speed · Σ wᵢ/secᵢ`, and the blended pose covers
`Σ wᵢ·strideᵢ·secᵢ` of ground per unit φ. So the quantity a caller actually needs is

```
(Σ wᵢ·strideᵢ·secᵢ) · (Σ wⱼ/secⱼ)
```

which collapses to `Σ wᵢ·strideᵢ` only when every clip is the same length. A game dividing by the
weighted mean of the strides is wrong the moment its walk and run clips differ in duration, and it
is wrong by an amount that looks like a tuning problem. **Phase 2's arm tests this empirically —
commanded speed in, measured foot travel out — rather than asserting the algebra.**

### `gametest` gets a blend axis in metres per second

Today the knob is `ground_speed / PLAYER_SPEED` with entries at 0 / 0.5 / 1
(`gametest.c:2674`, `:2418-2420`). Once the strides are known, the entries sit at their own
measured speeds and the knob is `param = ground_speed` — an absolute axis. Two things fall out:

- `speed = clamp(ground_speed / animator_stride_speed(a), RATE_MIN, RATE_MAX)` stays near 1 inside
  the covered range and does the stretching outside it.
- **The `--speed` normalisation bug disappears rather than being fixed.** `gametest.c:2669-2673`
  carries a five-line comment explaining that the knob must divide by the compile-time
  `PLAYER_SPEED` and not by the `--speed` cap, or the gear re-normalises and `--speed` becomes
  useless for the one thing it is for. On an absolute axis there is no gear to re-normalise. The
  comment and the coupling both go.

**Full stick becomes what the clips can honestly carry**: `player_speed = top_entry_stride *
RATE_MAX`, derived at init unless `--speed` overrode it. On `t_pose.fbx` + `strut_walk` that is
about 3.0 m/s against today's 10.

**Two constants are secretly ratios and must become ratios**, or the demo breaks the moment
`player_speed` moves: `CHASER_SPEED 6.0f` (`:170`) and `GROTTO_SWIM_SPEED 4.0f` (`:459`, whose own
comment reads "against PLAYER_SPEED 10: a swimmer is not a runner"). At a derived 3.0 m/s the
chaser outruns the player and swimming is faster than running. Both become fractions of the live
`player_speed`.

**When a clip refuses, say so and keep today's behaviour.** The generated puppet's clips will
refuse, so the bare `./out/bin/gametest` keeps its 0 / 0.5 / 1 axis, `PLAYER_SPEED` 10 and
`speed = 1`. One `if`, and one printed line naming the clip — spec 11.107's rule. That line is the
runtime documentation of the limitation, seen by whoever runs it.

### Decisions already taken (do not relitigate)

- **`gait()` is not being given a stance phase.** The look happens on
  `--puppet assets/models/t_pose.fbx`, which already falls back to `strut_walk.fbx`
  (`gametest.c:2399-2410`) — a real humanoid with a real stance, both committed. That also settles
  the "real character judged by eye" `docs/verification.md` has owed since 12.1. A compass gait for
  the generated puppet is its own piece of work and would cost a regenerate, a `puppet_golden`
  re-bake and `ik-swing`'s band re-argued.
- **Full stick matches the fastest clip**, not the other way round.
- **No new assets.** Mixamo Idle/Running would slot into the same axis with no code change; the
  spec does not wait for them.

## Phases

Branch `12.10-stride-matching` off master; spec committed first, on its own, before any code.
Each phase ends with its arms green and the app run where the phase changed what it draws.

**Phase 0 — look at it, then build the arm that is red.** Before any engine change:
`./out/bin/gametest --puppet assets/models/t_pose.fbx`, walked at a stick deflection near the
clip's stride, at a third of it, and at full. Record what each looks like. Then give
`--ik-probe lock` a travel-speed multiplier and print the stance slide at **0.5x, 1x and 2x** the
clip's own stride; add `ik-slide-speeds` asserting the bar at all three. **It must be red at 0.5x
and 2x today.** That arm is the entire claim of this spec; an arm that cannot fail now proves
nothing later.

**Phase 1 — the measurement.** `animation_stride_speed` in `animation.c`, with the four refusal
tests and the two-loop sampling. Arm `anim-stride`: on `strut_walk.fbx` it agrees with the probe's
own independent fit to within a stated tolerance (two code paths, one quantity — agreement is the
check), and on the generated `walk` it **refuses**.

**Phase 2 — the blended query.** `AnimatorEntry.stride`, `animator_stride_speed`. Arm `anim-rate`:
set `speed` from the helper at a mid-blend `param` across two clips of **different duration**, tick
a cycle, and measure the actual stance-foot travel per second — it must equal the commanded speed.
The weighted-mean shortcut fails this arm; that is why it exists.

**Phase 3 — `gametest` drives it, and the look.** Measure the three clips at init; on success place
entries at their world strides, set `param = ground_speed`, set `speed` from the clamp, derive
`player_speed`, and make `CHASER_SPEED`/`GROTTO_SWIM_SPEED` fractions of it. On refusal print once
and keep today's axis. Delete the `--speed` normalisation comment and its coupling. **Then run it**
— `--puppet assets/models/t_pose.fbx` at a walk, at a stop, at a turn, and against `--no-lock`.
Phase 0's arm turns green.

**Phase 4 — the scale blind spot.** 12.9 shipped a world-space distance compared against a
model-space threshold, live at `PLAYER_SCALE 2`, and no arm could see it because the probe runs at
scale 1. The model-to-world stride conversion is the same seam. Add a lock-probe pass at rig scale
2 and assert the slide bar holds there too.

**Phase 5 — the docs.** `docs/foot-locking.md`'s "What the demo cannot show" section is now
answered and says so. `docs/verification.md` (the IK section's owed items, and the 12.1 "real
character" debt Phase 0 discharges), `AGENTS.md`'s `animator.c/h` and `ik.c/h` rows and the
`gametest` table row, `docs/cli-reference.md` for `--speed`'s changed meaning, and
`docs/game-engine-roadmap.md` — item 6's tail and the intro paragraph that calls this a blocker.

**The numbers that decide it**, not a green suite:

- `ik-slide-speeds`: the stance slide at 0.5x / 1x / 2x the clip's stride. 12.9's headline was

- `animation_stride_speed` on `strut_walk.fbx` against the probe's 0.95 m/s.
- `animator_stride_speed` against measured foot travel at mid-blend.

**The watch**, which no arm replaces:

```bash
./out/bin/gametest --puppet assets/models/t_pose.fbx            # walk, stop, turn

./out/bin/gametest                                              # the refusal path, and its printed line
```

## Out of scope

- **Root motion.** The other answer to the same problem, and a larger one — it inverts the
  ownership, making the clip drive the controller rather than the controller drive the clip.
- **A stance phase for `gait()`.** Decided above; its own piece of work.
- **2D blend spaces / strafe sets.** The axis here is forward speed. A turn stops sliding because
  the lock pins the foot, not because anything is matched laterally, and the spec should say that
  precisely rather than claiming more.
- **Authored stride as clip metadata.** The runtime measurement needs no asset format change.

## As built

### Phase 0 — the look, and the arm that is red

**What the look found, before any code.** `gametest --puppet assets/models/t_pose.fbx` walked at
`--speed 1.9`, which is the clip's own stride and the one speed at which foot locking works, poses
the character at **blend 0.19** — 62 per cent `rest_pose_` against 38 per cent walk. On this rig
the rest pose is a T-pose, so the character crosses the world with its arms straight out. At the
default 10 m/s the pose is a correct-looking walk that travels five times faster than its feet do.
Both are the same defect from opposite ends: the blend knob is `ground_speed / PLAYER_SPEED` and
`PLAYER_SPEED` is a constant with no relationship to any clip.

**`--ik-probe rate`**, a fourth walking case beside `lock`. It measures the clip's stride from a
weight-0 recording exactly as `lock` does, then walks the body at **0.5x, 1x and 2x** that speed
and reports, per speed, how long the lock held, how far the toe travelled, and — the number this
case exists for — how far the solver had to move the ankle from where the animator put it.

Three shared helpers came out of `lock` on the way, and its numbers are unchanged to the digit
(`stride 0.952081`, `plant slide 0.078273`, `hold slide 0.003416`): `ik_probe_stance` (the window
and the least-squares stride), `ik_probe_drift` (world travel of a held contact, and its largest
single tick) and `ik_probe_walker` (an animator with an IK system, two legs, two toes and a
pelvis).

**Slide alone could not have carried this arm, and finding that out is most of what Phase 0 was
for.** The first formulation asserted the slide bar at all three speeds and very nearly passed:

| travel | lock holds | slide | correction |
|---|---|---|---|
| 0.5x | 50% of the cycle | 0.90% of a leg | **39.9%** |
| 1x | 50% | 0.42% | 5.1% |
| 2x | **29%** | 0.95% | **42.4%** |

A lock inside its `unlock_distance` holds the toe perfectly still *whatever the body is doing* —
so at half speed the foot does not slide at all, and the leg is hauled 0.33 m away from the pose to
achieve it. That is a foot that does not slide on a character that does not walk, and it is exactly
the T-Rex posture `docs/foot-locking.md` records the method warning against. `fix` is that gap.
At 2x the mismatch exceeds `unlock_distance` (0.45 x 0.82 = 0.37 m) partway through the stance and
the lock gives up, which `hold` catches from the other side.

`ik-slide-speeds` asserts all three: hold > 30 per cent, slide < 1 per cent of a leg, correction <
10. It is **red at 0.5x and 2x** and green at 1x, which is the whole claim of this spec stated as a
number. The playback rate it reads comes from `ik_rate_playback`, which returns 1 and says why —
the engine cannot yet answer the question.

### Phase 1 — the measurement, and what it found on the way

`animation_stride_speed` in `animation.c`: one loop sampled at 60 Hz, the pose accumulated to
globals through `pose_local`/`accumulate_global`, each ankle's dwell taken as the samples within
15 per cent of its own lift, and the toe's horizontal velocity across that dwell by least squares.
`--anim-probe stride` is its exercise and `anim-stride` the arm.

**The dwell scan is circular**, which is not a detail: a clip loops, so a stance that straddles the
loop point is one stance, and a linear scan calls it two — which is the difference between a clip
that walks and a clip this refuses. strut_walk's right stance is exactly such a one (samples
49..103 of 86).

**The refusal works and the generated walk is refused.** `gait()` swings straight thighs as
`A·cos(p)`, so each foot is lowest at mid-stride where it is fastest, and both feet reach their
minimum at the same instant. Two of the four tests fire on it independently: two dwells per foot
per loop, and no antiphase between the feet. A fit taken anyway lands on a swing and reports a
plausible magnitude pointing the body backwards, which is why refusing is a result rather than a
gap.

**The two feet disagree by 23 per cent, and the clip is what disagrees.** The left stance is 47
samples at 0.952081 m/s, the right 55 at 0.732105. The left figure is the ik probe's own
independent fit **to six digits** — one implementation samples the clip directly, the other ticks
it through an animator with a solver attached, and they land on the same number. So the spread is
the asset: strut_walk is an asymmetric strut with one foot dragging.

The published answer is **one fit over both stances**, each slope weighted by its own spread
(0.816590), rather than the mean of two (0.842093). That is both "the single body speed that best
explains both windows" and the correct way to combine two regression slopes — a long stance pins
the body over more of the loop and says more about it. `CETRA_STRIDE_TRACE=1` prints the per-foot
window and fit, which is what a disagreement has to be resolved against.

**A defect in the right leg, filed not fixed.** Grading both feet in the `rate` case — `lock`
walks the body at the left foot's implied speed and then grades the left foot, which says nothing
about the other leg — shows the right ankle carrying a standing correction of about 0.3 of a leg.
Walking the body at the right foot's *own* implied speed barely moves it (0.300 against 0.311),
where the left foot's correction tracks travel speed exactly as the model predicts (0.173 / 0.108
/ 0.042 at 0.732 / 0.817 / 0.952 m/s). The per-tick dump says the correction is almost pure Z,
builds over the first 25 ticks of the hold and then plateaus — a contact label opening during late
swing, not a lock losing ground. **It is a spec 12.9 property that no one-footed instrument could
see, it is independent of playback rate, and fixing the contact label would move `ik-contact`,
`ik-slide` and `ik-hysteresis` with it.** Out of scope here; recorded so the next reader does not
rediscover it.

`ik-slide-speeds` is therefore **per foot and relative to that foot's own matched-speed figure**,
plus an absolute bar on the hold. An absolute correction bar would encode the right leg's defect;
a ratio asks only what this spec claims — that matching the rate makes the other speeds behave
like the one that already worked. Red today for three stated reasons: left at half, left at
double, right lets go at double.

### Phase 2 — the blended query

`AnimatorEntry.stride` and `animator_stride_speed`. All six `AnimatorEntry` construction sites in
the tree are brace initialisers with two fields, so every one still compiles and gets `stride = 0`
— "unknown", which is the behaviour they already had, and which the query reports honestly
(0, not a number short of one term) rather than plausibly.

**`space_weights` now writes into a caller's array instead of into the space**, and that is the
whole reason the query can be `const`. It is also a correctness fix in waiting: a game writes the
knob in its update and the animator ticks in pre-render, so anything reading the weights the last
advance left would answer for the *previous* frame's knob. The query recomputes them from `param`.

**The answer is not the weighted mean of the strides.** The space keeps one clock; the blended
pose lays down `sum(w · stride · seconds)` of ground per turn of the loop while the clock turns
the loop at `sum(w / seconds)`, so the answer is the product. The two expressions agree only when
every clip is the same length — which is exactly what a walk-and-run space is not. `anim-rate`
blends a 2.0 s entry striding 1.0 with a 0.5 s entry striding 2.0 and asserts **1.875** against the
mean's 1.500, with the gate recomputing both from the inputs the probe printed rather than taking
the engine's word for which it is.

The strides there are stated rather than measured, and the committed clips cannot exhibit this any
other way: rescaling one clip's time changes its stride inversely, and under that the two
expressions coincide exactly. What separates them is distance-per-loop, which needs two genuinely
different motions.

### Phase 3 — the app, and the look

`build_locomotion` measures the three clips at init. When the moving ones answer, every entry
sits at the WORLD speed it implies, the knob becomes `ground_speed` in metres per second, and
`player_speed` is derived as the fastest entry's stride times the rate ceiling. When they refuse,
the axis stays a fraction of `PLAYER_SPEED` exactly as before and the run says so in one line.
`CHASER_SPEED` and `GROTTO_SWIM_SPEED` became `CHASER_FRACTION` and `GROTTO_SWIM_FRACTION`, which
is what they always meant: at a derived 2.67 m/s a written-down 6 would have outrun the player.

The absolute axis also **deletes** the `--speed` coupling rather than fixing it. The knob had to
divide by the compile-time constant and never by the `--speed` cap, or the gear re-normalised and
`--speed` stopped meaning anything; five lines of comment existed to say so. An absolute axis has
no gear to re-normalise.

**On `t_pose.fbx` + `strut_walk` the axis is 0 to 1.67 m/s and full stick is 2.67**, the walk
stretched to 1.6x. Against `--no-lock` at full stick the frame moves **2217 px**, where before
this spec the same comparison at the default speed was 0 px — the demo can show the feature at the
speed you actually play it.

**What the look found that no arm did.** At any stick short of full, the walk played at about
eighteen times speed. `rest_pose_` is **two ticks** — 0.033 s — and the blend space phase-syncs:
one clock in the ticks of whichever entry carries weight first, every other entry sampled at the
same fraction of its own length. A two-tick rest pose beside an 86-tick walk turns that clock 43
times too fast for the walk, and partial stick is the only range where both carry weight. This has
been true since 12.9 shipped the fallback and no arm could see it, because the probe never plays
two entries. Held frames have no phase to lose, so the fallback gives the rest pose the walk's
period and the sync becomes a no-op; the playback rate at a 0.5 m/s creep went from clamped at 0.6
to 1.000.

The trace's weight columns were gated on `count == 3` and blanked themselves for a two-entry
space; they are gated on the source's NAME now, and the tail carries `speed`.

**What the look found that this spec cannot fix**: on `t_pose.fbx` the only standing clip is the
bind pose, so blending toward "idle" blends toward a T-pose. Below about 0.5 m/s the arms come up.
That is the asset — the rig ships no idle animation — and it is why the entries sit at their
measured strides rather than lower: the walk covers everything from 1.0 m/s up, and the T-pose is
only visible at a crawl.

### Phase 4 — the scale blind spot

`--ik-probe scale` walks the same clip twice with the rig's node scaled 1 and 2, and `ik-scale`
asserts the two runs are identical in model units. Every threshold the solver owns is in model
space and a fraction of the leg, so a scale on the node must reach the world matrix and nothing
the solver decides.

This is the blind spot spec 12.9 shipped a live bug through — a world distance compared against a
model threshold, which at `PLAYER_SCALE 2` made the documented `unlock_distance` behave as half of
itself. Nothing could see it, because every other case in the probe runs the rig at scale 1 and
the app that carries the scale has no arm at all. **Re-introducing that exact comparison takes the
slide at scale two from 0.003670 to 0.012118 and leaves scale one untouched**, which is the arm
being checked against the failure it was written for rather than against an opinion.

### Phase 5 — the docs

`docs/foot-locking.md`'s last section was "What the demo cannot show"; it is now "what fixed it",
and carries three things the spec learned about the FEATURE rather than about stride matching: that
slide does not measure whether locking works, that past the band a clip can carry the answer is to
blend to another clip, and that the right foot's contact label opens during late swing.
`docs/game-engine-roadmap.md` retires "the nearest thing to a blocker" in both places it appears.
`docs/verification.md` closes two owed items — the demo, and the real character owed since 12.1 —
and records what looking at that character cost to find. `docs/cli-reference.md`'s `--speed` entry
loses its caveat about which constant the knob divides by, because there is no longer a knob to
normalise. `AGENTS.md` gains the measurement on the `animation.c/h` row, the blend formula and the
phase-sync trap on `animator.c/h`, the model-space rule and the slide caveat on `ik.c/h`, and the
derived travel speed on the `gametest` row. Arm counts go from nineteen to twenty-one.

### What is owed

- **The right foot's contact label**, described above: filed, not fixed, because moving it moves
  `ik-contact`, `ik-slide` and `ik-hysteresis` with it.

  speed axis has two entries and a walk stretched to 1.6x is its top gear. A Mixamo Running clip

  drops to two because walk and run are the same clip.

  below about 0.5 m/s the arms come up. That is the asset.
