# 11.50 — `foliageShadows` joins the material vocabulary

## Context

An ivy-covered stone arcade is being authored in Blender for import through the `render` app
(spec 11.51). Its leaf cards are ALPHA_MASK, and that combination — **imported** ALPHA_MASK
foliage — turns out never to have existed in this tree before. It does not shadow, in either
direction, and no file can say otherwise.

`Material.foliage_shadows` is what opts alpha-masked geometry back into the shadow map. It was
added in `c92e868` for the tree showcase, and the reasoning still holds exactly:

> ALPHA_MASK materials are excluded from the shadow map entirely because hair strands alias
> into streaks at map-texel scale. Leaf cards are centimeters, not millimeters, so they resolve
> cleanly — and the dappled canopy shadow is the whole point of the surface.

The flag works. What it lacks is any authoring path. Nothing in `import.c` or `cscene.c` writes
it; the only writers in the tree are `apps/tree/src/tree.c:1294` and
`apps/forest/src/forest.c:666`, both C apps that reach the field directly. So masked foliage
shadows correctly when the app that builds it is compiled, and cannot shadow at all when it
arrives through a file.

Nobody has hit this because the corpus's only imported ivy is `abandoned_window`, and
`specs/11.28:283` records that its *"483 ivy leaves are ALPHA_BLEND and go through OIT, not the
opaque pass"* — so it never wanted the flag.

### Why it was excluded, and why that reason does not survive contact with the code

`1327ac1` built the material vocabulary and excluded four fields from it on a stated principle:

> Deliberately shading-only. `alphaMode`, `alphaCutoff`, `doubleSided` and `foliage_shadows`
> decide which PASS a mesh draws in and whether it is culled, so a mistyped value there moves
> geometry between the opaque and transparent queues rather than merely misshading it.
> **Everything in the table can be applied blind because the worst case is an ugly surface.**

The invariant in that last sentence is the real rule, and it is a good one — the parser is
deliberately blind to what keys mean, so what makes it safe is that no row can do worse than
produce an ugly surface.

**`foliage_shadows` cannot move geometry between the opaque and transparent queues.** In
`classify()` the camera lane is computed from `transmissive` and `blend` alone
(`draw_list.c:97`); `foliage` never reaches `*lane`. `DRAW_FOLIAGE` has exactly two consumers
in the whole tree, both in the shadow path:

```
draw_list.c:104     *flags |= DRAW_FOLIAGE;
shadow.c:590        masked_only = (flags & DRAW_ALPHA_MASKED) && !(flags & DRAW_FOLIAGE);
shadow.c:661        bool foliage = (item->flags & DRAW_FOLIAGE) != 0;
```

What it moves is *shadow caster set* membership — depth cascades versus the transmittance set.
That is a real queue change, but the worst outcome of getting it wrong is the streak-and-acne
aliasing the default protects hair from: an ugly surface, which is what the invariant already
tolerates.

**The four are not alike, and only this one is orphaned by the exclusion.**

| field | moves the camera lane? | native glTF representation? | exclusion costs |
|---|---|---|---|
| `alphaMode` | **yes** — sets `masked` and `blend` | yes | nothing; fully earned |
| `alphaCutoff` | no | yes | a second source of truth avoided |
| `doubleSided` | no (sets `DRAW_DOUBLE_SIDED`) | yes | a second source of truth avoided |
| `foliage_shadows` | **no** | **none** | **the capability itself** |

For the first three, exclusion prevents a conflict — each already arrives from the file
(`import.c:298-302`, `import.c:322-338`), so a `.cscn` key would duplicate a fact the GLB
already carries. For the fourth, exclusion removes the only way to say the thing at all.

**Its guard makes a wrong value safer than rows already in the table.** `draw_list.c:96`:

```c
bool foliage = masked && mat->foliage_shadows && mat->alphaCutoff > 0.0f && mat->albedo_tex;
```

All four conditions are required. Set it on a non-masked material, or one with no albedo
texture, or with a zero cutoff, and it is a **no-op**. The only way to make it act is to
deliberately target alpha-masked textured foliage. Compare `roughness`, already in the table
with no guard whatsoever, where a mistyped `10` silently wrecks a surface.

## Non-goals

- `alphaMode`, `alphaCutoff` and `doubleSided` stay out. Their exclusion is separately earned
  (see the table) and nothing here argues against it.
- No change to the default. `foliage_shadows` stays off, so hair keeps the contract `c92e868`
  gave it and every existing scene is unchanged by construction rather than by measurement.

## Phase 1 — widen the field

`Material.foliage_shadows` is a `bool`, and `MaterialParam` has FLOAT / COLOR / INT / TEXTURE
only. `MATERIAL_PARAM_INT` at `offsetof(Material, foliage_shadows)` would write four bytes into
one.

Widen it to `int` rather than inventing `MATERIAL_PARAM_BOOL` for a single member.
`emissive_light`, `subsurface_profile` and `wind_mode` are already `int` in this struct, so an
int-backed material flag is the established shape here. `draw_list.c:96` reads it in boolean
context and is unaffected; so are the two C writers, which assign `true`/`false`.

## Phase 2 — one row, and an amended rationale

- Add a `MATERIAL_PARAM_INT` row to `MATERIAL_PARAMS` (`material.c:31-92`) with enum labels,
  modelled on the existing `emissiveLight` row. Order is the stored value, and **0 must stay
  "off"** so a calloc'd material keeps the default — the opposite polarity from
  `EMISSIVE_LIGHT_NAMES`, which opts in at 0. Getting this backwards would silently turn
  foliage shadows on for every material in the corpus, so the label order is load-bearing.
- Group: "Maps and wind" would be wrong (it is neither); it belongs beside the alpha contract
  it modifies. Rows of a group must stay consecutive — an editor walks runs.
- **Amend, do not delete**, the exclusion rationale at `material.h:257-260`. A rule that
  quietly loses a member teaches the next reader nothing. It should record that
  `foliage_shadows` was admitted because it cannot move the camera lane and is guarded four
  ways, while the other three stay out — `alphaMode` because it genuinely does move the lane,
  the other two because they would become a second source of truth for something the GLB
  already carries.
- The GUI picks the row up for free from the same table (`gui.c:208-229`), which is the first
  time anyone can judge whether leaf cards alias in the cascades without recompiling.

## Verification

The default does not change, so the claim to prove is that **nothing moves unless authored**.

1. `./build.sh`, then the full `scripts/gates.py` suite and `goldens.py`.
2. `raiden` is the instrument, and the only one in the corpus: ALPHA_MASK hair with an albedo
   texture is the sole existing material that satisfies three of the four guard conditions, so
   it is where setting the fourth is visible. Its recipe already exists in CLAUDE.md.
   - With no `foliageShadows` key: **0 px** against a pre-change build, pinned with
     `--no-auto-exposure -E 1.0` and `--no-springs`. Measure the same-build floor first.
   - With `foliageShadows: "on"` authored on `Hair_1` via a scratch `.cscn`: the frame must
     move, and the diff must be the groom and the shoulder under it. This is the arm that
     proves the key is wired rather than merely accepted — a key that parses and does nothing
     would pass the first check perfectly.
3. Confirm the no-op guards: the key on a non-masked material, and on a masked material with no
   albedo texture, must each render 0 px. This is the safety argument above, checked rather
   than asserted.
4. `cscene_apply.c` already reports unknown keys and bad enum labels per material, so a typo is
   loud. Confirm `foliageShadows: "yes"` reports *"has no value"* rather than being ignored.
