# 14.2: text input and scrolling panes

## Context

**What 14.2 builds.** cetra's UI gains a text field and a scrolling pane, which pcb needs for two
things in its step 6, before the chat exists:
- the command palette, opened with Cmd+K: type a few letters to filter the commands, each shown
  with its key;
- the `/` jump to any part or net by name.

Both are a text field over a list. The chat comes in pcb's step 9 and adds a scrolling history with
an input line. This is item 5 of `docs/eda-roadmap.md`. The roadmap's order is 1, 2, 5, 6; items 1
and 2 are built.

**What pcb's ARCH says, and what it leaves to us.** ARCH says little about these widgets:
- the palette "runs any command by typing a few letters, with each command's key beside it"
  (ARCH.md:1734);
- `/` jumps "to any part or net by name, fuzzy" (1727);
- the chat is always visible and can be collapsed (1718);
- "One key puts the cursor in the chat; Esc returns to the view; the focused pane has a subtle
  border" (1731);
- names and values are ASCII (188, 162); prose may not be ("240 Ω").

pcb has no UI code yet. ARCH leaves four things open, and this spec settles each:
- **Matching**, i.e. which names match what was typed, and in what order: a fuzzy matcher in
  cetra. It scores what was typed against one name and gives the matched letters. pcb keeps its
  lists (the command table, its parts and nets) and its own tie-break, natural order.
- **Row layout**: rows are elements the app builds, as today. The matched letters are highlighted
  with styled text (below), the one piece a row couldn't do before.
- **Chat message format**: cetra gives styled text: colour and font for parts of a label or a
  read-only field. What a message holds (clickable change lines, accept and reject, speakers,
  Markdown) is pcb's step 9, built from rows of ordinary elements.
- **Input methods**: finished characters arrive, from dead keys, Option combinations, the emoji
  picker, and a Chinese or Japanese input method once a character is picked. Text still being
  composed is not shown, since GLFW 3.4 never reports it.

## Found while planning

- **The element list is closed, and a gate holds it**: `ui-elements-closed` reads `ui.h` for the
  six constructors (`gates.py:27919`, `_UI_KINDS`). `ui.h:225` says a new kind needs its own spec;
  this spec is that.
- **The layout has no overflow.** Rects are absolute window points. A container whose children
  are too big lets them spill, with no content size recorded (`_arrange`, `ui.c:549-628`).
- **Children can't be clipped.** `_emit` draws an element's children after its draw callback
  returns (`ui.c:677-680`), so nothing can wrap them in a clip.
- **The draw list's offset moves vertex positions only.** The rounded-corner SDF rect, the clip
  rects and `uRect` stay where they were (`ui_draw.c:187-209`, `:352`, `:807`). That is already
  wrong during a SLIDE transition, and it would be wrong for anything scrolled.
- **Hit testing and navigation ignore clips** (`_hit`, `ui.c:815`; `_nav`, `:846`).
- **Moving the pointer takes focus** (`ui.c:989-993`), which suits a game menu. It would steal a
  text field's focus every time the mouse passed over a button.
- **`back` pops whatever screen is on top** (`ui.c:1044`).
- **`UIInput` has no wheel, no characters and no keys.**
  - Typed characters go only to ImGui (`engine.c:1272`).
  - The key callback hands GLFW's repeats to the app's callback but latches only presses
    (`engine.c:1692`).
  - Nothing outside ImGui's backend uses the clipboard.
- **The font atlas holds printable ASCII only** (`text.c:20`).
  - The UI walks text byte by byte, and drops a character the atlas lacks with no advance
    (`ui_draw.c:389-441`).
  - The canvas advances by such a character's own width instead (`canvas_edit.c:796-799`).
  - The one UTF-8 decoder in the tree is private to `canvas_edit.c:804`.
- **The canvas's glyph table holds codepoints below 128** (`canvas_constants.glsl:31`), so a
  larger atlas changes nothing the canvas draws.
- **There is no wrapped layout.** `ui_text_wrap_point` is a helper, and apps put in `'\n'`
  themselves and re-wrap on resize (`apps/silent/src/backpack_menu.c:227-245`).
- **ImGui's copy of stb_textedit nearly compiles as C.** Its implementation uses four ImGui names:
  a `LastMoveDirectionLR` member, a `Stb` member, `ImS8`, and `ImGuiDir_Left` and `ImGuiDir_Right`
  (`imstb_textedit.h:515, 538, 588, 994, 1060-1062`). ImGui runs it on UTF-8 bytes, through
  `GETNEXTCHARINDEX`/`GETPREVCHARINDEX` (`imgui_internal.h:1236-1242`,
  `imgui_widgets.cpp:4045-4060`). It also carries ImGui's fixes over upstream 1.14: redo discard,
  the last line, and the caret at a wrap point.
- **The vendored GLFW is 3.4, which has no API for input-method composition.** A Chinese or
  Japanese input method's finished characters arrive as character events, as dead keys, Option
  combinations and the emoji picker do. The text being composed before that is never reported, so
  the field can't show it, and the input method's choice window can't be placed at the caret.
- **A label draws in one style**: `ui_draw_text` takes one `UIStyle` for the whole string
  (`ui_draw.c:492`), so no part of a label can be coloured or set in another font.
- **A blink can't be timed on the UI's `dt`.** Idle mode keeps waits out of the engine's clock
  (spec 14.1), so the blink has to read the wall clock.
- **The pointer script is used by three apps**: `render`, `shapes` and `canvas`.

## Design

### Typed input reaches the UI (engine, `input.h`, `ui.h`)

- **The engine records what is typed.**
  - A new char callback forwards to ImGui, then records the codepoint.
  - The key callback also records presses and repeats.
  - Both go into one ordered list on `InputState`, of `InputKeyEvent {int key; int mods; uint32_t
    codepoint;}`. An event is either a key with codepoint 0, or a character with key 0.
  - It is one list because order matters: 'a' then Backspace is not Backspace then 'a'.
  - The list is cleared with the scroll and key latches before each poll (`engine.c:3799`).
  - Nothing is recorded while ImGui wants the keyboard.
  - It holds 64 events, and an overflow is warned once.
- **The clipboard is the engine's.** `engine_clipboard_get` and `engine_clipboard_set` use GLFW's
  in a window. Headless, they use a string the engine owns, so a gate run never touches the user's
  clipboard.
- **`UIInput` gains:**
  - `float wheel_y`, in wheel units;
  - `const InputKeyEvent* key_events` and `int key_event_count`;
  - `double time`, the clock that double clicks are measured on.

  `ui_input_add_keyboard(UIInput*, const Engine*)` fills those three from the engine. The time is
  `glfwGetTime` in a window, and frames times the fixed step headless. Apps keep building the
  pointer half themselves, as today.
- **The pointer script becomes the input script.**
  - Two new tokens: `type=TEXT` (UTF-8, with `\s` for a space and `\\` for a backslash) and
    `key=NAME`, with modifiers joined by `+`.
  - The modifiers are `shift`, `ctrl`, `alt`, `super`, and `mod`, which is the platform's shortcut
    modifier: Cmd on macOS, Ctrl elsewhere. So a script is portable.
  - Tokens apply in line order, through the same recording path as the callbacks.
  - It is renamed `engine_set_input_script`, and the flag `--input-script`, in `render`, `shapes`
    and `canvas`.

### UTF-8 and the atlas (`text.c`, `ui_draw.c`)

- **One decoder.** `_utf8_next` moves from `canvas_edit.c` to `text.h` as `text_utf8_next`, and
  every UI measure and draw walks codepoints with it.
- **The atlas grows.** It now holds:
  - printable ASCII;
  - Latin-1 (U+00A0-00FF);
  - Greek (U+0391-03A9, U+03B1-03C9);
  - a short list of symbols: dashes, curly quotes, bullet, ellipsis, ‰, €, arrows, minus, Ω, ∞,
    ≈, ≠, ≤, ≥.

  A codepoint the font itself lacks is left out.
- **A character the atlas lacks** advances by its own width, as the canvas already does, and
  draws as an outlined box. It is never a silent gap.
- **What UTF-8 covers, stated plainly:**
  - **Stored:** every character is kept, copied, pasted and stepped over whole.
  - **Drawn:** the atlas's characters draw; any other (Chinese, emoji) draws as the box and stays
    correct in the text.
  - **Composed:** text being composed by an input method isn't shown (above).

### Styled text (`ui.c`, `ui_draw.c`)

- **A label or a read-only field can take runs**: `UITextRun {start, length, color, font}`, a byte
  range of its text with its own colour and, optionally, its own font, given with
  `ui_set_text_runs(el, runs, count)` and copied.
  - Text outside every run takes the element's style.
  - A run changes the colour and the face, not the size: lines keep the element's line height and
    baseline, so a monospace run sits in the line.
  - Runs must be in order, not overlap, and fall on codepoint boundaries; anything else is refused
    by name.
  - Setting the text clears the runs, so an app sets the text and then its runs.
- **Measuring, wrapping and drawing walk the runs**, one function for the advance and kerning of
  each glyph in its run's font, so a wrapped line, a caret and a drawn glyph agree. Kerning stops
  at a change of font.
- **A read-only field selects and copies across runs**, which is plain text.
- **An editable field stays in one style.** Editing styled text would mean moving the runs at
  every keystroke, and nothing needs that yet.
- **Who uses them here:** the palette and the jump highlight their matched letters; the test app's
  history has messages with a coloured word and a monospace name.

### The fuzzy matcher (`fuzzy.c/h`, new)

- **`int fuzzy_match(const char* query, const char* name, size_t* positions, size_t cap)`**: does
  `query`'s every character appear in `name`, in order? It returns a score (higher is better), or
  -1 for no match, and writes the byte offset of each matched character to `positions`.
- **What scores higher:** a match at a word's start (after a space, `_`, `-`, `/`, `.`, `[`, or at
  a change from lower to upper case), runs of adjacent letters, and a match at the name's start.
  Gaps cost a little. ASCII letters match either case.
- **It finds the best-scoring placement, not the first**: a small dynamic program over the query's
  and the name's characters, after fzf's second algorithm. So `rtnt` matches "**r**ou**t**e
  **n**e**t**" on its word starts rather than the first r, t, n and t it meets.
- **It searches nothing.** The app loops over its own list, calls it on each name, sorts by score
  and its own tie-break, and highlights `positions` with runs.
- No GL, no UI and no allocation, so its arm needs no window.

### Layout in two axes, and wrapped text (`ui.c`)

- **The layout runs one axis at a time.** It does width (measure, then arrange), then wraps text,
  then height (measure, then arrange).
  - Widths never depended on heights, so every existing tree lays out to the same floats: read in
    `_measure` and `_arrange` (`ui.c:507-628`), where each axis's arithmetic touches only that
    axis. The `ui` arms hold that unchanged.
  - The split is what makes height-for-width possible.
- **A label with `wrap` set breaks at its arranged width.**
  - It measures its width as its longest word, so it never forces its parent wider than a word.
  - It takes its width from its parent: grown, fixed, or stretched across a column.
- **Line breaks are cached.** A wrapped label or field keeps them until its text, width or style
  changes, since the layout runs several times a frame.

### The scrolling pane (`ui.c`, `ui_draw.c`)

**`ui_scroll(parent)`** is a container that scrolls vertically.

- **Layout.** Its children are arranged at their full height from the pane's top less the scroll.
  - The content height is recorded, and the scroll is clamped to it.
  - A grown child still fills a short viewport.
  - The rects stay true window positions, so nothing downstream needs an offset.
- **Clipping.** `_emit` pushes the pane's clip, draws its children, and pops it.
  - Hit testing doesn't reach a pane's content outside its rect.
  - The draw list's offset now moves the SDF rects, the clips and `uRect` too, which also fixes the
    SLIDE transition.
- **Moving it:**
  - The wheel scrolls the innermost pane under the pointer, at `UITheme.scroll_step` points a unit.
    The step is tuned at the look.
  - Page Up, Page Down, Home and End scroll the pane holding the focus, when the focused element
    doesn't use them.
  - Navigation reaches elements scrolled out of view, and focusing one scrolls its pane by the
    least amount that shows it.
  - `ui_scroll_into_view(el)` does the same for an app.
  - Keys and scrolling into view ease, so they ask for frames until they arrive. The wheel and a
    dragged bar move it at once.
- **The bar.** A thin bar on the right edge shows while the content is taller than the pane. Its
  thumb can be dragged, and a click on the track moves a page.
- **`follow_end`**: a pane scrolled to its end stays there as content is added, as a terminal does,
  and a pane scrolled up stays put.
- **"The focused pane has a subtle border."** A pane takes its FOCUS state while the focus is
  anywhere inside it, so the theme's `scroll[UI_STATE_FOCUS].border` draws that border. No new
  concept is needed.
- **Virtual rows for long histories:**
  - **The calls:** `ui_scroll_set_rows(pane, count, estimate, build, user)` hands the pane a count
    and a function that fills one row. `ui_scroll_set_row_count` appends rows or drops them, and
    `ui_scroll_rows_changed` rebuilds some.
  - **Which rows exist:** the pane builds only the rows in view, plus one row either side and the
    row holding the focus, and frees the others. So a history of 100,000 rows lays out a screenful.
  - **Heights:** a row's height is measured when it is first built, at the pane's width, and kept.
    A row not yet measured counts at the estimate.
  - **Anchoring:** when a height changes above the view, the scroll moves with it, so the first
    row in view stays where it was.
  - **A change of width** turns every kept height back into an estimate to be measured again.
  - `ui_scroll_to_row` scrolls a row into view, building it if needed.

### The text field (`ui_field.c`, new)

**`ui_text_field(parent, flags, on_submit, user)`**, with three flags:
- `UI_FIELD_MULTILINE`: wraps, and grows to `max_rows` rows, then scrolls inside itself;
- `UI_FIELD_READ_ONLY`: the text can be selected and copied, not edited, and may carry styled
  runs;
- `UI_FIELD_SUBMIT_ON_ENTER`: in a multi-line field, Enter submits and Shift+Enter starts a new
  line, as a chat input does.

The element's `text` is the placeholder, drawn dim while the field is empty. The other calls are
`ui_field_text`, `ui_field_set_text`, `ui_field_set_on_change` and `ui_field_set_on_key`.

- **The editing core is stb_textedit, ImGui's copy already in the tree, on a UTF-8 buffer** that
  grows as needed. It gives the caret, selection, word moves, up and down with a remembered x,
  click and drag, and undo and redo.
- **It compiles from one C file, `ui_field.c`, with a short compatibility block:**
  - `typedef signed char ImS8;`;
  - `ImGuiDir_Left` and `ImGuiDir_Right` as 0 and 1;
  - the two members ImGui's code writes, `LastMoveDirectionLR` and `Stb`, on our edit struct;
  - a comment saying why, beside the block.

  That one file is also stb's implementation unit, so the compatibility block goes no further.
- **Where caret positions come from.** The widths stb sees use the same advance, tracking and
  kerning as the draw, from one function. A row is a wrapped line, or the whole text when it is
  single-line.
- **Keys follow the platform:**
  - **macOS:** Option+arrow moves a word, Cmd+arrow to the line's or the text's end, and
    Option/Cmd+Backspace deletes a word or to the line start. Cmd+A, C, X, V and Z work, and
    Cmd+Shift+Z redoes.
  - **Elsewhere:** Ctrl+arrow moves a word, Home and End the line, and Ctrl+Home/End the text.
    Ctrl+Backspace deletes a word. Ctrl+A, C, X, V and Z work, and Ctrl+Y or Ctrl+Shift+Z redoes.
  - **Shift** extends the selection.
  - **Repeats** come from the OS, as GLFW's repeat events.
  - **What is typed** is inserted from the character events. Control characters are dropped. A
    paste into a single-line field turns newlines into spaces.
- **The mouse:**
  - a click places the caret and a drag selects;
  - Shift+click extends the selection;
  - a double click selects a word, measured on `UIInput.time`;
  - a triple click selects the line.
- **Scrolling inside the field.** A single-line field scrolls sideways to keep the caret in view,
  and a multi-line field scrolls up and down.
- **Drawing.** The selection is drawn behind the text in the theme's `selection` colour. The
  caret is a thin bar in the text's colour.
- **The blink:**
  - The caret is solid for 0.8 s and hidden for 0.4 s, ImGui's rhythm, and solid again after any
    edit or move.
  - In a window, `_ui_overlay` times it from `glfwGetTime` and asks for the next change with
    `engine_request_frame_after`, so under idle the window wakes only for the blink.
  - Headless, the caret doesn't blink. A picture is then the same on every run, and an idle run
    ends.
- **Focus and keys:**
  - `ui_wants_keyboard(ui)` is true while a text field holds focus, or a modal screen is up. pcb's
    keys go to its views only when it is false.
  - `ui_pointer_over(ui)` says whether the last pointer was over the UI, so the wheel and a drag
    go to the right place.
  - Moving the pointer no longer takes focus from a text field. A click does: on another element
    it moves the focus there, and on nothing in a screen that isn't modal it lets go of the focus.
  - While a field holds focus it reads keys and characters, and the `nav_*` and `accept` values
    are ignored, so an app that maps the arrows to navigation doesn't move focus while typing.
  - **Esc, or `back`:** in a modal screen it closes the screen (the palette). In a screen that
    isn't modal it lets go of the focus, so keys return to the view (the chat).
  - **Enter** submits (single-line, or with `SUBMIT_ON_ENTER`).
  - **Tab and Shift+Tab** move the focus in tree order.
  - **`on_key`** sees each key first and can take it. The palette takes Up and Down to move its
    highlighted row while the caret stays in the field.
  - Game apps pass no key events, so all of this leaves them unchanged.
- **The theme gains** `text_field[UI_STATE_COUNT]`, `scroll[UI_STATE_COUNT]`, `selection` and
  `scroll_step`. Each zero inherits, as today.

### One text core or two: two

- **The field uses stb_textedit's flat buffer.** It walks rows from the start of the text, which
  is fine for fields of a few thousand characters.
- **Item 6's code editor needs large files, colour spans and a host-owned undo**, which is a piece
  table or an array of lines, borrowed from lite and vis as the roadmap says.
- **What they share** is written once here for item 6 to reuse:
  - the key-to-command mapping and its platform conventions;
  - the UTF-8 walking;
  - the measuring with advance and kerning, across styled runs, which gives the editor its
    colouring's measure as well.

The roadmap records this under item 6.

### The test app: `apps/canvas`

It tests engine features and gives us something to look at. It does not sketch pcb's interface:
no change lines, no accept or reject, no speaker formatting. Those are pcb's step 9 and need
nothing new from cetra.

**`--palette`:**
- Cmd+K (Ctrl+K elsewhere) opens a modal palette: a field over a list of the app's own commands,
  each sheet and each toggle with its key at the right, so it is useful as well as a test.
- The list is filtered and ordered by `fuzzy_match`, with the matched letters highlighted in runs.
- Up and Down move the highlight, Enter runs, a click runs, and Esc closes.
- `/` opens the jump over 5,000 generated names, to work a long virtual list the same way.

**`--history`:**
- A column on the right with a scrolling history and an input line under it. The canvas views
  shrink to leave room for it.
- The history is virtual rows, each a read-only wrapped field, seeded with 200 plain messages, a
  few with a coloured word and a monospace name in runs.
- The input line is multi-line and submits on Enter.
- Enter in a view puts the caret in the input line, and Esc returns to the view.
- A sent message gets a canned reply that streams in word by word, which works `follow_end` and
  the frame requests.
- The wheel scrolls the history over it, and zooms the canvas elsewhere.

**Under `--canvas-probe`** it prints the field's text, the list's rows and matched positions, and
the history's rows, built rows and scroll, for the gates.

## As built

### Phase 1: typed input, the clipboard, UTF-8 and the atlas (`8395bba2`)

- **The engine's typing list** is `InputState.key_events`, 64 `InputKeyEvent`s a batch, cleared
  with the wheel and key latches before each poll. The key and character callbacks split as the
  pointer's do: `_engine_key` and `_engine_char` are the halves past ImGui that the input script
  reaches too, and both keep what ImGui's text field takes.
- **A scripted key is a press and its release** in one frame, through `_engine_key`, so it reaches
  `key_pressed`, the typing list and the app's key callback as a keyboard's does. The script
  carries up to 32 typing events a line, inline in the range, so a parse that fails part way frees
  nothing per range. Real keys still work under a script; only the mouse is replaced.
- **The clipboard** is `engine_clipboard_get`/`_set`; headless it is `Engine.clipboard`, owned.
- **The atlas** holds 264 codepoints over 17 ranges, those the face has. Roboto-Bold's still fits
  1024², and ASCII is placed first in the old order, so every ASCII glyph keeps its place and UVs:
  the `canvas` group, whose glyph arms compare against stb's own rasterizer, and
  `canvas-under-ui` pass unchanged.
- **Found and fixed: the atlas's UVs were wrong after it doubled.** Each glyph divided its pixel
  position by the atlas's size when it was placed, so a glyph placed before a doubling sampled the
  wrong quarter. The ASCII set never doubled it, which is why nothing showed; the UVs are now
  pixels until the last glyph is placed and divided by the final size.
- **A face's missing codepoint is left out of the atlas** (`stbtt_FindGlyphIndex` is 0), ASCII
  included, so it draws the UI's box rather than the face's `.notdef`. No font in use lacks an
  ASCII glyph.
- **The box** is drawn over the face's own advance for the codepoint, which for Roboto's
  `.notdef` is narrow; it reads as a box and not a gap, which is the point.
- **The canvas app** gained `--ui-text TEXT`, a label in the `--ui` panel, and under
  `--canvas-probe` prints `canvas typed ...`, what `ui_input_add_keyboard` hands the UI each frame.
- **Arms**: `ui-typed` and `ui-glyphs`, in the `ui` group, end to end through apps/canvas.
- **Falsified**: with `_engine_char` recording nothing, `ui-typed` failed, handed only the keys;
  with the box not drawn, `ui-glyphs` failed at 0 px of ink for the missing codepoint. Nothing else
  failed.
- **Gates**: `ui`, `canvas`, `idle` and `camera` pass, the last two through the renamed flag.

### Phase 2: the layout in two axes, wrapping and styled runs (`82aff11e`)

- **The layout runs one axis at a time** (`_measure` and `_arrange` take an axis): every width,
  then each label's lines, then every height. Every existing `ui` arm passes unchanged, and the
  canvas panel with UTF-8 text renders 0 px from its phase 1 picture.
- **One walk of the text** (`ui_text.h`, private to the UI's files, in `ui_draw.c`): `UIText`, a
  string with its style and runs, and `_walk_next` the one per-glyph step that measuring
  (`ui_text_span_width`, `ui_text_pen`), breaking (`ui_text_break`) and drawing
  (`ui_text_draw_span`) all take. `ui_draw_text`, `ui_text_width` and `ui_text_wrap_point` are
  now calls into it, with the arithmetic in the order it had.
- **A wrapping label** (`UIElement.wrap`) measures its width as its longest word and breaks at
  the width it is given, less its padding; it is drawn at its rect, as a plain label always was,
  so a label's left padding still moves neither. Its lines are `UILines`, kept while the width,
  face, size and tracking match; `ui_set_text` and `ui_set_text_runs` drop them.
  `UIElement.wraps` counts the breaks, which is what `ui-wrap-cache` reads.
- **Styled runs** (`UITextRun`, `ui_set_text_runs`) on a label: a colour (alpha 0 the label's) and
  a face, at the label's size. A label with runs and no wrap keeps lines broken at its `\n`s, so
  it takes the same draw. Kerning and tracking start afresh at a change of face.
- **The draw list's offset** now moves the corner SDF's rect, a pushed clip and a program's `uRect`
  with the quads, which also corrects a SLIDE transition's corners.
- **Quads read back** (`ui_draw_list_quad_count`, `ui_draw_list_quad`), public, for the probes:
  the runs arms read each glyph's colour and size from them.
- **The probe's new cases** live in `apps/gametest/src/ui_text_probe.c`, called from the `--ui-probe`
  dispatch when no older case matches. A case's lines must carry its own name as their case word,
  which the gate filters on: the runs case first printed three names and read as nothing.
- **Renamed from the plan**: the wrapping arm is `ui-wrap-label`, since `ui-wrap` already exists
  (the paragraph breaker's), and the runs arms are `ui-runs-draw`, `ui-runs-wrap` and
  `ui-runs-refused`, the plan's `ui-runs-*` spelled out.
- **Falsified**: the cache's early return taken out failed `ui-wrap-cache` (3 breaks after three
  layouts); a wrapped label's height from its `\n`s failed `ui-wrap-label` (30 high against 96);
  a run's colour ignored failed `ui-runs-draw`. Nothing else failed.
- **Gates**: `ui`, `canvas` and `idle` pass.

### Phase 3: the scrolling pane (`cf49de85`)

- **`ui_scroll`**, kind `UI_SCROLL`, the seventh element (`ui-elements-closed` counts it; the
  closed-list comment in `ui.h` says so). `scroll`, `scroll_target` and `scroll_content` are the
  engine's; `follow_end` a setting; `UITheme.scroll[]` and `scroll_step` its look and its wheel.
- **Layout**: the Y pass's main-axis arrange starts a pane's children at its top less its scroll,
  settled there (`_scroll_settle`) against the content just measured: clamped, and moved to the end
  when it followed and the content grew. **Found while building: a growing pane must ask no height
  of its parent.** A GROW axis is measured at its FIT size, and a pane's FIT height is its content,
  so the history's pane first came out 9,890 points tall inside a 600-point column; a growing pane
  now measures as its padding down the axis it scrolls.
- **Drawing**: the pane's fill and border under its content, the content clipped inside the
  border, a child wholly out of view not emitted, the bar's thumb over it.
- **Input**: hit tests, `_pane_at` and `ui_pointer_over` see a pane's content only where the pane
  shows it. The wheel scrolls the deepest pane under the pointer at once; Page Up, Page Down, Home
  and End scroll the pane the focus is in, or the one under the pointer with nothing focused,
  easing; a press on the bar's strip drags the thumb or pages, and is a press on nothing under it.
- **Reveal** (`_reveal`, `ui_scroll_into_view`): on a navigated focus, and on a focus the app set
  or a screen arrived with -- told apart by `focus_seen`, the focus as the last pass left it. A
  focus the pointer moved is not revealed, or hovering a half-shown row would scroll it.
- **`ui_scroll_into_view` takes the UI system**, a change from the plan: a pane's padding is the
  theme's to resolve. It takes it as const, as cppcheck asked.
- **`ui_pointer_over` takes the point**, `(ui, x, y)`, rather than reading the last pass's
  pointer: the canvas app asks at a press and at a wheel, before the next pass runs.
- **The canvas app's `--history`**: a 360-point column at the window's right, the views sharing
  what is left, with 200 wrapped messages in a pane that follows its end -- each speaker in a
  colour, every fortieth message a part's name in the second face. The column takes the real
  pointer and keyboard (`live_ui_update`); a press or the wheel over it does not reach the canvas.
- **Arms**: `ui-scroll-layout`, `-wheel`, `-clip`, `-into-view`, `-follow`, `-bar` through the
  probe; `ui-history-clip` end to end. Its first run counted the column's own anti-aliased top
  and bottom rows as leaked text; the strips keep two pixels in from the column's edges.
- **Falsified**: the clip opened to the window failed `ui-history-clip` (1,651 px in the padding);
  the hit test reaching past the pane failed `ui-scroll-clip` (a click below the pane landed);
  `follow_end` switched off failed `ui-scroll-follow`. Nothing else failed.
- **Gates**: `ui`, `canvas` and `idle` pass.
- **The look** is yours to take in a window: `./out/bin/canvas --sheet board --history` -- the wheel
  and the bar over the column, the clip at its top, the coloured speakers. The headless picture
  showed the column pinned to its end, the speakers coloured and the thumb at the bottom.

### Phase 4: the text field and the matcher (`bb7388cf`)

- **`ui_text_field`**, kind `UI_TEXT_FIELD`, the eighth element, in `ui_field.c` behind a private
  header (`ui_field.h`) that `ui.c` lays out, routes input and draws through. Its state is
  `UIElement.field`; `max_rows` a setting; `UITheme.text_field[]` and `selection` its look.
- **stb_textedit from C**: ImGui's copy compiles from `ui_field.c` with a compatibility block of
  five names, not the plan's four -- `ImS8`, `ImGuiDir_Left`, `ImGuiDir_Right`, the
  `LastMoveDirectionLR` and `Stb` members, and `IM_ASSERT`, which the header also uses. stb's
  widths are the walk's pens (`_glyph_width`), its rows the walk's breaks (`_layout_row`), its
  line moves the visible row's ends (`_row_start`, `_row_end`), its word moves a class walk that
  ends a word on macOS and starts the next elsewhere.
- **Undo a word at a time**: stb records every character it is given, so `_merge_typing` joins a
  typed insert to the one before unless it is a space after something that is not. **Found:
  stb's records say what UNDO does**, so a typed insert is a record that deletes, its length in
  `delete_length`; the first merge read `insert_length` and joined nothing.
- **Keys**: the platform's conventions, Cmd on macOS and Ctrl elsewhere for the shortcuts, Option
  or Ctrl for a word, Cmd+arrow to a line's or the text's end; on one line Up and Down go to its
  start and end. A paste sanitizes: newlines a space on one line, a tab a space, control
  characters out. Typed characters are refused by a read-only field, as cut and paste are.
- **The pointer**: a press places the caret, Shift extends (`UIInput.pointer_mods`, a field the
  plan did not name: the pointer half needed the modifiers held at the press), a second press
  within 0.4 s and 4 points selects a word and a third the row; a held press selects to the
  pointer.
- **Focus**: the pointer passing over leaves a field its focus; a press on nothing in a screen
  that is not modal lets go of the focus; while a field holds it, navigation and accept are
  ignored and back lets go (`_let_go`: a modal screen pops); Tab and Shift+Tab move in tree order
  (`_tab`) for any focus. **Found: the field decided `typing` before the pointer**, so a press on
  nothing that let go of the field still handed its keys to a NULL field and crashed; `typing` is
  now the focus as the pointer left it.
- **The blink**: the overlay sets `UISystem.now` from the wall clock and asks idle mode for the
  caret's next change (`caret_wake`); headless the caret does not blink. A caret restarts lit at
  any move or edit (`caret_moved`, taken up by the draw).
- **`ui_wants_keyboard`**, and `ui_set_text_runs` on a read-only field, refusing an editable one.
- **`fuzzy_match`** (`fuzzy.c/h`, public): fzf's numbers -- 16 a match, -3 and -1 a gap, 8 at a
  word's start, 7 at a turn into upper case or a digit, 4 a run, the first character's bonus
  doubled -- over a 32 by 256 table of int16 on the stack, the best placement by carrying a gap's
  best along each row, and the positions by walking back. **The plan's example was wrong**:
  "rtnt" scores "rotate tint" (81) over "route net" (77), since "nt" runs in "tint". The arm uses
  "rn", "route net" (49) over "print" (29), and "st" in "fast stop" at 5 and 6, where the first
  placement would take 2 and 3.
- **The canvas app**: `--palette` (Cmd+K or Ctrl+K, the app's ten commands with their keys, which
  `on_key` now runs too: = and - zoom, 0 resets, P prints) and `/` (the jump, the best twelve of

  is not typed into it; the history's input line, multi-line and submitting on Enter, focused by

  sit in a fitting pane with no gaps, so hidden rows take no room; **a spacing of zero means the

- **Arms**: `ui-field-type`, `-edit`, `-utf8`, `-select`, `-clipboard`, `-undo`, `-caret-x`

### Phase 5: virtual rows (`dbb5aa78`, `b6bdb54a`)

- **`ui_scroll_set_rows`**, `ui_scroll_set_row_count`, `ui_scroll_rows_changed` and
  `ui_scroll_to_row`, with `UIRowFn`. `ui_scroll_to_row` takes the UI system as const, as
  `ui_scroll_into_view` does. The rows' state is private to `ui.c` (`struct UIRows`, behind
  `UIElement.rows`): a height a row, whether it was measured, whether it is stale, the tops summed
  with the pane's spacing, and which child holds which row. `row_builds` counts the builds, which
  is what an arm can bound.
- **Building happens in the layout**, before each pass (`_rows_settle`): the rows in view from
  where the last layout left the scroll and the pane's height, one either side, and the row
  holding the focus; the rest are freed. Each row is a container the pane makes, of kind
  `UI_ROOT`, so it has no look of its own, stretched across the pane. A row freed lets go of
  anything the system held inside it: the press, the bar's drag, `focus_seen`, a screen's focus.
  What is built can change what the layout finds, so `ui_layout` runs again on what is built then,
  three times at the most. A screen with no rows lays out once, as before.
- **Heights**: a pane of rows is as tall as every row, built or not, at its measure or its
  estimate (`_rows_measure`); arrange puts each built row at its own top less the scroll. A new
  content width makes every kept height an estimate again, measured as each row is next built,
  and no row is built again for it.
- **Anchoring**: a height that changes above the first row in view is added to the scroll in the
  arrange, so that row stays where it was. **Found by the falsification**: the first version
  anchored on the row at the scroll (`_row_at`), which counts the gap after a row as part of that
  row. With only a row's gap at the top of the view, that row's growth was not anchored and moved
  everything in view by its growth. It now anchors on the first row any of which shows
  (`_row_seen`). The arm's first form didn't see it: it wheeled up onto rows the reveal had already
  measured, so nothing above the view changed height. It now builds the row above the view again,
  taller.
- **A row scrolled to is aimed at again until it is measured** (`UIRows.reveal`): its place was
  an estimate's until it was built, and the rows above it measured on the way move it.
- **The canvas app**:
  - **The history** is rows of read-only multi-line fields over the app's own message arrays, so
    a message can be selected and copied. Each field is in the column's colour, with the speaker
    coloured and a part's name in the second face (`build_message`).
  - **Sending and replying**: a sent message and its reply are appended with
    `ui_scroll_set_row_count`; the reply streams by rebuilding its own row
    (`ui_scroll_rows_changed`).
  - **The palette and the jump** are one list of rows over every match, not the best twelve. The
    list fits up to twelve rows and scrolls past that. Up and Down rebuild the old and new
    highlighted rows and scroll to the new one.
  - **Headless check**: "n" in the jump matches 2,000 of the 5,000 names and builds 15 rows.
    Fifteen downs leave the highlight at the list's bottom edge. The probe prints the list's rows
    and how many are built (`canvas palette list`).
  - **The second face is PressStart2P**, a pixel font, which is why a part's name looks blocky.
- **Arms**: `ui-rows-built` (100,000 rows, 7 held at the top and 8 at row 50,000, 15 built in
  all, none on a second layout), `ui-rows-measure`, `ui-rows-anchor` and `ui-rows-focus`, through
  the probe.
- **Falsified**: dropping the anchoring failed `ui-rows-anchor` on both halves: row 100's bottom
  was 30 points under the pane's, and the first row moved 30. Freeing the focused row failed
  `ui-rows-focus` (kept 0). Nothing else failed.
- **Gates**: `ui`, `canvas` and `idle` pass.
- **The look** is yours in a window: `./out/bin/canvas --sheet board --palette --history`. Try `/`
  then a letter, Up and Down through the long list, the wheel over it, and a message sent and its
  reply streaming in.
