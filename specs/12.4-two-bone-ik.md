# Spec 12.4 — Two-bone IK and foot planting

## Context

`docs/game-engine-roadmap.md` Part 2 lists **IK** as absent: _"Foot planting,
look-at/aim. Quality-of-life, not blocking. ~1 week (two-bone)."_ With 12.3 merged,
the vertical-slice path (Part 3 items 1-5) is complete; item 6 is Steamworks, which
is explicitly "near ship" work gated on a Steam partner account and a redistributable
binary SDK — the first non-vendored dependency in a tree whose build rule is that
everything is `add_subdirectory` from source. IK is the piece that pays off now: it
sits entirely on 12.1's pose seam, needs no external anything, and is analytically
gate-verifiable on the existing puppet.

**Scope is foot planting only.** Look-at/aim is a different solver — a single-joint aim
constraint, not a two-bone triangle — and becomes its own spec if wanted. Hand IK is
deferred for want of anything in gametest for a hand to reach.

**Non-goals:** look-at/aim; hand/prop attachment; full-body IK or a general N-joint
solver (CCD/FABRIK); IK on forest's terrain (its player is a bare capsule with no rig);
retargeted IK across skeletons.

---

## What already exists (surveyed, not assumed)

The feature is a sibling of spring bones, not a new mechanism. Every structural
question it raises has a committed answer in `springbone.c/.h`:

| need | already there |
|---|---|
| A seam with **model-space** joint positions | `animation_state_apply_pose` (`animation.c:1017`), between the parent-first accumulation loop and "PASS 2: Compute final bone matrices". `spring_bone_update` is called there at `:1038` with `state->local_transforms` and `state->global_transforms` |
| Write-back idiom | `springbone.c:336-342` — `glm_quat_from_vecs` → `glm_quat_mat4` → `glm_mat4_mul(rotation, target, global_transforms[i])`, then restore the head translation |
| Descendant correction | springbone's loop re-accumulates `global = parent_global * local` for every unsimulated bone (`springbone.c:266-271`) — "identical for bones with no simulated ancestor, corrected for descendants of one" |
| Attach / own / free | plain field `struct SpringBoneSystem* springs` (`animation.h:169`), NULLed at `animation.c:457`, freed at `:469`, written directly by the app (`render.c:3800`) |
| Snap instead of lerp on a jump | `teleport_distance` in `SpringBoneParams`, plus `needs_reset`; reset is called on clip switches from `animator.c:212` and `:292` |
| Degenerate-input guard | `rest_len < 1e-6f` → follow the animation rigidly (`springbone.c:290`) |
| Chain registration by name | `spring_bone_add_chain(system, root_bone_name)`, with `bone_to_joint[MAX_BONES]` holding `-1` for unsimulated bones |
| The ground query | `physics_world_raycast` / `_filtered` / `_ignore` (`physics.h:344-348`) |
| The ground **normal** and on/off signal | `character_controller_get_ground_normal` (`character.h:119`), `_get_ground_state`, `_is_grounded` — already read for the jump gate at `gametest.c:1149` |

**No new engine API is required outside the IK module itself.**

## Two facts about the puppet that shape the design

From `assets/gen_puppet_fixture.py:56-78`:

1. **The bind pose is exactly the singular configuration.** The hip pivot
   (`LeftUpLeg`) sits at y=0.90 and the ankle (`LeftFoot`) at y=0.08 — 0.82 apart —
   while the bone lengths are thigh 0.42 and shin 0.40, summing to exactly 0.82. The
   leg is *perfectly straight* at bind, which is where `cos(knee) = -1` sits on the
   clamp boundary and the knee's bend plane is undefined. A naive solver yields NaN
   or a random bend direction on frame one.
2. **The walk clip never bends the knee.** `gait()` rotates `LeftUpLeg`/`RightUpLeg`
   ±30° about X and nothing else; the legs swing as rigid sticks for the whole cycle.
   So the singularity persists across the animation and the pole vector must supply
   the bend plane, because the clip never does.

Both make this a hostile fixture, which is the right kind.

## The two blockers this spec must also fix

**1. Nothing in gametest is uneven.** The world is a flat 50x50 plane with a static
box collider of half-extents `(25, 0.5, 25)` (`gametest.c:896-918`). Grep finds no
ramp, stairs, slope or mesh collider anywhere in the app; the only other bodies are
the door, its frame, five `srand(42)` crates and the chaser, none of which produces a
per-foot height difference. **On flat ground at the height the clip was authored for,
foot IK is an identity** — every arm would pass with the solver body deleted. So the
spec ships a static ramp-and-steps fixture beside the existing floor.

**2. The floor is drawn half a metre below the surface it is stood on.** Traced
end-to-end, no inference left:

| | |
|---|---|
| Floor entity position | `(0, -0.5, 0)` (`gametest.c:890`) |
| Collider | `entity_add_rigid_body` creates the body at `entity->position` verbatim (`physics.c:611`, `settings.Position = vec3_to_jpc_r(entity->position)`); box half-extent `(25, 0.5, 25)` → spans y ∈ [−1, 0], **walkable top y = 0** |
| Visual | `mesh_generate_plane` writes EVERY vertex at `cy = plane->position[1]`, and gametest passes `.position = {0,0,0}` (`geometry.c:821`, `gametest.c:896`) → all vertices at local y=0. `sync_entity_transforms` then writes the node local from the entity position for every active entity (`entity.c:276`), and `entity_get_transform_matrix` adds no offset (`entity.c:252-262`) → **drawn at y = −0.5** |

The puppet is 3.6 m tall at `PLAYER_SCALE 2`, so it stands ~14% of its own height
clear of the floor it appears to be on; every crate rests the same 0.5 m up. Nobody
caught it because no golden photographs the player against the floor and the `anim`
probes compare bone matrices on the CPU.

**This must be fixed before a foot target means anything** — "plant the foot on the
ground" currently has two different answers in this scene. The fix is one of: move the
floor entity to `(0, 0, 0)` and drop the collider to a top of y=0 by its own extent, or
generate the plane at its collider's top. Whichever is chosen, it moves the player and
the crates half a metre in every windowed frame, so the two gametest goldens are
re-baked in the same commit and nothing else rides along.

## Further constraints

- **`assets/puppet.gltf` is byte-locked.** The `fixture-gen` gate (`gates.py:17165`)
  reruns every `assets/gen_*.py` into a scratch tree and demands byte equality with the
  committed asset. Any rig change goes through `gen_puppet_fixture.py`, never the file.
  Foot planting needs no rig change, but this forecloses "just add an IK bone".
- **Two transforms in the player chain are already owned by other writers.** The entity
  node's local is overwritten every step by `sync_entity_transforms` (`entity.c:276`),
  and `player_rig->original_transform` is rewritten wholesale by the facing-yaw block
  (`gametest.c:1134-1137`) whenever `ground_speed > 0.1`. Only `"puppet_rig"` and the
  joints below it are free to touch.
- **`driven[]` is a trap for anything that writes a `Pose`.** `pose_local`
  (`animation.c:729`) ignores a bone's TRS and copies the bind matrix verbatim unless
  `driven[i]` is set. Only bites if IK writes the pose rather than the globals.
- **Spring bones write `global_transforms` ONLY** — never back into `local_transforms`,
  and never into the `Pose`. So the skinning matrices see the swing and the pose does
  not. That is the precedent IK either follows or deliberately departs from.
- **`Mesh.bone_aabb`** (`mesh.h:178-184`) bounds a posed skinned mesh for culling. §7
  settles that it needs no change, but the question has to be asked of any pass that
  moves a bone.
- **A 34th golden would falsify prose in FOUR places** — `docs/verification.md:11` and
  `:589`, `AGENTS.md:159`, and `AGENTS.md:189`, the last of which states a full breakdown
  ("all 33 are single frames with TAA off, thirty of them static scenes… the thirty-first
  a rig posed purely by frame index… and the last two menus") that a 34th falsifies
  arithmetically, not just numerically. (`verification.md:487` also already says "thirteen
  gate arms" where 14 now run; worth fixing in passing.)
- `--only` is **substring** matching in gates.py and **exact** in goldens.py. No existing
  gate selector contains "ik", so the selector is unambiguous today.

## Design

### 1. IK writes `global_transforms` ONLY — never the `Pose`, never the locals

The decisive fact is rig-specific and easy to miss: **no clip drives `*Leg` or `*Foot`.**
`gait()` animates only `*UpLeg` and `*Arm` plus a Hips height curve, so `driven[i]` is 0
for the knee and ankle in all seven clips — and `pose_local` (`animation.c:729`) discards
a bone's TRS and copies the bind matrix whenever that bit is clear. **A knee rotation
written into the `Pose` would be silently discarded on every frame of every clip.**
Setting `driven=1` to work around it forfeits the decompose/recompose bit-identity
spec 12.1 rests on (`animation.h:221-231`).

Two further arguments point the same way. The solve needs model space, which does not
exist until after the accumulation loop, so a pose-writing IK would need
accumulate → solve → write locals → re-accumulate, two full passes. And a sweep of every
reader confirms **nothing downstream wants the corrected pose**: `prev_bone_rows` derives
from `bone_matrices` and is latched at the top of `animator_update`, `node_set_pose`
installs an `AnimationState*`, and `save.c:467` persists clip name/time/speed/param but no
pose. Writing globals also makes the correction visible for free to the two instruments
that already read them — the bone X-ray (`render.c:2411`) and `--anim-probe`.

### 2. The call site: `animation.c:1041`, AFTER the springs

```c
    if (state->ik)
        ik_solve(state->ik, state->global_transforms, delta_time);
```

Inserted between the spring block closing at `:1040` and `// PASS 2` at `:1042`.

**Before the springs is wrong, and would have been the intuitive choice.**
`spring_bone_update` re-accumulates `global = parent_global * local` for *every
unsimulated bone, unconditionally* (`springbone.c:265-272`) — and the leg joints are
unsimulated, so an earlier IK solve is **erased**. Surviving it would cost a
`glm_mat4_inv` per joint per frame to write locals back, exactly the write-back springbone
refuses. The hazard is latent in gametest (which installs no springs; only
`render.c:3800` does) and live in `apps/render`, so the order is chosen on the mechanism.

The honest cost of running last: springs computed their targets against the pre-IK pose,
so a hair chain lags a pelvis drop by one frame in its *swing* — not in position, since
§3 translates spring-corrected bones along with everything else. A one-frame error in a
damped Verlet target is invisible; an erased swing is not.

**No `animator.c` edit.** Springs reset on a hard cut (`animator.c:212`, `:292`); IK must
not. A cut moves the animated foot but not the *ground*, and the ground is what the target
tracks — so easing across a cut is correct. `ik_reset` stays app-driven (teleport, respawn).

### 3. The pelvis drop is a rigid translation, not a re-accumulation

After the springs have run, `global[i] == global[parent] * local[i]` is **false** for
simulated bones, so a parent-first re-accumulation would wipe every swing. But a pelvis
drop is a *pure translation*, and for a pure translation the product is just the offset
added to the translation column:

```c
for each bone i in the pelvis subtree:
    global_transforms[i][3][0..2] += offset;   // three float adds
```

Exact rather than conservative, no matrix multiply, no inverse, and it composes with
corrections already written — a spring bone's corrected global translates rigidly too.
Subtree membership is resolved once at registration into a `uint8_t
in_pelvis_subtree[MAX_BONES]`, mirroring `animator_mask_subtree` (`animator.c:356`).

Order inside `ik_solve`: ease/snap each target → measure each foot's reach deficit against
the *undropped* hip, scaled by that foot's weight (a foot at weight 0 must not drag the
pelvis) → `drop = min(max deficit, max_pelvis_drop)` → translate the subtree → solve each
chain against the *dropped* hip.

**The drop is what makes the fixture's numbers closed-form.** Without it, on real ground
the sole plane already sits at or below every ray hit, so the solve only ever clamps and no
knee bends at all — the ramp arms would have nothing to assert.

### 4. The solve, and the singularity that is the common case

Law of cosines in model space, lengths measured live from the animated pose. Clamp `dist`
into `[|L1-L2|*(1+1e-4), (L1+L2)*(1-1e-4)]` — on this rig `[0.02, 0.82)` — **and**
`glm_clamp` every cosine before `acosf`. Both, because one ulp past `L1+L2` yields a NaN
that reaches `bone_matrices` and then `prev_bone_rows`, poisoning TAA the *following*
frame as well.

**The bend-plane resolution is inverted from the textbook order.** Hip, knee and ankle are
exactly collinear at bind and no locomotion clip bends the knee, so
`cross(B-A, C-A)` is the zero vector on essentially every frame. The pole-derived axis is
therefore the **primary** path and must be correct, not a fallback:

1. Pole carried in the **hip's own frame** — `pole_model = glm_mat4_mulv3(globals[hip],
   pole_local, 0.0f)`, then `axis = normalize(cross(normalize(d), pole_model))`. Using the
   hip frame rather than a model-space constant means a clip that turns the hips carries
   knee-forward with it. (A model-space constant would also work *in gametest*, since yaw
   lives on `player_rig->original_transform` and never on the bones — a property of the
   app, not the engine, so it must not be baked into the solver.)
2. The current triangle normal, when the clip *has* bent the knee.
3. A `fallback_axis` computed at registration from the bind globals, for a leg pointing
   straight along the pole direction.

Positions become per-joint rotations through springbone's exact idiom
(`glm_quat_from_vecs` → `glm_quat_mat4` → `glm_mat4_mul(rotation, target, out)` →
restore the translation column). cglm's `glm_quat_from_vecs` already handles parallel and
antiparallel inputs, so the rotation construction cannot NaN; the exposure is entirely in
`acosf` and the normalizes.

**Weight blends the TARGET, not the matrices** — `effective = lerp(C, applied_target,
weight)` — because a lerp of two rotation matrices is neither a rotation nor orthogonal.
Skipping the chain entirely at `weight <= 0` also makes weight 0 **bit-identical** to no
IK, which is what preserves the existing goldens.

### 5. `IkSystem` — new `cetra/src/ik.c/.h`, a sibling of springbone

Ownership mirrors springs exactly: a forward decl at `animation.h:147`, a plain
`struct IkSystem* ik;` field at `:169`, `NULL` at `animation.c:457`, freed at `:469`,
installed by a plain write from the app.

```c
IkSystem* create_ik_system(Skeleton* skeleton);
void      free_ik_system(IkSystem* system);
IkFootParams ik_default_params(void);
int  ik_add_foot(IkSystem*, const char* hip, const char* knee, const char* ankle,
                 const vec3 knee_forward);          // foot index, or -1
bool ik_set_pelvis(IkSystem*, const char* pelvis_bone);
void ik_foot_set_target(IkSystem*, int foot, const vec3 target, const vec3 normal,
                        float weight);
void ik_reset(IkSystem*);
void ik_solve(IkSystem*, mat4* global_transforms, float delta_time);
```

`IkFootParams` carries the rig-shaped constants — `reach_limit`, `max_pelvis_drop`,
`teleport_distance`, `blend_rate`, `max_foot_pitch_deg`. The app owns the per-frame
gameplay values: target, normal, weight.

**One deliberate asymmetry with `spring_bone_update`:** no `local_transforms` parameter.
Springbone takes it because it re-accumulates; IK does not, and a parameter with no reader
misstates the contract. Worth a comment, or it reads as an oversight.

Pop mitigation follows `springbone.c:296-300` literally: on `needs_reset`, or when
`|target - applied_target| > teleport_distance`, snap both; otherwise ease at `blend_rate`.

### 6. The raycast stays in the app

`ik.c` includes `animation.h` and cglm and nothing else — it never learns what a
`PhysicsWorld` is. This preserves a property verified across the tree: **no engine file
outside `game/` mentions raycast at all.** The seam is `ik_foot_set_target`, taking plain
`vec3`s.

**Targets must be set in `on_pre_render`, not `on_update`.** `update_all_animators` runs
in `game_pre_render` (`game.c:291`), once per *rendered frame*, and after the app's
`on_pre_render`. `on_update` is the fixed step and may run zero or N times per frame, so
setting targets there hands the single animator tick either a stale target or the last of N.

Per foot: `physics_world_raycast_filtered(..., 1 << OBJ_LAYER_STATIC, &hit)` — the mask
convention is documented at `physics.h:353`. Filtering to static is **required**, not
stylistic: the player's own inner body is created in `OBJ_LAYER_DYNAMIC`
(`character.c:194`), so an unfiltered ray from inside the capsule hits the player. The
consequence to state plainly: **feet plant on the floor and the ramp, not on the crates.**
Then convert the hit into model space — `PLAYER_SCALE` is 2.0, so a missed division reads
as feet over- or under-reaching by exactly 2x and looks like a solver bug.

### 7. `Mesh.bone_aabb` needs no change

`_posed_bounds` (`draw_list.c:337-358`) unions `aabb_transform(bone_aabb[b],
bone_matrices[b])`, and PASS 2 rebuilds `bone_matrices` **from the globals IK just
corrected** — so each moved bone's box is transformed by its moved matrix and the bound
follows automatically. The `aabb_expand` margin exists for wind and the CDLOD morph, which
displace *in the vertex shader* where a CPU bound cannot see them; IK displaces on the CPU
inside the very matrices the bound is computed from. No margin, no new field.

### 8. Rejected alternatives

| rejected | why |
|---|---|
| Write the `Pose` | `driven[]` discards every knee correction on this rig; `driven=1` forfeits 12.1's bit-identity; needs two accumulation passes |
| IK before `spring_bone_update` | springbone's unconditional re-accumulation erases it; surviving costs an inverse per joint per frame |
| Pelvis drop by full re-accumulation | after springs, `global == parent*local` is false for simulated bones, so it wipes every swing |
| N-joint CCD / FABRIK | out of scope; closed-form two-bone is exact and has no convergence knob |
| Hand the engine module the `PhysicsWorld` | would be the first `game/physics.h` include in `cetra/src/`, for a value the app already holds |
| Blend by lerping animated and solved matrices | a lerp of rotations is not a rotation; blending the target also makes weight 0 bit-identical |
| An authored wedge mesh for the ramp | `entity_add_rigid_body` already carries `entity->rotation` into `settings.Rotation`, so a rotated box needs no new asset and a wedge's plane is no more exact |

## Risks

- **The exactly-singular bind is the common case, not an edge case.** Hip-to-ankle is
  exactly `L1+L2` at bind and no locomotion clip bends the knee, so the current-triangle
  bend axis is degenerate on nearly every frame. The pole path must be right; a bug there
  reads as a knee bending sideways or flipping, and "does it usually work" will not catch it.
- **One `acosf` NaN outlives its frame.** A NaN reaching `bone_matrices` propagates into
  `prev_bone_rows` (`animation.c:486`), so it poisons TAA the *following* frame too. Both
  the `dist` clamp and the per-cosine `glm_clamp` are carried for that reason.
- **Foot sliding is NOT solved by this.** Planting the ankle at a raycast point does not
  lock it against horizontal motion; true foot locking is a further step. Stated so it is
  not later filed as a defect.
- **The pelvis drop moves the visual, not the capsule**, so on a steep slope the mesh can
  sink relative to collision. `max_pelvis_drop` bounds it.
- **The target is one frame old by construction** — the raycast runs in `on_pre_render`,
  the solve inside the animator tick that follows.
- **The floor fix moves every windowed frame by 0.5 m.** It is the one change here that
  disturbs the existing corpus, so it lands in its own phase with the goldens re-baked and
  the diffs eyeballed immediately after.
- **`state->ik` stays NULL by default**, exactly the springs precedent — so every existing
  golden is untouched until an app opts in.

## Verification

### The fixture — `--ik-ground`, off by default

**The ramp**: one rotated static box, top plane `y = 0.25·(x − 14)`, slope
`atan(0.25) = 14.0362°`. Half-extents `(6.0, 0.5, 4.0)`, rotation `+atan(0.25)` about +Z,
centre `(18.0, 1.0 − 0.5·√17/4, 0)`. The centre's y is **derived in the source from the
plane**, never written as a literal, so the app carries the ugly constant and the gate
states `y = 0.25(x−14)`. It meets the floor exactly at x=14 (no lip to trip on) and clears
the crates by 0.56 m and the door by 6.9 m.

**The staircase**: three axis-aligned static boxes at x = −15/−17/−19, tops at
0.5/1.0/1.5, each sitting on the floor. Riser 0.5 — under gametest's
`step_height = 0.4 * PLAYER_SCALE = 0.8`, though *not* under the engine default of 0.4,
which wants a comment at the constant.

**The number the group hangs on.** Standing at x=18 (at rest `ground_speed ≤ 0.1`, so the
yaw block does not rewrite `player_rig` and the stance stays axis-aligned), the feet are at
world x = 18.20 and 17.80, so the ground under them is 1.050 and 0.950 — **Δ = 0.100
exactly**, which is `tan θ × stance = 0.25 × 0.40`. Independent of the capsule's resting
height, of Jolt's slop, and of the pelvis drop, because the drop cancels out of a
*difference*. The staircase gives Δ = 0.500 with the uphill foot on the **opposite** side,
so a solver that hardcodes which leg bends passes the ramp and fails the step.

**Why flag-gated.** The menu is drawn over the live scene, and its backdrop is
0.88 × 0.88 = 0.774 opaque — ~22.6% of the world reaches the frame, with the floor plainly
legible in `menu_golden.png` and `AGENTS.md:189` describing both goldens as "menus over a
sim that has advanced thirty steps". The camera reaches nearly the whole 50 m floor, so
there is no out-of-frame corner to hide in. Off by default, the two menu goldens are
unaffected by the fixture and are re-baked only by the floor fix, one phase earlier.

### `--ik-probe <case>` — nine cases, split on whether physics is the point

Six cases (`reach`, `clamp`, `singular`, `identity`, `pole`, `analytic`) build scene +
entity manager only, the `run_anim_probe` shape: the solver is a pure function of
(hip, target, a, b, pole), and giving it physics would make exact math depend on Jolt.
Three (`ground`, `slope`, `step`) add `create_physics_world` + `build_ik_ground`, the
`run_save_probe` shape, because planting's input is a *raycast* and three bug classes live
only there — the ray hitting the character's own capsule, the ray missing the ramp and
finding the floor under it, and a hit point that is right while the plane is wrong.

Grammar `ik <case> <label> <key> <numbers...>` at `%.6f`, read by
`_IK_PROBE = re.compile(r"^ik ([\w-]+) (\w+) (\w+)((?:\s+-?[\d.]+)+)$", re.M)`. A dividend
worth a comment at the regex: that character class admits **no letters and no exponent**,
so a `nan` or `inf` prints a line the regex cannot match, the key vanishes, and the arm's
`key not in d` branch fails it — **NaN is caught by absence on every arm, for free.**

Joint positions are read from `AnimationState.global_transforms`, the space the solver
actually writes, rather than re-derived from `bone_matrices`.

### The `ik` gate group — twelve arms

| arm | asserts | tolerance | why that tolerance |
|---|---|---|---|
| `ik-reach` | ankle lands on target, 9 directions | **< 1e-5 m** | ~10 float ops on values ~1.6 m ⇒ ~2e-6 m; 1e-5 is 5x. Measure the floor before widening |
| `ik-clamp` | beyond reach: straight AND aimed; plus a target **at the hip** (the inner singularity at \|a−b\| = 0.04) | dist < 1e-5, bend **== 0.0**, align > 1−1e-6 | the bend is a clamped *branch* result, so exact 0 is legitimate |
| `ik-singular` | bend at c = 1.64 → 0.000000; at c = 0.04 → 180.000000 | **exact** | both are `acos(∓1)` exactly; the clamp is the point |
| `ik-identity` | re-solve from a **bent** pose changes nothing | **== 0.0 exactly** | the repo's own precedent — an identity asserted to a tolerance is not an identity |
| `ik-pole` | knee goes +Z; reversing the pole reverses it; the span proves it is read at all | ±0.05, span > 0.10 m | expected offset is 0.282 m, so 5.6x inside |
| `ik-analytic` | `acos((c²−a²−b²)/2ab)` at c = 1.62/1.60/1.40/1.20/1.00 → 17.92/25.37/54.72/85.97/104.90° | **worst < 0.05°** | dβ/dc = 449 °/m at the tightest point ⇒ needs c to 1.1e-4 m against a ~4e-6 budget, **28x margin**. Capped at 1.62 because the derivative is unbounded at 1.64 |
| `ik-ray-self` | the foot ray hits the world, not the capsule it was cast from | exact flags | boolean |
| `ik-grounded` | sole pinned through a 2.0 s idle cycle, **and visibly not pinned with IK off** | on < 1e-4 m, off > 0.015 m | the "off" leg has a stated expected value: the authored 0.01 hips amplitude × scale 2 = 0.02 |
| `ik-slope` | ray heights 1.050/0.950, Δ 0.100, uphill knee 40.236°, downhill **0 exactly** | < 1e-4 m, < 0.05° | ray/box is ~1e-6 m; bend sensitivity 203 °/m ⇒ 250x margin |
| `ik-step` | the same at Δ 0.500, uphill knee 91.96°, other leg | as above | the least sensitive point in the design (97 °/m) |
| `ik-repeat` | two `slope` runs print identical digits | **exact** | determinism is yes/no, and the raycast is this feature's one new input |
| `ik-frame` | IK on vs `--no-ik` over the ramp differ in pixels | **≥ 20 px** | `anim-twin`'s bar and rationale; set from a measured floor once frames exist |

Registered as `("ik", "two-bone IK and foot planting (reach, clamp, the singular bind
pose, a ramp of known slope; spec 12.4):", run_ik_gate)`, after `save` and before `import`.

### No new golden — deliberately

The `puppet` golden's argument (CPU numbers pass under a consistently-wrong skinning) is
weaker here: the IK arms read **absolute joint positions in the space the splice writes**,
so a wrong space or bone is a wrong number rather than a matching pair, and pose→GPU for
this rig is already covered. The blocking reason is determinism: `--rebake` renders twice
and refuses any difference, and `verification.md` records gametest pixel counts of
55937 / 35967 / 224729 / 55937 across four runs with the cause **unmeasured**. Baking a
34th golden against an open determinism signal would be refused — correctly — leaving the
phase with nothing. `ik-frame` covers the splice instead: two renders of one build, no
stored reference, no camera flag, no prose to update.

A golden becomes right once someone measures gametest's determinism floor and it comes back
0, *and* `--cam-eye`/`--cam-target` land on gametest for another reason.

### What the gate cannot see

A new `### The foot-planting path` section in `docs/verification.md` after
`### The real-character path`, plus its Contents bullet. Five debts, of which the sharpest
is that **every arm stands the rig still**: foot planting's real failure is temporal —
popping at a nosing, sliding because the target is chased rather than locked — and the
puppet's walk has no contact phase to lock to, since it never bends a knee. Also: the
pelvis drop as a *look* rather than a number; a surface the ray disagrees with (thin
geometry, overhangs, dynamic bodies); that the singular bind makes this rig a severe and
**unrepresentative** instrument, since a real rig is authored with a few degrees of bend
and never visits the singularity; and that nothing plants the *chaser's* feet, which is
the per-entity question `anim-two-rigs` had to ask of the animator. Verdict line:
**Owed. The solver is exact on a ramp nobody has walked up.**

Plus a windowed pass by eye, which is what closes the first of those: popping at the step
nosings, the knee snapping straight as the leg approaches full extension, and the pelvis
failing to drop far enough for the trailing foot to reach.

## Open numbers to measure, not guess

- `ik-reach`'s 1e-5 m and `ik-identity`'s exact 0 assume a closed-form solver that
  short-circuits an already-satisfied target. If quaternion normalisation puts exact 0 out
  of reach, **measure the floor and quote it** — do not widen the bar by guess.
- `ik-frame`'s 20 px is borrowed from `anim-twin`, which passes "by orders of magnitude"
  with unexplained variance. Set it from a measured floor once the frames exist.
- The capsule's resting height on the camber is derived from ideal sphere-on-plane
  tangency and ignores `character_padding`. The probe should **print** it for diagnosis;
  no arm should compare it.

## What changed in implementation

Corrections to the plan above, recorded so this document describes what shipped rather
than what was intended. The design held; the verification did not survive contact.

**`ik-grounded` became `ik-plant`, and its claim shrank.** It was specced as "the sole
stays pinned through a 2.0 s idle cycle, and visibly is not with IK off". The case that
was written poses the rig once and never ticks a clip, so that docstring would have been
a claim the code did not honour. It asserts what is measured: six feet land on the ground
their ray found, to 0.00000000 m.

**`ik-frame` was dropped.** Three reasons, none of them effort. On flat ground the solve
is now an identity by design (0.0198 degrees, the float floor at the singularity), so IK
against `--no-ik` at the default spawn measures nothing; standing the player on the ramp
needs camera and position flags gametest does not have; and `menu`'s 752 px bistability
would sit inside any bar the arm could set. The consequence is stated in
`docs/verification.md`: nothing photographs this feature.

**`ik-swing` was added, and it is the one that matters.** It ticks a walk cycle and
measures the ankle's vertical travel. It exists because the eleven arms this spec planned
all passed while the player's feet were welded to the floor — every one of them poses the
rig once, and a solve that overwrites a stride looks perfect in a single pose. The defect
was found by watching the character, not by the suite.

**Three solver corrections, each found the same way.** The release decision moved from the
caller into `ik_solve`, because a caller can only read the previous frame's solved globals
and a planted foot therefore reads as planted forever. `reach_limit` went from 0.995 to
1.0: near full extension the knee angle goes as the square root of the shortening, so on a
bind pose that is exactly straight, half a percent of length bought an unremovable 11.47
degrees. And the pelvis drop now reads the same faded weight the solve does, since
disagreeing bobbed the whole body at frame rate.

**`max_foot_pitch_deg` was removed and `plant_fraction` added.** Sole-to-normal alignment
is not implemented — the rig states no sole axis and guessing one is worse than leaving
the foot where its clip put it — so a knob nothing read was deleted. `plant_fraction`
replaced it: the height above target, as a fraction of leg length, at which a foot is
released.

**The three physics cases run with release disabled.** They ask whether the solve reaches
the ground it was handed; whether a foot should be planted at all is `ik-swing`'s question.
Mixed together, a foot whose target sits below the clip's fades to partial weight and lands
short, which reads as a solver that misses when it is a release behaving as specified.

**What this is not.** Planting keeps no memory, so a contact point is never held and a
walking character slides — by design, not by defect. `docs/foot-locking.md` records the
technique that closes it and the four specific things missing here. That is its own spec.

**`--ik-ground` was removed after the fact, and the ground is now always in the scene.**
The design above gates the ramp and steps behind a flag to keep them out of the two menu
goldens. That reasoning was sound about the goldens and wrong about the priority: flat
ground is the one configuration where the solve is correctly an identity, so the DEFAULT
scene demonstrated nothing, and running the app with no flags showed a feature that
appeared to do nothing at all. Trading the only demonstration of the work for two
unchanged reference images is the wrong way round. Both goldens were re-baked with the
fixture in frame — `menu` moved 1175 px and `menu_focus` 1241 px, and the other 31 held
at 0 px, which is the containment the flag was protecting.
