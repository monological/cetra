# Spec 11.104 — Orthographic past the jitter: the perspective-only stack

## Context

Spec 11.103 fixed the TAA jitter under an orthographic camera and gave the render app `--ortho
<height>`, then documented the flag as DIAGNOSTIC ONLY because its correctness review found the
rest of the frame still assumed perspective. That caveat lives inside a flag's entry in the CLI
reference and nowhere else, which is the gap this spec closes: a known engine limitation belongs in
the roadmap and, better, in the fix.

Exploration found the surface is larger than the review's four sites, but it collapses:

**Six perspective-only formulas**, and where each lives:

| # | formula | sites |
|---|---|---|
| 1 | NDC-Z → view Z, `-P32/(P22+ndcZ)` | `depth.glsl:12` — one helper, twelve callers (DoF ×2, SSS ×2, soft particles, SSR ×4, water ×2, the CoC helper) |
| 2 | UV + linear Z → view XY, `ndc·(-z)·invFocal` | `depth.glsl:21` (GTAO ×2, contact shadows) and DUPLICATED as `froxelViewPos` in `froxel.glsl:79-84` (fog inject ×3, aerial LUT) |
| 3 | near plane, `P32/(P22-1)` | five hand-rolled copies: `ssr:195`, `contact_shadow:115`, `aerial_lut:38`, `froxel_composite:90`, `postfx.c:2506` |
| 4 | world length → screen length, `k·P00·r/(-z)` | `gtao:212`, `sss_gather:122` (+ `sss_pyr_down:50`, `preintegrated_skin:187`, `pbr_frag:1830` — the same `/depth` family) |
| 5 | UV → view ray, `normalize(vec3(ndc·invFocal, -1))` | `froxel_integrate:46-48` (`rayScale`), `tonemap:378` (spec-occ V); cloud march and ocean grid DEFERRED |
| 6 | per-fragment view vector from the eye point | `pbr_frag:1603` (V) and `:1041` (POM), `water_frag:856`, plus two the review missed: `gtao:176` and `ssr:198` |

**Four CPU sites:** `light_cluster.c:98-101` (the froxel wedge scales with depth), `draw_list.c:192-196`
(LOD by `radius/distance`), `occlusion.c:254-258` (backface test against the eye POINT), and
`shadow.c:341-351` (cascade fit from `tan(fov/2)`, and `set_camera_orthographic` never clears the
stale FOV).

**Already correct, untouched:** attachment 2's linear Z is TRUE view-space z from the vertex stage,
so every consumer that only reads depth is fine; every `projection * vec4(p,1)` then `/w` site;
SSR's `invProjection` unproject (the one agnostic precedent); frustum culling (Gribb-Hartmann off
the VP); occlusion.c's own projection step; refraction's reprojection; motion blur, TAA, TAAU,
spec-occ composite, the hi-Z pyramid.

**What is wrong in `apps/shapes` today, and has always been:** the view vector fans up to 10.6
degrees off the true forward at the frame edges, so the specular highlight drifts across identical
shapes, a flat-on plate carries a false radial Fresnel rim, and GTAO (on by default) integrates over
positions warped by a factor that scales with depth.

## The design: branch on the matrix, perspective untouched

**One predicate, already shipped.** `projection[2][3]` is a literal 0 under `glm_ortho` and -1 under
`glm_perspective`; the jitter lands in `[3][0..1]` or `[2][0..1]` and never here. 11.103 already
selects the jitter element on `draw_projection[2][3] == 0.0f`. Every site below branches on the same
test, which is uniform across a draw and so costs nothing (the 11.93 rule).

**The perspective side of every branch is the current expression, byte for byte.** There is no
general formula and no fallback: the 29 goldens and every jittered gate arm cannot move, by
construction, and the orthographic side is proven by the new arms alone. This is the decision, made
because this tree has measured algebraically-identical arithmetic moving 31,800 px once
(`contact_shadow_frag:222-228`), and byte-identity as a property of the code beats byte-identity
as a test result.

### A. `include/depth.glsl` (the includer already declares `uniform mat4 projection`)

```glsl
bool  projectionIsOrtho()           // projection[2][3] == 0.0
float viewZFromNdcZ(float ndcZ)     // ortho: (ndcZ - P32)/P22   persp: unchanged
float nearPlaneDist()               // -viewZFromNdcZ(-1.0), positive — REPLACES five copies
vec3  viewPosFromLinZ(vec2 uv, float linZ)
                                    // ortho: xy = (ndc - P3x)/Pxx, no depth term (P3x carries
                                    // the ortho jitter, so this reconstructs the jittered raster
                                    // exactly)   persp: unchanged, invFocal folded from 1/Pxx
float screenLengthAt(float r, float viewZ)
                                    // ortho: 0.5*P00*r   persp: 0.5*P00*r/(-viewZ)
vec3  viewRayVecAt(vec2 ndc)        // ortho: (0,0,-1)   persp: (ndc*invFocal, -1), UNnormalised
                                    // so froxel_integrate's rayScale = length() is op-for-op
vec3  viewDirToCamera(vec3 viewPos) // ortho: (0,0,1)    persp: normalize(-viewPos)
vec3  worldDirToCamera(vec3 worldPos, vec3 camPos, mat4 viewM)
                                    // ortho: vec3(viewM[0][2], viewM[1][2], viewM[2][2])
                                    // persp: normalize(camPos - worldPos)
```

`invFocal` is deleted as a parameter and as `tonemap_frag`'s uniform (the helper folds `1/P00`);
`froxelViewPos` in `froxel.glsl` calls `viewPosFromLinZ` instead of duplicating it (`froxel.glsl`
gains the include; include-once is real, `gen_shader_header.py:15-38`). Two shaders need the
`projection` uniform ADDED with a C upload: `tonemap_frag` (replacing the `invFocal` upload at
`postfx.c:3827`) and `sss_pyr_down_frag` (in `postfx_build_sss_pyramid`, which has the matrix).

**The V sign, derived once.** The view matrix's third rotation row is the view-space +Z axis in
world coordinates, i.e. the camera's BACKWARD direction. V points from surface to camera, which
under a parallel projection is that same direction for every fragment — so `V = +row 2`, no
negation. Cross-check: `shadow.c:1567-1569` negates the same row to get FORWARD, and
`mat3(view) * row2 = (0,0,1)`, the view-space V.

### B. Shader sites

- Formula 1: `depth.glsl:12` only. Twelve callers untouched.
- Formula 2: `gtao:172-175, 279`, `contact_shadow:200-201`, `froxel.glsl:79-84`; the four froxel
  callers drop their local `invFocal`.
- Formula 3: the four GLSL copies → `nearPlaneDist()`. `postfx.c:2506` gets the C twin with a
  comment pointing at the GLSL one.
- Formula 4: `gtao:212` → `min(screenLengthAt(radius, linZ), MAX)`. The SSS family: `sss_gather:122`
  divides by `-viewZ` today; it and `sss_pyr_down:50`, `preintegrated_skin:187`, `pbr_frag:1830`
  take a `clipW` that is `-viewZ` under perspective and `1.0` under ortho. `projScale`
  (`postfx.c:1740, 2271`) is already "pixels per world unit at clip w = 1" and stays.
- Formula 5: `froxel_integrate:46-48`, `tonemap:377-378`.
- Formula 6: `pbr_frag:1603` → `worldDirToCamera(WorldPos, camPos, view)`, hoisted above the POM
  block so `:1041` becomes `transpose(TBN) * V`; `water_frag:856` → `viewDirToCamera(ViewPos)`;
  `gtao:176`; `ssr:198` (feeds `reflect` and the probe Fresnel).
- `pbr_frag`'s `projection` is `draw_projection` (`render.c:474`); jitter never touches `[2][3]`.

### C. CPU sites

- **`light_cluster.c:71-111`.** `ClusterFrame` gains `w_per_depth = -P[2][3]` and `w_const =
  P[3][3]`; `_sphere_touches_cluster` scales the wedge by `w = w_per_depth*d + w_const` instead of
  `d`. Reads the MATRIX, not `is_orthographic`, because probe-capture faces re-enter with their own
  90-degree matrix. Perspective: `w = d` exactly.
- **`draw_list.c:192-196`, `draw_list.h`, `render.c:851-857`.** `LodSelect` gains
  `float ortho_height` (0 = perspective); `projected = ortho_height > 0 ? radius/(0.5*ortho_height)
  : radius/distance`. The LOD select has no matrix; `ortho_height` is the exact quantity.
- **`occlusion.c:217-266`, `occlusion.h`, `render.c:100`.** The eye becomes a HOMOGENEOUS point:
  `(position, 1)` perspective, `(view row 2, 0)` orthographic — an eye at infinity — and the
  backface test is one formula, `to_eye = eye.xyz - eye.w * p`. The probe sweep's distance
  (`:665`) measures from the ray's own near anchor rather than the eye.
- **`shadow.c:341-351`, `shadow.h`.** `CascadeCamera` gains `float ortho_height`; the fit BRANCHES:
  ortho half-extents `(h/2·aspect, h/2, (far-near)/2)`, centre at the slice midpoint, radius the
  half-diagonal. `set_camera_orthographic` must NOT touch `fov_radians` — clearing it would discard
  the GUI slider's value for the switch back, and no FOV makes a frustum-sphere fit a box.

### D. Deferred, recorded in the spec and the row, not fixed

The skybox cube (`ibl.c:766-792`, a ±1 cube covers ~1% of an orthographic frame) and the sky
background; the ocean projected grid (`ocean.glsl:197-214`); the cloud march (`cloud_march:50, 68`,
keeps its `invFocal`); the depth-sort key (`draw_list.c:365`, perf only); the gizmo's
`world_per_px` (`render.c:2185, 2357`). An orthographic camera looking at a sky is a design
question, and none of these is a wrong pixel on the content the fix is for.

## The instruments

**Every existing golden and arm is perspective**, so all of them prove the perspective path is
untouched (which the branch form guarantees anyway) and NONE can see whether ortho became correct.
The one ortho arm, `taa-ortho`, compares ortho against ortho and cancels a common-mode error. A
new group `ortho` carries the proof. **Every bar is set against a MEASURED reading on the broken
build** — the arms are written and run BEFORE the fix, in phase 1, and their before-numbers go in
the docstrings.

`--ortho` survives `--cam-eye`/`--cam-target` (the pose hook never touches the projection), so
authored-camera fixtures are usable. All arms run without TAA; expected floor 0 px, measured anyway.

## Risks

- **A site the enumeration missed.** Three agents swept; two extra V sites turned up in the second
  pass. The ortho golden is the net for the next one.
- **`ortho-ao`'s parity is approximate** (±4.3% residual perspective scale at the depth extremes,
  0.8% at the sphere). ε is measured on the fixed build, not derived, and the dark-fraction arm
  carries the discriminating claim.
- **GTAO's early-out** (`gtao:220`) is what the broken build hides behind on deep ortho scenes. It
  stays as it is; the fix makes the radius right so the early-out stops firing.
- **The cascade fit branches rather than generalises**, so the perspective arm stays byte-for-byte;
  the texel snap at `shadow.c:371-373` would turn a one-ULP difference into a texel otherwise.

## As built

Eight commits, one per phase as planned. What the plan got wrong, in the order it was found:

**The instruments (phase 2) lost one arm and inverted one prediction.** `ortho-view-flat` was
dropped: the broken build's Fresnel rim over the flat-on quad read ONE code, not the 3 to 10
predicted, so the arm could not discriminate. `ortho-cluster` predicted the broken wedge would
OVER-assign (every light into every tile, ~6400 indices against the 6144 pool); it under-assigns.
A wedge scaled by depth puts a tile edge at `ndc * depth / P00`, tens of units at the fixture's
depths, so the innermost tiles swallow every light and the outer tiles are empty: 65 indices
against the matched perspective's 709, ratio 0.09. The bar became two-sided (0.5 to 2.0), which
catches both failure directions. `ortho-ao`'s perspective floor was set from a measurement (0.0037
dark fraction, so 0.001) rather than the 0.02 guessed, and its box statistic became a DEFICIT
ratio because a mean absolute difference over the box diluted a 30-code ring to 2.4 codes.
`ortho-dof`'s "sharp passes through" bar was 2.0 codes until the perspective control was measured
at 6.1; it is 12.0. `ortho-lod-height` compared against the wrong reference in its first draft.

**The branch form is not byte-identical, and this is the finding of the spec.** The plan's whole
argument was that a branch whose perspective arm is the previous expression cannot move a golden.
Three moved (water 130 px, DoF 12, skin 9) with the perspective arm never taking the new path,
bisected to `viewZFromNdcZ`: an `if`, a ternary and a coefficient form all move water and skin,
and re-ordering `viewRayVecAt`'s reciprocal did nothing. The compiler re-lowers the divide when
its surroundings change, per program. The depth inverse keeps ONE coefficient form for both
projections, `(P33*ndcZ - P32) / (P22 - P23*ndcZ)`, and the two goldens were re-baked at last-bit
drift with the user's approval ("this difference is so small"). Every OTHER helper's perspective
arm is still the previous expression, and no other golden moved through phases 3 to 7. The
finding is saved beside the helper in `depth.glsl`'s header.

**The 30th golden** is `ortho_shadow`: the dir shadow fixture at `--ortho 12` with GTAO, the

**The reviews found four sites the enumeration missed, and one of them refuted its own
instrument.** Five background reviews ran after phase 7. Four were quality passes and their fixes
are one commit: the harness had transcribed three fixture cameras by hand where `_cscn_camera`
exists to forbid it, copied `_projector` to drop one divide, and rebuilt `render()`'s argv to read
a log line `_import_log` already returns; the near-plane C twin branched where the GLSL has one
coefficient form; the SSS pyramid uploaded the projection per mip; `pbr_frag` computed V twice
where the plan said hoist it; and a dozen comments narrated helpers or mis-attributed the goldens'
movement. The fifth review, on altitude, found what three enumeration sweeps had not: the froxel
fog's history reprojection through the PREVIOUS projection, its phase-function ray direction,
the aerial LUT's path length and direction, and water's optical path (two sites) plus its
short-band fade. All are formula 2's inverse, formula 5 or formula 6 again, in passes no ortho
arm looked at. Three helpers joined `depth.glsl` for them (`viewPathLength`,
`worldRayDirFromEye`, `uvFromViewXY`, and `projectionIsOrthoM` for a matrix that is not the
bound one), every perspective arm the previous text, and the goldens did not move.

**The fog got an instrument; the aerial LUT got a hand check; water refuted its arm.** The
eye-invariance design cannot see the fog or aerial sites, because a froxel's view-space
position does not move with the eye under a parallel projection. `ortho-fog-volume` reads the
fog volume fixture's own box-over-gap contrast under ortho at the authored framing: the broken
history read every cell's past from the centre column and blended the boxes into the gap,
**0.9567 against perspective's 0.5904 (ratio 1.62); fixed, 0.6049 (1.025)**. The aerial LUT
has no fixture where parity is reachable (its scene is 20 km deep and its fog range is a
multiple of the scene radius, so no telephoto eye stays inside it), and was checked by hand
under `--ortho` on its fixture: haze by depth alone, no gradient toward the frame edges. Water's
arm was written, committed failing at **246,444 px**, and could not pass: **226,641** with the
path fixed, then **384,957** with an orthographic branch on the projected grid as well. Two
reasons, both properties of the fixture rather than defects: the water plane CROSSES the near
plane under a tilted parallel view, so the eye's position along the axis decides how much of
the plane is clipped, and the grid is deferred for cause -- under ortho its far-capped rows
spike (fp32 at 1e6 units lands them pixels off) and its uniform lattice moires against the wave
field, which the perspective grid's near-dense rows never showed. The branch was reverted, the
grid stays on the deferred list with those findings, and the water path fix carries the
argument that parallel rays make the path the planar depth. The arm's numbers are kept beside
where it would have lived in `gates.py`.
