# 8.6 Remote Build Orchestration

## Context
`8.0-windows-portability` shipped the cross-platform build: `cetra/src/thread.{c,h}` (portable
pthread shim), `cetra/src/compat.h` (POSIX-call shim), `vcpkg.json`, a `CETRA_DEP_PROVIDER`
auto-switch in `CMakeLists.txt` (pkg-config on macOS/Linux, `find_package`+vcpkg on Windows,
chainloading the vcpkg toolchain when `VCPKG_ROOT` is set), `_POSIX_C_SOURCE` scoped to Linux,
and Jolt/cimgui + cwalk forced to Windows-safe settings. The tree now builds natively on all
three OSes.

What is missing is a way to *drive* the non-host builds from the development machine. Cetra is
developed on macOS; the Linux and Windows builds run on two VMs hosted on the `star` KVM box:
- **linbuild** — Ubuntu 24.04, on the `default` NAT (192.168.122.0/24). `cmake --preset
  linux-debug` builds as-is (native pkg-config path).
- **winbuild** — Windows 11 Pro, on the `winbuild` NAT (192.168.150.0/24); clang-cl / MSVC /
  Windows SDK / vcpkg installed, `VCPKG_ROOT=C:\vcpkg`.
- **star** is the hypervisor and the only route to either VM (both sit behind its NATs); it is a
  jump host, not a build target.

Goal: `build.sh --target macos|linux|windows` from the Mac, building each target on its VM, with
**no hardcoded IP addresses** anywhere in the repo or the developer's config.

Constraint: the macOS/Linux paths must stay byte-identical (the 0-differing-pixels rule). Every
change here is additive — a build.sh flag, a PowerShell entry point, host/ssh config — and does
not touch the shipped engine source.

## Addressing (no hardcoded IPs)
The single source of truth for addresses is `~/.ssh/config` on the Mac; everything else refers to
aliases:
```
Host cetra-host          # hypervisor / jump
    HostName star.local  # mDNS -> tracks star's LAN IP
    User neo
Host cetra-linux         # Linux build VM
    HostName linbuild    # resolved on star via libnss-libvirt
    User neo
    ProxyJump cetra-host
Host cetra-win           # Windows build VM
    HostName winbuild    # resolved on star via libnss-libvirt
    User dev
    IdentityFile ~/.ssh/winbuild
    ProxyJump cetra-host
```
- `ProxyJump` provides reachability (both VMs are behind star's NATs). Under ProxyJump the final
  `HostName` is resolved on the jump host, so the Mac never needs a VM's IP.
- On star: `avahi-daemon` publishes `star.local`; `libnss-libvirt` + an nsswitch `hosts:` entry
  resolve the guest names `linbuild`/`winbuild` to their current leases; DHCP reservations pin
  both VMs' MACs so the names are stable.
- `build.sh` reads `CETRA_LINUX_SSH` (default `cetra-linux`) and `CETRA_WIN_SSH` (default
  `cetra-win`) so the targets can be overridden without editing the script.

## `build.sh --target`
`build.sh` is a thin preset wrapper (`-r/-c/--no-joltc`, `uname`→`${platform}-${type}` preset,
submodule init, `cmake --preset` + `--build`). Add `--target <macos|linux|windows>`:
- Default / target == host platform: the existing local build, unchanged.
- Remote target from the Mac:
  1. `rsync -az --delete` the working tree (exclude `out/ .git my_models/`) to `~/cetra`
     (linbuild) or `C:/Users/dev/cetra` (winbuild). rsync (not a tar re-send) preserves mtimes,
     so remote rebuilds stay incremental.
  2. linux: `ssh cetra-linux 'cd ~/cetra && ./build.sh [-r] [-c]'`.
     windows: `ssh cetra-win 'powershell -ExecutionPolicy Bypass -File
     C:/Users/dev/cetra/tools/build.ps1 [-Release] [-Clean]'`.
  3. Stream the remote output; report the artifact path.
- winbuild has no rsync by default — install a lightweight rsync on the guest so the sync path is
  uniform and incremental.

## `tools/build.ps1` (new)
Windows counterpart to `build.sh`: refresh `PATH` from the registry; locate VS via `vswhere` and
`Enter-VsDevShell -Arch x64` (the `windows-*` presets require the x64 SDK INCLUDE/LIB env); set
`$env:VCPKG_ROOT='C:\vcpkg'` *after* entering the dev shell (so it uses the bootstrapped vcpkg,
not the VS-bundled one Enter-VsDevShell points at); run `cmake --preset windows-debug` +
`cmake --build --preset windows-debug`. Params `-Release`, `-Clean`. First run: vcpkg builds
glfw3/glew/cglm/assimp for `x64-windows-static-md` (~20-40 min), then the source links.

## Files
- `build.sh` — add `--target` + remote dispatch.
- `tools/build.ps1` — new Windows build entry point.
- Out of repo: `~/.ssh/config` (Mac); star host infra (avahi, libnss-libvirt + nsswitch, DHCP
  reservations); winbuild (install rsync, add the Mac's public key).

## Verification
- **macOS determinism:** local `build.sh` → render a known scene and `magick compare -metric AE`
  against the pre-change build = 0 (the source is untouched; this must hold).
- **Linux:** `./build.sh --target linux` → `out/bin/*` on linbuild.
- **Windows:** `./build.sh --target windows` → vcpkg builds the deps, clang-cl links →
  `out/windows-debug/bin/*.exe`; smoke-run one app.
- **Incremental:** touch one `.c`, re-run the remote target → only that translation unit rebuilds.
