# Spec 11.60 — D9: terrain material layers, as a material feature

## Context

`apps/forest`'s terrain is shaded by **albedo (1,1,1) x a per-vertex tint at 2.604 world units**,
with no albedo map, no normal map, and a constant roughness of 0.92 (`forest.c:790`). `g_mat_terrain`
is named exactly twice in the whole file — once to create it, once to attach it — and carries no
texture at all. UV0 is computed, world-continuous across tile seams, and **sampled by nothing**
(`terrain.c:513`). That is why the ground does not hold up close, and no palette fixes it.

11.59 shipped the producer this needs: the erosion bake's **flow / deposit / wear** masks, a pure
clamped `[0,1]` function of position at 1.957 units/texel — *finer than the 2.604-unit vertex grid
that samples them*, so vertex colour is throwing detail away today. They have exactly two readers,
`terrain_tint` and the height probe. Nothing else in the tree touches them.

The roadmap books this as **row 42 / D9, effort M**, and names it the next thing to build.

### The roadmap's own sketch for D9 is wrong, in three specific ways

It calls for a second surface program (`terrain_frag`) that a Material points at. Exploration does
not support that:

1. **The "lighting arrives free" argument counts the wrong half.** `ubo_wire_blocks` really does bind
   all seven UBOs at link (`ubo.c:68-86`) and `uniform_set_*` really is a location-guarded no-op
   (`uniform.c:93-97`) — both confirmed. But those deliver the *data*, not the *code*. The shading
   itself is **~740 lines written inline in `pbr_frag.glsl` with no include behind it**: PCSS/CSM
   (`:574-810`), the clustered light loop body (`:1566-1885`), the IBL split-sum block
   (`:1887-2074`).
2. **The precedent it cites is not one.** It says the program "follows `pbr_skinned`'s pattern".
   `create_pbr_skinned_program` (`program.c:520-531`) compiles **`pbr_frag_shader_str`** — a different
   *vertex* shader over the same *fragment* shader. Exactly not a second fragment shader.
3. **The declaration it says is missing already exists.** `pbr_frag` is at exactly 16/16 (with
   `cloudShadowTex` and `oitMomentTex` already `#define`d onto `sceneColorTex`), so the row is right
   that there is no room for a *new* one. But `maskArray` is a `sampler2DArray` that is **already
   declared, already built and already bound on every draw**, and `mask_layer_for`
   (`mask_array.c:64-73`) dedups by GL id and knows nothing about masks.

**The rule that decides it** is the engine's own, from 11.45 (`ocean.glsl:61-82`): *a cap counted in
declarations is a cap on how many DISTINCT shapes of data a program reads.* Layer maps are the same
shape as mask maps. They are not a new tenant class — they are more tenants.

`water_frag` is the counter-example that proves the boundary rather than contradicting it. It earned
its own program by needing a sampler `pbr_frag` could not spare *and* by having a genuinely different
lighting model, and it **paid**: it does not include `lights_ubo.glsl` at all, lighting from one
`sunDir` (`water_frag.glsl:69-73`) with no clustered lights, punctual shadows, LTC panels or GI. That
trade is right for an ocean and ruinous for the largest opaque surface in the scene. **The test is
whether the lighting model differs, not whether the texture count does.**

**Intended outcome:** terrain that holds up at walking distance, as a general layered-surface
material any Mesh can use — for zero new sampler declarations, zero new units and zero new programs.

## Design

### Layers are tenants of the material texture array

`mask_array` is generalised from "the six masks" into what it structurally already is: the program's
**array-texture pool**. Masks stay its first tenant; layers become its second. Its hard-wired six-slot
driver (`mask_array.c:91-101`) grows a second walk over each material's layer set. `mask_layer_for`,
the allocation, the `mask_copy` blit pass and the `async_loader_is_busy` deferral are all reused
unchanged.

**Two array layers per material layer**, so four material layers cost eight:

| array layer | rgb | a |
|---|---|---|
| `2i + 0` | albedo (stored non-sRGB, decoded in shader) | **height**, for height-blending |
| `2i + 1` | normal.xy + roughness.z | ao |

Storing albedo non-sRGB and decoding in the shader is not a workaround — it is the established
pattern the stochastic path already uses (`pbr_frag.glsl:1012-1024`), proven end to end in
`apps/tree`.

### Weights come from a splat layer, not from vertex colour

The splat map is **another layer in the same array**, sampled by a world-space UV: `rgb` = three
weights, base = `1 - sum`. Chosen over vertex colour for three reasons — the erosion field is finer
than the vertex grid, weights survive LOD (`lod.c` rewrites indices only, so lower levels just
interpolate further), and vertex colour is a trap here: `pbr_frag.glsl:1036` runs `sRGBToLinear` over
it unconditionally, so a 0.5 weight would arrive as 0.214.

The array is `GL_REPEAT`, so the splat UV is clamped in the shader — one `clamp()`, because the map is
only ever addressed over `[0,1]`.

### Blending is height-weighted, not a lerp

`b_i = w_i + h_i * sharpness`, keep `b_i` within `blendRange` of `max(b)`, normalise. This is the
single cheapest quality jump available: gravel interlocks with sand instead of averaging into mud.
A linear lerp is kept reachable so the gate can compare against it.

### Triplanar, gated on slope

Confirmed greenfield — zero hits for triplanar / world-aligned anywhere in `cetra/shaders` or
`cetra/src`. Terrain's UV0 is a top-down projection (`x*0.05, z*0.05`), so a 80-degree cliff stretches
its texture 5.8x. New `include/triplanar.glsl`; the side projections are skipped where their blend
weight is negligible, so flat ground pays one tap set and cliffs pay three.

### `terrain_tint` changes only when layers are present

A layered terrain writes **macro variation** into vertex colour (the two Perlin fields, centred on
white) instead of a material colour, since the layers now carry material identity and applying both
would double-darken. Gated on a new `TerrainParams` flag, so **the un-layered path stays byte-identical**
and every existing frame is untouched.

### Scatter reads the masks

A live inconsistency 11.59 introduced and left open: `terrain_tint` paints a stream channel where
`flow > 0.58`, and `sample_ground` (`forest.c:313-332`) then plants a tree in it, because a channel bed
is flat and flat passes the slope gate. Same for scoured bedrock. `sample_ground` gains the mask
reads — `terrain_mask_at` already has the exact signature shape it calls `terrain_normal_at` with.

## The fixture

`assets/layer_fixture.cscn` over a layered quad, with layer maps as small **painted** PNGs written by
`assets/gen_layer_fixture.py` with asserts — ground truth is a closed form, the way
`gen_terrain_fixture.py` and `gen_ies_fixture.py` already work. It renders in the `render` app, so
unlike anything hosted in `apps/forest` it is pixel-deterministic and can carry a **golden**. Forest
keeps generating its own layers procedurally in C; both feed one array.

| arm | asserts | rejects |
|---|---|---|
| `layers-off` | a material with no layers is **0 px** against today | the feature disturbing the existing path |
| `layers-select` | each patch resolves the layer its splat selects | channel order, layer indexing, base-weight arithmetic |
| `layers-height` | the interlock is sharp; a linear-lerp leg fails it | height-blend silently degrading to a lerp |
| `layers-triplanar` | a steep face reads unstretched; the planar leg fails it | the projection never actually running |
| `layers-srgb` | a mid-grey layer round-trips; a hardware-decode leg fails it | the double-decode trap |
| `terrain-layer-probe` | resolved weights equal `terrain_mask_at` at sampled points | a splat baked at the wrong scale or transposed |
| `forest-scatter-channel` | tree count in high-flow cells drops to zero | the scatter/tint inconsistency returning |

Each arm gets a named one-line mutation that must turn it red, per project convention. `layers-off`
and the 24 existing goldens are the identity claims.

## Verification

```bash
./build.sh                                    # release too, for any timing quoted
python3 scripts/goldens.py                    # all 24 at 0 px -- nothing authors layers
python3 scripts/gates.py --only layers,terrain,forest,fixture-gen,gate-docs
python3 scripts/gates.py                      # once, at the end
```

- **All 24 goldens 0 px**, plus the new one. With no layer set the path must be byte-identical.
- **`apps/forest --render-mode 6` must stay 0 px** — it is forest's only pixel-deterministic
  instrument (the Hillaire sky puts the ordinary path at ~35,000 px run-to-run), and it is the albedo
  view, so the layer blend has to be visible in it or the arm reads nothing. Measure the floor at the
  exact framing first.
- The array's canonical size and memory are **logged at build**, because one size serves every layer
  and adding large layers to a scene with small masks promotes them all. This is the design's one
  real cost and it is reported rather than assumed.
- No GPU work while gates run.
