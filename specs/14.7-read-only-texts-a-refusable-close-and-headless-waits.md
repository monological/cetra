# 14.7: read-only texts, a refusable close, and headless waits

## Context

pcb's window (pcb spec 6.1) was reviewed, and four of its findings were changes to cetra, not
pcb. Three are wanted now and are this spec; the fourth goes with pcb's next spec.

- **A read-only text.** pcb's messages pane is a code editor on a text the window writes, and a
  person must not type into it. Today pcb puts the text back every frame over anything typed: vim
  thinks it deleted a line, and a frame later the line is back. pcb's conflict pane, which shows
  what the disk holds of a file, has no such guard at all. cetra's text field already has a
  read-only flag (`UI_FIELD_READ_ONLY`); the editor and its text have none.
- **A close the app can refuse.** When a file is in conflict and what was typed in it is not saved,
  pcb refuses its own Cmd+Q and `:qa`. But the window's close button closes the window anyway, and
  nothing in cetra lets the app say no. On macOS, Cmd+Q from the app menu is the same close request
  (below), so pcb's own refusal may never even see that key.
- **Headless frames that wait for work.** Under idle mode, a headless run keeps drawing frames while
  an input script runs, even with work out. So a scripted frame N may or may not see the result of
  work begun in frame N-1, depending on how fast the machine is. pcb makes its main thread wait in
  two places so its window tests repeat. cetra's canvas app has `--editor-lag` for the same reason.
  Each app writing its own wait is the engine's job left undone.

The fourth finding, host key sequences in the vim mode for pcb's `gd` and its leader key, waits for
pcb's spec 6.2, which adds view keys and will want them too.

Branch `14.7-read-only-texts-a-refusable-close-and-headless-waits`.

## Found while planning

- **Every edit a person makes enters through one call**: `text_doc_apply` (`text_doc.c:785`), with
  undo and redo through `text_doc_undo_in` and `text_doc_redo_in` (`text_doc.c:899-911`). The host's
  own edits are `text_doc_replace` and `text_doc_set_text`. A guard already stands at the door:
  `_may_change` (`text_doc.c:738`), which refuses a change made from inside `on_action`.
- **On macOS, the app menu's Quit is a close request on every window.** GLFW's
  `applicationShouldTerminate` (`ext/glfw/src/cocoa_init.m:402`) calls `_glfwInputWindowCloseRequest`
  for each window and cancels the termination. So the close button and Cmd+Q from the menu reach the
  app the same way: the window's should-close flag is set unless a close callback clears it. cetra
  installs no close callback; the loop simply ends when the flag is set (`engine.c:3630`).
- **The idle loop draws while an input script runs, work or no work**: `_engine_idle_next`
  (`engine.c:968`) returns `IDLE_DRAW` whenever `_engine_input_script_running`, before it looks at
  `work_out`. With no script running, a headless run already waits for work.
- **`--editor-lag` has a second use besides repeating**: the gate arm `ui-editor-ranges-late`
  (`gates.py:29527`) uses it to make a parse's result arrive six frames late on purpose, to test
  that results from an older version land where the typing since moved them. So the flag stays,
  even though repeating no longer needs it.
- **`engine_end_work` asks for a frame before it lowers the count** (`engine.c:1058-1074`), and
  the idle decision reads the count before the request. That order is what stops a headless run
  ending before a result is drawn: the loop sees either the work still out or the request already
  made. Part 3 makes work out a reason to wait even with a frame asked for, and then the order alone
  can hang a run (below).
- **The texture loader's count drops only when a frame delivers** (`async_loader.c:684`): a decode
  finished on its thread still counts until the main thread has uploaded it and run its callbacks,
  inside a frame. A wait on that count would wait for a frame it stops from drawing.
- **The text field copies on a read-only cut** (`ui_field.c`, the Cmd+X case): the selection is
  copied, and cut only when the field is not read-only.
- **The input script's lines are frame ranges** (`frame_script_at`): a token holds for every frame
  of its line's range, so a `close` has to act once, on the range's first frame.
- **Vim 9.2 with `'nomodifiable'`**, run here on a two-line text from its start, each command fed
  as typed, then `w`:

  | command | text | register | after it |
  |---|---|---|---|
  | `dd`, `x`, `dw`, `vd`, `cw`, `p`, `u` | unchanged, E21 | unchanged | normal mode |
  | `yy` | unchanged, no error | the line | normal mode |
  | `i`, `o`, `A`, `s`, `cw` | unchanged, E21 | unchanged | normal mode: the `w` moved the cursor |
  | `iab`, then `'nomodifiable'` set, then `cd`, Esc | `ab` typed, `cd` refused, E21 | -- | insert mode until the Esc |

  So a refused change yanks nothing, a command that would enter an insert stays in normal mode,
  and a text made read-only during an insert leaves the insert open and refuses each character.

## The design

### 1. A read-only text (`text_doc.c`, `ui_editor.c`, `ui_editor_vim.c`)

- **`TextDoc.read_only`**, a plain setting, false by default. While it is true, every change a
  person makes through an editor is refused: `text_doc_apply` and the editor's undo and redo do
  nothing and return false. The host's own changes, `text_doc_replace` and `text_doc_set_text`,
  still go through: the host is what keeps the text, as pcb appends its messages. `text_doc_undo`
  and `text_doc_redo` called by the host also go through, since the host asked for them.
- **A refusal is told to the host**, once per refused action, through
  `text_doc_set_on_refused(doc, fn, user)`. The host says it however it says things; pcb's status
  line would say the messages are read only. A refusal is not an error, so nothing is logged.
  `text_doc_apply` tells it for the refusals it makes. For one the text never sees -- the vim
  mode's `i`, which changes nothing by itself -- the private `text_doc_refuse(doc)`
  (`text_doc_edit.h`) tells it, so there is one path to the host either way.
- **The editor in a read-only text**: carets, selections, scrolling, find and copy all work as
  usual. In the standard mode, typing, paste, delete and the editing commands change nothing, each
  keystroke's action one refusal, however many carets it has. **Cut copies the selection and
  refuses the delete**, as the read-only text field does.
- **The vim mode in a read-only text** does what vim does with `'modifiable'` off (its E21), as
  measured above:
  - motions, search, the visual modes, yank and `:` work;
  - the commands that change the text (`x`, `d`, `c`, `p`, `r`, `J`, `>`, `<`, `~`, `.`, and `u`
    and Ctrl+R unless the host took them with `ui_editor_vim_set_undo`) change nothing and **yank
    nothing**: the clipboard keeps what it held;
  - the commands that would enter insert mode (`i`, `a`, `o`, `O`, `I`, `A`, `s`, `S`, `C`, and
    `c` with a motion) stay in normal mode rather than enter an insert that cannot type;
  - each command is one refusal, even one made of several actions. So the mode asks whether the
    text is read-only before it runs a command, rather than letting each of its actions be refused;
  - **a text made read-only during an insert leaves the insert open**: each character typed is
    refused, and Esc leaves it as usual.
- Whether the editor shows a read-only text differently -- a dim caret, a mark in the gutter -- is
  left to the host's theme. Nothing is drawn differently by default.

### 2. A close the app can refuse (`engine.c`)

- **`engine_set_close_hook(engine, fn, user)`**, with
  `typedef bool (*EngineCloseFn)(Engine* engine, void* user)` returning true to close. It is called
  when the window system asks the window to close: the close button everywhere, Alt+F4 on Windows
  and Linux, and on macOS the app menu's Quit and its Cmd+Q. GLFW sends all of them as one close
  request. cetra installs a GLFW close callback that asks the hook; when the hook says no, it
  clears the window's should-close flag and asks for a frame, so the app can say why it stayed
  open. With no hook installed, the window closes as it does now.
- **It is not asked when the engine or the app itself ends the run**: the frame limit
  (`exit_after_frames`), and an app setting the should-close flag itself. Those are the app
  deciding, which is what pcb's `:qa!` is.
- **Headless, a test can ask**: the input script gains a `close` token, which asks the hook exactly
  as the close button would, once, on the first frame of its line's range. A headless run receives
  no close requests from anywhere else.
- A game can use the hook too: silent, for instance, could save before it closes. Nothing in this
  spec changes any game.

### 3. Headless frames that wait for work (`engine.c`)

- **Headless, under idle mode, while work is out (`engine_begin_work` not yet ended), the next frame
  waits for it**, whether or not an input script is running. So work begun in frame N has always
  landed by frame N+1, on any machine. A window is unchanged: it never waits for work, since input
  has to reach the screen within a frame.
- **`engine_end_work` wakes the loop a second time, after it lowers the count.** The request still
  comes first, so the loop still cannot end a run before the result is drawn. But a loop that wakes
  on that request before the count is lowered sees the work still out and waits again, and with
  only the one wake nothing would wake it after. The second wake is that missing one. It is a race
  no arm can force, so the code states the argument beside the two wakes.
- **Only the work an app counts** with `engine_begin_work` is waited for. The texture loader's
  decodes are not: its count drops only when a frame delivers a texture, so a wait on it would
  never end. A test that needs its textures in asks with `engine_finish_texture_loads`. The `idle`
  and `canvas` arms are re-run with this change; any that reads otherwise is examined, not
  re-baked.
- **A run whose work never ends waits for it, and after ten seconds says so once**, naming how much
  work is out, so a hung test names its cause rather than only timing out.
- `--editor-lag` stays (above); its comment loses "so a headless run repeats".

### 4. What pcb does with this, in its own spec, not this one

- Makes its messages and its conflict pane read-only, and drops the putting-back each frame.
- Refuses a close while a file is in conflict, through the hook, so the close button and the
  macOS menu's Cmd+Q are refused as its own Cmd+Q and `:qa` are.
- Drops its two headless waits (`disk_frame`, `code_evaluate`).

## Tests (no window unless said)

- **`text-doc-read-only`**:
  - an editor action on a read-only text is refused, its version unchanged;
  - undo and redo from an editor are refused;
  - `text_doc_replace` and `text_doc_set_text` from the host still change it;
  - `on_refused` is called once per refused action, and never for the host's changes;
  - with `read_only` false, nothing differs from before.
- **`ui-editor-read-only`**, through the canvas app's editor (`--read-only`, below) and an input
  script: typing, Backspace, paste and cut change nothing; a selection copied, and one cut, reach
  the clipboard; the caret moves; a keystroke at three carets is one refusal.
- **`ui-vim-read-only`**, in two halves:
  - through `--vim` and a script: `x`, `dd`, `p`, `.` and `cw` change nothing and leave the
    clipboard as it was; `i` and `o` stay in normal mode; `/`, `j`, `v` and `y` work, the yank on
    the clipboard; a command of several actions is one refusal; a text made read-only during an
    insert refuses what is typed and leaves the insert open until Esc.
  - against vim: a set of the oracle's cases run again on a read-only text, beside vim with
    `'nomodifiable'`, text and cursor compared byte for byte as `ui-vim-oracle` compares them.
  The existing vim oracle arms are unaffected, since they never set `read_only`.
- **`engine-close-hook`**: the canvas app with `--refuse-close` refuses the first close and accepts
  the next. An input script's `close` at frame 5 leaves the run going and is printed as refused; a
  second `close` ends it. Without the flag, `close` ends the run at once. A `close` on a line
  spanning several frames asks once.
- **`idle-work-waits`**: the canvas app under `--idle` with its board filled on a thread
  (`--edit-thread`), made slow on purpose (`--work-delay MS`, below). A script reading the board in
  the frame after the work began finds it filled at a delay of 0 and at 300 ms alike.
