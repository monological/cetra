# 14.7: read-only texts, a refusable close, and headless waits

## Context

pcb's window (pcb spec 6.1) was reviewed, and four of its findings were changes to cetra, not
pcb. Three are wanted now and are this spec; the fourth goes with pcb's next spec.

- **A read-only text.** pcb's messages pane is a code editor on a text the window writes, and a
  person must not type into it. Today pcb puts the text back every frame over anything typed: vim
  thinks it deleted a line, and a frame later the line is back. pcb's conflict pane, which shows
  what the disk holds of a file, has no such guard at all. cetra's text field already has a
  read-only flag (`UI_FIELD_READ_ONLY`); the editor and its text have none.
- **A close the app can refuse.** When a file is in conflict and what was typed in it is not saved,
  pcb refuses its own Cmd+Q and `:qa`. But the window's close button closes the window anyway, and
  nothing in cetra lets the app say no. On macOS, Cmd+Q from the app menu is the same close request
  (below), so pcb's own refusal may never even see that key.
- **Headless frames that wait for work.** Under idle mode, a headless run keeps drawing frames while
  an input script runs, even with work out. So a scripted frame N may or may not see the result of
  work begun in frame N-1, depending on how fast the machine is. pcb makes its main thread wait in
  two places so its window tests repeat. cetra's canvas app has `--editor-lag` for the same reason.
  Each app writing its own wait is the engine's job left undone.

The fourth finding, host key sequences in the vim mode for pcb's `gd` and its leader key, waits for
pcb's spec 6.2, which adds view keys and will want them too.

Branch `14.7-read-only-texts-a-refusable-close-and-headless-waits`.

## Found while planning

- **Every edit a person makes enters through one call**: `text_doc_apply` (`text_doc.c:785`), with
  undo and redo through `text_doc_undo_in` and `text_doc_redo_in` (`text_doc.c:899-911`). The host's
  own edits are `text_doc_replace` and `text_doc_set_text`. A guard already stands at the door:
  `_may_change` (`text_doc.c:738`), which refuses a change made from inside `on_action`.
- **On macOS, the app menu's Quit is a close request on every window.** GLFW's
  `applicationShouldTerminate` (`ext/glfw/src/cocoa_init.m:402`) calls `_glfwInputWindowCloseRequest`
  for each window and cancels the termination. So the close button and Cmd+Q from the menu reach the
  app the same way: the window's should-close flag is set unless a close callback clears it. cetra
  installs no close callback; the loop simply ends when the flag is set (`engine.c:3630`).
- **The idle loop draws while an input script runs, work or no work**: `_engine_idle_next`
  (`engine.c:968`) returns `IDLE_DRAW` whenever `_engine_input_script_running`, before it looks at
  `work_out`. With no script running, a headless run already waits for work.
- **`--editor-lag` has a second use besides repeating**: the gate arm `ui-editor-ranges-late`
  (`gates.py:29527`) uses it to make a parse's result arrive six frames late on purpose, to test
  that results from an older version land where the typing since moved them. So the flag stays,
  even though repeating no longer needs it.
- **`engine_end_work` asks for a frame before it lowers the count** (`engine.c:1058-1074`), and
  the idle decision reads the count before the request. That order is what stops a headless run
  ending before a result is drawn: the loop sees either the work still out or the request already
  made. Part 3 makes work out a reason to wait even with a frame asked for, and then the order alone
  can hang a run (below).
- **The texture loader's count drops only when a frame delivers** (`async_loader.c:684`): a decode
  finished on its thread still counts until the main thread has uploaded it and run its callbacks,
  inside a frame. A wait on that count would wait for a frame it stops from drawing.
- **The text field copies on a read-only cut** (`ui_field.c`, the Cmd+X case): the selection is
  copied, and cut only when the field is not read-only.
- **The input script's lines are frame ranges** (`frame_script_at`): a token holds for every frame
  of its line's range, so a `close` has to act once, on the range's first frame.
- **Vim 9.2 with `'nomodifiable'`**, run here on a two-line text from its start, each command fed
  as typed, then `w`:

  | command | text | register | after it |
  |---|---|---|---|
  | `dd`, `x`, `dw`, `vd`, `cw`, `p`, `u` | unchanged, E21 | unchanged | normal mode |
  | `yy` | unchanged, no error | the line | normal mode |
  | `i`, `o`, `A`, `s`, `cw` | unchanged, E21 | unchanged | normal mode: the `w` moved the cursor |
  | `iab`, then `'nomodifiable'` set, then `cd`, Esc | `ab` typed, `cd` refused, E21 | -- | insert mode until the Esc |

  So a refused change yanks nothing, a command that would enter an insert stays in normal mode,
  and a text made read-only during an insert leaves the insert open and refuses each character.

## The design

### 1. A read-only text (`text_doc.c`, `ui_editor.c`, `ui_editor_vim.c`)

- **`TextDoc.read_only`**, a plain setting, false by default. While it is true, every change a
  person makes through an editor is refused: `text_doc_apply` and the editor's undo and redo do
  nothing and return false. The host's own changes, `text_doc_replace` and `text_doc_set_text`,
  still go through: the host is what keeps the text, as pcb appends its messages. `text_doc_undo`
  and `text_doc_redo` called by the host also go through, since the host asked for them.
- **A refusal is told to the host**, once per refused action, through
  `text_doc_set_on_refused(doc, fn, user)`. The host says it however it says things; pcb's status
  line would say the messages are read only. A refusal is not an error, so nothing is logged.
  `text_doc_apply` tells it for the refusals it makes. For one the text never sees -- the vim
  mode's `i`, which changes nothing by itself -- the private `text_doc_refuse(doc)`
  (`text_doc_edit.h`) tells it, so there is one path to the host either way.
- **The editor in a read-only text**: carets, selections, scrolling, find and copy all work as
  usual. In the standard mode, typing, paste, delete and the editing commands change nothing, each
  keystroke's action one refusal, however many carets it has. **Cut copies the selection and
  refuses the delete**, as the read-only text field does.
- **The vim mode in a read-only text** does what vim does with `'modifiable'` off (its E21), as
  measured above:
  - motions, search, the visual modes, yank and `:` work;
  - the commands that change the text (`x`, `d`, `c`, `p`, `r`, `J`, `>`, `<`, `~`, `.`, and `u`
    and Ctrl+R unless the host took them with `ui_editor_vim_set_undo`) change nothing and **yank
    nothing**: the clipboard keeps what it held;
  - the commands that would enter insert mode (`i`, `a`, `o`, `O`, `I`, `A`, `s`, `S`, `C`, and
    `c` with a motion) stay in normal mode rather than enter an insert that cannot type;
  - each command is one refusal, even one made of several actions. So the mode asks whether the
    text is read-only before it runs a command, rather than letting each of its actions be refused;
  - **a text made read-only during an insert leaves the insert open**: each character typed is
    refused, and Esc leaves it as usual.
- Whether the editor shows a read-only text differently -- a dim caret, a mark in the gutter -- is
  left to the host's theme. Nothing is drawn differently by default.

### 2. A close the app can refuse (`engine.c`)

- **`engine_set_close_hook(engine, fn, user)`**, with
  `typedef bool (*EngineCloseFn)(Engine* engine, void* user)` returning true to close. It is called
  when the window system asks the window to close: the close button everywhere, Alt+F4 on Windows
  and Linux, and on macOS the app menu's Quit and its Cmd+Q. GLFW sends all of them as one close
  request. cetra installs a GLFW close callback that asks the hook; when the hook says no, it
  clears the window's should-close flag and asks for a frame, so the app can say why it stayed
  open. With no hook installed, the window closes as it does now.
- **It is not asked when the engine or the app itself ends the run**: the frame limit
  (`exit_after_frames`), and an app setting the should-close flag itself. Those are the app
  deciding, which is what pcb's `:qa!` is.
- **Headless, a test can ask**: the input script gains a `close` token, which asks the hook exactly
  as the close button would, once, on the first frame of its line's range. A headless run receives
  no close requests from anywhere else.
- A game can use the hook too: silent, for instance, could save before it closes. Nothing in this
  spec changes any game.

### 3. Headless frames that wait for work (`engine.c`)

- **Headless, under idle mode, while work is out (`engine_begin_work` not yet ended), the next frame
  waits for it**, whether or not an input script is running. So work begun in frame N has always
  landed by frame N+1, on any machine. A window is unchanged: it never waits for work, since input
  has to reach the screen within a frame.
- **`engine_end_work` wakes the loop a second time, after it lowers the count.** The request still
  comes first, so the loop still cannot end a run before the result is drawn. But a loop that wakes
  on that request before the count is lowered sees the work still out and waits again, and with
  only the one wake nothing would wake it after. The second wake is that missing one. It is a race
  no arm can force, so the code states the argument beside the two wakes.
- **Only the work an app counts** with `engine_begin_work` is waited for. The texture loader's
  decodes are not: its count drops only when a frame delivers a texture, so a wait on it would
  never end. A test that needs its textures in asks with `engine_finish_texture_loads`. The `idle`
  and `canvas` arms are re-run with this change; any that reads otherwise is examined, not
  re-baked.
- **A run whose work never ends waits for it, and after ten seconds says so once**, naming how much
  work is out, so a hung test names its cause rather than only timing out.
- `--editor-lag` stays (above); its comment loses "so a headless run repeats".

### 4. What pcb does with this, in its own spec, not this one

- Makes its messages and its conflict pane read-only, and drops the putting-back each frame.
- Refuses a close while a file is in conflict, through the hook, so the close button and the
  macOS menu's Cmd+Q are refused as its own Cmd+Q and `:qa` are.
- Drops its two headless waits (`disk_frame`, `code_evaluate`).

## Phase 1: the read-only text, as built

`e38c4610`, `762d8530`, `1b97e62f`.

**The text.** `TextDoc.read_only` is a setting, and `text_doc_set_on_refused` installs a
`TextDocRefusedFn(doc, editor, user)`, the editor named when there is one. `text_doc_apply` with any
edits, `text_doc_undo_in` and `text_doc_redo_in` refuse while it is set and tell the hook. The
host's `text_doc_replace`, `text_doc_set_text`, `text_doc_undo` and `text_doc_redo` go through. The
private `text_doc_refuse(doc, view)` tells a refusal the text never saw.

**The standard mode needed nothing.** Every edit reaches `text_doc_apply`, a refused one already
left the carets where they were, and cut already copied before it deleted.

**The vim mode** refuses through one `_refused(c, kept)`, before anything of the command is done:
- in `_operate_on`, after the carets are at the operator's start, which is where vim's E21 leaves
  the cursor and how a visual command lets its area go;
- in `_block_operate`, `_put`, `_join`, `_replace`, `_tilde` and the charwise visual replace;
- in the visual put, as the delete under it;
- in normal mode's `i a I A o O`, before the cursor moves.

`u` and Ctrl+R needed nothing: they run the editor's undo, the text refuses it, and `3u` stops at
the first.

**Where vim, measured, differs from this spec's design:**
- **A refused command is what `.` makes again.** After a refused `x`, `dw`, `vld`, `p` or `ciw`,
  `.` on the text made modifiable again makes it. So `_refused` keeps the command, unless it would
  have begun an insert, which vim never reaches. `.` on a read-only text makes it again, refused
  again, and the rest of the replay is dropped through the `failed` stop `.` already had, as vim's
  error drops it. The first draft refused `.` up front, and the oracle found `ciwZ<Esc>w.` landing
  where vim's did not.
- **A visual or block `I` or `A` begins its insert**, where vim refuses each character typed. The
  design listed `I` and `A` among the commands that stay in normal mode, which is true of normal
  mode's alone.
- **A block `A` whose top line stops short of the block is refused before its insert.** Vim pads
  that line before the insert can begin, which E21 refuses, and leaves the cursor on the line's
  last character in normal mode.
- On a read-only text a block insert makes no room, no padding and no tab split, so it asks for
  nothing the text would refuse, and its carets stand where the room would begin.

**Found on the way, in 14.5's vim mode on a writable text.** The read-only oracle exposed both,
since nothing ever goes in there:
- A block `I` or `A` that typed nothing ended at the block's corner. Vim ends it as any insert: the
  cursor one left of its caret. `_leave_insert` now asks whether anything went in by the text's
  length, as vim does.
- An empty block `A` took its top line's padding back out. Vim keeps it, having made it before the
  insert began (`762d8530`).

Four empty block inserts are in the oracle corpus now (`<C-v>jI<Esc>`, `<C-v>jlA<Esc>`,
`<C-v>j$A<Esc>`, `<C-v>jjlA<Esc>`); the corpus had none.

**The canvas app**: `--read-only`. Each refusal is counted and said on the vim line ("Cannot make
changes, the text is read only"). The probe prints `canvas editor refused N` and
`canvas editor clip HEX`.

**Arms**, under names other than the plan's where the group's own names differ:
- `ui-doc-read-only` (planned as `text-doc-read-only`; the ui group's text arms are `ui-doc-*`).
- `ui-editor-read-only`: typing, Backspace, cut and paste change nothing; Cmd+D's word copied and
  cut to the clipboard; four refusals.
- `ui-vim-read-only`: the `vim-read-only` probe and the canvas app by a script.
- `ui-vim-read-only-oracle`: an arm of its own, as `ui-vim-oracle` and `ui-vim-random` are, so it
  skips alone without vim. It runs the whole corpus on a read-only text beside vim with
  `'nomodifiable'`: 6,672 cases, 0 differing. Three sequences are left out by name, and the arm
  fails if they leave the corpus: `Goq) (z)<Esc>^da(`, `Goq) (z)<Esc>^di(` and
  `Goq (z)<Esc>^da(`. With their `o` refused, what they would insert is read as commands, and it
  holds `q` and `(`, a macro and a sentence motion the mode leaves out.

**Falsified**, each broken in the committed code, then restored:
- **The text's refusal off:** `doc-read-only` reads 0 throughout.
- **Normal mode's `i` refusal off:** the canvas script ends in insert mode with 11 refusals, not 7.
- **The empty block insert's ending off:** the four empty block inserts differ from vim, writable
  and read-only.
- **A refused command not kept:** the probe's "`.` makes it again" still passed. Its last refused
  command was visual, and the visual path keeps its change itself. The probe now ends on a refused
  `5J` (`1b97e62f`), and broken again it reads `repeat kept 0`.

**The look**: the canvas app on `text_doc.h` under `--read-only --vim`, after `x`. The `#` is still
there, and the line under the editor says why.

**Verification**: `ui`, `canvas`, `idle` and `gate-docs` pass. `ui-vim-oracle` passes 6,708 cases
and `ui-vim-read-only-oracle` 6,672.

## Phase 2: the refusable close, as built

`d6ce68f4`.

- **`engine_set_close_hook` and `EngineCloseFunc`** (planned as `EngineCloseFn`; the header's
  callback types are `...Func`). The hook and its user are BY FUNCTION fields.
- **A GLFW close callback asks the hook.** Refused, it clears the window's should-close flag, which
  GLFW sets before it calls back, and asks for a frame.
- **The input script's `close`** asks once, on the first frame of its range. It is asked as that
  frame ends, before the frame limit, which a refusal must not undo. So a close that is taken makes
  that frame the run's last, and its screenshot: asked when the line is read, the run ended with no
  screenshot, which the canvas runner needs. A script's frame N ends as the run's frame N + 2, as its
  typing reaches that frame.
- **Not handled:** a refused close from the window arriving after the frame limit set the flag
  clears it. The next frame's limit sets it again, so the run draws one frame more.
- **The canvas app**: `--refuse-close` refuses the first close, said on stdout, and takes the next.
  The probe prints `canvas close asked N refused M frames K`.
- **`engine-close-hook`**, in the idle group with the engine's loop:
  - refused then taken: asked 2, refused 1, the run ending on the second's frame, 11;
  - no hook: ended by the first close, frame 7;
  - a close over frames 3 to 6: asked once, the run going on to its 30.
- **Falsified:**
  - The hook's answer ignored: the refused-then-taken run ends at the first close.
  - The close asked on every frame of its range: asked twice, ending at frame 6.

  Run together, the first hid the second, the run ending before the range asked again, so they
  were broken apart.
- **Verification**: `idle`, `canvas` (24 arms, re-run for the probe's new line) and `gate-docs`
  pass.
- **The look in a window** is the user's: `./out/bin/canvas --refuse-close`, its close button, then
  Cmd+Q.

## Phase 3: headless waits for work, as built

`75f0822a`.

- **`_engine_idle_next`**: headless, work out is waited for before anything else that asks, a
  request or a script's frame. A window is unchanged.
- **`engine_end_work`** asks first, as before, and wakes the loop again once its count has fallen.
  That second wake is a race no arm can force, so it is argued in the comment beside it.
- **Work that never ends** is said once after `ENGINE_WORK_WARN_SECONDS` (10): headless, the wait
  times out there to say it, and goes on waiting.
- **Found by the gates: `idle-thread` hung.** The canvas app began the board's work at the sheet's
  build and started its thread frames later, after a timed wake. Under the new rule the frame that
  would start the thread waited for its work, for good. The 14.1 contract already said work is
  begun by the code that starts it, and the app now begins it as the thread starts.
  `engine_begin_work`'s header now says never frames ahead of the start, since headless the frame
  that would start it waits for it. pcb's spec should check its own two sites against this.
- **`--editor-lag`'s comment keeps "so a headless run repeats", qualified.** The plan dropped it,
  but without idle mode frames still do not wait for work, and `ui-editor-ranges-late` runs without
  it.
- **The canvas app**: `--work-delay MS` sets the board thread's pause (50 by default), and under
  `--idle` headless it prints `canvas idle work begun N` and `canvas idle work landed M`.
- **`idle-work-waits`**: the board's work, begun as frame 1 draws, lands in frame 2 at a pause of
  0 ms and of 300 ms, while a script keeps every frame drawing.
- **Falsified**: with the headless wait taken out, the 300 ms work lands at frame 23, past the
  script's frames, and the 0 ms work still at 2 on this machine. That is why the arm has the slow
  run.
- **Verification**: `idle` (12 arms), `canvas` (24) and `gate-docs` pass. The ui group's canvas
  arms run without idle mode, which the change does not reach.

## Phase 5: reviews, as built

`5912deec`, `5053e0d2`.

Six reviews ran in background agents at high effort over `master..77ca7063`: `/simplify`'s four
angles (reuse, simplification, efficiency, altitude), a correctness pass, and the thermo-nuclear
review. All six were back before anything was applied. The thermo-nuclear review found the branch

Vim 9.2 was asked the points in dispute before anything was changed:
- after a refused visual `p`, `.` makes the delete under it;
- after a refused `3s`, `.` keeps the count of 3;
- a `J` on the last line, an `r` past the line's end and a `~` on an empty line are beeped at,
  with no E21, and are kept for nothing;
- a refused `r` is kept for nothing too.

**Applied:**
- **What `.` keeps of a refused command has one owner, the caller.**
  - Before: `_refused` kept the command itself and set a flag that silenced the caller's keep. It
    kept the wrong things: a refused visual put kept the put, where the writable path keeps the
    delete under it, and a refused `3s` kept a count of 0, since its case zeroes the counts first.
  - Now: the flag and the `kept` parameter are gone, and a refusal only tells the host and stops a
    replay. The functions that refuse report the command as made, so the keep is the caller's own,
    with its count, keys and area.
  - A refused change records the Esc its insert would have ended with, so `.` on a text made
    writable again leaves no insert open.
  - `C`, `s` and `S`, and visual `c`, `s`, `C`, `S` and `R`, keep their change when the insert
    ends, so they keep at once a change refused before one began.
  - A refused `r` reports nothing made, so it is not kept.
- **A refusal only where the command would do something.** `_join`, `_replace` and `_tilde` refuse
  after they know whether anything would change, so a `J` on the last line, an `r` past the end and
  a `~` on an empty line beep.
  - The read-only oracle then found `3J` on the last line, which moves the cursor to the line's
    start: vim refuses it. So `_join` refuses whenever it would do anything, a move included.
  - `~` on an empty line had been kept for `.` on a writable text too, where vim keeps nothing:
    `_tilde` now says whether it swapped anything.
- **A headless busy-wait, found by three reviews.** With work out and a timed wake already passed --
  the code editor asks for "a wake of now" while it has rows to wrap -- the wait was
  `glfwWaitEventsTimeout(0)` in a loop at full CPU until the work ended. Waiting for work is now its
  own state, `IDLE_WAIT_WORK`, in which a timed wake is no deadline, and the warning has one
  deadline of its own. No arm can see a spin.
- **One wake as work ends, found by four reviews.** `engine_end_work` stores its request, lowers
  its count, then wakes the loop once. The request before the count still keeps a run from ending
  before the result is drawn, and the race the second wake was argued against no longer exists. The
  wake is one helper, `_engine_wake`, which `engine_request_frame` shares.
- **A refused close could undo a quit, found by two reviews.** The frame limit, idle mode's end and
  the app's own quit set the same flag GLFW's close request sets, and a refusal cleared it. The
  engine now notes whether the run was ending as the window's events are read (`Engine.ending`), and
  a close then is not asked; a script's `close` is not asked once the flag is set. Phase 2's "not
  handled" note is handled, and the script's close no longer depends on where it stands against the
  frame limit.
- **Smaller:**
  - A refused Enter in an insert left open no longer sets up a second refusal at Esc.
  - `text_doc_empty_step` does nothing on a read-only text, which would have dropped the host's redo.
  - The top line's padding is no longer recorded only for `_leave_insert` to skip it.
  - `_block_insert` decides `room` first, and the refusal reads as an action.
  - The visual replace exits early when refused.
  - `engine_begin_work`'s header states the cause: counted work must end with no frame drawn.
  - The canvas app has one hex printer, `say_hex`; derives its refused count from its asked
    count; and `board_late_settle` says whether it landed the work.
  - `gates.py` has `_canvas_editor` for the editor's probe lines, and `_idle_run` reads the work
    lines.
- **The arms' gaps, from the correctness review:**
  - `ui-vim-read-only`'s script yanks first and checks the refused commands leave the clipboard.
  - `ui-editor-read-only` cuts with nothing copied before, so it sees that the cut copies.
  - `engine-close-hook` adds a close over frames 3 to 6 with no hook, which ends at the first.
  - The probe gains six cases against vim's own run: a refused visual put and `3s` made again once
    writable, the three beeps, and a refused `r`.

**Not applied:**
- **Padding a block `A`'s lines lazily, as vim does** (altitude). It would let a block insert need
  no read-only special case, but it rewrites the writable path for an edge case: a text made
  read-only during a writable block `A`.
- **Waiting for work without idle mode** (altitude). That is outside this spec, and pcb runs under
  idle mode.
- **Running the read-only oracle only on sequences that can change the text** (efficiency). It
  would save about 70 s a run, but the classifier is a judgement that can go wrong: `u` changes
  case in visual mode.
- **Running gate processes in parallel** (efficiency). The file has no precedent for it, and it
  saves seconds.
- **A per-line helper for the block insert's padding** (thermo-nuclear). It is smaller once the top
  line is not recorded.

**Falsified:**
- a refused `3s` not kept by its caller: the probe reads `count again 0`;
- `~` refused on an empty line: `tilde again 0`.

**Verification**:
- `ui`, `canvas`, `idle` and `gate-docs` pass.
- `ui-vim-oracle` agrees with vim on 6,708 cases, `ui-vim-random` on 1,600 and
  `ui-vim-read-only-oracle` on 6,672.
