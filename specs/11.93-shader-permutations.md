# 11.93 — The uber-shader, and whether a permutation is what fixes it

Phase 4 of the Tier 5 performance programme (11.89 carries the shared evidence base; 11.90–11.92
were phases 1–3).

## Why this phase is different from the three before it

Phases 1–3 were all submission-side. Each removed real work and **none of them moved the frame**,
because forest's frame is shading-bound: after 11.92 the opaque pass is ~147 ms of a ~199 ms
frame, **74%**, while every CPU submission row together is ~11 ms.

So this is the phase where the clock either moves or the programme stops claiming it can. It is
also the phase with the largest gap between what the roadmap asserts and what has been measured,
which is why the first half of this spec is a probe and not a design.

## What is actually true today

Verified in the tree, not quoted from the roadmap:

- **There is no define injection and no permutation system.** `compile_shader` (`shader.c`) calls
  `glShaderSource(id, 1, &source, NULL)` — count 1, one string, no prelude. Every material in
  every app resolves to the same `pbr` program.
- **`pbr_frag.glsl` is 2,513 lines** before includes, and its includes bring `layers.glsl` (473),
  `lights_ubo.glsl` (311), `decals_ubo.glsl` (244), `probe_specular.glsl` (187), `ltc.glsl` (153),
  `preintegrated_skin.glsl` (213), `csm.glsl` (161), `msm.glsl` (127) and more.
- **`sampleLayeredSurface` is called unconditionally** (`pbr_frag.glsl:1066-1071`). Both arms of
  the `layersVtActive` branch call a layered sampler; neither is gated on `layered`, which is
  computed ten lines above at `:1061` and then used only for the albedo decode at `:1075`. The
  `layerCount <= 0` early-out is *inside* the callee (`layers.glsl:211-213`). So a leaf card links
  and calls the entire four-layer body to be handed back a neutral surface.
- **The terminal `FragColor` write is unconditional**, which is what stops the driver eliminating
  any of it, and `pbr_frag` says so itself at `:1558-1563`.
- **Every shader is `#version 330 core` against a 4.1 context**, so `textureGather` is available
  and unused. The PCF kernel is 9 fetches where 3 gathers would do.

## The mechanism is REGISTER PRESSURE, and that changes what a permutation is for

The in-tree calibration is at `pbr_frag.glsl:1146-1153`, and it is worth reading exactly:
hoisting **two `vec3`s** so they live across the shader body cost **11% of the opaque pass on a
scene with no decals in it** — against 3.1% for the entire rest of the decal feature.

That is not a story about executed instructions. Every feature gate in this shader is a
**dynamically uniform** branch, so a scene that does not use a feature already skips its work. The
cost of the uber-shader is what it does to **occupancy**: live values and declared samplers are
paid by every fragment whether or not the branch is taken.

**So the phase's hypothesis is: cutting live-value sets and sampler declarations for a material
that cannot use them recovers occupancy, and that is worth a measurable fraction of 147 ms.**

Stated that sharply because it is falsifiable, and because the three phases before it each had a
booked premise that measurement deleted.

## Step 1 is a probe, and it decides whether the rest happens

**Hand-strip `pbr_frag.glsl` to forest's actual feature set and measure the opaque pass.** No
permutation system, no `shader.c` change — a throwaway edit, measured, reverted.

Forest uses layered terrain (`layer_count`), subsurface on the leaf material (0.55), alpha-masked
foliage, wind, and CSM. It does **not** use clearcoat, sheen, transmission, parallax/POM,
anisotropy, decals, IES profiles, or area lights.

That strip is the **upper bound on what any permutation system can deliver**, for the reason
11.91's fence-less arena was an upper bound: every part omitted from the probe would only cost
time. If the bound is inside the noise floor, this phase closes the way the arena did and the
programme records that GL 4.1 forward shading at this feature count is simply what it costs.

Two runs each side, floor first. The opaque row's floor has been 1.7% all session.

**A second, cheaper probe runs first, because it tests the premise rather than the fix**: confirm
that a runtime `--no-*` toggle for an unused feature moves nothing. If disabling a feature at
runtime is free, the branches really are being skipped, and the remaining cost really is
compile-time. If it is *not* free, the model above is wrong and the phase needs rethinking before
anything is built.

## What the probes said

Baseline on this host was unusually stable — opaque 149.267 / 149.242, a **0.02% spread** — so
everything below is well clear of noise.

### The premise holds: runtime skipping is worth nothing, compile-time removal is worth 16%

Guarding the unconditional `sampleLayeredSurface` call with `if (layered)`, so an unlayered
material stops calling into the four-layer body:

| | opaque GPU |
|---|---|
| baseline | 149.25 |
| layered call guarded | 149.20 |

**Nothing.** The call was already returning immediately; skipping it changes no work, because the
work was never the cost.

Then the ceiling probe — the five features forest does not use (decals, LTC area lights, sheen,
anisotropy, POM), removed at compile time:

| | opaque GPU | FRAME wall |
|---|---|---|
| baseline | 149.25 | 203.72 |
| five features stripped | **125.12** | **179.03** |

**−24.1 ms of opaque (−16.2%), −24.7 ms of frame (−12.1%).** Two runs each side.

**This is the first phase in the programme where the frame moved.** Phases 1–3 removed real
submission work and the clock did not notice; this removes no work at all — every one of those
branches was already being skipped — and the clock moves by 12%. That is occupancy, and it
settles the hypothesis this spec was written to test.

### The costs are NOT additive, and budgeting them individually would mislead

Measured cumulatively while stripping: decals alone 146.24, plus LTC 144.40, plus the other three
130.16 — but the same five strips **without** the layered guard came out at 125.12. The guard,
which costs nothing on its own, costs 5 ms when combined with the strips.

Register allocation is a whole-shader optimisation, so a feature's cost depends on what else is
live. **No per-feature price tag from this spec should be treated as a budget line**, and a
permutation system cannot be validated feature-by-feature.

### The verification plan below is INFEASIBLE, and the probe is what proved it

This spec proposed a gate arm asserting a variant renders 0 px against the uber-shader. It cannot:

| change | differing channels (of 4.8M) | max delta |
|---|---|---|
| layered guard alone | 27,129 | 14 |
| five strips alone | 27,171 | 14 |
| both together | 26,920 | 14 |

Three different edits — one of them a provably exact semantic no-op — all perturb the same ~0.56%
of channels by the same maximum. The delta histogram decays smoothly from 1, which is the
signature of floating-point scheduling, not of a semantic difference. Two runs of one build ARE
byte-identical, so this is not forest's nondeterminism: it is the driver re-scheduling arithmetic
when the surrounding code changes.

**So on this driver a permutation cannot be pixel-identical to the uber-shader even when it is a
provably exact subset.**

### ...and the conclusion drawn from that was WRONG

The paragraph above originally continued: *"a pixel count cannot distinguish a correct variant from
one with a real bug"*. That is false, and the mutation test below is what falsified it.

The error was measuring the wrong thing — and the REPAIR was wrong too, in the same way, which is
why this section has been rewritten twice.

The 27,000 figure counts RAW CHANNEL differences of any magnitude, on forest, at 1600x900. The
first correction said `goldens.py` "counts pixels exceeding a threshold". **It does not.**
`compare()` shells to `magick compare -metric AE` with no `-fuzz`, so it is an exact count with no
tolerance anywhere. The real explanation is simply that the six moved goldens are different scenes
at different sizes, and on them the frames genuinely differ in **8 pixels total, every one a single
LSB** — verified by decoding both PNGs channel by channel.

Right conclusion, wrong mechanism, twice. The lesson that generalises: when a number surprises,
the first instinct is to explain it, and an explanation that predicts the number is not the same
as the one that produced it.

Measured on the shipped variants:

| | sheen_fixture |
|---|---|
| correct variant | **0 px** |
| sheen deliberately dropped from the resolver | **65,402 px** |
| scheduling noise, on fixtures using no gated feature | 1–3 px |

**Four orders of magnitude.** The pixel count separates them cleanly, and the phase's verification
did not need rebuilding around a tolerance after all. Recorded because the wrong conclusion was
stated with the same confidence as the right one, and because "I measured something adjacent to
the question" is how it happened.

## If the probe pays: the smallest thing that could work

1. **`shader.c` gains a `defines` parameter**, and `glShaderSource` goes to `count = 2` — the
   `#version` line, then the define block, then the body. The split is required: `#version` must
   be the first thing in the source, so a prelude cannot simply be prepended to the file.
2. **Variant names key the existing program cache**, which is already name-keyed, so nothing new
   is needed to store them.
3. **An engine-side material -> variant resolver**, which does not exist today:
   `set_material_shader_program` is app code and the only writer. This is the part with real
   design risk, and it is where the spec expects to spend its judgement.
4. **Every variant must set `depth_prepass_safe` and `instanced`** (`program.h`). A variant that
   misses the first lets the prepass stamp depth with no coverage test, which **deletes** alpha-
   masked geometry rather than shading it wrong; one that misses the second makes a batched draw
   put every instance at the first one's transform. Both are silent.

What the variants gate, in evidence order: the **sampler declarations** (a forest leaf needs 8 of
16, and this is the only lever that changes a link-time property), then the dead live-value sets
calibrated against the 11% figure, then the MRT writes an unbound attachment does not need.

## Two things that ride along and are not permutations

- **Guard the layered call.** `if (layered)` around `pbr_frag.glsl:1066-1071` is a one-line change
  that skips a call the callee immediately returns from. Worth measuring on its own, before any
  permutation work, because if the call site is the cost then the permutation is a large answer to
  a small question.
- **`#version 410` + `textureGather` for the shadow kernels** (`csm.glsl`,
  `punctual_shadow.glsl`). Independent of everything above, needs no variant, and the context has
  allowed it since the engine was written.

## What this phase inherits from 11.91

The **depth-only instance block**. `model` alone is 64 B an instance against 192 B for the three,
so the same 12,288-byte block holds **192 instances rather than 64** and the shadow pass's 10,951
instances fit in a third of the draws. It was deferred here because a second `CETRA_INSTANCE_MAX`
means a second block declaration and therefore a second program — which is exactly what this spec
builds. It is a submission win on a shading-bound frame, so expect it to move draws and not the
clock, and measure it separately rather than folding it into this phase's headline.

## What shipped

**Opaque 149.25 → 123.55 ms (−17.2%), frame 203.72 → 177.02 ms (−13.1%).** Two runs a side against
a 0.02% baseline spread, geometry untouched (`samples shaded` and `depth complexity` identical).

That beats the hand-strip ceiling of 125.12 / 179.03 — the probe left the anisotropy map fetch in,
which the shipped gates remove — so the resolver captures **the whole win available on this scene**
rather than a fraction of it. forest resolves to `pbr-0` — all five
features off — which is exactly the configuration the probe measured.

Three pieces:

- **`shader_source_with_defines`**, splicing after the `#version` line. A free function rather than
  a parameter on `create_shader`, which was the first shape and the wrong one: only the lit surface
  is ever a variant, so threading it through `create_shader` and `create_program_from_source` would
  have put a `NULL` at 39 call sites that cannot want one. A variant is a property of the SOURCE.
- **Five `#ifndef` gates in `pbr_frag`, subtractive.** No defines is byte-identical to the shader
  that shipped, so a resolver that fails to run yields the slow program rather than a fast one
  missing a feature. Wrong-and-slow is recoverable; wrong-and-pretty is what ships.
- **`engine_resolve_material_variants`, run EVERY FRAME.** The mask is a pure function of six
  material fields and two scene bits, any of which a GUI slider moves with nothing marked dirty, so
  a flag would have to be set by every writer and the one that forgot leaves a material on a
  variant missing a feature it was just given. Recomputing makes that unrepresentable; the
  expensive half is compiling, which happens once per mask.

The mask is **conservative**: a bit set for an unused feature costs occupancy, a bit missing for a
used one deletes it silently, so every test is the shader's own gate widened to what the CPU can
see.

### Six goldens rebaked, and why that is not a regression going quiet

`froxel_fog`, `water_fixture`, `translucent_shadow`, `layer_fixture`, `cornell_leak`,
`clearcoat_fixture` — each moved **1–3 px**.

**Not one of them exercises a gated feature.** Fog, water, translucency, layers and clearcoat are
all outside the five, so their movement cannot be an omitted feature — it is the scheduling noise
measured above, now under a different program. Verified per fixture, including the trap that every
one of these auto-loads a sibling `.cscn` which could have added a light the `.gltf` does not show.

**The stronger evidence, which the first draft of this section did not cite:** all 29 goldens moved
off the uber-shader, because no fixture carries all five bits. 23 came back **byte-identical** —
and four of those DO exercise a gated feature: `sheen_fixture` on the sheen bit, and
`roughness_sweep` / `backface_dark` / `guard_thin_panel` on the area bit via `--area-light`. Two
gated features rendering bit-exact under their variants is not what a systematically dropped
feature looks like; the sheen mutation moved 65,402 px.

Total movement across all six: **8 pixels of 6.65 million, every one a single LSB.**

### The arm, and the mutation that proves it

`pbr-variant` has three arms. `pbr-variant-lean` is the one that says the resolver ran at all —
without it every material could sit silently on the uber-shader and every pixel arm in the suite
would still pass. `pbr-variant-keeps` is the one that matters: a fixture using a feature must land
on a variant carrying it.

**Mutation-tested, per 11.92's lesson that an arm which merely passes is not evidence.** Dropping
the sheen bit from the resolver takes `pbr-variant-keeps` red and `sheen_fixture` to 65,402 px,
while `pbr-variant-lean` and `pbr-variant-full` stay green — so the arm fails for the right reason
and the failure it guards is genuinely visible.

## What seven reviewers changed

Three thermo-nuclear passes and four `/simplify` angles, all read-only, collected before anything
was applied. The headline result of that round: **one shipped correctness bug**, found by two
reviewers independently and confirmed by a third.

**The area-light ordering bug.** `engine_resolve_material_variants` read `scene->lights` 48 lines
before `scene_build_emissive_lights`, which is the frame's only writer of it. On the frame a
derived LTC panel (spec 11.49) first appears, every material was already on a variant compiled
without area lights, while the cluster list carried a panel. And the guard covered only the LTC
table fetch, not the panel integral — so `ltcPanel` ran with an identity `Minv` and a zero
amplitude. The diffuse form factor does not use `Minv`, so **the panel lit the surface correctly
and its specular came out identically zero**: a lamp with no highlight. Reachable through a
`--config` restore, and bakeable permanently into one face of a GI capture.

Fixed twice over, because the ordering fix alone leaves the shader fragile: the resolve moved below
the emissive build, and the panel integral now shares its tables' predicate. The header states the
invariant it actually needs — *after every writer of the scene bits it reads*, not merely before
the readers of `shader_program`. Those pull in opposite directions and only one half was written
down.

**The C-to-GLSL contract could be typed wrong.** C emitted the TEXT `"#define CETRA_NO_SHEEN 1"`
and the shader tested `#ifdef CETRA_NO_SHEEN`. Nothing bound them. A rename or typo on either side
meant the guard never fired, the variant silently kept the feature it was built to drop, the
picture stayed correct, and the only symptom was that the optimisation stopped happening — which
no golden can see, and which **none of the three new arms could see either**, since all three read
the C side. Both now include `pbr_features.glsl` and share a **mask**: the `wind_bounds.glsl`
mechanism, on a shader that already reaches one of those files transitively. A bit renamed breaks
both compiles.

**Four reviewers converged on the same structural fix** — put the mask on `ShaderProgram` beside
`instanced` and `depth_prepass_safe`. That deleted the per-frame `snprintf`/`strcmp`, the
name-prefix family test (which would have swallowed any future program called `pbr-something`),
and a second copy of the naming rule whose two spellings disagreeing would have compiled and leaked
a fresh program every frame while rendering correctly throughout.

**Gates were red on this branch and only the full suite could say so.** `gate-docs` is the last
group and `--only` matches by substring, so no targeted run reaches it. The docstring had no line
at indent 4, so `cleandoc` stripped six and the arm names landed where the checker cannot see them.

Three more that were mine and wrong rather than merely clumsy: three features had two sites each
and I gated one of each, leaving the anisotropy map fetch and its `atan`/`cos`/`sin` live for four
hundred lines; the `#version` scan matched the token anywhere, and `pbr_frag` includes a chunk whose
comment contains it, so the documented fallback was false for the one shader this runs on; and the
splice moved every body line number, regressing an invariant `gen_shader_header.py` preserves on
purpose.

### What the reviewers proposed and this spec declined

- **`pbr_skinned` joining the family.** It uses the same fragment source — only the vertex stage
  differs, so `render.h`'s stated reason for excluding it was false and is now corrected. But
  admitting it means building skinned variants, which is a change of scope rather than a fix, and
  every skinned material is on the uber-shader until someone does it. Named as a limitation rather
  than explained away.
- **Gating sampler DECLARATIONS.** The spec put this first in evidence order and it still has not
  shipped. Gating the area panel removes the last read of `ltcTex`, so the declaration is now
  removable — that is a Wall 1 escape worth its own spec, not a footnote in this one.
- **An arm on the ASSIGNMENT.** All three arms read which variants were BUILT, not which material
  landed on which. Inverting the resolver's sheen test produces an identical set of builds and only
  the golden catches it. Closing that needs a per-material log line; recorded, not done.
- **`PBR_FEAT_PARALLAX` has no coverage of any kind.** No golden uses a height map. If that leg of
  the predicate were wrong, POM would be compiled out of every material in the engine and the whole
  suite would stay green.

## Verification

- **Goldens will move, and this spec names which and why before rebaking.** A permutation that is
  a true subset renders identically; one that is not is a wrong picture. The programme's rule
  stands: a rebake is not a way to make a regression quiet.
- **A new gate arm asserting a variant renders 0 px against the uber-shader** for a material that
  uses every feature. That is the arm that makes "this variant is a subset" a checked claim rather
  than a design intention — and after 11.92, where the batch arm turned out to guard only half the
  change, it gets a mutation test: break one variant deliberately and confirm the arm goes red.
- `--only cluster`, `--only forest`, `--only overdraw` during; whole suite at the end, and
  **without editing `gates.py` while it runs** — that corrupted 11.92's first full run, because
  `gate-arm-docs` reads the source from disk.
- **`prepass-crossover` is red on unmodified master on this host** (11.91 measured it three times a
  side). Expect noise; check it the same way rather than re-running until green.
- **forest's triangle count is not run-to-run stable** (~0.007%, 11.92), so any triangle assertion
  needs a tolerance. Its draw counts are exactly stable.
