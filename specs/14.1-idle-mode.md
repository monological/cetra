# 14.1: idle mode

## Context

**What 14.1 builds.** cetra gains idle mode: an app switches it on, and the engine stops drawing
frames when nothing has changed. It waits for something to happen instead, and still puts input
on screen within one frame. It is item 2 of `docs/eda-roadmap.md`, and pcb's window (its step 6:
schematic, layout, code editor) needs it. An EDA tool open all day must not redraw a still
schematic 60 times a second.

**Scope, as the roadmap now says** (commit `9596eac8`):
- **The switch is off by default.** Every game, every other app and every golden is unchanged.
  pcb and `apps/canvas` turn it on.
- **Idle only applies to frames that draw no 3D scene.** A frame whose scene has anything to draw
  keeps the loop drawing every frame, exactly as today, so even a 3D app that turned the switch on
  sees no difference.
- **A still 3D view drawn on demand belongs to item 3**, with TAA settling, the accumulation pcb's
  ARCH asks for, and what keeps a 3D frame alive. Not here.

## Found while planning

- **`engine_run` pumps events once per drawn frame**, with `glfwPollEvents` at its end
  (`engine.c:3601`). Nothing waits except the minimized-window branch (`engine.c:3252-3268`).
  `glfwPostEmptyEvent` is used nowhere, so nothing on another thread can wake a waiting loop.
- **The window registers no refresh, focus or cursor-enter callback.** ImGui's backend, installed
  without its own callbacks (`engine.c:1085`), says the app must forward focus and cursor-enter
  (`imgui_impl_glfw.cpp:88-89`). The engine forwards neither.
- **A gap in `total_frames` reads as lost history.** The shadow tiles redraw every face after one
  (`shadow.c:2309`), and the froxel fog, fog layer, SSR wet carry-over and clouds drop their
  histories (`postfx.c:3072`, `3220`, `1445`, `sky_clouds.c:352`). So a wait must not advance it.
- **A wait would reach every animation as one step.** `delta_time` is deliberately unclamped
  (`engine.c:3227-3232`), and the windowed `render_time` is `glfwGetTime()` (`engine.c:3298-3302`).
- **The UI's eases never arrive.** Hover, focus and a toggle's travel approach their targets
  exponentially on the wall-clock delta, with no snap (`ui.c:772-786`, `UI_EASE_SECONDS` 0.12).
  So a UI that asked for frames until it was still would ask forever.
- **ImGui spreads input over frames.** `ConfigInputTrickleEventQueue` is on by default, so a press
  and release in one poll take two frames. The queue is reachable through cimgui
  (`igGetCurrentContext()->InputEventsQueue`, `cimgui.h:3007`).
- **The texture loader's workers publish without waking anything** (`async_loader.c:283-291`).
- **The canvas app draws over an empty scene with a camera** (`canvas_app.c:1413-1418`), so
  "no 3D scene" has to mean a scene with nothing to draw, not no scene.
- **Gamepads are polled, never events** (`game/input.c:33-36`).
- **Three comments describe an early return that no longer exists**: `game.c:199-201`,
  `game.c:334-335` and `engine.h:505-506`. They are fixed in passing, since phase 1 edits those
  functions.

## Design

### The switch and the calls (`engine.h`, public)

```c
bool idle; // SETTINGS: draw only when something asks for a frame; read at each frame's end

void engine_request_frame(Engine* engine);                        // any thread
void engine_request_frame_after(Engine* engine, double seconds);  // main thread: a timed wake
void engine_begin_work(Engine* engine);  // any thread: a result is coming that will be drawn
void engine_end_work(Engine* engine);    // any thread: it is in; asks for a frame
```

- **`EngineConfig.idle`** sets it at creation; after that it is a plain field.
- **A request from another thread** sets an atomic flag and calls `glfwPostEmptyEvent`, which
  GLFW allows from any thread. A request from the main thread only sets the flag.
- **A change made inside a frame is drawn by that frame.** That covers the app's hooks, its input
  callbacks, and the overlays. So the app asks only for changes made elsewhere: another thread, or
  a time it chose. A worker's parse finishing is `engine_end_work`, and pcb's blink is
  `engine_request_frame_after`.
- **Timed wakes:** `engine_request_frame_after` keeps the earliest deadline it has been given.

### The loop (`engine.c`)

**At the end of each drawn frame, with idle on:**
1. The loop polls, as today.
2. It runs the pointer script's frame, as today.
3. It asks whether the next frame is wanted. If not, it waits with `glfwWaitEvents`, or with
   `glfwWaitEventsTimeout` up to a timed wake. It checks again on each wake, so a spurious wake
   waits again.

**The next frame is wanted when:**
- **This frame's scene had something to draw:** the draw list holds an item, or there is a sky,
  a skybox, water, falling rain, fire or a particle system. One function states this.
- **An input event arrived.** Every callback marks the wait as woken: key, char, mouse button,
  cursor, scroll and framebuffer size. So do three callbacks this spec adds:
  - window refresh, for a window that was uncovered;
  - focus, now also forwarded to ImGui;
  - cursor enter, now also forwarded to ImGui.

  The char callback is wrapped so it marks the wait too.
- **A request is pending, or a timed wake is due.**
- **The engine itself still has something to finish without a 3D scene:**
  - the loading screen is shown;
  - finished textures are waiting to be delivered;
  - a pointer script has frames left;
  - the debug GUI still has queued input (below).

  The UI asks for its own frames (below).

**The clocks across a wait:**
- **The wait is taken out of the clock.** It is added to `last_frame_time`, so the next
  `delta_time` excludes it.
- **The windowed `render_time`** becomes `glfwGetTime()` less the total waited, so time-driven
  things resume where they stopped instead of jumping.
- **Headless is already excluded**, since its time is `total_frames` steps.
- **`total_frames` advances only on drawn frames**, so a frame after a wait is still adjacent to
  the last one, and no history is dropped.

**Headless, with idle on:**
- There are no input events, so the run never waits for one. It does wait for a timed wake (in
  real time), and for work that is out: an `engine_begin_work` not yet ended, or a texture decode
  in flight.
- **It ends at the first frame after which nothing wants another and nothing is out.** That frame
  is the screenshot. The check sits before the final-screenshot block at `engine.c:3591`.
- `--frames N` stays the most frames drawn, and `--screenshot-every` counts drawn frames. With idle
  off, nothing changes.
- This is what `pcb render` wants: draw until the view is done, then save it.

**The game framework is continuous:** `game_frame_update` asks for every frame. A running game
is never idle, and gamepads give no events.

### What asks for frames without a 3D scene

- **The UI** (`ui.c`):
  - An ease snaps to its target within 1/1024, so it arrives.
  - `_ui_overlay` asks for the next frame while any of these hold:
    - an ease is off its target;
    - a screen is still entering;
    - an element's own program reads `uTime`. This is tested once by
      `glGetUniformLocation(program, "uTime")` when the program is set.
- **The debug GUI** (`engine.c`): while the GUI is drawn, it asks for frames while ImGui's input
  queue holds events, and for one more after the frame that emptied it, so hover settles.
- **The texture loader** (`async_loader.c`):
  - A worker calls a notify function after publishing a result. The engine sets it to
    `engine_request_frame`, and the loader stays free of GLFW.
  - Finished results waiting in the queue want a frame. Decodes still in flight do not: they are
    work that is out, and they wake the loop when they land.
- **The FPS overlay** (`gui.c`): with idle on, it adds the count of frames drawn, so you can see a
  still window not drawing.

### The test app (`apps/canvas`)

- **`--idle`** turns it on.
- **`--edit-thread` under idle** stops joining its thread:
  - The board's edit is filled during the run, between `engine_begin_work` and `engine_end_work`,
    after a short sleep.
  - An update hook applies it on the frame that wakes. That is pcb's flow.
- **New flags:**
  - `--idle-wake S,...` asks for timed wakes;
  - `--idle-load PATH` loads a texture through `engine_load_texture`;
  - `--pointer-script PATH` takes the engine's scripted pointer.
- **At exit it prints** the frames drawn, the time waited, and each frame's `delta_time`.

`apps/render` gains `--idle`, so the gates can show that a 3D scene is unchanged by it.

## As built

### Phase 1: the loop

Commit `6a144b94`.

- **The switch, the calls and the wait** are as designed. A request reaches a waiting loop by
  `glfwPostEmptyEvent` only while the loop is waiting: the loop raises an atomic `waiting` before
  it reads the flags, and a request stores its flag before it reads `waiting`, so one of the two
  always sees the other. A request made from the main thread, during a frame, posts nothing.
- **`engine_end_work` asks for the frame before it lowers the work count**, and the loop reads the
  count before the request, so a headless run never sees neither and ends early.
- **A hidden window is sent a refresh on its first poll** on macOS. Headless, that drew a frame
  more, so the refresh callback is registered only for a shown window, which shows something to
  refresh.
- **The headless end** is decided before the frame's screenshot, so the last frame is the
  picture. If something lapses between that check and the wait, the loop draws one more frame,
  whose own end closes the run.
- **The scene-has-content rule** reads the draw list's count, and counts an IBL, a sky, water,
  falling rain, an active fire or a particle system as content.
- **The pointer script keeps the loop drawing while it has a frame left**, which it learns from the
  last frame any of its ranges covers.
- **Measured:**
  - the canvas app in a window under `--idle`, still, at 0.0% CPU;
  - the late board waits about 16 ms for its thread rather than drawing;
  - a 3D fixture under `--idle` draws every frame and is 0 px from the run without it.
- **Falsified:**
  - with the wait left in `delta_time`, idle-timed fails, its deltas at the wakes' 0.202 and
    0.300 s;
  - with no scene counted as content, idle-3d fails, its twelfth frame never drawn.

  Both arms passed again once the code was restored.
