# 11.91 — The instance arena, and the measurement that shrank it

Phase 2 of the Tier 5 performance programme (spec 11.89 carries the shared evidence base;
11.90 was phase 1).

## What this was booked as, and what it is

The programme booked this phase as "submission architecture (CPU, both passes)", on the
observation that `instance_chunk_upload` ends in `ubo_upload`, which orphans and re-sends a
12,288-byte allocation for every batched draw — roughly 105 MB a frame at 11.89's draw counts.

**Phase 1 already removed most of it.** Shadow draws went 7,630 -> 730, so the shadow pass's
share of that traffic fell by an order of magnitude before this spec opened. What is left is
1,659 draws a frame, of which the batched ones each still send 12 KB.

So the first thing this spec owes is a ceiling, not a design.

## The ceiling, measured

Re-baselined on this machine, which is running materially slower than when 11.90 was measured
(opaque 60 -> 158 ms GPU on identical geometry — 25,496,217 triangles both times). **Nothing
here is comparable to a number in 11.89 or 11.90.** forest, release, 1600x900 window on a
Retina framebuffer, 120 headless frames, two runs for the floor:

| row | GPU | CPU |
|---|---|---|
| shadow cascades | 18.759 / 18.592 | 5.348 / 5.560 |
| opaque | 159.887 / 157.230 | 7.747 / 7.753 |
| TIMED | 196.918 / 193.782 | |
| FRAME (wall) | 203.377 / 200.303 | |

Floor: 1.7% on opaque, 1.5% on the frame.

**Every CPU-side submission row in the frame totals ~13 ms against a 200 ms frame.** The frame
is GPU-bound and the opaque pass is 80% of it.

Then the falsification probe: `ubo_upload` skipped for the instance block only, behind an env
var, everything else identical.

| | CPU shadow | CPU opaque | GPU opaque | samples shaded | depth complexity |
|---|---|---|---|---|---|
| baseline | 5.348 | 7.747 | 159.887 | 41,646,195 | 1.81 |
| no instance upload | 4.313 | 5.904 | 84.467 | 23,465,809 | 1.02 |

**The GPU half of that is not a result and must not be quoted as one.** With no upload every
batch reads whatever the previous one left in the block, so instances collapse onto one
transform, cover half the screen they should, and depth complexity falls from 1.81 to 1.02. The
opaque pass got faster because it drew a different, smaller picture. This is exactly the failure
mode 11.89's caveat exists for, in its GPU form rather than its CPU one, and it is written down
here because the number is seductive: 159.9 -> 84.5 ms reads like the whole phase paying for
itself, and it is worth nothing.

**The CPU half is a result**, because the fill loop still ran and only the two GL calls went
away:

- shadow  5.348 -> 4.313 = **1.035 ms**
- opaque  7.747 -> 5.904 = **1.843 ms**
- **2.88 ms total, 1.4% of a 200 ms frame.**

That is the honest ceiling on removing the per-draw upload *as CPU work*. It is what this phase
can be expected to buy, and the design below has to be worth 2.9 ms or it is not worth shipping.

## What the probe could NOT measure, and the two probes that can

The orphan is not only CPU work. `glBufferData(size, NULL)` asks the driver for a fresh 12 KB
allocation per batched draw; at ~1,300 batched draws that is ~16 MB of allocation churn a frame
that the GPU column may also be paying for. The probe above cannot see it, because dropping the
upload changed the picture.

Two probes can, and both keep the picture bit-identical because they send the same bytes to the
same place:

1. **Drop the orphan, keep `glBufferSubData`.** Measures what the orphan costs *and* what it
   buys — without it the driver may stall on a store the previous draw is still reading, so this
   can legitimately come out slower. Either answer is information.
2. **One `glBufferData(size, data)` instead of orphan + `glBufferSubData`.** The same transfer as
   a single call.

These run first. If the orphan turns out to cost real GPU time, the arena's value is larger than
2.9 ms and the spec says so with a number. If it does not, the arena is a 2.9 ms CPU change and
the spec says that instead.

**This ordering is the point.** 11.89 shipped after a confidently-stated number that had no
basis; the rule that came out of it is that a claim gets measured before it gets built, not
after.

### What they said

All three modes report `samples shaded 41,646,195` and `depth complexity 1.81`, identical to the
baseline — which is what makes these numbers mean something and the first probe's GPU column
mean nothing.

| mode | opaque GPU | TIMED GPU | FRAME wall | CPU shadow | CPU opaque |
|---|---|---|---|---|---|
| orphan + subdata (shipping) | 158.6 | 196.0 | 203.0 | 5.99 | 7.98 |
| no orphan | 208.4 | 258.8 | 267.0 | 28.97 | 210.8 |
| one `glBufferData(size, data)` | 147.6 | 185.9 | 200.1 | 5.05 | 6.88 |

Three runs for the shipping mode, two for the third, one for the second — it did not need a
second.

**The orphan is load-bearing, and the cost of dropping it is 62 ms a frame.** The CPU opaque row
going to 210.8 ms is the whole story: every `glBufferSubData` into the live allocation syncs
against the reads still in flight. This is 11.28's finding arrived at from the other side, and it
is now recorded on `ubo_upload` itself rather than only in a spec — the next reader to think the
orphan is superstition has a number.

**But orphan-and-fill in ONE call beats orphan-then-fill by 11.0 ms of opaque GPU**, a 6.9% move
against a 1.7% floor. `glBufferData` with a non-NULL pointer replaces the allocation exactly as
the NULL form does, so it keeps the property the orphan was chosen for and drops a second
traversal of the same 12 KB. It also takes ~2.2 ms of the 2.88 ms CPU ceiling above.

That is a two-line change, it is orthogonal to the arena, and it **ships first as its own
commit** — so the arena is measured against a baseline that already has it, and has to earn its
complexity against the cheap fix rather than against the expensive status quo. 29/29 goldens at
0 px.

The short-write path keeps the split form, and must: `glBufferData` sizes the buffer to its
argument, so passing a prefix length there would shrink the allocation the binding point
describes. `light_cluster.c` writes a prefix every frame, so this is a live path and not a
hypothetical.

**What this leaves for the arena** is the ~0.7 ms of CPU the single call did not take, plus
whatever the per-draw ALLOCATION costs — which is the one thing none of the three probes isolate,
because all three of them allocate. That is now the arena's whole case, and it is a smaller case
than the phase was booked with.

## The design

One arena buffer, a bump allocator inside it, `glBindBufferRange` per draw. No orphan, no
per-draw upload.

Everything it needs is GL 4.1 core: `glBindBufferRange` (3.1), `glMapBufferRange` with
`GL_MAP_UNSYNCHRONIZED_BIT` (3.0), `glFenceSync` (3.2 — present in the context, used nowhere in
the tree today).

### Layout

```
[ frame N%K region ][ frame (N+1)%K region ] ...   K regions, one per in-flight frame
      ^ bump offset walks forward within the region
```

- A region holds `INSTANCE_ARENA_CHUNKS` chunks, each `UBO_INSTANCES_BLOCK_SIZE` rounded up to
  the driver's `GL_UNIFORM_BUFFER_OFFSET_ALIGNMENT`. That alignment is **queried, not assumed** —
  it is 256 on the Apple driver and 16 on others, and a hardcoded 256 wastes memory where a
  hardcoded 16 is `GL_INVALID_VALUE` at bind.
- K = 3. Two is the minimum that lets the CPU write while the GPU reads; three is what keeps the
  fence from being the thing that blocks.

### The fence, and why it is not optional

Writing a region the GPU is still reading is the bug the orphan exists to prevent, and an arena
that skips the fence has reintroduced it with no diagnostic — the symptom is a batch drawn at
next frame's transforms, which on a swaying forest is indistinguishable from wind. So: one
`GLsync` per region, signalled at end of frame, waited on before that region is reused. A wait
that actually blocks is a real event and gets a counter, because a fence that is always hot is a
ring that is too short and there is no other way to find out.

### Overflow

A frame that needs more chunks than a region holds must not silently wrap and corrupt itself.
Two candidate policies, and the spec picks the first:

- **Fall back to the existing per-draw `ubo_upload` path for the overflow.** The old path stays,
  correct and slow, and the arena is a fast path over it. A scene that overruns gets today's
  performance, not tomorrow's picture.
- Grow the arena and re-bind. Rejected: reallocating mid-frame invalidates the fences and the
  binding, which is a second failure mode to reason about for a case the fallback already handles.

The fallback also answers what happens on a driver where the arena cannot be created at all.

### The depth-only block

`model` alone is 64 B an instance against 192 B for the three. The shadow depth stage reads
`uInstModel` and nothing else — `_draw_shadow_items` already passes `shading = false` and
`_instance_chunk_fill` already skips filling the other two.

At the same 12,288-byte block that is 192 instances rather than 64, so the same 10,951 shadow
instances fit in a third of the draws. **But `UBO_INSTANCE_MAX` is baked into
`instancing.glsl` as `CETRA_INSTANCE_MAX` and into the run-length caps in both `_visible_run`
and `_ordered_caster_run`**, so a second, larger cap means a second block declaration and a
second program — which is a permutation, and permutations are phase 4 (11.93).

**Deferred to 11.93 for that reason**, and noted here so the phase-4 spec inherits it rather
than rediscovering it. What lands in this spec is only the arena.

## The arena itself is REFUSED, and this is the measurement that refused it

Before spending 48 MB of VRAM and a fence ring on the remaining ~0.7 ms, the same discipline
applies: price the thing first. The one quantity none of the three probes above isolates is the
per-draw ALLOCATION, because all three of them allocate.

So: a fence-less bump arena over one 48 MB buffer, `glMapBufferRange` with
`GL_MAP_UNSYNCHRONIZED_BIT | GL_MAP_INVALIDATE_RANGE_BIT` at the head, `glBindBufferRange` per
draw, 4096 chunks so a wrap is rare enough that the missing fence does not corrupt the
measurement. That is the arena with its correctness machinery removed and its performance intact
— an UPPER BOUND on what the real one could deliver, since every part omitted costs time.

Two runs each, against the shipped single-call baseline:

| | opaque GPU | TIMED GPU | FRAME wall | CPU shadow | CPU opaque |
|---|---|---|---|---|---|
| single call (shipped above) | 146.8 | 184.0 | 199.8 | 4.92 | 6.89 |
| + fence-less arena | 147.7 | 185.0 | 199.5 | 5.06 | 6.38 |

`samples shaded 41,646,195`, `depth complexity 1.81` in both.

**Nothing moves.** CPU opaque is 0.5 ms better, opaque GPU is 0.9 ms worse, the frame is 0.3 ms
apart, and every one of those is inside the 1.7% floor. The upper bound on the arena is zero.

The reason, in hindsight: **`glBufferData`'s orphan is not an allocation in the sense the plan
assumed.** A driver servicing 1,300 identically-sized orphans a frame is popping a free list, not
asking the kernel for memory — the block it hands back is one it recycled from a frame the GPU
has finished with. That is the same bookkeeping a fenced arena does, already implemented, already
correct, and done by the party that actually knows when the GPU is finished. The arena's whole
pitch was to do that job manually, and it turns out to have been doing it for us all along.

So the arena would have cost 48 MB of VRAM, a fence ring, an overflow fallback, two counters and
a gate arm to prove the fallback was not silently swallowing the feature — to reimplement, worse,
something the driver already does. **The cheap fix took the win and the expensive one had nothing
left to take.**

### What this does NOT say

It does not say per-draw uniform uploads are free. It says the ALLOCATION is. The upload itself
was worth 11.0 ms of opaque GPU and that is exactly what the single-call change collected. A
platform whose driver does not pool orphans would answer differently, and this measurement is one
machine's.

### And the depth-only block is still owed

`model` alone is 64 B an instance against 192 B, so a depth-only block holds 192 instances where
this one holds 64 — the shadow pass's 10,951 instances in a third of the draws. That win is
untouched by anything here, because it is about the BLOCK'S SHAPE and not about how the block
gets to the GPU. It needs a second block declaration and therefore a second program, which is a
permutation, which is 11.93. Carried there.

## Steps

1. ~~**The two orphan probes.**~~ Done; the orphan is worth 62 ms, and orphan-and-fill in one call
   is worth 11.0 ms of opaque GPU over orphan-then-fill. **Shipped.**
2. ~~**`ubo_arena.c/h`.**~~ **Refused by measurement**, above. Its upper bound is zero.
3. ~~**Route the instance block through it.**~~ Nothing to route.
4. ~~**Counters for the fallback and the blocking fence.**~~ No arena, no fallback, no fence.
5. **Measure and verify.** Done: 29/29 goldens at 0 px, whole gate suite green.

## Verification

- **0 px on all 29 goldens.** This changes where bytes live, not what they say. Any movement is a
  bug, not a rebake — and the first probe is exactly why: a wrong instance block is a plausible
  frame.
- Whole gate suite green.
- No new gate arm. The one this spec planned — assert the arena is actually used — exists only to
  guard a fallback that only exists because the arena does. Nothing shipped that needs it, and an
  arm asserting a property of code that is not there is worse than no arm.
- Cross-build comparisons pinned with `--no-auto-exposure -E 1.0`.

## What phase 2 delivered

**One `if`.** Orphan-and-fill in a single `glBufferData` where the write covers the whole
allocation, orphan-then-fill where it does not.

Measured on forest at 1600x900 Retina, against a 1.7% floor:

| | before | after |
|---|---|---|
| opaque GPU | 158.6 | 146.8 |
| TIMED GPU | 196.0 | 184.0 |
| FRAME wall | 203.0 | 199.8 |

**−11.8 ms of opaque GPU, −12.0 ms of accounted GPU, −3.2 ms of wall clock.**

The wall-clock line is the honest one and it is much smaller than the GPU line: ~15 ms of this
frame is outside every timed scope, so removing GPU work inside them does not return all of
itself. That gap is worth a look on its own and is not this spec's.

## The thing the programme should know

The opaque pass at ~147 ms GPU is **74%** of a 200 ms frame, and every CPU-side submission row
together is ~11 ms. Phase 4 (shader permutations, spec 11.93) is where the frame is.

Phase 2 was booked as an architecture change and closed as a one-line one, because the
measurement kept shrinking it: phase 1 removed most of the traffic, the single call took the rest
of the win, and the arena's upper bound came out at zero. That is the programme working. The
alternative — building the arena because the plan said so — would have shipped 48 MB of VRAM, a
fence ring and a gate arm for no measurable gain, and every one of those would have been
permanent.
