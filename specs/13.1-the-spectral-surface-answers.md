# Spec 13.1 — The spectral surface answers on the CPU

Under [13.0](13.0-the-coast-in-the-water.md), which says why this is one of only two things in the
water subsystem worth spending on.

## Context

`procedural/water_waves.h:48` answers "how high is the water over this (x, z)" for the Gerstner
model: it inverts the horizontal map by fixed-point iteration, re-evaluates the four-octave train,
applies the shoal factor, and publishes a residual so a caller can tell a converged answer from a
plausible one. Its header says why it exists — *"buoyancy, a boat hull, a splash spawn point and a
gameplay 'am I underwater' test all need the answer on the CPU, at one point, now."*

For the spectral model it returns `water->level` and says so:

> **THE SPECTRAL PATH IS NOT ANSWERED HERE, and cannot be.** An FFT cascade's displacement exists
> only as a texture the transform just wrote, so reproducing it on the CPU means running the
> transform on the CPU — a second implementation of the thing whose whole point is that it runs on
> the GPU. Callers get the still level for that model, and `water_waves_available` says so rather
> than leaving them to discover a flat answer.

That paragraph is correct about the approach it rules out and wrong about the conclusion it draws
from it. **There is a third option: evaluate on the GPU, where the cascades already are, into a
target small enough to read back.** One texel per query point. `shore_chain.h:29-31` restates the
same "nothing on this side to sample them with" for the swash forcing, from the same premise.

**The gap is not theoretical — the instrument already reports it.** `apps/render --water-probe`
(`render.c:4433-4470`) prints the CPU query over a 4x4 grid across `extent * 0.5`, each point
carrying `h=`, `n=` and `residual=`. On a spectral sea its first line is

```
water-probe model=fft available=0 level=0.0000
```

and all sixteen rows under it are the plane. The comment above that block (`render.c:4425-4427`)
already names the cost: *"the GPU surface leaves no number behind, so without this the seam buoyancy
is meant to consume would ship untested."*

**Outcome: the same probe, on the same fixture, under `--water-waves fft`, prints `available=1` and
sixteen real heights — and the machinery that produces them is checked against an exact answer
before it is ever pointed at a sea that has none.**

## The instrument needs no change

`assets/scenes/water_fixture.cscn` authors `"waves": "gerstner"` **and** a complete spectral sea
state beside it (`windSea` 11.5 m/s over 120 km of fetch, `swell` 8.4 m/s over 310 km), so
`--water-waves fft` switches the same fixture to the same sea, and `--water-bed dome` adds shoaling
to either. `docs/verification.md:243` records it at **0 px twice on one build** — *"the surface is a
pure function of the frame clock"* — which is the precondition every arm below rests on.
`beach_fixture.cscn` is the surf instrument for the shoaled case.

The whole matrix is reachable today with no new flags:

| run | today | after |
|---|---|---|
| `--water-waves gerstner --water-probe` | exact CPU answer, `available=1` | unchanged, **and now the reference** |
| `--water-waves fft --water-probe` | `available=0`, sixteen rows of `level` | `available=1`, sixteen real heights |
| either `+ --water-bed dome` | shoaling on the drawn surface only | shoaling in the answer too |

**That the fixture carries both models is what makes this spec checkable at all.** The Gerstner path
has a closed-form CPU answer; the new GPU machinery can be pointed at it first and required to
reproduce it. Only once the ring, the latency, the inversion and the evaluation are green against a
known answer does the spectral sea — which has no known answer — get asked anything.

## Design

### The readback's shape is settled by precedent, not by taste

This engine has **refused a fence-based readback twice, in writing.** `postfx.c:1877-1882`:

> The read BLOCKS. A PBO plus a fence would not (measured 0.033 ms against 5.253), but it lands each
> measurement whenever the GPU happens to finish, which makes adaptation depend on frame timing —
> and equal headless runs then stop matching. This engine trades that the other way round
> everywhere else, so it does here too.

and `specs/10.2:315-322` records the same decision as *"refusing a speedup that is paid for in the
wrong currency."* The sanctioned asynchronous shape is `layers_vt.c`'s **fixed-latency pack-buffer
ring** (`layers_vt.h:93-103`):

> read back through a PBO ring consumed at FIXED latency — always the slot from `VT_FEEDBACK_RING`
> frames ago, never "whichever fence signalled", which is what keeps residency a pure function of
> frame history.

So: a ring, a fixed slot, a published constant latency, no fence. A same-build run stays bit-equal to
itself, which is exactly what `water_fixture`'s 0 px depends on and what an arm reading a number back
would otherwise destroy.

**The one genuinely new thing here is the format.** No float has ever gone through a pack buffer in
this tree — the VT ring is RGBA8, and every float readback (`postfx.c:1887`, `water.c:2347`) is a
blocking `glGetTexImage`. `glReadPixels(GL_RGBA, GL_FLOAT, NULL)` out of an RGBA32F FBO into a pack
buffer is unproven on this driver, so it gets a phase of its own before anything is built on it.

### The pass

`water_probe_frag.glsl`, including `ocean.glsl`, run into an `N x 1` RGBA32F FBO with one texel per
query slot. It slots into `_water_run_spectral` (`water.c:1719-1873`) **after the mip chain** —
step 4, so it reads this frame's cascades complete — inside the state bracket already open at
`water.c:1729-1737`, reusing `water->fft_vao`. That is precisely the shape the foam pass already has
at `water.c:1804-1862`. Viewport `N x 1`; nothing, beside 45 existing draws.

Per texel, three things in order:

**1. Invert the horizontal displacement.** An FFT cascade's output is Lagrangian: `oceanEvaluateAt`
says where the water that *started* at parameter `p` ended up, not the height standing over world
XZ. Waves push water sideways as well as up, and at `water_fixture`'s 0.6 steepness that is not a
rounding error. So iterate

```
p_0 = q
p_{n+1} = q - displacement(p_n).xz
```

mirroring `_waves_solve` (`water_waves.c:186-218`) — same loop, same step cap, same convergence
test — but against the cascade textures rather than a closed form.

**2. Evaluate at the recovered parameter**, through `oceanEvaluateAt` (`ocean.glsl:981`), so the
answer comes from the *same function the vertex shader calls*. A second evaluation path is the thing
this spec exists not to create; `shore_runup.h:18-19` already files CPU-twin duplication under "the
precedent and the warning".

**3. Write `vec4(height, slopeX, slopeZ, residual)`.** The residual is the last step size, which is
exact and free — `water_waves.c:180-186` records why that works. It is published for the reason
`water_waves.h:51-58` gives:

> everything else this file returns looks plausible whether or not the inversion converged, because
> an unconverged answer is still a point on the surface — just not the one over the query.

### The API

One entry point on `water.h` covering both wave models, so nothing downstream branches on which sea
it was handed:

```c
#define WATER_PROBE_MAX 16   // the probe grid's own 4x4; a refused slot returns false

// Register a query. Answered from the next spectral pass onward; what a caller reads is
// WATER_PROBE_LATENCY frames old on the spectral path and current on Gerstner.
bool water_probe_set(Water* water, int slot, float x, float z);

typedef struct {
    float height;    // world Y of the surface over (x, z)
    vec3  normal;
    float residual;  // how far the recovered parameter landed from the query, world units
    int   age;       // frames since this answer was computed; 0 on the Gerstner path
} WaterSample;

// false when there is no usable surface, the slot is unset, or the ring has not filled --
// never a silent `level`.
bool water_probe_result(const Water* water, int slot, WaterSample* out);
```

Gerstner delegates straight to `water_surface_at` and answers with `age = 0`; spectral answers from
the ring. `water_waves.h`'s own contract is untouched — it stays a pure function of parameters and a
position with no GL state, which is the stated reason it lives in `procedural/` rather than in
`water.c`. The GL half belongs to the file that owns the passes.

**Refusal is the feature, not a guard.** `water_waves.c:236` hands back `water->level` for the
spectral model, so a caller that forgets to check gets a usable-looking plane — which was the right
call when nothing better existed and is the wrong one now. The new call returns `false` and the probe
names why, in `water_fft_probe`'s existing grammar (`water.c:2319-2338`):
`available=0 reason=nowater|gerstner|unseeded|alloc`.

### Decisions taken (do not relitigate)

- **A ring at fixed latency, never a fence.** Two written refusals (`postfx.c:1877`,
  `specs/10.2:315-322`) and one written contract (`layers_vt.h:93-103`). The latency is a published
  constant, not a measurement of when the GPU felt like finishing.
- **One evaluation, on the GPU.** A CPU FFT is the second implementation `water_waves.h:23-27` and
  `shore_chain.h:29-31` correctly refuse. This spec does not refute their reasoning; it answers a
  question they did not ask.
- **Gerstner first, spectral second.** The order is the verification. Building the machinery against
  the sea that has no reference answer would leave every failure indistinguishable from every other.
- **The probe does not smooth, average, or hold a ceiling.** The research demo's carries a four-tap
  mean and a decaying maximum; both belong to whatever is floating, not to the water. A caller
  wanting a mean registers more slots.
- **Model-transparent API, latency published.** One call for both seas; `age` says which answered.

## Phases

Branch `13.1-the-spectral-surface-answers` off master; the spec commits first, alone, before any
code. Each phase ends with its arms green and the fixture **looked at** where the phase changed what
is drawn — which, for most of these, is nowhere, and that is itself worth confirming.

**Phase 0 — look at it, and measure the floor.** Render `water_fixture` under both wave models and
watch the surface. Run `--water-probe` both ways and record what the sixteen rows say today. Measure
the 0 px determinism floor at the framing the arms will use, per `docs/verification.md:15`. Then
write `water-probe-spectral-agrees`, which must be **red**.

**Phase 1 — a float through a pack buffer.** The ring alone, in isolation: RGBA32F FBO,
`glReadPixels(GL_RGBA, GL_FLOAT, NULL)` into a pack buffer, mapped N frames later, no fence. New on
this driver. If it does not work, the spec's shape changes here and nowhere later.

**Phase 2 — the pass and the inversion, against the answer we already have.** `water_probe_frag.glsl`,
the fixed-point solve, the residual — run on the **Gerstner** path, where `water_surface_at` is an
exact reference on the same sixteen points of the same fixture at the same `t`. This is the phase the
spec stands on: it proves the ring, the latency, the inversion and the evaluation in one comparison.
Arms: `water-probe-gpu-matches-cpu`, `water-probe-eulerian` (two-sided against an un-inverted
evaluation, or it proves nothing).

**Phase 3 — the public API.** `water_probe_set` / `water_probe_result`, the Gerstner delegation, the
refusals. Arms: `water-probe-latency`, `water-probe-refuses`.

**Phase 4 — the spectral path.** Point the proven machinery at `WATER_WAVES_FFT`. **One structural
change belongs here**: today's probe prints once from setup at `t = 0`, because `water_surface_at` is
pure CPU and needs no frame; the spectral answer needs the loop to have run and the ring to have
filled, so the spectral print moves to the last frame under `-f`. Arms: `water-probe-spectral-agrees`
(green now), `water-probe-spectral-still` (a zero-energy sea probes to exactly `level`),
`water-probe-variance` (sampled height variance against the `cascade_height_var` the seeding
predicted — `water_fft_probe` already computes the other half of that comparison).

**Phase 5 — the shoaled case, and the look.** `--water-bed dome` on `water_fixture`, and the same
grid on `beach_fixture`: the answer must shoal where the drawn surface shoals. **Then run both
fixtures and look at them**, because a probe that agrees with a wrong surface agrees with nothing.

**Phase 6 — the docs.** Three places now say the opposite thing — `water_waves.h:23-27`,
`shore_chain.h:29-31`, and `render.c:4425-4432` — plus `docs/verification.md`'s water-fixture entry,
`docs/cli-reference.md`, and `AGENTS.md`'s water row.

## Verification

Scoped per phase:

```bash
python3 scripts/gates.py --only water    # every phase. --only is a SUBSTRING match,
                                         # so this runs water-night too
python3 scripts/gates.py --only beach    # phase 5
```

End of job: `./build.sh`, the full `gates.py`, `goldens.py`. **No golden should move** — the probe
writes to its own target and changes no shading. Assert 0 px rather than re-baking.

**The numbers that decide it**, not a green suite:

- The GPU probe against `water_surface_at` on Gerstner: sixteen points, same fixture, same `t`,
  agreement to float precision. **This is the arm the spec stands on.**
- The inversion residual at `water_fixture`'s 0.6 steepness, against the same probe with the
  inversion removed — two-sided.
- A zero-energy sea probing to exactly `level`, not approximately.
- Sampled height variance against `cascade_height_var`'s prediction.
- The latency is exactly `WATER_PROBE_LATENCY` frames, and identical across two runs.

**The watch**, which no arm replaces:

```bash
./out/bin/render -m assets/scenes/water_fixture.cscn --water-waves fft
./out/bin/render -m assets/scenes/water_fixture.cscn --water-waves fft --water-bed dome
./out/bin/render -m assets/scenes/beach_fixture.cscn
```

## Out of scope

- **A CPU evaluation of the spectrum.** Still correctly refused, for the reason
  `water_waves.h:23-27` gives.
- **Any game-layer consumer.** This spec ends at `water.h` and the render app's probe.
  `apps/gametest` is where the seam will eventually be spent, but its grotto passes
  `height_at = NULL` (`gametest.c:1638-1639`) so there is no bed at all, and its sea is 2.5 m/s over
  900 m of fetch — centimetres, against a character four units tall. **It cannot show this working**,
  which is why it is not the instrument.
- **Driving the swash film off a real sample.** `shore_chain.h:29-31` becomes answerable; acting on
  it changes the forcing model for both wave paths and is its own spec with its own risk.
- **Buoyancy through Jolt.** Unbound in this engine; `gravity_factor` is rigid-body-only and
  unreachable from a `CharacterVirtual`.
- **A probe that answers about the previous frame's surface.** `oceanPreviousWorldAt` exists for
  motion vectors; nothing has asked for it on the CPU.

### Found on the way, not fixed here

Two defects in `apps/gametest`, both one-line, both left for whoever next opens that file — naming
them here so the next reader does not rediscover them:

- `grotto_float_velocity` (`gametest.c:1586`) aims its spring at the bare constant `GROTTO_WATER_Y`
  rather than at `grotto_surface_y`, twenty lines under a comment promising *"ONE subtraction, so
  the buoyancy, the speed scale, the IK gate, the camera's footing and the animation cannot disagree
  about where the water is."* Moving `water->level` today moves everything except the spring.
- The bob's arithmetic at `gametest.c:240` derives `4.0^2 / (2 * 9.81) = 0.815 m`, but the app's
  gravity is `20.0f` (`gametest.c:3616`), which gives 0.40 m. The measured 0.80 m agrees with the
  comment and not with the app's own constant, so one of the two is wrong.
