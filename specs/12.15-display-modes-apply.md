# Spec 12.15 — the display settings apply

## Context

`settings.c` (spec 12.2) persists a window mode, and **nothing reads it**. `window_mode` is
written to the file, round-tripped, and gate-asserted as a name — by zero runtime code.
Three places in the tree say so in their own words:

> `settings.c:298-306` — *"window_mode is PERSISTED and not applied, and that is a gap
> rather than a decision I am pleased with. ... making it take effect wants engine support
> that does not exist yet."*

> `gametest.c:326-329` — *"window_mode is in the file and deliberately NOT on the screen:
> settings_apply cannot make it take effect yet, and a control that changes when clicked
> and does nothing is the defect this app already shipped once."*

> `docs/verification.md:818-820` — *"nothing has ever gone fullscreen. That is a gap in the
> feature and not only in the testing."*

Nothing outside vendored GLFW calls `glfwSetWindowMonitor`, `glfwGetPrimaryMonitor` or
`glfwGetVideoMode` — `glfwCreateWindow`'s monitor argument is hardcoded `NULL`
(`engine.c:471-472`). The engine has never been able to leave a window.

This is the one settings row that lies to the player, which is worse than an absent
feature: the UI, the file and the round-trip arm are all green over a dead value.

**Outcome: display mode, monitor and vsync are chosen in the settings screen, applied
immediately, persisted, and restored on the next run — and a run can START in the chosen
mode rather than flashing through a window first.**

---

## Decisions taken before planning

| | |
|---|---|
| **Modes** | Three: windowed, exclusive fullscreen, borderless. |
| **Resolution** | **No resolution list.** Both non-windowed modes take the monitor's CURRENT video mode. The performance lever stays `--render-scale` / TAAU (spec 11.7), which already has a GUI slider and gate coverage and buys the same framerate with no display-mode change. |
| **Monitors** | A picker, persisted **by name**, so unplugging a display cannot silently move the game to the wrong one. |

**One consequence makes the exclusive path far smaller than it looks:** the mode requested
is always the one already in use, so **no display resolution is ever changed**. That takes
resolution-restore-on-crash, stored-mode-no-longer-offered validation, and a saved
resolution out of scope. It does not take out saved window GEOMETRY, which is the second
thing the gap comment names and which this spec has to keep.

---

## The three blockers

`settings.c:298-306` names two. Exploration found a third it does not.

**1. "choosing a monitor"** → a monitor picker persisted by NAME. The descriptor table has
only `SET_FLOAT`, `SET_INT`, `SET_BOOL` (`settings.c:34`), so this needs a fourth row type
`SET_STRING` over a fixed `char monitor[64]` in `GameSettings`. Empty = primary = default =
first-run behaviour.

**2. "restoring a position and size saved beforehand — state the engine does not keep"** →
the engine keeps it. Four ints on `Engine`, latched on the way OUT of windowed and replayed
on the way back. This is the whole of the missing engine support.

**3. The engine cannot re-apply vsync, and a mode switch needs it re-applied.**
`EngineConfig.no_vsync` is consumed once (`engine.c:881` → `:482`) and there is no field on
`Engine`, so the swap interval is unrecoverable after init — while `settings.c:295` is a
SECOND, independent `glfwSwapInterval` writer. Taking a monitor can drop the swap interval,
and neither writer is in a position to put it back. So `Engine` gains `vsync` +
`engine_set_vsync`, re-applied at the end of every mode change, and `settings_apply` calls
that rather than GLFW. One writer, one reader, where there were two writers and no reader.

## Design

### The invariant that makes this small

`_engine_framebuffer_size_callback` (`engine.c:1083-1110`) is documented as *"the ONLY
writer of fb_width/fb_height/win_width/win_height after init"*, and
`_engine_sync_render_targets` (`engine.c:788-807`) already rebuilds the scene target and
post chain at the frame top whenever the derived sizes disagree with `target_render_w/h` /
`target_post_w/h` — *"so a size field changing behind our back heals instead of desyncing."*

**So `engine_set_window_mode` writes none of those four fields.** It calls GLFW, GLFW fires
the existing callback, the existing frame top rebuilds. Mode switching adds no resize path:
the 0x0 guard, the camera aspect, the text ortho and the UI's points→pixels scissor ratio
(`ui_draw.c:764-768`, the de-facto content scale) are all already correct on the far side.

**Any implementation that writes those four fields directly has broken the invariant and
should be rejected in review.** A pleasant consequence: moving between displays of
different DPI already works, because that ratio is re-derived from the callback's readings
rather than from a cached scale factor.

### Engine surface (`engine.h` / `engine.c`)

The engine cannot see `game/settings.h` — it is the layer below — so it gets its own enum
and `settings.c` static-asserts the two agree. That is this repo's technique for a number
two sides must share (`shore_constants.glsl`, `pbr_features.glsl`) at its simplest: drift
becomes a compile error.

```c
typedef enum {
    ENGINE_WINDOW_WINDOWED = 0,
    ENGINE_WINDOW_FULLSCREEN,   // exclusive, at the monitor's current mode
    ENGINE_WINDOW_BORDERLESS,   // undecorated window filling the monitor
} EngineWindowMode;

int         engine_monitor_count(const Engine* engine);
const char* engine_monitor_name(const Engine* engine, int index);

// BY FUNCTION: moves the window, latches or replays the windowed geometry, and
// re-applies vsync. Leaves the size fields to the framebuffer callback.
// NULL or "" selects the primary monitor, as does a name no display answers to.
void            engine_set_window_mode(Engine* engine, EngineWindowMode mode, const char* monitor);
EngineWindowMode engine_window_mode(const Engine* engine);
void            engine_set_vsync(Engine* engine, bool vsync);
```

Two `EngineConfig` fields (`window_mode`, `monitor`) so a run can be CREATED in the chosen
mode — `glfwCreateWindow` takes a monitor argument, and using it avoids a windowed flash on
every launch for a player who chose fullscreen. That is exactly what the `EngineConfig`
banner (`engine.h:534-540`) exists for: *"a hidden window is decided when the window is
made."*

### The transitions

Geometry is latched on the first departure from windowed and replayed on every return, so
borderless → fullscreen → windowed lands where the window started rather than where the
last mode left it. GLFW is **3.4** (`glfw3.h:287-301`), so the runtime `glfwSetWindowAttrib`
and `glfwGetMonitorWorkarea` this needs are both available.

| to | how |
|---|---|
| windowed | `glfwSetWindowMonitor(win, NULL, saved.x, saved.y, saved.w, saved.h, 0)`, then `GLFW_DECORATED` true |
| fullscreen | latch geometry, then `glfwSetWindowMonitor(win, mon, 0, 0, vm->width, vm->height, vm->refreshRate)` with `vm = glfwGetVideoMode(mon)` |
| borderless | latch geometry, `GLFW_DECORATED` false, `glfwSetWindowMonitor(win, NULL, ...)` to the monitor's origin and video-mode size |

Every path is a no-op under `engine->headless && !engine->window`, matching how
`settings_apply` already guards vsync.

### Settings surface

- `GameSettings` gains `char monitor[64]`; `window_mode` stays `int`.
- `SETTINGS_WINDOW_MODES` gains `"borderless"` **appended at index 2, never inserted** —
  `settings.c:52-53` warns that *"A label inserted in the middle re-points every saved file
  silently, so the static assert below is the thing that has to move first."* The enum order
  is therefore windowed / fullscreen / borderless, and the screen lists them in that order
  rather than reordering behind a mapping nobody can see.
- `SET_STRING` needs a capacity on `SettingField`; a single `SETTINGS_STRING_CAP` is enough
  for one row and is the smaller change.
- `settings_apply` gains one branch, guarded exactly as the vsync branch is.

### The settings screen

`gametest.c:5997-6025` gains two `ui_selector` rows — the closed element list
(`ui-elements-closed`, `gates.py:23852-23861`) permits no new element kind and needs none.

The monitor selector binds an `int` index into the LIVE monitor list while the file holds a
NAME, so: on load, find the index whose name matches and fall back to 0; on change, copy
that index's name into the struct. A name no connected display answers to is the unplugged
case and resolves to primary without comment.

The comment at `gametest.c:326-329` explaining the control's absence goes, and the
write-on-close at `:5868-5876` already carries both new values unchanged.

## Verification

### A new `display` gate group

There is **no `settings` group** — settings verification is one arm of `ui`
(`ui-settings-roundtrip`, `gates.py:23864-23887`). This feature spans the engine and the
settings file, so it gets its own group and its own `gametest --display-probe <case>`,
alongside the existing `--ui-probe` / `--anim-probe` / `--ik-probe` / `--save-probe`.

**It can run headless, and that is a real finding rather than an assumption.** Eight of the
ten `ui` arms already create a **live hidden GLFW window and a GL 4.1 context**
(`gametest.c:6441-6458` → `create_game` → `_setup_engine_glfw`, `GLFW_VISIBLE=FALSE`). From
that state `glfwGetMonitors`, `glfwGetVideoMode`, `glfwSetWindowMonitor` and
`glfwGetWindowMonitor` are all reachable, and no frame is ever drawn.

| arm | asserts |
|---|---|
| `display-modes` | windowed → fullscreen → borderless → windowed; after each, `glfwGetWindowMonitor` is non-NULL for fullscreen only, and `GLFW_DECORATED` is false for borderless only |
| `display-geometry` | the round trip: position and size after returning to windowed are **exactly** the ones it left with |
| `display-monitor-name` | every monitor's name resolves to its own index; an unknown name and an empty name both resolve to primary |
| `display-settings-apply` | a mode in `GameSettings` reaches `engine_window_mode` through `settings_apply` — the arm that would have caught the original defect |
| `display-one-vsync-writer` | static read of `settings.c`: no `glfwSwapInterval` remains, mirroring `ui-elements-closed`'s file-read idiom |

**A machine with no monitors SKIPs, never FAILs** (`gates.py:1307-1309`'s idiom) — a VM or
CI box may enumerate zero displays, and a red suite there would be noise.

**Three `gate-arm-docs` constraints, since it reads the function source from disk:** the
docstring's arm list sits at exactly two spaces, in run order, anchored by a shallower prose
line; each name appears as a **literal** inside its own `print(f"  name ... PASS ...")`; and
arm names **may not be built in a loop**, which rules out the natural
`for mode in modes: print(f"  display-{mode}")`. Register the group in `GATE_GROUPS`
(`gates.py:23892`). Do not edit `gates.py` while a run is in flight.

### Falsification — the deliverable, not a formality

Spec 12.14 exists because an arm passed against the code it was written to replace. Stub
`engine_set_window_mode` to return immediately and confirm `display-modes`,
`display-geometry` and `display-settings-apply` all go **red** while the other `ui` and
`save` arms stay green. Two of the three are red by construction today, since there is no
way to leave a window at all.

### Must not move

```bash
python3 scripts/gates.py --only ui       # ui-settings-roundtrip gains "borderless" as a legal label
python3 scripts/gates.py --only display  # the new group
python3 scripts/gates.py --only save     # shares CETRA_SETTINGS_DIR isolation
python3 scripts/goldens.py --only menu
python3 scripts/goldens.py --only menu_focus
```

The two menu goldens photograph `--ui-screen main`, not the settings screen, so they should
be **0 px**. Two warnings from `docs/verification.md` apply: they are *"knowingly stale"*
since 12.6 (`:775-778`), and their instability *"reaches 48,886 px"* with 0 px on a re-run of
the same binary (`:704-711`) — **re-run before believing any non-zero**.

### By hand, and it is the acceptance test

Windowed and on a second display: every mode from the settings screen; the file surviving a
relaunch in each mode; a monitor unplugged between runs falling back to primary rather than
vanishing; vsync still honoured after a mode change; the menu still laid out correctly at
the new size (`ui-layout-resize` covers the pure function, not the live transition).

## Out of scope

- **A resolution list**, and with it saved resolutions and stored-mode validation. Decided
  above; `--render-scale` is the lever.
- **The 4K / HiDPI debt** (`verification.md:802-806`). This spec does not change how points
  become pixels — it relies on the framebuffer callback that already does — so that debt is
  untouched, neither closed nor worsened.
- **The `uTime` windowed bug** (`verification.md:821-829`), adjacent in that file and a
  genuinely different problem: a clock, not a window.
- **Persisting input bindings**, owed in `settings.h` and blocked on a key-capture element
  the closed UI list does not have.
- **`ui_volume`** — loaded, saved, and pushed to a bus nothing plays on, with no slider. A
  real near-miss of the same "green over a dead value" kind, found while exploring, and not
  this spec's to fix.
- **Every app but `gametest`.** No other app reads `GameSettings`. The engine API is general;
  only the demo grows a screen for it.

## What shipped, and where it diverged from this plan

### The verification plan was wrong, and the code is better for it

The plan said the `display` group could exercise the mode switch headlessly, on the grounds
that eight of the ten `ui` arms already create a real hidden GLFW window with a live context.
That much is true. What it missed is that **`engine_set_window_mode` refuses under headless
on purpose** — a suite that seized a display would be intolerable, and a golden whose frame
size came from whatever monitor the machine has would not be a golden. So there was nothing
for the planned `display-modes` and `display-geometry` arms to watch.

The fix is this repo's own `ui_layout` move: **split the decision from the effect.**
`engine_window_placement` is a pure function of (mode, monitor rectangle, saved geometry) —
no GLFW, no Engine, no display — and the GLFW half is reduced to two calls with no arithmetic
in them. The arms read the decision; `display-headless` asserts that the refusal holds, which
is the arm every other golden in the corpus rests on.

The arms as planned and as shipped:

| planned | shipped | |
|---|---|---|
| `display-modes` | `display-placement` | reads the pure function, not the window |
| `display-geometry` | (folded into `display-placement`) | the windowed row IS the geometry round trip |
| `display-monitor-name` | `display-monitors` | plus NULL and empty, which the plan omitted |
| `display-settings-apply` | `display-apply` | vsync, since the mode cannot land headless |
| — | `display-headless` | new: the refusal itself |
| `display-one-vsync-writer` | `display-vsync-writer` | as planned |

### Three things the plan did not anticipate

- **`engine_monitor_index`.** The plan had the app resolving a stored name to a selector index
  itself. That is a second copy of the primary-monitor fallback, and two copies of a fallback
  is how a settings screen ends up showing a display the window is not on. One function now,
  used by the picker and by the engine's own lookup.
- **Creation reuses the switch.** Rather than a separate monitor-at-creation path, the window
  is created HIDDEN, moved through `engine_set_window_mode`, then shown. One mode path instead
  of two, and it is also what stops a fullscreen launch flashing a window first.
- **`--list-monitors`.** Added while looking for a way to check the feature without a display.
  It earns its place: it prints the names `--monitor` and the settings file take, from the
  engine's own view, so what a player can store and what this build can find are one list.

### Falsified, as the plan required

Two mutations, each reverted:

| stub | result |
|---|---|
| `engine_window_placement` returns the windowed answer for every mode | `display-placement` **FAIL**, other four green |
| `settings_apply` calls `glfwSwapInterval` directly again (the pre-12.15 second writer) | `display-apply` and `display-vsync-writer` **FAIL**, other three green |

`display-vsync-writer` also caught a real defect in itself on first run: it counted every
mention of `glfwSwapInterval` in `settings.c` and so failed on the comment explaining why the
function is deliberately not called there. It counts calls now — an arm that fails on its own
explanation gets read as noise and deleted rather than believed.

### What was NOT done, and why

**Phase 2's look.** A fullscreen run seizes the display it is run on, and that was declined
rather than forced. What was photographed instead is the settings screen itself, headless, at
500x640 — the Display row lays out between VSync and Tonemap and reads `Windowed`, and no
Monitor row appears because this machine has one display. **A window actually moving is owed**,
and `docs/verification.md` now records it alongside the second-display gap: with one monitor,
`display-monitors` cannot distinguish a correct name lookup from one that always answers 0.
