# cetra 14.15: whole-line ranges, an exact scroll and change jumps

## Context

pcb 6.5 (pcb's `specs/6.5-comparing-versions.md`) compares a past version of a design with the
design now. Its code pane becomes one pane with both sides, settled with the user from a mockup:
the old text on the left, read only, removed lines red; the file now on the right, editable, added
lines green; whole lines coloured, as on GitHub; the two scrolled together, lined up by their top
lines; `]c` and `[c` going to the next and previous change, on into the next changed file.

pcb builds that from two editors in a row, each on its own text, and three things the editor does
not give today:

- **A range colours only behind its characters.** `_band` runs from the column of the range's
  first byte to its last (`ui_editor.c:2503`), and `_on_row` refuses a range on an empty row
  (`ui_editor.c:2514`): a red line stops at its last character, and an added empty line shows no
  green at all.
- **The scroll position is public only in whole rows.** `ui_editor_top` gives the offset starting
  the top row, and `ui_editor_scroll_place` sets the part of a row scrolled past to 0
  (`ui_editor.c:1064-1074`). The line and row are in the internal `ui_editor_view_top`
  (`ui_editor_hooks.h:26`) and the part of a row nowhere. A second editor held to a first snaps a
  row at a time while the first glides under a trackpad.
- **`]c` cannot reach the host.** It is two keys, and a host's layer binds one; it cannot be a
  vim motion either, since pcb's answer may be another file. `]` and `[` are no prefixes in the
  vim mode today (`ui_editor_vim.c:5064-5072` lists the ones there are).

Not in this spec, each the host's to live without:
- **Blank filler rows** to line the two sides up row for row, as GitHub's split view pads them:
  rows that are not the text's touch the editor's row model throughout (`_rows_of`, `_top_of`,
  every caret move). pcb lines the sides up by their top lines and accepts the drift below.
- **Turning wrapping off**: pcb's sides wrap where their lines are long, as the editor does now.
- **Dashed lines on the canvas** (`docs/eda-roadmap.md`, item 1's "left for later"): pcb dashes
  its ghosts itself.

Branch and spec: `14.15-whole-line-ranges-an-exact-scroll-and-change-jumps`, off cetra's master
(`f433bcc0`).

## The design

### 1. A style that fills whole lines

One field in `UIEditorStyle` (`ui.h:307`):

```c
bool whole_lines; // background behind every row of each line the range reaches, edge to edge
```

- **What it covers:** every row of each line whose bytes, its line break included, the range
  overlaps: from the text's left edge (`ed->text.x`) to the editor's right edge, an empty line
  included. A range `[line_start, next_line_start)` covers exactly its lines; a range ending at a
  line's start does not reach that line. The gutter keeps its colour.
- **Drawn first**, under the other backgrounds (other ranges, find's matches, the selections), so a
  selection on a red line still shows.
- **Only the background widens.** The style's text colour and underline still go by the range's
  bytes.
- **False is the default**, so a zeroed style draws what it draws now: `ui-theme-identity` and
  every golden are untouched.
- In `_draw` (`ui_editor.c:2526`): before the per-row background loop, each range whose style has
  `whole_lines` and that reaches the line (its own test, not `_on_row`, which refuses empty rows)
  draws one quad per row, `ed->text.x` to `content.x + content.w`. `RANGES_DRAWN` is unchanged.

### 2. The exact scroll position

Two calls in `ui_editor.h`, beside `ui_editor_top`:

```c
// The line at the view's top, and how far the view is scrolled into it in rows: 1.25 is a quarter
// of the way down its second row.
size_t ui_editor_top_line(const UIElement* el, float* rows);
// The view put with `line` at its top, `rows` of it scrolled past, held to the text's lines and
// that line's rows as a wheel's scroll is. Before the editor is laid out on its text, taken at its
// next layout.
void ui_editor_scroll_line(UIElement* el, size_t line, float rows);
```

- The getter reads `at.top_line`, `at.top_row` and `at.top_frac`. The setter splits `rows` into the
  row and its part; before layout it is a new pending kind beside `PENDING_REVEAL` and
  `PENDING_PLACE`.
- `ui_editor_view_top` stays internal for what uses it.
- No scroll hook: a host polls each frame, which pcb does already for everything it reconciles.

### 3. `]c` and `[c`, answered by the host

In `ui_editor_vim.h`, beside the lookup of spec 14.9:

```c
// ]c and [c, vim's next and previous change, asked of a host that knows what changed: `forward`
// for ]c, `count` how many changes on (1 with none typed). The host moves the carets where it
// likes, another text included. False when there is none, and nothing moves. Asked in normal mode
// with no operator waiting; never kept for `.`.
typedef bool (*UIEditorVimChangeFn)(UIElement* el, bool forward, int count, void* user);
// NULL for none: ]c and [c then do nothing.
void ui_editor_vim_set_change(UIEditorVim* vim, UIEditorVimChangeFn fn, void* user);
```

- **`]` and `[` become prefixes in normal mode**, as `g` and `z` are (`ui_editor_vim.c:5064`).
  `_second` takes `c` and asks the host through the same path as `_ask_host`
  (`ui_editor_vim.c:4885`), with `_switch` after, so a host that showed another text has the mode
  let go of this one.
- **Anything else after the prefix does nothing** and leaves nothing pending, as vim beeps at a
  `]` it does not know; Esc lets it go.
- **With an operator waiting** (`d]c`) the operator is let go and nothing changes. In vim `]c` is
  also a motion, which a host answering in another text cannot be.
- **In visual mode** `]` and `[` stay what they are now.
- `ui_editor_vim_keys` lists `]c` and `[c`.

## Tests

Probe cases in `apps/gametest/src/ui_editor_probe.c`, each read by an arm in the `ui` group with
`doc_flags`, its docstring in `gates.py`'s list:

- **`editor-whole-lines`** -> `ui-editor-whole-lines` (the `probe_editor_shapes` shape:
  `editor_fixture`, `editor_pass`, quads read back with `ui_draw_list_quad`). A text with a short
  line, an empty line, a line long enough to wrap and a last line; one style with `whole_lines` and
  a red background on layer 0, one without on layer 1. Flags:
  - `rows`: each row of each covered line has one red quad from the text's left edge to the
    editor's right, the wrapped line's every row and the empty line's one included;
  - `ends`: a range ending at a line's start does not colour that line;
  - `under`: a selection on a covered line draws over the red;
  - `plain`: the style without the flag still bands only its characters;
  - `zero`: a zeroed style draws no quad.
- **`editor-scroll-line`** -> `ui-editor-scroll-line`. A long text in a short editor:
  - `read`: scrolled 2.5 rows down (a wheel, or `ui_editor_scroll_rows` where the probe may reach
    it), the getter gives line and rows
    that put a second editor's first glyph at the same y as the first's;
  - `set`: `ui_editor_scroll_line` there, the two editors' glyph rows at the same y;
  - `pending`: set before layout, taken at it;
  - `held`: past the last line, held as a wheel's scroll is.
- **`vim-change`** -> `ui-vim-change`, beside `vim-lookup` (its recorder's shape). Flags:
  - `asked`: `]c` asks forward 1, `[c` backward 1, `3]c` forward 3;
  - `operator`: `d]c` asks nothing, deletes nothing, leaves nothing pending;
  - `unknown`: `]x` and `]` Esc do nothing, nothing pending;
  - `visual`: `]c` in visual mode asks nothing;
  - `declined`: an answer of false leaves the carets;
  - `repeat`: `.` after `]c` makes the change before it again;
  - `read_only`: a read-only text still asks;
  - `elsewhere`: a host showing another text has vim let go of this one, as `vim-lookup`'s does;
  - `none`: with no host, nothing.
- **The vim oracle**: `]c` and `[c` sequences join `_VIM_SEQUENCES` only if vim, out of diff mode,
  keeps the keys typed after its beep as cetra does; else the spec says why they are left out.

## As built

**Phase 1** (`f636a863`). `UIEditorStyle.whole_lines` sits after `underline`.
- **`_draw`:**
  - Per line, it takes the line's end with its line break: one past the last byte, except on the
    last line, which has none.
  - A range reaches the line when it starts before that end and ends after the line's start.
  - Its quads are drawn in a loop of their own before the other ranges' bands, so a plain range on
    another layer draws over them.
  - The per-character band loop skips a whole-line style, so its background is never drawn twice.
- **The probe** (`editor-whole-lines`): `short`, an empty line, 40 `word `s and `last`, in a 600 by
  300 editor. The long line wraps to three rows, so five rows are covered. Layer 0 has a red
  whole-line range from 0 to `last`'s start; layer 1 has a green plain range on `last`'s first two
  characters. A selection sits on bytes 1 to 3.
  - `rows`: the five rows above `last` have one red quad each, all at the text's left edge and the
    same width. That width is over 40 cells and ends inside the editor's rect.
  - `ends`: no red quad on `last`'s row.
  - `under`: the selection's quad is drawn after the first red one.
  - `plain`: the green band is two cells wide.
  - `zero`: with both styles zeroed, no flat quad has the whole-line quad's place and width.
- **Verified:**
  - cetra builds with no warnings.
  - `scripts/gates.py --only ui,gate-docs` passes, 102 arms, `ui-theme-identity` and the vim oracle
    arms among them.
  - Falsified: with the flag ignored, so a whole-line style bands only its characters, `rows`
    fails and the other four pass. It finds four red quads for five rows: the empty line has none.
- **The look:** `apps/canvas --editor cetra/src/shore_runup.h -x -f 10`. Two renders on the branch
  are byte-identical, a noise floor of 0. A render with master's `ui.h` and `ui_editor.c` is
  byte-identical to them.
