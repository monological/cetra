# Spec 12.17 — movement is camera-relative again

## Context

Turn the follow camera with the arrow keys in `apps/gametest`, then press W: the character
walks across the screen rather than up it. Reported as a bug, and it is one — but not the one
it looks like.

The behaviour is deliberate. Spec 12.13 made movement **world-aligned** and argued it at
length in a comment above the code (`gametest.c:3125-3139`): camera-relative movement welds
the character's forward to the camera's, so you only ever see its back and can never cross the
frame.

**What 12.13 did not do is tell anyone.** Two documents still describe the old behaviour:

| | says |
|---|---|
| `docs/cli-reference.md:880` | "Movement under the flag is camera-relative: W into the screen, S back toward the lens, whichever way you have aimed it." |
| `AGENTS.md` (gametest row) | "movement is camera-relative off `cam_yaw` instead" |

So the documented behaviour is camera-relative, the shipped behaviour is world-aligned, and
they have disagreed since 12.13. Anyone checking the docs before reporting this would have been
told they were right.

**Outcome: W goes away from the camera under the follow camera, the docs and the code agree,
and a gate arm asserts which scheme is live so this cannot flip silently a third time.**

### Why camera-relative wins on the merits too

12.13's argument assumed forward-away-from-camera means the character's front is unreachable.
That does not hold here: `cam_yaw` moves **only** when the player presses an arrow (the camera
never chases facing — that design was tried in 12.6 and abandoned), so orbiting round a standing
or walking character to see its front is a thing the player can simply do. 12.13 traded a
momentary inconvenience for a permanent disorientation.

---

## The change

One site. `apps/gametest/src/gametest.c:3140-3141` currently spends the raw action vector:

```c
vel[0] = input_dir[0] * player_speed;
vel[2] = input_dir[2] * player_speed;
```

Rotate `input_dir` into the camera's frame first. With `f = (sin(cam_yaw), 0, cos(cam_yaw))`
the camera's horizontal forward and `r = (-cos(cam_yaw), 0, sin(cam_yaw))` its right:

```
world.x = -cos(cam_yaw) * input_dir[0] - sin(cam_yaw) * input_dir[2]
world.z =  sin(cam_yaw) * input_dir[0] - cos(cam_yaw) * input_dir[2]
```

**At the default `cam_yaw` of pi this is exactly the identity** — `sin` is 0 and `cos` is -1,
which cancels both the strafe sign and the forward negation. That is the same property 12.13
relied on to make its change invisible to the suite, now running in reverse: every gamepad
script, every trace displacement and both menu goldens touch no arrow key, so none of them
moves.

### Scope, stated rather than finessed

`cam_yaw` is the FOLLOW camera's state, and `follow_camera_update` is the only writer
(`gametest.c:3531`). Under `--no-follow-cam` the drag/orbit controller owns the camera and
`cam_yaw` stays at pi, so movement there remains world-aligned; the same is true under
`--cam-eye`/`--cam-target`, which exist to pin a framing for A/B screenshots.

That asymmetry is deliberate and goes in the comment. Deriving the yaw back out of
`engine->camera` would cover both cameras with one rule, and is the wrong trade: `--cam-eye`
states a POSE for reproducible framing, and having it silently rotate the controls is a worse
surprise than the orbit camera keeping the scheme it has today.

### The comment is the deliverable as much as the code

12.13's comment argues one direction with no record that the other was ever live. Rewrite it to
carry both, and why this came back — otherwise the next reader flips it a third time with an
equally confident paragraph.

## Verification

### The arm nothing currently provides

The `gamepad` group reads the trace's **MOVE column** — the action value the app commanded —
and explicitly not position, because five boxes fall at `rand()` positions that differ per
platform's libc (`gates.py:14672-14677`). So **no existing arm can see this change in either
direction**, which is exactly how 12.13 flipped it unnoticed.

`--trace-player` already prints `pos` and `vel`; `_GAMETEST_TRACE` skips both with
`(?:\s+-?[\d.]+){3}`. The arm needs no new probe output, only a second regex.

`gamepad-camera-relative`: two scripted pads through `apps/gametest`, both holding forward
(`ly=-1`), one of them first holding `rx=1` long enough to swing `cam_yaw` about 90 degrees.
Read the `vel` columns and compare the two headings.

- **camera-relative** (wanted): the headings differ by the camera's turn
- **world-aligned** (today): the headings are identical

Assert the turned run's heading tracks `cam_yaw`, and report both. Two-sided, so reverting the
rotation reddens it and nothing else.

### Must not move

`gamepad` (19 actions), `anim`, `ik`, `save`, `ui`, plus the `menu`, `menu_focus` and `puppet`
goldens. None touches an arrow key, so all should be bit-identical rather than merely close —
if any of them moves, the identity-at-default claim above is wrong and that is the finding.

### By hand, and it is the acceptance test

Turn the camera 90 degrees with the arrows, hold W, and confirm the character walks away from
the lens rather than across the frame. Then walk toward the camera and confirm you can still
see the character's front, which is the thing 12.13 was protecting.
