# cetra 14.11: a panel shows it has the keys

## Context

pcb's schematic pane shows no border when it has the focus, where its code pane does. ARCH says
the focused pane has a subtle border. The code pane's comes from cetra: the code editor kind's
FOCUS style (`theme.editor[UI_STATE_FOCUS]`, default in `_default_style`, `cetra/src/ui.c:161-182`).
The schematic is a **panel** that takes keys through a hook (spec 14.10) and paints itself
(`ui_set_draw`). It misses the border for two reasons:
1. A panel has one theme style, `UITheme.panel` (`ui.h:325`), with no FOCUS state; only scroll,
   text field, editor and the four controls have per-state entries.
2. A draw hook replaces everything cetra draws for the element (`_emit`, `ui.c:1618-1622`).

The user chose to fix it in cetra, so layout, 3D and every later pane kind get it too.

**The rule: a panel is drawn focused while it takes the keys** -- the rule a text field and the
code editor already follow ("FOCUS its border while it takes the keys"). A panel takes the keys
when it has a key hook (`_takes_keys`, `ui.c:573`). Restricting it so is needed, not taste: the
canvas palette's rows (`apps/canvas/src/canvas_app.c:2821`) are focusable panels with no hook,
and the focus follows the pointer over them, so "every focused panel" would outline whichever row
the mouse is on, apart from the row the palette lights. Only focusable elements are ever focused,
hovered or pressed (`_hit`, `ui.c:1841`), so every panel that is not focusable -- every menu, HUD
and container in the tree -- is untouched.

Branch and spec: `14.11-a-panel-shows-it-has-the-keys`, off cetra's master (clean, at `36419439`).

## The design

**The theme** (`cetra/src/ui.h`, `ui.c`):
- `UIStyle panel;` becomes `UIStyle panel[UI_STATE_COUNT];`, documented as `scroll` is: "FOCUS its
  border while it takes the keys, drawn over what a draw hook paints". Nothing outside `ui.c`
  reads or writes `theme.panel` (checked: cetra's apps and pcb). `_theme_entry` returns
  `&t->panel[state]`, its `default` case too.
- `_default_style`'s `UI_PANEL` case gains, for FOCUS and ACTIVE, the code editor's focus border:
  `(0.45, 0.70, 1.00, 0.6)`, width 1. So a focused pane looks the same whichever kind it is.

**The state** (`_state_of`, `ui.c:1531`, the paint state `_emit` and `ui_slider_track` read; the
easing reads `el->state` and is untouched): a panel in FOCUS or ACTIVE that does not take the keys
paints as NORMAL, with a comment saying why (a list's row follows the pointer and is no place the
keys go).

**A drawn panel** (`_emit`, `ui.c:1618`): after the hook paints, a panel whose paint state is
FOCUS or ACTIVE has its resolved style's border drawn over it -- `ui_draw_rect` with the fill and
image cleared, which draws the border alone (`ui_draw.c:229-260`). A panel with no hook needs
nothing new: `ui_draw_rect` already draws its fill and border from the resolved style.

**For the arm**: `ui_draw_list_quad_border(dl, i, vec4 border, float* width)` in `ui.h` beside
`ui_draw_list_quad`, reading the vertex's `border` and `params[1]` (`ui_draw.c:34-41, 967`); the
existing reader returns only rect, fill and kind.

## Tests

`ui-panel-focus`, a new arm in the `ui` group: `apps/gametest/src/ui_editor_probe.c` gains
`probe_panel_focus` (dispatch beside `element-keys`, `ui_editor_probe.c:3034`, using `say_flag`
and `ui_draw_list`/`ui_draw_list_quad_count` as `ui_text_probe.c:82` does), and `gates.py` a
`doc_flags("panel-focus", N, ...)` call beside `element-keys` (`gates.py:29580`) plus its entry in
the arm docs (`gates.py:28389`). Flags:
- a panel with a key hook and a draw hook: unfocused, only the hook's quad; focused, a quad over
  its rect with no fill and the default focus border, width 1; pressed (ACTIVE), the same;
- a panel with a key hook and no draw hook, focused: its own quad carries the border;
- a focusable panel with no key hook, focused (a list's row): no border;
- `theme.panel[UI_STATE_FOCUS].border` set by the app: drawn in that colour;
- a label with a draw hook, focused: no border added.

Each rule falsified once from its commit: the state rule (the row gains a border), the border
over the hook (the drawn panel has none), the theme entry by state (the app's colour ignored).

## As built

### Phase 1: the border

Built as planned. `UITheme.panel` is `panel[UI_STATE_COUNT]`; `_default_style` gives a panel the
editor's border in FOCUS and ACTIVE; `_state_of` paints a panel that takes no keys as NORMAL in
those two states, which is the one place the rule lives; `_emit` draws the resolved style's border,
fill and image cleared, after a panel's draw hook; and `ui_draw_list_quad_border` reads a quad's
border back. Nothing in cetra's apps or in pcb wrote `theme.panel`, so the array broke no caller.

**Arm**: `ui-panel-focus`, seven flags, in the `ui` group. `--only ui,canvas,gate-docs` passes:
121 arms, none skipped, the canvas `--ui` panel and palette unmoved.

**Look**: the canvas app's `--sheet board --ui --ui-keys` panel before and after a click. Clicked,
it has the rim; unclicked, none. Its fill is the border's blue, so the rim is faint there; the
look that matters is pcb's dark schematic, after the bump.

**Falsified**, each from `488f85c4`:
- The state rule dropped: `row none` failed, a focusable panel with no key hook outlined.
- The border over a draw hook dropped: `drawn focused`, `drawn pressed` and `theme colour` failed.
- The theme entry read at NORMAL whatever the state: `theme colour` failed, the app's red ignored
  for the default blue.

**Found on the way**: Homebrew's `python3` is now 3.15, which has no numpy, so `gates.py` fails to
start under it; 3.14 has numpy and runs the suite.
