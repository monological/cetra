# 11.56 — Contact shadows for the lights that cannot have a shadow map

## Context

Roadmap item 26 (C5). The row says A3's contact-shadow march should extend from the key light to the
N nearest cluster lights, and gives this reason:

> Every other light in the scene lands on CSM/punctual maps whose texel footprint loses the
> millimetre-scale contact, which is the specific artifact A3 exists to fix.

**That reason is false, and the spec corrects it.** A punctual map is a *perspective* map fitted to
one light, and `punctual_size_for` picks its edge from the layer count against a 96 MiB budget: a
lone spot gets 4096², two to six layers — which includes a point light's six faces — get 2048², and
seven or more drop to 1024². So a 90° cube face is **~1 mm/texel at 1 m** in the case this argument
names, ~0.5 mm for a spot and ~2 mm at the floor. Every rung is finer than the contact gaps A3 draws.
The contact hairline that did exist was found in 9.8, root-caused — **far-side depth storage, not
resolution** — and fixed in 10.3 (near-side storage) and 10.4 (receiver-plane bias), with
`cornell_box`'s box/floor contact as the explicit visual gate. The punctual path also runs 3×3 PCF
with per-tap plane bias. Where a map exists, the contact is already sharp.

**The real gap is that almost no local light has one.**

| | |
|---|---|
| `MAX_PUNCTUAL_SHADOW_LAYERS` (`shadow.h:21`) | **8** |
| `LC_MAX_CLUSTER_LIGHTS` (`light_cluster.h:29`) | **128** |
| layers a point light consumes (`shadow.c:771`) | **6** |

So ~120 of 128 clusterable lights can never have a map, by construction — the second point light in a
scene silently gets nothing (latched warning, `shadow.c:1268`). And **every 11.49-derived panel is
ineligible**: `create_light` defaults `cast_shadows = false`, `emissive_light.c` never sets it, and
`shadow.c:1239` skips it — measured at **41% of the lit level leaking through a solid wall**
(`specs/11.49:787`). The fog pass already concedes the same population: *"unshadowed — the engine has
no shadow map for point lights"* (`froxel_inject_frag.glsl:313`).

So 11.56 is not "sharpen a blurred contact". It is **"give the lights that structurally cannot have a
map some occlusion at all"** — a bigger and more defensible win than the row claims, and one that
flips the cull: skip lights that already have a map rather than march the N nearest.

**The derived panels are named above as motivation and are NOT served by this spec.** They are in the
map-less population for the same reason and the 41% figure is theirs, but an area panel is skipped
from marching (see the Design section, and the review correction under it). What changed for them is
only that they now count in the fold's denominator, so they no longer inflate another light's term.
The leak itself is still open.

## What the exploration settled, so it is not re-litigated

- **A postfx pass can already read the cluster light list.** `create_post_program` →
  `create_program_from_source` → `setup_program_uniforms` → `ubo_wire_blocks`, against buffers
  `glBindBufferBase`'d for the context's lifetime. `froxel_inject_frag.glsl:319` is the shipped proof
  — it walks the list with **zero C-side binding work**. Adding `#include "lights_ubo.glsl"` to
  `contact_shadow_frag.glsl` is sufficient. The row's "postfx-only" and "Wall 1 unaffected" both hold.
- **Half res is already rejected for this signal**, by 9.4 with a stated reason: *"contact shadows
  are a sharpness feature, and half-res output smears the per-texel silhouette response into a
  visible stipple."* Full internal res stays.
- **The realistic light count is one.** Every `.cscn` in `assets/` has ≤1 light. The only many-light
  path is `--point-light-grid` (clamped 11×11 = 121). The index pool averages **2 lights per
  cluster** before truncation.

## Design

### The cull is the design: skip lights that already have a map

Inside the cluster loop, `shadowMisc.y` is the punctual base layer, `-1` when the light casts none.
`if (clusterLights[li].shadowMisc.y >= 0.0) continue;` is one line, and it is both halves of the
argument at once — it is the performance cap *and* it prevents double-shadowing a light that already
has a 3×3-PCF perspective map. Directionals keep their existing path unchanged.

`froxel_inject_frag.glsl:320` is the precedent for a type/eligibility `continue` with a stated
correctness reason rather than a budget.

### The march, per light

The existing march is a constant `lightDirVS` for every pixel. A local light needs it per-pixel:

| | point (`dirType.w == 1`) | spot (`== 2`) | area (`== 3`) |
|---|---|---|---|
| direction | `normalize(posVS - P)` | same | **skip in v1** |
| reach | `min(csDistance, distance(posVS, P))` — must not march past the light | same | — |
| early-out | `getDistanceAtt` | + `spotConeFactor` | — |

**Area panels are out of v1 and the spec says why**: `posRange.xyz` is a panel *centre*, a panel has
no single `L`, and `pbr_frag` shades it through an entirely separate LTC branch that never computes
one. Marching to the centre would be a different approximation from the one the shading uses. This is
the one place the 11.49 population is not served, and it should be stated rather than discovered.

> **Review correction.** "A panel has no single direction to march along" is too strong: `dirType.xyz`
> ships a normalized panel normal and `shadowMisc.zw` its extent, so a centre or corner direction is
> available. The real reason is the one the table already gives — marching it would be a DIFFERENT
> approximation from the LTC integral the shading used, which is worse than not marching. A centre is
> good enough to weigh how much light arrives, so a panel does count in the fold's denominator.

**`view` becomes a uniform on the CS program.** `posRange.xyz` is world space; `postfx_run` already
receives `view` (`engine.c:1791`) and currently passes only `projection`. One extra uniform.

The near-plane clamp (`lightDirVS.z > 0.0`) and the `MAX_UV_LEN` screen clamp both move inside the
per-light loop, and the `ndl < 0.05` early *return* becomes a per-light `continue`.

### The composite: contribution-weighted fold

One `R8` channel cannot say "light A is blocked here, light B is not". 9.4 already booked the honest
fix as out of reach: *"True direct-only would need a separated direct-light buffer the forward
renderer does not produce; not worth it."*

So the N visibilities fold into one scalar **weighted by each light's own contribution**:

```
w_i   = luminance(colorIntensity) * attenuation(dist) * max(dot(N, L_i), 0)
vis   = sum(w_i * vis_i) / sum(w_i)
```

postfx has normals (`normalsTex`), linear Z (`linDepthTex`) and now the light list, which is
everything `w_i` needs. This is principled rather than arbitrary: it is the fraction of **direct**
light the pixel loses. It keeps the R8 target, the existing blur and the existing accumulator, and it
degrades to exactly today's behaviour at N=1.

> **Two corrections from the review, both material.**
>
> This section originally said the target, the blur and `run_temporal_accum` were "all
> single-channel". Only the target's *format* is — `ssao_blur_frag` is RGBA and already carries AO's
> bent normal in `.gba` through the same bilateral weights, and `temporal_accum_frag` is explicitly a
> shared plain-RGBA accumulator that clamps per channel. More channels are unavailable for a
> different reason, and it is the CONSUMER: `tonemap_frag` has one scene sample with no per-light
> decomposition, so N visibilities collapse to one scalar at the multiply whatever they travelled in.
> Same conclusion, sound argument.
>
> And **`sum(w_i)` above is wrong as written** — it must run over every light that reaches the pixel,
> not every light this pass marched. A light with its own map, and an area panel, still deliver light
> here; leaving them out makes `vis` mean "fraction of the MARCHED light lost" while `tonemap`
> multiplies the whole sample by it. Measured consequence: one blocked practical beside a bright
> mapped spot takes 23% off a pixel that should lose 1%.

**State the residual honestly in the code**: the fold still multiplies a summed image that includes
ambient. What this spec first wrote — that the error is *"bounded by `csStrength` and by the weight
of a light dim enough not to have earned a shadow map"* — is false twice over, and the review said
so: `create_light` defaults `cast_shadows` false, so the brightest lamp in a scene is routinely
map-less, and the layer pool overflows on the SECOND point light whatever its brightness. The two
approximations that actually remain are the omitted ambient (unchanged from 9.4) and a mapped light
counting its *unshadowed* weight, since this pass cannot read its map. The second biases the term
DOWN where a mapped light is itself in shadow — pixels already dark, which is the harmless direction.

### The gate has to change

`cs_active` requires `fog_light_count > 0` — a shadow-casting **directional**. A room lit only by
practicals never runs the pass, and the GUI says "(needs a shadow-casting directional light)". That
gate becomes "a directional **or** at least one mapless local light in view", and the GUI text, the
`--contact-shadows` help ("along the key light"), and `postfx.h:240-243`'s comment all follow.

## Phases

**P0 — the fixture and the baseline, before any shader change.** No scene in the corpus has a local
light near a contact; `contact_fixture.cscn` has *zero* lights. Build one: a practical close to a
surface with an object resting on it, plus a second light that is *not* occluded, so the
contribution-weighted fold has something to get wrong. Record the current frame — the pass does not
even run there today (`fog_light_count == 0`), which is the fail-first evidence.

Also establish the pass's own cost row: **contact shadows appear in no published timing table**.
Off/on at a fixed framing, interleaved A/B/A/B per AGENTS.md, before N is priced.

**P1 — the march goes per-light.** `#include "lights_ubo.glsl"`, the `view` uniform, the cluster loop
with the `shadowMisc.y >= 0` cull, point and spot only. **Bit-identical at N=0 local lights**: the
`contact_debug` golden pins the march arithmetic at 0 px on a sun-only fixture, and the inline IGN
carries an explicit do-not-refactor note because of it. That golden is the regression bar for this
phase.

**P2 — the weighted fold and the gate.** The `w_i` estimate, the `cs_active` change, the GUI and help
text. Goldens 0 px again (no golden has a local light).

**P3 — coverage.** A `contact` gate group, in `run_penumbra_gate`'s shape: render twice (with and
without the feature), **divide** to isolate the shadow term, refuse to proceed if `lit - umbra` is
too small to be an edge, then assert. Three arms, and the third is the one this corpus keeps
learning it needs:
- the term is non-zero where a mapless practical meets a contact (**there is no such arm today** —
  the only contact-shadow test is a 0 px golden of the debug view)
- a mapped light is **not** double-shadowed — its term is unchanged with the feature on
- the falsifier: with the occluder removed the term goes to 1, so "no shadow" and "no light" are
  distinguishable

**P4 — cost, measured not asserted.** `--point-light-grid` already exists as a many-lights harness.
Price N=1, 4, 16 mapless lights against the P0 row. Reference points: the post chain is 20.3 ms at
1600×1200 (SSR 8.3, atmosphere 4.2, GTAO 1.9); 9.4 records full-res 16-step as ~8× the old half-res
8-step march. Budget ~350 µs for the profiler scope itself on small passes.

**P5 — correct the record.** The roadmap row's justification is wrong and must be rewritten, not
merely marked done: the contact it claims to fix was fixed in 10.3/10.4, and the population it
actually serves is the ~120 mapless lights. `AGENTS.md` gains the changed gate, the area-light
exclusion, and the cost figures. Also fix two stale comments 9.4 left: `postfx.h:241` and `:249` say
"AO res" and `docs/aaa-rendering-roadmap.md:352` says "8-step per-pixel march … at AO res" — both

## Measured

### The pass, and what a light costs

`--profiler`, three interleaved repetitions per configuration, medians. On
`contact_local_fixture` at 1600x1000 requested — **3200x2000 internal**, which is where these
numbers live and they do not transfer without dividing by the pixel count.

Coincident lights, every copy reaching exactly the pixels the original does:

| lights | pass GPU | step |
|---|---|---|
| 1 | 3.153 ms | |
| 2 | 4.511 ms | +1.36 / light |
| 4 | 9.540 ms | +2.51 / light |
| 8 | 19.070 ms | +2.38 / light |

Linear past two, at **2.43 ms per additional fully-covering light**, which normalises to
**0.38 ms per megapixel per light**. Run-to-run spread under 0.06 ms, so the linearity is
real and not fitted. The 1 -> 2 step is smaller because `practical_front` points back toward
the camera and most of its marches hit the near-plane clamp within a step or two.

**Cost tracks COVERAGE, not count, and that is the cluster walk doing its job.** Sixteen
lights SPREAD across the scene (`--point-light-grid 4,3,5`) cost **+0.77 ms** over the
two-light baseline, against the +38 ms that sixteen coincident ones would. A pixel marches the
lights whose cluster entry reaches it, so a scene with many small practicals pays for the few
that overlap it. A scene with many large overlapping ones genuinely pays, and there is no cap
hiding that — see below.

CPU is flat at **0.083-0.094 ms** across every configuration: the pass is one draw whatever
the light count.

### No cap, deliberately, and what that means

Nothing bounds the number of lights a pixel marches except the cluster list itself. A cap would
be a silent truncation of the kind `AGENTS.md` warns about — it would make the term wrong in
exactly the crowded scenes where it is largest, with nothing to say so. The bound that exists is
the honest one: `LC_MAX_CLUSTER_INDICES` is 6144 over 3072 clusters, so the index pool saturates
at an average of 2 lights per cluster and the culler reports it. On the 16-light grid above it
was saturated (6144 of 6144 indices) against 3966 at two lights.

### The instrument, which had to be worked around

**The profiler cannot price a sub-millisecond pass inside a heavy frame on this driver.** Timer
queries are checked and never waited on (`PROFILER_RING` 4), and on a frame with a 31 ms opaque
pass every small scope — contact shadows, GTAO, the AO denoise, spec-occ, SSR, all three resolves
— retires unavailable on every slot and reports **0.000 ms**. The same scopes read normally on a
light frame. That is why the pricing above runs on a two-mesh scene at high resolution rather than
on `contact_fixture` where P0's baseline was taken, and why P0's own 0.29-0.33 ms figure should
not be differenced against anything measured later: re-running that exact configuration an hour
later read 0.055 ms with every other small scope down by the same factor.

## The review, and what it changed

Eight agents over the branch after P5 closed it — four on quality (shader, C integration, gate and
fixture, whole-change design), four on cleanup (reuse, simplification, efficiency, altitude). They
found three defects and one dead test, and the spec had shipped all four.

**The fold's denominator omitted every light it skipped.** Recorded above where the design was
stated, because that is where the error was made. It is the largest of the four: the term was
"fraction of the MARCHED light lost", applied by `tonemap` to a sample containing every light.

**`shadow_layer` was read raw, and it goes stale.** It is maintained only while the depth pass runs,
so switching shadows off at runtime leaves every mapped light claiming a layer nothing draws — and
the march then skipped exactly the lights that had just lost their maps, while `cs_mapless_lights`
fell to 0 and switched the pass off in a practicals-only room. **Not an engine-wide property**: the
review checked, and `pbr_frag` survives it because `punctualShadow()` bounds the layer by
`punctualShadowCount`. This pass was the first consumer of `shadowMisc.y` as a standalone eligibility
test, so the exposure was new. Fixed at the PACK SITE (`light_cluster.c`) behind
`shadow_live_punctual_layer`, so all three consumers now read one meaning. The sharpest part:
`shadow.c` documents this exact hazard **twelve lines below** the loop that ignored it.

**The cluster walk ran on every pixel of every frame**, including frames whose light list is empty
and every iteration is a guaranteed `continue`. Gated on `lightCounts.y`, already in the UBO.
Note the efficiency agent's proposed gate (`cs_mapless_lights`) was bit-exact against the OLD fold
and would have changed behaviour against the fixed one, since skipped lights now carry weight — the
two findings had to be resolved together rather than applied in sequence.

**A fixture assert that could not fail.** Assert 3 measured a mirror that three lines above it
*construct*, so it held for every value of every constant in the file, while the four properties
`contact-fold`'s closed form actually rests on — equal range, colour, height, mirrored depth — went
unchecked. Replaced and falsified both ways.

### One claim the review got wrong, and the check that caught it

The design agent reported the texel arithmetic as 2× off, on the grounds that `6 · 2048² · 4` is
100.7 MB against a 96 MB budget. Those are the same number in different units: 100,663,296 bytes is
exactly 96 MiB, the test is `<=`, and a point light does get 2048². The claim as originally written
was right for the case it named; what it lacked was that the size is layer-count dependent, which is
what the Context section now says. **Verify a correction before taking it** — the same rule this spec
applied to the roadmap row applies to the review of the spec.

### Coverage the review left open, and how it closed

Both gaps below were recorded as known-uncovered when the review landed. Both are now arms, and the
suite goes **210 → 212**.

**The mixed path — `contact-mixed`.** `contact_local_fixture` has two point lights and no
directional, so nothing rendered `hasKeyLight == 1` with local lights folded — the path where the
denominator fix bites hardest and where the summation order changed. The arm adds a shadow-casting
directional as a gate variant, then a *mapped* lamp beside it, and reads two steps:

| | strip |
|---|---|
| local lights only | 0.6326 |
| + a key directional | 0.8192 |
| + a MAPPED lamp beside it | 0.8957 |

Each step adds exactly one light that joins the **denominator and nothing else** — the sun's ray
leaves over open ground so it carries no occlusion of its own, and the mapped lamp is never marched.
The closed form predicted both before they were measured: **0.8187 and 0.8958**. And the second step
is the denominator fix alone: restoring the old behaviour makes the third read **0.8208, exactly the
second**, because a mapped light then contributed nothing at all.

**The stale layer — `contact-stale`, and it needed a new instrument.** `--no-shadows` clears the
master switch *before frame 0*, so no punctual layer is ever assigned and an arm using it exercises
the never-enabled path only. The state that leaves `shadow_layer` stale is the **transition**, and
headless had no way to reach it — which is exactly why the defect survived five phases and a full
gate run. **`--shadows-off-at <frame>`** clears the switch mid-run, in the `--render-scale-at` idiom
and for the same reason: a runtime transition a gate has to see. The arm reads the map-less **0.6326**
after the switch against **1.0000** with the system left on, so both states sit in one line.
Falsified by packing the raw `shadow_layer`: the strip goes to **1.0000** — the light keeping a map
it no longer has, which is the defect exactly.
