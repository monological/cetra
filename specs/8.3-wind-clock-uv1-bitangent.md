# Wind Clock + UV1 Guard + Bitangent Retirement

Three phases, one commit each, verified independently. Phases 1-2 are surgical
correctness fixes that cannot change any rendered pixel today. Phase 3 changes
the vertex format engine-wide and CAN visually regress mirrored-UV imported
assets, which is why it is last and separately revertable.

## Context

Two defects left over from the tree work (specs 8.0–8.2, now on master). Both are
invariants currently enforced by a comment rather than by the code, and both are
latent — nothing in the repo triggers either today, which is exactly why they
would be found late and confusingly.

**1. The wind clock disagrees between passes.** Wind displacement in the vertex
shader is a function of a `time` uniform, and two passes run it: the shadow depth
pass and the main shading pass. They take that value from different places.
`shadow.c:671` uses `engine->last_frame_time`; `render.c:381` uses `time_value`,
a parameter of `render_current_scene` that the *app* supplies. Five apps pass
five different things:

| caller | passes | clock |
|---|---|---|
| `apps/tree` | `engine->last_frame_time` | matches — deliberately |
| `apps/render`, `apps/shapes` | fresh `glfwGetTime()` | ~a frame ahead |
| `apps/gametest`, `apps/spores` | `game->time` | fixed-timestep sim accumulator |
| `probe.c:203` | `0.0f` | frozen |

`game->time` is a different clock entirely: quantised to `fixed_timestep`,
paused with the game, and drifting from wall time whenever the loop clamps a
long frame. A game-framework scene with a wind material would render its shadow
from the geometry's pose at a different moment than the geometry is drawn at —
the shadow sways out of phase with the thing casting it. The comment at
`shadow.c:668-670` asserts the two are the same clock, which is true only for
one app.

**2. UV1 means two things at once.** Engine-wide, UV1 is the second texture
coordinate set; `pbr_frag.glsl:832` reads `vec2 aoUV = (texCoords2Exists > 0) ?
TexCoords2 : uv;`. But tree and grass meshes pack wind data there (`.x` branch
phase, `.y` flex weight), which are not coordinates at all. Calling
`set_material_ambient_occlusion_tex` on a tree material would sample the AO map
at (phase, flex) — compiles, links, runs, produces plausible garbage, no warning
possible. The only protection today is prose in `tree_gen.h` and the specs.

## Design

### Phase 1: One engine-owned frame clock

**Why this shape and not the obvious alternatives.** The ordering decides it: the
shadow pass runs at `engine.c:2036`, the app's render callback at `engine.c:2090`.
Anything the app supplies arrives *after* the shadow map is already rendered. So
passing the time into `render_shadow_depth_pass` cannot work (`engine_run` does
not yet know what the app will pass), and having `render_current_scene` stash it
for the shadow pass to read cannot either (the shadow pass would read the
previous frame's value — the same bug, one frame wide).

The clock therefore has to be established by whoever drives the frame, before the
shadow pass, and read by both. Confirmed workable because **`run_game` does not
drive its own loop** — it delegates to `engine_run` (`game.c:264-271`), and
`game->time` is advanced by `game_frame_update` at `engine.c:2019`, before the
shadow pass at 2036.

- **`engine.h`**: add `double render_time` — "the time this frame renders at;
  every pass that animates from time reads this one value." Place it with the
  per-frame latches (`normals_this_frame`, `gui_frame_active`), whose comment at
  `engine.h:154-156` describes exactly this idiom. It does not duplicate
  `last_frame_time`, which is declared under `// FPS tracking` and is being
  abused for this today.
- **`engine.c`**, right after `last_frame_time` is updated (~line 1992):
  `engine->render_time = engine->last_frame_time;` — the default for
  non-game apps.
- **`game/game.c`**, at the end of `game_frame_update` (after the accumulator
  loop, ~line 246): `engine->render_time = game->time;`. This is the point of the
  design — a game keeps its deterministic sim clock, and wind correctly freezes
  when the game is paused. The write lands before the shadow pass.
- **`shadow.c:671`**: read `engine->render_time`. Fix the now-accurate comment.
- **`render.c` / `render.h`**: drop the `float time_value` parameter from
  `render_current_scene` and read `engine->render_time` at `render.c:381`. This
  is what makes the desync unrepresentable rather than merely fixed. Note the
  asymmetry it removes: `uDeltaTime` and the wind params already come off the
  engine/scene at that same call site; only `time` came from the caller.
  Thread-through in `_render_scene_iterative` / `_render_node` goes away too.
- **Call sites** (6): `apps/tree`, `apps/render`, `apps/shapes`, `apps/gametest`,
  `apps/spores`, `probe.c`. Every app's semantics are preserved — tree and the
  wall-clock apps get the same value, the game apps keep `game->time`.
- **`tree.c:1231-1232`**: delete the comment about matching the shadow pass; the
  engine now guarantees it.

**`probe.c` needs explicit handling, not inheritance.** The probe bake runs its
own shadow pass (`probe.c:116`) and then shades six faces (`probe.c:203`). Those
agree today only because both are effectively 0 at load. Freeze deliberately:
save `engine->render_time`, set it to 0 before the shadow bake, restore it with
the rest of the substituted state (`probe.c:119-152` / `:222-240`). Freezing is
right for a static bake and is consistent with the existing bind-pose treatment
of skinning documented at `probe.c:46-49` — but it must cover both the bake and
the shading, or a future mid-run re-capture silently desyncs.

### Phase 2: Make the UV1 rule structural

One line, no C change:

```glsl
// pbr_frag.glsl
uniform int uWindMode;   // add the declaration
...
vec2 aoUV = (texCoords2Exists > 0 && uWindMode == 0) ? TexCoords2 : uv;
```

`uWindMode` is already uploaded per material in
`_update_program_material_uniforms` (`render.c:200`), `uniform_set_int` is
location-guarded (`uniform.c:190-194`), and the vertex and fragment stages of one
program share a uniform location — so declaring it in the fragment shader picks
up the existing upload with nothing else to change.

**This IS the fix, not a stopgap.** `wind_mode` is already the authoritative
declaration of UV1's meaning: the vegetation modes *define* UV1 as (phase, flex)
— the vertex shader reads it that way unconditionally under modes 1 and 2, so a
vegetation mesh whose UV1 held real texture coordinates would displace by
garbage and is broken by construction. There is no case the branch fails to
represent. The alternatives are worse, not merely bigger:

- A separate "uv1 semantic" enum on the material would be redundant state — a
  second field that must always agree with `wind_mode`, with an undetectable
  failure mode when it doesn't. Deriving beats declaring twice.
- A dedicated wind vertex attribute buys the ability for a wind mesh to also
  carry a real second UV set — a need nothing has (a static lightmap on
  geometry that displaces every frame is broken anyway, and the AO path is the
  engine's only UV1 consumer; audited across all shaders and VAO setup). Cost
  is a Mesh stream, VBO, upload path, builder and import plumbing, 8
  bytes/vertex. Slot audit: meshes use 0-8; 9-11 are the particle billboard's
  per-instance attributes (bare literals, separate VAO — no hardware conflict,
  but taken by convention); 12-15 are free, and GL 4.1 guarantees 16. If this
  is ever done, slot 12 is the clean choice. Revisit only if a second consumer
  of per-vertex aux data appears, and then likely as a generic aux attribute
  rather than a wind-specific one.

Comment updates should say the shader *enforces* the rule, not ask the reader to
follow it: `material.h`'s wind_mode block gains "modes >= 1 redefine UV1 as
(phase, flex); the AO path falls back to UV0 for these materials", and
`tree_gen.h:21-22`'s "NB for the caller: never bind an AO texture" warning is
replaced by a note that the engine handles it.

While in `common.h`: document slots 9-11 in the canonical `GL_ATTR_*` map. The
audit found they are consumed by the particle billboard renderer as bare
literals (`particle_renderer.c:45-61`, `particle_vert.glsl:7-9`) and the header
is silent about them — one comment prevents the next person from "discovering"
a free slot that isn't.

### Phase 3: Retire the bitangent stream (tangent.w handedness)

The audit showed slot 4 is nearly dead weight: `pbr_frag.glsl:790-795` already
re-derives `B = cross(Ng, T)` via Gram-Schmidt and reads the interpolated
bitangent ONLY for a handedness sign (`if (dot(B, TBN[1]) < 0) B = -B;` — same
pattern at :644-648 for clearcoat). That sign carries real information solely
for Assimp-imported meshes with mirrored UVs; every procedural producer emits
exactly `cross(N, T)`. Standard fix, and the glTF convention: a vec4 tangent
whose `.w` is the handedness, bitangent derived in the vertex shader.

Net: **frees slot 4 and saves 8 bytes/vertex** (drop 12-byte bitangent, add
4-byte tangent.w) on every mesh in the engine. The raw savings are modest; the
recurring cost is the real motive — every new mesh producer has been filling a
stream the renderer reduces to one bit (tree, grass, and ground all just did),
and retiring it ends that tax. It is also a small correctness win: the skinned
path currently bone-rotates the authored bitangent, which shears under blended
non-uniform-scale bones (the same class of bug pbr_skinned_vert already fixes
for normals with an inverse-transpose); deriving B after the transform
sidesteps it. And it matches how normal maps are actually baked: mikktspace
defines B as w * cross(N, T) reconstructed at shading time, which is what
glTF's vec4 tangent encodes.

Complete reader/producer list (audited; `mesh->bitangents` has no other C
readers, and `shadow_depth_vert` uses no tangent data):

- **`mesh.h` / `mesh.c`**: `tangents` becomes 4 floats/vertex (slot 3 upload
  becomes 4f); delete `bitangents`, `bitangent_vbo`, the slot-4 upload block,
  and the destructor frees.
- **`common.h`**: retire `GL_ATTR_BITANGENT` (comment the slot as free).
- **Shaders** (`pbr_vert`, `pbr_skinned_vert`, `shape_vert`):
  `layout(location=3) in vec4 aTangent;`, drop `aBitangent`, derive
  `vec3 B = cross(N, T) * aTangent.w` AFTER the model (and bone) transform of
  N and T. The skinned path currently bone-rotates the authored bitangent;
  deriving after rotation replaces that. `pbr_frag` needs NO change: TBN stays
  a mat3, the sign-preservation branch at :794 becomes a no-op by construction
  (dot of the derived B with itself), and the anisotropy path at :993 reads the
  now sign-corrected TBN[1], which is more correct for mirrored UVs, not less.
- **`import.c:557-611`**: compute `w = sign(dot(cross(N, T), B_assimp))` per
  vertex from the Assimp bitangent, store into tangent.w, stop copying the
  bitangent array. This is the ONLY producer with real handedness.
- **Procedural producers** — all emit w = 1 and stop writing bitangents:
  `geometry.c` primitives (cube/cylinder/plane/sphere fill explicit
  cross(N,T) arrays today), `apps/tree/src/tree.c` ground mesh,
  `apps/tree/src/mesh_builder.{h,c}` (`mb_vertex` loses its bitangent
  parameter; `btn` stream deleted), which covers `tree_gen.c` and `grass.c`.

Risk and why it is phase 3: any mistake shows up as flipped normal-mapped
lighting, and only on imported assets with mirrored UVs — subtle to spot.
Verify with before/after headless renders of the imported scenes, not just the
procedural ones.

## Verification

```bash
./build.sh
# tree: wind and its shadow must stay locked. Strip the frames and check the
# canopy shadow moves with the canopy, not against it.
./out/bin/tree -x -f 480 --screenshot-every 80 -S <scratch>/wind.ppm
# the curtain scene is the other wind consumer (cloth mode, moving shadows)
./out/bin/render -m assets/abandoned_window/abandoned_window.cscn -x -f 240 \
    --screenshot-every 80 -S <scratch>/curtain.ppm
# probe capture path must still bake cleanly
./out/bin/render -m assets/abandoned_window/abandoned_window.cscn --probe -x -f 60 \
    -S <scratch>/probe.ppm
# the two game-loop apps are what the clock fix is for -- they must still run
./out/bin/spores -x -f 120 -S <scratch>/spores.ppm
```

`gametest` is windowed-only, so run it interactively for a few seconds to confirm
the loop is intact.

For the UV1 guard, the direct check is that binding an AO texture on a
vegetation material no longer samples wind data: temporarily
`set_material_ambient_occlusion_tex(bark_material, bark_roughness_tex)` and
confirm the trunk shades from UV0 rather than going haywire, then revert.

Phase 3 verification is before/after image comparison, captured BEFORE starting
the phase:

```bash
# imported, normal-mapped, the only real handedness carriers:
./out/bin/render -m assets/abandoned_window/abandoned_window.cscn -x -f 120 -S <scratch>/p3_window_{before,after}.ppm
./out/bin/render -m <a my_models FBX with normal maps> -x -f 120 -S <scratch>/p3_model_{before,after}.ppm
# procedural (w = 1 everywhere, must be pixel-identical):
./out/bin/tree -x -f 120 -S <scratch>/p3_tree_{before,after}.ppm
```

Compare with `magick compare -metric AE` — the procedural scenes must differ by
~0 (only TAA/exposure noise); the imported scenes must show no lighting flips on
normal-mapped surfaces. Flipped-looking bump lighting on any mirrored-UV island
means the import-path w computation has the sign inverted.
