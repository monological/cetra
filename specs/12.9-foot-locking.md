# Spec 12.9 — Foot locking

## Context

Spec 12.4 shipped foot *planting* and booked its successor in the same breath. Planting asks
"where is the ground under this foot right now?" every frame and keeps **no memory**, so the
point a foot solves to travels with the character. A walking character therefore slides — not
as a bug to find but as a property of the design — and the stride runs at **89% of the clip's
own** (`ik-swing`: 0.128942 against 0.149859).

`docs/game-engine-roadmap.md` Part 3 item 6 is this work, and it is the only remaining item
before Steamworks. `docs/foot-locking.md` already carries Holden's technique and names the four
things `ik.c` lacks: no contact signal, no hysteresis, no held contact point, position-only
blending — plus a fifth note that `max_pelvis_drop` is the remedy the author warns against.

**Host app: `gametest`.** It is the only IK host in the tree (`apps/render` has no IK at all),
it already owns the ramp and the three steps, the thirteen-arm `ik` gate group, and a
`--ik-probe` that runs headless with no GPU. Nothing here needs a new app or a new fixture
world.

**Rig: the generated puppet, gaining a toe.** Not raiden — that commit has been reverted and the
model is Konami-derived. The puppet is generated by `assets/generators/gen_puppet_fixture.py`,
so a toe bone is a table entry rather than a download, and it stays deterministic, tiny and
license-clean. Two committed assets make this work without any new art:

- `assets/models/strut_walk.fbx` — a real walk cycle on the `cetra_rig:` skeleton, **with
  `LeftToeBase`/`RightToeBase` channels**, already binding onto the puppet by exact name
  (`anim-clip-loads` asserts exactly that). It has the knee bend and the stance phase the
  generated `gait()` does not.
- `assets/models/t_pose.fbx` — a fully skinned humanoid on the same rig, with toe bones. This
  is the "real character judged by eye" that `docs/verification.md:538` has owed since 12.1,
  reachable through gametest's existing `--puppet <path>`.

Outcome: a foot in contact holds one fixed **world** point for the whole contact phase, the
slide goes to zero, and the stride returns to the clip's own.

---

## Design

### Where locking lives: in `ik.c`, above the solve

`ik.h` already states that whether a foot is planted is decided in the solver "and never by the
caller", because only the solver sees this frame's animated pose — a caller reads its own last
solve. That argument applies unchanged to the contact label and the lock state, so locking is a
layer in front of `solve_two_bone`, not a change to it, and not the app's to re-implement.

The one thing the solver lacks is **world space**. A frozen contact must be a world point; the
solve works in model space. `gametest.c:2951-2953` already computes `to_world`/`to_model` from
`player_skel_root->global_transform`, so the matrix exists at the call site.

New engine surface, `cetra/src/ik.h` / `ik.c`:

- `void ik_set_world(IkSystem*, mat4 model_to_world)` — by-function (it inverts once and stores
  both), called each frame before the animator tick.
- `ik_add_foot` gains an optional **toe bone**. Holden's rule is lock the toe, not the heel; the
  solve still positions the ankle, derived from the toe target by the current ankle→toe offset.
  A NULL toe keeps today's ankle-locking behaviour, so the API stays usable on a toeless rig.
- `IkFoot` gains `contact_world`, `locked`, `time_since_transition`, the previous frame's clip
  toe position, and the inertialization offsets (`offset_pos`, `offset_vel`).
- `IkFootParams` gains `lock_distance`, `unlock_distance`, `contact_height`, `contact_speed` and
  `transition_time`. **Every distance is a fraction of leg length**, per 12.5's rule that metres
  do not carry to a rig of another size — the same units `plant_fraction` and `max_pelvis_drop`
  already use.

### The contact label, and where it deviates from Holden

Holden labels contacts offline from toe speed and height, on clips that carry root motion. Ours
do not — the character controller moves the entity — so model-space toe speed during stance is
the walk speed, not zero, and thresholding it would label nothing.

So the label is derived at runtime from the clip's own pose at the seam (`global_transforms`
before any IK write): **toe height above its ground target, and vertical toe speed**. Both are
rig-agnostic, need no authored data and no baking step, and the deviation is deliberate — record
it in the spec rather than leaving the next reader to rediscover why the horizontal term is
absent.

This is checkable rather than hopeful: `strut_walk.fbx` has a known stance window, so a gate arm
asserts the labeller recovers it and — the half that matters — that it is neither always-on nor
always-off.

### What goes away

`max_pelvis_drop` is the warned-against remedy, and 12.5 found its cap has **never been
exercised** by any arm. It is replaced as the primary reach remedy by an exponential soft-clamp
on extension, with the drop bounded hard. Holden's judgement, worth quoting in the spec: *a
little sliding is better than breaking the source animation.*

### Decisions already taken (do not relitigate)

- **All six phases**, not a subset. The extension soft-clamp and the inertialized transition are
  in scope, so every one of the four gaps `docs/foot-locking.md` names is closed by this spec.
- **The toe carries a box**, and `puppet_golden` / `menu` / `menu_focus` are re-baked.

## Phases

Each ends with the affected gate group green and is independently revertable. Branch
`12.9-foot-locking`; spec committed first, on its own, before any code (house rule).

**Phase 0 — the instrument, before anything moves.** The 12.8 lesson, and 12.4's own: eleven of
twelve arms passed while the feet were welded to the floor. Add `--ik-probe lock` to
`gametest.c` (alongside the existing ten cases, same `ik <case> <label> <key> <numbers>` grammar
at `%.6f` so NaN fails by absence), ticking a walk while translating the rig at the clip's own
stride speed and printing the **world-space** foot position and contact state per frame. Add
`ik-slide` to `scripts/gates.py`, measuring horizontal world travel of the foot during one
contact phase. **It must be red today** — record the number in metres; an arm that cannot fail
now will not prove anything later.

**Phase 1 — the rig gains a toe.** `LeftToeBase`/`RightToeBase` in the generator's `BONES` table
(with a box: a toe nobody can see is a toe nobody can judge). Regenerate; `fixture-gen` proves
byte-reproducibility. `anim-clip-loads` should now match two more `strut_walk` channels — assert
the new count. **Re-bake `puppet_golden`, `menu` and `menu_focus`**, which is owed anyway: both
menu goldens have been stale since 12.6 flipped the follow camera on.

**Phase 2 — the contact label.** Per-foot clip-pose history and the height/speed thresholds in
`ik.c`; the probe prints the label. Arm: `ik-contact` asserts the stance window against
`strut_walk`'s known shape, and that the label is not constant.

**Phase 3 — the lock, with hysteresis.** `ik_set_world`, the frozen `contact_world`, the two
thresholds. Arms: `ik-lock` (slide within a tolerance of zero — the Phase 0 arm turning green),
`ik-hysteresis` (bounded transition count over a cycle; one threshold oscillates, two do not),
`ik-unlock` (releases past `unlock_distance` rather than straining the chain).

**Phase 4 — inertialization.** Replace the plain position lerp on `applied_target` (`ik.c:395`)
with the cubic blend carrying velocity. Arm: bounded acceleration across a transition — a
position-only blend arrives at a lock with the wrong speed and is dragged straight afterwards,
which is a number, not a look.

**Phase 5 — extension soft-clamp, pelvis drop demoted.** Arm: at full extension the ankle sits
inside the clamp and the pelvis moves less than a stated bound.

**Phase 6 — the look, and the docs.** `docs/foot-locking.md` currently ends "Nothing here is
implemented yet" — rewrite its last section as what shipped and what deviates.
`docs/verification.md`'s foot-planting section (its Owed verdict, and the stale "twelve arms"
count where the group now has thirteen), `AGENTS.md`'s `ik.c/h` row, and
`docs/game-engine-roadmap.md` Part 3 item 6.

## As built — Phase 0, the instrument

`--ik-probe lock` and the `ik-slide` arm. **The number this spec exists to move:**

```
ik lock clip seconds     1.433333
ik lock clip stride      0.568040
ik lock foot lift        0.165302
ik lock contact ticks    50
ik lock contact fraction 0.581395
ik lock plant slide      0.108473
ik lock plant slidefrac  0.132284
```

A stance foot travels **0.108473 m across the ground** — 13.2 per cent of this rig's leg —
while the body moves at the speed that would hold it still. `ik-slide` is RED, deliberately,
and stays red until Phase 3. An arm that could not fail before the feature existed would
prove nothing after it.

Two things about the instrument were wrong on the first run and are worth carrying:

- **The contact band is a fraction of the foot's own LIFT, not of leg length.** Stated in leg
  lengths it read **77 per cent of the cycle** as contact, swallowing a low swing pass along
  with the stance; the window then had near-coincident endpoints, which halved the derived
  stride and tripled the slide to 0.362 m. At 15 per cent of lift the window is 58 per cent of
  the cycle, which is what a walk's stance actually is.
- **The stance velocity is a least-squares fit over the window, not its two endpoints.** A foot
  that rocks at heel-strike and toe-off moves the endpoints without moving the average.

The body speed is derived rather than chosen, which is what makes the number attributable: it
is the stance foot's own mean backward velocity, so it is by construction the speed at which
the animation's feet are stationary in the world. The residual 0.108 m is therefore entirely
the clip's stance velocity not being constant — which no single body speed can absorb and only
a frozen contact point can.

**`PLAYER_SPEED` is 10 m/s on a rig with an 0.82 m leg**, against this clip's own 0.57 m/s.
Locking cannot rescue that: at more than ten times the stride speed every lock breaks its
`unlock_distance` immediately, which is the technique behaving correctly. Whatever the game
does about that is a separate question from whether the mechanism works, and this probe asks
only the second.

## As built — Phase 1, the toe

`LeftToeBase` / `RightToeBase` on the generated puppet, 20 bones to 22. `strut_walk.fbx`
already carried channels for both, so `anim-clip-loads` — which reads the joint count out of
the emitted glTF rather than holding a constant — went from 20 of 20 to **22 of 22** with no
edit. All fourteen `anim` arms and all thirteen pre-existing `ik` arms pass unchanged.

The toes are **appended** to the bone table rather than filed beside their own feet, because a
bone inserted mid-table renumbers every one after it and the order is what the engine
accumulates globals in. Parent-first is the only property the table must have, and the end of
the list satisfies it.

They take the front of the existing foot rather than extending it: the foot box gives up the z
it hands over, so the union spans exactly what the foot did. That is not tidiness — the
generator asserts the mesh is symmetric in z, and a toe reaching further forward than the heel
reaches back fires it. The sole stays at y = 0 on both boxes and the ankle's bind is untouched,
so `sole_offset` is still 0.080000 and `ik-sole` never moved.

**One golden moved, not three.** `puppet` by 1641 px, re-baked. `menu` and `menu_focus` read
**0 px** — the plan expected them to move, and they did not: the player sits behind a backdrop
at that framing and the foot is not in it. So the re-bake this phase was budgeted for was
mostly not owed, and the two flaky menu goldens did not have to be touched at all.

## As built — Phase 2, the contact label

`ik_contact_label` in `ik.c`, `ik_foot_set_toe` on the header, and the `ik-contact` arm.

```
ik lock label fraction 0.500000
ik lock label agree    0.754386
ik lock label runs     3.000000   over 3 cycles
```

**The label is judged at the ANKLE and the contact is held at the TOE**, and that split was
measured rather than chosen. The first implementation judged at the toe, as Holden does, and
found **6 contacts over 3 cycles** — each stance broken in two. `CETRA_IK_TRACE=1` (the
per-tick stderr dump the probe now carries for exactly this) named the cause: on a clip
retargeted onto a rig of other proportions, the toe JOINT passes back through its own bind
clearance in mid-swing — 0.0390 against a stance value of 0.0137 — and because that pass is the
bottom of an arc it is momentarily slow as well, so neither the height threshold nor the speed
threshold rejects it. The ankle at the same instants reads 0.12 airborne against 0.085 planted
and separates cleanly.

Holden detects at the toe because his clips are authored for the rig that plays them. Ours are
not, and this is what that costs. The toe remains what a lock HOLDS, which is a question about
where the contact is rather than about how it is found.

**`runs == cycles` is the whole arm**, and it is the only one of the three numbers that saw the
bug: with the label flapping, the fraction moved from 0.49 to 0.50 and the agreement from 0.62
to 0.75 — neither of which any bar would have caught. A count of state changes is what says a
boolean is steady.

The second deviation from Holden, recorded once here rather than rediscovered: contacts are
labelled **at runtime from the pose at the solve seam**, not offline from the clip. Our clips
carry no root motion — the character controller moves the entity — so a stance foot's
model-space horizontal speed is the walk speed rather than zero, and the horizontal term the
method thresholds on would label nothing. Vertical height and vertical speed say the same thing
about a foot that has been set down and not yet picked up, and need no authored data and no
baking step.

## As built — Phase 3, the lock

`ik_set_world`, `ik_lock_update`, the held `contact_world` point, and the arms `ik-slide`,
`ik-hysteresis`, `ik-unlock`.

```
ik lock hold fraction  0.500000   the lock holds half the cycle
ik lock hold pins      3          over 3 cycles: one contact each
ik lock plant slide    0.085407   10.4 per cent of a leg
ik lock hold slide     0.047165    5.8 per cent of a leg
ik lock fast           18 ticks per lock against 43 at the clip's own speed
```

**The slide falls by 45 per cent**, both numbers read over the same ticks. `ik-slide`'s bar is
2 per cent of a leg and is not met yet; the residual is identified and is Phase 4's.

Four things this phase found, none of which was in the plan:

- **The solve wrote only hip, knee and ankle, so anything below the ankle kept the clip's
  global while the ankle moved out from under it.** A latent defect since 12.4, unobservable
  until Phase 1 gave the corpus a rig with a bone below an ankle — on raiden, which has two
  toes a side, IK was never run. `rotate_below` now carries the ankle's subtree through both
  chain rotations, about the same pivots. It cannot re-accumulate: `ik_solve` deliberately
  takes no `local_transforms`, and a rigid rotation about a point needs only the globals.
- **The release fade and the lock were fighting.** `plant_fraction` ran the first five ticks of
  every stance at 0.63 to 1.00 weight, so a foot could not hold the point it had just pinned
  and the slide came out WORSE than planting's. A locked foot now takes its weight unfaded:
  the fade answers "is this foot down" from height alone because until this spec there was
  nothing better to ask, and the contact label is both better and STRICTER (0.05 of a leg
  against 0.10), so nothing is dragged that would not have been.
- **A lock must be taken verbatim, not eased into.** By the time a contact fires,
  `applied_target` has spent the whole swing chasing a fast-moving foot and is a long way
  behind it; easing makes the lock inherit that lag and pay it off across the stance.
- **Measuring each pass over its own window is not a comparison.** The height window opens
  about three ticks before the label does, and that sliver of genuine swing is larger than
  everything the feature does — it read 0.109 planted against 0.134 held and said the lock had
  made things worse. Both passes are now read over one interval, the longest the lock actually
  held, with `ik-contact` bounding that interval's shape from the other side.

**And one measurement that was not a finding at all.** The `menu` golden read **48,886 px**
against a build that had changed nothing it could see. It survived a bisect across four
commits, a build of master, a build of each phase, and a diff proving the Phase 1 and Phase 2
binaries render that frame byte-identically by hand — and then read **0 px on a re-run of the
same binary with no rebuild**, as did `menu_focus`. `docs/verification.md` records this
instability at 752, 672 and 675 px and says in terms that these two goldens cannot support
single-measurement attribution. **It reaches 48,886 px**, which is a focus highlight rather
than a few edge pixels, and that is worth writing down: the recorded magnitudes are small
enough to look like noise around a real change, and this one is not.

## As built — Phase 4, inertialization

`blend_rate` (1/seconds, an exponential ease) becomes `transition_time` (seconds, a cubic
Hermite from the captured offset to zero). **All seventeen `ik` arms pass and all 33 goldens
are 0 px.**

```
ik lock clip stride    0.952081   read from the clip alone
ik lock label agree    0.914894   up from 0.754
ik lock plant slide    0.078273    9.5 per cent of a leg
ik lock hold slide     0.011222    1.4 per cent of a leg
```

**0.0783 to 0.0112 m: the slide is down 86 per cent**, and the held phase is steady to ±0.003 m
over forty ticks.

The velocity term is what a lerp drops and is the whole point — but it needs the standard
guard: it may not carry the output further from the target than the position offset already
is. Without it a transition captured at a large velocity and a small offset blends the foot
OUT and back.

Three of the four numbers above moved for reasons that were not the blend, and each is worth
more than the phase's own change:

- **The reference has to come from the clip, not from a solved pass.** The body speed was being
  read off the planting pass, so it moved whenever the solver did — 0.587 m/s under planting,
  0.895 under an inertialized planting — which would have made every A/B incomparable with the
  one before it. A fourth pass at weight 0 now supplies the window and the speed, and nothing
  else. Label agreement rose from 0.754 to 0.915 as a side effect: the label is about the clip,
  and now so is the window it is compared against.
- **The contact is captured AFTER the solve.** Taken from the clip's pose, the point is
  somewhere the foot is not yet, so the lock spent its first ticks dragging the foot onto it —
  travel across the ground, reading as exactly the slide the lock removes. Captured at the end
  of the frame the decision is made, the pin moves nothing at all: that frame used the caller's
  own target. It also retires the method's "height clamped to the ground" step, which existed
  to stop a pin at whatever height the label admitted; the solve has already put the ankle on
  the ground by then.
- **The first lock of a recording is a warm-up and must not be the one measured.** The rig
  starts from `ik_reset`, so its first contact settles over ticks no later one spends: 0.026 m
  against 0.010 for the cycles either side. Three cycles are recorded exactly so a settled one
  is available, and the longest run over ALL of them was reporting the cold one.

## As built — Phase 5, the pelvis drop demoted, and the soft clamp refused

`max_pelvis_drop` 0.6098 to **0.31** of a leg, and `ik-drop`, the arm spec 12.5 recorded that
nothing in the tree had.

```
ik drop pelvis moved  0.254200   the cap, exactly
ik drop pelvis cap    0.254200
ik drop reach deficit 0.500000
ik drop reach short   0.245800   the remainder, left short
```

The cap is set from the CONTENT, not from taste: the deepest thing the demo world asks is the
staircase's 0.5 m riser, which leaves the lower foot 0.25 m past reach — 0.305 of this rig's
leg. 0.31 covers that and nothing beyond it, where 0.6098 was double. A first attempt at 0.05
was too tight and said so loudly: `ik-plant` missed by 0.209 m, which is the deficit less the
cap, exactly as designed.

`ik-drop` asserts the deficit EXCEEDS the cap before asserting anything else — without that it
is the arm 12.5 described, where every fixture asks for less than the cap and a wrong cap passes
either way. Its second half is the refusal: past the cap the foot is left short, because the
hips covering the rest is the "T-Rex" posture the method warns against.

It also needed the release switched off, which is worth recording. The release fades a foot
whose ankle sits above its target, and a target half a metre below the floor is
indistinguishable to it from a foot the clip has lifted — so with it on the foot is let go
before the drop can see it, and the case measured a drop of exactly zero.

### The exponential soft clamp is REFUSED, and the reason is arithmetic

The method soft-clamps leg extension rather than hard-limiting it. On this rig that is the
wrong trade and the file already carried the argument, which this spec re-measured:

| soft band | knee bend it costs, permanently |
|---|---|
| 1 per cent | 16.2 degrees |
| 2 per cent | 23.0 degrees |
| 5 per cent | 36.4 degrees |

A soft band has to begin BELOW full extension to smooth anything, and near full extension the
knee angle goes as the SQUARE ROOT of the shortening — so every near-straight leg in the scene
pays. What the softening buys is continuity in the ankle's VELOCITY as a target leaves reach;
the position is already continuous, since `min(want, hi)` is.

**This refusal is about the rig, not about the method.** These numbers are what a bind pose that
is exactly straight costs; on a rig that binds with a bent knee the same band costs a fraction
of it, and the next person should re-measure rather than inherit the conclusion. The note now
sits in `solve_two_bone` beside the clamp it explains.

## As built — Phase 6, the look and the docs

**The plan's third watch line is wrong and is withdrawn.**
`--puppet assets/models/t_pose.fbx` does not stand a real character in gametest: the app
requires the rig to carry clips named idle, walk and run, and the only committed humanoid — a
65-bone Mixamo Beta rig, toe bones and all, 56,716 vertices — carries Mixamo-named stacks. It
logs `has no rig with clips; keeping the box`. The repo has exactly one humanoid locomotion
clip, `strut_walk.fbx`, which cannot fill a three-entry blend space. **The real-character look
stays owed**, and now the reason is specific rather than a shrug.

**What the watch did establish, and it is the finding of the phase.** Driven by a scripted pad:

| the player | `--no-lock` against locking |
|---|---|
| full stick, 10 m/s | **0 px** |
| stick 0.12, ≈ the clip's own stride | **52,244 px** |

At full speed the contact label never fires — the player moves at about ten times the stride its
animation implies — so no lock forms and the two are the same picture. That is the mechanism
behaving correctly: there is no contact to hold. Near the clip's own stride the feature is
plainly live.

So the feature works and the demo cannot show it, and the reason is not in `ik.c`. A game on
this engine has to match travel speed to its clips — stride matching, or root motion — and
neither exists here. That is now the nearest thing to a blocker on the game roadmap, and it is
an animation problem rather than an IK one.

Docs updated: `docs/foot-locking.md` (its closing section is now what shipped and where it
deviates, and the header no longer says nothing is implemented), `docs/verification.md` (the
foot-planting section's verdict, the arm count from twelve to eighteen, and the menu-golden
instability at 48,886 px), `AGENTS.md`'s `ik.c/h` row, `docs/cli-reference.md` (`--no-lock` and
what it does not show), and `docs/game-engine-roadmap.md` (item 6, the IK row and the verdict).

## As built — the review round

`/thermo-nuclear-code-quality-review` and `/simplify`, seven background agents. What they found
was worth more than the phase that preceded it: **two live defects, a dropped instrument that
found a third when written, and eleven false claims in prose this spec had just added.**

### The two live defects

**The unlock test compared a WORLD distance against a MODEL-space threshold.** `leg` is measured
from `global_transforms`; `glm_vec3_distance(toe_world, contact_world)` was not. The partner test
five lines below was model-space on both sides. gametest puts `PLAYER_SCALE 2` on the parent of
the node handed to `ik_set_world`, so a model drift of *d* read as *2d* and the documented 0.45
of a leg was behaving as **0.225** — the hysteresis gap halved in the only app that runs the
feature. No arm could see it: the probe builds its world matrix by translating an identity, so
every arm runs at scale 1 where the bug is invisible by construction. The fix DELETES code — the
held point was already being converted into model space nine lines later, so the test moves there
and the outward transform goes.

**`ik_set_world` sat behind a weight-0 early return, and the weight never reached zero.**
`ik_update_targets` snapped its local `ik_weight` to 0 and returned *before* calling
`ik_foot_set_ground`, so `IkFoot.weight` stayed a hair above `1e-3` forever and the solver's
documented "weight 0 is bit-identical to no IK" path never fired. 12.9 then leaned on exactly
that: `ik_lock_update` gates on `weight <= 0`, and its comment claimed this kept a lock out of the
frames before a caller had established where the rig stands. For the only caller those are
precisely the frames where the weight is not zero. Airborne on a hop, the ray keeps hitting, the
world matrix and the target both freeze at the last grounded frame, and a lock can pin in mid-air
through a stale matrix — released one frame after landing, with the leg reaching for where the
character used to be. Zero is now handed over rather than returned on.

### The instrument that was planned, dropped, and then found something

The plan booked a Phase 4 arm — "bounded acceleration across a transition — a number, not a
look". Five arms shipped and that was not one of them, with no recorded refusal. Two agents named
it independently. Written afterwards as **`ik-settle`**, it immediately failed:

```
ik lock hold slide 0.010256      the total drift
ik lock hold step  0.010256      the largest SINGLE TICK of it
```

The entire residual was one tick. The held target was derived through the **pre-solve**
ankle-to-toe vector, and the solve then rotates the foot, so the toe landed off the contact by
that vector times the rotation about to be applied — once, on the frame after every pin. Carrying
the vector the last SOLVE left instead:

| | slide | largest tick |
|---|---|---|
| before | 0.010256 | 0.010256 |
| after | **0.003416** | **0.003093** |

**Planting 0.0783 m against locking 0.0034 m over the same ticks — a 96 per cent reduction**, from
a bar of 1 per cent of a leg with 2.4x of headroom. `ik-slide`'s bar tightened from 2 per cent to
1 accordingly.

A note on the arm itself: its first formulation asserted the drift was "spread across the hold
rather than spent in one tick", which is exactly backwards — the better the lock, the smaller the
total, and the more of what remains is necessarily its own largest tick. It would have failed the
fix that motivated it. The bar is absolute and against planting instead.

### Structure

`locked` + `contact_pending` became `IkLockState` (OFF / PINNING / HELD), deleting a field, an
impossible fourth state and a dead reset line. `has_want_prev` was provably always equal to
`has_clip_prev` and is gone; `clip_ankle_prev` was a `vec3` with two dead components and is now
`prev_ankle_y`, which STATES that the label has no horizontal term. The leg length was being
derived twice from the same unmodified globals a hundred lines apart and is settled once on
`IkFoot`. The blend bookkeeping left `ik_solve`'s loop for `ik_advance_applied`, so the loop reads
as five named steps. `below_ankle` became an index list with a zero-count early out, which is what
makes the feature free on every rig without toes, and `rotate_below` now calls the shared
`skeleton_rotate_global` rather than restating its body. `solve_two_bone` lost a parameter that
existed only to bound a mask sweep.

The inertialization's velocity term was differenced from `want`, which changes identity at a
release — so the captured velocity was the jump over one tick, the cap bound every time at exactly
`transition_time / dt`, and the blend degenerated into a fixed reshaping of the position curve
carrying no measured velocity at all. It now differences the CALLER's target, which is written
every frame whatever the lock is doing.

Three invariants that were load-bearing and unstated now sit at their declarations:
`contact_height` must stay tighter than `plant_fraction` (the whole argument for an unfaded locked
weight), `teleport_distance` is the one field in metres and why, and an inverted
`lock_distance`/`unlock_distance` pair is refused by name on the first solve.

### What was refused

- **cglm's `glm_hermite`** for the hand-written basis: it associates the polynomial differently,
  so it is not byte-identical and would move `%.6f` gate rows and possibly a golden. Five lines of
  tidiness is not worth a re-bake.
- **Folding the two chain rotations into one group rotation about a composed pivot.** It is
  algebraically exact and would seal the class of bug this spec fixed — but it is different
  arithmetic, so it costs a golden re-bake to save two multiplies. Booked, not done.
- **Deleting the velocity term entirely** rather than fixing what it differences. The method is
  explicit that velocity continuity is the point; fixing the source keeps it and costs nothing.

### Eleven false claims, in prose this spec had just written

Counted mechanically: the `ik` group went from **13** arms to **19**, not twelve to eighteen.
"Eighteen times the stride" was Phase 0's retired 0.568 m/s reference; against the clip-only
0.952 it is about ten, and one doc had it right while four had it wrong. `docs/verification.md`
still said in terms that locking was not implemented and listed "the four specific things
missing". Two comments in `ik.c` said the contact label was judged at the TOE, nine lines above
the paragraph explaining why it is the ankle — the phase's headline finding, contradicted in the
file that implements it. `lock_distance = 0.15` was described as "a fifth of a leg". The puppet is
22 bones and six places still said twenty.

**And the t_pose diagnosis was wrong.** `--puppet assets/models/t_pose.fbx` does not fail at the
clip names: `take_puppet_root` requires a node named exactly `puppet`, so the load is refused
before a clip is read. The user reproduced this independently and got the red box. `--puppet` is
far less general than its name — it swaps one generated rig for another.

### Making it demonstrable

The review established that the demo could not show the feature; the fix is `--speed <m/s>`,
plus the reason it did not work on its own. The locomotion knob was `ground_speed / player_speed`
— normalised against the CAP, so full stick reads 1.0 and plays the run clip at any speed. It now
divides by `PLAYER_SPEED`, the blend space's own reference, so capping travel actually selects a
lower gear. `--speed 1.2` against `--speed 1.2 --no-lock` measures **22,643 px** apart.

What is still not demonstrable during locomotion, and is the honest limit: `gait()` swings thighs
about a straight leg, so gametest's own walk clip has no stance phase for a lock to hold. The
probe plays the committed `strut_walk.fbx` for exactly that reason. Giving the generated clips a
real stance is the next thing this demo wants.
