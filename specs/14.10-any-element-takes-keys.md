# 14.10: any element takes keys

## Context

pcb's spec 6.2 adds a schematic view to pcb's window: a pane that is not a code editor, which pcb
draws into with cetra's 2D canvas (`ui_set_draw` on a plain element, the canvas under it). Its keys
are vim-like and its own: `h j k l` pan, `+` and `-` zoom, `o` the overview, `r` turns the
selection, `=` gives it back to pcb's layout. Every pane kind pcb adds after it needs the same:
the board layout (step 7), the 3D view (step 8), the datasheets and the parts (step 10). None is a
text field or a code editor.

cetra's UI sends keys to two kinds of element only, and keeps the focus under a passing pointer for
those two only:
- `_ops` (`ui.c:563-569`) gives a widget table to a text field and to the code editor, and to
  nothing else; `_takes_keys` (`ui.c:571-575`) is whether an element has one: "a text field and an
  editor do, everything else leaves them to the screen and the app."
- `_route_keys` (`ui.c:2140`) hands each key and character to the focused element only when it
  takes keys. With anything else focused, every key goes to the screen: Tab moves the focus in tree
  order, Esc lets go, and Page Up, Page Down, Home and End scroll.
- The focus follows a moving pointer unless the focused element takes keys (`ui.c:2255-2258`): "A
  text field holding the focus keeps it as the pointer passes over other things". A schematic pane
  focused would lose the focus to a code pane the pointer crosses.
- `_takes_keys` also decides two things about the pointer, which are the widget table's: whether a
  press and a drag call the widget's own `press` and `drag` (`ui.c:2269-2276`), and whether a
  release activates the element (`ui.c:2300-2302`, since a field's action is its submit).
- The one key hook an app can set is a field's, `ui_field_set_on_key` (`ui.h:605`,
  `ui_field.c:472`), "a key the focused field sees before it acts on it; true takes it". It lives on
  the field's own state (`UIField.on_key`, `ui_field.c:75`), so a plain element cannot carry it. It
  sees keys only: the field types a character before it would ask (`_take_key`,
  `ui_field.c:744-755`).
- A press lands only on a focusable element (`_hit`, `ui.c:1820-1824`), and a panel is not one
  (`ui.c:373`): a press on a pane drawn in a panel is a press on nothing, which lets go of the focus
  on a screen that is not modal.

pcb could catch its keys itself before `ui_update` and put the focus back each frame. That is a
workaround every app with such a pane would write again, and the one pcb's 6.1.2 is removing
elsewhere. So the hook becomes every element's.

Branch `14.10-any-element-takes-keys`, on 14.9.

## The design

- **`ui_set_on_key(el, fn, user)`**, the `UIKeyFn` that exists now (`bool (*)(UIElement* el, const
  InputKeyEvent* key, void* user)`, true takes it), on any element. It lives on `UIElement`
  (`on_key`, `on_key_user`, by function), and NULL unsets it.
- **A hook sees every key and every character before the element acts, whatever the element.**
  `_route_keys` calls it, in one place, before the widget's own `key`; the field no longer knows a
  hook exists. A character must be seen because a pane's keys are characters on any layout: `+` is
  Shift and `=` on a US keyboard and a key of its own on a German one, so a hook matching keys alone
  would have to know every layout. The vim mode reads `$` and `%` from characters for the same
  reason.
- **A plain element with a hook takes keys.** `_takes_keys` is true for an element with a widget
  table or a hook, so while it holds the focus it is handed each key and character in turn. What
  its hook does not take goes to the screen as now: Tab moves the focus, Esc lets go, the page keys
  scroll. A key it takes takes the character that key makes with it (`_route_keys`' rule), so a
  `+` taken as a key types no `+` anywhere. A pane that should keep the focus through Esc takes it,
  as the vim mode does.
- **The pointer's three sites ask `_ops`, not `_takes_keys`**: the press, the drag and the release.
  They are the widget table's: a hooked panel has no `press` to call, and a hooked button still
  activates on release.
- **A hook does not make an element focusable.** The app writes `focusable = true` (a plain write)
  on a pane it wants a press to focus; one that is not focusable is focused by `ui_set_focus`. Being
  focusable also puts it in Tab's order and the pointer's: moved over it while a button holds the
  focus, it takes the focus, as a field does.
- **It keeps the focus under a passing pointer**, as a field does, because `_takes_keys` is what
  that rule asks. A press on another element still moves the focus.
- **`ui_wants_keyboard`** is true while one holds the focus, as for a field: an app reading keys of
  its own stands down, as the canvas app does for a field.
- **On a text field** the hook is asked about each character before the field types it, so a hook
  can keep a character out of the text. Every field hook today matches one key and declines a
  character, whose key is 0, so none changes. `UIField.on_key` and `key_user` go, and so does
  `_take_key`'s call.
- **On a code editor it is refused by name**: an editor's keys are its modes', and a host binds its
  own keys in a mode layer (`UIEditorMode.layer`). A hook in front of the modes would be a second
  way to bind the same keys.
- **`ui_field_set_on_key` goes.** Its callers move to `ui_set_on_key`: the canvas app's two
  (`canvas_app.c:2297`, `2905`), gametest's text probe (`ui_text_probe.c:1004`), and in pcb, at
  its next bump, `go.c` and `status.c`. `UIKeyFn`'s comment says what it now sees.
- **No pointer hooks.** A pane the app draws reads the pointer from its `UIInput`, as the canvas app
  does; the press that focuses it stays cetra's.

## Tests (no window)

- **`ui-element-keys`** (the `ui` group, gametest's `--ui-probe`):
  - a panel with a hook, focused: it is handed every key and character in order, a typed `+` as
    the key and then the character;
  - a key it does not take reaches the screen: Tab moves the focus on, Esc lets go;
  - a key it takes drops the character that key makes;
  - a press on it, focusable, focuses it and calls no widget code; not focusable, the press lets
    go, and `ui_set_focus` focuses it;
  - a pointer moving over another focusable element leaves the focus on it, and a press there
    moves it;
  - a button with a hook still activates on release;
  - `ui_wants_keyboard` is true while it holds the focus, and false once it lets go;
  - a panel with no hook, focused, behaves as before: its keys go to the screen, and a passing
    pointer takes its focus;
  - a field's hook is asked about a character before the field types it: one taking `/` keeps it
    out of the text, one declining it leaves it typed;
  - a hook on an editor is refused, and the editor's keys are unchanged.
- **The field's arms**, whose fields now take `ui_set_on_key`, pass unchanged.

## As built

### Phase 0

The spec and the roadmap, each committed alone (73e3765f and 1b098eeb), rebased onto 14.9 as
d50c06ab and 468d363c; the roadmap's line moved past the two bullets 14.9 had already replaced. The
spec was then corrected after a review (3835d573): a hook is handed characters on every element,
the pointer's three sites ask the widget table, and the app makes a pane focusable. The task tool
was not available in this session, so the phases stand in for the task list.

### Phase 1: the hook

As designed (d48d15e0), with these differences:
- **`UIKeyFn` moved up beside `UIDrawFn`**, since `UIElement` now holds one, and its comment says
  it is handed characters and that a key taken takes its character with it.
- **The hook is asked inside the widget's `keys_begin` and `keys_end`**, where the field asked its
  own.
- **The case is in the editor's probe** (`probe_element_keys` in `ui_editor_probe.c`), not the
  text probe: it needs an editor beside the panel, and that file has the editor's fixture and the
  one-flag-a-line form `doc_flags` counts. Its arm, `ui-element-keys`, follows
  `ui-editor-paired-char`, the arm for the same rule of a key and its character. It has 15 flags,
  the spec's list with "a press on the field moves the focus" as one of its own.
- **Falsified**: with `_takes_keys` as it was, 5 of the 15 flags fail -- the order the hook is
  handed things, `ui_wants_keyboard`, the focus kept under the pointer, Esc letting go, and the
  keys after `ui_set_focus`. The field's and the button's flags pass without it, since they stand
  on the one call site and the pointer's sites.
- **A hooked button takes the keys too**, so while it holds the focus navigation and `accept` do
  not activate it, as they do not a field; its hook may. No app hooks a button.
- **`--ui-keys`**: the panel takes every character and no key, its label saying the last two
  things it was handed. Its screen is not modal, so Esc lets go rather than closing it, and the UI
  is handed the real input each frame.

cetra builds with no warnings. The `ui`, `canvas` and `gate-docs` groups pass, 120 arms with none
failed or skipped, `ui-element-keys` among them.

**The look**, headless through an input script at 800 by 600, since a click cannot be made in a
window from here: a click on the panel, `h` and `+`, the pointer swept down across the field under
it, `o`, Tab, `x`. The label says `char h` and `char +`, then `char o` and `key 258 mods 0`: the
`o` typed after the pointer crossed the field reached the panel, and the Tab its hook declined
moved the focus to the field, which holds only the `x`.
