# Spec 13.39: loading without a freeze

## Context

Silent's loading screen (spec 13.34) stops animating for long stretches while the game loads. The
screen can only draw between steps (`load_seam` in `apps/silent/src/silent.c`, between materials
in `mats.c`, between capture units, and after each shader variant compile), so any single step
that runs long on the main thread freezes it.

A sampled headless run of the debug build found the stalls are mostly CPU work, and some of it is
work that need not happen at all:

| Stall | Time | Cause |
|---|---|---|
| Sampler counting, every program | 1,470 ms in all | `_count_program_samplers` (`cetra/src/program.c:455`) calls `glGetActiveUniform` once per active uniform, and Apple's driver walks every uniform-block member. That costs more than compile (500 ms) and link (460 ms) together. |
| Cat route check | 919 ms | `cat_places_check` ray-casts the cat's 86 links against an unoptimised Jolt broadphase. `physics_world_optimize` runs later, at `silent.c:893`. |
| Texture loading | 977 ms | `mats_register` loads synchronously; PNG decode is 520 ms of it. |
| Sound decoding | 705 ms | FLAC decode inside `ma_sound_init_from_file` (`audio.c:380`), two ~280 ms blocks. |
| Engine creation | 1.2 s | The window is shown at `engine.c:602`, then default programs and the post chain build with nothing drawn. |
| Other steps | 130-190 ms each | `kit_finish`, `woods`, `land-terrace`, `doors-prompt`. |

Intended outcome: the screen animates through loading with no stall over about 150 ms, except a
single shader compile, and init plus the first frames drops from about 6.5 s to about 3-3.5 s.

Pixels, sounds and gate results stay the same. Nothing is dropped: the cat check keeps running on
every launch.

Out of scope: the GI and probe captures, which are most of the total wait. They are paced at
100 ms a frame in a window, and need a spec of their own.

### Phase 0 as built

- **The query is public, not internal**: `engine_loading_screen_longest_wait` in
  `loading_screen.h`. An app cannot name `engine_internal.h`, and how long the screen stood
  still is a fair thing for any app with one to ask.
  - It counts a CHANCE to draw, drawn or not: `engine_draw_loading_screen`, the ticks between a
    long frame's pieces, and a frame.
  - Asking starts the count again.
  - Headless, `_loading_present` returns before drawing, so the chance is counted before that
    return. That makes a headless number what a window would freeze for.
- **Silent's `--startup-ms`**:
  - every row gains `still=`, the longest stand-still since the row before;
  - the `up` row gains `still-worst=` and `after=`.
- **The baseline command** is `-x -f 600 --mute --startup-ms --loading-screen
  --capture-budget-ms 100`. `--loading-screen` keeps the screen up headless, and
  `--capture-budget-ms 100` paces the captures as a window does during loading

## Phase 1: sampler counting (engine, internal)

- `_count_program_samplers`: one `glGetActiveUniformsiv(..., GL_UNIFORM_BLOCK_INDEX, ...)` over
  all active uniforms. Then `GL_UNIFORM_TYPE` and `GL_UNIFORM_SIZE` only for those with index -1.
  GLSL 4.10 forbids samplers in interface blocks, so block members can never be samplers.
- During development only, compute both the old and new counts for every program and log any
  disagreement. Remove that before committing.
- **Measure** engine creation and frame1 with `--startup-ms`.
- If the batched call is not markedly cheaper on Apple's driver, fall back: count only in
  `_create_pbr_variant`. That is the one reader, through the log line `program.c:706` parsed at
  `gates.py:23866`. Update the comments at `program.h:75-84` and `program.c:514`.
- Gates: `--only pbr-variant rain` (the `pbr-variant-samplers`, `rain-ledger` and
  `rain-relief-*` arms read the count).

### Phase 1 as built

**The batched call the plan named did not help.** `glGetActiveUniformsiv(GL_UNIFORM_BLOCK_INDEX)`
over every uniform still cost 1,212 ms of the 1,470.
- A sample showed why: `ShGetActiveUniformIndex` → `getBindingInfo`. Apple's driver finds a
  uniform BY INDEX by walking the whole uniform tree, whichever call asks and however many indices
  it is handed.
- So any question put per index over the block members costs the same.

**What shipped asks the BLOCKS instead.**
- `GL_UNIFORM_BLOCK_ACTIVE_UNIFORM_INDICES` gives each block's members.
- The uniforms in no block are the rest.
- Only those have `GL_UNIFORM_TYPE` and `GL_UNIFORM_SIZE` asked, in two batched calls.

**Results:**
- `_count_program_samplers` went from 1,470 ms to 25 in the sample, and program building from
  2,233 to 993.
- On allocation failure the count is -1, which the header already allows.

**Checked:**
- During development, the old one-by-one count was kept beside each version and compared on every
  program silent builds. There were 0 disagreements for both versions, and the eight lit-surface
  variants keep their counts: 16, 16, 13, 15, 13, 13, 14, 13. The cross-check is gone from the
  committed code.

**Timing**, two runs, against the baseline:

| Row | Baseline ms / still | Now ms / still |
|---|---|---|
| frame1 | 1,818-1,821 / 598-602 | 973-988 / 456-468 |
| cat | 1,369-1,371 | 1,231-1,256 (its skinned variant) |

Engine creation, before init, gains as well. `--startup-ms` does not see it, but the sample does.

**Gates:** `--only pbr-variant,rain` passes all of its 5 groups, including the arms that read the

## Phase 3: sounds on miniaudio's job thread (engine API + silent)

**`cetra/src/game/audio.c/h`:**
- Add `audio_sound_from_file_async`. It is `audio_sound_from_file` with
  `MA_SOUND_FLAG_ASYNC` and the system's `ma_fence` as `pDoneFence`. The fence is set up in
  `create_audio_system`.
- Add `audio_system_loading(audio)`, non-blocking: whether any async load is still decoding.
- Add `audio_system_wait_loaded(audio)`: `ma_fence_wait`, then start the device.
- The device is held (`ma_engine_stop`) from the first async load until then, so nothing mixes a
  half-decoded buffer.
- `audio_sound_from_file` stays synchronous; gametest's audio probe reads PCM straight after it.

**Silent:** `sounds_loop`, `clock.c`, `basement.c`, `lights.c`, `tv.c` and `cat_voice.c` load
through the async call. The voice prototypes are copied only after the wait.

**At the end of `on_init`:** draw the screen while `audio_system_loading`, then
`audio_system_wait_loaded`. That is before the first frame, so headless offline audio is
unchanged.

**Verify:**
- `--audio-dump` before and after is byte-identical.
- `--only audio`.

### Phase 3 as built

**Engine, `cetra/src/game/audio.c/h`:**
- `audio_sound_from_file_async`: the same load with `MA_SOUND_FLAG_ASYNC` and the system's
  `ma_fence` as its done fence. The fence is made and freed with the system.
- The first async load stops the device (`ma_engine_stop`). There is no device headless, so
  nothing to stop.
- `audio_system_loading`: whether any async sound still reads `MA_BUSY` from its data source.
  miniaudio holds a data buffer's result at `MA_BUSY` until its whole file is decoded, and only
  then releases the fence.
- `audio_system_wait_loaded`: waits on the fence, then starts the device again.
- `audio_sound_from_file` is unchanged, and synchronous.

**Silent:**
- All five loaders go through the async load: `sounds_loop`, `clock.c`, `basement.c`, `lights.c`
  and `cat_voice.c`.
  - Every one of them runs during init, so no load after the wait can stop the device again.
  - The voice prototypes (the drip, the cat's sounds) are copied only when played.
- `on_init` ends with the screen drawn while `audio_system_loading`, then the wait, as a new
  `audio-loaded` row.

**Checked:**
- `--audio-dump` over 400 frames is byte-identical to the build before. The reference was itself
  byte-identical across two runs.
- `--only audio`: all 10 arms pass.

**Timing:** the audio rows fell from 610 + 68 + 33 + 67 ms to 1.7 + 4.1 + 0.9 + 0.6.
`audio-loaded` takes 729 ms with `still=0`: the screen moves throughout. The worst stand-still is
now frame1's 433 ms.

**What it does not save yet: total time.** The sounds are asked for near the end of init, after
the doors, the lights, the television and the cat they belong to. Little main-thread work is left
to overlap the decode, so the wait is about as long as the decode was. Hiding it means starting
the loads earlier. The two wind beds are 4.2 of the 6.1 MB, but `sounds_start` needs the hung
doors for its zone links. That is a reordering of silent's init, and is left as a follow-up rather
than done here.

## Phase 4: textures on the loader's threads (engine API + silent)

**Engine:** two public calls over the internal `cetra/src/async_loader.c` (pattern:
`AsyncTexCallback` in `import.c:671-689`):
- A request: path, `TextureDesc`, and a material setter or callback. It decodes on the pool and
  publishes on the main thread through the same `texture_pool_publish`, so the pixels, mips,
  compression and cook are identical.
- A wait: it calls `async_loader_process_pending` in small batches and
  `engine_draw_loading_screen` until the loader is idle. It backs off when nothing was processed.
  It replaces gametest's hand-rolled spin (`gametest.c:2498`).

**Silent `mats.c`:**
- `load()` requests instead of loading.
- The stained-glass `emissive_tex = albedo_tex` (`mats.c:606`) moves into the albedo callback.

**Wait** just before `kit_free_unused` (`silent.c:756`):
- Decoding overlaps building the house and street, and nothing in between reads texture
  contents.
- Callbacks must never write into a freed material.

**Check** that nothing calls `set_texture_pool_directory` while decodes are in flight.

Only the decode moves; mips, compression and the cook stay on the main thread (the cook is
main-thread-only by charter). Moving those is a later step, only if measurement says it is worth
it.

**Verify:** silent's 23 views at 0 px against master.

### Phase 4 as built

**Engine (`engine.h`, `engine.c`):**
- `engine_load_material_texture(engine, pool, material, set, path, desc)` queues a decode on the
  async loader. `set` receives the texture once it is in the pool, and is not called for a file
  that cannot be loaded.
- `engine_finish_texture_loads(engine, pool)` uploads one texture at a time, drawing the screen
  between uploads, until the loader is idle. It sleeps 1 ms when nothing came in.

**Engine (`async_loader.c`): a fix found on the way.** `load_texture_async` now resolves a file
the way `texture_load_file` does, and answers from the pool when the file is already in it.
- The pool keys a file by its RESOLVED path, but the submit checked only the request.
- So a file request never hit the pool, and every repeat request decoded the image again. Its
  setter then landed in a later frame's uploads.
- Silent registers materials four times (the world's kit, the clock's, the doors' and the
  basement's). Two of those registrations come after the textures are in. Without the fix each
  would have decoded every texture again and waited for it.

**Silent `mats.c`:**
- `load()` requests through `engine_load_material_texture` with the material's own setter.
- `mats_register` waits with `engine_finish_texture_loads` before it returns.
- The stained glass's emissive is set from its albedo after the wait.

**The wait is NOT before `kit_free_unused`, as the plan said.**
- `kit_finish` frees a material its kit did not use, at once, for a kit that shares none: the
  clock's, the doors', the basement's.
- The clock's kit registers and finishes before the world's would have waited. Its unused
  materials would have been freed with their loads still on the way, and the callbacks would
  then write into freed memory.
- Waiting inside `mats_register` makes that impossible for every caller.
- What it gives up is overlapping the uploads with the house's build. That was always the small
  part: the win is the DECODE spreading over the loader's workers, and the uploads stay on this
  thread whichever way it is done.

**`gametest`'s `drain_async_loader`** keeps its comment and is now one call to
`engine_finish_texture_loads`.

**Timing:** `materials` went from 950-1,640 ms (still 300-500) to 404 ms (still 66). The
registrations after it hit the pool: `clock-hill` takes 5.5 ms, `doors-prompt` is unchanged at
143, and `audio-basement-lights` takes 1.3. A registration that decoded again would take hundreds
of milliseconds.

**Pixels:** silent's 23 views (`ab_views_silent.txt` plus the two clear overviews) are 0 px
against master's binary, every one. The binary carries phases 1-4 together.

**Gates:** `--only ik,graph,ragdoll`, the groups whose gametest runs import a `--puppet` through
