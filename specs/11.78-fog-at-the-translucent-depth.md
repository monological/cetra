# Spec 11.78 — fog at the translucent depth

## Context

`docs/aaa-rendering-roadmap.md:3046` records an unbooked limitation: fog and aerial
perspective land on a translucent pixel at the depth of the wall BEHIND it. The atmosphere
composite reads one linear-Z per pixel (`froxel_composite_frag.glsl:52`, from the aux
G-buffer), and the late pass writes no aux — `render.c:1342` drops `glDrawBuffers` to
count 1 when the opaque scope closes, and nothing re-arms it. A smoke card 2 m from the eye
in front of a wall at 40 m receives 40 m of fog.

Water already solves this exact bug for itself by writing aux (`water_frag.glsl:1233`), and
its comment says so in as many words. Translucent stacks cannot take that route: aux is
single-layer, so writing the glass would un-fog the wall.

**The fix:** decompose the pixel in the atmosphere composite using the MBOIT moments — which
already store, per pixel, the translucent stack's total absorbance `b0` and its
absorbance-weighted mean warped depth `b1/b0` — and fog the translucent contribution at its
own depth, the background at the aux depth. All work happens in the post chain, where there
is no sampler-ledger pressure.

### Why not the in-shader route (investigated first, rejected on three verified facts)

1. `froxel_composite_frag.glsl:20-21` samples **two** `sampler3D` volumes (fog + aerial),
   separately owned, differently parameterised, non-mergeable without a resample pre-pass.
   `pbr_frag` is at 16/16 declarations and no tenancy escape applies to a 3D type. D0's only
   viable candidate (irradiance→atlas fold) frees ONE unit and is itself blocked on
   ownership: 11.70 made unit 14 a two-tenant texture owned by *opt-in* subsystems, and
   always-present IBL is exclusive with neither — a three-way arbitration concept, not a
   sampler swap. D0's own 0-px gate "cannot pass" per its correction 3.
2. **Both volumes are built AFTER the scene pass** (`engine.c:2674` `render()`, then `:2686`
   `engine_present_frame` → `sky_update_aerial` at `:1810` and `postfx_build_fog_volume` at
   `postfx.c:2755`). An in-shader read samples frame N−1, undefined on frame 0.
3. The composite applies `pixel × T + S` to the already-blended pixel (`GL_ONE, GL_SRC_ALPHA`,
   `postfx.c:2823`), so in-shader-fogged glass would be fogged again at the wall's depth —
   correct compositing needs the same moments decomposition this plan uses anyway. The
   in-shader route strictly contains this one.

## Mechanism

`froxel_composite_frag.glsl` currently outputs one `(S, T)` pair per pixel
(`FragColor = vec4(fogLayer.rgb + aerialLayer.rgb * preExposure * fogLayer.a,
fogLayer.a * aerialLayer.a)`, line 89) and the caller's blend applies it. The change:
evaluate that same fold at TWO depths and blend the pairs by translucent coverage.

```glsl
// existing: (S,T) at zOpaque from linDepthTex .z          — unchanged arithmetic
// new:      (S,T) at zTrans, where
//   b0   = texture(momentTex, uvAtlas + vec2(0.0, 0.5)).r  // upper half of atlas
//   b1   = texture(momentTex, uvAtlas).r                    // lower half, .r = b1
//   zW   = b1 / b0                                          // mean warped depth
//   zTrans = oitNearFar.x * pow(oitNearFar.y / oitNearFar.x, (zW + 1.0) * 0.5)
//   cover  = 1.0 - exp(-b0)                                 // == 1 - stack transmittance
// out    = mix(pairOpaque, pairTrans, cover)
```

Key facts, all verified against the code before writing this:

- The moment atlas (`engine->moment_atlas_texture`, `engine.c:2139-2151`) is render-res width
  × **2× height**, RGBA32F, NEAREST: b1..b4 lower half, b0 upper at `+vec2(0, 0.5)`
  (`mboit.glsl:131-135`, `MBOIT_ATLAS_B0_TAP`). Engine-owned, resolved during the scene pass
  by `engine_end_moment_pass`, persists — valid at post time.
- `b0` alone yields both coverage and depth; **no revealage read needed**. One new
  `sampler2D` in a post program that declares four. Zero ledger pressure.
- The warp interval is the camera's near/far (`render.c:500-502` uploads
  `{camera->near_clip, camera->far_clip}` as `oitNearFar`); the unwarp inverts
  `mboitWarpDepth` (`mboit.glsl:31-35`).
- `cover == 0` ⇒ `mix(a, b, 0) == a` exactly ⇒ **bit-identical to today wherever no
  translucent drew** (b0 is 0 there). Gated off entirely (`momentArmed == 0`) the shader takes
  today's expression verbatim.
- `mboitWarpDepth` clamps `viewZ` below `nearFar.x`, so `zW ∈ [-1,1]` and the unwarp is
  bounded; guard `b0 < ~1e-5` to avoid 0/0.

## Changes

**`cetra/shaders/froxel_composite_frag.glsl`** — add `uniform sampler2D momentTex`,
`uniform vec2 oitNearFar`, `uniform int momentArmed`; factor the existing two
`froxelSampleMedium` calls + fold into a small function of `viewZ`, call at `-linZ` (as today)
and at `zTrans`, mix by `cover`. When `momentArmed == 0`, single call — today's path, same
expression order.

**`cetra/src/postfx.h`** — `PostFXGBufferWrites` (at `:737`, already carries `oit_fbo` and
`oit_moment_weighted`) gains `GLuint oit_moment_atlas;` (0 = not this frame) and
`float oit_near, oit_far;`. The struct's comment already frames it as "the engine's
frame-start decisions, passed through rather than re-derived" — this is more of exactly that.
Passed through rather than re-derived from `projection` because `camera.near_clip` is
recomputed per frame by render.c (the config-snapshot lesson).

**`cetra/src/engine.c:1830`** — fill the new fields at the `postfx_run` call site:
`engine->moments_this_frame ? engine->moment_atlas_texture : 0`, camera near/far.

**`tools/gen_fog_glass_fixture.py` + `assets/fog_glass_fixture.cscn/.gltf`** — the instrument

**Docs** — rewrite the roadmap `:3046` paragraph against what was verified here: the stale

from the wall; only the surface term is misfogged), particles (own pass, no moments), and the
`--no-oit` / `--no-oit-moments` paths (keep today's behaviour, gated). AGENTS.md gets the same

## As built

Shipped as planned in mechanism. Four corrections to the plan above, and one finding that
belongs to a different subsystem.

**The fixture's central instrument had to be redesigned.** The plan called for a blend pane
at alpha 1.0 — a byte-identical twin of the opaque pane differing only in `alphaMode` — as
the thing that isolates the defect. It cannot be used. `mboitAbsorbance` maps alpha 1.0 to
`-log(1e-4)` = 9.21, and the moment reconstruction charges a lone layer part of its own
absorbance, so the pane renders at about a FIFTH of its correct value: **38.9 against the
180.2 it owes, and exactly 180.20 under `--no-oit-moments`.** A twin there would have
measured the reconstruction, not the fog. The sweep is alpha 0.5 and 0.25 instead, which
works because equal radiance makes a blend pane's composite `a*E + (1-a)*E = E` at ANY
alpha — so coverage is free to be the variable.

**That is a real accuracy defect in a default-on path and it is NOT this spec's.** At alpha
0.5 the loss is 4.4%; at 1.0 it is 78%. Any near-opaque ALPHA_BLEND surface — a window pane,
a painted panel — renders far too dark under the shipping default. Recorded in the fixture,
not chased here.

**Every read is a RATIO of fog to no-fog**, which the plan did not say and which is
load-bearing: that 4.4% is present in both renders and divides out, leaving the fog.

**The plan put the generator in `tools/`.** Fixture generators live in `assets/`.

**And the fixture was first laid out at aspect 1.6 when the suite renders 400x300**, so its
outer panes fell off a 4:3 frame. Refitted; the asserts now derive the frustum from the
gate's own aspect.

### Measured

Fog-over-no-fog luma ratio per pane, at the shipping fixture and gate flags:

| | before | after |
|---|---|---|
| opaque pane (near, the truth) | 0.9309 | 0.9309 |
| backdrop gaps (far) | unchanged | unchanged |
| blend pane a=0.5 | 0.6640 | 0.8195 |
| blend pane a=0.25 | 0.6632 | 0.7519 |

The reading that matters is the coverage response: the two mirrored sweep panes differed by
**0.0008** and now differ by **0.0676**, against **0.0677** predicted from the near-vs-far
advantage. Coverage reached the composite nowhere at all before.

Two runs of one build diff **0 px** on this fixture. **All 27 goldens 0 px, no rebake** —
including `froxel_fog`, the aerial trio and `water_submerged`, which recompile the changed
shader and showed no codegen movement.

### Falsification

Four mutations, run by hand:

| mutation | result |
|---|---|
| `cover = 0.0` (the pre-fix state) | `fogdepth-coverage` 0.0031 vs 0.040 floor, `fogdepth-lift` 0.0055 vs 0.080 — both FAIL |
| `cover = 1.0` (fog everything near) | `fogdepth-lift` FAILS on its **ceiling**, under-near −0.0060, where its floor reads 0.4587 and would have passed |
| aux texture bound on the moment unit | both behaviour arms FAIL — a static frame's motion vectors are 0, so `b0` reads 0 and the pane never gets its fix |
| the `b0 > 1e-5` guard deleted | **nothing moves.** `cover` is 0 there, so `mix()` returns the surface answer whatever its other argument holds |

The third arm caught none of the four. It was rebuilt as `fogdepth-offpath` and is documented
as a **property statement rather than a discriminator** — its fallback half cannot be broken
from the shader either, because with no atlas generated there is no `b0` to arm from. It is
worth having the day someone gives the weighted-blended path a depth statistic.

**The guard stays despite being inert**: `b1/b0` is 0/0 on those pixels, which GLSL leaves
undefined, and `mix(a, NaN, 0.0)` is NaN wherever the hardware propagates `0 * NaN`. A guard
against undefined behaviour, not against a wrong number — and the shader now says so, since
the next reader will otherwise measure it and delete it.

## The review round

Three independent audits. What they changed, and one thing they disagreed about.

**The `mboit.glsl` contract was broken and the file's header proved it.** That file exists so
"the atlas layout has one home", and said "only pbr_frag includes it today". The composite
included it and then open-coded the half-height fold, the inverse of `mboitWarpDepth` and the
inverse of `mboitAbsorbance`. `MBOIT_ATLAS_B0_TAP` was exported and the `0.5` beside it was
not — so a side-by-side atlas would have moved one reader and left the other reading garbage,
with grep finding only the safe half. Now `mboitAtlasUV`, `mboitUnwarpDepth`,
`mboitStackAtlas` and `mboitStackOpacity` live beside the forwards, and
`mboitTransmittanceAtlas` goes through the same fold — it takes the reciprocal FRAME size,
so the halving is stated once. `oit_sphere_moments` 0 px across that change.

**`cover` was named for coverage and is opacity.** Equal to coverage only where a layer
covers a pixel whole; at MSAA the atlas resolve makes `b0` a mean over samples, so it is not
the mean of the per-sample opacities. Renamed and documented.

**The two audits disagreed about `oit_near`/`oit_far`, and the disagreement was the useful
part.** Both found the header comment false — it claimed `near_clip` drifts from the
projection, when `render.c:2067-2069` assigns it and rebuilds the projection in the same
block. One concluded the fields should be deleted and both planes reconstructed, as the
shader already does for the near. The other said keep them, because the FAR plane does not
survive that inversion. Measured, and the second is right: `P[2][2]` is `-(f+n)/(f-n)`, so
recovering `f` divides by a residual that cancels to nothing at a wide range — **1.3% error
at 0.02→10k, 11.9% at 0.01→50k**. The fields stay, folded to one array, with the real reason
written down.

**The gate transcribed geometry that lives in the generator.** Nine crop boxes and an
adjacency table, hand-derived from pane positions and the frustum. Falsified: moving
`PANE_X` inner from 1.05 to 1.20 passes all seven of the generator's assert groups and slides
the half pane's edge from 0.311 to 0.294, under a gap box ending at 0.295 — the backdrop
reference would have sampled the pane beside it and the arm would still have printed PASS.
The margin was 0.016 of frame width, about 6 px. Boxes now project from the generator's own
numbers through `_projector(_cscn_camera(...))`, and the same mutation moves the reads with
the geometry (coverage 0.1103 → 0.1103). The generator gained a `__main__` guard so the gate
can import it, which also retired a two-place `FOG_DENSITY` whose comment on both sides
claimed to be one-place.

**`fogdepth-offpath`'s honesty note named the wrong half as the survivor.** Its identity half
is what underwrites the goldens claim — the only assertion anywhere that the `b0` gate leaves
a translucency-free fog frame exactly as it was. It survived the four mutations because none
touched that gate, not because nothing can.

Also applied: `_mask_box_luma` → `_box_luma` with the third local copy of `luma()` deleted;
a null check on a pointer `postfx_run` dereferences before it checks `fx`; a verification
claim in the shader; a header comment naming its caller; a GLSL comment narrating
`render.c`'s draw-buffer mechanism; and `mediumAt` taking an aerial slice count rather than
an `isSky` flag, so a function about media stops explaining the sky-view LUT.

**`oit_moment_weighted` is gone, and the reason it nearly survived is worth recording.** The
audit found it provably equivalent to `oit_moment_atlas != 0`, and the first response here was
to defer it as "changing the OIT composite's blend selection, a default-on path outside the
blast radius". **That was wrong** — both fields were set in one initializer from one bool, so
passing the atlas test computes the identical value and selects the identical blend. Nothing
about it was outside anything. It was caution phrased as a reason, which is the same failure
mode as a coverage claim nobody checked.

Verified before removing: `moments_this_frame` is only ever assigned `moments_ready`
(`render.c:1559`), which requires `engine_begin_moment_pass` to have returned true, and that
function's failure path zeroes `moment_atlas_texture` before returning false. So a true flag
implies a live atlas by construction. Goldens 0 px, and `oit`, `catcher-transparency` and
`draw-list` read identical to the digit.

The field's contract moves onto the handle rather than being lost: non-zero says both *the
accumulation is in moment-weighted form* and *here is the atlas*. One field because a frame
cannot have one without the other, and because two could disagree — which would mis-composite
every translucent pixel while looking like a flag someone forgot to set. That is the argument
`postfx.c`'s slice-count comment already makes eight lines from this code: one state per
medium, not a count plus a flag that can contradict it.
