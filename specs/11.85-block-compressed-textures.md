# Spec 11.85 — F1, block-compressed textures

## Context

Every texture in this engine sits in GPU memory **raw**, 4 bytes per texel, and no document
said so until Track F was written (commit `bd3cbf8c`). The PNG/JPEG on disk is irrelevant —
that is file compression, expanded to full size at load. Measured, live, every frame:

- **`raiden`**: 20 textures, 23.9M texels → **~127 MB** (with mips)
- **`apps/forest`**: material array **117.3 MB** at 11 layers of 2048x1024, page pair **42.7 MB**

Block compression stores each 4x4 tile as 8 or 16 bytes and the GPU's texture hardware decodes
it in silicon as it samples. It never expands in memory: 4-8x smaller permanently, and slightly
faster, because less bandwidth moves per lookup. It is lossy.

*(The "slightly faster" half was measured after the fact and is **not true on this engine's
content** — see "It is a VRAM win and NOT a speed win" below. Left as written, because it is
the reason anyone reaches for this and the correction is the interesting part.)*

**The obvious plan is wrong and a probe proved it.** BC7 needs GL 4.2; Apple stops at 4.1 and
exposes no extension, so `GL_COMPRESSED_RGBA_BPTC_UNORM` returns `GL_INVALID_ENUM`. RGTC reads
as absent for the opposite reason — core since GL 3.0, so it carries no extension string — and
works. Available and verified: **BC5, BC4, DXT1/DXT5 including the sRGB variants.**

Goal: compress everything that can be compressed, in the order the mechanisms force.

## What makes this one spec and not three

Three different mechanisms, in a forced order:

| piece | why it is its own phase |
|---|---|
| plain 2D textures | pixels already on the CPU; encoder slots straight in |
| the material array | built by RENDERING into it (`material_texture_array.c:266`), and a compressed texture is not color-renderable — needs a per-layer readback |
| splitting the array | colour and non-colour cannot share one internal format; a 2nd array is a 17th sampler and `pbr_frag` is **verified 16/16** — needs D0 |
| colour (DXT) | no mechanism problem, purely a quality call |

**`pbr_frag` is exactly 16/16**: 12 own declarations plus `csm` / `punctual_shadow` / `ltc` /
`gi_volume`. `cloudShadowTex` is `#define`d onto `sceneColorTex` (`pbr_frag.glsl:200`) and costs
nothing. So the array split genuinely requires D0, which frees exactly one unit.

## Phases

1. **Spec alone**, branch `11.85-block-compressed-textures` off master.

2. **CPU mip chain, still uncompressed.** `glGenerateMipmap` cannot fill a compressed chain, so
   mips must be built CPU-side before encoding. Landing this FIRST, uncompressed, isolates "mips
   moved" from "compression moved" — the 11.84 discipline. A 2x2 box halving in
   `texture.c`, ~20 lines, no new dependency (no `stb_image_resize` is vendored and none is
   needed for power-of-two halving). *Expect goldens to move; measure and re-bake deliberately.*

3. **The encoder, inert.** New `cetra/src/texture_compress.c/h`: BC4, BC5, DXT1, DXT5 as pure
   functions over 4x4 blocks, no GL, deterministic. Plus a `TextureFormat` hint following
   `TextureAlpha`'s exact shape and header-comment style (`texture.h:146-160`) — the caller
   STATES the semantic because `texture_gl_formats` only knows `is_srgb`, which is false for
   normals and masks alike. Default preserves today's behaviour, so nothing moves yet.
   Add `--no-texture-compression` (the bisect lever) and a VRAM probe — there is no texture
   memory counter today, and the win is unassertable without one.

4. **Opt in normals + masks on the plain 2D path.** `texture.c:560` (file) and `:637` (memory);
   call sites in `import.c` state the slot semantic. BC5 for normals, BC4 for single-channel
   masks. *First real win — measure raiden's VRAM and the per-format error.*

5. **D0, and it can stop here.** Fold the IBL irradiance cube into the GI atlas on unit 14 as an
   octahedral tile, freeing unit 11. The atlas already has two tenants (GI, probe columns) and
   `giAtlasSize` is already a uniform, which is what made 11.70's tenancy work.
   **D0's own entry sets the bar: the raiden baseline must be 0 px.** It is a pure storage
   change, so anything else means the octahedral resample is lossy where it matters — and then
   this item STOPS with phases 1-4 shipped and the array left single.

6. **The material array.** After the `mask_copy` draws, read each layer back
   (`glGetTexImage`), build its mips and encode CPU-side, upload via
   `glCompressedTexSubImage3D`. Split into two arrays by tenant kind: colour (layer albedo,
   decal albedo) stays RGBA8, non-colour (packed normal/rough/AO, splats, masks) becomes
   BC5/BC4. Touches `material_texture_array.c/h`, `layers.glsl`, `decals_ubo.glsl`, `pbr_frag`.

7. **Colour, as something to LOOK at.** DXT1/DXT5 sRGB on albedo. The only phase with visible
   risk, and the one the earlier answer deliberately excluded — so it ships behind the flag and
   is accepted or dropped on an A/B render, not on a number. Note the array's albedo is stored
   **linear** by design, where RGB565 endpoints are perceptually worse in the dark end than in
   sRGB, so array colour is the last candidate rather than the first.

8. **Goldens re-baked deliberately, full suite, docs closeout** (AGENTS.md texture model, Track F
   F1 as-built, roadmap row 51).

## Files

**New**: `cetra/src/texture_compress.c/h`, `assets/gen_texcomp_fixture.py` + its fixture.
**Core**: `texture.c/h` (mips, hint, compressed upload), `material_texture_array.c/h`,
`import.c` (state the semantic), `ibl.c/h` + `gi_volume.c/h` + `include/gi_volume.glsl` +
`pbr_frag.glsl` (D0's fold).
**Harness**: `apps/render/src/render_args.h` + `render.c` (flag, probe), `scripts/gates.py`.

## Two hazards found while exploring

- **`texture.c:285`** reads a texture's top mip back as `GL_RGBA` (11.49's emissive-light fit)
  and **`layers_vt.c:177`** does the same on the array (the composite cache's per-layer mean).
  GL decompresses on readback so both keep working, but both now read lossy values — the
  derived area-light colour and the cache's macro means shift slightly. Name it, measure it.
- **Unsized internal formats** (`texture.c:185-197` passes `GL_RGB` / `GL_RGBA` / `GL_SRGB`)
  mean the engine does not currently state its own storage — the driver picks. The VRAM probe
  in phase 3 must query `GL_TEXTURE_INTERNAL_FORMAT` rather than assume.

## Verification

- Noise floor first at each arm's framing, per the standing rule.
- `--no-texture-compression` reaches the uncompressed frame **exactly 0 px** — provable, and the
  bisect lever.
- **D0: raiden 0 px, or the item stops at phase 5.**
- Per-format max error against an uncompressed twin, budget STATED beside the constant. **F1 is
  the only item in this roadmap whose 0 px bar is unavailable by construction**, so the error
  budget is the acceptance test.
- **Anti-vacuity**: a normal map encoded as DXT5 (the wrong format) still renders a plausible
  frame, so the normal arm must read the reconstructed Z, not whole-frame pixels. Falsify by
  swapping BC5 for DXT5 and confirming the arm goes red.
- VRAM probe asserts the predicted ratio per format on raiden and forest.
- `./build.sh`; `--only texcomp,layers,decals,emissive` during; full suite + goldens at the end.

## Said out loud

- **This is an L, not an M.** Four mechanisms and a roadmap dependency.
- **Every golden moves twice** — once at phase 2 (CPU mips), once at phase 6/7. Both re-baked
  deliberately, and phase 2's re-bake happens before any compression exists so the two are
  never entangled.
- **Forest's array may be the wrong prize.** Its 117.3 MB comes partly from the canonical-size
  promotion (one 2048 source beside forty 256s), which compression does not address and a
  resolution policy would. Worth measuring the split before assuming compression is the answer.

## As built

Eight phases planned, eight run. **Four things the plan got wrong, and the largest one is
about the suite rather than the feature.**

### The corpus cannot see mips at all

Phase 2 landed the CPU mip chain and all 28 goldens read 0 px. That looked like the two
filters agreeing. It was not: **the goldens are also 0 px with every mip level painted solid
black**, and so is the raiden recipe this repo calls its best baseline. They sit near the
camera and never minify, so none of them samples a level above 0 — and most of a compressed
texture's bytes live in the chain.

Both 0 px readings this spec produced early were vacuous, and both were only caught by
deliberately breaking the mechanism and watching the number stay put. That is what moved the
fixture from phase 8 to the front of the queue and gave it its one non-negotiable property: a
surface that recedes.

Against the driver's own filter, measured on forest at `--render-mode 6`: **59,927 px of
480,000, PAE 15/255**, with frame means 0.174706 and 0.174727 — five thousandths of one code
apart, so the driver was filtering sRGB in linear space too and what moved is local rounding.

### The array was the wrong prize, and D0 does not hold

Phase 6 was to split the material array by colour, which needed a 17th sampler, which needed
D0. Neither survived contact.

**The array**: forest's 117.3 MB is eleven layers — four albedo-plus-height, four packed
normal-roughness-AO, a splat, two roughness masks. The packed maps and the splat are **three
independent quantities in one image**, and BC4 keeps one channel while BC5 keeps two with
paired endpoints; neither compresses a packed map without corrupting quantities that have
nothing to do with each other. **There are no normal maps in that array.** A split would have
compressed two layers of eleven.

**D0**: `pbr_frag` reads `irradianceMap` on one line, and that line is the ELSE of `giEnabled`
— the irradiance map answers when there is no GI volume. `gi_volume_bind` returns before
binding the atlas when the volume is inactive. **The texture D0 folds into is the one not
bound in the only case the fold has to serve.** The roadmap recorded for many specs that D0
had no scheduled consumer; the first one to arrive found it unsound.

What paid instead cost nothing: forest's two normals are plain material slots reached through
the memory loader, so teaching that loader a `TextureUse` compressed them with no sampler and
no fold.

### A third upload path, shipped broken by the commit that warned about it

Phase 2's commit said the filter runs on the CPU "rather than leaving two filters that have to
agree with each other and silently would not". `async_loader.c` had its own `glTexImage2D` and
`glGenerateMipmap` — and it is the path every **external** model texture takes. So that commit
left exactly the defect it described. `texture_upload_image` is now the one path.

### What it cost and what it saved

| | raiden | fixture |
|---|---|---|
| uncompressed | 81.354 MB | 3.000 MB |
| BC5 + BC4 (default) | 74.854 MB, RMSE 0.87 codes | 1.833 MB, RMSE 1.5 codes |
| + DXT colour | 37.253 MB, RMSE 1.6 codes | RMSE 8.4 codes |

The fixture is **five times more sensitive to DXT than raiden**, which is what it is for.
`--no-texture-compression` declines every block format exactly — ao_fixture compares 0 px
against its old golden — so the one bar this item could not set at 0 px is set by budget
instead, and the lever beside it is provable *for the storage question*. It is **not** a
return to the pre-11.85 engine, and the paragraph below says why.

Colour is **off by default**, the one default here chosen by taste rather than measurement.

### What the bisect lever does and does not reach

**`--no-texture-compression` is not a full return to the pre-11.85 engine.** It declines every
block format, but the CPU mip chain and the Z rebuild are unconditional. Both were measured
(59,927 px on forest; 0 px on ao_fixture, 52,353 on raiden), neither is reachable by a flag,
and a bisect across this spec has to use the commits rather than the switch.

### It is a VRAM win and NOT a speed win, measured three ways

The usual argument for block compression is bandwidth. It is true and **not
observable on this engine's content**.

| | measured |
|---|---|
| VRAM | raiden **81.354 → 74.854 → 37.253 MB** |
| visual cost | 0.16 to 8.4 codes, by format and content |
| frame time | **+0.3%**, against a 2.2 s spread within each configuration |
| load time vs MASTER | **+0.7%** (1.102 s → 1.110 s) — after the review; **+12% before it** |

Frame time is a wall-clock A/B/A/B over 200 frames at 2400x1500. **The GPU
profiler could not price it at all** and that is its documented behaviour: at
1600x1000 the opaque pass is ~2 ms and the effect sits under the timer's jitter,
at 3200x2000 half the samples retire unavailable and print 0.000.

The win is absent rather than small because nothing here is texture-fetch bound
— the fixture is one quad, and 3 MB fits in cache either way.

### The load-time number took three attempts, and the first two were vacuous

This is the spec's most repeated mistake, and it is the same one every time.

The **first** measurement compared compression on against off and reported
−0.4%, i.e. free. Both legs pay the CPU mip chain, so it isolated the *encoder*
— which really is free — and could not see the filter at all. The filter was the
cost: `texture_srgb_encode_byte` measured **111 ms of a 145.7 ms chain** for one
2048² sRGB texture, on the default path for every colour texture whether or not
compression is on.

The **second** attempt was the GPU profiler, which cannot resolve this at any
resolution on this content.

The **third** is the only one that answers: build master, time the same load.
Against it the branch was **+12%** as first written, and is **+0.7%** with the
reverse-table encoder. A comparison that never renders the code you are trying
to price cannot price it, and both earlier attempts were that.

### Left alone, deliberately

**Packed ORM is the largest remaining gap.** Raiden carries 21.3 MB in a single
2048 ORM map and ~29 MB across all of them, and no format here compresses one:
three independent quantities in one image. Splitting ORM into three BC4s at
import is a material-system change.

**The seven texture entry points were not collapsed.** Three reviewers reached
`TextureDesc` independently and the house has 17 precedents for it
(`GameConfig`, `PhysicsConfig`, `RockParams`, `PostFXGBufferWrites`). It is the
right shape and it is a 27-site sweep touching `is_srgb` at every one — too
large to land on top of a review round without its own before/after. It is the
one structural finding deferred rather than applied, and it should be the first
thing a follow-up does. **Done in 11.86, and the sweep was the smaller half:
the eight-step body from decoded pixels to a pooled Texture was written out
three times and had already drifted, including an `is_srgb` the async path
recovered by sniffing a format that cannot carry it below three channels.**

**`apps/tree` still tags none of its three procedural normal maps**, so they
store uncompressed. A saving left rather than a defect — and it is why the
stochastic path was safe while its Z rebuild was missing. **Done in 11.86:
54.667 → 41.667 MB for 0.081 of a code. The Z rebuild is not missing on the
stochastic path; it was checked before tagging.**

**The probe's line shape is not the house `k=v` form**, so `gates.py` carries a
bespoke parser where `_probe_render` would have done. Worth converting the next
time either side is touched. **Done in 11.86.**

**`clearcoat_fixture` is in neither `goldens.py` nor `gates.py`.** Not recorded
here when it should have been: it is why the coat-normal defect above reached a
commit at all. **Closed in 11.86** with a golden and a five-arm group.
