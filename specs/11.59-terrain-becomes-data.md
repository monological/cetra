# Terrain: from runtime fBm to an authored, eroded, layered surface

## Context

Cetra's terrain (`cetra/src/procedural/terrain.c`, 230 lines) is fBm over Perlin evaluated at
runtime. `terrain_height_at(params, x, z)` is a **pure function** — no stored grid — and that purity
is what lets eight independent consumers agree with nothing shared between them: the visual tiles,
the Jolt collider, the scatter, the water-bed seam, the character spawn, the trace diagnostic, the
normal central-difference, and the per-frame camera floor clamp.

That is not how AAA terrain works, and the difference is structural rather than a matter of taste.
**Hydraulic erosion is a simulation over a grid, not a function of position**: the height at a point
depends on how much water flowed through it, which depends on the entire upstream watershed. You
cannot answer "what is the eroded height at (x, z)?" without having computed the whole field. So the
moment erosion enters, terrain becomes DATA — which is why UE, Unity, Frostbite and Decima all
consume a baked heightfield, and why the generation happens in Gaea / World Machine / Houdini.

**And the geometry is the smaller half of the payoff.** Eroded terrain reads as real because the
materials are placed by the same process that shaped the ground: the sim knows where water flowed,
so it yields flow-accumulation, deposition and wear masks that put gravel in stream beds, silt on
valley floors and bare rock on scoured ridges. Cetra approximates this with slope + altitude + two
decorrelated Perlin fields (`terrain.c:121-155`) — the best available without a sim, and precisely
why it reads as procedural: **the dirt is not where water would put dirt.** Erosion and material
layers are therefore ONE item. The sim produces exactly what the layer system consumes.

The roadmap does not contain this. Grepped: **"splat", "virtual texture" and "erosion" appear
nowhere** in `docs/aaa-rendering-roadmap.md`, and exploration confirmed **no layer-blending system of
any kind exists** anywhere in `cetra/src`, `cetra/shaders` or `apps` — zero hits for splat, decal,
detail-map, triplanar or blend-weight outside vendored third-party trees. The only booked terrain
item is **D4 (row 36, XL)**, whose entire scope is *"rings as windows into a streamed mip pyramid"*.
D4 also contains an unresolved contradiction: it calls for streaming **height data** while relying on
`terrain_height_at` being **analytic** for the T-junction stitch it inherits from D3. Today there is
literally nothing to stream, which is why D4 has no measurement behind it.

**Intended outcome:** book the missing items honestly, then build the one that unlocks the rest —
a heightfield backend behind the existing interface, an in-engine erosion bake that feeds it, and the
masks that make the ground look authored. D4 gets re-scoped to follow, with a real memory figure.

## The architectural key

Keep the interface, swap the backend.

```
terrain_height_at(params, x, z)
    |__ analytic : fbm over Perlin      (today; allocates nothing)
    |__ field    : bicubic over a grid  (new)
```

A filtered grid sample is still evaluable at arbitrary XZ, still deterministic, still a pure function
of `(state, x, z)`. **All eight consumers keep working unchanged.** Only `TerrainParams` grows a
field pointer. This is what makes the program tractable and why the first phase is small.

## The second key, found during exploration, which resizes the whole materials question

`include/ocean.glsl:63-78` states the rule 11.45 established: *"a cap counted in declarations is a
cap on how many DISTINCT shapes of data a program reads, and six identical fields were only ever one
shape."* Consolidating six cascade `sampler2D`s into one `sampler2DArray` freed five units.

**N terrain material layers are one shape.** A full splat system is `sampler2DArray layerAlbedo` +
`sampler2DArray layerNormal` + a weight source = **three declarations, not 2N**. Which means:

- Multi-layer terrain materials do **not** need virtual texturing to be possible. They need a texture
  array and a program with room, and a fresh program has room.
- **Building RVT first would be caching before there is anything to cache.** RVT earns its keep at
  8+ layers, or when roads/decals/mesh-blending must composite in — not at four layers costing eight
  taps. It stays the destination; it is not the next step.

Two stale claims to fix while here: `CLAUDE.md` says `water_frag` "reached the same ceiling in 11.42
and is the second program to sit at 16/16" — **11.45 took it to 11 declarations** and it has five
free. And D4's data-vs-function contradiction above.

## Part 2 — Spec 11.59: the heightfield backend + the erosion bake

Branch `11.59-<slug>`, plan committed to `specs/11.59-*.md` alone, before any code, per the project
workflow. Next spec number confirmed: 11.58 is the highest.

### D6 — the backend

New `TerrainField` beside `TerrainParams` in `procedural/terrain.h`:

```c
typedef struct TerrainField {
    int    res;        // res x res, row-major
    float* height;     // world Y
    float* flow;       // erosion masks; D7 fills them, NULL until then
    float* deposit;
    float* wear;
} TerrainField;
```

`TerrainParams` gains `const TerrainField* field;` — **NULL keeps today's path byte-identical**,
which is the invariant every existing forest arm rests on.

Three decisions that are contracts, not details:

- **Bicubic (Catmull-Rom), not bilinear.** `terrain_normal_at` (`terrain.c:109`) central-differences at
  `h = extent/(tiles*tile_segments)` = **1.30 units** on what will be a ~0.98-unit cell. Bilinear is
  C0 — piecewise-constant derivative — so normals would facet on cell boundaries, and that faceting
  reaches the scatter's slope gate (`forest.c:305`) as well as the shading.
- **Out of domain, clamp to edge.** `forest.c:939` queries at the third-person camera eye, which sits
  `CAM_DISTANCE` behind the player and **can leave `[-extent, +extent]`**; the analytic field answers
  there, a bounded grid does not. Clamp matches `CLAMP_TO_EDGE` and matches the water bed's existing
  documented policy ("outside it the bed field reads its edge").
- **Thread-safety is not regressed, and not improved either.** `terrain_height_at` is already
  documented not thread-safe (`terrain.h:44-46`) because of the `g_perm` memo (`terrain.c:52-63`). A
  field sample touches no statics, so the field path is *incidentally* safe — say that, rather than
  implying a new guarantee.

Template: `_water_bake_bed` (`water.c:742-821`) is the in-tree precedent for a CPU height grid with
derived data and self-invalidation on parameter change. Note it currently calls the height function
**65,536 times per frame** from both `water_update` and `water_render`, self-guarded on
`(extent, level, units_per_metre)` — a field sample makes that strictly cheaper.

### D7 — the erosion bake

New `cetra/src/procedural/erosion.c/h`. `src/procedural/*.c` is a CMake glob
(`cetra/CMakeLists.txt:70`) — no build-file edit.

**CPU, grid-based (Eulerian), double-buffered, threaded exactly like `sky_clouds.c:116-142`.**
Chosen over GPU fragment ping-pong deliberately:

- The output feeds the **physics collider** and the **scatter**, both CPU.
  `physics_create_mesh_shape` takes a CPU float array (`game/physics.h:286`) and **JoltC exposes no
  `HeightFieldShape`** — verified, no `HeightField` symbol in `ext/JoltC/JoltC/Functions.h` — so a
  grid becomes a triangle soup regardless. A GPU sim would mandate a 67 MB readback.
- The cloud bake proves the determinism property: disjoint slabs, zero synchronisation beyond the
  joins, **output bytes identical at any thread count** (`sky_clouds.c:112-115`). Grid erosion has
  that same shape *if and only if* it is double-buffered, because then each output cell reads only
  the previous buffer. **Droplet/Lagrangian erosion does not and must be refused** — droplets write
  to shared cells, so the result depends on scheduling.
- The project's readback policy already prefers blocking-and-deterministic over async-and-fast
  (`postfx.c:1762-1766`: PBO+fence measured 0.033 ms against 5.253 ms and was **rejected** because it
  made results frame-timing-dependent and broke headless run-to-run equality).

If 4096²+ is ever needed, the GPU escape is `_water_fft_transform` (`water.c:1292-1315`) — the tree's
worked template for an N-stage fragment ping-pong on GL 4.1, with parity even by construction and
invariant uniforms hoisted out of the loop.

Model: Mei/Decaudin virtual pipes (rain → flux → water update → erosion/deposition by sediment
capacity → semi-Lagrangian sediment transport → evaporation), plus thermal erosion at the angle of
repose. Fixed iteration count, no RNG, fixed per-cell float order.

**The outputs are the point**: `height`, plus `flow` (throughput → stream beds), `deposit` (→ valley
silt), `wear` (→ exposed bedrock). Curvature is derived at read time, not stored.

**P0 measurement, before anything is wired**: bake 1024² × ~250 iterations; time it; assert threaded
and single-threaded agree **bit for bit**. If they do not, the threading is wrong and the item stops.
Publish through `--terrain-erosion-probe` in the `--water-fft-probe` / `--ies-probe` idiom, so the sim
is checkable without rendering a frame.

### The immediate visual win, at near-zero cost

Feed `terrain_tint` (`terrain.c:121-155`) the `flow`/`deposit`/`wear` masks instead of slope+altitude
+noise, and the ground's colour starts agreeing with its shape — the largest look change in the whole
program, confined to one function, with no new sampler, no new program and no new pass. It is also
the **falsifier for D7**: wrong masks are visible immediately, before a texture system is built on
top of them. And it is not throwaway — vertex colour still multiplies albedo under D9's detail
layers (`pbr_frag.glsl:1035-1038`).

**One real bug to fix here.** `terrain.c:18-22` documents the five tints as *linear* measured albedos
(grass ≈ 0.2), but `pbr_frag.glsl:1036` runs `sRGBToLinear(VertexColor.rgb)` on them — they are
decoded twice, so every terrain albedo in the corpus is darker than the comment claims. Fix the
values or the comment; do not leave them contradicting.

### D8 — import / export

The bake and the importer **meet at one format**, which is what unifies the two authoring paths:
dev-time bakes and writes, ship-time loads, and a Gaea/World Machine export drops into the same slot.

- **`.r16`** — headerless 16-bit unsigned, the literal UE / World Machine / Gaea interchange format.
  Resolution from file size, world height range declared in the `.cscn`. Trivial both directions, no
  new dependency.
- **16-bit PNG** on the read side via `stbi_load_16` — present in vendored stb and **called nowhere
  in the repo** (`texture.c` is 8-bit throughout; `stbi_loadf` appears only at `ibl.c:261`). Gaea
  exports PNG16, so this is the convenience path.
- Masks as 8-bit raw siblings.

Deliberately **not** routed through `texture.c`: `texture_gl_formats` (`texture.c:185-199`) hard-wires
*unsized* internal formats from channel count and has no path that can request 16-bit or float. This
is CPU-side height data, not a texture load.

## The fixture

A terrain fixture cannot be a `.gltf` — the thing under test is a height FIELD. So:
a committed small **`.r16`** (256², a few hundred KB) plus a `.cscn` that loads it, generated
deterministically with `assert`s that fail loudly if it stops testing anything. Every arm falsifiable
by a named one-line mutation, per project convention.

| arm | asserts | rejects |
|---|---|---|
| `terrain-analytic` | field NULL is **0 px** against today's build | the backend disturbing the existing path |
| `terrain-threads` | 1 thread vs N threads **bit-identical** | a sim with a cross-cell write hazard |
| `terrain-erosion` | probe: mass conserved within tolerance; flow accumulates **downhill** | a sim that runs and produces plausible garbage |
| `terrain-masks` | flow/deposit/wear decorrelated from slope alone | masks that are secretly still slope+noise |
| `terrain-roundtrip` | bake → write `.r16` → read → sample equals the in-memory sample | byte order / range mapping in the importer |
| `terrain-clamp` | a query outside `[-extent, extent]` returns the edge, not NaN or 0 | the `forest.c:939` camera case |
| `terrain-bicubic` | normals continuous across a cell boundary; a bilinear leg fails it | a C0 sampler shipped by mistake |

# AS BUILT

Shipped over eight commits plus a review round. **D6, D7 and D8 are done; D9-D11 and the
re-scoped D4 remain booked.** All 24 goldens 0 px, all 45 gate groups green.

## What the plan got right

The central move held exactly as designed. `terrain_height_at` kept its signature, grew a
SOURCE, and **all eight consumers kept working with no change at all** — the analytic path
measured **0 px on forest at `--render-mode 6`** against a 0 px floor, before and after the tint
rewiring. Nothing outside the three functions that install a field ever asks which source is
active. Eulerian-over-Lagrangian, the flux-based transport, the clamp policy and the
`.r16`-as-the-meeting-point design all shipped as written.

## What differed, and why

**1. Semi-Lagrangian advection had to be replaced.** The plan named the Mei pipeline including
its semi-Lagrangian sediment transport. That is the textbook stage and it **leaked 3.06% of the
sediment budget over 220 iterations**: a bilinear gather conserves mass only for a
divergence-free field, and this one is not. Replaced with flux-based transport — sediment rides
the same pipes the water does, so every gram one cell sheds is a gram exactly one neighbour
takes. Closure went from 3e-2 to **5e-09 relative**, and `terrain-budget` asserts it rather than
quoting a tolerance.

**2. The first parameter defaults made the terrain a lake.** Rain over evaporation IS the
equilibrium water depth, and 0.55 over 0.055 put ten units of standing water over two-unit
cells. Every cell drained into every other, flow read 0.48-0.94 uniformly, and the tint painted a
kilometre of ground one colour. 0.02 over 0.5 is 40 mm. Flow also changed meaning: **drainage
throughput, not standing depth**, log1p-compressed before scaling because drainage is
heavy-tailed where erosion and deposition are not.

**3. The fixture was too smooth to test its own filter.** At 85 samples per cycle bilinear and
bicubic differ by **five 16-bit codes**, so `terrain-bicubic` was green against a bilinear
sampler. It now carries a near-Nyquist band at 7.5 samples per cycle — the regime forest actually
bakes in — and the generator asserts the separation instead of assuming it.

**4. Three of the eight planned arms could not fail.** Falsifying by hand found `terrain-clamp`
passing with the clamp deleted (Catmull-Rom over four EQUAL taps returns that value, so a
far-outside query reads the edge either way — the arm now samples inside the first cell beyond
the boundary), `terrain-bicubic` passing twice (a smoothness ratio, then an analytic normal:
`terrain_normal_at` differences over less than a cell, and inside a cell a bilinear surface IS
the linearisation that difference estimates — only a cell MIDPOINT value can see a filter), and
`terrain-budget` passing because the clamp mutated is structurally unreachable.

**5. The plan's own `terrain-analytic` arm was never built**, and the review caught it. It ships
as **`terrain-seed`**: seed a field from the fbm, run no sim, require the two to agree at the
nodes the seed wrote. Reads exactly **0.000000**; a transposed seed reads 37.4 against a 24.4
range. It needed a `--erode-iterations -1` seed-only path, which is a legitimate configuration
rather than a test hook.

## What the review found that the implementation missed

**Two functional defects, both invisible to every arm that existed.**

- **The masks did not round-trip.** The plan said "masks as 8-bit raw siblings" and only the
  height was written, so a shipping load got the eroded GEOMETRY and then shaded it with the
  slope-and-altitude guess erosion exists to replace — the feature's own opening failure, reached
  through its own save path. Measured flow **0.684 out, 0.000 back**. Fixed, and
  `terrain-roundtrip` now asserts the masks at one 8-bit step.
- **`terrain_tint` normalised altitude by `TerrainParams.height`**, which is the fbm's amplitude
  and goes inert the moment a field is installed. A file loaded over 0..1200 into an app whose
  params say 95 read `alt` up to 12.6 — every surface above y = 32 fully under snow, dirt band
  unreachable. `TerrainField` now states its own range.

**Plus:** `ends_with_ci` reinvented `strcasecmp` (which `compat.h` has shimmed all along) and
folded only its left operand; an 8-bit PNG loaded silently as 256 terraces on the path justified
by "DCC tools export 16"; `--heightmap` discarded `--erode-save` in silence.
