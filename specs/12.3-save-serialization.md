# Spec 12.3 — Save serialization

## Context

`docs/game-engine-roadmap.md` Part 3 item 5, the last blocking gap: **Save / serialization —
Partial. `.cscn` describes scenes; settings persist since 12.2; no runtime GAME state does.**
Everything else on the path to a vertical slice is done or genre-dependent.

The authoring half exists (`.cscn`, §6.0) and the tuning half exists (`config_snapshot.c`,
spec 11.71) and the player-preferences half exists (`game/settings.c`, spec 12.2). What is
missing is the one file none of those can be: **where the player actually was.**

Confirmed absent by sweep — `save|serialize|deserialize` across `cetra/src` and `apps/` hits
only `physics_cook.{h,cpp}` (Jolt BVH cooking) and `game/settings.c`. Nothing serializes an
entity, a body, a character or an animator.

**The format is cJSON, and that is a decision rather than a default.** Protobuf and Cap'n
Proto were considered and rejected: both need a host-side code generator (`protoc`, `capnp`)
present on macOS, Linux and Windows before the build starts, which is exactly what the
vendoring rule in `AGENTS.md` exists to prevent — the only `find_package` calls in this tree
are OpenGL, Threads, Git and Python3. Both are C++-first with third-party C ports. And both
sell properties a single-player save does not have: zero-copy mapping (a save is read once,
into a load that rebuilds a Jolt world), cross-language wire compatibility, and compact
encoding for a file that is a few hundred KB.

What they get right and this spec copies is **tagged, name-keyed fields** — Unreal reaches the
same property through UPROPERTY reflection, Unity through name-keyed fields, Source through
`datamap_t`'s `DEFINE_FIELD`. Cetra's descriptor table is the hand-written form of the same
thing, and `settings.c` and `config_snapshot.c` already prove the technique twice. This is the
third table, and the third cJSON reader — which `config_snapshot.c:1656-1659` names in advance
as the moment to hoist its two shared helpers.

**The distinction that decided the format: self-describing versus packed.** Packed binary is
what is hard, because skipping an unknown field means knowing how many bytes to jump, and
getting that wrong desynchronizes the rest of the file with no error. Self-describing formats
(JSON, CBOR) make skip-unknown free. If this ever needs to be binary, the swap is CBOR and it
costs a day, because the table, the versioning, the migrations and the drop policy are all
unchanged — only the encoder moves. That is recorded here so the next person does not
re-litigate it.

**Non-goals** (stated, not built): replay/determinism recording; networked or cloud save
conflict resolution; save file encryption or anti-tamper; compressing the file; saving
particle pools, live audio playback positions, or Jolt's internal solver state (see Risks);
a save-slot browser UI (12.2's element list is closed — an app builds one from it).

## Design

### 1. What a save is, and what it is not

Three files describe a session and none contains the others:

| file | says | owner |
|---|---|---|
| `.cscn` / app `on_init` | what EXISTS in the world | `cscene.c`, the app |
| config snapshot | how the RENDERER is tuned | `config_snapshot.c` (11.71) |
| settings | what the PLAYER chose | `game/settings.c` (12.2) |
| **save** | **where the player WAS** | **this spec** |

A save names its source in a `source` block, the `config_snapshot.h:33-60` convention, and is
applied **on top of** a scene the app has already built. It never creates a scene, a light, a
material or a mesh. **It restores state onto objects; it does not author objects** — with the
one deliberate exception of spawned entities, §4.

### 2. The module — `cetra/src/game/save.c/.h` (new)

Lives in `game/` beside `settings.c`, for the reason `settings.h:14-17` already states: the
technique is shared, the table cannot be. `config_snapshot.c`'s owner enum has no Entity, no
RigidBody, no CharacterController and no Animator, and no `CFG_STRUCT_*` entry they could hang
from.

**No CMakeLists edit is needed.** `cetra/CMakeLists.txt:114-128` globs `src/game/*.c`, and the
forwarder at `:58-59` makes anything under `game/` public automatically (`_rel MATCHES
"^(game|procedural)/"`), which is why `game/settings.h` is app-facing without appearing in
`CETRA_PUBLIC_HEADERS`. The glob has no `CONFIGURE_DEPENDS`, so a new `.c` needs a
re-configure, not just a rebuild.

```c
typedef struct SaveLoadResult {
    bool ok;                        // false ONLY for file-level refusal
    int  from_version;              // what the file was written at, before migration
    int  migrations_run;
    int  entities_restored;
    int  entities_spawned;
    int  dropped_missing_entity;    // §5 case 1
    int  dropped_unknown_spawner;   // §5 case 3
    int  dropped_unknown_component; // §5 case 4
    int  unknown_keys;              // the config_snapshot sweep, ported
} SaveLoadResult;

bool save_write(SaveSystem*, const char* path);
SaveLoadResult save_read(SaveSystem*, const char* path);
bool save_default_path(char* out, size_t cap, const char* slot); // beside settings.json
```

A result rather than a bool, because three of this spec's four policies are "drop and count"
and the counts have to go somewhere a gate arm can assert and a game can display.

### 3. The descriptor table, and the one thing it needs that neither predecessor has

Mirrors `settings.c` in skeleton and borrows `config_snapshot.c`'s pieces as the data demands:
the **token-paste owner map** (`CFG_STRUCT_##owner_`, `config_snapshot.c:124-153` — it
documents a real memory-corruption bug, and a save has four owner structs, which is exactly
the case it guards), the `_decode_value` / `_store_value` split, `_field_ptr` /
`_field_ptr_const` **copied verbatim including their comments**, and the dotted-path
`_section` walker.

Types: `SAVE_BOOL`, `SAVE_INT`, `SAVE_FLOAT`, `SAVE_VEC3`, `SAVE_QUAT` (a `versor`, new),
`SAVE_ENUM`, `SAVE_STRING` (new — a fixed `char[N]` at an offset plus a `cap` on the row, the
smallest honest way to fit a string into an offset-based table).

**The genuinely new mechanism: accessor rows.** A body's live pose and velocity are not at an
offset — `RigidBody` (`physics.h:242-257`) holds only creation parameters plus opaque handles,
and the API is asymmetric: `rigid_body_get_linear_velocity` / `set_linear_velocity` both exist,
but there is **no `rigid_body_get_position`** (the pose flows body → entity through
`sync_physics_to_entities`, `physics.c:800`). `config_snapshot.c` has `ConfigApplyFn` for the
write-in direction only; a save needs both directions.

```c
typedef void (*SaveGetFn)(const void* base, double* out, int n);
typedef void (*SaveSetFn)(void* base, const double* v, int n);
#define SAVE_ROW_FN(owner_, type_, key_, get_, set_) /* offset unused */
```

So velocities go through the existing velocity API, the character's pose through
`character_controller_get_position` / `_set_position` (`character.h:112-116` — a
`CharacterVirtual` is not a body, the same asymmetry `physics_world_shift_origin` warns about),
and a body's pose is read from the synced `entity->position` / `->rotation` and written back
through `rigid_body_set_position` / `_set_rotation`. **No new engine API is required.**

### 4. Sections, and entity identity

```
version, floor, source          file-level
world       { time, paused }    the sim clock; NOT the accumulator (a fresh one is
                                sub-step error, and restoring it restores nothing)
entities    [ ... ]             the array
<app>       { ... }             any table an app registers, §7
```

**One `entities` array, matched by NAME**, `config_snapshot.c:1391-1452`'s mechanism ported:
each entry writes `name` always (every `Entity` has a `char name[64]`, so unlike lights and
materials there is no unnamed case) and `index` alongside it; the reader prefers the name scan
and falls back to the index. Entity **ids are not stored** — `create_entity` assigns
`id = em->next_id++` and gametest's creation order is flag-dependent (`--no-chaser`, `--twin`),
so an id means something different between two runs of the same binary.

An entry carries a component object per component the entity has, **keyed by name** —
`"rigid_body"`, `"character"`, `"animator"`, `"audio_source"` — and never by the
`ComponentType` value. `COMPONENT_BIT(type)` is `1u << type`, so removing an enum member
renumbers every one after it; `component_mask` is a runtime query optimization and does not
reach disk. This makes §5 case 4 a non-question.

**Animator restore is a snap**, per the approved scope: `animator_source_name()` (the base
source's name — a space's given one or a clip's own), the base clock phase, plus `playing`,
`speed` and `param`, which are SETTINGS fields and plain writes. On load, if the saved source
name equals what the app already played at init — the common case, since gametest plays its
locomotion space in `on_init` — only the phase and knobs are restored; otherwise the name is
looked up with `scene_find_animation` and played through `animator_play`. A save taken
mid-crossfade loads with the destination playing. No new animator API.

### 5. The four structural policies

**The organizing rule: file-level problems refuse the file, record-level problems drop the
record and count it.** One lost crate never costs the other forty hours.

| case | policy |
|---|---|
| Save names an authored entity the scene no longer has | **Drop, count, log once.** The record is a state overlay with no target. Refusing would make a shipped game unpatchable — every level edit would invalidate every save. |
| Scene has an entity the save does not | **Leave it at its authored state.** This is content added to a level the player already visited, and it is the whole argument for name-matching over indices — an ordinal save silently applies entity 12's state to entity 13. |
| Save names a spawner that no longer exists | **Drop, count** — but prevent it: a spawner name is a permanent contract, like a reserved protobuf field number. Retiring one means registering a tombstone that spawns nothing, so the deletion is a decision somebody wrote down rather than a silent loss. |
| A `ComponentType` is removed | **Dissolves** — components are keyed by name, §4. Keep enum tombstones anyway (`COMPONENT_MESH_RENDERER` is already one) as belt-and-braces. |

Only two things refuse the file: it will not parse, and its version is below `SAVE_FLOOR`.

### 6. The spawner registry

A spawned entity's record is the *only* record of its existence, so it carries a recipe:

```c
typedef Entity* (*SaveSpawnFn)(EntityManager*, const cJSON* params, void* user);
void save_register_spawner(SaveSystem*, const char* name, SaveSpawnFn, void* user);
```

`{"name": "box_7", "spawner": "box", "params": {...}}` — name absent from the scene plus a
known spawner means spawn it, then apply the rest of the record exactly as for an authored
entity. Unknown spawner drops per §5.

This forces a real fix in gametest. `spawn_falling_box` (`gametest.c:335-374`) draws position,
colour and half-extent from `rand01()` and stores the last two **nowhere** — they live only
inside a `Material` and a Jolt shape. `srand(42)` makes a fresh run reproducible but a restore
cannot replay an RNG it did not count. The spawn becomes: roll the parameters, build a params
object, call one recipe function. The recipe is then the single path both the keypress and the
loader take.

### 7. App state the engine cannot see

An entity walk cannot reach `player_yaw` (`gametest.c:81` — the player's only facing state,
since gametest never writes `entity->rotation` and the yaw is rebuilt into
`player_rig->original_transform` every step), `box_count` (`:53` — restore it or names
collide), `chaser_yaw`, `heart_timer`, `catch_cooldown`, the three door flags (`:213`, `:214`,
`:377`), or `ui_menu_paused` (`:136`).

So an app registers its own table over its own struct:

```c
void save_register_table(SaveSystem*, const char* section,
                         const SaveField* rows, int count, void* base);
```

gametest collects those file statics into one `GametestSave` struct and registers a table over
it. That is a modest refactor and it is the honest fix — it also makes the state that is
genuinely "the game" legible in one place instead of scattered across twenty file scopes.

### 8. Versioning and the migration chain

Per the approved scope, the full mechanism ships:

- **Per-section `version`**, not one file-wide integer. Unreal's `FCustomVersion` insight: a
  monolithic version forces every subsystem to coordinate a bump.
- **`former_key` on a descriptor row** — the reader tries `key`, then `former_key`. Kills pure
  renames with no migration function, the way Unity's `[FormerlySerializedAs]` does.
- **A migration table**, `{section, from_version, fn}`, run in order from the file's version to
  the current one. **Migrations run on the parsed cJSON tree before the descriptor walk**, the
  DataFixerUpper property: a migration written now must not depend on what the struct looks
  like in three years.
- **`SAVE_FLOOR`** — below it the file is refused by name. The floor is what makes old
  migrations deletable; without one you keep every migration forever.
- **Never reuse a retired key.** A `reserved` list beside the table, and enum label tables keep
  holes as placeholders (`config_snapshot.c:177-186`'s `"unused_6"` convention) because index
  is value.
- **A committed fixture ladder** — one small save per historical version in `assets/saves/`,
  each loading to a state the current writer reproduces. These are the only test that catches a
  *semantic* change (same key, same type, different meaning), which no tagged format detects.
  They are text, so they are reviewable in a diff, and they never change once committed.

### 9. Two departures from the existing tables, both deliberate

**Atomic write.** `settings.c:205` and `config_snapshot.c:1248` both `fopen(path, "wb")` and
overwrite in place. A half-written screenshot config costs a re-dump; a half-written save costs
the player's progress. This writes to `<path>.tmp`, `fflush` + `fsync`, then `rename()`, with a
comment saying why it differs.

**Floats at `%.9g`.** cJSON prints `%1.15g` with a `%1.17g` round-trip fallback
(`ext/cJSON.c:580-586`), so a float already survives exactly — but `0.3f` writes as
`0.300000011920929` where `%.9g` gives `0.300000012`, equally exact and ~40% smaller. Written
through `cJSON_AddRawToObject` (`ext/cJSON.h:270`), and `%.9g` is already the house precision
for `--anim-probe` so a textual diff is a bit diff.

This is also where `config_snapshot.c:1656-1659`'s standing invitation is taken up — its
comment says `_string_or` / `_int_or` "are not shared because a `static` in one .c is not
reachable from another, which is a seam worth widening the day a third cJSON reader appears."
This spec is that third reader. A small `cetra/src/json_util.h/.c` takes those two plus the
`%.9g` float writer; `config_snapshot.c` and `cscene.c` switch to it. Internal header, not in
`CETRA_PUBLIC_HEADERS`.

### 10. gametest

- **F5 / F9 quicksave and quickload**, as two new rows in the `actions[]` table (`:180-209`) so
  they are rebindable like everything else and reachable from a pad.
- **The box spawner registered** as `"box"`, §6.
- **`GametestSave`** — the file statics of §7 in one struct, one registered table.
- **`--save-probe <case>`** — the early-exit headless probe, the shape `--ui-probe`
  (`gametest.c:1868-1946`) and `--anim-probe` (`:1394-1544`) already established: parse,
  early-return before the real game exists, print `save <case> <label> <key> <numbers>` at
  `%.6f` so one regex reads it, return an rc. Dispatched in `main` after the `anim_probe` arm
  (`:2420-2430`). Like `run_anim_probe` it builds its own world, since `on_init` never runs.

### 11. The `save` gate group and the must-not-move set

Appended to `GATE_GROUPS` after the `("ui", ...)` entry at `gates.py:22590-22591` and before
`("import", ...)`, with `run_save_gate(workdir)` defined above the list. Docstring with a
column-0 prose line and arms at exactly two spaces after `getdoc`'s common-indent strip; every
verdict line prints its arm name as a **literal** at the print site, because `_ARM_PRINTED`
(`gates.py:16220`) regexes the function's own source and a formatted name is invisible to it.
Save files go under `os.path.join(workdir, "save-...")` through a `CETRA_SETTINGS_DIR`-style
override, never the real per-user directory — the `ui-settings` arm's pattern (`:22450-22452`).

| arm | asserts |
|---|---|
| `save-roundtrip` | write known non-defaults, read back into a **zeroed** struct, every field survives — so a loader that merely leaves a field alone fails |
| `save-entities` | N entities' poses, rotations and velocities restore; the character controller's position and velocity go through their own API |
| `save-spawned` | a spawned box returns with its size and colour, which exist nowhere but the save |
| `save-missing` | a save naming an absent entity drops exactly one and loads the rest |
| `save-unknown-spawner` | an unregistered spawner drops one, counts one, and the file still loads |
| `save-components` | a component object keyed by a name no longer known is dropped and counted; the enum value never appears in the file |
| `save-migrate` | every committed fixture in the ladder loads to the state the current writer reproduces |
| `save-rename` | a fixture written with a retired key lands in the renamed field via `former_key` |
| `save-floor` | a file below `SAVE_FLOOR` is refused by name and applies **nothing** |
| `save-sim` | save, step 120 fixed steps, reload, step 120 again — poses agree within a stated solver tolerance, and the tolerance is measured rather than assumed |

All CPU, no GPU, no window — `run_anim_probe` proves a headless game with an `EntityManager`
is reachable, and physics is CPU. Fits the suite's budget.

**Must not move**, before and after each core phase: all 33 goldens, and the `anim`, `audio`,
`ui`, `gamepad` and `config` groups — gametest is touched heavily and those five are what see it.

## Verification

- **Automated, here.** The ten arms above, all analytic and GPU-free. The strong one is
  `save-migrate` against the committed ladder — it is the only thing that catches a semantic
  change, and the only reason to commit fixtures at all. `save-sim` is the one that produces a
  number nobody knows yet: how far a restored world diverges from one that never stopped.
  Measure the tolerance before quoting it; a count without its floor is not a measurement.
- **By hand, windowed.** gametest: spawn a dozen boxes, push the door open, quicksave mid-swing,
  spawn more, quickload — the boxes and the door return, the extras are gone, the player faces
  the way they did. Relaunch the binary and load the same file. Save with a menu up.
- **Not verifiable here, recorded as owed.** A save surviving an engine upgrade in anger (only
  time produces that); the Linux and Windows save paths, which are the same debt 12.2 already
  carries for `settings_default_path`; and Steam Cloud syncing a save between two machines on
  different patch levels, which is what would make **forward** compatibility (an old build
  reading a new save, needing unknown-field *preservation* rather than skipping) real rather
  than theoretical.

## Risks

- **A restored world is not bit-exact, deliberately.** Jolt's contact caches, island assignments
  and sleep timers are not serialized. Doing so would pin the save format to `JPH_VERSION_ID`
  (which `physics_cook.h` already exports for exactly this reason) and break every save on a
  physics upgrade — a worse trade than a crate settling a millimetre differently. **This must be
  said in `save.h`'s header comment**, or someone files it as a bug. `save-sim` bounds it.
- **The app-table refactor touches gametest broadly.** Collecting twenty file statics into a
  struct is mechanical but wide, and gametest hosts the `anim`, `audio`, `ui` and `gamepad`
  groups plus two goldens. Those are the must-not-move set for a reason; run them at every phase.
- **The spawner contract is a promise the compiler cannot keep.** Nothing stops a future edit
  renaming `"box"`. The tombstone convention and a `reserved` list are the whole defence, and
  `save-unknown-spawner` only proves the failure is graceful, not that it did not happen.
- **`SAVE_STRING` is new to this family of tables.** A fixed `char[N]` plus a `cap` on the row is
  the version that fits an offset table; a `char*` would need an allocator contract the design
  has no room for. If a string wants to be unbounded, that is a redesign, not a widening.
- **Scope.** The migration chain is real work that pays off later rather than now. It ships
  because retrofitting versioning onto files already in players' hands is the one thing that
  cannot be done late.
