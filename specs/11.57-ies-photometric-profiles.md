# 11.57 — IES photometric profiles

## Context

Roadmap item 25 (C3), nominated by the roadmap's own what's-next paragraph as one of two remaining
unblocked-and-small items. Its premise is sound and, unusually for this table, checkable:

> 9.9/10.0 made punctual lights genuinely photometric — candela and lux imported as authored, an
> EV100 camera — and then every one of those lights radiates through a bare analytic cone.

`Light.intensity` really is stored in the type's canonical photometric unit (`light.h:58-60`), and
`spotConeFactor` really does then push it through a smoothstep between two cosines
(`lights_ubo.glsl:98-103`). The gap is real. An IES profile is the measured angular distribution of
a real luminaire, and it is what makes an interior read as lit rather than shaded.

**Exploration corrected the row on the one thing that shapes the whole design.** The row says the
table "lives in the existing std140 light UBO alongside the packed lights". Taken literally that is
broken: `ubo_upload` orphans the whole allocation (`ubo.c:44-47`) and `light_cluster.c:412-414`
rewrites only the live prefix `224 + 96·N`, so anything after `clusterLights[128]` is **undefined
every frame**. Placed *before* the lights it works but re-uploads static data on every invocation —
and `render_current_scene` re-enters **seven times on a probe-capture frame**.

**And the row's deferral of asymmetric profiles does not survive that correction.** It defers them
"rather than paying a unit for the symmetric 90%" — a Wall-1 argument that assumes a 2D table means a
*texture*. It does not. A dedicated UBO block costs **bytes, not sampler units**, and the tree already
has two precedents: `ShoreFilmBlock` (4112 B, binding 5) and `stochastic.glsl`'s 64-entry inverse CDF,
whose comment states the principle outright — *"a uniform array rather than a texture, which is what
lets this run in a program that has declared all sixteen samplers the driver allows."* Once the table
is a UBO block, the symmetric and asymmetric cases differ only in stride. **So this spec implements
full LM-63, both cases, and there is no v1/v2 split.**

Budgets, kept apart because conflating them is what produced the deferral:

| | used | limit | scarce |
|---|---|---|---|
| `pbr_frag` texture units | 16 | 16 | **full — Wall 1** |
| UBO binding points | 6 (0–5) | ≥ 36 guaranteed | no |
| bytes in a new UBO block | 0 | 16384 guaranteed | no |

## Decisions taken, with their reasons

**Normalised shape, with the peak seeded from the file.** The profile is divided by its own peak and
multiplies `intensity`; `intensity` stays the sole brightness control. This keeps `_scale_emitters`
(`gates.py:104-126`) — gates.py's single definition of "what counts as an authored intensity", which
four scale-invariance fixtures rest on — true without modification, and leaves untouched the
documented Φ/4π decision at `light.c:95-98` (lumens→candela divides by 4π *even for spots*, so
narrowing a beam does not brighten it).

Normalising does **not** discard the file's absolute output, because `intensity = file_peak` makes
the two readings identical. So the loader **seeds `intensity` from the file's peak candela when the
scene did not author one**, which needs a `has_intensity` presence flag on `CSceneLight` — already
the house convention there (`cscene.h:66-71`: optional fields carry their own `has_*` flag because
"absent = keep the engine default"). Physically correct by default, authored value still wins,
and the probe reports which applied.

**The profile REPLACES the spot cone.** A profile is the angular distribution; multiplying it by a
second analytic falloff yields a distribution matching neither the file nor the authored cone. So a
profiled spot's `cone` goes dead and the parser says so once. Two consequences must move with it,
both named by exploration:
- `shadow.c:817-821` derives its FOV from `2·acos(outerCutOff)·1.15`. A real IES skirt emits past the
  analytic cone, so the FOV must come from the profile's angular support or the skirt renders
  outside the shadow map and reads as unshadowed.
- `light_cull_radius` (`light.c`, moved there in 11.56) solves `intensity × peak_color` against 1/256
  with no cone or profile term. A forward-concentrating luminaire reaches 5–10× isotropic on axis, so
  the profile's peak gain belongs in that solve — in `light_cull_radius`, per its own doc comment
  calling it "a pure function of one light and part of what `range` MEANS".

**The glTF spot cone bug is fixed first.** `import.c:1352-1353` assigns assimp's
`mAngleInnerCone`/`mAngleOuterCone` — **half-angles in radians** — straight into `cutOff`/`outerCutOff`,
which every consumer reads as **cosines**. An imported 30° spot ships `0.524`, read as
`cos⁻¹ = 58.4°`, and `shadow.c:819` then builds a 117° shadow frustum for it. The `.cscn` path is
correct (`cscene_apply.c:236-238` applies `cosf(glm_rad(...))`). IES indexes off exactly this
contract, so it is fixed before it is built on, not after.

## Design

### Storage: a 7th UBO block, variable stride

`UBO_BINDING_IES = 6` in `ubo.h`'s registry, `IesBlock`, uploaded **once at profile load** and never
touched by `light_cluster.c` — which is what sidesteps the orphan, the `memset` at
`light_cluster.c:390`, and the 7×-per-capture re-upload in one move. Structurally the `ShoreFilmBlock`
shape (`ubo.h:51-81`, `shore_film.glsl:23-33`, created in `water.c:1418`).

```
IesBlock {
    ivec4 iesCounts;        // x = profile count
    vec4  iesDesc[MAX];     // per profile: x = float(pool offset), y = vTaps,
                            //              z = hTaps, w = horizontal span (deg)
    vec4  iesPool[N];       // candela/peak, 4 scalars per vec4, hand-decoded
}
```

**Ceiling 32 vertical × 16 horizontal**, and each profile spends only what it needs — the descriptor
carries its own `vTaps`/`hTaps`. 32 vertical taps is 5.6°, which sits at or above what LM-63 files
actually carry: the common grids are 19 or 37 vertical angles (10° or 5° steps), so a finer table
would mostly resample noise upward. Symmetric and asymmetric then differ **only in `hTaps`**:

| profile | bytes |
|---|---|
| 32 × 1 (symmetric) | 128 B |
| 32 × 8 (quadrant/bilateral) | 1 KB |
| 32 × 16 (ceiling) | 2 KB |

One 16 KB block holds ~8 fully asymmetric profiles or ~126 symmetric ones, and mixed sets share the
pool. **Never declare a bare `float[]` in std140**: `lights_ubo.glsl:44-46` records that scalar arrays
take a vec4 stride and a raw `uint[3072]` would silently 4× its block. Decode like `clusterWord`
(`lights_ubo.glsl:57-64`) or `shoreFilmTip` (`shore_film.glsl:45-48`).

### Per-light reference: `attenCutoff.y`

Free, zero-filled, read by nothing, and already documented "reserved" (`lights_ubo.glsl:30`, written
`light_cluster.c:181`). `-1 = no profile`, matching `shadowMisc.y`'s existing convention for the
punctual shadow layer. **Zero bytes added to `GpuPackedLight`.**

### The frame, and the axis invariant

An asymmetric profile needs a *roll* about the luminaire axis, not just an axis. `Light.up` exists and
`_area_panel_dir` / `_area_panel_up` (`light_cluster.c:153-171`) already orthonormalise exactly that
frame for panels — reuse both.

**Axis normalisation is not currently an invariant**, and for IES it is a correctness question rather
than a style one: the lookup is `acos(dot(L, axis))`, and a non-unit axis skews that angle
non-linearly. Three policies exist today — `light_cluster.c:210` packs raw, `shadow.c:751/1567`
normalise, `scene.c:822-829` normalises only for lights attached to a `SceneNode`. Fix at the pack
site (`light_cluster.c:210`), matching what `_area_panel_dir` already does.

### Lookup

`iesProfile(idx, L, axis, up)` in `lights_ubo.glsl`, beside `getDistanceAtt` and `spotConeFactor` and
for the reason stated there: *"a surface and the fog in front of it have to agree about how a lamp
dies off, or the beam separates from the pool it casts."* Bilinear over (vertical, horizontal), on a UNIFORM
index — `angle / step` — rather than the warped one `preintegrated_skin.glsl` uses, because 32 taps
already sits at or above the source grid and a warp both bake and probe must agree on buys nothing
here. `hTaps == 1` collapses the horizontal lerp to the same tap twice, so the symmetric case needs
no branch. LM-63 declares its horizontal range (0–0 full, 0–90 quadrant, 0–180 bilateral, 0–360
none) — fold the query angle into the declared span, one helper, same path for all four.

**The tail tap must be exactly 0.** `pbr_frag.glsl:1677`'s `if (attenuation <= 0.0) continue` skips
9 shadow taps plus the whole GGX/clearcoat/sheen/POM chain, and its comment says it "is only safe
because the photometric one is" exactly zero. A profile folded into `attenuation` inherits that
contract — pin it as a table invariant at bake time, not an accident of the file.

### The five sites the profile must reach

Exploration found the falloff evaluated in five places, not one. Applying it in some but not all
reproduces the exact error class 11.56 just fixed.

| # | site | note |
|---|---|---|
| 1 | `pbr_frag.glsl:1664-1668` | main PBR loop |
| 2 | `pbr_frag.glsl:1297-1302` | `renderMode == 7` debug — a **hand-duplicated copy**, easiest to forget, invisible to goldens |
| 3 | `froxel_inject_frag.glsl:326-335` | clustered point fog — **never reads `dirType.xyz` today**; needs the axis |
| 4 | `froxel_inject_frag.glsl:283-285` | spot shaft, standalone uniforms via `scene_first_spot_light` |
| 5 | `contact_shadow_frag.glsl:317-319` | fold weight; its denominator is "every light that reaches the pixel" |

## Phases

**P0 — the cone contract.** Fix `import.c:1352-1353` (`cosf` on both) and normalise the packed axis at
`light_cluster.c:210`. Add `warn_unknown_keys` to `parse_lights`, which is the **only** parse block
without one (twelve others have it) — a misspelled light key is silently ignored today, the same
failure that let `water_fixture` author `sun_elevation` flat for four specs. A fixture with a glTF
spot, since none exists; measure whether any golden moves (exploration found no glTF spot in the
corpus, so the expectation is 0 px — to be measured, not assumed).

**P1 — the reader and the tool.** `tools/gen_ies_table.py`: LM-63 parse, symmetry resolve, resample to
a fixed grid, emit the pool. Then the C reader in `cetra/src/ies.c/h`, scene-owned and cached by path
like `TexturePool` (`scene.c:51/92-96` is the ownership shape), path resolved via `resolve_in_place`
like `env_hdr` (`cscene.c:797`), profile path an inline `char[CSCENE_MAX_PATH]` because `cscene_free`
is a bare `free(desc)`.

**P2 — the block and the lookup.** `IesBlock`, the binding, `ubo_wire_blocks`, `iesProfile` in
`lights_ubo.glsl`, and site 1. Goldens must be **0 px** — no scene authors a profile yet, so nothing
may move.

**P3 — the other four sites**, plus the shadow FOV from profile support and the peak term in
`light_cull_radius`.

**P4 — `--ies-probe`.** Four-part CLI wiring mirroring `--wind-bound-probe` verbatim (args field, usage
line, parse arm, call after `engine_run`), header first with `available=`/`reason=`. Format
`ies-probe <tag> k=v k=v`, parsed by the existing shared `_probe_render` — **no new parser**. Rows:
one per profile, one per sampled angle with `file_cd` / `table_cd` / `rel_err`.

**P5 — fixture and gate.** `assets/gen_ies_fixture.py` imports `tools/gen_ies_table.py` via
`spec_from_file_location` — the `gen_hair_fixture.py` pattern, whose stated property is *"the fixture
verifies the tool rather than trusting it."* Synthesise `.ies` files whose candela are known **by
construction** (one symmetric, one bilateral, one fully asymmetric, one degenerate), so ground truth
is *painted, not measured*. An `ies` gate group; every arm falsified by hand.

**P6 — the record.** Correct C3's row: the deferral was priced in texture units and the placement
removes that price; both cases ship. Note the `LightsBlock` upload hazard. `AGENTS.md` gains the
block, the flag, the fixture and the five sites.

## Built

Complete, P0 through P6. **24 goldens 0 px throughout** — no scene in the corpus authors a profile,
so the un-profiled path is provably untouched — and the suite gains an `ies` group of four arms.

### Three things the plan got wrong, all caught by something mechanical

**The block sizing.** The plan estimated "~8 fully asymmetric profiles" in one 16 KB block. The
`_Static_assert` written to guard exactly that claim rejected it on the first build: `1 + 8 + 8·512/4`
vec4 is 16528 bytes against a guaranteed 16384. The real number is **seven**, and the same assert
caught that the first draft had a *fixed*-stride pool where the plan called for variable stride.

**The descriptor.** One vec4 per profile could not carry the file's measured vertical range, and
outside that range the answer must be **zero rather than the clamped edge** — a file measured 0..90
stopped there because the luminaire emits nothing above it, and clamping a nonzero edge would light
the ceiling *and* break `pbr_frag`'s exact-zero early-out. Descriptors are two vec4.

**The cull radius.** The plan booked a peak-gain term against `light_cull_radius`, reasoning that a
luminaire concentrates 5–10× on axis. True of the *absolute* reading; **normalising makes
`profile ≤ 1`, so `intensity × profile ≤ intensity` and the existing solve is already an upper
bound.** One of the two stated consequences of replacing the cone simply is not one. The other — the
spot shadow frustum — is real and is fitted to the profile's angular support.

### Two defects the work found in itself

**The UBO block was never wired.** It linked, uploaded and read as zeroes, so a bilateral test profile
rendered a perfectly round pool — a plausible frame with the feature entirely inert. `ubo_wire_blocks`
needed a seventh entry. Found only because the test file's answer was known before the render.

**The horizontal fold used a modulo.** A partial sweep *mirrors*: a bilateral file measured 0..180
describes 190° as 170°, not 10°. Caught while constructing the bilateral fixture, whose monotone ramp
is the only thing that can tell the two apart.

### Falsification

Every `ies` arm was falsified by hand and each failed alone:

| break | arm | reading |
|---|---|---|
| modulo fold instead of mirror | `ies-table` | relative error **1.0** at `ies_bilateral v=0 h=180` |
| guess the span instead of reading it | `ies-symmetry` | names both wrong files |
| drop the peak seeding | `ies-seed` | `reported=False on the light=False` |
| stub the profile index in the shader | `ies-shape` | **0 px** on both reads |

And `gltf-cone`, from P0: reverting the `cosf` reads 0.3491/0.5236 — the raw radians, *inverted*,
exactly as predicted before it was run.

### Notes for later

- **`--no-shadows` and the runtime toggle** are unaffected here; the profile is scene state, not
  shadow state.
- **Only the fog's first spot scatters.** That is pre-existing (`scene_first_spot_light`), so a
  second profiled spot's beam is unscattered while its floor pool is correct. Unchanged by this spec
  and worth knowing before reading a foggy frame with two spots in it.
- **Area panels ignore profiles.** An IES file describes a point-like emitter's angular
  distribution; a panel is shaded by an LTC integral over its area. ~~Nothing refuses it — the index
  simply never reaches the LTC branch.~~ **Corrected in the review round below: it reaches
  `contact_shadow_frag`'s fold weight, which is a defect. Refused now at authoring and at pack.**

## Review round

Eight agents over the finished diff — four `/thermo-nuclear-code-quality-review`, four
`/simplify`. Recorded because of what the pattern says rather than for the list: the
findings that mattered most were **claims this spec made about its own coverage**, and
five phases plus 24 green goldens plus 217 green arms had not touched any of them.

### The falsification table above was measuring the wrong copy

`ies-table`'s row is correct — a modulo in `ies.c` really does read 1.0 at
`ies_bilateral v=0 h=180`, because `_parse_and_resample` queries `a_h == span` exactly and
`fmodf(180, 180)` folds the last plane onto the first. But that is the C copy, reached by
accident at one query. The GLSL copy, which is the one that decides pixels, was covered by
`ies-shape` alone, and `ies-shape` asserted `moved > 0 and differs > 0` over the two files
where the fold cannot matter: `ies_symmetric` returns before it (`hTaps == 1`) and
`ies_asymmetric` spans 360, where a modulo IS the mirror. **The bilateral and quadrant
files — the two whose stated reason for existing is this exact case — were never
rendered.** Four separate shader mutations left the whole group green: mod-for-mirror, a
scrambled pool decode, a transposed v-major read, and a 90-degree azimuth rotation.

Both source comments and AGENTS.md said the probe held all three copies together. It could
not: the probe samples **at the taps**, deliberately and correctly, and every tap lies
inside `[0, span]` where a mirror and a modulo agree exactly. So did both of the C fold's
call sites, which made `ies_fold_horizontal` unreachable outside one incidental query.

Now: the tool's copy is asserted by `gen_ies_fixture.py`, the C copy by the probe's new
`mirror` rows, and the GLSL copy by `ies-mirror` — the fixture is symmetric about x = 0,
so a partial sweep must render a left-right symmetric frame. Bilateral 0.0055 and quadrant
0.0059 against **0.9861 and 0.8347** with the mirror replaced by a modulo, with the
symmetric and 360 files unmoved either way as controls.

### "Nothing refuses it" was the defect, not the design

The note above said an area panel's profile index is inert because it never reaches the
LTC branch. True in `pbr_frag`. False in `contact_shadow_frag`, which folds the angular
term into the **denominator** at :318 and only skips panels at :332 — so a profiled panel
was weighted by a distribution its shading never applies. That is the identical error
11.56 fixed and measured at 23% on a pixel that should lose 1%. Refused now at authoring
and again at pack, so the invariant every shader relies on is true by construction.

### Three more the spec asserted and did not test

- **A profile REPLACES the cone.** Stated here, in `froxel_inject_frag`'s comment and in
  `ies-shape`'s docstring. `assets/ies_fixture.cscn` authors a **point** light and
  `spotConeFactor` returns 1.0 for every non-spot, so multiplying and replacing were
  byte-identical on every arm in the group. `ies-replace` renders two spots differing only
  in cone: 0 px, and 340,926 px when falsified.
- **The tail is exactly zero.** `lobe()` returns a literal 0.0 at 90 degrees, so
  `0.0 / peak` is already exact and the snap enforcing it was never what was measured —
  deleting it from both readers left everything green. `ies_tinytail.ies` carries 1.2e-6 cd
  there, and now deleting the snap turns `ies-table` red.
- **`punctualAngular` is the one place the falloff is decided.** Four of the five sites
  went through it; the fog's spot shaft — the one the comment named — restated the rule as
  its own ternary. Split into `punctualAngularOf` (values) and `punctualAngular` (the
  cluster-list adapter) so the claim is true.

### Defects the review found that no arm could have

- `iesProfile` answers **1.0** out of range, the neutral for a multiplier, consumed as a
  replacement — so a stale index made a light an unbounded omnidirectional emitter that
  could never return exact zero, taking `pbr_frag`'s early-out with it. Reachable because
  the upload keyed on profile **count**, on engine-owned state, against a scene-owned
  library: two scenes with one profile each never re-uploaded. Keyed on a revision now.
- `shadow.c` open-coded `light_cluster.c`'s Gram-Schmidt for the fog spot's roll and
  **diverged at the degenerate case**, producing a NaN where the cluster path substitutes
  −Y. Five of the eight agents found this one independently. Both call `light_emission_frame`.
- A `.cscn` could not aim or roll a profiled point light: `direction` was read behind a
  type test excluding point, `up` only inside the area branch, and both sit in `known[]`
  so `warn_unknown_keys` — added by this very spec to end exactly that failure — stayed
  silent. The fixture's own light is the case.
- The C reader and the reference tool already **disagreed about TILT**: `strstr` anywhere
  against line-anchored, case-sensitive against folded, prefix against equality. Drift
  present at merge, invisible because the fixture feeds both only well-formed files.

### What was right and is recorded as such

`light_cull_radius` was correctly **not** given the peak term this spec's design section
booked for it: the table is normalised to peak 1 and multiplies `intensity`, so the
existing solve already bounds it and the function stays pure. Two agents checked
independently. The 16 KB block at its own binding, the `attenCutoff.y` index convention,
and `gates.py` restating the closed form rather than importing the generator (which would
make ground truth a function of the thing under test) all survived scrutiny unchanged.

### Reading

24 goldens 0 px, all 43 gate groups green. The `ies` group is six arms, up from four.

## Follow-up: `--ies-profile`

Added after the review round, from use rather than from a report. The feature shipped with a
`.cscn` as the **only** way to attach a profile, which meant the four fixture files could not
be looked at without hand-editing a committed asset — and that is not a fixture problem, it is
the actual workflow: what you want to do with this is point the renderer at a manufacturer's
`.ies` on a scene you already have.

`--ies-profile <file>` applies one to every point and spot light, overriding whatever the scene
authored. It runs after `apply_cscene_light_overrides`, so the flag wins, in the same direction
as `--no-water` over an authored `water{}` block. Directionals and area panels are skipped for
exactly the reason they refuse an authored profile, which is what makes it safe to point at a
mixed scene: the practicals take it, the sun and the softboxes do not.

Same intensity rule as the authoring path — a light still at the fallback takes the file's peak
candela, since normalised x peak IS absolute and a correct shape at 1 cd is unusable.

`ies-flag` reads three things, and the middle one is the point:

| read | want | falsified (loaded, never applied) |
|---|---|---|
| against the same file **authored** in the `.cscn` | 0 px | 340,030 |
| against the file it replaced | > 0 | **0** |
| on `contact_local_fixture`, which authors no profile at all | > 0 | **0** |

The 0 px is the reading that matters: the flag and the scene-file path are not two paths that
agree, they are one path reached two ways. And the falsification is the failure the arm exists
for — loading a profile into the scene's library while applying it to no light prints an
identical `--ies-probe`, because the library is scene state and loading is not applying. An arm
reading the probe would have passed.
