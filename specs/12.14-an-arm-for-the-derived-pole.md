# Spec 12.14 — an arm for the derived IK pole

## Context

Spec 12.11 changed which way a knee bends. `ik_add_foot` had taken the bend direction from
its caller — `knee_forward`, a vector in the HIP's frame — and every caller in the tree passes
the `+Z` that suits the generated puppet. On a rig whose thigh binds 178° away from that one,
the same vector points backwards and the knee folds under on every stance frame, with every
chain resolved and nothing warning. So the pole is now taken from the RIG: the perpendicular
part of the bind knee's offset from the hip–ankle line, rotated into the hip's bind frame,
with `knee_forward` kept as the fallback for a rig that binds straight.

**That change has no instrument.** `ik-pole` — the one arm that reads the pole at all — runs
on the generated puppet, whose three leg joints share one x and one z *to the digit*. Its bind
knee sits exactly on the hip–ankle line, so it takes the FALLBACK path, and every number the
arm prints is the behaviour that existed before 12.11. Deleting the derivation entirely leaves
all 21 `ik` arms green.

**Outcome: the derivation is asserted by an arm that fails against the code it replaced.**

---

## AMENDED — the fixture this plan was going to build already exists

The first version of this plan built a bent-knee variant of the generated puppet. Exploration
retired that, for two independent reasons. Both are recorded because the first draft was wrong
in a way worth not repeating.

**1. `assets/models/t_pose.fbx` already binds bent — and binds its hip ROTATED.** Read
straight out of the binary FBX's `Properties70` for the leg chain:

| | |
|---|---|
| thigh / shin | 44.371 / 44.528, hip→ankle span 88.835 |
| knee perpendicular offset | **1.694, a ratio of 0.01907** against `IK_POLE_BEND` 0.01 |
| knee bend | 4.37° forward, pole direction ≈ `(0, −0.03, +0.9995)` |
| hip bind rotation | **non-identity** — 0.74° X on the hips, 1.19° X and 180° Z on the thigh |

So it exercises the derivation *and* the rotation into the hip's bind frame — the half the
first draft explicitly filed as out of scope because the puppet's hip binds unrotated and a
wrong conversion would pass. It is already committed and already the 12.11 retarget source.

It also closes a gap `docs/verification.md:517-533` states in its own words — *"What no suite
here covers is a real rig"*, listing a rig *"whose rest pose is not identity"*.

**2. The generator variant was never the small edit this plan claimed.** "Only the two knee
rows of the `BONES` table move" was wrong. Everything from `gen_puppet_fixture.py:90` to the
end is module scope, and `_chunks` (:308) and `accessors` (:324) are module-level lists that
closures append to — a second variant in one process shares one buffer and one accessor list.
Emitting one properly means the `gen_cornell_rooms.py` refactor: a local `emit()` that builds
buffers, accessors and the `gltf` dict inside itself, called once per variant.

(A related detail that made the first draft's reasoning shakier than it looked: the mesh is
built from `BONES` columns 3–4, `centre` and `half`, **not** from `BIND` — so moving a joint
does not move its box. The z-symmetry assert would not have fired, but the fixture would have
carried a bind knee off the line with its geometry left behind.)

## GATE — one command, and it decides the approach

```bash
./out/bin/gametest --puppet assets/models/t_pose.fbx --ik-probe pole
```

- **`span` collapses toward 0 and `back` comes out POSITIVE → proceed.** The derived pole beat
  both stated vectors.
- **`span` stays near 0.36 with `fwd`/`back` opposite in sign → STOP.** The rig fell back, the
  ratio did not survive import, and the generator variant is back on with its true cost.

**Why this is not a formality.** The 0.01907 ratio clears the 0.01 threshold by only about
**2×**, and it was computed from raw FBX properties — *before* assimp's `$AssimpFbx$` node
splitting and the unit/axis conversion at import. Whether it still clears after
`skeleton_compute_bind_globals` accumulates the imported chain is a measurement, not a
deduction.

---

## The assertion

**Reuse `--ik-probe pole` completely unchanged.** It already registers the foot twice with
opposite `knee_forward` (`+Z`, then `−Z`) and reports each resulting knee-z plus the span. The
rig is the only new input.

| | straight puppet (`ik-pole`, today) | `t_pose.fbx` (`ik-pole-derived`, new) |
|---|---|---|
| `fwd` (caller says `+Z`) | +0.1786 | positive |
| `back` (caller says `−Z`) | −0.1786 | **positive** |
| `span` | 0.3573 | **≈ 0** |

`back` is the load-bearing cell: it flips sign. Against the pre-12.11 code the same run gives
two opposite knees and a wide span, so the arm is red.

Note t_pose's derived pole points **+Z**, which happens to agree with the caller's default — so
unlike the `−0.06` fixture the first draft designed, agreement rather than disagreement is what
is being read. The span collapsing plus `back` flipping is what carries it; a sign test on
`fwd` alone would be vacuous here. **Take the bars from the gate's measured numbers**, not from
this table.

## The plumbing

`gametest --puppet <rig> --ik-probe pole` **works today with no C change** — `--ik-probe`
dispatches after the parse loop (`gametest.c:6480`) and `run_ik_probe` reads the global
`puppet_path` (`gametest.c:133`), loading it with `create_scene_from_model_path`.

On the Python side `_gametest_probe_text` already takes an `extra` list (`gates.py:14814`), but
the `_gametest_probe` wrapper does not pass it through and `_ik_probe` is `@functools.cache`d
on the case alone. Rather than thread an argument through a memoised helper seventeen call
sites share, give the one t_pose call its own small uncached runner beside `_ik_probe_run`.

## Verification

```bash
python3 scripts/gates.py --only ik     # the new arm, and the existing 21 printing IDENTICAL digits
python3 scripts/gates.py --only anim   # anim-retarget reads t_pose as a retarget SOURCE
python3 scripts/goldens.py --only puppet   # 0 px
```

The existing 21 `ik` arms must be digit-identical: nothing about the generated puppet changes,
and it takes the same fallback path it always did.

**The arm must be FALSIFIED, not just seen to pass.** Stub the derivation back out — make
`ik_add_foot` always take `knee_forward` — and confirm `ik-pole-derived` goes red while
`ik-pole` stays green. An arm for a fix that passes against the code the fix replaced is the
whole thing this spec exists to prevent, so this is the deliverable rather than a formality.

Cost to note: this arm imports an FBX through assimp where every other `ik` arm loads a
generated glTF, so it is the slowest in the group and the only one whose input is not stated in
a table a reader can check. That is the price of testing the real path, and it is the right
trade here — but it is a reason to keep it to ONE arm rather than pointing the rest at t_pose.

## Out of scope

- **A bent generated fixture.** Retired above. Worth revisiting only if the gate fails, or if a
  later spec wants a bend whose exact numbers are stated in a table rather than imported.
- **Re-measuring the refused extension soft-clamp.** `docs/foot-locking.md` records the refusal
  as *"a property of a bind pose that is exactly straight, not of the method"* and asks for a
  re-measure *"on a rig that binds bent"*. t_pose is one — but that is a question about IK
  behaviour, not about this arm.
- **Pointing the other `ik` arms at t_pose.** They assert the solver's arithmetic, which the
  bind pose does not change, and each would pay the import cost.
