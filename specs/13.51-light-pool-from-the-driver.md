# 13.51: the light index pool sized by the driver -- 64 KB where it is allowed, 16 KB otherwise

## Context

In silent's hall a hard horizontal line crosses the far door, and it moves when the player steps
forward or back. The cause is the clustered-light index pool overflowing. Every froxel's light list
lives in one uniform buffer of 16,384 one-byte slots, sized to the 16 KB GL 4.1 guarantees. The
slots are handed out froxel by froxel, nearest slice first, and once they run out every later froxel
gets an empty list. At the reported camera the view needs 18,270 slots. The pool runs dry at slice
13 (5.0 to 7.2 m), row 5, column 3, so the tile rows above 3/8 of the screen lose all their local
lights.

Spec 13.6 (`569ced13`) grew the pool to 16 KB and measured four views at 10.1k to 12.8k. Between
Oct 5 and Oct 8 the player's house gained six lights within a few metres of this hall, and the
overflow came back. Nothing reported it: the warning prints once a session, during load, when the
kitchen tubes have no range yet, so it blamed `tube_window` at radius 144.

A probe of this Mac (Apple M1 Max, GL 4.1 on Metal) reports `GL_MAX_UNIFORM_BLOCK_SIZE = 65536`.
GL guarantees only 16384. So the pool is sized at startup from what the driver allows, at most
64 KB (65,536 slots), with 16 KB as the floor. It needs no texture slot, and the grid word's 20-bit
offset field already holds 65,536. It is still a cap. Running out would take, on average, more than
21 lights reaching every froxel in view.

The overflow warning also changes: it fires each time an overflow starts, not once per session.

## Design

**One process-wide size, read once.** The GL context is per process, and the two places that need
the size have no Engine in hand: `create_shader` (shader.c) and `ubo_wire_blocks` (ubo.c, called
from `setup_program_uniforms`). So the size lives in `ubo.c` behind two calls:
- `ubo_limits_init()` reads `GL_MAX_UNIFORM_BLOCK_SIZE`, caps it by the env lever `CETRA_UBO_LIMIT`
  (bytes) when that is set, clamps it to [16384, 65536], and floors it to a 16-byte row.
- `ubo_cluster_indices_block_size()` returns the result. Before init it answers 16384, the
  guaranteed size.

`engine.c` calls init beside the sampler-budget read (~line 582), which comes before the light
cluster context (~line 1113) and before any program is built (~line 1850). It logs one line:
`Uniform blocks: driver allows %d bytes; light index pool %d slots`.

**Shader side: a spliced define, with the safe default in the chunk.**
- `include/lights_ubo.glsl` declares `uvec4 lightIndices[CETRA_CLUSTER_INDEX_ROWS];`, behind an
  `#ifndef` default of 1024 (16 KB). An unspliced source is the guaranteed size, never one a driver
  could refuse.
- `create_shader` runs every source through the existing `shader_source_with_defines`
  (shader.c:36), splicing `#define CETRA_CLUSTER_INDEX_ROWS <size/16>` after `#version`. It is
  inert in shaders that do not include the chunk. It splices into every source because an app's
  late surface or hook can reach `lights_ubo.glsl` through the runtime include resolver.
- The function's `#line 2` keeps every body line number. Splicing on top of a pbr variant's own
  define block is safe, since each splice resets the line count.
- `ubo_wire_blocks` validates `ClusterIndexBlock` against `ubo_cluster_indices_block_size()`
  instead of the constant. A source that somehow missed the splice then fails loudly as a layout
  mismatch, not as silently wrong lights.

**C side: storage at the most, capacity from the driver.**
- `light_cluster.h`: `LC_MAX_CLUSTER_INDICES` becomes 65536, the static storage of
  `GpuClusterIndexBlock`. `UBO_CLUSTER_INDICES_BLOCK_SIZE` becomes `UBO_CLUSTER_INDICES_BLOCK_MAX`
  (65536), and the existing static asserts follow it. The 20-bit offset assert still holds.
- `LightClusterContext` gains `uint32_t index_capacity`, set in `create_light_cluster_context` from
  `ubo_cluster_indices_block_size()`. The UBO is created at that size.
- `_assign_index_offsets` clamps against `index_capacity`, not the constant. The upload at
  light_cluster.c:879 already sends only the live prefix, so it needs no change.

**The capture key folds the pool size.** A reflection-probe capture that overflows at 16 KB and
fits at 64 KB comes out differently. So `capture_key.c` folds the capacity beside the driver
strings (~line 94); otherwise a cooked column baked under the env lever would be found under the
default.

**The warning fires per episode.** `warned_index_overflow[2]` is replaced by an episode state per
kind (camera, capture):
- An overflow that starts while the kind is armed warns. The text keeps its current shape and adds
  the demand and the pool size ("needs N of M slots").
- The kind re-arms after the pool has fit for `LC_OVERFLOW_REARM` (120) consecutive builds of that
  kind, so a camera hovering at the edge cannot fill the log.

     continuing.
   - Then a per-pass `--profiler` A/B, default against the 16 KB lever, each run twice for its noise

     `overflowed`. Under the lever the indices stop at 16384 and the warning prints.

     removed), then the mutation is reverted.
