# E5 — Instanced submission, shadow culling, and LOD chains

## Context

**Wall 2 (`docs/aaa-rendering-roadmap.md:557-564`), taken with E4's instrument in hand.** One draw per
mesh, issued in scene-traversal order; culling is a per-mesh AABB test in the camera passes and
nothing at all in the shadow pass; no LOD; no instancing outside `particle_renderer.c`. Every Track D
item that adds *objects* rather than *pixels* runs into this, and D4 Terrain is hard-blocked on it.

The intended outcome is that the renderer stops paying per-object costs that scale with object count
rather than with what is on screen: repeated meshes submit as one instanced draw, the shadow pass
culls against the volume it is already computing, and dense meshes carry simplified index ranges
selected by screen size.

## What measurement established, before any code

E4 shipped `--profiler`. Running it against the repo's only many-object scene corrected this
plan's premise twice, and both corrections are load-bearing.

**The target scene.** `assets/abandoned_window/abandoned_window.glb` — 553 mesh-bearing nodes, 71
distinct meshes, 15 materials, and **483 nodes referencing the same 19-vertex / 18-triangle
`IvyLeafMesh`, all sharing one Material**. `import.c` does not deduplicate geometry, so that is 483
`Mesh` structs, 483 VAOs, and 483 `glDrawElements` calls of 54 indices. It is determinism-grade
(`CLAUDE.md`, 0 px pairwise since 11.2).

**`opaque` is pixel-bound, not draw-bound.**

| resolution | pixels | `opaque` GPU |
|---|---|---|
| 200x150 | 30k | 1.399 ms |
| 800x600 | 480k (16x) | 15.551 ms (11.1x) |
| Retina default | ~4x of 800x600 | 61.316 ms (3.9x) |

So instancing has **at most ~1.4 ms of GPU time** to win on this scene at the operating point where
the CPU signal is visible. Anyone reading only the Retina row would conclude the opposite.

**The CPU submission cost is real, and smaller than first claimed.** Culling every mesh with a far
camera, which leaves resolution, fog, particles and the whole post chain intact:

| run | `opaque` | TIMED | FRAME (wall) | residual |
|---|---|---|---|---|
| base, x3 | 1.316 / 1.323 / 1.371 | 9.612 / 9.673 / 9.701 | 16.531 / 16.539 / 16.688 | 6.92 / 6.87 / 6.99 |
| all 553 culled | 0.000 | 5.496 | 8.947 | **3.45** |

Wall drops 7.64 ms while TIMED drops 4.12 ms, so **~3.5 ms is non-GPU work attributable to ~1,660
draws — about 2.1 us of CPU per draw.** An earlier draft of this plan said 11 us/draw; that compared
two different scenes and charged the difference to draw count. **Withdrawn.** A subsequent claim that
the residual is pure GPU idle and instancing has no measurable win is also wrong — it rests on runs
taken while three agents rendered concurrently.

**Run-to-run noise is 0.9% on TIMED and 4.2% on `opaque`** (the three base runs above, quiet
machine). A perf arm is therefore viable; `gpu-scale`'s existing 20% band sits well above this floor.
Measure on a quiet machine or the floor is meaningless.

**The fixture has no shadow casters, so no shadow-pass number in this repo has ever been measured.**
`import.c` never sets `cast_shadows`; `light.c:42` defaults it false; `abandoned_window.cscn:14-32`
declares one point light that does not ask; `CSceneLightOverride` (`cscene.h:75-83`) has no field
that could turn it on. `update_shadow_system` returns at `shadow.c:1202` and no `shadow cascades` row
has ever appeared for this asset. **The pass that walks the whole graph once per cascade per caster,
with zero culling, is unmeasured on every asset in the tree.** Fixing that is a prerequisite, not a
finding.

## Design

Seven phases, each a separate commit that ships alone and has at least one arm that can fail for the
reason it claims. **Phases 0-2 are the irreducible core** and are byte-identical by construction.

### Phase 0 — the instrument, and a fixture that runs the shadow pass

`GL_TIME_ELAPSED` cannot see the 2.1 us/draw. Two additions:

**A CPU column on the existing scopes.** `ProfilerScope` (`profiler.c:21-28`) gains
`double cpu_t0, cpu_accum_ms; int cpu_samples; float cpu_shown_ms`. Bracketing is *unchanged* — the
same 41 `scope_begin`/`scope_end` sites, no new call sites, and the two costs that matter (`opaque`,
`shadow cascades`) are already inside scopes. Clock is `glfwGetTime()`, following `sky.c:376`.

Reported as a **second stdout table**, `===== CPU TIMING =====`, same `%-28s %8.3f ms` row format. The
GPU table stays byte-identical so `_GPU_ROW` (`gates.py:2310`) and every existing `gpu-*` arm keep
working. A merged two-column table was rejected: it breaks `gpu-parse`, and an arm that fails for a
format change it caused has stopped measuring the renderer.

> Caveat for the spec prose: CPU-in-scope includes driver backpressure — a `glDrawElements` can block
> when the command queue is full, charging GPU time to the CPU column. This is why every CPU claim
> below is pinned to `-W 200 -H 150`, where the frame is not pixel-bound.

**Submission counters, owned by the profiler.** `meshes_seen`, `meshes_culled`, `draws`,
`instances`, `program_switches`, `material_switches`, incremented at the two scene-mesh draw sites
(`render.c`, `shadow.c`) and zeroed in `profiler_begin_frame`, which is the actual frame top.

They live on `Profiler` rather than on `Scene` because every consumer is gated on the flag, so
collecting them unconditionally would charge the default path for something nothing could read —
and because it makes the NULL check at each increment a live gate rather than an unreachable
branch. One row table drives both the stdout block and the HUD, so adding a counter is one edit
rather than three lists that can silently disagree.

**Renamed while doing this.** The module measured GPU time when 11.27 built it; it now measures
GPU time, CPU time and submission, so `gpu_profiler.[ch]` became `profiler.[ch]`, `GPUProfiler`
became `Profiler`, the HUD header "GPU Timing" became "Profiler", and `--gpu-profile` became
`--profiler`. The stdout banners stay `GPU TIMING` / `CPU TIMING` / `SUBMISSION`, because those
name sections rather than the instrument, and the first is a gate assertion surface.

**These integers, not the milliseconds, are what the gates assert.** An integer has a noise floor of
exactly zero, which is the only honest answer to a suite documented as flaky
(`specs/11.26:250-259`). Milliseconds are reported for humans.

**`cast_shadows` in `light_overrides`** — three lines in `cscene.c` + the field, so any `.cscn` can
make an imported light cast. Then a sibling `assets/abandoned_window_shadowed.cscn` loading the same
GLB with a casting sun, leaving the determinism-grade original untouched.

> That sibling is a copy of a 113-line file differing by one key, and `.cscn` has no include
> mechanism, so an edit to the original silently makes the pair render different scenes. Accepted
> because no arm compares the two against each other — each is compared against itself across
> builds — and because the shadowed variant exists to measure real content, not to match. If an
> arm ever does compare them, derive it instead, the way `scaled_copy` already derives a .cscn.

**`assets/gen_instancing_fixture.py` + `instancing_fixture.cscn`** — following
`gen_dir_shadow_fixture.py`'s discipline. One 12-triangle mesh referenced by **130 nodes** on a grid
(deliberately spanning more than two 64-instance chunks), one shadow-casting directional, a fixed
camera. Exact instance counts to assert against.

| arm | asserts | catches |
|---|---|---|
| `submit-parse` | every block parses; 0 unreadable rows across GPU, CPU and SUBMISSION | a shifted format failing as itself, not as passes that appear to have vanished |
| `submit-sum` | `meshes_seen == instances + meshes_culled`, exactly | a miscounted early-out. Written on **instances**, not draws: batching makes one draw carry many meshes, and an invariant a later phase breaks is not one |
| `submit-count` | `draws == instances == 131 x (1 + 3 cascades) = 524` | a pass that stops drawing or double-counts |
| `submit-cull` | far camera: `meshes_culled == 131`, `draws == 393` (shadow only, which has no cull yet), `opaque` GPU < 0.01 ms | a counter wired to the node list rather than to submission — that one would not move at all |
| `submit-exact` | two runs of one build report **identical** integers | a counter that is frame-phase dependent, i.e. cannot carry a claim |
| `cpu-attrib` | some row reads exactly 0.000 ms GPU and > 0 CPU | the CPU column wired to the same clock as the GPU one. Structural, not statistical: `GL_TIME_ELAPSED` does not count `glBlitFramebuffer` on this driver. SKIPs rather than fails where no such row exists |

`submit-cull` is load-bearing: without it every other arm passes against plausible constants.

**Two arms from this plan did not survive contact and are recorded rather than quietly dropped.**
`cpu-attrib` was specified as "`opaque` CPU exceeds `opaque` GPU" — measured 0.992 ms against
1.316 ms, because that pass is pixel-bound. The premise was wrong, not the code. And an
`instances == draws` arm was written, then deleted as a tautology: both were incremented on
adjacent unconditional lines, so it could not fail. `submit-count` carries the half that can.

#### What Phase 0 measured

The CPU column closes the gap this plan opened with. On `abandoned_window_shadowed` at 200x150,
**TIMED went from a fraction of the frame to 22.348 ms of a 23.880 ms wall frame — 94% accounted
for.** The residual the Context section could only bound is CPU time, and it is now itemised:

| row | GPU | CPU |
|---|---|---|
| `shadow cascades` | 0.699 ms | **7.109 ms** |
| `opaque` (553 draws) | 1.316 ms | 0.661 ms |

**The shadow pass costs ten times more on the CPU than on the GPU**, and it is the largest single
CPU row in the frame. That is the pass with no frustum culling, walked once per cascade.

Per draw that is 1.2 us in `opaque` against 4.3 us in the shadow pass, and the difference is NOT
established as submission cost: the shadow pass runs first in the frame and absorbs backpressure
from the previous frame's GPU work, which the header names as the CPU column's one confound.
**Phase 4 is the experiment.** If culling removes draws and the row falls in proportion, the cost
was submission; if the row holds while the draws go, it was waiting. Either answer is worth having
and the plan does not depend on which.

Counts on the same scene: 2708 seen, 57 culled, 2651 drawn — and 2651 - 992 = 1659 = 553 x 3, the
cascade multiplier, exactly.

### Phase 1 — redundant state elimination (byte-identical, no flags)

A flag whose off-path is indistinguishable from its on-path is an untestable flag. All three of these
are provably no-ops in output.

**1a. Uniform value cache.** `UniformBinding` gains `float value[16]; unsigned char count, valid`.
Each `uniform_set_*` (`uniform.c:162-202`) compares and early-returns on a hit. Sound because uniform
state is per-program-object state in GL and survives `glUseProgram`, and no program here is ever
relinked in place.

*The one real hazard, fixed structurally.* Eleven sites write raw `glUniform*` for ranged array
uploads the setters cannot express (`render.c:88/97/122/931`, `shadow.c:390/393/452/464`,
`postfx.c:1811/2164/2168/2171`). If a uniform were ever written both raw and cached on one program the
cache would go stale silently. Today none is — but that is a convention, not an invariant. Make it
structural: every raw site obtains its location through `uniform_location()`, so **have that public
function mark the binding dirty**, with an internal non-dirtying lookup for the setters. Ten lines,
and it survives someone adding a raw site later, which is the actual failure mode.

Expected win: five of the 9-11 per-mesh uniforms are identical across all 483 ivy leaves
(`lineWidth`, `uWindMaskMinY/MaxY`, `vertexColorExists`, `texCoords2Exists` — all read off the shared
`Mesh`), plus the ~110 per-program-switch uploads that the OIT sub-pass resets
(`render.c:989/1019/1036`) currently re-issue unchanged four times a frame.

**1b. VAO bind coalescing.** `render.c:558-560` and `shadow.c:604-606` bind *and unbind* per draw.
Track `current_vao` beside `current_program`/`current_material`, bind on change only, drop the
`glBindVertexArray(0)`, restore once per pass. Halves VAO traffic now; **collapses 483 binds to 1 after
Phase 2**, so the two must be measured jointly as well as apart. `_render_xyz` (`render.c:571`) must
update the tracked value.

**1c. Node-cached normal matrix.** `glm_mat4_inv` + `glm_mat4_pick3t` runs per mesh *per pass*
(`render.c:520-524`) — up to 553x4 mat4 inversions a frame for a value that changes once. Add
`mat3 normal_matrix` to `SceneNode`, computed in `apply_transform_to_nodes` (`scene.c:794`), the sole
writer of `global_transform`.

**1d, which the plan did not have: the shadow walker gets a material block.** It had none — the
scene walker guards its whole material upload on `state->material != mat`, and the depth walker
re-issued `alphaTested`, `alphaCutoff`, `tsmOpacity`, `tsmHasAlbedo`, the albedo bind, `uWindResponse`
and `uWindMode` per *mesh*, all seven of them material-derived. Behind one pointer compare they
become per material: on the ivy scene that is ~7 x 553 x 3 uploads a frame collapsing to ~7 x 15,
and it is the single largest item in the phase.

It arrived by a wrong turn worth recording. The first attempt was a `GLuint albedo_tex` field on
the tracker, aimed at the texture rebind alone. That was the same idea one level too low: every
other field in `SubmitState` is an identity key covering a block of work, and a single texture name
beside them invites "then where are the other five textures?" — a question with no answer, because
the real gap was the missing block, not the missing field.

**Verified, not assumed:** `mat` can no longer be NULL inside the walk. A mesh with no material is
now skipped, matching `_render_node`, which already refused to draw one — so NULL is free to mean
"no material claimed" in the tracker, which it could not while a NULL-material mesh was a legitimate
thing to upload. Three defensive `mat &&` guards collapsed with it.

| arm | asserts | catches |
|---|---|---|
| goldens + raiden | all 21 and the skinned recipe **0 px** | a guard skipping a write it should have made |
| `tsl-*` (existing) | the analytic translucent-shadow stack unmoved | the material block changing what a caster uploads |
| full gate suite | all arms | the walkers' restructure anywhere it is visible |

A planned `uniform-dirty` arm was **dropped**, not shipped weak: a gate cannot toggle a uniform
mid-run headlessly, and the `--render-scale-at` substitute could not be made to fail for the reason
it claimed. `specs/11.27:189` sets that bar and 11.26 shipped two arms that missed it.

#### What Phase 1 measured, and the one number that was the instrument's own fault

Three runs each, quiet machine, `abandoned_window_shadowed` at 200x150:

Both endpoints re-measured on a QUIET machine after the review round, three runs each, because the
first pass was taken while review agents rendered concurrently and the earlier figures carried their
load. `abandoned_window_shadowed` at 200x150:

| | Phase 0 | Phase 1 + review fixes | delta |
|---|---|---|---|
| `shadow cascades` CPU | 7.040 ms (spread 2.1%) | **5.781 ms** (1.9%) | **−17.9%** |
| `TIMED` | 22.543 ms (6.6%) | **20.275 ms** (1.3%) | **−10.1%** |
| `FRAME (wall)` | 23.860 ms (6.4%) | **21.232 ms** (2.3%) | **−11.0%** |

The material block is the largest single contributor; 1a, 1b and 1c together are less. 1a's share is
measured directly rather than inferred: a build-time toggle over six alternating runs puts the value
cache at **−0.213 ms on the shadow pass and −0.659 ms on the frame**, against 0.092 ms/frame spent on
its own compares — earning about 7x. Its hit rate is **66.3%** over 400 frames, and
`model`/`uPrevModel`/`uNormalMatrix` are 30% of all sets but 85% of all misses, which is why no
special case for them is worth a branch.

An intermediate measurement showed `FRAME` **rising** to 24.37 ms. Not noise and not the renderer: a
debug assert added during review — `glGetIntegerv(GL_CURRENT_PROGRAM)` per uniform set, thousands of
GL queries a frame — cost about 6% of the frame in the debug build this project builds by default. It
is retained behind `-DCETRA_CHECK_UNIFORM_BINDING=1` rather than `NDEBUG`, because an audit that is on
by default would make every timing after it wrong by more than the work it measures. Swept once with
it on across 23 scenes x 6 flag variants plus the capture paths: **zero violations.**

**The ceiling this phase found, which matters more than the win.** Sampling shows the Apple GL driver
copying the *whole program uniform block* at draw time (`GLDContextRec::setRenderProgramUniforms` ->
`_platform_memmove`). `model` changes every draw, so the block is dirty every draw no matter how many
uniforms the cache skipped. **No CPU-side value cache can reach it; only moving transforms into a
buffer can**, which is Phase 5.

> **Read every percentage here as a Debug-build number.** This project's default preset compiles with
> `-g -Wall -std=gnu11` and **no `-O` flag at all**, and cetra's own code is 5-13x cheaper at `-O3`
> while the driver's is not. Re-sampled in release: the driver's block copy holds at **11.8%** and is
> unambiguously dominant, but `uniform_binding`'s `HASH_FIND_STR` falls from 4.7% to **0.88%**, and
> `apply_transform_to_nodes` from 1.14% to 0.086%. An earlier draft of this section called the hash
> lookup "the largest non-driver symbol, an argument for interned slots" — **withdrawn**: that ranking
> is an artefact of the unoptimised build. Frame time barely moves between the two, which says the
> same thing from the other end: this workload is driver-bound, not cetra-bound.

**And a caution for the Phase 2 gate.** 1a's win and Phase 5's win are partly the same win counted
twice: collapsing 483 draws to 8 turns "483 x N redundant per-mesh writes" into "8 x N". Re-measure
rather than bank it.

|---|---|---|---|---|
| shadow cascades | 1659 | 0 | 1659 | 60 |
| opaque | 57 | 15 | 42 | 11 |
| oit moments | 496 | 21 | 475 | 4 |

### Phase 2 — mesh dedup at import

The instancing batch key *is* `Mesh*`: `Material` is a field of `Mesh`, so same mesh implies same
material implies same program. Without dedup, 483 ivy leaves are 483 distinct keys and instancing is
unreachable. This phase is a prerequisite, not an optimisation.

`Mesh` gains `int refs` (1 at `create_mesh`) and `unsigned id` (monotonic — a sort/batch key that is
**not a pointer**, since allocation order is not stable across runs). `free_mesh` decrements and
returns above zero, so every existing caller stays correct unchanged.

`process_ai_node` (`import.c:1538`) gains a `Mesh** mesh_cache` sized `mNumMeshes`, **exactly
mirroring the `mat_cache` beside it** (`:1560-1578`) — whose own comment names this case: *"one
aiMaterial can be shared by hundreds of meshes (e.g. ivy leaves)"*. `meshIndex` is already read at
`:1554` and discarded; it becomes the key.

0-px because DFS order is unchanged and `aabb`, `material`, `vao` are all functions of the aiMesh
alone, while `global_transform` still varies per node.

A scene-owned mesh pool is the architecturally correct ownership model and touches every app plus
`game/entity.c`; a borrow flag is positional and dangles. Both rejected, recorded. Assimp's
`aiProcess_FindInstances` stays unused: it merges *different* aiMeshes it judges identical, a riskier
claim than "the file already says these are one mesh".

| arm | asserts | catches |
|---|---|---|
| `dedup-identity` | `abandoned_window` + all 21 goldens + raiden **0 px** | dedup changing what is drawn |
| `dedup-count` | import reports **71** meshes for 553 mesh-bearing nodes (was 553) | the cache never hitting — the dead-feature failure |
| `dedup-leak` | `leaks` clean of any mesh-rooted allocation on load-and-exit | a refcount wrong in either direction |

#### As built

`Mesh` gained `refs` (1 at creation, so the single-node case is byte-for-byte the ownership it had
before) and a monotonic `id`. `mesh_ref` claims a share; `free_mesh` returns early above zero.
`process_ai_node` gained a `mesh_cache` beside the `mat_cache`, keyed on the aiMesh index that was
already being read and discarded.

**Measured, quiet machine, three runs each:**

| | Phase 0 | Phase 1 | Phase 2 | cumulative |
|---|---|---|---|---|
| `shadow cascades` CPU | 7.040 ms | 5.781 | **4.901** (0.9% spread) | **−30.4%** |
| `TIMED` | 22.543 ms | 20.275 | **17.435** (1.4%) | **−22.7%** |
| `FRAME (wall)` | 23.860 ms | 21.232 | **18.657** (0.8%) | **−21.8%** |

**Phase 2 alone is −15.2% on the shadow pass, more than all of Phase 1**, and the reason is 1b: the
VAO coalescing shipped in Phase 1 could not collapse anything while every ivy leaf owned its own VAO.
483 nodes now share one, so a cascade binds it once instead of 553 times. The two phases had to land
in this order for either number to exist, which is the clearest evidence in the item that the
sequencing was right.

The scene also stops building 482 redundant VAOs and their buffer sets at load. `leaks` reports no
mesh-rooted allocation, and the 395 → 417 difference between a one-mesh scene and this one scales
with shader programs rather than meshes — pre-existing program-cache leaks, not this phase's.

One consequence recorded rather than fixed: `upload_buffers_to_gpu_for_nodes` walks nodes, so a
shared mesh uploads once per holder — 483 redundant 19-vertex uploads, once, at load.

> An earlier draft of this paragraph said an `uploaded` flag "would break `apps/tree`'s
> `regenerate_grass`, which re-uploads deliberately". **Withdrawn — that is false.** `regenerate_grass`
> and `regenerate_tree` free the old mesh and `create_mesh()` a new one on every rebuild, so a
> per-mesh flag would read false every time; nothing in this tree re-uploads an existing mesh. The
> real reason to leave it is that a flag is a footgun the moment someone edits vertex data in place.
> The clean fix is the one the next phase wants anyway: register distinct meshes on the `Scene` the
> way materials already are, and upload per mesh rather than per node.

**What the importer throws away, and Phase 6 will want back.** `mesh_cache` *is* the scene's
distinct-mesh list, and it is freed three lines after it is complete — where the material dedup in
the same loop calls `add_material_to_scene` and keeps its list on the `Scene`. Everything downstream
that is per *distinct mesh* has to rebuild it: the redundant uploads above, and Phase 6's LOD
generation, which must run once per mesh and not once per holder. A borrowed `scene->meshes`
mirroring `scene->materials` is ~10 lines and is a step toward the deferred mesh pool rather than a
detour. Deliberately not done here: this phase's job was the dedup, and the consumer arrives in
Phase 6.

`Mesh.id` currently has no reader. It exists because a batch or sort key cannot be a pointer, and
Phase 3's `DrawItem` names `Mesh*` as the batch key with a DFS index for order — **if Phases 3 and 5
land without touching `id`, delete it.** `-Wall` gives no signal for an unread struct member, so
nothing else will raise it.

> **Decision gate.** If Phases 1+2 recover most of the ~3.5 ms, Phases 5-6 must be re-argued on the new
> numbers rather than shipped because the roadmap said "instancing". Recording a decision to stop is a
> legitimate outcome for this item and the honest one.

### Phase 3 — one draw list, replacing five traversals

`render_current_scene` walks the graph four times with OIT on (`render.c:845/1013/1030/1040`), each
re-running `frustum_test_aabb_transformed` over all 553 meshes; `shadow.c:496` is a *second, recursive*
walker. Build the list once, let each pass filter it.

New `cetra/src/draw_list.h`/`.c` — not inside `render.c`, because `shadow.c` consumes it and making
`shadow.c` include `render.h` is how the two walkers stayed separate in the first place.

```c
typedef struct DrawItem {
    Mesh*      mesh;          // batch key, after Phase 2
    SceneNode* node;          // gizmo + naming only; never read at draw time
    mat4       model, prev_model;
    mat3       normal_matrix;
    vec3       world_min, world_max, world_center;
    float      world_radius;
    uint8_t    lane;          // opaque / blend / transmissive / xyz
    uint8_t    flags;         // skinned, wind, double-sided, alpha-masked, caster sets
    uint32_t   seq;           // DFS index — keeps ordering total and pointer-free
} DrawItem;
```

Transforms are **snapshotted, not pointed at**, so a later graph mutation cannot change what a
half-drawn frame is drawing. 553 items is ~100 KB, grow-only and reused.

`lane` carries the existing routing from `render.c:309-325` verbatim, evaluated **once per item**
instead of 5 branches x 553 meshes x 4 passes. The three late-pass counters become range lengths
known *before* any pass draws, rather than side effects of the opaque pass's reject branch — but the
pre-cull/post-cull asymmetry (`render.c:330-342`: blend counted pre-cull, transmissive post-cull) must
be preserved exactly, since it gates the refraction resolve.

Rebuilt when `(frame_index, scene->transform_epoch)` changes, with `apply_transform_to_nodes` bumping
the epoch. Consequence worth having: `scene_capture_faces` re-entering `render_current_scene` six
times becomes six *selects*, not six rebuilds, and `gi_volume_update`'s first sweep — today 12 probes
x 6 faces x 4 sub-passes = **288 full DFS walks in one frame** — becomes one build.

**DFS order is preserved exactly**, so this phase is 0 px. `_render_scene_iterative` pushes children in
reverse and `_render_shadow_node` recurses in order; the list reproduces both.

Deletions: `_render_scene_iterative`, `_render_shadow_node`, `_ensure_traversal_stack_capacity`,
`scene->traversal_stack`, the three side-effect counters, and **`scene->traversal_transforms` — which
is already dead**: allocated (`scene.c:54`), grown (`render.c:609`), freed (`scene.c:156`), never read,
and carrying a comment that names a function which allocates its own stack instead.

Not deleted, and flagged: the `current_program = 0; current_material = NULL` resets at
`render.c:989/1019/1036` are load-bearing — texture unit 6 has two disjoint tenants (moment atlas vs
refraction source) and the reset forces the re-upload that keeps them apart (`render.c:411-421`). These
become an explicit named `submit_state_reset()` and get their own arm.

| arm | asserts | catches |
|---|---|---|
| `list-identity` | `oit_cards --no-oit`, `oit_sphere`, `hair_fixture` at **0 px** across two renders of one build | a reordering. Those three are the fixtures where order is *visible* — the unsorted late pass, transmissive over transmissive, and A2C dither. The goldens cannot serve here: they were baked from an older build, so a rebake would absorb a reordering silently |
| `list-once` | `meshes_seen` in the opaque pass equals the mesh-node count exactly, and no late pass appears on an all-opaque fixture | a pass reverting to a graph walk, or a lane filter that stops filtering |
| `oit-identity` | `--oit` vs `--no-oit` **differ** by > 0 px | the inverse arm: the lane routing collapsing to one branch. OIT routing is the one place the filter must disagree with itself between passes, so equality means it stopped |

#### As built, and what the review had to correct

**The plan's `oit-identity` was specified backwards** — "0 px with `--oit` and with `--no-oit`". Those
two configurations are *supposed* to differ (measured: 269,385 px); an arm asserting they match could
only ever have passed by the routing collapsing. Rewritten as an inverse arm.

**A use-after-free shipped in the first cut and was caught by review.** The list was stamped on the
frame index alone, so in `apps/tree` the shadow pass flattened the graph, the app's render callback
freed those meshes on a slider change, and the camera pass then drew freed memory. Confirmed both
directions under Guard Malloc: `exit=139` without the epoch, `exit=0` with it, same repro. Without
Guard Malloc it exits 0 and renders plausibly, because the freed blocks are immediately reallocated —
silent UB, which is worse.

The fix is a global monotonic graph epoch folded into the stamp. Global rather than a `Scene` field
because the mutators that matter have no way back to a `Scene`, and bumped by the mutators themselves
rather than by callers, because a rule an app must remember is a rule an app forgets. Three of the
five bump sites are ones the design would have missed: `regenerate_tree` writes `mesh_count = 0`
**directly** with no API call, so node-level bumps alone are insufficient; and the list refuses
`vao == 0`, so `upload_mesh_buffers_to_gpu` is itself an invalidation.

**Deletions the first cut left on the table**, all applied: the XYZ gizmo was a lane holding a NULL
mesh, breaking the list's own "every item is drawable" contract and forcing a skip into every
consumer — it is now a separate small array. `DRAW_TRANSLUCENT` and `DRAW_SKINNED` are gone: the
first was derivable from the lane, the second had no reader. Two of the three late-pass counts are
lane populations known at build, so only the frustum-gated one still scans. And the camera path was
still re-deriving `alpha_mode` and `doubleSided` per item while the shadow path read the flags — the
half of the phase that motivated it was unapplied on the side that motivated it.

### Phase 4 — shadow-layer culling

`_render_shadow_node` tests nothing. Each layer's `lightSpaceMatrix` **is** its coverage volume by
construction — `compute_cascade_light_space_matrix` (`shadow.c:311-369`) pushes the eye back by
`radius + scene_pad` precisely so casters outside the view slice but toward the light stay inside the
ortho box. So `frustum_extract_from_vp` on that matrix and a test per item is not merely conservative,
it is **exact**: anything rejected contributed nothing to that layer. Gribb-Hartmann is
projection-agnostic, so the same code serves the punctual perspective layers.

The existing fit was designed for a cull that was never written. This is ~15 lines on top of Phase 3
and it is the largest draw-count reduction in the item: 3 cascades x 553 meshes, plus up to 8 punctual
layers and 6 more under TSM.

Two exclusions, both correctness rather than thrift. **Skinned** items carry `NO_CULL` — their AABB is
the static bind pose (`mesh.c:134-155`), so a tight cascade box can drop an animated character out of a
shadow it should cast; the camera path already has this defect and this phase must not propagate it.
**Wind** items likewise — `windOffset` displaces vertices after the AABB was computed, and
`abandoned_window.cscn:67-72` gives the curtains `windResponse: 1.0`, so this is live content.

| arm | asserts | catches |
|---|---|---|
| goldens + raiden | all 21 and the skinned recipe **0 px** | a cull volume dropping a caster the map needs — the only way this can fail. `dir_shadow`, `translucent_shadow` and `cornell_leak` are the ones that would show it |
| `shadowcull-draws` | at 1 cascade the fit is the whole scene and the same code must cull **exactly 0**; at 3 it must cull **> 0** | a cull not attached to the light's own volume — that one rejects at both counts. The inverse arm |
| `shadowcull-live` | `abandoned_window_shadowed`: **>= 15%** of casters rejected | culling that runs and never fires. The instancing fixture cannot show this: it sits inside every cascade by construction |

#### As built

**−23.3% on the shadow pass, the largest single win in the item.** Three runs, 0.8% spread:

| | Phase 3 | Phase 4 | delta |
|---|---|---|---|
| `shadow cascades` CPU | 4.910 ms | **3.765 ms** | **−23.3%** |
| `TIMED` | 18.291 ms | **17.056 ms** | −6.8% |
| `FRAME (wall)` | 19.550 ms | **18.329 ms** | −6.2% |

**503 of 1,659 casters culled — 30% — at 0 px.**

**This settles the question Phase 0 opened.** That phase measured the shadow row at 7.1 ms of CPU
against 0.7 ms of GPU and could not say how much was submission and how much was the pass absorbing
backpressure from the previous frame, since it runs first. Phase 4 is the experiment it named:
**culling removed 30% of the draws and the row fell 23%** — near-proportional, so the cost was
submission. Had the row held while the draws went, it was waiting.

Three existing arms went red and were **correct to**: `submit-count`, `submit-cull` and the first cut
of `shadowcull-draws` all encoded "the shadow pass has no cull". They now assert what survives —
`meshes_seen` is still exactly nodes x cascades, and `draws + culled` still equals it. `submit-cull`
improved in the process: with the camera aimed at nothing, opaque draws 0 while the shadow pass still
draws 131, which says plainly that it follows the light rather than the camera.

One correction to the plan's own text: it predicted the instancing fixture would cull nothing at 3
cascades. It culls 33 of 393 — the near slices are tighter than the whole-scene fit even for a grid
that fits the view. The arm asserts the measured behaviour, and `shadowcull-live` covers the case the
fixture genuinely cannot show.

### Phase 5 — instanced draws, via a std140 UBO

Adjacent runs over the list sharing `(mesh, lod_level)` and length >= 4 become
`glDrawElementsInstanced`.

**The draw-count reduction is the visible half; the uniform block is the other one, and Phase 1
measured it.** Sampling the process shows the driver copying the WHOLE program uniform block at draw
time (`GLDContextRec::setRenderProgramUniforms` -> `_platform_memmove`, ~11% of main-thread CPU).
`model` changes every draw, so the block is dirty every draw and the copy is proportional to the
program's entire uniform footprint, not to what changed. No CPU-side cache can reach that — Phase 1's
value cache skips the `glUniform*` call and the driver copies the block anyway.

Moving the per-instance transforms into a buffer is what removes it, and it is the same move Unreal
and Godot made for the same reason: per-draw data belongs in a buffer object the caller updates and
binds explicitly, not in loose uniforms whose target is whatever is currently bound. Expect this
phase to pay twice — once in draw calls, once in that 11%.

**Not attribute divisors.** Only slots 12-15 are free (`common.h:23-27`) and GL 4.1 guarantees 16;
`model` + `uPrevModel` + `uNormalMatrix` need 11. Packing to fit requires deriving the normal matrix
in-shader, which guarantees the instanced and non-instanced paths differ in the last bits and throws
away the strongest arm available. Divisors would also mutate the mesh VAO, a shared object the shadow
pass and the fallback path also use.

**A UBO instead**, joining the registry at `ubo.h:17-20` that exists so collisions are impossible by
construction:

```glsl
#define CETRA_INSTANCE_MAX 64
layout(std140) uniform InstanceBlock {
    mat4 uInstModel[CETRA_INSTANCE_MAX];
    mat4 uInstPrevModel[CETRA_INSTANCE_MAX];
    mat4 uInstNormal[CETRA_INSTANCE_MAX];   // upper 3x3 read as mat3
};
uniform bool uInstanced;
```

64 x 3 x 64 B = **12288 bytes exactly**, identical to `UBO_CLUSTERS_BLOCK_SIZE`, so
`ubo_wire_program_block`'s validation of the driver's `GL_UNIFORM_BLOCK_DATA_SIZE` against the C mirror
applies unchanged — the guard this tree built for the clustered-light blocks and the one that catches
std140 drift. Storing the normal matrix as `mat4` costs 16 B/instance over a padded `mat3` and removes
the whole class of hand-packed-column bugs. 483 ivy leaves become **8 draws**.

Lives in `shaders/include/instancing.glsl`, following the `wind.glsl`/`skin.glsl` chunk idiom — one
declaration, two consumers, and std140 guarantees one buffer serves both. `pbr_vert.glsl:51` and
`shadow_depth_vert.glsl:30` become select-then-use so downstream arithmetic is textually unchanged:

```glsl
mat4 M  = uInstanced ? uInstModel[gl_InstanceID]     : model;
mat4 Mp = uInstanced ? uInstPrevModel[gl_InstanceID] : uPrevModel;
mat3 Nm = uInstanced ? mat3(uInstNormal[gl_InstanceID]) : uNormalMatrix;
```

**One program, not two.** A `#define`d variant adds a program switch (~110 GL calls) per batch and a
second path that can drift — and this tree has been burned by two shader files drifting apart. The
branch is uniform across the whole draw; every driver specialises it. `gl_InstanceID` is 0 for
non-instanced draws, so both paths are safe unconditionally.

Because the UBO carries the *same floats* the uniform path uploads, `--no-instancing` is a **0 px**
arm. Skinned meshes are excluded at run detection: `g_current_animation_state` (`render.c:63`) is a
single global bone set, so N instances would share one pose.

| arm | asserts | catches |
|---|---|---|
| `inst-off-identity` | all 21 goldens 0 px with `--no-instancing`, i.e. after the shader edit | the `uInstanced` select perturbing the default path |
| `inst-identity` | `--instancing` vs `--no-instancing` **0 px** on both fixtures | the UBO path computing different arithmetic |
| `inst-count` | `abandoned_window` opaque `draws` 553 -> <= 120; `instances` equals the off-run's `draws` | a dead flag, an unparsed argument, a failed UBO wire — all of which pass `inst-identity` trivially |
| `inst-inverse` | instancing off: `instances == draws` exactly; on: `instances > draws` | a fabricated counter |
| `inst-chunk` | the 130-instance fixture matches the same scene with `CETRA_INSTANCE_MAX` forced to 1000 | an off-by-one at the chunk seam — renders 64 right and 1 wrong, which no whole-frame diff against a same-chunked build can see |
| `inst-shadow` | `abandoned_window_shadowed`: shadow-scope `draws` falls by the same factor as opaque's | instancing wired into the shading traversal only |

### Phase 6 — LOD chains via meshoptimizer

Vendored at `cetra/src/ext/meshoptimizer/` with its own CMake target, as `cimgui` and `JoltC` already
are, linked **PRIVATE** since only `import.c` consumes it. C++ sources behind an `extern "C"` header,
the same shape as the existing C++ dependencies.

**LOD levels are index ranges over the same vertices.** `meshopt_simplify` produces a new index buffer
against the unchanged vertex buffer, so concatenating every level into **one EBO** and drawing with an
offset means no extra VBOs, no extra VAOs, and no VAO switching:

```c
size_t lod_offset[CETRA_LOD_MAX];   // byte offset into the single EBO
size_t lod_count[CETRA_LOD_MAX];    // index count
float  lod_error[CETRA_LOD_MAX];    // meshopt's reported error, in mesh units
int    lod_levels;
```

`glDrawElements(mode, lod_count[l], GL_UNSIGNED_INT, (void*)lod_offset[l])` — and the identical offset
works for `glDrawElementsInstanced`, so **LOD composes with Phase 5 for free**. Level 0 is the original
index data at offset 0, so a mesh with no chain is byte-identical to today.

Generated at import, after `calculate_aabb`, at a fixed error ladder; skipped for skinned meshes
(weights must transfer to surviving vertices, and errors show as tearing during animation) and for
meshes below a triangle floor. Selection is per `DrawItem` at list build, from the projected radius
already computed for culling. The batch key becomes `(mesh, lod_level)`, so instances at different
distances group separately — which is correct, and is exactly what makes distance-graded instancing
work.

`--lod-bias`, `--no-lod`, and a GUI slider, per the roadmap's flag+toggle policy (`:1025`).

> **What this will and will not do on current content, stated up front.** meshoptimizer locks mesh
> borders by default, and every ivy leaf and grass blade is nearly all border — those will simplify to
> approximately themselves, correctly and pointlessly. The only asset here dense enough to benefit is
> raiden, which is skinned and therefore excluded. **The chain is being built for content that does not
> exist yet**, principally D4 terrain and any future props. That is a defensible reason to build it and
> a bad reason to claim a win from it; the arms below prove the selector, not the beauty.

| arm | asserts | catches |
|---|---|---|
| `lod-off` | `--no-lod` and `--lod-bias 0` at the near camera: **0 px** vs a pre-Phase-6 build | a "disabled" path that isn't; a level-0 range that is not the original indices |
| `lod-monotone` | sweeping distance, the selected level is non-decreasing and `triangles_submitted` non-increasing | a threshold parsed and dropped — a failure this tree has shipped twice |
| `lod-count` | a purpose-built dense fixture reports `lod_levels > 1` and a triangle drop at distance | a generator that silently produced one level |
| `lod-skinned` | raiden recipe 0 px, `lod_levels == 1` on every skinned mesh | decimation reaching the case it must not |

## Deliberately deferred

- **Draw sorting by program/material.** The roadmap's third E5 limb, and the evidence says it wins
  nothing here: `abandoned_window` exports its 483 ivy leaves as one contiguous name-ordered block, so
  current DFS order already costs ~60 material switches in 553 draws, and no other asset interleaves
  materials at all. The list makes sorting a `qsort` on a pointer-free key whenever a fixture justifies
  it. **Shipping it now would be an unfalsifiable claim** — `sort-switches` cannot be written against
  any existing content.
- **Back-to-front transparent sorting.** OIT is on by default and order-independent; sorting would move
  `--no-oit` pixels including the raiden hair, which has moved four times already, for no measured win.
- **Nanite-style cluster DAGs.** Need compute shaders, SSBOs, `glMultiDrawElementsIndirect` and 64-bit
  atomics — all GL 4.3+, above the 4.1 macOS ceiling. Filed where the ceiling itself is, Tier 5.
- **Occlusion culling.** Its own latency story on GL 4.1 occlusion queries.
- **Instancing skinned meshes.** Blocked on the single global `g_current_animation_state`.
- **Screen-size / density culling.** Falls out of the list in a few lines once a consumer asks; no
  content demands it today.
- **Moving the transform update ahead of the shadow pass.** `render_shadow_depth_pass` runs at
  `engine.c:2231`, `apply_transform_to_nodes` inside the app callback after it — so shadows read last
  frame's transforms. A real latent one-frame lag, found here, deserving its own item and its own arm.
- **A scene-owned mesh pool.** The correct ownership model; refcounting composes with it later.
- **A `gl_use_program()` choke point, and with it a free bind check.** The uniform value cache assumes
  the setters run with their own program bound — `glUniform*` writes whatever is bound, not what the
  `UniformManager` names, so a set under the wrong program updates that one and records it here, after
  which the next legitimate write is skipped as already-held. It is verified (zero violations across
  seven scenes under `-DCETRA_CHECK_UNIFORM_BINDING=1`) but only *believed* going forward, because the
  check costs a `glGetIntegerv` per set — about 6% of the frame — and is therefore off.

  Godot and Unreal do not have this problem, and not because they assert harder: neither lets app code
  call `glUseProgram`. Both route it through one place that mirrors GL state (Unreal's
  `FOpenGLContextState`, Godot's shader-version bind path), so "what is bound" is a variable, and the
  check is a compare rather than a driver round trip. Cetra calls `glUseProgram` from ~30 sites.

  Routing them through one function would make the check free enough to run always, filter redundant
  program binds engine-wide, and **delete `SubmitState.program`** — that field exists only because
  nothing global knows what is bound. Its own item rather than folded into Phase 3: it touches every
  `glUseProgram` in the tree, and mixing it with a rewrite of both walkers gives a change nobody can
  bisect.
- **Interned uniform slots or caller-held bindings.** `uniform_binding`'s `HASH_FIND_STR` measured
  ~6.9% of main-thread CPU after Phase 1 — the largest non-driver symbol in the process. The material
  block removed a large share of the lookups; what remains wants an enum-indexed slot array or handles
  hoisted out of the draw loop. Byte-identical by construction, but it re-threads every hot call site,
  which is work Phase 3's draw list does anyway.

## Process

Per `CLAUDE.md`: branch off master, copy this plan to `specs/11.28-instanced-submission-and-lod.md`,
**commit the spec before any code**, create the task list, then implement. One commit per phase, each
with its goldens run and its arms green before the next begins — the phases are ordered so each one's
measurement informs whether the next is still worth doing.

**If it has to shrink, cut from the bottom.** Phases 0-2 are the irreducible core and a complete
deliverable on their own. Next to keep is Phase 4 (shadow culling): ~15 lines, provably conservative,
and the largest draw-count reduction in the item. Then Phase 3, then 5, then 6.
